摘要

安全支付确认（SPC）是一种用于支持简化 支付交易期间身份验证的 Web API。它旨在将身份验证扩展到 不同商家，适用于广泛的身份验证协议，并 生成用户已确认交易详情的密码学证据。

1. 引言

本节及其子节均为非规范性内容。

本规范定义了一种 API，使 Web 上的支付流程能够使用强身份验证 方法。其目标是提供与 [webauthn-3] 相同的身份验证优势和用户隐私保护，并通过增强功能满足 支付处理的需求。

与 [webauthn-3] 类似， 本规范定义了两个涉及用户的 相关流程。第一个是§ 3 注册（以前称为 “登记”）， 在该流程中，用户与依赖方之间建立关系。 第二个是§ 4 身份验证——安全支付确认支付 方式，在该流程中，用户响应 依赖方的质询（可能通过中间支付服务 提供商）， 以同意某笔特定支付。

本规范的目标之一是减少 结账期间的身份验证阻碍，其中一个方面是尽可能增加 用户通过一次注册能够完成的身份验证次数。也就是说，在获得 依赖方同意的情况下，理想情况下用户可以“注册一次”，然后 在任何商家源上（以及通过支付服务提供商）进行身份验证， 而不仅限于用户最初注册的商家源。

为此，安全支付确认的一项重要功能是 商家（或其他实体）可以代表依赖方发起身份验证流程。依赖方 必须 在创建凭据时选择允许此行为。

从功能上讲，本规范为 支付方式定义了一种新的 PaymentRequest API 支付方式，并添加了一个WebAuthn 扩展，以扩展 [webauthn-3]， 增加支付专用的数据结构和设备绑定功能，并 放宽相关假设，使该 API 能够在支付上下文中被调用。

1.1. 使用场景

尽管 [webauthn-3] 为 Web 提供了通用的身份验证功能， 但以下使用场景说明了本规范定义的支付专用 扩展的价值。

我们假定，基于密码学的身份验证在 在线交易中的一般使用场景已经得到广泛确立。

1.1.1. 交易 确认的密码学证据

在许多在线支付系统中，发行支付工具的实体（例如银行） 通常会寻求通过身份验证来减少欺诈。 [webauthn-3] 和本规范使得可以使用身份验证器， 对商家源以及交易金额和货币等重要的 支付专用信息进行密码学签名。随后，作为 依赖方的银行可以验证已签名的支付专用 信息， 并将其作为决定是否授权支付的依据之一。

如果银行使用普通的 [webauthn-3]， 则需要验证的支付专用信息 必须存储在 WebAuthn 的 challenge 中。 这会引发以下几个问题：

  1. 这是对 challenge 字段的误用（该字段本来用于防止重放 攻击）。

  2. 对此没有相应的规范，因此每家银行可能都必须 自行设计支付专用信息在质询中 格式化和编码的方式，从而使部署更加复杂，并 加剧碎片化。

  3. 法规可能要求提供证据，证明用户已经看到并同意 支付专用信息。普通的 [webauthn-3] 并未提供 此类显示机制：对于存储在 challenge 字段中的信息，没有规定相应的用户体验。

这些限制促使安全支付确认采用以下行为：

  1. 与普通的 [webauthn-3] 一样，challenge 字段仅用于防止重放攻击。

  2. SPC 规定了支付专用信息的格式。这将使 通用验证代码和测试套件的开发成为可能。

  3. SPC 保证用户代理已将支付专用 信息呈现给用户，且恶意网站（或在受信任网站上恶意 注入的 JavaScript 代码）无法绕过这一过程。

    • 支付专用信息包含在 CollectedClientData 字典中，无法通过 JavaScript 篡改。

    注： 银行及支付 生态系统中的其他利益相关方目前已充分信任 通过浏览器使用 TLS、iframe 和其他 Web 功能进行的支付。 本规范旨在提高 Web 支付的安全性和易用性。

1.1.2. 商家对身份验证的控制

商家希望避免用户在结账过程中流失，尤其是通过 减少身份验证阻碍来实现这一目标。希望 使用 依赖方 （例如银行） 希望使用 [webauthn-3] 对用户进行身份验证时，通常会从 iframe 中执行此操作。然而，商家更希望自行管理 用户身份验证的体验，同时仍允许依赖方 验证 身份验证的结果。

这一限制促使安全支付确认采用以下行为：

  • 借助 SPC，依赖 方以外的其他参与方可以代表依赖方使用身份验证 凭据。随后，依赖方可以 验证身份验证结果。

此功能为依赖方带来的另一项好处是，他们不再 需要自行构建身份验证的前端体验。取而代之的是， 支付服务提供商可能会代表商家构建这些体验。

注： 希望自行提供 身份验证用户体验的依赖方 仍然可以在 iframe 中使用 SPC 来实现。

1.1.3. 设备绑定的密码学证据

在支付行业中，设备持有证明作为第二重身份验证因素 发挥着重要作用。WebAuthn 允许使用同步通行密钥，使同一凭据 可在多个设备上使用（Web 身份验证 § 1.2.1 使用多设备凭据的消费者）。 虽然同步功能改善了登录场景中的用户体验，但有人 担心，在某些监管环境下，仅使用同步通行密钥无法满足设备持有 要求。

这些担忧促使用户代理创建辅助的公私 密钥对，其中私钥仅存储在 一台设备上（且仅在该设备上使用）。此类密钥及其在 SPC 中的使用被称为 浏览器绑定密钥。

1.2. API 使用场景示例

本节将介绍安全支付确认的若干使用场景 以及使用此 API 的相应示例代码。请注意，这些只是 示例流程，并不限制 API 的使用范围。

1.2.1. 结账期间注册

这是一个首次使用的流程，其中发卡银行会在用户 于某个商家结账期间创建并存储一个新凭据。

  1. 用户访问 merchant.example，选择要购买的商品，然后进入 结账流程。用户输入支付工具的详细信息，并 表示希望付款（例如，按下“付款”按钮）。

  2. 商家通过带外方式（例如使用另一种协议）与 发行该支付工具的银行通信。发卡银行要求 验证用户身份，并提供一个由银行控制的 URL，供 商家在 iframe 中打开。

  3. 商家打开一个指向 bank.example 的 iframe，并将 allow 属性 设置为 “publickey-credentials-create”。

  4. 在 iframe 中，发卡银行通过 传统方式（例如短信一次性密码）确认用户身份。确认后，银行邀请 用户注册 SPC 身份验证，以便将来付款时使用。

  5. 用户表示同意（例如，在银行的用户体验界面中点击“注册”按钮）， 银行随后在 iframe 中运行代码（参见下面的示例）。

  6. 用户完成 WebAuthn 注册流程。系统会 创建一个新凭据并将其返回给发卡银行，银行将其存储在服务端 数据库中，并与用户及其支付工具关联。

  7. 验证完成；银行的 iframe 关闭，商家完成 用户的结账流程。

以下是以这种方式注册用户的示例代码。请注意，该示例代码 假定可以使用 async/await，以便更容易阅读 Promise 处理逻辑。

if (!window.PublicKeyCredential) { /* 客户端不具备相应能力。处理错误。 */ }

const publicKey = {
  // 质询应由银行服务器创建并发送给 iframe。
  challenge: new Uint8Array([21,31,105 /* 服务器生成的另外 29 个随机字节 */]),

  // 依赖方：
  rp: {
    name: "Fancy Bank",
  },

  // 用户：
  user: {
    // 这是 WebAuthn 的一部分。SPC 不要求提供此信息，
    // 但银行服务器可以使用此信息在
    // 后续交易中识别该用户。为同一用户提供不一致的值
    // 可能导致为该用户创建多个凭据，
    // 从而因需要选择凭据而影响用户体验。
    id: Uint8Array.from(window.atob("MIIBkzCCATigAwIBAjCCAZMwggE4oAMCAQIwggGTMII="), c=>c.charCodeAt(0)),
    name: "jane.doe@email.example",
    displayName: "Jane Doe",
  },

  // 在此示例中，依赖方既接受 ES256 凭据，也接受 RS256
  // 凭据，但更倾向于使用 ES256 凭据。
  pubKeyCredParams: [
    {
      type: "public-key",
      alg: -7 // "ES256"
    },
    {
      type: "public-key",
      alg: -257 // "RS256"
    }
  ],

  authenticatorSelection: {
    userVerification: "required",
    residentKey: "required",
    authenticatorAttachment: "platform",
  },

  timeout: 360000,  // 6 分钟

  // 指明这是一个 SPC 凭据。目前必须这样做，以便
  // 浏览器知道该凭据与 SPC 有关。这还允许
  // 在跨源 iframe 中创建凭据，而这正是本
  // 示例所需要的。
  //
  // 本规范的未来版本可能不再需要此扩展。
  extensions: {
    "payment": {
      isPayment: true,
      // 允许使用的算法列表，可选。如果未提供或为空，则
      // 使用 pubKeyCredparams，默认采用 ES256 和 RS256。在此
      // 示例中，允许使用 ES256 和 RS256，且优先选择 RS256。
      browserBoundPubKeyCredParams: [
        {
          type: "public-key",
          alg: -257 // "RS256"
        },
        {
          type: "public-key",
          alg: -7 // "ES256"
        }
      ]
    }
  }
};

// 注意：以下调用将使身份验证器显示用户界面。
try {
  const newCredentialInfo = await navigator.credentials.create({ publicKey });
  // 将新凭据的信息发送到服务器进行验证和注册。
} catch(err) {
  // 没有可接受的身份验证器，或用户拒绝同意。请妥善处理。
}

1.2.2. 商家网站上的身份验证

这是已注册凭据的用户 执行交易，且发卡银行和商家希望使用安全 支付确认时的流程。

  1. 用户访问 merchant.example，选择要购买的商品，然后进入 结账流程。用户输入支付工具的详细信息，并 表示希望付款（例如，按下“付款”按钮）。

  2. 商家通过带外方式与支付 工具的发卡银行通信（例如，使用另一种协议）。发卡银行要求 验证用户身份，同时通过提供使用 API 所需的信息， 告知商家其接受 SPC。此 信息包括质询以及与该 用户和支付工具关联的所有凭据 ID。

  3. 商家运行下面所示的示例代码。

  4. 用户同意 SPC 用户体验界面中显示的支付专用信息， 然后执行后续的 WebAuthn 身份验证流程。已签名的 密码学数据返回给商家（包括 AuthenticationExtensionsPaymentOutputs 中的浏览器绑定密钥输出）。

  5. 商家通过带外方式将已签名的密码学数据发送给 发卡银行。发卡银行验证该密码学数据，从而确认 用户身份有效、已向用户显示哪些支付专用信息，以及 用户已同意该交易。发卡银行授权 交易，商家完成用户的结账流程。 发卡银行存储浏览器绑定密钥的公钥， browserBoundPublicKey。

以下是对用户进行身份验证的示例代码。请注意，该示例代码 假定可以使用 async/await，以便更容易阅读 Promise 处理逻辑。

/* securePaymentConfirmationAvailability 指示浏览器是否 */
/* 支持 SPC。它不表示用户是否拥有可在此设备上 */
/* 使用的凭据。 */
const spcAvailable =
  (await window.PaymentRequest?.securePaymentConfirmationAvailability?.()) === 'available';
if (!spcAvailable) {
  /* 浏览器不支持 SPC；商家应回退到传统流程。 */
}

const request = new PaymentRequest([{
  supportedMethods: "secure-payment-confirmation",
  data: {
    // 从银行获取的凭据 ID 列表。
    credentialIds,

    rpId: "fancybank.example",

    // 质询也从银行获取。
    challenge: new Uint8Array([21,31,105 /* 银行生成的另外 29 个随机字节 */]),

    instrument: {
      displayName: "FancyBank Platinum Card",
      details: "****1234 | 01/29",
      icon: "https://fancybank.example/card-art.png",
    },

    payeeName: "Merchant Shop",
    payeeOrigin: "https://merchant.example",

    paymentEntitiesLogos: [
      {
        url: "https://fancybank.example/logo.png",
        label: "Fancy Bank",
      },
      {
        url: "https://securenetwork.example/logo.png",
        label: "Secure Network",
      },

2. 术语

SPC 凭据

一种可用于本规范所定义行为的WebAuthn 凭据。

本规范无意限制依赖方在其他身份验证流程（例如 登录）中可以（或不可以）如何使用 SPC 凭据。

注： 本规范的当前版本 要求依赖方明确选择允许凭据用于 第一方或第三方上下文。从长远来看，我们 希望所有WebAuthn 凭据 都能在第一方上下文中用于 SPC（例如，在 依赖方的域上），并且只有在允许 第三方使用凭据时才需要明确选择。

已启用第三方使用的 SPC 凭据

一种SPC 凭据， 其依赖方在 创建凭据时已明确选择允许依赖 方以外的其他参与方在安全支付确认身份验证中使用该凭据。

静默 确定 SPC 凭据是否已启用第三方使用的步骤

一个尚未定义的流程，通过该流程，用户代理可以根据给定的 依赖方标识符和凭据 ID，静默地（即 无需用户交互）确定该 ID 所表示的凭据 是否为已启用第三方使用的 SPC 凭据。

注： 参见WebAuthn 问题 1667。

静默 确定凭据是否可用于当前设备的步骤

一个尚未定义的流程，通过该流程，用户代理可以根据给定的 依赖方标识符和凭据 ID，静默地（即 无需用户交互）确定该 凭据 ID 所表示的凭据是否可用于当前设备（即， 能否作为 WebAuthn Get 调用的一部分成功使用）。

这使用户代理能够仅在用户 有可能成功完成交易时，才有条件地向用户显示 交易用户体验界面。

注： 此特性很可能要求SPC 凭据是 可发现的；因此本规范 目前将其规定为一项要求。

注： 此特性与 WebAuthn 条件式用户界面 提案所要求的特性非常相似。两者 很可能都可以由同一个底层 API 支持。

浏览器绑定 密钥

一种公私密钥对， 除 WebAuthn 凭据外，还会对交易详情进行签名， 并由用户代理将其绑定到单一设备。注： 之所以采用此名称， 是因为此功能最初是为浏览器实现的，但该概念适用于任何用户代理。

密钥对

密钥对是一个由公 钥和私钥组成的结构体， 两者的类型均由实现定义。

注： 公钥和私 钥是 IANA COSE 算法注册表 [IANA-COSE-ALGS-REG] 所引用密码学算法的特定参数。

注： 公钥部分在注册 期间通过 CollectedClientAdditionalPaymentRegistrationData.browserBoundPublicKey 返回，并在支付断言期间通过 CollectedClientAdditionalPaymentData.browserBoundPublicKey 返回。

注： 私钥用于 生成包含在 BrowserBoundSignature.signature 中的密码学签名。 用户 代理不会导出私钥，并且可以将私钥存储在 设备的安全元件中。

4. 身份验证——安全支付确认支付方式

为了通过安全支付确认对支付进行身份验证，本规范 定义了：

  1. 一个支付处理器，即安全支付确认支付 处理器，用于处理对给定支付进行身份验证的请求。

  2. 此支付处理器的标准化支付方式 标识符， “secure-payment-confirmation”。

安全支付确认支付处理器 与用户确认交易， 然后执行身份验证流程，以验证 用户身份并创建表示该身份验证流程的已签名数据块。

从整体上看，安全支付确认的身份验证与 [webauthn-3] 类似，但存在 一个重要的概念性变化。安全支付确认 允许第三方（例如商家）代表 依赖方触发身份验证流程，并传入其通过 某个未指定的其他渠道从依赖方获取的凭据。参见 § 1.1.2 商家对身份验证的控制。

4.4. SecurePaymentConfirmationRequest 字典

dictionary SecurePaymentConfirmationRequest {
    required BufferSource challenge;
    required USVString rpId;
    required sequence<BufferSource> credentialIds;
    required PaymentCredentialInstrument instrument;
    unsigned long timeout;
    USVString payeeName;
    USVString payeeOrigin;
    sequence<PaymentEntityLogo> paymentEntitiesLogos;
    AuthenticationExtensionsClientInputs extensions;
    sequence<PublicKeyCredentialParameters> browserBoundPubKeyCredParams;
    sequence<USVString> locale;
    boolean showOptOut;
};

SecurePaymentConfirmationRequest 字典包含以下 成员：

challenge

依赖方在服务器端生成的随机质询， 用于防止重放攻击。

rpId

凭据的依赖方标识符。

credentialIds

给定支付工具的凭据标识符列表。

instrument

对支付工具名称和图标的描述，用于在 注册期间显示，并与交易详情一起进行签名。

timeout

对交易详情进行签名的请求超时前的毫秒数， 最多为 1 小时。默认值和 允许值的范围由用户代理定义。Web 身份验证 提供了有关超时的其他 指导。

payeeName

此 SPC 调用对应的收款方（例如 商家）的显示名称。可选，可以与 payeeOrigin 一起提供，也可以代替它提供。

payeeOrigin

此 SPC 调用对应的收款方（例如 商家）的源。可选，可以与 payeeName 一起提供，也可以代替它提供。

paymentEntitiesLogos

一个可选的徽标列表，表示协助完成 此 SPC 调用对应支付的实体，并按显示 优先级降序排列。用户代理不必显示其中任何或全部 徽标，参见§ 4.9 检查能否 付款的步骤。

注： 本规范有意 不明确规定徽标的具体呈现方式，以保留用户代理对 呈现方式的控制权，并允许其根据 多种考虑因素和限制条件，以最佳方式显示信息。不过， 列表中徽标的顺序确实很重要，这意味着开发者可以通过实验 确定某种特定顺序是否能产生预期结果。

extensions

应当用于传入凭据的所有WebAuthn 扩展。调用方不需要指定 支付扩展；系统会自动添加。

注： 如果此字典 非空，第三方 SPC 调用将抛出异常，以避免针对 依赖 方可能存储私有数据的扩展发起攻击。参见§ 11.1.3 WebAuthn 扩展 仅允许由依赖方使用。

browserBoundPubKeyCredParams

允许的凭据类型列表，用于限制 浏览器绑定密钥所使用的密码学算法类型。

注： 仅当需要创建 浏览器绑定密钥时，才会使用此成员。

locale

一个可选的语言标签列表（参见[BCP47]），用于标识 调用方的区域设置偏好。如果设置了至少 一个语言标签，用户代理将确定列表中的任何标签 是否与安全支付确认对话框使用的语言一致。如果提供的语言 标签均不匹配，则用户代理将以 “NotSupportedError” DOMException 拒绝 PaymentRequest.canMakePayment() 返回的 Promise。

showOptOut

是否应在交易确认用户体验界面 中为用户提供选择退出的机会。 可选，默认为 false。

4.6. 检查安全支付确认是否 可用

向 PaymentRequest 添加一个静态 API， 以便为开发者提供一种 简化的方法来检查安全支付确认是否可用。 此方法 securePaymentConfirmationAvailability() 返回一个枚举成员，指示安全支付确认 可用，或不可用并在一定程度上说明 根本原因。使用枚举作为输出旨在帮助开发者 根据用户的身份验证选项提供指导和提示。

enum SecurePaymentConfirmationAvailability {
  "available",
  "unavailable-unknown-reason",
  "unavailable-feature-not-enabled",
  "unavailable-no-permission-policy",
  "unavailable-no-user-verifying-platform-authenticator",
};

partial interface PaymentRequest {
    static Promise<SecurePaymentConfirmationAvailability> securePaymentConfirmationAvailability();
};

SecurePaymentConfirmationAvailability 枚举包含以下成员：

available

指示用户代理认为安全支付 确认 API 在调用方框架中可用。

注： 此结果不表示 任何特定的SPC 凭据当前是否可用或将来是否可用。

unavailable-unknown-reason

指示安全支付确认 API 由于未知原因在 调用方框架中不可用。为了 保护用户隐私，用户代理可以始终选择 返回此结果，而不是更具体的原因。

unavailable-feature-not-enabled

指示安全支付确认 API 在 调用方框架中不可用，因为该功能尚未启用。

unavailable-no-permission-policy

指示安全支付确认 API 在 调用方框架中不可用，因为该框架缺少“payment” 权限策略。

unavailable-no-user-verifying-platform-authenticator

指示安全支付确认 API 在 调用方框架中不可用，因为没有可用的用户验证型平台身份验证器。

注： 也可以通过调用 isUserVerifyingPlatformAuthenticatorAvailable 获取此信息，但为了方便开发者，仍将其纳入此 API。

在给定的 Document document 中调用 securePaymentConfirmationAvailability() 时， 用户代理必须执行以下 步骤。如果需要保护用户隐私， 或者由于用户代理特定的原因无法完成某个步骤， 用户代理可以随时选择返回 “unavailable-unknown-reason”。

  1. 如果用户代理不支持安全支付确认，或者 虽然支持安全支付确认，但该功能通过某种 用户代理特定的机制被禁用，则返回 “unavailable-feature-not-enabled”。

  2. 如果未对 document 启用“payment”权限策略， 则返回 “unavailable-no-permission-policy”。

  3. 如果没有可用的用户验证型平台身份验证器， 则返回 “unavailable-no-user-verifying-platform-authenticator”。

  4. 如果存在任何其他原因，导致在 document 中调用 安全支付确认功能时无法正常运行，则返回 “unavailable-unknown-reason”。

  5. 返回“available”。

此 API 允许开发者在决定是否 发起 SPC 流程时执行以下检查：

const spcAvailable =
    PaymentRequest &&
    PaymentRequest.securePaymentConfirmationAvailability &&
    await PaymentRequest.securePaymentConfirmationAvailability() === 'available';

注： 建议使用静态的 securePaymentConfirmationAvailability 方法进行 SPC 功能检测， 而不是在已构造的 PaymentRequest 对象上调用 canMakePayment。

注： 有关此 API 的隐私注意事项，请参见 § 12.5 通过 securePaymentConfirmationAvailability 进行指纹识别。

4.7. 安全支付确认 功能的可用性

向 PaymentRequest 添加一个静态 API， 以便为开发者提供一种 确定安全支付确认功能 可用性的方法。此方法 getSecurePaymentConfirmationCapabilities() 返回一个将功能键 映射到布尔值的记录。 

partial interface PaymentRequest {
    static Promise<SecurePaymentConfirmationCapabilities> getSecurePaymentConfirmationCapabilities();
};

typedef record<DOMString, boolean> SecurePaymentConfirmationCapabilities;

SecurePaymentConfirmationCapabilities 中的键 必须按字典序 升序排列。键的集合 应该包含 SecurePaymentConfirmationCapability 的 枚举值集合， 但 用户代理可以根据需要省略键；参见 § 12.6 通过 getSecurePaymentConfirmationCapabilities 进行指纹识别。

当给定功能的值为 true 时，表示已知该功能 当前在此用户代理的安全支付 确认实现中受到支持。

当给定功能的值为 false 时，表示已知该功能 当前在此用户代理的安全支付 确认实现中不受支持。

当某项功能不作为键存在时，表示此用户代理的安全支付确认 实现是否支持该功能尚不明确。

此 API 允许开发者在决定是否 发起安全支付确认流程时检查特定功能是否受支持，如下所示：

if (PaymentRequest && PaymentRequest.getSecurePaymentConfirmationCapabilities) {
    const capabilities = await PaymentRequest.getSecurePaymentConfirmationCapabilities();
    if (capabilities.browserBoundKeyHardware) {
        // 使用 SPC API 时，将可以使用硬件支持的 BBK。
    }
}

注： 有关此 API 的隐私注意事项，请参见 § 12.6 通过 getSecurePaymentConfirmationCapabilities 进行指纹识别。

    注： 无论是否有任何凭据 匹配，都必须获取图像资源，以防止尝试探测 凭据是否存在。

  3. 用户代理可以选择从 data["paymentEntitiesLogos"] 中移除条目， 从列表末尾开始，向列表开头移动。

    注： 这允许用户代理控制 显示的徽标数量， 同时保留徽标按调用方指定的显示 优先级降序排列的语义。

  4. 对于 data["paymentEntitiesLogos"] 中的每个 logo：

    1. 为 logo 获取图像资源，传入 «["src" → logo["url"]]» 作为 image，并解码结果。

    2. 如果获取或解码失败，则将 logo["url"] 设置为空字符串。

      注： 这使依赖方能够知道 指定的徽标未被显示，因为 输出的 paymentEntitiesLogos 序列中对应徽标的 url 字符串将为空。

    注： 无论是否有任何凭据 匹配，都必须获取徽标资源，以防止尝试探测 凭据是否存在。

  5. 对于 data["credentialIds"] 中的每个 id：

    1. 运行静默 确定凭据是否可用于当前设备的步骤，传入 data["rpId"] 和 id。 如果结果为 false，则从 data["credentialIds"] 中移除 id。

    2. 如果 data["rpId"] 不是 request 的相关设置对象的源， 则运行静默 确定 SPC 凭据是否已启用第三方使用的步骤，传入 data["rpId"] 和 id。如果 结果为 false，则从 data["credentialIds"] 中移除 id。

  6. 返回 true。

4.10. 显示交易确认用户体验界面

当调用 PaymentRequest.show() 且选中安全支付确认支付 处理器时（该算法的步骤 19–24）， 用户代理必须向用户呈现一个用户界面， 使其能够选择是否继续以及如何继续。

4.10.1. 向用户呈现的信息

为避免限制用户代理的实现选择，本规范 不要求用户代理显示特定的用户界面。然而，为了 使依赖方能够信任 CollectedClientPaymentData 中包含的信息， 用户代理必须确保将以下信息 告知用户，并获取用户对 身份验证的同意：

  • payeeName， 如果存在。

  • payeeOrigin， 如果存在。

  • total， 即交易的 currency 和 value。

  • instrument 的详细信息，即 支付工具的 displayName、 details 和 icon。 如果无法从输入的 icon 中 获取或解码图像资源， 则用户代理可以不显示图标，或改为显示通用支付工具 图标。

    注： 如果指定的图标无法获取 或解码，则 iconMustBeShown 在此处必须为 false，因为 否则此前的检查能否 付款的步骤就会失败。

  • 由 paymentEntitiesLogos 中的 url 条目表示的徽标， 如果 非空。

    • 用户代理不必显示每个 PaymentEntityLogo 的 label， 但应该出于无障碍目的使用它们。 label 仍将被包含在 CollectedClientAdditionalPaymentData 中并参与签名。

如果 showOptOut 为 true，则用户代理 必须为用户提供机会，使其能够表示希望退出 给定依赖方的流程。

6. 浏览器绑定密钥存储

这是由用户代理拥有的内部组件，用于管理 依赖于平台的密码学密钥对，包括其与SPC 凭据（即通行密钥）的关联。每个浏览器 绑定密钥存储均由单个 用户代理拥有，并由该用户代理将其同时绑定到设备和浏览器。每个 用户代理可以拥有多个浏览器绑定密钥存储， 例如，当用户代理具有多个配置文件时。 本节介绍浏览器绑定密钥 存储，以及使用浏览器绑定密钥对创建、绑定、检索和签名的过程。

注： 浏览器绑定密钥存储需要 生成密钥对、检索密钥 对、导出公钥和生成签名。许多操作系统 提供了实现这些操作的 API，并且在可用时支持将 私钥存储在设备的安全元件中。例如 Android KeyStore、 Apple CryptoKit 或 Windows 下一代 密码学 API。

注： 浏览器绑定密钥的要求和设计注意事项 在 BBK 需求文档中进行了描述。 浏览器绑定密钥存储及其过程的设计基于这些要求和 注意事项。 在该需求文档中，术语“已安装的浏览器程序”用于指代用户代理， 因为 该文档是以浏览器实现为背景编写的。然而，这些要求和设计 注意事项 适用于任何用户代理实现。

浏览器绑定密钥存储包含以下内容：

browser_bound_map

一个将凭据 ID映射到密钥对标识符的映射。

注： 每个密钥对标识符最多只能与 一个凭据 ID关联。

keypair_map

一个将作为密钥对标识符的字节数组映射到由 公私密钥对及其 算法标识符 COSEAlgorithmIdentifier 组成的元组的映射。

注： 用户代理可能正在使用一个 提供与 keypair_map 等效功能的密码学 API，在这种情况下，用户代理将 这一部分交由密码学 API 处理。

6.1. 创建密钥对

要在给定一个 PublicKeyCredentialParameters allowed_algorithms 的情况下创建密钥对， 并返回由密钥对及其 COSEAlgorithmIdentifier 组成的元组， 以及密钥对 标识符的字节数组，执行以下步骤：

注： 从允许的算法或默认允许的 算法中生成密钥对。

  1. 如果 allowed_algorithms 为空， 则将此列表设置为 按以下顺序包含以下内容的默认列表：

    • type = PublicKeyCredentialType， 其中 alg = -7（“ES256”）。

    • type = PublicKeyCredentialType， 其中 alg = -257（“RS256”）。

  2. 从 allowed_algorithms 中移除所有类型不是 PublicKeyCredential 的条目。

  3. 从 allowed_algorithms 中移除用户代理 不支持的所有条目。

    注： 用户代理可能在不同设备平台上 支持不同的密码学算法 集合。

  4. 如果 allowed_algorithms 的大小为零，则 返回 null。

    注： 在这种情况下，用户代理不会添加任何浏览器 绑定输出。

  5. 如果 allowed_algorithms 的大小大于 零，则

    1. 令 chosen_algorithm 为 allowed_algorithms[0]。

    2. 令 bbk 为使用与 chosen_algorithm 对应的既定过程 生成公私密钥对的结果。 有关既定的密钥生成算法，请参阅 IANA COSE 算法注册表 [IANA-COSE-ALGS-REG]。 如果结果为失败，则 返回 null。

    3. 令 bbk_and_algorithm 为元组 (bbk, chosen_algorithm)。

    4. 令 bbk_id 为以下任一项

      1. 按以下方式初始化的字节数组：

        1. 令 bbk_id 为长度为 32 的数组。

        2. 调用 getRandomValues(bbk_id)。

      2. 对实现定义的密钥生成 过程返回的密钥对句柄进行序列化后得到的字节数组。此字节数组 必须能够标识该密钥，以便以后在获取或创建浏览器 绑定密钥时检索。

      注： 许多密码学 API 可能返回 标识符、句柄或 包装密钥，而不是私钥，并同时返回公 钥。例如，当私钥存储在安全 元件中时，用户代理无法直接访问私钥， 必须将标识符／句柄／包装密钥传入密码学 API 的 另一个函数才能使用。

    5. 将 keypair_map[bbk_id] 设置为 bbk_and_algorithm。

    6. 返回 (bbk_and_algorithm, bbk_id)。

本规范可以规定 优先选择硬件存储中的算法（按 给定顺序），然后选择软件中的算法（按相同的给定顺序）。目前， 这个问题可能并不重要，因为 Chrome 计划在每个平台的硬件中仅支持一种 算法。参见安全支付确认问题 #288，其中 讨论了 BBK 的存储类型，包括允许哪些存储 类型以及是否向依赖方公开存储类型等其他问题。

6.2. 绑定密钥对

要绑定密钥对， 给定包含密钥对 标识符的字节数组 bbk_id，以及字节数组 credential_id，并可能返回 失败，执行以下步骤：

注： 将凭据 ID（即通行密钥标识符）的浏览器绑定密钥标识符 存储在 browser_bound_map 中。

  1. 将 browser_bound_map[credential_id] 设置为 bbk_id。捕获 InvalidStateError、 TypeError 和 QuotaExceededError 错误，然后返回失败。

    注： 底层文件系统操作可能会抛出错误， 例如 write(buffer, options)。 此处返回 false 会导致用户代理避免 在交易中包含浏览器绑定密钥，在这种情况下， 依赖方不会在本次交易中获得浏览器绑定密钥。 在后续支付断言中，将再次尝试 创建新的密钥对。

6.3. 检索密钥对

要在给定字节数组 credential_id 和由 PublicKeyCredentialParameters 组成的列表 allowed_algorithms 的情况下，获取或 创建浏览器绑定密钥，并返回由密钥对及其 COSEAlgorithmIdentifier 组成的元组：

注： 查找与凭据 ID关联的现有密钥对，或创建 一个新的关联密钥对，并返回该密钥对及其算法。

  1. 如果 browser_bound_map[credential_id] 存在

    1. 令 bbk_id 为 browser_bound_map[credential_id]。

    2. 令 bbk_and_algorithm 为 keypair_map[bbk_id]。

  2. 如果 browser_bound_map[credential_id] 不存在

    1. 令 (new_bbk_and_algorithm, bbk_id) 为使用 allowed_algorithms 创建 密钥对的结果。

    2. 令 binding_result 为使用 bbk_id 和 credential_id 绑定密钥对的结果。如果结果为失败，则令 bbk_and_algorithm 为 null。

    3. 如果 binding_result 不为失败，则令 bbk_and_algorithm 为 new_bbk_and_algorithm。

  3. 返回 bbk_and_algorithm。

6.4. 获取浏览器绑定公钥

要在给定密钥对和 COSEAlgorithmIdentifier 的元组 bbk_and_algorithm 的情况下，获取 浏览器绑定公钥，并返回一个字节数组：

注： 获取浏览器绑定密钥的已编码公钥。

  1. 令 bbk 为 bbk_and_algorithm[0]。

  2. 令 algorithm 为 bbk_and_algorithm[1]。

  3. 令 public_key 为按照 algorithm 的既定过程 检索到的 bbk 的公钥。

  4. 令 encoded_public_key 为 public_key 的 COSE_Key 编码。参见 WebAuthn 的 Web 身份验证 § 6.5.1 已证明的凭据数据中的credentialPublicKey。

  5. 返回 encoded_public_key。

6.5. 对客户端数据进行签名

要在给定密钥 对和 COSEAlgorithmIdentifier 的元组 bbk_and_algorithm，以及字节数组 client_data_json 的情况下，生成浏览器绑定签名，并返回一个字节数组：

注： 使用浏览器绑定 密钥的私钥对 CollectedClientData （包括 CollectedClientAdditionalPaymentData 或 CollectedClientAdditionalPaymentRegistrationData） 进行签名。

  1. 令 bbk 为 bbk_and_algorithm[0]。

  2. 令 algorithm 为 bbk_and_algorithm[1]。

  3. 令 signature 为使用 bbk 的私 钥，通过 algorithm 对 client_data_json 执行签名操作的结果。参见 IANA COSE 算法注册表 [IANA-COSE-ALGS-REG]。

    注： 结果将是使用 bbk 的私钥 对 client_data_json 生成的密码学 签名。

  4. 返回 signature。

9. SPC 依赖方操作

9.1. 验证身份验证断言

为了执行安全支付确认的身份验证流程， 依赖方必须按以下方式操作：

  1. 令 credential 为 SPC caller 成功调用安全支付确认支付 处理器后返回的 PublicKeyCredential。

    注： 由于 SPC 旨在支持商家 控制身份验证，调用 SPC 的实体可能不是 依赖方。第一步假定 SPC 调用方已将 通过 SPC 获取的凭据返回给依赖 方。

  2. 按照 WebAuthn 中的 规定执行步骤 3–21，并进行以下更改：

    1. 在步骤 5 中，验证 credential.id 是否标识 依赖方提供给 SPC caller 的公钥凭据之一。

    2. 在步骤 11 中，验证 C["type"] 的值 是否为字符串 payment.get。

    3. 在步骤 12 中，验证 C["challenge"] 的值 是否等于依赖方提供给 SPC caller 的质询的 base64url 编码。

    4. 在步骤 13 中，验证 C["origin"] 的值 是否与依赖方预期 SPC 被调用的源 匹配。

    5. 在步骤 13 之后，插入以下步骤：

      • 验证 C["payment"]["rpId"] 的值 是否与依赖方的源匹配。

      • 验证 C["payment"]["topOrigin"] 的值 是否与依赖方预期的顶级源匹配。

      • 验证 C["payment"]["payeeName"] 的值 是否与本应向用户显示的收款方名称匹配（如果有）。

      • 验证 C["payment"]["payeeOrigin"] 的值 是否与本应向用户显示的收款方源匹配（如果有）。

      • 验证 C["payment"]["paymentEntitiesLogos"] 的值 是否为本应向用户显示的徽标的严格有序子集 （如果有）。

        注： 用户代理 可以不显示所有徽标，但不得 在 CollectedClientAdditionalPaymentData 中包含 未向用户显示的徽标。

      • 验证 C["payment"]["total"] 的值 是否与本应向用户显示的交易金额匹配。

      • 验证 C["payment"]["instrument"] 的值 是否与本应向用户显示的支付工具详情匹配。

11. 安全注意事项

由于本规范基于 WebAuthn 构建， WebAuthn 安全 注意事项 同样适用。以下子节包含当前安全支付 确认特有的安全注意事项，即本规范 与 WebAuthn 存在差异的方面。

11.1. 跨源身份验证流程

安全支付确认与 WebAuthn 的一个重大区别在于， 它允许第三方使用其他 依赖方的凭据发起身份验证流程，并将断言返回给 第三方。此功能可能使依赖方面临 登录和 支付攻击，下文将对此进行讨论。

11.1.1. 登录攻击

由于为安全支付确认创建的凭据是有效的 WebAuthn 凭据，依赖方可能希望 对给定用户使用同一个 凭据进行登录和支付。如果未仔细验证 收到的断言，这可能使依赖方的登录系统 面临潜在攻击。

攻击过程如下：

  1. 用户访问 attacker.example，该网站是商家网站或伪装成商家网站。

  2. attacker.example 从 relyingparty.example 获取用户的凭据， 可能通过合法方式，也可能从 relyingparty.example 或 relyingparty.example 与之共享凭据的其他参与方窃取。

  3. attacker.example 发起 SPC 身份验证，用户同意 交易（该交易可能合法，也可能不合法）。

  4. attacker.example 获取通过 API 调用收到的支付断言，并将其发送到 relyingparty.example 的登录端点，例如通过 向 https://relyingparty.example/login 发送 POST 请求。

  5. relyingparty.example 使用了有缺陷的断言验证代码， 该代码检查签名，却未能验证必要的字段（见 下文），因此认为此次登录尝试是合法的。

  6. relyingparty.example 向 attacker.example 返回登录 Cookie 等信息。 用户在 relyingparty.example 上的账户此时已遭到入侵。

依赖方可以通过两种方式防范此类攻击。

首先，依赖方必须始终遵循适当的正确断言 验证步骤，无论是用于WebAuthn 登录还是SPC 支付。特别是， 以下字段均可用于检测凭据的 不当使用：

  • CollectedClientData["type"]—— 登录时为“webauthn.get”， SPC 时为“payment.get”。

  • CollectedClientData["challenge"] ——此值应 由依赖方服务器在调用 WebAuthn 或 SPC 之前提供给网站，并应验证其是否与预期的、 适当的、先前提供的值匹配。

  • CollectedClientData["origin"] ——如果 SPC 跨源执行，此值将包含调用方的源 （例如上述示例中的 attacker.example）。

其次，依赖方可以考虑将支付凭据和登录 凭据分开。如果这样做，依赖方 应仅在子域上注册 安全支付确认凭据（例如 https//payment.relyingparty.example），并应在数据库中将支付凭据和 登录凭据分开存储。

注：按照目前的编写方式，安全支付确认规范 允许任何 WebAuthn 凭据用于 SPC 身份验证。 然而，当前实现并非如此，它们只允许 创建时指定了 payment 扩展的凭据参与 SPC 身份验证，并且 规范将来可能会更新以反映这一点。

在当前实现和规范中，使用 payment 创建的凭据 可以在依赖方希望的情况下用于登录。预计这一点不会改变。

11.1.2. 支付攻击

安全支付确认断言如果不是 正在进行的在线交易的一部分，基本上就毫无用处。

多种机制可以防范以下攻击：恶意 第三方不尝试劫持用户账户，而是使用 安全支付确认凭据（无论通过合法方式还是其他方式获取） 发起未经授权的支付：

  • 当攻击者发起 SPC 时，用户代理将向用户显示 一个明确列出交易详情（包括收款方 和金额）的用户界面。在这种情况下，用户很可能会选择“取消”。

  • 如果用户确实同意交易，并完成后续的 WebAuthn 身份验证流程，那么攻击者现在就获得了一份针对 依赖方的已签名 SPC 断言。

  • 如果依赖方未预期有交易发生，则会拒绝 该断言。

  • 如果依赖方预期有交易发生，则会检测到 以下至少一种情况并拒绝该断言：

    • CollectedClientData["challenge"] 不正确， 如果攻击者试图与正在进行的合法支付竞速。

    • CollectedClientData["origin"] 不正确， 如果攻击者试图介入用户与合法商家 网站之间并转发断言。

11.1.3. WebAuthn 扩展仅允许由依赖 方使用

WebAuthn 允许在身份验证流程中使用身份验证扩展。 某些扩展可用于存储或检索 （身份验证器上的）对依赖方而言敏感的数据。

在安全支付确认身份验证流程中，第三方（即 调用方）可以为属于其他 依赖方的凭据发起该流程。如果允许调用方指定任意 WebAuthn 扩展，他们可能能够访问属于 依赖方的敏感数据，而依赖方并不 打算将这些数据共享给 调用方。

例如，largeBlob 扩展允许存储和检索 大量数据。如果攻击者可以使用 largeBlob 扩展发起 SPC 流程，那么在用户授权该流程的情况下， 他们可能能够读取依赖方存储在其中的数据。

为降低此风险，安全支付确认禁止 在跨源身份验证流程中使用 WebAuthn 扩展；只有当 调用方是依赖方时才允许使用。

11.2. 商家提供的身份验证数据

银行可以且应该通过 验证收到的身份验证断言来防范欺骗， 确保其与商家提供的交易详情 一致。

这是因为本规范的第三方 身份验证流程意味着，即使在合法交易中（即 依赖方预期的交易），也是由第三方提供 向用户显示的交易详情：

  • 交易金额和货币

  • 支付工具名称和图标

  • 收款方名称和源

这可能导致欺骗攻击，即商家向用户提供错误的 数据。例如，商家可以告诉银行（在 后端）它正在发起一笔 100 美元的购买交易，却向 SPC API 传入 1 美元（从而向用户显示一笔 1 美元的交易供其验证）。或者，商家 可以提供正确的交易详情，却传入与 依赖方 预期不符的安全支付确认凭据。

实际上，安全支付确认使防范此类攻击变得 比目前的 Web 更容易。在当前的在线支付中，银行必须 相信商家在结账 流程中向用户显示了正确的金额（而任何欺诈行为都要在付款后， 用户检查账户对账单时才会被发现）。

11.3. 攻击者生成的浏览器绑定密钥

该 依赖方（例如银行）能够且应当防范攻击者 生成的 BBK，方法是通过 验证身份验证 断言，该断言包含 BBK 公钥，并忽略 签名无效的密码报文中的 BBK 公钥。虽然会存在 两个签名，一个来自 SPC 凭据，另一个来自 BBK， 但仍应使用通行密钥（除了 BBK 之外）验证该断言。 BBK 提供的是额外的签名，而不是对通行密钥 签名的替代。

伪装成商家的攻击者可能尝试将BBK 公钥替换成另一个公钥，而 攻击者控制 对应的私钥。随后，攻击者冒充用户， 访问商家网站，并在商家调用 SPC 时使用攻击者的 私钥对 SPC 密码学数据进行签名。攻击者由此绕过了 BBK 的设备绑定机制。

然而，这种攻击并不可行：

  1. 当攻击者替换 BBK 时：依赖 方会在使用通行密钥公钥验证 包含 BBK 公钥的 CollectedClientData 时检测到 签名不正确。依赖 方应该拒绝该交易，并将此 BBK 公钥视为 不可信。

  2. 当攻击者试图冒充用户时：依赖 方 会在使用通行密钥公钥 验证时检测到签名不正确。依赖方应该继续将此 BBK 公钥视为 不可信。

11.4. 缺少用户激活要求

如果用户代理不要求用户激活，如 § 4.3 修改用户激活要求所述， 则应该考虑一些额外的安全 缓解措施。不要求用户激活会增加 垃圾信息和点击劫持攻击的风险，因为这允许在用户 事先未与页面交互的情况下发起安全支付 确认流程。

为了缓解垃圾信息问题，用户代理可以决定在达到某个阈值后强制要求用户 激活，例如，在当前页面上已经 向用户显示过一次无需用户激活的安全支付确认流程之后。 为了缓解点击劫持攻击，用户代理 可以实现一个时间阈值，在对话框显示后立即发生的点击将被忽略。

另一个相关的缓解措施存在于 PaymentRequest.show() 中： 支付请求 API 要求文档可见，因此无法从 后台标签页、最小化窗口或其他类似的隐藏状态触发 SPC。

12. 隐私注意事项

由于本规范基于 WebAuthn 构建， WebAuthn 隐私注意事项 同样适用。以下子节包含当前安全支付 确认特有的隐私注意事项，即本规范 与 WebAuthn 存在差异的方面。

12.1. 探测凭据 ID

根据 WebAuthn 关于身份验证 流程隐私的章节，安全支付确认的实现者必须确保 恶意调用方（现在甚至可能不是依赖方） 无法区分以下情况：

  • 凭据不可用。

  • 凭据可用，但用户不同意使用它。

如果能够区分上述情况，就会泄露信息，使 恶意依赖方能够通过探测哪些 凭据可用来识别用户。

安全支付确认通过始终显示 交易确认用户体验界面， 并在没有可用的 SPC 凭据以及存在可用的 SPC 凭据但 用户选择不使用它这两种情况下，返回相同的错误（一个“NotAllowedError” DOMException）来缓解此风险。

12.2. 关联不同的支付工具

如果依赖方对给定用户的 多个支付工具使用相同的凭据，这可能使商家能够关联 原本可能无法关联的支付工具信息。也就是说， 对于用户 U 使用支付工具 P1 和 P2 执行的两笔不同交易（无论是在同一商家 M，还是两个串通的商家 M1 和 M2）， 商家现在可能能够得知 P1 和 P2 属于同一个用户。

对于目前许多在线支付流程，这可能不是重大 风险，因为用户通常已经提供了足够的信息 来进行这种关联（例如姓名、电子邮件地址、收货地址）。

然而，如果涉及较少身份识别信息的支付方式 （例如令牌化）变得普遍，生态系统 利益相关方就必须采取措施保护用户隐私。例如：

  • 支付系统可以制定规则，限制第三方存储凭据 ID 或 BBK 公钥。

  • 当依赖方将多个支付工具分配给单个 SPC 凭据时，可以选择不与其他参与方共享该凭据 ID。在这种情况下，依赖方仍然可以自行使用 SPC 凭据（在 第一方或第三方上下文中）对用户进行身份验证。

  • 依赖方（例如银行）可以允许用户为 每个支付工具注册不同的 SPC 凭据。这并不妨碍依赖 方在内部关联这些账户。

12.3. 凭据 ID 作为跟踪媒介

即使对于单个支付工具， 依赖方返回的凭据 ID 也可能被恶意实体用作跟踪媒介， 因为 它们是具有很强识别能力的跨站点标识符。然而，为了从 依赖方获取这些凭据 ID，商家已经需要向 依赖方提供一个具有同等识别能力的标识符（例如信用卡号码）。

12.4. 浏览器绑定密钥作为跟踪媒介

BBK 公钥仅在每次 SPC 支付断言时返回（以及 最初在第一方上下文中创建SPC 凭据时返回一次）。然而，为了获取 BBK，商家必须先从依赖方获取凭据 ID， 才能发起 SPC，而且用户必须使用 通行密钥对交易进行身份验证。由于访问 BBK 公钥需要先获得 凭据 ID，因此 BBK 公钥不会增加额外的跟踪能力。

12.5. 通过 securePaymentConfirmationAvailability 进行指纹识别

securePaymentConfirmationAvailability API 存在潜在的 指纹识别风险，因为它可以静默返回安全支付确认 API 在特定框架中不可用的具体原因。这些 原因被认为不会泄露大量信息，但仍应 加以考虑：

  • unavailable-feature-not-enabled： 存在一定的指纹识别风险，具体取决于用户代理在什么情况下 认为安全支付确认可用或不可用。鼓励用户 代理向所有用户提供安全支付确认 （如果实现了本规范），或至少向规模足够大的 用户群体提供，以确保不会产生（额外的）指纹识别能力。例如， 用户代理可以向使用某种操作系统的所有用户提供安全支付确认， 但不向使用其他操作系统的用户提供——这样，指纹识别风险就被限制为 不超过用户代理字符串已经泄露的信息。

  • unavailable-no-permission-policy： 不存在（额外的）指纹识别风险，因为“payment” 权限策略是否启用已经可以通过尝试构造 PaymentRequest 对象进行静默检测（如果未启用该权限策略， 构造时将抛出错误）。

  • unavailable-no-user-verifying-platform-authenticator： 相对于现有的 isUserVerifyingPlatformAuthenticatorAvailable API，不存在（额外的）指纹识别风险。

除上述注意事项外，本规范还允许用户代理 选择返回 unavailable-unknown-reason， 即使 已知具体原因，只要用户代理希望通过这种方式保护用户 隐私。例如，当用户代理检测到 当前框架已经访问了其他存在 指纹识别风险的 API 时，就可能这样做。

12.6. 通过 getSecurePaymentConfirmationCapabilities 进行指纹识别

getSecurePaymentConfirmationCapabilities API 存在潜在的 指纹识别风险，因为它可以静默返回有关 用户设备具备或不具备哪些功能的具体信息。

为降低此风险，用户代理应该优先从返回的 记录中省略某个键，而不是返回 false。省略该键（如 § 4.7 安全支付 确认功能的可用性中所述）所暴露的 指纹识别信息少于明确确认不支持某项功能。用户 代理也可以选择省略某项受支持的功能，以 保护用户隐私。

对于 SecurePaymentConfirmationCapability 中列出的特定功能，注意事项如下：

  • browserBoundKeyHardware： 存在泄露用户设备具有硬件安全芯片这一信息的风险。此 信息可能已经可以通过其他 Web API 静默获取，例如 [DBSC]。

12.7. 用户选择退出

API 选项 showOptOut 指示 用户代理提供一种方式，让用户能够表示希望退出 依赖方的信息存储。当用户选择退出时，会向 调用方返回一个 OptOutError， 以表明用户选择 退出的意图。随后由调用方负责处理退出请求，例如清除 为用户存储的支付信息。

实现者必须确保返回 OptOutError 不会 泄露用户拥有凭据但未完成身份验证这一事实。 可以通过与 § 12.1 探测凭据 ID类似的方式缓解此风险，例如在 未找到匹配凭据的情况下，也通过中间用户体验界面向 用户提供 选择退出的机会。

这并非用于删除浏览器数据或凭据的机制—— 而是供开发者通过用户代理提示用户选择退出。用户代理 应该向用户明确说明这一点，例如使用以下解释性文字： “此提供商可能存储了有关您支付方式的信息，您 可以请求删除这些信息。”

12.8. 通过区域设置进行指纹识别

locale 成员存在潜在的 指纹识别风险，因为它可以静默暴露安全 支付确认对话框使用的区域设置。为此，攻击者可以创建多个使用不同区域设置的安全 支付确认请求，并观察 PaymentRequest.canMakePayment() 调用是否 以 错误拒绝，直到攻击者识别出安全支付 确认对话框使用的区域设置。

如果安全支付确认对话框使用的区域设置比较罕见， 攻击者就可以借此唯一识别用户。

虽然这是一种指纹识别途径，但请注意，此区域设置 可能已经通过其他 API 暴露（例如，通过HTML § 8.10.1.2 语言偏好）。

13. 无障碍注意事项

用户代理将 icon 和 displayName 一起呈现。依赖方通过在 displayName 中提供足够的信息，确保图标呈现的无障碍性 （例如，如果图标代表一家银行，则在 displayName 中包含银行名称）。

实现本规范的用户代理应该同时遵循 WebAuthn 的无障碍 注意事项 和PaymentRequest 的无障碍注意事项。

14. 国际化注意事项

API 的调用方应该使用 locale 成员，使交易对话框的区域设置与其作为 API 输入提供的可显示字符串（例如 displayName）的区域设置保持一致。 特别是，调用方应该：

  • 尽量使 locale 的值（如果提供） 与可显示字符串的语言 保持一致。

  • 使用 PaymentRequest.canMakePayment() 确定安全支付确认对话框是否会以 locale 中设置的区域设置显示。

  • 如果无法找到包含其他 语言子标签的区域设置的匹配项， 则回退到仅包含主语言子标签 （例如 "en"）的语言标签。

  • 确保提供的可显示字符串内部的书写方向变化 在字符串显示时能够正确呈现（参见 如何使用 Unicode 控制字符处理双向文本 和 基本方向的行内 更改 以获取更多信息）。

实现（以及其他尝试显示值的过程） 在将可显示字符串值插入用户界面时，应该对其应用双向隔离。 当书写方向已知时，应该设置相应方向； 未知时则默认使用首个强方向字符（“auto”）。

    问题索引

    本规范的当前版本仅支持每个 PaymentEntityLogo 包含一个 URL，因此 只需复制数据并对 数据结构进行签名，就足以表明向用户显示了什么。未来 版本可能会为每个 PaymentEntityLogo 添加多个 URL， 例如，以原生方式支持深色模式。如果 发生这种情况，本规范将需要向依赖方指明给定的 PaymentEntityLogo 显示了哪个 URL。 ↵
    本规范可以规定优先选择硬件存储中的算法（按 给定顺序），然后选择软件中的算法（按相同的给定顺序）。目前， 这个问题可能并不重要，因为 Chrome 计划在每个平台的硬件中仅支持一种 算法。参见安全支付确认问题 #288，其中 讨论了 BBK 的存储类型，包括允许哪些存储 类型以及是否向依赖方公开存储类型。 ↵
