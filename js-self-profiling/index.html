本规范描述了一个允许 Web 应用控制采样性能分析器的 API，用于 测量客户端 JavaScript 的执行时间。

引言

复杂的 Web 应用目前只能有限地了解客户端 JS 执行时间的具体消耗位置。由于无法高效地 收集栈样本，应用不得不在代码中插入 性能分析钩子，而这些钩子既不精确，又可能显著降低 执行速度。通过提供一个操控采样性能分析器的 API， 应用可以收集丰富的执行数据，以便进行聚合和分析， 同时将开销降至最低。

示例

以下示例演示了用户如何对开销较大的操作进行性能分析，每 10ms 收集一次 JS 执行 样本。跟踪记录可以发送到服务器进行分析，以调试异常情况，并研究 JS 执行的 整体特征。

        const profiler = new Profiler({ sampleInterval: 10, maxBufferSize: 10000 });
        const start = performance.now();
        for (let i = 0; i < 1000000; i++) {
             doWork();
        }
        const duration = performance.now() - start;
        const trace = await profiler.stop();
        const traceJson = JSON.stringify({
          duration,
          trace,
        });
        sendTrace(traceJson);

另一个常见的实际场景是在整个页面加载过程中对 JS 进行性能分析。此示例对 onload 事件进行性能分析，并将性能计时数据与跟踪记录一并发送。

        const profiler = new Profiler({ sampleInterval: 10, maxBufferSize: 10000 });

        window.addEventListener('load', async () => {
          const trace = await profiler.stop();
          const traceJson = JSON.stringify({
            timing: performance.timing,
            trace,
          });
          sendTrace(traceJson);
        });

        // 页面的其余 JS 初始化逻辑

定义

样本是一个描述符，用于描述 给定时刻的瞬时执行状态。每个样本都 与一个栈关联。

栈是一个帧列表，必须按 从最外层帧到最内层帧的顺序排列。

帧是栈上下文中的一个元素， 包含有关当前执行状态的信息。

性能分析会话

性能分析会话是样本的抽象生产者。每个会话具有：

  1. 一个状态，其值为 {started, paused, stopped} 之一。
  2. 一个采样间隔，定义为会话获取样本的周期。

    不要求用户代理按此速率采集样本。但是， 建议优先保证按此速率进行采样，以 生成质量更高的跟踪记录。

  3. 一个要进行性能分析的代理。
  4. 一个要进行性能分析的域。
  5. 一个时间原点，样本时间戳的测量 以其为基准。
  6. 一个样本缓冲区大小限制。
  7. 一个存储已捕获样本的 ProfilerTrace。

应支持在同一页面上运行多个性能分析会话。

状态

在 started 状态下，用户代理应尽力 通过执行采集样本算法来捕获样本，该算法[= 以 并行方式 =]在每次采样间隔过去后执行。 在 paused 和 stopped 状态下，用户代理不应捕获样本。

性能分析会话必须以 started 状态开始。

用户代理可以将会话从 started 转为 paused，也可以从 paused 转为 started。

建议用户代理在浏览上下文 不处于前台时暂停性能分析会话的采样。

处于 stopped 状态的会话不得转为 started 或 paused 状态。

处理模型

给定一个性能分析会话，要采集样本，执行以下步骤：

  1. 如果 ProfilerTrace.samples 的长度大于或等于与性能分析会话关联的样本缓冲区大小 限制，则向关联的 Profiler 触发一个类型为 samplebufferfull 的新事件，将状态转为 stopped， 然后返回。
  2. 令 sample 为一个新的 ProfilerSample。
  3. 将 sample 的 ProfilerSample.timestamp 属性设置为当前高精度时间，其基准 为性能分析会话的时间原点。
  4. 令 stack 为与性能分析会话的代理关联的执行上下文 栈。
  5. 将 sample 的 ProfilerSample.stackId 属性设置为对 stack 运行获取栈 ID算法的结果。
  6. 令 marker 为给定性能分析会话所关联的 环境设置对象运行捕获标记算法的结果。
  7. 如果 marker 不为 null，则将 sample 的 ProfilerSample.marker 属性设置为 marker。
  8. 将 sample 添加到与会话的 ProfilerTrace 关联的 ProfilerTrace.samples 中。

给定一个环境 设置对象 settings，要捕获标记，执行以下步骤：

  1. 令 candidateMarker 为最能描述以下顶层工作的 ProfilerMarker 值： 采集样本时，用户代理正在性能分析会话的代理上执行的工作；如果没有适用的值， 则为 null。
  2. 如果 candidateMarker 为 null，则返回 null。
  3. 如果 candidateMarker 所描述的工作是为某个特定文档执行的，而该文档不[= 同源 =]于 settings 的源，则返回 null。
  4. 返回给定 candidateMarker 和 settings 运行过滤标记的结果。

用户代理内部活动到 ProfilerMarker 值的映射有意被 定义为由实现定义，因为引擎架构各不相同。作为非规范性指导，预期用户代理 在执行作者脚本时报告 script，在垃圾回收期间报告 gc， 在重新计算已计算样式时报告 style，在计算盒几何信息 （即重排）时报告 layout，在栅格化或合成文档内容时报告 paint。 other 标记用于不属于上述任一 类别的用户代理工作。当没有适用的类别时（例如，代理空闲时），捕获标记 算法返回 null，而生成的 ProfilerSample 上不设置 ProfilerSample.marker 属性。

同源检查确保标记仅描述为与性能分析器[= 同源 =]的文档执行的工作，这与 API 不得暴露跨源活动的要求一致。对于 无法归属于单一文档的工作 — 例如，引擎范围的垃圾回收 — 则 不受此检查约束；此类工作仅在性能分析器处于跨源隔离状态时暴露， 这一要求由过滤标记强制实施。

给定一个 ProfilerMarker marker 和一个环境设置对象 settings，要过滤标记， 执行以下步骤：

  1. 如果 settings 的跨源隔离 能力为 true，则返回 marker。
  2. 如果 marker 为 "style" 或 "layout"，则返回 marker。
  3. 返回 null。

过滤标记算法产生的可观察行为是：在未跨源隔离的 上下文中，ProfilerSample 上仅出现 style 和 layout 标记； script、gc、paint 和 other 标记被抑制。请参阅 有条件的标记暴露，了解此行为背后的理由。用户 代理可以提供选择启用机制（例如，源试用令牌或文档策略），以扩大 过滤标记针对特定环境设置对象返回的集合；此类选择启用机制不得 跨源暴露标记。

给定一个绑定到 stack 的执行上下文栈，要获取栈 ID，执行 以下步骤：

  1. 如果 stack 为空，则返回 undefined。
  2. 令 head 为 stack 的栈顶元素，tail 为 stack 移除栈顶元素后的剩余部分。
  3. 令 parentId 为对 tail 递归调用获取栈 ID的结果。
  4. 令 frameId 为对 head 调用获取帧 ID的结果。
  5. 如果 frameId 为 undefined，则返回 parentId。
  6. 令 profilerStack 为一个新的 ProfilerStack，其 ProfilerStack.frameId 等于 frameId，且 ProfilerStack.parentId 等于 parentId。
  7. 返回对 profilerStack 和 ProfilerTrace.stacks 运行获取元素 ID的结果。

给定一个绑定到 context 的执行 上下文，要获取帧 ID，执行以下步骤：

  1. 如果与 context 关联的[= 域 =]与 性能分析会话关联的域不匹配，则返回 undefined。
  2. 令 instance 等于与 context 关联的函数 实例。
  3. 令 scriptOrModule 等于与 context 关联的 ScriptOrModule。
  4. 令 |attributedScriptOrModule : ScriptOrModule| 等于运行以下 算法的结果：
    1. 如果 |scriptOrModule| 不为 null，则返回 |scriptOrModule|。
    2. 如果 |instance| 是内置函数对象，则返回包含 调用 |instance| 的函数的 ScriptOrModule。

      上述逻辑的目的是确保不可访问的 脚本所调用的内置函数不会暴露在跟踪记录中，具体通过使用调用 它们的 ScriptOrModule 进行归属判定来实现。

      “[…] 包含调用 |instance| 的函数的 ScriptOrModule” 应有更严格的定义。我们可以利用栈中 定义了 ScriptOrModule 的最顶层执行上下文来提供此信息，但这并不理想 -- （理论上）可能存在其他机制将内置函数加入执行 上下文栈，在这种情况下，归属判定将无效。

    3. 否则，返回 null。
  5. 如果 |attributedScriptOrModule| 为 null，则返回 undefined。
  6. 令 |attributedScript : Script| 为从 |attributedScriptOrModule|.[[\HostDefined]] 获得的[= 脚本 =]。
  7. 如果 |attributedScript| 是[= 经典脚本 =]，且其静默 错误布尔值等于 true，则返回 undefined。

    此检查确保我们不会包含通过 CORS 跨源响应提供的跨源脚本中的栈帧。我们可能需要考虑重命名静默错误，以更好地体现 此用例。

  8. 令 frame 为一个新的 ProfilerFrame。
  9. 将 frame 的 ProfilerFrame.name 设置为与 函数实例名称，其关联对象为 |instance|。
  10. 如果 |scriptOrModule| 不为 null：
    1. 令 script 为从 scriptOrModule.[[\HostDefined]] 获得的脚本。
    2. 令 resourceString 等于 基 URL，其所属脚本为 script。
    3. 将 ProfilerFrame.resourceId 设置为对 resourceString 和 ProfilerTrace.resources 运行获取元素 ID的结果。
    4. 将 frame 的 ProfilerFrame.line 设置为以下行的从 1 开始的索引： instance 在 |script| 中的定义所在的行。
    5. 将 frame 的 ProfilerFrame.column 设置为以下列的从 1 开始的索引： instance 在 |script| 中的定义所在的列。
  11. 返回对 frame 和 ProfilerTrace.frames 运行获取元素 ID的结果。

要获取 list 中 item 的获取元素 ID，运行以下步骤：

  1. 如果 list 中存在一个与 item 逐分量相等的元素，则返回其索引。
  2. 否则，将 item 追加到 list 的末尾，并返回其索引。

Profiler 接口

      [Exposed=(Window, Worker)]
      interface Profiler : EventTarget {
        readonly attribute DOMHighResTimeStamp sampleInterval;
        readonly attribute boolean stopped;

        constructor(ProfilerInitOptions options);
        Promise<ProfilerTrace> stop();
      };

每个 Profiler 必须恰好与一个性能分析会话关联。

sampleInterval 属性必须反映所关联的 性能分析会话的采样间隔，以 DOMHighResTimeStamp 表示。

stopped 属性必须为 true，当且仅当性能分析会话的状态为 stopped。

new Profiler(options)

给定一个类型为 ProfilerInitOptions 的对象 options，new Profiler(options) 运行以下步骤：
  1. 如果 options 的 {{ProfilerInitOptions/sampleInterval}} 小于 0，则抛出 RangeError。
  2. 令 |globalObject| 为当前全局对象。
  3. 如果 |globalObject| 是一个 Window 或一个 WorkerGlobalScope：
    1. 获取 策略值，策略为 |globalObject| 中的 "js-profiling-mode"。令 |profilingMode| 为其结果。
    2. 如果 |profilingMode| 既不是 "eager" 也不是 "lazy"：
      1. 获取 策略值，策略为 |globalObject| 中的 "js-profiling"。令 |jsProfilingEnabled| 为其结果。
      2. 如果 |jsProfilingEnabled| 为 false，则抛出一个 "NotAllowedError" DOMException。
  4. 否则，抛出一个 "NotAllowedError" DOMException。
  5. 创建一个新的性能分析会话，其中：
    1. 所关联的采样间隔设置为 ProfilerInitOptions.sampleInterval 或用户代理支持的下一个较低间隔。
    2. 所关联的时间原点等于 |globalObject| 的时间原点。
    3. 所关联的样本缓冲区大小限制设置为 {{ProfilerInitOptions/maxBufferSize}}。
    4. 所关联的[= 代理 =]设置为外围代理。
    5. 所关联的[= 域 =]设置为当前域 记录。
    6. 所关联的 ProfilerTrace 设置为 «[{{ProfilerTrace/resources}} → «», {{ProfilerTrace/frames}} → «», {{ProfilerTrace/stacks}} → «», {{ProfilerTrace/samples}} → «»]»。
  6. 返回一个与新创建的性能分析会话关联的新 Profiler。

stop() 方法

停止性能分析器并返回跟踪记录。此方法必须运行以下步骤：

  1. 如果所关联的[= 性能分析会话 =]的状态为 stopped，则返回[= 一个 promise 其拒绝原因为 =]一个 "InvalidStateError" DOMException。
  2. 将[= 性能分析会话 =]的状态设置为 stopped。
  3. 令 |p:Promise| 为[= 一个新 promise =]。
  4. [= 并行 =]运行以下步骤：
    1. 执行任何[= 由实现定义 =]的工作，以停止[= 性能分析会话 =]。
    2. 使用与性能分析器的[= 性能分析会话 =]关联的 {{ProfilerTrace}} 兑现 |p|。
  5. 返回 |p|。

性能分析 会话不应包含在调用 stop() 后采集的任何样本。

ProfilerTrace 字典

      typedef DOMString ProfilerResource;

      dictionary ProfilerTrace {
        required sequence<ProfilerResource> resources;
        required sequence<ProfilerFrame> frames;
        required sequence<ProfilerStack> stacks;
        required sequence<ProfilerSample> samples;
      };

resources 属性必须返回由采集 样本算法设置的 ProfilerResource 列表。

frames 属性必须返回由采集样本 算法设置的 ProfilerFrame 列表。

stacks 属性必须返回由采集样本 算法设置的 ProfilerStack 列表。

samples 属性必须返回由采集样本 算法设置的 ProfilerSample 列表。

此表示形式受到V8 跟踪 事件格式 和Gecko 性能分析格式的启发， 旨在便于高效地序列化。

ProfilerSample 字典

        enum ProfilerMarker { "script", "gc", "style", "layout", "paint", "other" };

        dictionary ProfilerSample {
          required DOMHighResTimeStamp timestamp;
          unsigned long long stackId;
          ProfilerMarker? marker;
        };

timestamp 必须返回其初始化时的值。

stackId 必须返回其初始化时的值。

marker 必须返回采集样本算法为其初始化的值，或者 在未设置标记时不存在。允许暴露的标记值集合由 过滤标记算法控制。

在跨源隔离的上下文中，过滤标记算法返回 ProfilerMarker 枚举中的每个值。在未隔离的上下文中，它仅返回 style 和 layout，因此其他标记均被抑制（对应的 ProfilerSample 上不存在 marker 属性）。

ProfilerStack 字典

        dictionary ProfilerStack {
          unsigned long long parentId;
          required unsigned long long frameId;
        };

parentId 必须返回其初始化时的值。

frameId 必须返回其初始化时的值。

ProfilerFrame 字典

        dictionary ProfilerFrame {
          required DOMString name;
          unsigned long long resourceId;
          unsigned long long line;
          unsigned long long column;
        };

name 必须返回其初始化时的值。

resourceId 必须返回其初始化时的值。

line 必须返回其初始化时的值。

column 必须返回其初始化时的值。

ProfilerInitOptions 字典

      dictionary ProfilerInitOptions {
        required DOMHighResTimeStamp sampleInterval;
        required unsigned long maxBufferSize;
      };

ProfilerInitOptions 必须支持以下字段：

  • sampleInterval 是应用期望的采样间隔。此值必须 大于或等于零。
  • maxBufferSize 是期望的样本缓冲区大小限制，以样本数计。

文档策略

本规范在配置 点方面扩展了文档 策略，以控制性能分析能力和初始化行为。

js-profiling-mode

本规范定义了一个配置 点，其名称为 js-profiling-mode。其类型 为 enum，允许的值为 "eager" 和 "lazy"。其默认 值为空字符串。

设置后，此策略授权脚本使用 JS 自分析 API。

eager

当 js-profiling-mode 设置为 "eager" 时，它向用户代理表明 预期会在页面加载期间进行性能分析。

用户代理可以利用此提示尽早初始化性能分析基础设施，在文档加载期间尽早存储所需的 元数据并预热性能分析组件。但是， 即使未主动使用性能分析，这也可能引入不可忽略的性能开销。此 开销可能对首次内容绘制（FCP）和最大内容 绘制（LCP）等指标产生负面影响。

lazy

当 js-profiling-mode 设置为 "lazy" 时，它向用户代理表明 性能分析将有条件地使用。

用户代理可以利用此提示，将性能分析相关的初始化开销推迟到第一个 Profiler 实例化时，从而在未主动使用性能分析时，避免在关键渲染阶段产生 性能成本。但是，如果初始化发生在用户交互 处理期间，则可能对交互到下一次绘制（INP）产生负面影响。此模式尤其 适用于根据采样决策有条件地启用性能分析的文档。

js-profiling（已弃用）

本规范还定义了一个配置 点，其名称为 js-profiling。其类型 为 boolean，其默认 值为 false。

启用时，此策略授权脚本使用 JS 自分析 API，并向用户代理表明应 尽早初始化性能分析基础设施（在语义上等同于 js-profiling-mode=eager）。

js-profiling 布尔配置点已弃用，改用 js-profiling-mode。如果两者均指定，则 js-profiling-mode 优先， 且必须忽略 js-profiling。实现应支持 js-profiling 以保持向后兼容，但可以在未来移除支持。

隐私与安全

以下各节详细介绍了 API 在隐私与安全方面的一些选择，并说明针对 各类攻击的防护策略。

跨源脚本内容

该 API 通过 静默错误 属性，要求所有经由 采集样本算法纳入的函数均定义于通过CORS 同源方式提供的脚本中，从而避免暴露跨源脚本的内容。 浏览器内置函数（例如 performance.now()）也必须仅在从 [= CORS 同源 =]脚本调用时才被纳入。

因此，除了通过手动插桩已经能够获知的信息外，该 API 不会额外暴露有关 跨源脚本内容或执行特征的信息。鼓励用户代理 在选择支持极低的采样间隔值（例如，小于 一毫秒）时验证这一点仍然成立。

跨源执行

通过 采集样本算法中的域检查，API 应无法观察到跨源执行上下文。因此，与性能分析器 共享同一个代理的跨源 iframes 和其他执行上下文，其执行情况将无法通过此 API 被观察到。

计时攻击

对于任何可能引入新的高精度计时 信息来源的 API，计时攻击始终是需要关注的问题。跟踪记录中收集的时间戳应与 [[?HR-Time]] 的 当前高精度时间来自同一来源，以避免引入新的侧信道攻击途径。

请参阅 [[?HR-Time]] 中关于时钟 分辨率的讨论。

有条件的标记暴露

默认情况下，过滤标记算法仅在性能分析器的环境设置对象的跨源隔离 能力设置为 true 时，才暴露 script、gc、 paint 和 other 标记。这些标记可能反映无法可靠归属于 单一源的引擎工作 — 例如，垃圾回收和其他跨上下文的引擎活动可能 将不同上下文中的工作关联起来，而绘制可能合成来自其他框架的内容。在没有隔离的情况下暴露 此类工作的时间信息，因而可能促成某种跨源侧信道，而这正是 跨源 隔离旨在缓解的风险，因此对此类标记的暴露以跨源隔离为前提。用户代理可以通过显式选择启用来扩大所暴露的 集合（如上文过滤标记的注记所述），但此类选择启用机制 不得跨源暴露标记。

style 和 layout 标记无需跨源隔离即可暴露， 因为它们揭示的时间信息已经可以在同源范围内观察到。文档已经能够同步地 刷新自身的样式和布局，并使用现有 API 测量所需时间 — 例如， getBoundingClientRect() 会强制执行布局，而 getComputedStyle() 会刷新样式 （以及在需要时刷新布局）。为保持此性质，捕获标记算法仅针对以下情况报告 标记：工作是为与性能分析器同源的文档执行的；对于无法 归属于同源文档的工作，不通过这些标记报告。因此，它们不会暴露 同源文档原本无法自行获取的任何 时间信息。
