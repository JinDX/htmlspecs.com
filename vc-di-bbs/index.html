1. 简介

本规范定义了一种密码套件，用于 按照数据完整性 [VC-DATA-INTEGRITY-1.1] 规范， 使用 BBS 签名方案创建、验证和派生证明。 BBS 签名方案直接提供选择性披露和不可关联的 证明。它提供四个在发行者、 持有者、验证者模型中工作的高级函数。具体而言，发行者使用 BBS Sign 函数 创建一种称为“BBS 签名”的密码学值，该值用于对 原始凭证进行签名。持有者收到 使用 BBS 签名的凭证后，会使用 BBS Verify 函数验证该凭证。

然后，持有者从收到的凭证中选择要选择性披露的信息， 并使用 BBS ProofGen 函数生成一个 称为“BBS 证明”的密码学值，该值用于为此“派生凭证”创建 证明。密码学“BBS 证明”值无法与 原始“BBS 签名”关联，并且持有者可以为其他“派生凭证” 生成不同且不可关联的“BBS 证明”，包括任何 包含完全相同信息的凭证。 最后，验证者使用 BBS ProofVerify 函数验证从持有者收到的派生 凭证。

将 BBS 签名方案应用于可验证凭证涉及 本文档中规定的处理。 通常，该套件使用 RDF 数据集规范化算法 [RDF-CANON] 将输入文档转换为其 规范形式。然后，颁发者使用选择性披露原语将 规范形式分为强制性语句和非强制性语句。这些语句与其他信息 分别进行处理，并与适当的密钥材料一起作为 BBS Sign 函数的输入。此输出用于 生成受保护的凭证。持有者在收到凭证后使用一组选择性披露 函数和 BBS Verify 函数 来确定其有效性。

类似地，在收到使用 BBS 签名的凭证后，持有者使用 RDF 数据集 规范化算法 [RDF-CANON] 将输入 文档转换为其规范形式，然后应用选择性披露 原语，将规范形式分为强制性语句和选择性 披露的语句，这些语句经过适当处理并作为 BBS ProofGen 函数的输入。经过适当处理后，此函数的输出 将成为发送给验证者的已签名选择性披露凭证。通过使用 规范化和选择性披露原语，验证者随后可以使用 BBS verifyProof 函数验证该凭证。

2. 数据模型

以下各节概述了本规范用于验证 方法和数据完整性证明 格式的数据模型。

2.1 验证方法

这些验证方法用于验证使用符合 [CFRG-BBS-SIGNATURE] 的 BLS12-381 密码密钥材料 生成的数据完整性证明 [VC-DATA-INTEGRITY-1.1]。这些 密钥类型的编码格式 在本节中给出。在处理数字签名期间， 可以使用能够生成等效密码密钥材料的无损密码密钥转换 过程。

2.1.1 Multikey

受控标识符 v1.0中定义的 Multikey 格式用于表示本规范中 定义的密码套件所使用的公钥。

publicKeyMultibase 属性表示 BLS12-381 G2 群中 381 位公钥的 Multibase 编码 Multikey 表达形式。

验证方法的 publicKeyMultibase 值必须 以 base-58-btc 前缀（z）开头，该前缀定义于 受控标识符 v1.0的 Multibase 一节。随后是 一个经过 Multibase 编码的 BLS12-381 381 位公钥值， 如受控标识符 v1.0的 Multikey 一节中所定义。 不得允许任何其他编码。

建议开发者不要意外发布私钥的表示形式。 如果在 publicKeyMultibase 值中使用了 0xeb01 之外的 Multicodec 值，本规范的实现将产生错误。

2.2 证明表示

2.2.1 DataIntegrityProof

证明包含 [VC-DATA-INTEGRITY] 的 证明一节 中指定的属性，并具有以下限制。

证明的 verificationMethod 属性必须是一个 URL。 对 verificationMethod 进行解引用必须得到一个对象， 该对象包含值设置为 Multikey 的 type 属性。

证明的 type 属性必须为 DataIntegrityProof。

证明的 cryptosuite 属性必须为 bbs-2023。

证明的 proofValue 属性值必须是一个 按照 [CFRG-BBS-SIGNATURE] 生成的 BBS 签名或 BBS 证明，并按照第 3. 算法节中的过程进行序列化和 编码。

3. 算法

以下算法描述了如何将可验证凭证与 BBS 签名方案 [CFRG-BBS-SIGNATURE] 一起使用。使用 BBS 签名 方案时，应该使用 SHA-256 变体。

在添加或验证证明时，实现应该尽早获取并缓存验证方法信息。本节中传递给 函数的参数使用来自验证 方法的信息（例如公钥大小）来确定函数参数（例如 密码哈希算法）。

使用 RDF 数据集规范化算法 [RDF-CANON] 时， 该算法的实现默认会检测 数据集投毒， 并在检测到后中止处理。

3.1 实例化密码套件

此算法用于配置一个密码套件，供 可验证凭证数据完整性 1.1中的 添加证明和 验证证明 函数使用。该算法接受一个选项对象 （映射 options） 作为输入，并返回一个密码套件 实例（结构体 cryptosuite）。

  1. 将 cryptosuite 初始化为空结构体。
  2. 如果 options.type 不等于 DataIntegrityProof，返回 cryptosuite。
  3. 如果 options.cryptosuite 为 bbs-2023，则：
    1. 将 cryptosuite.createProof 设置为第 3.3.1 创建基础证明 (bbs-2023)节中的算法。
    2. 将 cryptosuite.verifyProof 设置为第 3.3.5 验证派生证明 (bbs-2023)节中的算法。
  4. 返回 cryptosuite。

3.2 bbs-2023 函数

3.2.1 serializeBaseProofValue

以下算法序列化基础证明值，其中包括 BBS 签名、HMAC 密钥和强制指针。 必需的输入为基础签名 bbsSignature、bbsHeader、 publicKey、HMAC 密钥 hmacKey、一个 mandatoryPointers 数组、featureOption，以及根据 featureOption 的值，可能还包括 signer_nym_entropy 值。 输出会生成单个基础证明字符串值。

  1. 根据 featureOption 的值，按如下方式设置 proofValue。
  2. 如果 featureOption 等于 "baseline"：
    1. 初始化一个字节数组 proofValue，其起始内容为 BBS 基础证明 头字节 0xd9、0x5d 和 0x02。
    2. 将 components 初始化为包含以下五个元素值的数组： bbsSignature、bbsHeader、publicKey、hmacKey 和 mandatoryPointers。
  3. 如果 featureOption 等于 "anonymous_holder_binding"：
    1. 初始化一个字节数组 proofValue，其起始内容为 BBS 基础证明 头字节 0xd9、0x5d 和 0x04。
    2. 将 components 初始化为包含以下六个元素值的数组： bbsSignature、bbsHeader、publicKey、hmacKey 和 mandatoryPointers。
  4. 如果 featureOption 等于 "pseudonym"：
    1. 初始化一个字节数组 proofValue，其起始内容为 BBS 基础证明 头字节 0xd9、0x5d 和 0x06。
    2. 将 components 初始化为包含以下六个元素值的数组： bbsSignature、bbsHeader、publicKey、hmacKey、 mandatoryPointers 和 signer_nym_entropy。
  5. 如果 featureOption 等于 "holder_binding_pseudonym"：
    1. 初始化一个字节数组 proofValue，其起始内容为 BBS 基础证明 头字节 0xd9、0x5d 和 0x08。
    2. 将 components 初始化为包含以下六个元素值的数组： bbsSignature、bbsHeader、publicKey、hmacKey、 mandatoryPointers 和 signer_nym_entropy。
  6. 按照 [RFC8949] 对 components 进行 CBOR 编码，其中对任何 components 不得使用 CBOR 标记。 将生成的编码值附加到 proofValue。
  7. 将 baseProof 初始化为使用 proofValue 的 multibase-base64url-no-pad 编码得到的字符串。也就是说，返回一个以“u”开头并以 proofValue 的 base64url-no-pad 编码值结尾的字符串。
  8. 将 baseProof 作为基础证明返回。

3.2.2 parseBaseProofValue

以下算法解析 bbs-2023 选择性 披露基础证明值的各个组成部分。必需的输入是一个证明值 （proofValue）。输出会生成单个对象已解析基础证明，其中包含 六个或七个元素，名称分别为 "bbsSignature"、"bbsHeader"、 "publicKey"、 "hmacKey"、"mandatoryPointers"、"featureOption"，以及可能存在的可选功能 参数 "signer_nym_entropy"。

  1. 如果 proofValue 字符串不是以 u （U+0075 LATIN SMALL LETTER U）开头， 表明它不是一个 multibase-base64url-no-pad-encoded 值， 则必须引发错误，并且应该传达 PROOF_VERIFICATION_ERROR 错误类型。
  2. 将 decodedProofValue 初始化为对 proofValue 中前导 u 之后的子字符串进行 base64url-no-pad 解码的结果。
  3. 检查 BBS 基础证明是否以允许的头值开头，并按如下方式设置 featureOption 变量：
    1. 如果 decodedProofValue 以字节 0xd9、 0x5d 和 0x02 开头，则将 featureOption 设置为 "baseline"。
    2. 如果 decodedProofValue 以字节 0xd9、 0x5d 和 0x04 开头，则将 featureOption 设置为 "anonymous_holder_binding"。
    3. 如果 decodedProofValue 以字节 0xd9、 0x5d 和 0x06 开头，则将 featureOption 设置为 "pseudonym"。
    4. 如果 decodedProofValue 以字节 0xd9、 0x5d 和 0x08 开头，则将 featureOption 设置为 "holder_binding_pseudonym"。
    5. 如果 decodedProofValue 以任何其他三字节序列开头， 则必须引发错误，并且应该 传达 PROOF_VERIFICATION_ERROR 错误类型。
  4. 将 components 初始化为一个数组，该数组是对 三字节 BBS 基础证明头之后的字节进行 CBOR 解码的结果。
  5. 根据 featureOption 的值，基于 components 返回一个对象， 如下所示：
    1. 如果 featureOption 等于 "baseline"，则按顺序将基于 components 的对象 属性名设置为 "bbsSignature"、"bbsHeader"、"publicKey"、"hmacKey" 和 "mandatoryPointers"，并添加 featureOption 作为属性。
    2. 如果 featureOption 等于 "anonymous_holder_binding"，则将 基于 components 的对象属性名按顺序设置为 "bbsSignature"、"bbsHeader"、 "publicKey"、"hmacKey" 和 "mandatoryPointers"，并 添加 featureOption 作为属性。
    3. 如果 featureOption 等于 "pseudonym"，则将 基于 components 的对象属性名按顺序设置为 "bbsSignature"、"bbsHeader"、 "publicKey"、"hmacKey"、"mandatoryPointers" 和 "signer_nym_entropy"，并 添加 featureOption 作为属性。
    4. 如果 featureOption 等于 "holder_binding_pseudonym"，则将 基于 components 的对象属性名按顺序设置为 "bbsSignature"、"bbsHeader"、 "publicKey"、"hmacKey"、"mandatoryPointers" 和 "signer_nym_entropy"，并 添加 featureOption 作为属性。

3.2.3 serializeDerivedProofValue

以下算法序列化派生证明值。必需的输入 为 BBS 证明（bbsProof）、标签映射（labelMap）、一个 强制索引数组（mandatoryIndexes）、一个 选择性索引数组（selectiveIndexes）、BBS 呈现头 （presentationHeader）、featureOption 指示符，以及 根据 featureOption 的值，一个 nym_domain、pseudonym 和/或 lengthBBSMessages 值。 输出会生成单个派生证明 值，并将其序列化为字节字符串。

  1. 将 compressedLabelMap 初始化为调用 第 节中的算法并将 labelMap 作为参数传入所得的结果。
  2. 根据 featureOption 的值执行以下操作：
    1. 如果 featureOption 等于 "baseline"：
      1. 将 proofValue 初始化为以 披露证明头字节 0xd9、0x5d 和 0x03 开头。
      2. 将 components 初始化为包含以下值的元素数组： bbsProof、compressedLabelMap、mandatoryIndexes、 selectiveIndexes 和 presentationHeader。
    2. 如果 featureOption 等于 "anonymous_holder_binding"：
      1. 将 proofValue 初始化为以 披露证明头字节 0xd9、0x5d 和 0x05 开头。
      2. 将 components 初始化为包含以下值的元素数组： bbsProof、compressedLabelMap、mandatoryIndexes、 selectiveIndexes、 presentationHeader 和 lengthBBSMessages。
    3. 如果 featureOption 等于 "pseudonym"：
      1. 将 proofValue 初始化为以 披露证明头字节 0xd9、0x5d 和 0x07 开头。
      2. 将 components 初始化为包含以下值的元素数组： bbsProof、compressedLabelMap、mandatoryIndexes、 selectiveIndexes、 presentationHeader、nym_domain、pseudonym 和 lengthBBSMessages。
    4. 如果 featureOption 等于 "holder_binding_pseudonym"：
      1. 将 proofValue 初始化为以 披露证明头字节 0xd9、0x5d 和 0x09 开头。
      2. 将 components 初始化为包含以下值的元素数组： bbsProof、compressedLabelMap、mandatoryIndexes、 selectiveIndexes、 presentationHeader、nym_domain、pseudonym 和 lengthBBSMessages。
  3. 按照 [RFC8949] 对 components 进行 CBOR 编码，其中对任何 components 不得使用 CBOR 标记。 将生成的编码值附加到 proofValue。
  4. 将派生证明作为使用 proofValue 的 multibase-base64url-no-pad 编码得到的字符串返回。也就是说，返回一个 以“u”开头并以 proofValue 的 base64url-no-pad 编码值结尾的字符串。

3.2.4 parseDerivedProofValue

以下算法解析派生证明值的各个组成部分。 必需的输入是一个派生证明值（proofValue）。输出会生成 单个派生证明值对象，其中 包含六至九个元素，名称为 "bbsProof"、 "labelMap"、"mandatoryIndexes"、"selectiveIndexes"、"presentationHeader"、 "featureOption"，并且根据 featureOption 参数的值， 还包括 "nym_domain"、"pseudonym" 和/或 "lengthBBSMessages"。

  1. 如果 proofValue 字符串不是以 u （U+0075， LATIN SMALL LETTER U）开头，表明 它不是一个 multibase-base64url-no-pad-encoded 值， 则必须引发错误，并且应该传达 PROOF_VERIFICATION_ERROR 错误类型。
  2. 将 decodedProofValue 初始化为对 proofValue 中前导 u 之后的子字符串进行 base64url-no-pad 解码的结果。
  3. 检查 BBS 披露证明是否以允许的头值开头，并按如下方式设置 featureOption 变量：
    1. 如果 decodedProofValue 以头字节 0xd9、 0x5d 和 0x03 开头，则将 featureOption 设置为 "baseline"。
    2. 如果 decodedProofValue 以头字节 0xd9、 0x5d 和 0x05 开头，则将 featureOption 设置为 "anonymous_holder_binding"。
    3. 如果 decodedProofValue 以头字节 0xd9、 0x5d 和 0x07 开头，则将 featureOption 设置为 "pseudonym"。
    4. 如果 decodedProofValue 以头字节 0xd9、 0x5d 和 0x09 开头，则将 featureOption 设置为 "holder_binding_pseudonym"。
  4. 将 components 初始化为一个数组，该数组是对 三字节 BBS 披露证明头之后的字节进行 CBOR 解码的结果。如果该结果 不是包含五个、六个、七个或八个元素的数组， 则必须引发错误，并且应该传达 PROOF_VERIFICATION_ERROR 错误类型。
  5. 使用调用 第 节中的算法所得的结果替换 components 中的第二个元素，将 components 中现有的 第二个元素作为 compressedLabelMap 传入。
  6. 将派生证明值作为一个对象返回，其属性分别设置为这五个、 六个、七个或八个元素，并使用名称 "bbsProof"、"labelMap"、 "mandatoryIndexes"、"selectiveIndexes"、"presentationHeader"，以及可选的 "nym_domain"、"pseudonym" 和/或 "lengthBBSMessages"。 此外，将 featureOption 及其值添加到该对象。

3.3 bbs-2023

bbs-2023 密码套件接受一个输入文档，并使用 RDF 数据集规范化算法 [RDF-CANON] 对文档进行规范化，然后应用一系列 转换和密码学 操作，最终生成数据完整性证明。本节中的算法 还包括对此类数据完整性证明的验证。

3.3.1 创建基础证明 (bbs-2023)

以下算法规定了在给定 未保护数据 文档的情况下如何创建数据完整性 证明。 必需的输入为一个 未保护数据 文档（映射 unsecuredDocument）、一组证明 选项（映射 options）、一个强制 JSON 指针数组 （mandatoryPointers）、一个 featureOption 指示符参数，以及根据 featureOption，一个 commitment_with_proof 字节数组。 输出会生成一个数据完整性 证明（映射） 或一个错误。

featureOption 参数用于指示正在使用哪项可选功能（如果有）。 它可以采用以下值之一："baseline"、 "anonymous_holder_binding"、"pseudonym" 或 "holder_binding_pseudonym"。请注意，"baseline" 用于表示 不使用任何可选功能的情况。如果 featureOption 设置为 "anonymous_holder_binding"、"pseudonym" 或 "holder_binding_pseudonym"，则 必须提供 commitment_with_proof 输入。 如果 featureOption 设置为 "pseudonym" 或 "holder_binding_pseudonym"，则 必须提供 signer_nym_entropy 输入。

  1. 令 proof 为证明选项 options 的克隆。
  2. 令 proofConfig 为运行 § 4.2.4.2 证明配置节中的算法并将 options 作为参数传入所得的结果。
  3. 令 transformedData 为运行 § 4.4.1 TransformSD 中的算法并将 unsecuredDocument、 proofConfig 和 options 作为参数传入所得的结果。
  4. 令 hashData 为运行 § 4.4.2 HashSD 中的算法并将 transformedData 和 proofConfig 作为参数传入所得的结果。
  5. 令 proofBytes 为运行第 3.3.2 基础证明序列化 (bbs-2023)节中的算法并将 hashData、 options、featureOption，以及在需要时将 commitment_with_proof 作为 参数传入所得的结果。
  6. 令 proof.proofValue 为 proofBytes 的 base64url 编码的 Multibase 值。
  7. 将 proof 作为数据完整性 证明返回。

3.3.2 基础证明 序列化 (bbs-2023)

以下算法由受 BBS 保护的可验证 凭证的发行者调用，规定了如何创建基础证明。该基础证明只会 提供给持有者，由持有者负责从中生成派生证明， 并仅向验证者公开证明中选择性披露的详细信息。此 算法设计为与数据完整性 [VC-DATA-INTEGRITY-1.1] 规范 第 4 节：算法中定义的算法结合使用。必需的输入为 密码哈希数据（hashData）、 featureOption，以及在需要时提供的 commitment_with_proof。 如果 featureOption 设置为 "anonymous_holder_binding"、 "pseudonym" 或 "holder_binding_pseudonym"，则 必须提供 commitment_with_proof 输入；如果未提供， 则必须引发错误，并且应该传达 PROOF_GENERATION_ERROR 错误类型。 如果 featureOption 设置为 "pseudonym" 或 "holder_binding_pseudonym"，则 必须提供 signer_nym_entropy 输入；如果未提供， 则必须引发错误，并且应该传达 PROOF_GENERATION_ERROR 错误类型。 输出会生成一个以一系列字节表示的数字证明值。

  1. 将 proofHash、mandatoryPointers、mandatoryHash、 nonMandatory 和 hmacKey 初始化为 hashData 中与其属性名关联的值。
  2. 将 bbsHeader 初始化为依次连接 proofHash 和 mandatoryHash 所得的结果。
  3. 将 bbsMessages 初始化为一个字节数组的数组，其中包含 使用 UTF-8 字符编码编码的 nonMandatory 字符串数组中的值。
  4. 根据 featureOption 的值，使用以下过程计算 bbsSignature。
    1. 如果 featureOption 等于 "baseline"，则使用 [CFRG-BBS-Signature] 的 Sign 过程计算 bbsSignature， 使用适当的密钥材料，将 bbsHeader 作为 header，并将 bbsMessages 作为 messages。
    2. 如果 featureOption 等于 "anonymous_holder_binding"，则使用 [CFRG-Blind-BBS-Signature] 的 BlindSign 过程计算 bbsSignature， 使用适当的密钥材料，将 commitment_with_proof 作为 commitment_with_proof，将 bbsHeader 作为 header， 并将 bbsMessages 作为 messages。这提供 匿名持有者绑定功能。
    3. 如果 featureOption 等于 "pseudonym" 或 "holder_binding_pseudonym"， 发行者会为 signer_nym_entropy 生成一个 密码学随机值，并使用 [CFRG-Pseudonym-BBS-Signature] 中的 "Blind Issuance" 操作计算 bbsSignature， 使用 适当的密钥材料， 将 bbsHeader 作为 header， 将 bbsMessages 作为 messages， 将 commitment_with_proof 作为 commitment_with_proof，以及 signer_nym_entropy 值。 如果发行者将来可能需要向此持有者重新发行 绑定到相同 nym_secret 的凭证，则应该 保留 signer_nym_entropy 值；否则，可以丢弃该值。

      这提供凭证绑定的 假名或持有者绑定和 假名功能。
  5. 将 `proofValue 初始化为调用第 3.2.1 serializeBaseProofValue节中的算法所得的结果，将 bbsSignature、 bbsHeader、 publicKey、hmacKey、mandatoryPointers、 featureOption，以及根据 featureOption 的值将 signer_nym_entropy 作为参数传入。

    注意：publicKey 是公钥的字节数组，按照 [CFRG-BBS-SIGNATURE] 进行编码。
  6. 将 proofValue 作为数字证明返回。

3.3.3 添加派生证明 (bbs-2023)

以下算法由受 bbs-2023 保护的 可验证 凭证的持有者调用，用于创建选择性披露派生证明。 该派生证明将提供给验证者。输入包括一个 JSON-LD 文档（document）、一个 BBS 基础证明 （proof）、一个用于选择性披露 语句的 JSON 指针数组（selectivePointers）、一个可选的 BBS presentationHeader（字节数组）、一个 featureOption 参数、支持所选 featureOption 的附加参数（见下文）， 以及任何自定义 JSON-LD API 选项， 例如文档加载器。输出会生成单个选择性公开的文档 值，以对象表示。

如果 featureOption 等于 "anonymous_holder_binding"， 必需的附加输入为 holderSecret 和 proverBlind。这些值应当 已由持有者预先计算。有关背景 信息，请参见 匿名持有者绑定。

如果 featureOption 等于 "pseudonym"，必需的 附加输入为 prover_nym 和 proverBlind，两者均为 持有者所知，以及 nym_dofmain，后者由持有者设置或由验证者传达 给持有者。 有关背景信息，请参见凭证绑定的假名。

如果 featureOption 等于 "holder_binding_pseudonym"，必需的 附加输入为 holder_secret、prover_nym 和 proverBlind， 这些值 均为持有者所知，以及 nym_dofmain，后者由持有者设置或 由验证者传达给持有者。 有关背景信息，请参见持有者绑定和假名。

  1. 令 proofData 对象为第 3.2.2 parseBaseProofValue节中的算法返回的结果。 proofData 对象至少会包含字段 bbsSignature、 bbsHeader、publicKey、hmacKey、mandatoryPointers 和 featureOption。 根据 featureOption 的值，可能还会存在其他字段。
  2. 将 disclosureData 初始化为调用 § 4.4.3 CreateDisclosureData中的算法并传入 document、proofData、 selectivePointers 以及任何自定义 JSON-LD API 选项（例如文档 加载器）时返回的对象。disclosureData 对象将包含以下字段： revealDocument、mandatoryIndexes、selectiveIndexes、 verifierLabelMap mandatory 和 nonMandatory。
  3. 将 newProof 初始化为 proof 的浅拷贝。
  4. 将 newProof 中的 proofValue 替换为调用 第 3.3.4 派生证明序列化节中的算法，并将 proofData 和 disclosureData 作为参数传入所得的结果。
  5. 将 revealDocument 中 "proof" 属性的值设置为 newProof。
  6. 将 revealDocument 作为选择性公开的文档返回。

3.3.4 派生证明 序列化

以下算法生成派生证明。 输入为 proofData 和 disclosureData 对象。

  1. 将 bbsMessages 初始化为一个字节数组的数组，其中包含 使用 UTF-8 字符编码编码的 nonMandatory 字符串数组中的值。
  2. 根据 featureOption 参数的值， 将 bbsProof 设置为通过下面相应过程计算得到的值。
    1. 如果 featureOption 等于 "baseline"， 将 bbsProof 设置为通过 [CFRG-BBS-SIGNATURE] 中的 ProofGen 过程计算得到的值，即 ProofGen(PK, signature, header, ph, messages, disclosed_indexes)， 其中 PK 是原始发行者的公钥，signature 是 bbsSignature，header 是 bbsHeader， ph 是 presentationHeader messages 是 bbsMessages，disclosed_indexes 是 selectiveIndexes。
    2. 如果 featureOption 等于 "anonymous_holder_binding"， 将 bbsProof 设置为通过 [CFRG-Blind-BBS-Signature] 中的 BlindProofGen 过程计算得到的值，其中 PK 是原始发行者的公钥， signature 是 bbsSignature，header 是 bbsHeader，ph 是 presentationHeader， messages 是 bbsMessages，disclosed_indexes 是 selectiveIndexes， 以及 commitment_with_proof。持有者还将提供其 holder_secret，以及用于计算 commitment_with_proof 的 proverBlind。这是 匿名持有者绑定功能选项。 将在 IETF API 最终确定后 更新。
    3. 如果 featureOption 等于 "pseudonym"， 使用 [CFRG-Pseudonym-BBS-Signature] 中的 "Verification and Finalization" 操作， 并使用空的 committed_messages 数组， 以同时验证 bbsSignature 并计算 nym_secret 值。此操作使用 prover_nym、 signer_nym_entropy 和 secret_prover_blind。

      确定 nym_domain。根据使用场景，它可能由 验证者指定，也可能由持有者设置。使用 [CFRG-Pseudonym-BBS-Signature] 中的 "Proof Generation with Pseudonym" 操作来生成派生证明。 此操作接受以下输入： 将原始发行者的公钥作为 PK， 将 bbsSignature 作为 signature， 将 bbsHeader 作为 header， 将 presentationHeader 作为 ph， 将 bbsMessages 作为 messages， 将 selectiveIndexes 作为 disclosed_indexes， 一个 nym_secret， 一个 nym_domain， 一个用于 committed_messages 的空数组， 以及一个 secret_prover_blind。 除提供 分配给 bbsProof 的原始 密码证明值外， 它还会返回 pseudonym。

      这是用于 凭证绑定的假名 功能选项。将在 IETF API 最终确定后更新。
    4. 如果 featureOption 等于 "holder_binding_pseudonym"， 使用 [CFRG-Pseudonym-BBS-Signature] 中的 "Verification and Finalization" 操作， 并使用仅包含 holder_secret 作为其唯一值的 committed_messages 数组， 以同时验证 bbsSignature 并计算 nym_secret 值。此操作使用 prover_nym、 signer_nym_entropy 和 secret_prover_blind。

      确定 nym_domain。根据使用场景，它可能由 验证者指定或由持有者设置。使用 [CFRG-Pseudonym-BBS-Signature] 中的 "Proof Generation with Pseudonym" 操作来生成派生证明。 此操作接受以下输入： PK，即原始发行者的公钥， signature，即 bbsSignature，header 是 bbsHeader， ph 是 presentationHeader， messages 是 bbsMessages，disclosed_indexes 是 selectiveIndexes， 此操作接受以下输入： 将原始发行者的公钥作为 PK， 将 bbsSignature 作为 signature， 将 bbsHeader 作为 header， 将 presentationHeader 作为 ph， 将 bbsMessages 作为 messages， 将 selectiveIndexes 作为 disclosed_indexes， 一个 nym_secret， 一个 nym_domain， 将 committed_messages 数组的唯一值作为 holder_secret， 以及一个 secret_prover_blind。 除 提供分配给 bbsProof 的原始密码证明值外， 它还会返回 pseudonym。 这是用于 持有者绑定和假名 功能选项。将在 IETF API 最终确定后更新。
  3. 如果 featureOption 等于 "anonymous_holder_binding"、 "pseudonym" 或 "holder_binding_pseudonym"，则将 lengthBBSMessages 参数设置为 bbsMessages 数组的长度。
  4. 返回调用 3.2.3 serializeDerivedProofValue 算法所得的值，其参数分别对应 bbsProof、将 "verifierLabelMap" 作为 labelMap、 mandatoryIndexes、selectiveIndexes、revealDocument、 pseudonym，以及在 已计算时传入 lengthBBSMessages。

  1. 令 unsecuredDocument 为移除 proof 值后的 document 副本。

4. 可选功能

本节为非规范性内容。

BBS 签名的密码学属性允许支持 高级功能的变体。本规范仅限于 支持这些增强功能中最相关的部分，我们将在 以下各节中进行说明。变量 commitment_with_proof、holder_secret、 prover_nym、signer_nym_entropy 和 pseudonym 与这些 功能相关，除此之外 BBS 签名和证明并不需要它们。

议题 1：可选 BBS 功能存在风险

本节描述并包含在本规范 算法中的可选 BBS 功能存在风险，如果它们各自的规范 未能按照相同的时间表在 IETF 达到 RFC 状态，或者每项可选 功能没有至少两个独立实现，则会在 本规范最终定稿前将其移除。

4.1 匿名持有者绑定

此功能在颁发时将带有基础证明的文档绑定到一个 只有持有者知道的秘密，使得只有该持有者才能生成 能够通过验证的带派生证明的披露文档。例如，如果 攻击者获得了带基础证明的文档，他们也无法创建 能够通过验证的带派生证明的披露文档。

为提供此功能，持有者生成一个 holder_secret 值， 该值通常应至少为 32 字节长，并以密码学随机方式 生成。持有者绝不会共享该值。相反，持有者 使用 [CFRG-Blind-BBS-Signature] 的“承诺计算”操作， 生成一个承诺以及对知晓该 值的零知识证明。 此计算涉及密码学随机值，并计算 commitment_with_proof 和 secret_prover_blind 值。 commitment_with_proof 会传达给颁发者，而 secret_prover_blind 则保持秘密，并由持有者保留以用于 生成派生证明。 请注意，持有者可以多次运行“承诺计算”操作， 以生成不可关联的 commitment_with_proof 值供不同颁发者使用。

颁发者在收到 commitment_with_proof 后，按照本规范的 过程，并使用 [CFRG-Blind-BBS-Signature] 的“盲签名生成”操作，在文档上生成基础证明 （签名）， 其中使用持有者提供的 commitment_with_proof。

当持有者希望创建带有派生 证明的选择性披露文档时，他们使用本规范中的过程以及 [CFRG-Blind-BBS-Signature] 的“证明生成”操作。他们将自己的 holder_secret 作为 commited messages 数组中唯一的“消息”，并提供自己的 secret_prover_blind。

对带派生证明的披露文档进行验证时，使用 本规范中的过程以及 [CFRG-Blind-BBS-Signature] 的“证明验证”操作。

4.2 凭据绑定假名

本文档规定的使用 BBS 签名的可验证凭证支持 选择性披露和不可关联的密码学证明制品。所谓 “不可关联”，是指 派生证明中的密码学信息无法与其他 证明或原始签名关联。这意味着验证者无法确定 持有者以前是否出示过相同的凭证（使用不同的证明 实例），也无法据此断言某种身份。凭据绑定 假名提供了一种保护隐私的机制，允许密码学假名具备有限的 可关联性。此类假名可以完全由持有者确定， 也可以由持有者和验证者共同确定。

这种密码学假名（密码学标识符/名称）由 两部分计算而成。第一部分 nym_secret 由 持有者指定并且只有持有者知道； 第二部分 nym_domain 可以由持有者 或验证者指定，并由持有者和验证者共享。 颁发者在颁发过程中将凭据绑定到 nym_secret。 随后持有者可以根据 nym_secret 计算假名，并向 验证者证明这些假名与其正在出示的凭据绑定。 使用相同 nym_secret 但不同 nym_domain 值计算出的密码学假名彼此不可关联。

持有者可能会选择一个 nym_domain，以便为自己在某种 公共论坛中使用假名，例如选择 nym_domain = "Mark Twain"。 持有者使用该 nym_domain 和自己的 nym_secret 计算出的密码学假名基本上是唯一的，并且任何既不 知道 nym_secret 也不持有绑定到该 假名的基础可验证凭证的实体，都无法断言这一假名身份。请注意， （nym_domain, pseudonym）这一二元组必须与派生凭证一起发送，才能断言 此假名身份。

在另一种情况下，持有者可能正在使用验证者提供的服务，而 验证者希望跟踪一段时间内的访问情况，或者监控持有者对某些资源的 使用。在这种情况下，验证者选择持有者 在出示其派生凭证时需要使用的 nym_domain。例如， 验证者可能指定与其 DNS 域名绑定的公共 nym_domain（例如 "www.nym.example"）供持有者使用。验证者还可以 通过定期 更改 nym_domain（例如将其与日期绑定， "www.nym.example/2025-01-02"），表明其以某种方式支持数据最小化。本规范不规定 nym_domain 的取值。

最后，为防止恶意持有者获得另一持有者的 nym_secret 后得到绑定到该值的凭据， [CFRG-Pseudonym-BBS-Signature] 中的操作会让颁发者 添加一个随机化 因子 signer_nym_entropy，在生成签名期间将其与持有者的 部分 prover_nym 安全地“混合”。这会得到一个 nym_secret，颁发者可以从密码学上保证 该值是唯一的，供持有者使用。

凭据绑定假名的创建和使用概览如下 所示。

  1. 持有者创建一个称为 prover_nym 的安全值，该值应 至少为 32 字节长，并以密码学随机方式生成。然后 使用 [CFRG-Pseudonym-BBS-Signature] 中的 "Commitment" 操作，并传入空的 committed_messages 数组，以计算 commitment_with_proof 和 secret_prover_blind。持有者将 commitment_with_proof 连同凭据请求发送给颁发者，但绝不会 披露 prover_nym 和 secret_prover_blind，而是将它们保留供以后使用。
  2. 颁发者收到持有者关于带绑定假名凭据的请求 （featureOption 等于 "pseudonym"），以及 commitment_with_proof。 颁发者为 signer_nym_entropy 生成一个密码学随机值，并使用 [CFRG-Pseudonym-BBS-Signature] 中的“盲颁发”操作生成 基础证明。除其他 信息外，基础证明还将包含 signer_nym_entropy 值。如果 颁发者将来可能需要向该持有者重新颁发绑定到 同一 nym_secret 的凭据，则应保留 signer_nym_entropy 值； 否则，可以丢弃该值。
  3. 持有者收到带绑定假名的凭据后，使用本规范中的 过程，以及 [CFRG-Pseudonym-BBS-Signature] 中的“验证和最终确定”操作，并传入空的 committed_messages 数组， 以同时验证签名并计算 nym_secret 值。此操作 会使用 prover_nym、signer_nym_entropy 和 secret_prover_blind 等值。如果正在使用第三方监控，则需要将 nym_secret 值安全地共享给监控组织。
  4. 当持有者希望生成绑定到假名的派生证明时，需要 确定 nym_domain。如前所述，根据使用场景， 它可能由验证者指定，也可能由持有者设置。然后使用 本规范中的过程和 [CFRG-Pseudonym-BBS-Signature] 中的“使用假名生成证明” 操作来生成派生证明。 此操作的输入包括 nym_secret、nym_domain、空的 committed_messages 数组以及 secret_prover_blind 等。除了提供原始 密码学证明值之外，它还会返回 pseudonym 值，该值会 包含在派生证明中。
  5. 当验证者收到带绑定假名的派生证明时，他们使用 本规范中的过程以及 [CFRG-Pseudonym-BBS-Signature] 中的 “使用假名验证证明”操作来验证 派生证明。请注意，这些 过程还会验证在计算 pseudonym 时使用了指定的 nym_domain。

4.3 持有者绑定和假名

从某种意义上说，匿名持有者绑定和凭据绑定假名是 相互正交的功能，持有者和凭据生态系统可能希望同时使用 二者。例如，持有者可能希望将可验证 凭据绑定到 holder_secret，使得只有知道该值的持有者才能 根据基础证明生成派生证明，同时将 nym_secret 绑定到 基础证明，使得假名可以绑定到派生证明。这 对应于 featureOption 等于 "holder_binding_pseudonym"。

同时创建和使用匿名持有者绑定和 凭据绑定假名的概览如下所示。

  1. 持有者创建两个称为 holder_secret 和 prover_nym 的安全值，它们应 至少为 32 字节长，并以密码学随机方式生成。然后 使用 [CFRG-Pseudonym-BBS-Signature] 中的“Commitment”操作，其中 committed_messages 数组输入仅包含 holder_secret， 以计算 commitment_with_proof 和 secret_prover_blind。 commitment_with_proof 会与凭据请求一起发送给颁发者， 而 holder_secret、prover_nym 和 secret_prover_blind 则由持有者 保留供以后使用，并且绝不会披露。
  2. 颁发者收到持有者关于带绑定假名凭据的请求， featureOption 等于 "pseudonym"，以及 commitment_with_proof。 颁发者使用本规范中的过程，并为 signer_nym_entropy 生成一个密码学随机值，然后使用 [CFRG-Pseudonym-BBS-Signature] 中的 “盲颁发”操作生成 基础证明。除其他信息外，基础证明还将包含 signer_nym_entropy 值。如果颁发者将来需要向 该持有者重新颁发绑定到同一 nym_secret 的凭据，则应保留 signer_nym_entropy 值，否则可以丢弃该值。
  3. 持有者收到带绑定假名的凭据后，使用本规范中的 过程以及 [CFRG-Pseudonym-BBS-Signature] 中的“验证和最终确定”操作，其中 committed_messages 数组 仅包含 holder_secret， 以同时验证签名并计算 nym_secret 值。此操作会使用 holder_secret、 prover_nym、 signer_nym_entropy 和 secret_prover_blind 等值。如果正在使用第三方 监控，则会将 nym_secret 值安全地 共享给监控组织。
  4. 当持有者希望生成绑定到假名的派生证明时，需要 确定 nym_domain。如前所述，根据使用场景， 它可能由验证者指定，也可能由持有者设置。然后使用 本规范中的过程以及 [CFRG-Pseudonym-BBS-Signature] 中的“使用假名生成证明” 操作来生成 派生证明。 此操作的输入包括 nym_secret、nym_domain、 仅包含 holder_secret 的 committed_messages 数组， 以及 secret_prover_blind 等。除了提供原始 密码学证明值之外，它还会返回 pseudonym 值，该值会 包含在派生证明中。
  5. 当验证者收到带绑定假名的派生证明时，他们使用 本规范中的过程以及 [CFRG-Pseudonym-BBS-Signature] 中的 “使用假名验证证明”操作来验证 派生证明。请注意，这些 过程还会验证在计算 pseudonym 时使用了指定的 nym_domain。

5. 安全注意事项

在阅读本节之前，强烈建议读者先熟悉 数据完整性规范 安全注意事项一节中提供的一般安全建议。

5.1 基础证明的安全属性

本节为非规范性内容。

基础证明的安全性取决于相关 BBS 签名的安全属性。数字签名可能具有多种 理想的密码学属性 [Taming_EdDSAs]，其中包括：

EUF-CMA（选择消息攻击下的 存在性不可伪造性）通常是签名方案所要求的最低安全属性。 它保证任何拥有签名者公钥 p k 并且收到任意数量的、针对其自行选择消息的签名 （以自适应方式）的高效攻击者： { m i , σ i } i = 1 N ， 都无法针对新消息输出有效签名 σ ∗ ，其中新消息 m ∗ ∉ { m i } i = 1 N （除非概率可忽略不计）。如果攻击者针对新消息输出了有效 签名： ( m ∗ , σ ∗ ) ， 则称为存在性伪造。

SUF-CMA（选择 消息攻击下的强不可伪造性）是比 EUF-CMA 更强的概念。它保证 对于任何拥有签名者公钥 p k 并收到任意数量的、针对其自行选择消息的签名的高效攻击者： { m i , σ i } i = 1 N ， 都无法输出新的有效签名对 ( m ∗ , σ ∗ ) ， 使得 ( m ∗ , σ ∗ ) ∉ { m i , σ i } i = 1 N （除非概率可忽略不计）。强不可伪造性意味着 攻击者不仅无法为新消息生成签名，也无法为旧消息 找到新的签名。

在 [CDL2016] 中，在一些合理假设下，BBS 签名被证明 具有 EUF-CMA 安全性。此外，在 [TZ2023] 中，在类似假设下，BBS 签名 被证明具有 SUF-CMA 安全性。在这两种情况下，这些假设都与 离散对数问题的困难性有关，而该问题并不被认为在大规模 量子计算出现后仍然安全。

在非量子计算条件下，[CFRG-BBS-SIGNATURE] 为 BBS 签名套件实现者提供了 其他安全指南。与配对友好曲线有关的进一步 安全注意事项在 [CFRG-PAIRING-FRIENDLY] 中讨论。

5.2 派生证明的安全 属性

本节为非规范性内容。

派生证明的安全性取决于相关 BBS 证明的安全属性。[CDL2016] 和 [TZ2023] 都证明了 BBS 证明是对持有 BBS 签名这一知识的零知识证明。

如 [CFRG-BBS-SIGNATURE] 中所解释的，这意味着：

收到证明的验证方无法确定生成该证明时 使用的是哪个签名，从而消除了一个常见的关联来源。一般而言， 即使两个证明是由同一签名生成的，每个生成的证明也都与随机值不可区分。

并且

该方案生成的证明向验证者证明，生成证明的一方 （持有者/证明者或其代理）持有一个 签名，而无需披露该签名。

更准确地说，验证BBS 证明需要原始 颁发者的公钥，以及按正确顺序排列且未被更改的、已披露的 BBS 消息。

6. 隐私注意事项

本节为非规范性内容。

6.1 选择性披露 和数据泄露

选择性披露允许持有者将向验证者 披露的信息最小化，以实现特定目的。在规定 一个支持选择性披露的完整系统时，需要谨慎确保 尽量减少向 验证者泄露原本无意披露的附加信息。此类泄露可能通过 系统制品发生。这些制品可能来自系统的高层，例如 数据结构，也可能来自底层密码学原语。

例如，BBS 签名方案是一种在多个 消息上生成签名时空间效率极高的方案，也就是说，无论 消息数量是多少，发送给持有者的密码学 签名大小都是恒定的。然后，持有者可以选择性地向 验证者披露其中任意消息；但是作为该 密码学方案的一部分，颁发者最初签名的消息总数 必须向验证者披露。如果需要避免这种信息泄露， 则建议按照 [CFRG-BBS-SIGNATURE] 隐私注意事项一节中的建议， 将消息数量填充到共同长度。

在更高层面，数据如何映射为适合选择性披露的各个 语句，即 BBS 消息，也是潜在的 数据泄露来源。此密码套件能够通过使用 JSON-LD 处理将 输入转换为 RDF，消除许多用于表示 JSON 数据且可能泄露信息的 结构性制品 （嵌套、映射或数组位置等）。然后 RDF 可以表示为一种规范化、扁平化的简单 主语、属性、值语句格式（在可验证 凭证数据模型 [VC-DATA-MODEL-2.0] 中称为声明）。下面， 我们研究 RDF 规范化，即一种将 JSON-LD 格式的可验证凭证映射为 一组语句（BBS 消息）以用于 选择性披露的通用方案。我们将说明在执行此过程后， 仍然存在一个可能的信息泄露来源，并说明如何通过使用 带密钥的伪随机函数（PRF）来缓解这种泄露。

RDF 规范化可用于将 JSON-LD VC 扁平化为一组 语句。该算法依赖于 VC 的内容， 并使用密码学哈希函数帮助对 语句排序。本质上，其工作方式是：JSON-LD 文档中 表示声明主体的每个 JSON 对象，如果没有定义 @id 字段， 都会被分配一个 id。此类 id 称为 空白节点 id。需要这些 id 才能将声明表示为简单的 主语、属性、值语句，从而能够 区分每条声明中的主体。id 值按照 [RDF-CANON] 确定性设置，并基于文档中的数据以及 SHA-256 等密码学哈希函数的输出。

6.2 选择性披露 和不可关联性

在 VC 的某些用途中，为保护持有者隐私，防止跟踪或关联 多个不同的验证者 交互可能非常重要。特别是，我们考虑两个重要情况：(i) 验证者与 颁发者串通，以及 (ii) 验证者与验证者串通。在第一种 情况中，如图 1所示，验证者 会向凭据的原始 颁发者报告其与持有者的一次交互。在 这种情况下，颁发者可以使用已颁发的 VC 跟踪 持有者与不同验证者之间的所有交互。在第二种 情况中，如图 2所示，多个 验证者串通，共享 他们曾经交互过的持有者的信息。

我们使用术语不可关联性来描述 VC 系统 防止此类针对持有者隐私的“关联攻击”的属性。虽然术语 不可关联性相对较新，但 [NISTIR8053] 第 3.3 节讨论并 给出了一个通过关联攻击重新识别的案例研究。 关于针对数据隐私的关联攻击的知识体系整理可见于 [Powar2023]。针对用户隐私的关联攻击最 广泛的用途发生在 Web 浏览器指纹识别实践中，相关综述可见于 [Pugliese2020]。

为量化关联这一概念，[Powar2023] 引入了 匿名集的概念。在这里关注的 VC 情形中， 匿名集将包含特定 VC 的持有者以及与特定 颁发者相关联的其他持有者。匿名 集越小，越有可能跨验证者跟踪该持有者。由于签名 VC 包含对颁发者公钥的引用，因此，持有来自特定颁发者 VC 的持有者，其 匿名集的初始大小就是该颁发者使用该特定公钥/私钥对 颁发的 VC 数量。 非恶意颁发者应尽量减少用于颁发 VC 的公钥/私钥 对数量。请注意，匿名集概念与 [vc-bitstring-status-list] 中的 群体隐私概念类似。这里使用术语 关联时，通常是指任何会导致匿名集大小缩小的机制。

支持选择性披露的 VC 系统中的关联来源：

  1. 来自密码学原语的制品。
  2. 将 VC 映射为适合选择性披露的语句集合时产生的制品。
  3. 来自证明选项以及 VC 中强制披露信息的制品。
  4. VC 中选择性披露的信息。
  5. 基于外部 VC 系统的关联

下面逐一讨论这些来源。

6.2.1 通过 密码学制品进行关联

密码学哈希、HMAC 和数字签名从本质上会生成 高度唯一的标识符。由于 SHA-256 等哈希函数具有 抗碰撞属性，在不同输入下，其输出基本可以保证唯一， 从而形成强关联，即将匿名集 大小缩减为一。类似地，Ed25519 和 确定性 ECDSA 等确定性签名算法会针对不同输入生成基本唯一的输出， 并导致强关联。

这意味着可以通过 VC 内部的数字签名、HMAC 或哈希制品 在不同验证者之间轻易跟踪持有者， 因而容易受到验证者与验证者串通以及 验证者与颁发者串通的影响。某些 ECDSA 形式等随机化签名算法允许颁发者针对相同输入生成多个不同签名， 并将这些签名发送给持有者供不同 验证者使用。此类方法可以用来防止 基于串通跟踪的验证者与验证者攻击，但无法应对 验证者与颁发者串通。

要实现不可关联性，需要专门设计的密码学签名 方案，使持有者能够生成所谓的对持有签名这一 知识的零知识证明（ZKPKS）。这意味着 持有者可以获取此类 方案中颁发者提供的签名，计算 ZKPKS 并发送给验证者。该 ZKPKS 无法 关联回原始签名，但具备签名的所有理想属性， 即验证者可以使用它验证消息 是否由颁发者的公钥签名，以及消息是否未被 修改。此外，持有者可以为不同 验证者生成任意多个 ZKPKS，这些证明基本相互独立 且不可关联。BBS 就是支持此功能的一种签名方案。

虽然本文档中称为BBS 证明的 ZKPKS 具有有保证的不可关联性属性，但 BBS 与选择性披露结合使用时， 有两个制品可能导致可关联性。它们是最初签名的 消息总数以及已披露语句的索引值。 有关讨论和缓解技术，请参见 [CFRG-BBS-SIGNATURE] 中的隐私注意事项。

如 [CFRG-BBS-SIGNATURE] 的 颁发者的公钥一节中所述，存在一种潜在 威胁，即颁发者可能使用多个公钥，其中一些用于通过 验证者与颁发者串通来跟踪特定用户子集。由于颁发者的公钥 必须对验证者可见，即它会在 BBS 证明（派生证明）中被引用，因此如果颁发者 拥有许多不同公钥，尤其是如果其只对少量 用户（持有者）使用其中一小部分密钥，则这些公钥可能被用作关联点。

6.2.2 通过 VC 处理进行关联

我们在信息泄露一节中已经看到，RDF 规范化使用 哈希函数对语句排序，并且还会基于 HMAC 对语句顺序进一步 打乱。这可能留下某种指纹， 从而允许一定程度的关联。关联强度取决于 空白节点的数量（本质上即 VC 内的 JSON 对象数量）以及已披露 索引的数量。给定 n 个空白节点和 k 个已披露索引， 在最坏情况下，这会使匿名集大小缩小 C(n, k) 倍，即从 n 个元素的集合中 选择 k 个元素的组合数。可以通过 减少 VC 中空白节点的数量来使这一数字保持相当低，例如使 VC 保持简短和 简单。

6.2.3 通过 JSON-LD 节点标识符进行关联

JSON-LD 是一种基于 JSON 的关联数据序列化格式。因此，它支持 为文档内的每个对象 （JSON-LD 术语中的“节点”）分配一个全局无歧义的 @id 属性（节点标识符）。 这实现了关联数据的关联，从而可以将关于同一实体的信息相互关联。 根据使用场景，这种关联可能是理想的，也可能是不理想的。

使用 BBS 的不可关联性功能时，不能为个人或其个人可识别 信息使用全局无歧义的节点 标识符，因为其提供的强关联是不理想的。请注意，在表达非个人 信息的语句时使用此类标识符是可以接受的（例如使用全局无歧义标识符来标识大型 国家或音乐会活动）。还请注意，JSON-LD 对 @context 的使用会 将术语映射到 IRI，这通常不会影响不可关联性。

6.2.4 通过证明选项和强制披露进行关联

在 [VC-DATA-INTEGRITY-1.1] 规范中，给出了 VC 的 proof 属性的若干特性。需要注意的是，可选字段 不应在不同验证者之间提供强关联。可选字段包括： id、created、expires、domain、 challenge 和 nonce。例如，可选的 created 字段是一个 dateTimeStamp 对象，可以将 证明的创建日期指定到任意亚秒级精度。此类 信息如果存在，可能会大幅缩小匿名集的大小。如果 发行者希望包含此类信息，则应使其粒度尽可能粗， 并与一段时间内发行的 VC 数量相适应。

发行者还可以通过创建 基础证明时使用的 mandatoryPointers 输入，强制持有者向 验证者披露某些语句。参见 示例 9和 示例 10。这里的 强制是指， 除非向验证者披露这些语句，否则生成的派生证明将无法通过验证。 应注意，如果要求披露此类信息， 则应确保匿名集仍然足够大。

6.2.5 通过 持有者选择性披露进行关联

如 [Powar2023] 中所述， 已记录了许多通过 关联攻击重新识别个人的案例。因此，强烈建议持有者 尽可能少地披露信息，以帮助保持较大的匿名 集。此外，多次研究表明，看似无害的 信息也可能高度唯一，从而导致重新识别 或跟踪。有关一个涉及前马萨诸塞州州长的著名 案例的详细过程，请参见 [NISTIR8053]；有关对 94 个此类公开案例的进一步 分析和分类，请参见 [Powar2023]。

6.2.6 基于外部 VC 系统 的关联

需要指出的是，要维持不可关联性，即匿名性， 持有和传输 VC 的系统需要格外谨慎。IP 地址（第 3 层）或 Ethernet/MAC 地址（第 2 层）等网络 制品是众所周知的关联来源。例如，如果用户再次访问某个特定接入点， 移动电话的 MAC 地址可以用于跟踪用户，这促使 移动电话制造商提供 MAC 地址随机化功能。 公网 IP 地址通常足以提供信息，将个人地理定位到某个国家内的 城市或地区，从而可能大幅缩小 匿名集。
