1. 引言

本节为非规范性内容。

本规范描述了使用密码学来确保可验证凭证及 类似类型的受约束数字 文档的真实性和完整性的机制，尤其是通过使用数字签名 及相关数学证明。密码学证明所支持的功能 对分布式系统的实现者非常有用。例如，证明可以 用于：

  • 作出可在不丧失信任的情况下共享的陈述，因为其 作者身份可由第三方验证，例如作为 可验证凭证 [VC-DATA-MODEL-2.0]、可验证 出示， 或社交媒体帖文的一部分。
  • 作为由特定标识符所标识的实体进行身份验证，例如作为 去中心化标识符（DID）所标识的主体 [DID]。
  • 通过授权能力等机制，为远程执行环境中的操作 委托授权 [ZCAP]。
  • 同意可由另一方验证该同意的合同。
  • 此外，许多基于密码学数字签名的证明 还能提供完整性保护，使文档和数据 在遭到篡改时可被察觉。

1.1 完全披露

本节为非规范性内容。

根据可验证凭证数据模型 v2.0，一个可验证凭证 是由同一颁发者作出的一个或 多个声明 的集合。特定的持有者可以拥有 来自多个颁发者的可验证 凭证。在向验证者出示时，持有者可以 从其现有可验证凭证中只选择一个或一个子集来组成 可验证出示。通过尽量减少向给定可验证 出示中包含的凭证子集，并将其出示给给定的验证者，可以增强隐私。

在最简单的部署中，只能通过可验证出示共享完整的 可验证凭证。换言之，要共享给定可验证凭证中的单个声明， 整个可验证凭证都必须成为 可验证出示的一部分。 这种方法称为完全披露。

1.1.1 完全披露的工作原理

本节为非规范性内容。

数据完整性的操作在概念上很简单。要创建一个 密码学证明，需要执行以下步骤：1）转换， 2）哈希，以及 3）证明生成。

转换是由转换 算法描述的过程，该过程获取输入数据并为哈希过程做好准备。 一种可能的转换示例是获取参加某次会议的人员姓名记录， 按每个人的姓氏以字母顺序对列表进行排序， 然后按排序后的顺序将姓名重新写在一张纸上，每行一个。 转换的示例包括 规范化 和 二进制到文本编码。

哈希是由哈希算法描述的过程，该过程 使用 密码学哈希函数为转换后的数据计算一个标识符。此过程在概念上类似于 电话通讯录的工作方式，即获取某个人的姓名（输入数据） 并将该姓名映射到该人的电话号码（哈希值）。密码学 哈希函数的示例包括 SHA-3 和 BLAKE-3。

证明生成是由 证明序列化算法描述的过程，该算法计算一个用于保护 输入数据完整性免遭修改，或以其他方式证明达到某种 所需信任阈值的值。此过程在概念上类似于 在装有信件的信封上使用蜡封，以建立对 发送者的信任并表明信件在传输过程中未被篡改。 一般而言，证明序列化函数的示例包括 数字签名、 权益证明以及 知识证明。

要验证密码学证明，需要执行以下步骤： 1）转换，2）哈希，以及 3）证明验证。

在验证期间，转换和哈希步骤 在概念上与上文所述相同。

证明验证是一个由 证明验证算法描述的过程，该算法应用密码学证明 验证函数来判断输入数据是否可信。可能的证明 验证函数一般包括 数字签名、 权益证明以及 知识证明。

本规范详细说明了密码学软件架构师和 实现者如何将这些过程组合封装成称为 密码套件的事物，并将其提供给应用程序 开发者，以便保护应用程序数据在传输中和静态存储时的完整性。

1.2 选择性披露

本节为非规范性内容。

完全披露显然会对 主体和持有者双方的隐私产生重大影响。 为了进一步增强持有者的隐私，颁发者可以创建支持 选择性披露的可验证凭证。这是一种密码学 技术，它允许颁发者创建一个 可验证凭证， 使持有者能够从原始凭证中选择性地仅披露声明的一个子集，并将其置于 将要出示给验证者的派生凭证中。这一过程 通过颁发者向验证者保证派生 凭证中数据的完整性和真实性来实现。

请注意，选择性披露通常适用于声明 层级。持有者不能更改已颁发声明的含义，同时仍保持 派生凭证的可验证性。他们只能 通过一组选择性披露 约束，限制哪些 声明最终进入 派生凭证。不过，在某些情况下，更高级的技术，例如 将承诺披露与零知识证明（ZKP）相结合， 可以让持有者在维持基于颁发者的 真实性和数据完整性保证的同时， 披露少于“完整声明”的信息。 此外，颁发者还可以选择指定原始凭证中的某些 声明必须通过强制披露 约束予以披露。虽然通常由验证者负责 指明其理解并希望验证哪些声明，但无论是否可能存在这种约束， 都期望验证者始终请求其所需要的内容。

1.2.1 选择性 披露的工作原理

本节为非规范性内容。

在1.1.1 完全披露的工作原理一节中，说明了 创建和 验证 密码学证明的基本过程。在选择性披露中， 有三个过程而不是两个：1）颁发者创建一个基础证明，2） 持有者根据基础证明创建一个派生证明，以及 3）验证者 验证派生证明。 之所以需要这一步额外操作，是因为创建 派生证明的方法，与以特定方式创建的基础证明结合使用时效率要高得多。期望持有者 在出示时绝不披露 基础证明，因为基础证明中的某些信息可能 仅供持有者使用，例如用于创建保护隐私的 派生证明。

在图 3中，颁发者可以定义强制披露约束， 将声明划分为强制 声明（即，无论其他约束如何，都必须出现在派生凭证中的声明） 和不必 出现在派生凭证中的非强制声明。 是否施加强制披露约束是可选的。

转换和哈希步骤类似于 完全披露的情况，不同之处在于强制和非强制声明会 分别进行转换和哈希。 这些步骤的具体细节取决于底层密码学算法。

  • 简单的方法（称为SIC，即“对单个声明签名”） 涉及生成一个临时的 密码学密钥对。 该密钥对的作用域限定于特定的证明，并且一旦生成基础证明，其 私钥便会被丢弃。 该临时密钥对用于为强制声明块以及逐个为 非强制声明签名。随后会被签名的 基础证明数据结构中包含这些签名 值以及临时密钥对的公钥。
  • SIC的缺点是可能会为基础证明生成非常大的数据 结构。如果签名 大小较大，就会出现这种情况；某些抗量子签名方案正是如此，并且这对于某些应用而言可能会 大到不可接受。 在这种情况下，可以采用另一种方法（称为SHoC，即“声明的加盐哈希”）：为每个声明创建一个盐值 （即随机 nonce），然后对盐值+声明这一组合 应用哈希函数。 随后会被签名的基础证明数据结构中 包含哈希值列表，每个盐值+声明对应一个哈希值， 并与相应的盐值配对。SHoC方法的 缺点 是实现更为复杂，可能泄露已签名声明总数的信息， 而且即使是未披露的声明，其所有哈希值也必须包含在证明中， 从而增加证明的大小（但取决于哈希值大小，而不是签名大小）。

有关SIC和SHoC 的技术细节和比较，请参阅4.3.1 引言和表 1 （另加第三种方法，该方法适用于一种非常特定的签名方案，即 [VC-DI-BBS]）。

在图 4中，持有者可以通过选择性披露 约束指定向验证者披露哪些信息 子集。这些约束通过转换 和派生证明生成步骤，用于产生派生 凭证。这些步骤的执行方式 能够相对于 颁发者的意图保留派生数据的真实性和完整性。 派生证明数据结构包含对每个 声明的引用，这些声明 要么是强制声明，要么由选择性披露 约束确定。 具体细节取决于使用的是SIC还是SHoC方法。 在SIC情况下，其中包含已签名声明的列表。 在SHoC情况下，该结构更加复杂；其中包含选定的 盐值+声明条目列表、它们对应的哈希值，以及 所有非强制声明的哈希值+盐值对完整列表（验证时需要）。

选择性披露约束通常会被设置为 满足验证者接受派生 凭证所需的最低要求。

1.3 设计目标和理由

本节为非规范性内容。

本规范针对以下设计目标进行了优化：

简单性
该技术旨在便于应用程序开发者使用， 无需接受大量密码学培训。它按照以下利益相关方的 优先级进行优化：应用程序开发者优先于密码 套件实现者，密码套件实现者优先于密码套件设计者，密码套件设计者优先于密码 算法规范作者。该解决方案侧重于合理的默认设置，以 防止选择无效的保护机制。有关更多 详细信息，请参阅 5.2 保护应用程序开发者和 5.1 密码套件版本控制。
可组合性
许多历史上的数字签名机制采用整体式 设计，将数据转换、语法、 数字签名和序列化组合在一个规范中，从而限制了使用场景。本 规范对每个组件进行分层，从而支持更广泛的使用场景， 包括通用选择性披露和与序列化无关的 签名。有关更多 理由，请参阅5.6 转换一节、5.8 数据不透明性一节，以及 5.1 密码套件版本控制。
韧性
由于数字证明机制可能会因 技术进步而在毫无预警的情况下遭到破解，因此密码 套件 提供多层保护并能够快速升级非常重要。本 规范同时支持算法敏捷性和密码学分层， 同时仍使数字证明格式易于开发者理解 和使用。有关具体细节，请参阅5.4 敏捷性和分层一节。
渐进式可扩展性
新密码学保护机制的创建和部署被设计为 一个审慎、迭代且谨慎的过程，该过程承认扩展 会经历从实验到实现再到标准化的不同阶段。 本规范力求在提高 密码学创新速度的需求与稳定的生产级 密码套件的需求之间取得平衡。有关 建立新型密码学证明的说明，请参阅3. 密码套件一节。
序列化灵活性
密码学证明可以通过许多不同但等价的方式序列化，并且 往往与原始文档语法紧密绑定。本 规范允许创建不 绑定于原始文档语法的密码学证明，从而支持更高级的使用场景， 例如能够在 JSON 和 CBOR 等多种 序列化语法中使用同一个数字签名，而无需重新生成 密码学证明。有关这种方法的 优点说明，请参阅5.6 转换一节。
注：将 技术应用于更广泛的使用场景

尽管本规范主要关注可验证 凭证，但该 技术的设计具有通用性，因此也可用于其他 使用场景。在这些情况下，期望实现者自行开展充分的 尽职调查和专家评审，以确定该技术对其 使用场景的适用性。

1.4 一致性

除标记为非规范性的章节之外，本规范中的所有编写指南、图表、示例和注释 均为非规范性内容。本规范中的其他所有内容均为规范性内容。

本文档中的关键词 可以、必须、不得 、可选以及应该 应按照 BCP 14 [RFC2119] [RFC8174] 中的描述进行解释，但仅限于它们像此处所示 全部以大写形式出现时。

符合要求的安全文档是任何能够 转换为 JSON 文档并遵循 第 2.1 证明、2.2 证明目的、2.3 资源 完整性、 2.4 上下文和词汇表以及3.1 DataIntegrityProof中相关规范性要求的字节序列。

符合要求的密码套件 规范是 任何遵循第 3. 密码套件节中相关规范性要求的规范。

符合要求的 处理器是任何以 软件和/或硬件实现的算法，它根据第4. 算法节中的相关规范性陈述，生成和/或使用 符合要求的安全文档。符合要求的处理器必须 在使用 不符合要求的文档时产生错误。

1.5 术语

本文档通篇使用的部分术语定义于 可验证凭证数据模型 v2.0规范的 术语一节，以及受控标识符 v1.0 规范的术语一节。 本节定义本 规范通篇使用的其他术语。

密码套件
一种定义如何使用特定密码学原语 以实现特定安全目标的规范。这些文档通常用于 指定验证方法、数字 签名类型、 它们的标识符以及其他相关属性。有关更多详细信息，请参阅第 3. 密码套件节。
数据 完整性证明
一组表示数字证明以及验证该证明所需参数的属性。 数字签名是数据完整性 证明的一种类型。
证明目的
证明的具体意图；实体创建它的原因。该 受保护声明充当一种防护措施，以防止该证明被 滥用于其预期目的之外的其他用途。
公钥
可用于验证使用对应 秘密密钥创建的数字证明的密码学材料。
秘密密钥
一种密码学材料，有时称为 私钥，不得与任何人共享，并用于 生成数字证明和/或数字签名。

2. 数据模型

本节规定用于表示 数据完整性证明以及相关资源完整性的 数据模型。

本规范中的所有数据模型属性和类型都映射到 URL。 定义这些 URL 的词汇表是安全词汇表。 在受保护 文档中用于执行这种映射的显式机制是 @context 属性。

该映射机制由JSON-LD 1.1定义。为了确保文档在 不使用 JSON-LD 库的情况下也能以可互操作的方式使用，建议文档作者 确保领域专家已经：1）规定与 @context 属性关联的所有值的预期顺序， 2）发布每个 @context 文件的密码学 哈希值，以及 3）确认每个 @context 文件的内容 适用于预期的使用场景。

当文档由不使用 JSON-LD 库的处理器进行处理，并且要求使用与 JSON-LD 环境中相同的语义时，建议实现者：1）强制执行 @context 属性中的预期顺序 和值，以及 2）确保每个 @context 文件 与每个 @context 文件的已知密码学哈希值匹配。

将带有已发布密码学哈希值的静态、版本化 @context 文件 与 JSON Schema 结合使用，是实现上述 机制的一种可接受方法；在使用不利用 JSON-LD 库的处理器时， 这种方法可以确保正确的术语识别、类型确定 和顺序。 有关更多详细信息，请参阅可验证凭证数据模型 v2.0中的 特定类型处理一节。

2.1 证明

数据完整性证明提供有关 证明机制、 验证该证明所需的参数以及证明值本身的信息。所有这些 信息均使用关联数据词汇表提供，例如 安全 词汇表。

在对象上表示数据完整性证明时，必须使用 proof 属性。可验证凭证中的 proof 属性是一个命名图。如果存在， 其值必须是单个对象或无序对象集合， 并使用以下属性表示：

id
证明的可选标识符，它必须是 URL [URL]， 例如 作为 URN 的 UUID（urn:uuid:6a1676b8-b51f-11ed-937b-d76685a20ff5）。 此属性的用法在第 2.1.2 证明 链节中进一步说明。
type
证明的具体类型必须指定为映射到 URL 的字符串 [URL]。证明类型的示例包括 DataIntegrityProof 和 Ed25519Signature2020。证明类型决定保护和验证证明还需要哪些其他字段。
proofPurpose
创建证明的原因必须指定为映射到 URL 的字符串 [URL]。证明目的充当一种防护措施，以防止 证明被用于与 预期目的不同的用途。例如，如果没有此值，证明创建者可能 被诱骗在登录过程中（authentication）使用通常用于创建可验证 凭证（assertionMethod）的密码学材料，这 随后会导致创建一个他们从未打算 创建的可验证 凭证，而不是执行原本仅仅登录网站这一预期操作。
verificationMethod
验证方法是验证证明所需的手段和信息。 如果包含，其值必须是映射到 [URL] 的字符串。包含 verificationMethod 是可选的，但如果未包含， cryptosuite 等其他属性 可以提供一种获取验证证明所需信息的机制。 请注意，当 verificationMethod 表示在数据完整性证明中时，其值 指向数据的实际位置；也就是说，verificationMethod 通过 URL 引用 可用于验证证明的公钥的位置。该 公钥数据存储在受控标识符 文档中，该文档包含 对验证方法的完整描述。
cryptosuite
可用于验证证明的密码套件的标识符。有关更多信息，请参阅 3. 密码套件。如果证明 type 为 DataIntegrityProof，则必须指定 cryptosuite；否则， cryptosuite 可以指定。如果指定，其值必须是 字符串。
created
证明创建的日期和时间是可选的，如果包含，则必须 指定为 [XMLSCHEMA11-2] dateTimeStamp 字符串，可以使用协调世界时（UTC）， 以值末尾的 Z 表示，也可以带有相对于 UTC 的 时区偏移。符合要求的处理器可以选择使用 未带偏移而被错误序列化的时间值。未带偏移而被错误 序列化的时间值应解释为 UTC。
expires
expires 属性是可选的，如果存在，则指定 证明何时 过期。如果存在，它必须是 [XMLSCHEMA11-2] dateTimeStamp 字符串， 可以使用协调世界时（UTC），以值末尾的 Z 表示， 也可以带有相对于 UTC 的时区偏移。符合要求的处理器 可以选择使用未带 偏移而被错误序列化的时间值。未带偏移而被错误序列化的时间值应 解释为 UTC。
domain
domain 属性是可选的。它传达证明 预期使用的一个或多个安全域。 如果指定，相关值必须是 字符串或无序字符串集合。验证者应该使用该值 以确保该证明原本就预期用于验证者正在运行的安全域。 domain 参数的规定 对于验证者在证明创建者已知的 安全域中运行的质询-响应协议很有用。域值示例 包括：domain.example（DNS 域）、https://domain.example:8443 （Web 源）、mycorp-intranet（自定义文本字符串）以及 b31d37d4-dd59-47d3-9dd8-c973da43b63a（UUID）。
challenge
如果指定了 domain，则应该在证明中包含一个字符串值。 该值针对特定域和时间窗口仅使用一次。该 值用于缓解重放攻击。质询值的示例包括： 1235abcd6789、79d34551-ae81-44ae-823b-6dadbab9ebd4 和 ruby。
proofValue
一个字符串值， 用于表示使用指定的 verificationMethod 验证 数字证明所需的基数编码二进制数据。该值必须使用 受控标识符 v1.0规范第 2.4 Multibase 节中所述的 标头和编码来表示二进制数据。 该值的内容由特定密码套件确定，并设置为 该密码套件的添加证明算法所生成的证明值。 可以使用由密码套件指定、采用不同编码的替代属性 代替此属性，对验证数字证明所需的 数据进行编码。
previousProof
previousProof 属性是可选的。如果存在，它必须是字符串 值或无序字符串值列表。每个值标识另一个 数据完整性证明，这些证明必须全部通过验证，当前 证明才能被视为已通过验证。此属性用于第 2.1.2 证明链节。
nonce
由证明创建者提供的可选字符串值。此 字段的一种用途是通过降低由确定性生成的签名所产生的 可关联性来增强隐私。

2.1.3 证明图

在保护文档中的数据时，清楚界定 被保护的数据非常重要；这包括文档中表示的每个图，但不包括 包含与保护机制相关联数据的那个图，该图称为 证明图。建立这种分离使 处理算法能够以确定性方式保护和验证受保护的 文档。

在向输入文档添加 数据完整性证明之前，文档中包含的信息 表示在一个或多个 图中。为了确保来自不同数据完整性证明的信息不会 意外混合，使用证明图这一概念 来封装 每个数据完整性证明。与文档 proof 属性关联的每个值都标识一个单独的图，有时称为 命名图，其类型为 ProofGraph，其中包含一个数据完整性证明。

在执行 JSON-LD 处理时，使用这些图具有具体效果，因为 这样可以正确地将一个图中表示的陈述与另一个 图中的陈述分离。将处理限制为其他媒体类型（例如 JSON、YAML 或 CBOR）的实现者，如果将一个文档的数据 与另一个文档的数据合并，例如两个文档中的 id 值字符串相同， 则需要牢记这一点。如果对象没有 id 属性和/或未使用 URL 等全局标识符类型，即使这些对象看起来具有相似 属性，也不应将其合并，因为缺少这些信息时，无法判断 两个这样的对象是否正在表达有关同一实体的信息。

2.2 证明目的

描述其目的的证明有助于防止它被滥用于某些 其他目的。证明目的使验证者能够了解 证明创建者的意图，从而防止消息被意外滥用于 其他目的。例如，原本仅为作出 断言而签名的消息（可能打算广泛共享），被滥用为 用于向服务进行身份验证或执行某项操作的消息（例如调用 某项能力来执行操作）。

需要注意的是，证明目的与 JSON Web Key（JWK）中的 key_ops 限制、Web 密码学 API中的 KeyUsage 限制，以及互联网 X.509 公钥基础设施 证书和证书吊销列表（CRL）配置文件是不同的机制。证明目的表达的是 证明为何被创建及其预期使用域，而 上述其他机制旨在限制私钥可用于 执行哪些操作。证明目的会与证明一起“传递”，而密钥限制 不会。

以下是常用证明目的值的列表。

authentication

2.4.1 验证上下文

必须确保使用方应用程序明确批准了 它将处理的输入文档的类型，进而批准其语义。 如果不针对已知良好值检查 JSON-LD 上下文值，由于这些值所传达的语义可能存在差异， 可能会导致安全漏洞。 应用程序必须使用第 4.1.6 上下文验证节中的算法，或 实现等效保护的算法，来验证符合要求的受保护文档中的上下文。上下文 验证必须在运行 第 4.1.4 验证 证明节或第 4.1.5 验证证明集和证明链节中的适用算法之后运行。

虽然第 4.1.6 上下文验证节所述算法提供了一种 检查上下文值的方法，以及一种安全处理 未知上下文值的可选方法，但实现者可以使用能提供相同保护的 替代方法或不同的步骤顺序。

例如，如果不会执行 JSON-LD 处理，那么应用程序可以不执行 此项检查，而是遵循通过带外方式提供的任何受信任 文档中的指导，以正确理解 该类型文档的语义。

另一种方法是配置应用程序使用 JSON-LD 上下文 加载器（有时称为文档加载器），并且只使用 已批准上下文文件的本地副本。这将保证上下文文件及 其密码学哈希值永远不会发生变化，从而实际上得到与第 4.1.6 上下文验证节中的算法相同的结果。

另一种替代方法实际上也等效于 第 4.1.6 上下文验证节中的算法，即让 应用程序维护一份 已知上下文 URL 及其相关已批准密码学哈希值的列表， 而无需在本地存储每个上下文文件。这样就可以安全地 从网络加载这些上下文，同时不损害应用程序的安全 预期。

还有一种有效方法是让发送应用程序通过某种协议 将文档压缩为 接收应用程序所请求的确切内容，例如请求 可验证 出示的协议，同时省略在保护原始文档时使用的 其他发送方特定上下文值。只要 密码套件的验证算法给出成功的 验证结果，此类转换就是有效的，并会使先前由被省略上下文压缩的 术语产生完整 URL。也就是说，一个 先前基于发送方提供、但接收方未知的上下文（例如 `https://ontology.example/v1） 被压缩为 foo 的术语，将 改为被“展开”为类似 https://ontology.example#foo 的 URL，然后 在省略未知上下文并由接收应用程序应用 JSON-LD 压缩算法后，再被“压缩”为同一个 URL。

2.4.2 上下文注入

@context 属性用于确保实现在处理 本规范中的术语时使用相同的语义。例如，这 在处理 type 等属性并使用其 DataIntegrityProof 等值时可能很重要。

当应用程序保护文档时，如果文档中未 提供 @context 属性，或者文档中使用的数据完整性术语 未被 @context 属性中的现有值映射，则实现应该 注入或追加一个值为 https://w3id.org/security/data-integrity/v2 的 @context 属性，或一个或多个 至少具有相同声明的上下文，例如可验证凭证数据模型 v2.0 上下文（https://www.w3.org/ns/credentials/v2）。

不打算使用 JSON-LD 处理的实现可以选择 不 在文档顶层包含 @context 声明。但是，如果 未包含 @context 声明，则不得进行 与本规范或相应密码套件相关的扩展（例如添加 新属性）。

2.4.3 无损保护数据

HTML 处理器被设计为在检测到可恢复错误时 继续处理。JSON-LD 处理器也采用类似方式运行。这种设计理念 旨在确保开发者只需使用 JSON-LD 语言中对其有用的部分，而不会让处理器因 可能对开发者并不重要的事项而抛出错误。除其他影响外， 这种理念使 JSON-LD 处理器被设计为在遇到未定义术语等情况时， 不抛出错误， 而是警告开发者。

从 JSON-LD 转换为 RDF 数据集时，例如对 文档进行规范化 [RDF-CANON] 时，未定义术语和相对 URL 可能会被 静默丢弃。当值被丢弃时，它们不受数字证明保护。这 会造成预期不匹配：不了解 JSON-LD 处理器工作方式的开发者可能认为某些数据已受到保护， 但由于没有抛出错误，随后却惊讶地发现事实并非如此。 本规范要求，在执行 JSON-LD 转换时任何可恢复的数据丢失都必须产生错误，以避免 开发者的安全预期出现不匹配。

使用 JSON-LD 处理（例如 RDF 数据集 规范化 [RDF-CANON]）的实现，在 JSON-LD 处理器丢弃数据时必须 抛出错误，该错误应该为 DATA_LOSS_DETECTION_ERROR， 例如在输入文档中检测到未定义术语时。

类似地，由于符合要求的受保护 文档可以从一个 安全域传输到另一个安全域，因此处理 符合要求的受保护文档的符合要求的处理器 不能假定文档具有任何 特定基础 URL。反序列化为 RDF 时，实现必须确保 基础 URL 设置为 null。

2.5 与关联数据的关系

“关联数据”一词用于描述一种推荐的最佳实践，即 使用 URL 等标准来标识事物及其属性，从而在 Web 上 公开、共享和连接信息。当信息以 关联数据形式呈现时，可以轻松发现其他相关信息，并且可以轻松地将 新信息链接到其中。关联数据可以以 去中心化方式扩展，从而大幅降低大规模集成的障碍。

随着关联数据在各种应用程序中的使用日益增加， 有必要能够验证关联数据 文档的真实性和完整性。本规范通过使用数学证明 为数据文档添加身份验证和完整性保护，同时不会牺牲关联 数据的可扩展性和可组合性等特性。

注：使用关联 数据是一项可选功能

虽然本规范提供了对关联数据进行数字签名的机制，但 并非必须使用关联数据才能获得 本规范所提供的某些优势。

2.6 与 可验证凭证的关系

实现本规范的密码套件可用于保护 可验证凭证 和可验证 出示。处理 这些使用场景的实现者需要注意，在处理这些类型的文档时 可能适合进行额外检查。

在某些使用场景中，重要的是确保 证明中使用的验证 方法与 可验证凭证中的 issuer，或 可验证出示中的 holder相关联， 这种检查在 验证过程中进行。一种 检查这种关联的方法是确保 证明的验证方法的 controller 属性值 与用于分别标识 issuer 或 holder 的 URL 值匹配， 并且 验证方法表示在一个根据证明目的可接受的验证关系下。 这种特定关联表明 相应的 issuer 或 holder 是用于验证证明的验证方法的控制者。

建议文档作者和实现者理解 证明的有效期与 凭证的有效期之间的区别； 前者使用created 和expires 属性表示，而后者使用 validFrom 和 validUntil 属性表示。 虽然这些属性有时可能表示相同的有效期，但在 其他时候它们可能并不一致。在验证 证明时，重要的是确保关注的时间 （可能是当前时间或任何其他时间）位于 证明的有效期内（即位于 created 和 expires 之间）。 在验证 可验证凭证时， 重要的是确保关注的时间位于 凭证的有效期内（即 位于 validFrom 和 validUntil 之间）。请注意， 如果未能验证证明的有效期或 凭证的有效期， 可能会导致 接受本应被拒绝的数据。

最后，还强烈建议实现者理解， 与可验证凭证关联的 吊销信息，与验证 方法的吊销 和过期时间之间存在区别。 验证 方法的 吊销和 过期时间分别使用 revocation 和 expires 属性表示；它们与秘密密钥遭到 泄露或过期等事件有关；并且可能提供会泄露 控制者详细信息的时间信息，例如其安全实践或其可能 在何时遭到入侵。可验证凭证的吊销信息 使用 credentialStatus 属性表示；它与 个人失去由 可验证凭证 授予的权限等事件有关； 并且不提供时间信息，从而 增强隐私。

3. 密码套件

数据完整性证明旨在便于开发者使用， 因此力求最大限度地减少生成证明时需要记住的 信息量。通常，开发者只需提供密码套件名称（例如 eddsa-rdfc-2022），即可开始创建 证明。这些密码套件通常由 具备必要密码学训练的人员创建和审查，以确保使用 安全的密码学原语组合。本节规定编写 密码套件规范的要求。

所有数据完整性密码套件规范的要求 如下：

  • 规范必须以人类可读文档的形式发布在一个 URL 上。
  • 规范必须标识密码套件 type 以及可 与该套件一起使用的任何参数。
  • 规范必须详细说明用于将输入数据修改为待保护 数据的转换算法（如果有）、 参数以及其他必要细节。
  • 规范必须详细说明用于对 待保护数据执行密码学哈希的哈希 算法 参数以及其他必要细节。
  • 规范必须详细说明用于对数据执行密码学保护的证明序列化算法、 参数以及其他必要细节。
  • 规范必须详细说明用于对数据执行密码学 验证的证明验证算法、 参数以及其他必要细节。
  • 规范必须定义一个数据完整性密码套件实例化 算法，该算法接受一组选项（映射 options）并返回一个 密码套件 实例（结构体 cryptosuite）。此算法应该 列入可验证凭证扩展 文档。数据完整性密码套件 实例结构体具有 以下项。
    createProof
    一种算法，以输入文档（映射 inputDocument）和证明选项（映射 options）作为输入，并 生成一个数据完整性证明（映射）或错误。
    verifyProof
    一种算法，以受保护数据文档（映射 securedDocument）作为输入，并生成密码套件验证 结果或错误。密码套件验证结果是一个 结构体，其中包含 以下项：
    verified
    一个布尔值， 如果验证成功则为 true，否则为 false。
    verifiedDocument
    一个映射， 表示移除已验证 证明后的受保护数据 文档，前提是verified 为 true； 否则为 null。
    该结构可以包含对开发者 有用的其他实现特定信息，例如调试信息。如果产生错误， 则验证过程未能完成。错误（例如网络错误） 并不意味着将来再次尝试验证也会失败。
  • 规范必须详细说明算法中可能发生的任何已知资源耗尽攻击， 并为每种攻击提供可测试的缓解措施。
  • 规范必须包含“安全注意事项”一节，详细说明 该密码套件特有的安全注意事项。
  • 规范必须包含“隐私注意事项”一节，详细说明 该密码套件特有的隐私注意事项。
  • 与密码套件关联的 JSON-LD 上下文必须通过使用 @protected 关键字来保护其术语免遭不安全的重新定义。

密码套件 实例使用密码套件实例化算法进行实例化，并以 实现特定的方式提供给算法。实现可以使用可验证 凭证扩展文档来发现 已知的密码套件实例化 算法。

3.1 DataIntegrityProof

许多密码套件在表示 数据完整性证明时遵循相同的基本模式。本节规定这种 通用 设计模式，即一种称为 DataIntegrityProof 的密码套件类型， 它通过复用设计原语和源代码来减轻编写和实现密码套件 的负担。

当规定使用这种设计模式的密码套件时， proof 值采用以下形式：

type
type 属性必须包含字符串 DataIntegrityProof。
cryptosuite
cryptosuite 属性的值必须是一个用于标识 密码套件的字符串。如果处理环境支持 字符串 子类型，则 cryptosuite 值的子类型必须是 https://w3id.org/security#cryptosuiteString 子类型。
proofValue
proofValue 属性必须按照第 2.1 证明节中的规定使用。

密码套件设计者必须使用 第 2.1 证明节中定义的强制 proof 值属性，并且可以定义 其密码套件特有的其他属性。

注：旧式密码套件的设计 模式

2012 年至 2020 年的数据完整性密码套件中出现的一种设计模式是 使用 type 属性为某个 密码套件确定具体类型； Ed25519Signature2020 密码套件就是这样的规范之一。这 给密码套件实现带来了更大负担，因为每个新的 密码套件都需要规定新的 JSON-LD 上下文，从而 导致开发者体验欠佳。2020 年出现了这种设计 模式的精简版本，使开发者只需包含 一个 JSON-LD 上下文即可支持所有现代密码套件。这 促使更多现代密码套件——例如 EdDSA 密码套件 [DI-EDDSA]和 ECDSA 密码套件 [DI-ECDSA] ——基于本节所述的精简模式 构建。

为改善开发者体验，创建新的数据完整性 密码套件规范的作者应该使用现代模式——其中 type 设置为 DataIntegrityProof；cryptosuite 属性承载 密码套件的标识符；任何密码套件特有的密码学 数据都封装在 proofValue 中（即不直接作为应用层数据公开）。 已知遵循此模式的密码套件规范列表 载于 可验证凭证扩展的保护机制一节 文档中。

4. 算法

4.1 文档算法

下面定义的算法对表示为JSON 对象的文档进行操作。本 规范遵循 JSON-LD 1.1 处理算法和 API规范，将 JSON 对象表示为映射。 未受保护数据文档是一个不包含 任何证明值的映射。输入文档是一个尚未向其中添加 当前证明的映射，但它可以包含由之前的过程 添加到其中的证明值。受保护数据 文档 是一个包含一个或多个证明值的映射。

除下述 算法之外，实现者可以实现合理的默认设置和防护措施，以帮助缓解开发者错误、过度资源 消耗、新发现且存在特定 防护措施的攻击模型，以及实现其他改进。下面提供的算法是 可互操作实现的最低要求，并强烈建议开发者 加入有助于构建更安全且更 高效生态系统的额外措施。

4.1.1 处理模型

本节描述符合要求的处理器及其 应用程序特定软件所使用的处理模型。当软件 要确保信息遭篡改时可被察觉时，它执行以下步骤：

  1. 软件将信息组织成文档，例如 JSON 或 JSON-LD 文档。
  2. 如果文档是 JSON-LD 文档，软件选择一个或多个 JSON-LD 上下文，并使用 @context 属性表示它们。
  3. 软件使用可接受的密码学密钥材料，选择一个或多个满足 使用场景需求的密码套件，例如提供完全、选择性或不可关联 披露的密码套件。
  4. 软件使用第 4.1.2 添加 证明 节或第 4.1.3 添加证明集/链节中提供的适用算法， 添加一个或多个 证明。

当软件需要使用通过本规范所述机制 传输给它的信息时，它执行以下步骤：

  1. 软件将传入数据转换为第 4.1.4 验证证明节或第 4.1.5 验证证明集和证明链节所提供的适用算法能够理解 的文档。
  2. 软件使用 JSON Schema 或等效机制验证 传入文档是否遵循应用程序所使用的预期模式。
  3. 软件使用第 4.1.4 验证证明 节或第 4.1.5 验证证明集和证明链节中提供的适用算法来验证 传入文档的 完整性。
  4. 如果文档是 JSON-LD 文档，软件使用第 4.1.6 上下文验证节中提供的算法，或提供 等效保护的算法， 验证文档中使用的所有 JSON-LD 上下文值。

4.1.2 添加证明

以下算法规定如何向输入文档添加数字证明，并随后使用该证明验证输出 文档的真实性 和完整性。所需输入为输入文档（映射 inputDocument）、密码套件实例（结构体 cryptosuite），以及 一组选项（映射 options）。输出为受保护数据文档 （映射）或错误。 每当此算法对字符串进行编码时，它都必须使用 UTF-8 编码。

  1. 令 proof 为调用 cryptosuite.createProof 中指定的createProof 算法，并将 inputDocument 和 options 作为参数传入后所得的结果。如果该算法产生错误， 则必须传播该错误，并且应该传达 错误类型。
  2. 如果 proof.type、 proof.verificationMethod 和 proof.proofPurpose 中一个或多个值未设置，则必须引发错误，并且应该 传达错误类型 PROOF_GENERATION_ERROR。
  3. 如果 options 具有非 null 的 domain 项，则它必须 等于 proof.domain，否则必须引发错误，并且应该传达 错误类型 PROOF_GENERATION_ERROR。
  4. 如果 options 具有非 null 的 challenge 项，则它必须 等于 proof.challenge，否则必须引发错误，并且 应该 传达错误类型 PROOF_GENERATION_ERROR。
  5. 令 securedDataDocument 为 inputDocument 的副本。
  6. 将 securedDataDocument.proof 设置为 proof 的值。
  7. 将 securedDataDocument 作为受保护数据文档返回。

4.1.3 添加证明集/链

以下算法规定如何从包含证明或 证明集/链的受保护文档开始，逐步向证明 集或证明链添加证明。所需输入为受保护数据文档（映射 securedDocument）、密码套件（密码套件 实例 suite），以及一组选项（映射 options）。输出为新的 受保护数据文档（映射）。每当此算法对 字符串进行编码时，它 必须使用 UTF-8 编码。

  1. 将 proof 设置为 securedDocument.proof。令 allProofs 为空列表。如果 proof 是列表，则将 proof 的所有元素复制到 allProofs。如果 proof 是对象，则将该对象的副本添加到 allProofs。
  2. 令 inputDocument 为移除 proof 属性后的 securedDocument 副本。令 output 为 inputDocument 的副本。
  3. 令 matchingProofs 为空列表。
  4. 如果 options 具有作为字符串的 previousProof 项，则将 allProofs 中 id 属性与 previousProof 匹配的元素添加到 matchingProofs。如果 allProofs 中不存在 id 等于 previousProof 的证明， 则必须引发错误，并且应该传达错误类型 PROOF_GENERATION_ERROR。
  5. 如果 options 具有作为数组的 previousProof 项，则从 allProofs 中添加 id 属性与该 数组中某个元素匹配的每个元素。如果 previousProof 列表中的任何元素具有 与 allProofs 中任何元素的 id 属性均 不匹配的 id 属性，则必须 引发错误，并且应该传达错误类型 PROOF_GENERATION_ERROR。
  6. 将 inputDocument.proof 设置为 matchingProofs。
    注： 此步骤保护文档和现有证明

    此步骤添加对命名 图的引用，同时添加 证明 图中包含的所有声明的副本。此步骤至关重要， 因为它会在应用当前证明之前，将任何匹配的证明绑定到文档。 文档的 proof 值将在本算法后面的 步骤中更新。

  7. 运行第 4.1.2 添加 证明节中算法的步骤 1 至 6，并传入 inputDocument、suite 和 options。如果未引发异常，则 将生成的 proof 值追加到 allProofs；否则，引发该 异常。
  8. 将 output.proof 设置为 allProofs 的值。
  9. 将 output 作为新的受保护数据文档返回。

4.1.4 验证证明

以下算法规定如何通过验证数字证明来检查 受保护数据文档的真实性和完整性。该算法 接受以下输入：

mediaType
[MIMESNIFF] 中定义的媒体类型
documentBytes
媒体类型为 mediaType 的字节序列
cryptosuite
一个密码套件实例
expectedProofPurpose
一个可选字符串， 验证者使用它来确保 proof 是由证明 创建者出于预期原因生成的。有关常用值，请参阅第 2.2 证明 目的节
domain
一个可选的字符串集合，证明创建者 使用它将证明锁定到 特定安全域，验证者使用它确保不会在 不同安全域之间使用证明
challenge
一个可选字符串质询，验证者使用它确保 攻击者没有重放先前创建的证明

此算法返回一个验证结果，即一个结构体，其 项为：

verified
true 或 false
verifiedDocument
如果verified 为 false，则为Null；否则为一个输入文档
mediaType
如果verified 为 false，则为Null；否则为一个媒体类型，其中可以包含参数
warnings
一个ProblemDetails 的列表，默认为空列表
errors
一个ProblemDetails 的列表，默认为空列表

当某一步骤称“必须引发错误”时，这意味着必须返回一个 验证结果，其中verified 值为 false，并且errors 列表非空。

  1. 令 securedDocument 为在 documentBytes 上运行将 JSON 字节解析为 Infra 值所得的结果。
  2. 如果 securedDocument 不是映射，或者 securedDocument.proof 不是映射，则必须引发错误，并且应该传达 错误类型 PARSING_ERROR。
  3. 令 proof 为 securedDocument.proof。
  4. 如果 proof.type、 proof.verificationMethod 和 proof.proofPurpose 中一个或多个不存在， 则必须引发错误，并且应该传达 错误类型 PROOF_VERIFICATION_ERROR。
  5. 如果给出了 expectedProofPurpose，并且它与 proof.proofPurpose 不匹配， 则必须引发错误，并且应该传达 错误类型 PROOF_VERIFICATION_ERROR。
  6. 如果给出了 domain，并且它与 proof.domain 不包含相同的字符串（将单个字符串视为仅包含 该字符串的集合），则必须引发错误，并且应该传达错误类型 INVALID_DOMAIN_ERROR。
  7. 如果给出了 challenge，并且它与 proof.challenge 不匹配，则必须 引发错误，并且应该 传达错误类型 INVALID_CHALLENGE_ERROR。
  8. 令 cryptosuiteVerificationResult 为使用 securedDocument 作为输入运行 cryptosuite.verifyProof 算法所得的结果。
  9. 返回一个具有以下项的验证结果：
    verified
    cryptosuiteVerificationResult.verified
    verifiedDocument
    cryptosuiteVerificationResult.verifiedDocument
    mediaType
    mediaType

4.1.5 验证证明集和 证明链

在证明集或证明链中，受保护数据文档具有一个 proof 属性，其中包含证明列表（allProofs）。以下 算法提供了一种检查 受保护数据文档真实性和完整性的方法，即验证 allProofs 中的每个证明。 也可以采用其他方法，尤其是在只希望验证 allProofs 中所含证明的一个子集时。如果采用另一种方法 仅验证证明的一个子集，则需要注意，该子集中任何 具有 previousProof 的证明，只有在其引用的 证明也被视为已验证时，才能被视为已验证。

所需输入为受保护数据文档 （securedDocument）。将生成与 allProofs 中每个证明相对应的验证结果列表，并将单个组合验证结果作为输出 返回。 实现可以与组合验证结果一起返回任何其他验证结果和/或 任何其他元数据。

  1. 将 allProofs 设置为 securedDocument.proof。
  2. 将 verificationResults 设置为空列表。
  3. 对 allProofs 中的每个 proof，执行以下步骤：
    1. 令 matchingProofs 为空列表。
    2. 如果 proof 包含 previousProof 属性，并且该 属性的值是字符串，则将 allProofs 中 id 属性值与 previousProof 的值匹配的元素添加到 matchingProofs。 如果 allProofs 中不存在 id 值等于 previousProof 值的证明，则必须引发错误，并且应该传达错误 类型 PROOF_VERIFICATION_ERROR。如果 previousProof 属性是列表，则从 allProofs 中添加 id 属性值与该 列表中某个元素的值匹配的每个元素。如果 previousProof 列表中的任何 元素具有与 allProofs 中任何元素的 id 属性值均不匹配的 id 属性 值，则必须引发错误，并且应该传达错误类型 PROOF_VERIFICATION_ERROR。
    3. 令 inputDocument 为移除 proof 值后的 securedDocument 副本，然后将 inputDocument.proof 设置为 matchingProofs。
      注：保护文档和先前的证明

      请参阅第 4.1.3 添加证明集/链节步骤 6 中的注释，以了解 此步骤保护哪些文档属性和先前的证明。

    4. 在 inputDocument 上运行第 4.1.4 验证证明节中算法的步骤 4 至 8；如果未引发异常，则将 cryptosuiteVerificationResult 追加到 verificationResults。
  4. 将 successfulVerificationResults 设置为空列表。
  5. 令 combinedVerificationResult 为空结构体。将 combinedVerificationResult.status 设置为 true，将 combinedVerificationResult.document 设置为 null，并将 combinedVerificationResult.mediaType 设置为 null。
  6. 对 verificationResults 中的每个 cryptosuiteVerificationResult：
    1. 如果 cryptosuiteVerificationResult.verified 为 false， 则将 combinedVerificationResult.verified 设置为 false。
    2. 否则，将 combinedVerificationResult.document 设置为 cryptosuiteVerificationResult.verifiedDocument，将 combinedVerificationResult.mediaType 设置为 cryptosuiteVerificationResult.mediaType，并将 cryptosuiteVerificationResult 追加到 successfulVerificationResults。
  7. 如果 combinedVerificationResult.status 为 false，则将 combinedVerificationResult.document 设置为 null，并将 combinedVerificationResult.mediaType 设置为 null。
  8. 返回 combinedVerificationResult、successfulVerificationResults。

4.1.6 上下文验证

以下算法提供了一种机制，可用于确保 应用程序在执行文档输入特定的业务规则之前，理解 与该文档关联的上下文。有关此算法的更多 理由，请参阅第 2.4.1 验证上下文节。 此算法接受以下输入：文档（映射 inputDocument）、一组 已知 JSON-LD 上下文（列表 knownContext），以及一个用于 在检测到未知上下文时重新压缩的布尔值（布尔值 recompact）。

此算法返回一个上下文验证结果， 即一个结构体，其项为：

validated
true 或 false
validatedDocument
如果validated 为 false，则为Null；否则为一个输入文档
warnings
一个ProblemDetails 的列表，默认为空列表
errors
一个ProblemDetails 的列表，默认为空列表

上下文验证算法如下：

  1. 将 result.validated 设置为 false， 将 result.warnings 设置为空列表， 将 result.errors 设置为空列表，将 compactionContext 设置为空 列表； 并将 inputDocument 克隆到 result.validatedDocument。
  2. 令 contextValue 为 result.validatedDocument 的 @context 属性值， 该值可能未定义。
  3. 如果 contextValue 与 knownContext 不深度相等， result.validatedDocument 中的任何子树包含 @context 属性，或者 contextValue 中的任何 URI 解引用到与已知良好值或密码学哈希不匹配的 JSON-LD 上下文文件，则执行适用操作：
    1. 如果 recompact 为 true，则将 result.validatedDocument 设置为 使用 inputDocument 和 knownContext 作为输入运行 JSON-LD 压缩算法所得的结果。如果压缩失败，则向 result.errors 添加至少一个错误。
    2. 如果 recompact 不为 true，则向 result.errors 添加至少一个错误。
  4. 如果 result.errors 为空，则将 result.validated 设置为 true；否则，将 result.validated 设置为 false，并从 result 中移除 document 属性。
  5. 返回 result 的值。

实现可以包含额外警告或错误，以强制执行 实现特定或特定使用场景所需的进一步验证规则。

  • detail 值应该为该错误提供更长且人类可读的字符串。

4.2 密码套件通用算法

4.2.1 引言

本节为非规范性内容。

编辑者注

这些算法适用于非选择性披露的情况。其中有 两个由一组通用函数构建的关键算法。它们 是“创建证明”和“验证证明”，分别由4.1.2 添加 证明 和4.1.4 验证证明通用算法调用。 对于所有非选择性披露密码套件，这些算法都具有共同的 结构。我们在下面两节中给出这些 算法以及其中使用的通用函数。 这里可能需要解释所有参数，即规范化 方案、哈希函数、签名函数、验证函数以及 证明编码。

4.2.2 创建证明

以下算法规定，在给定 未受保护数据文档和正确指定的 密码套件时，如何创建数据完整性证明。 密码套件的选择会设定 canonScheme、 hashName、sigFunc、verifyFunc 和 proofEncoding 的值，这些值 用于 下面的算法。其他必需输入是 未受保护数据文档（映射 unsecuredDocument）和一组证明 选项（映射 options）。输出为数据完整性证明（映射）或错误。

  1. 令 proof 为证明选项 options 的克隆。
  2. 令 proofConfig 为运行第 4.2.4.2 证明配置节中的算法所得的结果，并将 options、cypherSuiteName、canonScheme 和 hashName 作为参数传入。
  3. 令 transformedData 为运行第 4.2.4.3 转换节中的算法所得的结果，并将 unsecuredDocument、 options、 cypherSuiteName、canonScheme 和 hashName 作为 参数传入。
  4. 令 hashData 为运行第 4.2.4.1 哈希节中的算法所得的结果，并将 transformedData、 proofConfig 和 hashName 作为参数传入。
  5. 令 proofBytes 为运行第 4.2.4.4 证明序列化节中的算法所得的结果，并将 hashData、options 和 sigFunc 作为参数传入。
  6. 如果 proofEncoding 为 base64，令 proof.proofValue 为 proofBytes 的 base64-url 编码的 Multibase 编码；否则，如果 proofEncoding 为 base58，令 proof.proofValue 为 proofBytes 的 base58-btc 编码的 Multibase 值。
  7. 将 proof 作为数据完整性证明返回。

4.2.3 验证证明

以下算法规定，在给定 受保护数据文档时，如何验证数据完整性证明。必需输入为 受保护数据文档（映射 securedDocument）。此 算法返回 一个验证结果，它是一个结构体，其 项为：

verified
true 或 false
verifiedDocument
如果verified 为 false，则为Null；否则为未受保护数据文档
  1. 令 unsecuredDocument 为移除 proof 值后的 securedDocument 副本。
  2. 令 proofOptions 为移除 proofValue 后的 securedDocument.proof 副本。
  3. 将 cryptosuiteName 设置为 securedDocument.proof.cryptosuite， 它必须是指定密码套件之一。 根据密码套件规范，设置 canonScheme、 hashName、 verifyFunc 和 proofEncode 的值。
  4. 如果 proofEncode 为 base64，令 proofBytes 为 securedDocument.proof.proofValue 中的 Multibase 解码的 base64-url 值；否则，令 proofBytes 为 Multibase 解码的 base58-btc 值。

4.3 选择性披露 算法

4.3.1 引言

本节为非规范性内容。

对支持密码学选择性披露的凭证，会使用三种高级算法。 首先，颁发者使用添加基础 证明算法创建支持选择性 披露的已签名凭证。然后，持有者使用添加派生证明算法 创建由颁发者签名的凭证的选择性披露版本，并 附带派生证明。最后，验证者使用验证派生 证明算法，依据颁发者的验证 信息验证收到的带派生证明的选择性披露凭证。

本规范允许采用三种不同的选择性披露实现方法， 它们主要作用于可验证凭证中的声明 层级；也就是说，它们允许持有者选择性地 披露或不披露凭证中的每个特定声明。这三种方法 考虑了所使用的基础密码学签名 算法的效率。只有一种（待）标准化的密码学签名 算法 BBS 原生支持选择性披露，也就是说，它会针对有序声明列表生成基础 签名，并支持针对该声明列表的子集创建 “派生签名”。对于其他 密码学签名算法，通常使用两种方法： （1）为每个声明提供单独的签名，或者（2）对所有声明的 “加盐哈希”列表进行签名。我们将第一种称为SIC（对 单个声明签名），第二种称为SHoC（声明的加盐哈希）。 签名算法天然支持多个声明的情况 将称为MCS（多声明支持）。

所有方法都使用类似的机制来保护与证明相关的元数据， 并最大限度减少派生 证明中未披露信息的数据泄露。出于这些目的，它们在基础证明和派生证明中 都会产生大致相似的开销。 同样，所有方法都使用相同的编码来表示 进入证明的各个数据项，即 CBOR，并使用 base64-url 将原始八位字节最终编码为字符串。因此，此信息未显示在摘要 表 1中。

SIC 方法会在转换步骤之后对各个声明进行签名。因此， 其基础证明大小随声明数量乘以所选签名算法生成的 签名大小而增长。因此，这种方法 适用于生成较小签名的签名算法。类似地， 派生证明的大小随已披露声明的数量 乘以签名大小而增长，也就是说，披露的声明越少， 证明越小。这是一个很好的特性，而另外两种方法不具备该特性。

采用SHoC 方法时，会为 每个声明创建一个盐值（随机 nonce）。将该盐值与声明连接起来，然后对成对的盐值+声明列表 应用密码学 抗碰撞哈希函数， 从而生成哈希列表，每个声明对应一个哈希。新配对的盐值 和哈希列表会组合起来，并使用所选签名算法进行签名。只需要一个 签名；因此，这种方法适合签名 大小较大的签名算法。此方法的一个缺点是，完整的 盐值和哈希列表都必须传递给持有者和验证者。为了验证 已披露的声明，验证者首先需要验证组合后的 盐值和哈希列表的签名；然后需要获知该声明在 列表中的索引；接着使用列表中的适当盐值，验证 盐值与收到的声明连接后的哈希值是否与 表中的哈希匹配。

在一种 MCS 签名算法 BBS 中，生成的基础证明非常短， 只有 80 字节，而派生证明会为每个未披露声明增加 32 字节。

4.4.1 TransformSD

以下算法规定如何将未受保护的输入文档 转换为可作为第 4.4.2 HashSD 节中 哈希算法的输入的转换后文档，并且根据具体方法，还可以作为加盐哈希算法 4.6.1 SaltedHashSD 的输入。

  6. 将 nonMandatory 初始化为 groups.mandatory.nonMatching 映射中的值。

以下算法规定如何对 转换后的数据文档和证明配置进行密码学哈希， 生成可作为方法特定算法（例如 4.5.1 SerializeBase-SIC 和 4.6.2 SerializeBase-SHoC）输入的 密码学哈希数据。

4.6.5 ParseDerived-SHoC

以下算法解析 SHoC 方法派生证明 值中的组件。必需输入为派生证明值（proofValue）。 输出为单个证明数据对象，其中 包含六个元素，名称分别为 "signature"、"salts"、 "saltedHashes"、"labelMap"、"mandatoryIndexes" 和 "selectiveIndexes"。

  1. 如果 proofValue 字符串不以 u 开头，这表示它不是 multibase-base64url-no-pad 编码的值，则必须引发错误 并且应该传达错误类型 PROOF_VERIFICATION_ERROR。
  2. 将 decodedProofValue 初始化为对 proofValue 中前导 u 之后的子字符串执行 base64url-no-pad 解码所得的结果。
  3. 如果 decodedProofValue 不以 SHoC 方法派生证明 标头字节 0xd9、0x5d 和 0x11 开头，则必须引发错误 并且应该传达错误类型 PROOF_VERIFICATION_ERROR。
  4. 将 components 初始化为对 三字节 SHoC 方法派生证明标头之后的字节进行 CBOR 解码所得的数组。如果 结果不是包含以下六个元素的数组—— 长度与签名大小相对应的字节数组； 字节数组的数组，其中每个字节数组的长度均适合盐值大小； 字节数组的数组，其中每个字节数组的长度均与哈希大小相对应； 从整数到字节数组的映射，其中每个字节数组长度为 32； 整数数组；以及另一个整数数组——则必须 引发错误 并且应该传达错误类型 PROOF_VERIFICATION_ERROR。
  5. 使用调用 4.7.7 decompressLabelMap 中的算法所得的结果替换 components 中的第四个元素，并将 components 现有的 第四个元素作为 compressedLabelMap 传入。
  6. 将证明数据作为对象返回，其属性分别设置为这五个 元素，名称为 "signature"、"salts"、"saltedHashes"、 "labelMap"、"mandatoryIndexes" 和 "selectiveIndexes"。
编辑者注

我们是否还应该提及对 salts、 saltedHashes、mandatoryIndexes 和 selectiveIndexes 值的额外检查？尤其是， salts 和 saltedHashes 的长度必须相同。 mandatoryIndexes 和 selectiveIndexes 的所有 元素都应该处于从 0 到 salts 长度的范围内。mandatoryIndexes 和 selectiveIndexesArrays 中不应有重复项。此外，这些数组各自的元素 应按递增顺序排列。请注意，最低限度的额外检查 出现在 4.6.6 VerifyDerived-SHoC 中。

4.6.6 VerifyDerived-SHoC

以下算法尝试验证 SHoC 方法的派生 证明。该算法由受 SHoC 方法保护的 可验证 凭证的验证者调用。输入包括 JSON-LD 文档 （document）、派生证明数据（proofData）、验证数据 （verifyData）以及任何 自定义 JSON-LD API 选项，例如文档加载器。此算法返回 一个验证结果：

  1. 令 unsecuredDocument 为移除 proof 值后的 document 副本。
  2. 将 signature、salts、saltedHashes 和 selectiveIndexes 初始化为 proofData 参数中与各自属性名称关联的值，并将 proofHash、nonMandatory 和 mandatoryHash 初始化为 verifyData 参数中与 各自属性名称关联的值。
  3. 如果 salts 的长度与 saltedHashes 的长度不匹配， 则必须引发错误，并且应该传达 错误类型 PROOF_VERIFICATION_ERROR， 以表明盐值数量与加盐哈希数量不匹配。
  4. selectiveIndexes 数组元素的值必须介于 0 与 salts 数组长度减一之间。如果不是， 则必须引发错误，并且应该传达 错误类型 PROOF_VERIFICATION_ERROR， 以表明选择性索引超出范围。
  5. 将 toVerify 初始化为以下值按顺序进行字节连接的结果：proofHash、 mandatoryHash、salts 和 saltedHashes，其中数组值 本身也连接在一起。
  6. 将 verified 初始化为 true。
  7. 将 verificationCheck 初始化为应用 "cryptosuite" 属性所指示的适当签名算法的验证 算法所得的结果， 将 toVerify 作为要针对 signature 进行验证的数据。 如果 verificationCheck 为 false，则将 verified 设置为 false。
  8. 对 nonMandatory 中的每个条目（nq、index），验证每个 选择性披露（非强制）陈述的加盐 哈希：
    1. 令 computedHash 为 salts[selectiveIndexes[index]] 与 nq 连接结果的哈希。
    2. 将 verificationCheck 初始化为比较 computedHash 与 saltedHashes[selectedIndexes[index]] 值所得的结果。
    3. 如果 verificationCheck 为 false，则将 verified 设置为 false。
  9. 返回一个具有以下项的验证结果：
    verified
    verified 的值
    verifiedDocument
    如果 verified 为 true，则为 unsecuredDocument，否则为Null

4.7.3 createLabelMapFunction

以下算法创建一个标签映射工厂函数，该函数使用 输入标签映射将规范空白节点标识符替换为另一个 值。必需输入为标签映射 labelMap。输出为 函数 labelMapFactoryFunction。

  1. 创建函数 labelMapFactoryFunction，其具有一个必需输入 （规范节点标识符映射 canonicalIdMap），并将 空白节点标识符映射 bnodeIdMap 作为输出 返回。将该函数的实现设置为：
    1. 生成新的空 bnode 标识符映射 bnodeIdMap。
    2. 对 canonicalIdMap 中的每个映射条目 entry：
      1. 使用 entry 值中的规范标识符作为 labelMap 中的键，以获取新标签 newLabel。
      2. 向 bnodeIdMap 添加新条目 newEntry，使用 entry 中的键，并以 newLabel 作为值。
    3. 返回 bnodeIdMap。
  2. 返回 labelMapFactoryFunction。

4.7.4 createShuffledIdLabelMapFunction

以下算法创建一个标签映射工厂函数，该函数使用 HMAC 对规范空白节点标识符进行打乱。必需输入为 HMAC （此前已使用秘密密钥初始化）HMAC。输出为函数 labelMapFactoryFunction。

  1. 创建函数 labelMapFactoryFunction，其具有一个必需输入 （规范节点标识符映射 canonicalIdMap），并将 空白节点标识符映射 bnodeIdMap 作为输出 返回。将该函数的实现设置为：
    1. 生成新的空 bnode 标识符映射 bnodeIdMap。
    2. 对 canonicalIdMap 中的每个映射条目 entry：
      1. 对 entry 值中的规范标识符执行 HMAC 操作，以获得 HMAC 摘要 digest。
      2. 生成新的字符串值 b64urlDigest，并将其初始化为 "u" 后接 digest 值的 base64url-no-pad 编码版本。
      3. 向 bnodeIdMap 添加新条目 newEntry，使用 entry 中的键，并以 b64urlDigest 作为值。
    3. 按如下方式从 bnodeIdMap 派生打乱后的映射：
      1. 将 hmacIds 设置为 bnodeIdMap 中值的排序数组，并将 bnodeKeys 设置为 bnodeIdMap 中键的有序数组。
      2. 对 bnodeKeys 中的每个键，将该键在 bnodeIdMap 中的 值替换为该值在 hmacIds 数组中的 索引位置，并在前面加上 "b"，即 bnodeIdMap.set(bkey, 'b' + hmacIds.indexOf(bnodeIdMap.get(bkey)))。
    4. 返回 bnodeIdMap。
  2. 返回 labelMapFactoryFunction。
注

应注意，上述算法中的步骤 1.2 与 [DI-ECDSA] 的 第 3.3.4 节 createHmacIdLabelMapFunction中的步骤 1.2 相同， 因此开发者在同时实现 两者时或许能够复用代码或调用该函数。

4.7.5 createHmacIdLabelMapFunction

以下算法创建一个标签映射工厂函数，该函数使用 HMAC 将规范空白节点标识符替换为其编码后的 HMAC 摘要。必需输入为 HMAC（此前已使用 秘密密钥初始化）HMAC。输出为函数 labelMapFactoryFunction。

  1. 创建函数 labelMapFactoryFunction，其具有一个必需输入 （规范节点标识符映射 canonicalIdMap），并将 空白节点标识符映射 bnodeIdMap 作为输出 返回。将该函数的实现设置为：
    1. 生成新的空 bnode 标识符映射 bnodeIdMap。
    2. 对 canonicalIdMap 中的每个映射条目 entry：
      1. 对 entry 值中的规范标识符执行 HMAC，以获得 HMAC 摘要 digest。
      2. 生成新的字符串值 b64urlDigest，并将其初始化为 "u" 后接 digest 值的 base64url-no-pad 编码版本。
      3. 向 bnodeIdMap 添加新条目 newEntry，使用 entry 中的键，并以 b64urlDigest 作为值。
    3. 返回 bnodeIdMap。
  2. 返回 labelMapFactoryFunction。
注：其他 算法也是可行的

可以创建一种不同的原语，它返回一个标签映射工厂 函数，该函数改为对所得 HMAC 摘要进行排序，并根据其排序 顺序，使用前缀和整数在生成的标签映射中分配标签。 此原语可能对选择性披露方案有用， 例如 BBS，这类方案相较于最大限度减少未披露数据泄露，更重视不可关联性。

4.7.6 compressLabelMap

以下算法压缩标签映射。必需输入为 标签映射（labelMap）和 cryptosuite。输出为 压缩后的标签映射。

  1. 将 map 初始化为空映射。
  2. 对 labelMap 中的每个条目（k、v）：
    1. 如果 cryptosuite 设置为 ecdsa-sd-2023，则 向 map 添加一个条目，其键为从 k 中 "c14n" 前缀之后的 字符解析出的十进制整数，其值为对 v 中 "u" 前缀之后的字符执行 base64url-no-pad 解码所得的字节数组。否则，向 map 添加一个条目， 其键为从 k 中 "c14n" 前缀之后的字符解析出的十进制 整数，其值为从 v 中 "b" 前缀之后的字符解析出的十进制 整数。

4.7.8 skolemizeNQuads

以下算法将 N-Quad 字符串数组中的所有空白节点标识符 替换为自定义方案 URN。必需输入为 N-Quad 字符串数组（inputNQuads）和 URN 方案（urnScheme）。 输出为 N-Quad 字符串数组 skolemizedNQuads。 此操作旨在通过使用第 4.7.9 deskolemizeNQuads节中的算法实现可逆。

  1. 创建新的 N-Quad 字符串数组 skolemizedNQuads。
  2. 对 inputNQuads 中的每个 N-Quad 字符串 s1：
    1. 创建新字符串 s2，它是 s1 的副本，其中所有 空白节点标识符都替换为 URN（"urn:"）加上输入 自定义方案（urnScheme）、一个冒号（":"）以及 空白节点标识符的值。例如，类似于以下形式的正则表达式 可以实现所需结果： s1.replace(/(_:([^\s]+))/g, '<urn:custom-scheme:$2>')。

  3. 返回 skolemizedNQuads。

4.7.9 deskolemizeNQuads

以下算法将 N-Quad 陈述数组中的所有自定义方案 URN 替换为空白节点标识符。必需输入为 N-Quad 字符串数组（inputNQuads）和 URN 方案 （urnScheme）。输出为 N-Quad 字符串数组 deskolemizedNquads。此操作旨在 逆转第 4.7.9 deskolemizeNQuads节中的算法的使用。

  1. 创建新的 N-Quad 字符串数组 deskolemizedNQuads。
  2. 对 inputNQuads 中的每个 N-Quad 字符串 s1：
    1. 创建新字符串 s2，它是 s1 的副本，其中所有 URN（"urn:"）加上输入 自定义方案（urnScheme）、一个冒号（":"）以及 空白节点标识符的值，都替换为空白节点前缀（"_:"）加上 空白节点标识符的值。例如，类似于以下形式的正则表达式 可以实现所需结果： s1.replace(/(<urn:custom-scheme:([^>]+)>)/g, '_:$2').。
    2. 将 s2 追加到 deskolemizedNQuads。
  3. 返回 deskolemizedNQuads。

4.7.10 skolemizeExpandedJsonLd

以下算法将展开的 JSON-LD 文档中的所有空白节点标识符替换为自定义方案 URN，包括向 未标记的空白节点分配此类 URN。必需输入为展开的 JSON-LD 文档 （expanded）、自定义 URN 方案 （urnScheme）、UUID 字符串或其他具有可比随机性的字符串 （randomString）以及对共享整数的引用（count）。 还可以传入任何其他自定义选项（例如文档加载器）。 输出为斯科勒姆化 JSON-LD 文档的展开形式 （skolemizedExpandedDocument。此 操作中使用的斯科勒姆化旨在通过使用第 4.7.12 toDeskolemizedNQuads节中的算法实现可逆。

  1. 将 skolemizedExpandedDocument 初始化为空数组。
  2. 对 expanded 中的每个 element：
    1. 如果 element 不是对象，或者它包含键 @value，则将 element 的副本追加到 skolemizedExpandedDocument，然后继续处理下一个 element。
    2. 否则，将 skolemizedNode 初始化为对象，并对 element 中的每个 property 和 value：
      1. 如果 value 是数组，则将 skolemizedNode 中 property 的值设置为递归调用本算法所得的结果， 将 value 作为 expanded 传入，并保持 其他参数不变。
      2. 否则，将 skolemizedNode 中 property 的值设置为 递归调用本算法所得数组结果中的第一个元素， 将仅包含 value 一个元素的数组作为 expanded 传入，并保持其他参数不变。

    4. 否则，如果 skolemizedNode 中 @id 属性的值以 "_:" 开头，则通过将 skolemizedNode 中 @id 属性的值设置为 "urn:"、urnScheme 与空白节点标识符的连接结果， 在进行斯科勒姆化时保留现有空白节点 标识符（即现有 @id 属性值去掉 "_:" 前缀；例如，如果 @id 属性的现有值为 _:b0，则空白节点 标识符为 b0）。
    5. 将 skolemizedNode 追加到 skolemizedExpandedDocument。
  3. 返回 skolemizedExpandedDocument。

4.7.11 skolemizeCompactJsonLd

4.7.12 toDeskolemizedNQuads

以下算法将斯科勒姆化的 JSON-LD 文档（例如使用第 4.7.11 skolemizeCompactJsonLd节中的算法创建的文档） 转换为去斯科勒姆化 N-Quads 数组。必需输入为 JSON-LD 文档 skolemizedDocument。可以传入其他自定义选项（例如文档 加载器）。输出为去斯科勒姆化 N-Quad 字符串数组 （deskolemizedNQuads）。

  4. 返回 paths。

4.7.14 createInitialSelection

以下算法基于 JSON-LD 对象创建初始选择（JSON-LD 文档的片段）。这是第 4.7.16 selectJsonLd节中的算法内部使用的辅助函数。必需输入为 JSON-LD 对象（source）。输出为 JSON-LD 文档片段对象 （selection）。

  1. 将 selection 初始化为空对象。
  2. 如果 source 具有不是空白节点标识符的 id，则将 selection.id 设置为其值。注：任何 JSON 指针 路径中的所有非空白节点标识符必须包含在选择中，这包括任何 根 文档标识符。
  3. 如果设置了 source.type，则将 selection.type 设置为其 值。 注：选择必须包含任何 JSON 指针路径中的所有 type， 包括任何根文档 type。
  4. 返回 selection。

4.7.15 selectPaths

以下算法使用从已解析 JSON 指针解析出的 路径选择紧凑 JSON-LD 文档的一部分。这是第 4.7.16 selectJsonLd节中的算法内部使用的辅助函数。必需输入为 从 JSON 指针解析出的路径数组（paths）、紧凑 JSON-LD 文档（document）、要填充的选择文档 （selectionDocument）以及用于跟踪所选数组的数组的数组 （arrays）。此算法不产生 输出；而是使用通过 paths 选择的 任何值填充给定的 selectionDocument。

  1. 将 parentValue 初始化为 document。
  2. 将 value 初始化为 parentValue。
  3. 将 selectedParent 初始化为 selectionDocument。
  4. 将 selectedValue 初始化为 selectedParent。
  5. 对 paths 中的每个 path：
    1. 将 selectedParent 设置为 selectedValue。
    2. 将 parentValue 设置为 value。
    3. 将 value 设置为 parentValue.path。如果 value 此时为 undefined， 则必须引发错误，并且应该 传达错误类型 PROOF_GENERATION_ERROR， 以表明 JSON 指针与给定的 document 不匹配。
    4. 将 selectedValue 设置为 selectedParent.path。
    5. 如果 selectedValue 此时为 undefined：
      1. 如果 value 是数组，则将 selectedValue 设置为空数组， 并将 selectedValue 追加到 arrays。
      2. 否则，将 selectedValue 设置为初始选择，并将 value 作为 source 传递给第 4.7.14 createInitialSelection节中的算法。
      3. 将 selectedParent.path 设置为 selectedValue。
  6. 注：完成到目标值的路径遍历后，现在将计算所选值。
  7. 如果 value 是字面量，则将 selectedValue 设置为 value。
  8. 如果 value 是数组，则将 selectedValue 设置为 value 的副本。
  9. 在所有其他情况下，将 selectedValue 设置为一个对象，该对象合并 selectedValue 的浅拷贝与 value 的深拷贝，例如 {...selectedValue, …deepCopy(value)}。
  10. 从 paths 获取最后一个 path，即 lastPath。
  11. 将 selectedParent.lastPath 设置为 selectedValue。

4.7.16 selectJsonLd

以下算法使用 JSON 指针数组选择紧凑 JSON-LD 文档的一部分。 必需输入为 JSON 指针数组 （pointers）和紧凑 JSON-LD 文档（document）。假定 document 使用一个 JSON-LD 上下文，分别将 @id 和 @type 别名化为 id 和 type，并且仅在文档顶层使用一个 @context 属性。输出为一个新的 JSON-LD 文档，它表示原始 JSON-LD 文档的选择（selectionDocument）。

  1. 如果 pointers 为空，则返回 null。这表示未从 原始文档中选择任何内容。
  2. 将 arrays 初始化为空数组。此变量将用于跟踪 所选择的稀疏数组，以便在处理完所有 pointers 后 将其变为稠密数组。
  3. 将 selectionDocument 初始化为初始选择，并将 document 作为 source 传递给第 4.7.14 createInitialSelection节中的算法。
  4. 将 selectionDocument 中 @context 属性的值设置为 document 中 @context 属性值的副本。
  5. 对 pointers 中的每个 pointer，从根遍历文档到指针 目标值，同时构建 selectionDocument：
    1. 使用第 4.7.13 jsonPointerToPaths节中的算法，将 pointer 解析为路径数组 paths。
    2. 使用第 4.7.15 selectPaths节中的算法，并传入 document、paths、selectionDocument 和 arrays。
  6. 对 arrays 中的每个 array：
    1. 通过移除已定义元素之间的任何 undefined 元素， 将 array 变为稠密数组。
  7. 返回 selectionDocument。

4.7.17 relabelBlankNodes

以下算法使用空白节点标签映射重新标记 N-Quad 字符串数组中的空白节点标识符。必需输入为 N-Quad 字符串数组（nquads）和空白节点标签映射 （labelMap）。输出为带有重新标记后的空白节点 标识符的 N-Quad 字符串数组（relabeledNQuads）。

  1. 创建新的 N-Quad 字符串数组 relabeledNQuads。
  2. 对 nquads 中的每个 N-Quad 字符串 s1：
    1. 创建新字符串 s2，它是 s1 的副本，但 其中每个空白节点标识符都替换为 以该标识符作为 labelMap 中键所关联的值。
    2. 将 s2 追加到 relabeledNQuads。
  3. 返回 relabeledNQuads。

4.7.18 selectCanonicalNQuads

以下算法使用 JSON 指针数组选择斯科勒姆化紧凑 JSON-LD 文档的一部分，并输出所得的规范 N-Quads，其中任何空白节点标签都使用给定标签映射进行替换。 必需输入为 JSON 指针数组（pointers）、 斯科勒姆化紧凑 JSON-LD 文档（skolemizedCompactDocument） 和空白节点标签映射（labelMap）。可以传入其他自定义选项 （例如文档加载器）。假定 document 使用一个 JSON-LD 上下文，分别将 @id 和 @type 别名化为 id 和 type， 并且仅在文档顶层使用一个 @context 属性。 输出为一个对象，其中包含表示 原始 JSON-LD 文档选择的新 JSON-LD 文档（selectionDocument）、 去斯科勒姆化 N-Quad 字符串数组（deskolemizedNQuads）以及 使用替换后的空白节点标签的规范 N-Quads 数组（nquads）。

  1. 将 selectionDocument 初始化为第 4.7.16 selectJsonLd节中的算法所得的结果，并传入 pointers， 以及作为 document 的 skolemizedCompactDocument。
  2. 将 deskolemizedNQuads 初始化为第 4.7.12 toDeskolemizedNQuads节中的算法所得的结果，并传入 作为 skolemizedCompactDocument 的 selectionDocument，以及 任何自定义选项。
  3. 将 nquads 初始化为第 4.7.17 relabelBlankNodes节中的算法所得的结果，并传入 labelMap， 以及作为 nquads 的 deskolemizedNQuads。
  4. 返回包含 selectionDocument、 deskolemizedNQuads 和 nquads 的对象。

4.7.19 canonicalizeAndGroup

以下算法用于输出与紧凑 JSON-LD 文档的 自定义选择相匹配的规范 N-Quad 字符串。其做法是规范化 紧凑 JSON-LD 文档（使用标签 映射替换任何空白节点标识符），并根据 与每个组关联的选择对所得规范 N-Quad 字符串进行分组。每个组将使用 指定名称和 JSON 指针数组定义。JSON 指针将用于 选择斯科勒姆化文档的部分，使输出能够 转换为规范 N-Quads，以执行组匹配。

必需输入为紧凑 JSON-LD 文档（document）、 标签映射工厂函数（labelMapFactoryFunction）以及 命名组定义的映射（groupDefinitions）。可以传入其他自定义 选项（例如文档加载器）。假定 document 使用一个 JSON-LD 上下文，将 @id 和 @type 分别别名化为 id 和 type，并且仅在文档 顶层使用一个 @context 属性。输出为一个对象，其中包含创建的组 （groups）、斯科勒姆化紧凑 JSON-LD 文档 （skolemizedCompactDocument）、斯科勒姆化展开 JSON-LD 文档（skolemizedExpandedDocument）、去斯科勒姆化 N-Quad 字符串（deskolemizedNQuads）、空白节点标签映射 （labelMap）以及规范 N-Quad 字符串 nquads。

  1. 将 skolemizedExpandedDocument 和 skolemizedCompactDocument 初始化为第 4.7.11 skolemizeCompactJsonLd节中的算法所得结果中与其关联的值， 并传入 document 和任何自定义选项。
  2. 将 deskolemizedNQuads 初始化为 第 4.7.12 toDeskolemizedNQuads节中的算法所得的结果，并传入 skolemizedExpandedDocument 和任何自定义选项。
  3. 将 nquads 和 labelMap 初始化为第 4.7.1 labelReplacementCanonicalizeNQuads节中的算法所得结果中与其关联的 值，并传入 labelMapFactoryFunction、作为 nquads 的 deskolemizedNQuads，以及任何自定义选项。
  4. 将 selections 初始化为新映射。
  5. 对 groupDefinitions 中每个键（name）和值（pointers）条目：
    1. 添加一个键为 name 的条目，其值为第 4.7.18 selectCanonicalNQuads节中的算法所得的结果，并传入 pointers、labelMap、作为 document 的 skolemizedCompactDocument 以及任何自定义选项。
  6. 将 groups 初始化为空对象。
  7. 对 selections 中每个键（name）和值（selectionResult）条目：
    1. 将 matching 初始化为空映射。
    2. 将 nonMatching 初始化为空映射。
    3. 将 selectedNQuads 初始化为 selectionResult 中的 nquads。
    4. 将 selectedDeskolemizedNQuads 初始化为 selectionResult 中的 deskolemizedNQuads。
    5. 对 nquads 中的每个元素（nq）和索引（index）：
      1. 创建映射条目 entry，其键为 index，值为 nq。
      2. 如果 selectedNQuads 包含 nq，则将 entry 添加到 matching；否则，将 entry 添加到 nonMatching。
    6. 将 groups 中的 name 设置为一个对象，其中包含 matching、nonMatching，并将 selectedDeskolemizedNQuads 作为 deskolemizedNQuads。
  8. 返回包含 groups、 skolemizedExpandedDocument、skolemizedCompactDocument、 deskolemizedNQuads、labelMap 和 nquads 的对象。

4.7.20 hashMandatoryNQuads

以下算法使用提供的哈希 API，对必须 披露的 N-Quads 数组进行密码学哈希。必需输入为 必须披露的 N-Quads 数组（mandatory）和哈希函数 （hasher）。输出为密码学哈希（mandatoryHash）。

  1. 将 bytes 初始化为连接后的 mandatory N-Quads 的 UTF-8 表示。
  2. 将 mandatoryHash 初始化为使用 hasher 对 bytes 进行哈希所得的结果。
  3. 返回 mandatoryHash。

5. 安全注意事项

以下章节描述实现本规范的开发者 为创建安全软件而应当了解的安全注意事项。

5.1 密码套件版本控制

密码学通过使用秘密来保护信息。知晓 必要的秘密，可以在计算上轻松访问某些信息。如果通过 计算上困难的暴力破解成功猜出了该秘密，也可以访问相同的信息。 所有现代密码学都要求这种 计算上困难的方法始终保持困难，但由于科学和数学上的突破， 这一点并不总能成立。也就是说， 密码学具有保质期。

本规范通过假定当前使用的任何密码学方法随着时间推移都极有可能 被破解，为所有密码学方法的淘汰做好准备。软件系统必须能够随着时间推移 改变所使用的密码学方法，以便继续保护信息。这种改变可能 涉及增加所需秘密的大小，或修改所使用的密码学 原语。然而，某些密码学参数的组合 实际上可能降低安全性。基于这些假设，系统需要能够 将不同的安全密码学参数组合（也称为 密码套件）彼此区分开来。在标识或进行 密码套件版本控制时，可以采用多种方法，包括： 参数、数字和日期。

参数化版本控制指定密码套件中所使用的特定密码学参数。 例如，可以使用诸如 RSASSA-PKCS1-v1_5-SHA1 这样的标识符。此方案的优点是，训练有素的 密码学专家能够通过该 标识符确定所涉及的所有参数。此方案的缺点是，使用这类 标识符的大多数人并未受过良好训练，因此不会理解 前述标识符表示的是一个已 不再安全可用的密码套件。此外，这种知识缺失可能导致软件 开发者将密码套件标识符的解析进行泛化， 从而使任意密码学原语组合都变得可接受， 导致安全性下降。理想情况下，密码套件应当在软件中 作为特定且可接受的密码学参数配置文件来实现。

数字版本控制可以指定主版本号和次版本号，例如 1.0 或 2.1。数字版本控制传达明确的顺序，并暗示 较高版本号比较低版本号具有更强的能力。这种方法的优点 是，它用一个更简单的模型取代经验较少的 开发者可能无法理解的复杂参数，并传达可能需要 升级的信息。这种方法的缺点是，无法 明确判断升级是否必要，因为软件版本号的增加通常 并不要求升级才能继续运行软件。这可能 导致开发者认为他们使用的特定版本是安全的，而 实际上并非如此。理想情况下，应当向在软件中使用 密码套件的开发者提供额外信号，表明需要定期审查这些 套件是否仍然安全。

基于日期的版本控制为特定 密码套件指定特定发布日期。日期（例如年份）的优点是， 开发者可以立即看出该日期相对较旧还是较新。看到 较旧日期可能促使开发者寻找更新的 密码套件，而参数化或基于数字的版本控制方案 可能不会产生这种效果。基于日期的版本控制的缺点是，一些密码 套件可能在 5 至 10 年内都不会过期，从而促使开发者 寻找更新的密码套件，却发现并没有更新的套件。 虽然这可能带来不便，但它会促成更安全的 生态系统行为。

5.2 保护应用程序 开发者

现代密码学算法提供许多可调参数和 选项，以确保算法能够满足不同使用场景的各种需求。 例如，嵌入式系统具有有限的处理能力和内存环境， 可能没有足够的资源为给定算法生成最强的数字签名。 其他环境（例如金融交易系统） 可能只需要在交易进行的一天内保护数据，而 其他环境可能需要保护数据数十年。为满足 这些需求，密码学算法设计者通常提供多种方式来 配置密码学算法。

密码学库实现者通常会采用 密码学算法设计者和规范作者创建的规范，并以 使用其库的应用程序开发者可以使用所有选项的方式实现这些规范。 这可能是因为不知道特定应用程序开发者 在给定密码学部署中可能需要哪种功能组合。 因此，往往会向应用程序开发者公开所有选项。

使用密码学库的应用程序开发者通常不具备 为特定应用程序正确选择 密码学参数和选项所需的密码学专业知识。这种 专业知识的缺乏可能导致为特定应用程序 不恰当地选择密码学参数和选项。

本规范确定了利益相关方的优先顺序：保护应用程序 开发者优先于密码学库实现者，密码学库实现者优先于密码学 规范作者，密码学规范作者优先于密码学算法设计者。基于这些 优先级，提出以下建议：

  • 建议密码学算法设计者 [RFC7696] 尽可能减少 选项和参数的数量，以确保 密码学库实现者的软件库具有更容易审计的安全攻击 面。
  • 建议密码学规范作者在可能的情况下进一步 尽可能减少选项和参数的数量，以确保 密码学敏捷性，同时将下游软件库可审计的安全 攻击面保持在最低限度。
  • 建议密码学库实现者在可能的情况下向应用程序开发者提供已知 良好的选项和参数组合。理想情况下，任何算法 类（例如椭圆曲线数字签名）都应提供两个预设默认配置， 使用这些预设时无法 微调参数和选项。可以向专家提供库选项， 以便微调其对库的使用，但应阻止普通 应用程序开发者使用这些选项。
  • 密码学库实现者可以提供已弃用和实验性的 密码学功能，但建议仅在开发者明确 请求时提供，例如通过库选项，并且 库应产生警告，说明应用程序已启用已弃用或实验性的密码学功能。
  • 建议应用程序开发者从若干预设的 密码学库配置中进行选择，并避免修改密码学 选项和参数，或使用实验性或已弃用的密码学功能。

上述指导旨在确保在架构较低层提供有用的密码学选项和 参数，同时不向可能无法 充分理解每个选项利弊权衡的应用程序开发者 公开这些选项和参数。

5.3 密码套件 命名约定

第 5.1 密码套件版本控制节强调了 提供有关特定密码套件时效性的、相对容易理解的信息的重要性，而第 5.2 保护应用程序开发者节进一步强调应最大限度减少 需要指定的选项数量。实际上，第 3. 密码套件节 列出了密码套件的要求，其中包括对算法、转换、哈希和序列化的详细规定。 因此，密码套件的名称无需包含所有这些细节，这意味着第 5.1 密码套件版本控制节提到的 参数化版本控制既没有必要 也不可取。

建议的密码套件命名约定是一个 字符串，由签名算法标识符组成，如果密码套件支持不兼容的 实现选项，则通过连字符与 选项标识符分隔，之后再跟一个连字符和该套件提出时的大致 年份。

例如，[DI-EDDSA] 基于 EdDSA 数字签名，支持 两种基于规范化方法的不兼容选项，并且大约于 2022 年提出，因此它有两个不同的密码套件名称： eddsa-rdfc-2022 和 eddsa-jcs-2022。

尽管 [DI-ECDSA] 基于 ECDSA 数字签名，支持与 [DI-EDDSA] 相同的两种 不兼容规范化方法，并且通过两组替代的 椭圆曲线和哈希支持 两个不同的安全级别（128 位和 192 位），但它只有两个密码套件名称： ecdsa-rdfc-2019 和 ecdsa-jcs-2019。安全级别以及相应的 曲线和哈希由验证时使用的公钥的多密钥格式 确定。

5.4 敏捷性和分层

密码学敏捷性是一种实践，通过这种实践，人们设计 频繁连接的信息安全系统，以支持 在多个密码学原语和/或算法之间切换。密码学敏捷性的主要 目标是使系统能够快速适应新的 密码学原语和算法，而无需对 系统基础设施进行破坏性更改。因此，当某个特定密码学原语，例如 SHA-1 算法，被确定为不再安全可用时，系统可以 通过简单修改配置文件，重新配置为使用更新的原语。

当信息安全系统中的客户端和服务器 定期保持联系时，密码学敏捷性最有效。然而，当 由特定密码学算法保护的消息长期存在时，例如 可验证 凭证，和/或客户端（持有者）可能无法 轻松再次联系服务器（颁发者）时，密码学敏捷性就 无法提供所期望的保护。

密码学分层是一种实践，其中 设计很少连接的信息安全系统，使其 同时采用多个原语和/或算法。密码学分层的 主要目标是让系统在一个或多个密码学算法或原语 失效时仍能生存下来，而不会失去 对载荷的密码学保护。例如，同时使用 RSA、ECDSA 和 Falcon 算法对同一份 信息进行数字签名， 将提供一种可以在这三个数字 签名算法中的两个失效时仍能继续工作的机制。当某种特定密码学保护被攻破时， 例如使用 768 位密钥的 RSA 数字签名，系统仍可以利用 未被攻破的密码学保护继续保护 信息。强烈建议开发者对所有 可能需要保护一年或更长时间的已签名内容利用此功能。

本规范同时支持这两种形式的敏捷性。它支持 密码学敏捷性，使人们可以轻松从一种算法切换到 另一种算法。它还支持密码学分层，使人们可以 同时使用多个密码学算法，通常是并行使用， 从而用于保护信息的任一算法都可以在不依赖 或要求其他算法的情况下使用，同时仍保持数字证明格式 易于开发者使用。

5.5 更安全的抽象

证明包含一个 proofValue，其中可以嵌入若干 与密码学证明相关的参数。例如， 数据完整性 ECDSA 密码套件 v1.0 规范中的选择性披露算法 在 proofValue 中包含多个密码学签名，每个 可选择性披露的项对应一个签名。这样做是为了使该 技术对应用程序开发者而言更易用、更安全。

本规范强烈建议规范作者使用单个值来抽象 应用层很少需要的信息。就像表示图像的 data: URL 将许多图像渲染参数封装到 单个值中一样，proofValue 属性（以及其他类似属性） 抽象了对应用程序开发者没有用的信息，以便 简化对那些对应用程序确实重要的字段的识别。 以这种方式抽象信息会形成更易于 开发者处理的数据结构，同时也更不容易受到例如因编程错误 添加或删除关键属性而导致的意外 损坏，从而对密码学层产生负面影响。

本规范中的数据完整性设计将通常只对密码学层 有用的信息抽象到单个属性中，以减轻 应用程序开发者的负担并增强系统安全性。

5.6 转换

有时，在密码学保护过程中转换被保护的数据是有益的。 这种“内联”转换可以使 特定类型的密码学保护不受其所承载数据格式的影响。 例如，一些数据完整性密码套件使用 RDF 数据集规范化 [RDF-CANON]，它将初始 表示转换为规范形式 [N-QUADS]，然后进行序列化、 哈希和数字签名。只要表达受保护 数据的任何语法都能够转换为这种规范形式，就可以验证 数字签名。这使得同一个针对信息的数字签名可以 表示在 JSON、CBOR、YAML 和其他兼容语法中，而无需 为每种语法创建密码学证明。

能够跨多种语法表示相同的数字签名 是有益的，因为系统通常具有其运行所使用的原生数据格式。 例如，一些系统针对 JSON 数据编写，而另一些系统 针对 CBOR 数据编写。如果没有转换，以 CBOR 作为内部数据处理格式的系统就需要将数字签名的数据 结构存储为 JSON（反之亦然）。这会导致数据被重复存储，并且如果数据库中存储的 未签名表示意外偏离已签名表示， 还可能增加安全攻击面。通过使用 转换，数字证明可以存在于原生数据格式中，从而 有助于防止随时间推移发生原本无法检测的数据库漂移。

本规范旨在通过使用“内联”数据转换，避免要求复制已签名 信息。强烈建议应用程序开发者 以其应用程序的原生数据格式处理受密码学保护的数据， 不要将密码学证明与被保护的数据分开存储。 还强烈建议开发者定期确认 受密码学保护的数据在写入和读取 应用程序存储时没有遭到篡改。

某些转换，例如 RDF 数据集规范化 [RDF-CANON]，具有 针对攻击者可用来消耗 过多处理周期的输入数据集的缓解措施。此类攻击称为 数据集投毒，所有 现代 RDF 数据集规范化器都必须检测这些恶意 输入并停止处理。RDF 数据集规范化的测试套件 包含此类被投毒的数据集，以确保所有 符合要求的实现都具备这些缓解措施。一般而言，使用转换的密码套件 规范都必须缓解此类 攻击，并强烈建议实现者确保其使用的软件库 强制实施这些缓解措施。这些攻击与任何资源耗尽攻击 属于同一大类，例如 HTTP 客户端 故意放慢连接，从而耗尽服务器上的连接资源。 建议实现者在实施 防御性安全策略时考虑此类攻击。

5.7 受保护的信息

任何数据完整性证明所保护的数据是 转换后的数据。转换后的数据 由特定密码套件指定的转换算法生成。这种保护机制不同于一些 更传统的数字签名机制，后者不会对输入数据执行任何形式的 转换。转换的优点 详见第 5.6 转换节。

例如，密码套件，如 ecdsa-jcs-2019 和 eddsa-jcs-2022，使用 JSON 规范化方案（JCS）将数据转换为规范化 JSON， 然后对其进行密码学哈希和数字签名。这种 方法的一个优点是，添加或删除不会影响被签名 信息含义的格式字符，例如空格、制表符和换行符， 不会使数字签名失效。更传统的数字签名 机制不具备此能力。

其他密码套件，如 ecdsa-rdfc-2019 和 eddsa-rdfc-2022，使用 RDF 数据集 规范化将数据转换为规范化的 N-Quads [N-QUADS]，然后进行密码学哈希和数字 签名。这种方法的一个优点是，密码学签名可以 移植到多种不同语法中，例如 JSON、YAML 和 CBOR， 而不会使签名失效。更传统的密码学签名 机制不具备此能力。

强烈建议实现者和开发者不要信任 包含数据完整性证明的信息，除非该证明已经验证， 并且已验证数据由某个软件库的返回值提供， 该软件库已确认返回的所有数据都已成功受到保护。

5.8 数据不透明性

应用程序数据的可检查性会影响系统效率和 开发者生产力。当受密码学保护的应用程序数据，例如 基数编码的二进制数据，不容易被数据库等应用程序子系统处理时， 会增加处理受密码学 保护信息的工作量。例如，如果受密码学保护的载荷 可以由数据库原生存储和索引，则会产生一个更简单的系统， 该系统：

  • 可以在不更改受保护信息的情况下利用现有行业标准数据库功能，
  • 避免复制数据的复杂性，其中一个数据副本保留 消息和数字签名，而另一个副本仅存储并索引 消息，并由该副本驱动系统行为，
  • 避免必须在结构上修改 受保护信息的定制解决方案所带来的复杂性，例如序列化和反序列化 具有多个嵌套基数编码载荷的嵌套数字签名数据。

类似地，可以由多个上游网络系统处理的 受密码学保护载荷可以增强正确分层 安全架构的能力。例如，如果上游系统无需 反复解码传入载荷，则可以通过使上游子系统专门 主动抵御攻击来增强系统分配处理负载的能力。 虽然在采取实质性行动之前始终需要检查数字签名， 但可以对透明载荷执行其他上游检查——例如基于标识符的速率限制、 签名过期检查或 nonce/质询检查——以拒绝明显无效的请求。

此外，如果开发者无法轻松查看系统中的数据， 就会妨碍轻松审计或调试系统正确性的能力。例如， 要求应用程序开发者复制粘贴基数编码的应用程序数据 会使开发更加困难，并增加明显错误 被遗漏的可能性，因为每条消息都必须通过一个手动操作的 基数解码工具。

然而，有时正确的设计决策就是使数据 不透明。不需要由其他应用程序子系统处理的数据， 以及不需要由应用程序 开发者修改或访问的数据，可以序列化为不透明格式。示例包括数字 签名值、密码学密钥参数以及只需由密码学库访问、 无需由应用程序开发者修改的其他数据字段。 当底层子系统不会让应用程序开发者面对 不透明数据的底层复杂性时，也有适合使用数据不透明性的情况，例如执行 静态加密的数据库。在这些情况下，应用程序开发者仍然 针对透明的应用程序数据格式进行开发，而数据库负责 管理将应用程序数据加密写入长期存储以及从长期存储解密读取的 复杂性。

本规范力求提供一种架构，使应用程序数据 保持其原生格式而不变得不透明，同时其他密码学 数据，例如数字签名，则保留其不透明的二进制编码形式。 强烈建议密码套件实现者在设计其套件时考虑适当地使用数据 不透明性，并权衡 使应用程序数据不透明与在应用层提供对密码学数据访问之间的设计取舍。

5.9 验证方法绑定

实现者通过从验证方法的定义转到 受控标识符 文档，然后确保该受控标识符 文档还 包含对该验证方法的引用， 来确保验证方法绑定到 特定控制者。此过程 在 检索验证方法的算法中描述。

5.10 验证 关系验证

当实现正在验证证明时，至关重要的是， 它不仅要验证用于 生成证明的验证方法是否列在受控标识符 文档中，还要验证该方法 是否原本就用于生成正在验证的证明。此过程 称为“验证关系验证”。

验证关系的验证过程概述于 受控标识符 v1.0 规范的第 3.3 节 检索验证方法。

此过程用于确保密码学材料，例如私有 密码学密钥，不会被应用程序滥用于非预期目的。 密码学材料被滥用的一个示例是，原本用于颁发可验证凭证的私有密码学 密钥反而被用于 登录网站（即用于身份验证）。不检查验证关系 是危险的，因为某些密码学材料的限制和保护配置 可能由其预期用途决定。例如， 某些应用程序可能被信任为仅将密码学材料用于 一个目的，或者某些密码学材料可能受到更严格的保护， 例如存储在数据中心的硬件安全模块中， 而不是作为未加密文件存储在笔记本电脑上。

5.11 证明目的验证

当实现正在验证证明时，至关重要的是， 它要验证证明目的与预期用途相匹配。

此过程用于确保应用程序不会将证明滥用于 非预期目的，因为这对证明创建者而言是危险的。一个 滥用示例是，某个证明声明其目的是保护 可验证凭证 中的断言，但反而被用于身份验证以 登录网站。在这种情况下，证明创建者向任意数量的 可验证凭证 附加了证明，并预期这些凭证会分发给 数量不受限制的其他方。如果网站错误地将这种证明接受为 身份验证，而不是其预期用途， 则这些方中的任何一方都可以作为证明创建者登录网站。

5.12 规范化方法 安全性

执行转换（例如规范化）的方式可能 影响系统的安全特性。选择最佳 规范化机制取决于使用场景。通常， 满足所需安全要求的最简单机制 是最佳选择。本节尝试提供简单指导，以帮助 实现者在本规范提及的两种主要规范化机制之间进行选择， 即 JSON 规范化方案 [RFC8785] 和 RDF 数据集规范化 [RDF-CANON]。

如果应用程序仅使用 JSON，并且不依赖任何形式的 RDF 语义，那么使用采用 JSON 规范化方案 [RFC8785] 的密码套件是一种很有吸引力的方法。

如果应用程序使用 JSON-LD，并且需要保护 文档的语义，那么使用采用 RDF 数据集规范化 [RDF-CANON] 的密码套件是一种很有吸引力的 方法。

还建议实现者注意，也有其他不执行任何 转换的机制可用，这些机制通过将数据封装在 密码学信封中，而不是将证明嵌入数据中来保护数据，例如 JWT [RFC7519] 和 CWT [RFC8392]。 这些方法在某些使用场景中具有简单性的 优势，但代价是失去本规范详细描述的方法所提供的一些优点。

5.13 规范化方法 正确性

本规范使用的算法过程之一是规范化， 它是一种转换。规范化是这样一个过程： 将可能以多种语义 等价方式表示的信息作为输入，并以一种统一方式表示所有输出，这种方式称为 “规范形式”。

使用规范化所得数据完整性证明的安全性 高度依赖算法的正确性。例如，如果规范化算法将两个具有不同 含义的输入转换为相同输出，那么作者的意图可能会被 错误地呈现给验证者。攻击者可以利用这一点作为 攻击向量。

此外，如果输入中与语义相关的信息没有出现在 输出中，那么攻击者可以将此类信息插入消息， 而不会导致证明验证失败。这类似于 在对消息进行密码学签名时常用的另一种转换： 密码学哈希。如果攻击者能够从不同输入产生相同的密码学 哈希，那么该密码学哈希算法就不被视为 安全。

强烈建议实现者确保对任何用于将输入转换为哈希 过程的规范化算法进行适当审查。适当审查至少包括 与经过同行评审的算法正确性数学证明相关联；最好还应有多个实现， 并由标准制定组织中的专家进行审查。 强烈建议实现者不要发明或使用新机制，除非他们接受过 信息规范化方面的正式培训，和/或能够接触到该领域中 有能力提出经过同行评审的算法正确性数学证明的专家。

5.14 网络请求

本规范的设计使得在验证符合要求的受保护文档上的证明时 不需要任何网络请求。 然而，读者可能会注意到，JSON-LD 上下文 和验证 方法可能包含需要通过网络连接检索的 URL。 对于验证期间或验证后可能从网络加载的任何 URL，都存在这种问题。

在可能的情况下，强烈建议实现者永久或积极地 缓存此类信息，以减少可能需要通过网络获取这些 URL 的实现的攻击面。 例如，第 2.4 上下文和词汇表节描述了 JSON-LD 上下文的缓存技术，并且某些验证 方法，例如 did:key [DID-KEY]，根本无需从网络获取。

当无法使用缓存信息时，例如首次遇到 基于特定 HTTP URL 的验证方法实例时， 提醒实现者在任何可能从网络获取资源的过程中采取防御措施，以缓解 拒绝服务攻击。

5.15 其他安全注意事项

由于本规范所述的保护文档技术 具有通用性质，因此其使用带来的安全影响可能不会 立即为读者所察觉。为了理解完整软件系统中可能需要考虑的 安全问题类型，强烈建议实现者阅读 该技术在 可验证凭证 生态系统中的使用方式 [VC-DATA-MODEL-2.0]；有关更多信息，请参阅 可验证凭证安全注意事项一节。

6. 隐私注意事项

以下章节描述实现本规范的开发者 为创建增强隐私的软件而应当了解的 隐私注意事项。

6.1 不可关联性

当数字签名的载荷包含由多个 验证者看到的数据时，它就会成为一个关联点。此类数据的一个示例是 购物忠诚卡号码。可关联数据可由验证者用于跟踪 目的，而这有时可能违反隐私预期。 某些数据可以用于跟踪这一事实可能并不显而易见。 此类可关联数据的示例包括但不限于静态 数字签名或图像的密码学哈希。

可以创建不包含任何 可关联跟踪数据的数字签名载荷，同时仍提供一定程度的保证，表明该 载荷对于给定交互是可信的。这种特性称为 不可关联性，它确保数字签名载荷中不使用任何可关联 数据，同时仍提供一定程度的 信任，其充分程度必须由每个验证者确定。

需要理解的是，并非所有使用场景都需要甚至允许 不可关联性。在某些使用场景中，由于监管或安全原因， 需要可关联性和相关性，例如关联运输和储存 危险材料的组织和个人。当特定交互存在隐私预期时， 不可关联性非常有用。

至少有两种机制能够提供一定程度的不可关联性。 第一种方法是确保消息中使用的任何数据值都绝不会 在将来的消息中重复。第二种方法是确保任何重复的数据 值都能提供足够的群体隐私，使得在实践中无法 关联在交互中期望获得一定程度隐私的实体。

可以使用多种方法来实现不可关联性。这些方法包括 确保消息是一次性承载令牌，其中不包含 可用于关联目的的信息；使用能够确保 足够群体隐私级别的属性；以及使用能够让 出示消息的实体重新生成新签名，同时不会损害 对所出示消息信任的密码套件。

6.2 选择性披露

选择性披露是一种技术，它使 先前已签名消息（即由其创建者签名的消息）的接收者能够只披露 消息的一部分，而不会破坏这些部分的可验证性。 例如，为了租车，可以选择性披露数字驾驶执照。 这可能只涉及披露执照中的颁发 机构、驾照号码、出生日期和获准驾驶的机动车类别。 请注意，在这种情况下，驾照号码属于可关联 信息，但由于驾驶者的 全名和地址未被共享，因此仍保留了一定程度的隐私。

并非所有软件或密码套件都能够提供选择性披露。 如果消息作者希望接收者能够对其进行选择性披露， 那么作者需要在具体 消息上启用选择性披露，并且双方都需要使用支持该功能的密码套件。作者也可以 强制要求披露消息的某些部分。希望 选择性披露消息部分内容的接收者需要使用 能够执行这种技术的软件。支持 选择性披露的密码套件示例是 bbs-2023。

可以用不 保持不可关联性的方式选择性披露信息。例如，可能希望披露与某批货物相关的检验 结果，其中包括货物标识符或批次 编号，由于监管要求，这些信息可能必须可关联。 然而，可能无需披露完整检验结果，因为 只选择性披露通过/未通过状态就可能被认为足够。有关 在保护隐私的同时披露信息的更多信息，请参阅第 6.1 不可关联性节。

6.3 先前的证明

使用第 2.1.2 证明 链节中定义的 previousProof 功能时， 实现需要对一个或多个先前的证明进行数字签名， 从而将它们包含在受保护载荷中。这不可避免地会公开 与添加先前证明的每个实体相关的信息。

至少，先前证明的验证方法，例如 公钥，会被证明链中下一个证明的创建者看到。如果先前证明的创建者并不打算 被纳入证明链，这可能会成为隐私问题，但当 向任何类型的文档添加不可否认的数字签名时，这又是不可避免的结果。

可以使用更高级的密码学机制，例如 群签名， 来隐藏消息签名者的身份， 数据完整性密码套件也可以 缓解这一隐私问题。

6.4 对网络 请求进行指纹识别

对于在证明验证期间或之后可能从网络加载的任何 URL， 都存在指纹识别方面的顾虑。本 规范的设计使得在验证符合要求的受保护文档上的证明时 无需进行任何网络请求。 然而，读者可能 会注意到，JSON-LD 上下文和 验证 方法可能包含需要通过网络连接检索的资源 URL， 从而引发指纹识别方面的顾虑。

例如，符合要求的受保护文档的创建者 可能为每个文档分别构造唯一的 JSON-LD 上下文 URL 和 验证 方法 URL。在验证此类文档时，如果验证者从 网络获取这些信息，就会向文档创建者暴露其对该 符合要求的受保护文档的关注，这可能 导致除文档创建者之外的任何实体的隐私预期 出现不匹配。

强烈建议实现者遵循第 5.14 网络 请求节中 关于 URL 缓存以及从网络获取 URL 时采取防御性实现的指导。 鼓励使用诸如 Oblivious HTTP 等技术从网络检索资源，而不会暴露 发出请求的客户端。此外，还 可以使用启发式方法确定符合要求的受保护文档的创建者 是否正在以可能违反隐私预期的方式使用指纹识别 URL。 这些启发式方法可用于向可能 处理包含疑似指纹识别 URL 的文档的实体显示警告。

6.5 规范化方法 隐私性

执行转换（即规范化）的方式可能 影响系统的隐私特性。选择最佳 规范化机制取决于使用场景。 本节尝试提供简单指导，以帮助 实现者从隐私角度在本规范提及的两种主要规范化机制之间进行选择， 即 JSON 规范化方案 [RFC8785] 和 RDF 数据集规范化 [RDF-CANON]。

如果应用程序不需要对 受保护文档中的信息执行选择性披露，也不使用 JSON-LD，那么 JSON 规范化方案 [RFC8785] 是一种很有吸引力的方法。

如果应用程序使用 JSON-LD，并且可能需要选择性披露 受保护文档中的信息，那么使用采用 RDF 数据集规范化 [RDF-CANON] 的密码套件是一种很有吸引力的 方法。

还建议实现者注意，也有其他 不执行任何转换的选择性披露机制可用，它们通过将数据封装在 密码学信封中而不是将证明嵌入数据中来保护数据，例如 SD-JWT [SD-JWT]。这种方法在某些使用场景中具有简单性的 优势，但代价是失去本 规范详细描述的方法所提供的一些优点。

6.6 其他隐私注意事项

由于本规范所述的保护文档技术 具有通用性质，因此其使用带来的隐私影响可能不会 立即为读者所察觉。为了理解完整软件系统中可能需要考虑的 隐私问题类型，强烈建议实现者阅读 该技术在 可验证凭证 生态系统中的使用方式 [VC-DATA-MODEL-2.0]；有关更多信息，请参阅 可验证凭证隐私注意事项一节。

7. 无障碍注意事项

以下章节描述实现本规范的开发者 为确保其软件可供具有不同认知、运动和视觉 需求的人使用而强烈建议考虑的无障碍注意事项。通常而言，本规范由系统软件使用， 不会直接向个人公开需要考虑无障碍问题的 信息。然而，在某些情况下，个人可能会 间接接触到本规范所表示的信息，因此 针对这些情况提供以下指导。

7.1 呈现时间值

本规范允许表示与 密码学证明有效期相关的日期和时间。如果对证明进行处理并检测到其超出 允许的时间范围，这些信息可能会间接 暴露给个人。向个人公开这些日期和时间时， 强烈建议实现者在显示软件中表示日期和时间时考虑 文化规范和区域设置。 除这些 注意事项外，以减轻接收信息的个人认知负担的方式 呈现时间值也是建议的最佳实践。

例如，在传达某组特定 数字签名信息的过期日期时，强烈建议实现者使用更易理解的语言来呈现 过期时间，而不是使用 以准确性为优先的语言。将过期时间表示为“此票已于 三天前过期。”优于诸如“此票已于 2023 年 7 月 25 日下午 3:43 过期。”这样的表述。前者提供了一个更容易 理解的相对时间，而后者要求个人在脑中进行 计算，并假定其能够执行这种 计算。

A. 理解证明集 和证明链

本节为非规范性内容。

第 2.1.1 证明集节和第 2.1.2 证明链节 描述了如何在受保护数据文档中表示多个证明；也就是说， 与在受保护数据文档中只包含单个 证明 不同，可以像示例 6和 示例 7所示，在列表中表示多个证明。此列表的元素是 证明集的成员，并且可以选择构成证明链。本节的目的 是解释这些功能各自的预期用途，尤其是 它们不同的安全属性。这些不同的安全 属性导致第 4.1.3 添加证明集/链节中的处理存在差异。

本节以简化方式表示受保护数据文档及其证明， 以便观察重要的安全属性。

考虑一个包含三个签署人的场景：CEO、CFO 和工程副总裁。 每个人都需要拥有用于签署 文档的公钥和秘密密钥对。我们分别将这些签署人的秘密/公钥表示为 secretCEO/publicCEO、secretCFO/publicCFO 和 secretVPE/publicVPE。

当构建一个证明集，其中每个签署人都独立签署 inputDocument 时，我们用符号方式构造证明如下：

示例 9：证明创建方式的符号表示 
{
  "type": "DataIntegrityProof",
  "cryptosuite": "eddsa-jcs-2022",
  "created": "2023-03-05T19:23:24Z",
  "proofPurpose": "assertionMethod",
  "verificationMethod": publicCEO,
  "proofValue": signature(secretCEO, inputDocument)
}

其中 publicCEO 用作解析到 CEO 公钥的引用的占位符，而 signature(secretKey, inputDocument) 表示特定数据完整性密码套件 使用特定秘密密钥对 特定文档计算数字签名。type、cryptosuite、created 和 proofPurpose 属性与我们的讨论无关，因此将省略它们。具体来说， 下面展示一个由工程副总裁、CFO 和 CEO 签署的文档上的 证明集中的所有证明：

示例 10：证明集的符号表示 
{
  // 未显示受保护数据文档的其余部分（见上文）
  "proof": [{
    "verificationMethod": publicVPE,
    "proofValue": signature(secretVPE, inputDocument)
  }, {
    "verificationMethod": publicCFO,
    "proofValue": signature(secretCFO, inputDocument)
  }, {
    "verificationMethod": publicCEO,
    "proofValue": signature(secretCEO, inputDocument)
  }]
}

接收到包含证明集的受保护数据文档的 持有者或任何 其他中介，都能够在将其传递给另一个实体之前删除该集合中的任意 proof 值，而受保护 数据文档仍然能够通过验证。这可能符合也可能不符合原意。对于 向一位受重视的员工发送生日贺卡的签署人来说，使用证明集可能没有问题。 如果我们试图对一个审批沿公司层级逐级上升的业务流程建模， 这就不理想，因为任何 中介都可以从证明集中删除签名，而它仍能 通过验证；例如，在下面的示例中，看起来 CFO 和 CEO 在没有工程副总裁同意的情况下批准了某件事情。

示例 11：移除证明集中的签名 
{
  // 未显示受保护数据文档的其余部分（见上文）
  "proof": [{
    "verificationMethod": publicCFO,
    "proofValue": signature(secretCFO, inputDocument)
  }, {
    "verificationMethod": publicCEO,
    "proofValue": signature(secretCEO, inputDocument)
  }]
}

可以通过设置证明集中每个证明的 id 属性，使另一个证明能够引用它，从而在这些证明之间引入依赖关系。 换言之，被依赖的证明将由其他 依赖证明使用 previousProof 属性进行引用。这样的 依赖链可以具有任意深度。这种 证明链的意图是对业务流程中的审批链或 公证人见证模拟签名进行建模。

以下示例展示如何构建证明链：首先由 工程副总裁批准文档；随后 CFO 根据工程副总裁的 签名并经过审查后批准该文档； 最后 CEO 根据前两个签名并经过审查后批准 文档。由于其他人将引用工程副总裁的 签名，我们需要向证明添加 id。首先由工程 副总裁签署输入文档：

示例 12：包含第一个已设置 `id` 属性的证明的证明链 
{
  // 未显示受保护数据文档的其余部分（见上文）
  "proof": {
    "id": "urn:proof-1",
    "verificationMethod": publicVPE,
    "proofValue": signature(secretVPE, inputDocument)
  }
}

接下来，CFO 收到文档，验证工程副总裁已签署 该文档，并根据审查结果和工程副总裁的签名对其签署。 为此，我们需要通过指明对刚收到文档中的证明的 依赖关系来建立证明链。具体做法是 将第二个证明的 previousProof 属性设置为 urn:proof-1，这样就会将第二个证明“绑定”到第一个证明，然后 对其进行签名。以下示例展示如何创建对第一个证明的依赖关系：

示例 13：包含两个证明的证明链 
{
  // 未显示受保护数据文档的其余部分（见上文）
  "proof": [{
    "id": "urn:proof-1",
    "verificationMethod": publicVPE,
    "proofValue": signature(secretVPE, inputDocument)
  }, {
    "id": "urn:proof-2",
    "verificationMethod": publicCFO,
    "previousProof": "urn:proof-1",
    "proofValue": signature(secretCFO, inputDocumentWithProof1)
  }]
}

现在，当 CEO 验证收到的带有上述 证明链的受保护 数据文档时，会检查 CFO 是否是基于 工程副总裁的签名进行签署的。首先，会使用工程副总裁的公钥检查 id 属性值为 urn:proof-1 的证明。 请注意，此证明针对的是原始文档。

接下来，CEO 将使用 CFO 的公钥检查 id 属性值为 urn:proof-2 的证明。然而，为了确保 CFO 是在工程副总裁已经签署的证明基础上签署该文档的， 我们针对文档和 urn:proof-1 的组合来验证此证明。如果验证成功，CEO 就会签署，从而生成一个 针对包含 urn:proof-1 和 urn:proof-2 的文档的证明。最终的 证明链如下所示：

示例 14：包含三个证明的证明链 
{
  // 未显示受保护数据文档的其余部分（见上文）
  "proof": [{
    "id": "urn:proof-1",
    "verificationMethod": publicVPE,
    "proofValue": signature(secretVPE, inputDocument)
  }, {
    "id": "urn:proof-2",
    "verificationMethod": publicCFO,
    "previousProof": "urn:proof-1",
    "proofValue": signature(secretCFO, inputDocumentWithProof1)
  }, {
    "id": "urn:proof-3",
    "verificationMethod": publicCEO,
    "previousProof": "urn:proof-2",
    "proofValue": signature(secretCEO, inputDocumentWithProof2)
  }]
}

随后，该受保护数据文档的接收者会以类似的 方式对其进行验证，检查链中的每个证明。
