摘要

跨源存储（COS）是一种内容寻址缓存，允许 Web 应用跨不同源存储和检索大型文件，例如 AI 模型、WebAssembly 模块和广泛使用的 JavaScript 库。文件通过其加密哈希而非 URL 进行标识，因此，某个源获取过一次的字节完全相同的资源，可以由用户代理允许的任何其他源复用，而无需再次下载。为了防止通过缓存中是否存在某个文件来推断用户访问过哪些网站，只有其哈希达到类似 k-匿名的流行度门槛时，才允许跨源披露该文件。

1. 简介

本节为非规范性内容。

存储通常按源进行分区，以保护用户的安全和隐私。这是正确的 默认做法，但对于一小类体积非常大、极为流行且公开分发的 资源（AI 模型、WebAssembly 模块、JavaScript 库、游戏引擎和大型 Web 字体），这种方式并不合适， 因为无论哪个站点请求它们，它们逐字节都是完全相同的文件。当两个 互不相关的源都依赖同一个 8 GB 模型时，按源分区的存储会迫使 用户下载并保留该模型两次，这会浪费用户的带宽、存储空间 和电量，也会浪费整个网络的资源。

跨源存储（COS）是一种内容寻址缓存，它以加密哈希而不是 URL 作为键，使用户代理能够在选择使用它的多个源之间共享此类资源的单个存储副本。 将资源存储到 COS 始终是由存储源明确选择加入的行为，并且即使某个源原本 被允许读取资源，用户代理也可以拒绝确认资源是否存在；参见 § 8 隐私和安全考虑事项。

本规范的入口点是 requestFileHandle() 方法，该方法通过 crossOriginStorage 暴露： 

const hash = {
  algorithm: 'SHA-256',
  value: '8f434346648f6b96df89dda901c5176b10a6d83961dd3c1ac88b59b2dc327aa4',
};
try {
  const handle = await navigator.crossOriginStorage.requestFileHandle(hash);
  const file = await handle.getFile();
  // 对该文件执行某些操作。
} catch (err) {
  if (err.name === 'NotFoundError') {
    // 不在（可披露的）跨源存储中；改为从网络获取。
  }
}

本规范复用了 FileSystemFileHandle、 FileSystemWritableFileStream 以及文件系统标准 [FS] 中的相关 基础设施，并将其限定在一个专用文件系统中；该文件系统 在多个源之间共享，并与任何源的私有文件系统或用户可见文件系统分离。

本规范定义命令式 JavaScript API，以及宿主集成所构建于其上的共享存储步骤。 相关提案将同一底层缓存集成到其他宿主规范中：HTML 中 link 和 script 上的 crossoriginstorage 属性、 crossOriginStorage JavaScript 导入属性、CSS cross-origin-storage() <request-url-modifier>，以及用于 fetch() 的 crossOriginStorage RequestInit 选项。每一项都在各自的宿主规范中定义；参见 § 9 与其他规范的集成。

2. 概念

2.1. 哈希

COS 哈希是一个结构，包含 以下项：

算法

一个字符串， 用于命名 [WEBCRYPTO] 所识别的哈希算法，例如 "SHA-256"。

值

一个字符串，它是由 算法 生成的摘要的小写十六进制编码。 对于 "SHA-256"，其长度为 64 个字符。

algorithm 字典成员的类型是普通 DOMString，尽管它的值空间恰好就是 [WEBCRYPTO] 接受的哈希算法名称集合。HashAlgorithmIdentifier 是 (object or DOMString)，而它的 object 分支 会由 [WEBCRYPTO] 规范化为具有 Algorithm 形状的字典，使调用者能够向需要额外参数的算法传递这些 参数（例如 {name: "HMAC", hash: "SHA-256"}）。哈希 算法不接受此类参数， algorithm 会作为内容寻址 键的一部分被存储、比较和往返传递，并且本规范 示例中的每一次使用都是裸字符串；在此接受任意对象不会增加任何能力，却会让 相等性和序列化 变得不必要地复杂。因此，DOMString 是该字段 更窄且更正确的类型。

如果两个 COS 哈希值的 相等条件为：它们的 algorithm 值ASCII 不区分大小写匹配，并且它们的 value 值完全 相等。

注： value 已经在规范上要求为小写（见上文），因此对它的比较只是普通的 字符串比较。algorithm 没有规范要求的大小写形式，因此对它进行 ASCII 不区分大小写比较。

内容寻址 存储是指其条目以 相等性的 COS 哈希作为键：两个具有 相同字节且使用相同哈希算法的文件就是同一个条目，无论有多少源 存储了它们，也无论它们是从多少 URL 获取的。

2.2. COS 条目

每个用户代理都有一个单独的 COS 注册表，它是一个从 COS 哈希值到 COS 条目结构的映射， 由所有使用跨源存储的源共享。一个 COS 条目具有以下项：

哈希

一个 COS 哈希。

字节

Null，或者一个字节序列，其在 hash 的 algorithm 下的摘要等于 hash 的 value。在写入者完成 验证和 存储之前为 Null。

状态

为 "pending" 或 "written"。条目最初为 "pending"， 并且恰好只会在首次设置 bytes 时变为 "written"。

待处理写入者计数

一个非负整数，初始值为 0，用于统计尚未完成的写入者：由 完成创建请求返回的 FileSystemFileHandle 句柄，其关闭写入 尚未完成。仅用于在 验证和存储中判断失败的写入是否可以安全地 清理；参见 § 3.3 创建和写入文件。

源

一个列表，其中包含被明确授予跨源读取访问权限的源，该权限独立于 公共哈希 列表。该列表最初为空，只会增长。这是决定谁可以读取条目的三个彼此独立且可叠加的授权之一， 另外两个是其存储源（始终可读，并且与其 同站的源也始终可读）以及全局 可披露。

注： 如果一次写入的 origins 是一个明确为空的 列表 （origins: []），它授予的权限与省略 origins 的写入完全相同：即条目的 存储源以及与其同站的源，这是每个条目都具有的基线 （参见确定 COS 披露）。应用 上限 会把空列表变为 null，因此两种写入都会以相同状态进入后续的 完成创建请求。明确给出的列表只会增加接收方； 它绝不会阻止写入者自己的站点访问该条目。

全局可披露

一个布尔值，初始为 false，用于记录该条目是否曾以请求 全局（"*"）可用性的方式写入。当为 true 时，任何其请求 通过 § 8.3 可用性门控的源都可以读取该条目，也就是说，该源请求的hash 必须位于 PHL 上，并且 GREASE’ing 未抑制该请求。一旦被设置，它就会一直保持 true。

注： 这是一个独立于 origins 的项，因此后续 的全局可用性请求会在现有的明确 origins 列表之上增加 "*" 授权。 如果把两者合并为一个字段，那么提供字节的写入者就可以把一个列表范围的条目变成 "*" 范围的条目。由于 § 8.3 可用性门控 仅适用于 "*" 授权，此前能够通过该 列表 读取条目的源，在 hash 不 位于 PHL 上时，就会开始收到 "NotFoundError"。 将这些授权保持独立，可使每次可见性更改都严格地只是增加权限， 这正是可升级但绝不可降级所要求的。

存储源

一个集合，其中包含至少曾成功完成一次 写入该条目字节的源。该集合会跨页面加载持久保存，并随时间 增长；除 § 5.2 逐出所述情况外，绝不会缩小。位于 存储源中的源始终可以通过 requestFileHandle() 获取该条目的句柄， 无论 origins 如何，也无论 该条目的 hash 是否位于公共哈希列表 （PHL）上。 参见 § 3.5.1 原始存储者访问。

用户代理具有关联的 跨源存储队列，它是 启动新的并行队列的结果。对 COS 注册表的所有操作都要 排入此队列，以使它们按照 排入的 顺序执行，并且不会交错。

2.3. 公共哈希列表

确认某个哈希是否存在于跨源存储中，本身就可能泄露有关 用户浏览历史的信息（参见 § 8.2 跨站探测）。这种风险 特别针对全局 授权。条目的明确 origins 列表以及每个条目都带有的同站基线， 其披露范围已经受到存储源明确选择的限制，而 使条目全局可披露则可能将其暴露给 Web 上的任意 源。为了限制这一 特定风险，一个全局可披露资源仅在其哈希通过一个额外的、 独立门槛时，才会通过该授权向其存储源之外的源披露：即它必须属于 公共哈希列表 （PHL），这是一个供应商中立的、 由实现定义的COS 哈希 值允许列表。只有在某个哈希通过类似 k-匿名性的 流行度门槛之后（例如，相同字节的资源出现在至少一定数量的独立 源上），才会被加入公共哈希列表，这样确认其存在于共享缓存中就不会提供 关于任何特定用户的信息。

如果 COS 哈希 hash 等于用户 代理当前的公共哈希列表快照中的一个条目，则称其位于公共 哈希列表上。

公共哈希列表的检索协议、 更新频率、数据格式、流行度阈值和治理 将作为本规范的配套产物进行详细设计，其精神类似公共后缀列表——后者是 [URL] 标准的配套数据文件；参见本仓库中的 公共哈希列表说明文档。该设计 提议由 WHATWG 治理，其模式参考公共后缀列表跨供应商、 滚动发布的先例，并以独立确认的普遍性作为加入条件。 这是上文所述类似 k-匿名性门槛的一个具体实例，该门槛只在线下、哈希加入列表时应用一次， 因而用户代理无需在每次查询时重复执行。 这些内容目前都尚未在本提案之外确立。该列表的早期非规范性代码原型 目前位于本仓库的 public-hash-list/implementation/；一个专门的、 跨供应商仓库仍然是 PHL 说明文档中所描述的治理目标。本 规范只依赖于哈希是否位于 PHL 上，因此无论 列表的检索机制、治理模型或该设计的其他部分如何演进，本规范都保持正确。

3. CrossOriginStorageManager 接口

[Exposed=(Window,Worker), SecureContext]
interface CrossOriginStorageManager {
  Promise<FileSystemFileHandle> requestFileHandle(
      CrossOriginStorageRequestFileHandleHash hash,
      optional CrossOriginStorageRequestFileHandleOptions options = {});
};

dictionary CrossOriginStorageRequestFileHandleHash {
  required DOMString value;
  required DOMString algorithm;
};

dictionary CrossOriginStorageRequestFileHandleOptions {
  boolean create = false;
  (DOMString or sequence<DOMString>) origins;
};

interface mixin NavigatorCrossOriginStorage {
  [SameObject, SecureContext] readonly attribute CrossOriginStorageManager crossOriginStorage;
};
Navigator includes NavigatorCrossOriginStorage;
WorkerNavigator includes NavigatorCrossOriginStorage;

每个 Navigator 和 WorkerNavigator 对象都具有关联的 CrossOriginStorageManager 对象。crossOriginStorage getter 步骤 是返回this 关联的 CrossOriginStorageManager。

每个 CrossOriginStorageManager 对象都具有关联的源，该源在对象创建时被设置为 this 的相关设置对象的源。

注： 从相关设置对象获取源，而不考虑脚本本身的任何属性， 对 worker 会产生一个值得明确说明的结果。由 blob: URL 创建的 worker 具有创建它的上下文的源，因此它与该源共享完全相同的 跨源存储视图：这样的 worker 写入的内容，其创建页面可以读取回来，而 页面存储的内容，worker 也可以读取。blob: URL 本身并不是独立的源， 撤销它也不会使 worker 与该视图分离。由 data: URL 创建的 worker 具有不透明源。本规范目前并未定义当 调用方源为不透明源时 requestFileHandle() 应执行什么操作； 不透明源规则在验证 COS 请求中 仅约束调用者所指定的源。不透明源没有稳定身份可用于作为 存储 源或同 站比较的键，因此不存在任何有意义的授权对象。

3.1. requestFileHandle() 方法

handle = await navigator . crossOriginStorage . requestFileHandle(hash)

如果由 hash 标识的文件存在于跨源存储中，并且可以向调用源 披露，则返回该文件的句柄。否则，以 "NotFoundError" DOMException 拒绝。 "NotFoundError" 并不能证明该文件 在物理上不存在于跨源存储中；参见 § 8.3 可用性门控。调用者可以 将其视为“改为从网络获取此文件。”

handle = await navigator . crossOriginStorage . requestFileHandle(hash, { create: true })

返回可用于将由 hash 标识的文件写入 跨源 存储的句柄；如果尚不存在条目，则创建新条目，默认仅限同站源。 无论条目是否已经存在，调用者都需要通过该句柄的 createWritable() 方法写入完整的文件内容；用户代理会在此时验证所写入的字节是否哈希为 hash， 否则以 "DataError" DOMException 拒绝。此要求可防止 源利用创建请求作为探测 hash 是否已经存在的预言机。

handle = await navigator . crossOriginStorage . requestFileHandle(hash, { create: true, origins: "*" })

同上，并在写入完成后额外使该条目可以向任何其对 hash 的请求通过 § 8.3 可用性门控的源披露。

handle = await navigator . crossOriginStorage . requestFileHandle(hash, { create: true, origins: ["https://a.example", "https://b.example"] })

同上，但将披露严格限制为列出的源（此外还包括调用 源以及已经位于 存储源中的任何源）。

requestFileHandle(hash, options) 方法 的步骤如下：

  1. 令 result 为一个新的 promise。

  2. 令 realm 为 this 的相关 Realm。

  3. 令 global 为 this 的相关全局对象。

  4. 令 origin 为 this 关联的源。

  5. 如果以 global 为参数运行检查跨源存储权限 的结果为 false，则：

    1. 在给定 global 的DOM 操作任务源上排入一个全局任务， 以 "NotAllowedError" DOMException 拒绝 result。

    2. 返回 result。

  6. 令 validationFailure 为以 hash 和 options 为参数运行验证 COS 请求所得的结果。

  7. 如果 validationFailure 不为 null：

    1. 在给定 global 的DOM 操作任务源上排入一个全局任务， 以 validationFailure 拒绝 result。

    2. 返回 result。

  8. 将以下步骤排入 跨源存储队列：

    1. 如果 options["create"] 为 true：

      1. 以 result、hash、options、global 和 realm 为参数运行完成创建请求。

    2. 否则：

      1. 以 result、hash、origin、global 和 realm 为参数运行完成读取请求。

  9. 返回 result。

要验证 COS 请求，给定一个 CrossOriginStorageRequestFileHandleHash hash 和一个 CrossOriginStorageRequestFileHandleOptions options，返回 null 或 TypeError：

  1. 如果 hash["algorithm"] 不是 [WEBCRYPTO] 所识别的哈希算法 名称，则返回一个新的 TypeError。

  2. 当 hash["algorithm"] 与 "SHA-256" ASCII 不区分大小写 匹配时，如果 hash["value"] 不匹配正则 表达式 /^[0-9a-f]{64}$/，则返回一个新的 TypeError。

    注： 未来的哈希算法可以定义 不同的预期摘要长度；本 规范只对 "SHA-256" 作规范性约束，这与其在整个 示例中的用法一致。

  3. 如果 options["origins"] 存在并且 不是 "*"：

    1. 令 candidates 为 options["origins"]， 其中单个字符串按只包含一个项的列表处理。

    2. 如果 candidates 的大小 大于用户代理的 最大源列表长度，则返回一个新的 TypeError。

    3. 对于 candidates 中的每个 candidate：

      1. 如果在 candidate 上运行基本 URL 解析器的结果为失败，或者 解析后的 URL 的源是不透明源，则返回一个新的 TypeError。

  4. 返回 null。

3.2. 读取文件

要完成读取 请求，给定一个 promise result、一个 COS 哈希 hash、一个 源 origin、一个全局对象 global 和一个 Realm realm：

  1. 令 entry 为 COS 注册表中其 hash 等于 hash 的 COS 条目（如果存在），否则为 null。

  2. 如果 entry 不为 null，并且 entry 的状态为 "pending"：

    1. 在给定 global 的DOM 操作任务源上排入一个全局任务， 以 "NotAllowedError" DOMException 拒绝 result。

    2. 返回。

    注： 正在进行写入的哈希 会刻意表现得不同于不存在的哈希，以免调用者把正在进行的写入误认为真正的缓存未命中， 并仅为了写入该文件而开始冗余、并发地下载一个非常大的文件。 参见 § 3.3 创建和写入文件。

  3. 令 disclosableEntry 为以 entry 和 origin 为参数运行应用可用性 门控所得的结果。

  4. 如果 disclosableEntry 为 null：

    1. 在给定 global 的DOM 操作任务源上排入一个全局任务， 以 "NotFoundError" DOMException 拒绝 result。

    2. 返回。

  5. 令 handle 为创建新的 FileSystemFileHandle [FS]所得的结果，其 定位器在 跨源存储文件系统中寻址 disclosableEntry， 并位于 realm 中。

  6. 将 handle 的 COS 源设置为 origin。

  7. 将 handle 的可读取设置为 true。

    注： 此句柄已经通过应用可用性门控，因此调用源 有权访问该条目的字节。

  8. 在给定 global 的DOM 操作任务源上排入一个全局任务， 以 handle 兑现 result。

要确定 COS 披露，给定一个 COS 条目 或 null entry，以及一个 源 origin，返回一个 COS 条目或 null：

  1. 如果 entry 为 null，返回 null。

  2. 断言：entry 的状态为 "written"。

  3. 如果 origin 位于 entry 的存储 源中，则返回 entry。

    注： 原始存储者以及任何 已经成功写入该条目的源，都始终可以读取它。参见 § 3.5.1 原始存储者 访问。

  4. 如果 origin 与 entry 的存储源中的某一项同站，则返回 entry。

    注： 每个条目都具有的同站基线 （即不带 origins 选项的写入所请求的授权）始终有效， 无论之后增加了任何 origins 列表还是全局可披露授权。 因为它是在下方的公共哈希列表门控之前检查， 所以同站 源无论其 hash 是否位于 PHL 上，都可以读取该条目。同站在这里 被视为一个信任单元，因此不会跨越站点边界披露任何 § 8.2 跨站探测所保护的信息。

  5. 如果 origin 的序列化是 entry 的 origins 中的一项，则返回 entry。

    注： 位于明确 origins 列表中的源 可以读取该条目，而无需该条目 位于 PHL 上。存储源通过明确命名它作出了有界的披露决定 （参见 § 3.5 资源可见性升级和 § 7 Cross-Origin-Storage-Allow-Origin 标头）， 在此基础上再要求额外的 全局普遍性，会使普通的受限共享依赖于对通常是专有资源的无关公共策展。 在 全局可披露门控之前执行此检查， 正是为了防止后续的全局可用性写入 撤销已列出源的访问权限。参见 § 8.2 跨站 探测。

  6. 如果 entry 的全局可披露为 true：

    1. 如果 entry 的hash 不位于 PHL 上，返回 null。

      注： 公共哈希列表门控 仅适用于全局授权，即披露可能触及 Web 上任意源的唯一情况。 如果某个条目 全局可披露，但其 hash 不位于 PHL 上， 那么仅通过此授权满足条件的源不会获得披露；若某个源同时 位于存储源、与其同站的集合或明确 origins 列表中， 则已经在上面的步骤中返回。

    2. 如果用户代理选择对此请求应用 GREASE’ing， 返回 null。

      注： GREASE’ing 同样只适用于 全局授权。上面检查的那些授权永远不会 到达此步骤：存储源及其同站源属于一个信任单元，而明确 origins 列表中的源 是由其 Cross-Origin-Storage-Allow-Origin 标头授权的写入者有意指定的。

    3. 返回 entry。

  7. 返回 null。

要应用 可用性门控，给定一个 COS 条目或 null entry，以及一个 源 origin，返回一个 COS 条目或 null：

  1. 返回以 entry 和 origin 为参数运行确定 COS 披露所得的结果。

3.3. 创建和写入文件

由完成创建请求创建的 FileSystemFileHandle 具有关联的 请求的源，即在该句柄被成功写入后， 验证和存储将尝试把条目的 origins 升级到的值。

每个用于寻址 COS 条目的 FileSystemFileHandle 还具有关联的 COS 源，即取得该句柄的源，以及关联的 可读取布尔值，该值控制 getFile() 是否可通过该特定句柄披露条目的字节。 对于由完成读取请求返回的句柄，该值为 true，因为它已经通过 可用性门控；而对于由 完成 创建请求返回的句柄，在同一句柄的验证和存储成功之前，该值为 false。

注： 这被刻意设计为每个句柄自身的属性。 无论条目是否已经存在以及是否已经为 "written"，创建请求都会返回句柄（参见 完成 创建请求），因此如果使用按条目控制的规则，任意源都可以调用 requestFileHandle() 并传入 create: true，然后立即读取一个它从未写入过的条目，从而无需满足 origins、 PHL 成员资格或 GREASE’ing，即可获知其内容。本 规范中的每项披露控制都应用在读取路径上，因此按条目门控会让创建请求绕过 所有这些控制。要求调用者先提供正确的字节，意味着通过创建所得句柄进行的成功读取 不会披露调用者原本并不拥有的信息。

要完成 创建请求，给定一个 promise result、一个 COS 哈希 hash、一个 CrossOriginStorageRequestFileHandleOptions options、一个全局对象 global 和一个 Realm realm：

  1. 令 requestedOrigins 为以 options["origins"] 为参数运行规范化 请求的源所得的结果。

  2. 如果 requestedOrigins 是一个列表，则将 requestedOrigins 设置为以 requestedOrigins 和以 global 为参数运行获取 COS 范围上限所得的结果为参数运行 应用 COS 范围上限所得的结果。

  3. 令 entry 为 COS 注册表中其 hash 等于 hash 的 COS 条目（如果存在），否则为 null。

  4. 如果 entry 为 null：

    1. 将 entry 设置为一个新的 COS 条目，其中 hash 为 hash， bytes 为 null，state 为 "pending"，origins 为一个 空列表，globally disclosable 为 false，并且 storing origins 为一个空集合。

    2. 设置 COS 注册表[hash] 为 entry。

    注： 新条目最初没有明确的 origins 授权，并且不是 全局可披露的； 一旦字节被写入并 验证，requestedOrigins 会在下方通过 验证和 存储中的升级资源可见性应用到它， 这与找到现有条目的请求完全相同。这正是创建 请求在扩大可见性之前必须提供完整字节的原因（参见 § 3.5 资源可见性升级）。

  5. 将 entry 的待处理写入者计数加 1。

    注： 即使调用者从不在 handle 上调用 createWritable()， 或者从不关闭所得流，这仍会把 handle 作为一个尚未完成的写入者进行跟踪。 这样的 被遗弃句柄会永久计入 entry，这与在引入此机制之前，被遗弃的进行中 写入已经会让 entry 永久保持 "pending" 完全一样；参见 验证和 存储。

  6. 令 handle 为创建新的 FileSystemFileHandle [FS]所得的结果，其 定位器在 跨源存储文件系统中寻址 entry， 并位于 realm 中。

  7. 将 handle 的 COS 源设置为 global 的 相关设置对象的源。

  8. 将 handle 的请求的源设置为 requestedOrigins。

  9. 将 handle 的可读取设置为 false。

    注： 无论 entry 是否已存在，也无论它是否已经是 "written"，都会返回 handle。调用者仍需通过 handle 提供完整的文件字节，从而确保写入不能用于探测此前是否存在 （参见 § 8.2 跨站探测），并确保在接受请求中更宽松的 origins 值之前可以验证它；参见 § 3.5 资源可见性升级。

  10. 在给定 global 的DOM 操作任务源上排入一个全局任务， 以 handle 兑现 result。

要规范化 请求的源，给定一个 (DOMString or sequence<DOMString>) 或 undefined origins，返回 "*"、一个由源组成的列表，或 null：

  1. 如果 origins 不存在，返回 null。

  2. 如果 origins 为 "*"，返回 "*"。

  3. 令 list 为 « »。

  4. 对于 origins 中的每个 candidate （单个字符串按只包含 一个项的列表处理）：

    1. 令 candidateOrigin 为对 candidate 运行基本 URL 解析器 所得的源。

      注： 验证 COS 请求已经确认每个 candidate 都可解析为 非不透明源。

    2. 如果 list 不包含 candidateOrigin，则将 candidateOrigin 追加 到 list。

  5. 返回 list。

注： 在这里先进行去重，再执行之后任何到 现有条目的合并，可使 origins 从条目 首次创建时起就不含重复项，因此此后对它的每次克隆也都保持无重复。

当通过在其定位器 寻址某个 COS 条目的句柄上调用 createWritable() 获得的 FileSystemWritableFileStream 被关闭时 [FS]，用户代理必须在 该关闭操作的 promise 被兑现之前运行下面的验证和存储 步骤。

注： 无论关闭是如何 触发的，这都适用：无论是显式 close() 调用，还是到达其 源末尾并默认同时关闭目标的 pipeTo() 调用。[STREAMS] 在 流进入关闭状态时并不区分这两种情况，本算法同样不区分。

验证和存储 步骤，给定由已关闭 流的句柄所寻址的 COS 条目 entry、完整写入的字节序列 bytes，以及关闭操作的 相关设置对象的源 origin，执行如下：

  1. 令 computedValue 为 bytes 的小写十六进制摘要， 使用 entry 的algorithm 所命名的 算法，按照 [WEBCRYPTO] 计算。

  2. 如果 computedValue 与 entry 的value 不完全相等：

    1. 以 "DataError" DOMException 拒绝关闭操作的 promise。

    2. 将以下步骤排入 跨源存储队列：

      1. 将 entry 的待处理写入者计数减 1。

      2. 如果 entry 的state 为 "pending"，并且 entry 的 待处理写入者计数为 0， 则从 COS 注册表中移除 entry 的 hash。

        注： 这就是失败写入 清理自身的方式：一旦不存在其他 尚未完成的写入者，之后对相同哈希的 requestFileHandle() 调用将完全看不到条目，并得到普通的 "NotFoundError"。 该计数可防止 删除某个仍被另一个针对相同哈希并发进行中的写入者使用的条目 （例如两个标签页都发现该哈希不存在，并各自独立开始 写入它）：如果该写入者仍未完成， 或者已经成功，那么要么计数尚未到 0，要么 entry 的state 已不再是 "pending"， 因而此步骤什么也不会做。一个 已经是 "written" 的条目绝不会以这种方式被删除，无论之后有多少 写入者请求它并失败：只有一个从未成功 写入过的条目才有资格被删除。

    3. 中止这些步骤。

  3. 将以下步骤排入 跨源存储队列：

    1. 将 entry 的bytes 设置为 bytes。

    2. 将 entry 的state 设置为 "written"。

    3. 如果尚不存在，则将 origin 追加到 entry 的存储源。

    4. 将 entry 的待处理写入者计数减 1。

    5. 以 entry 和句柄的 请求的源为参数运行 升级资源可见性。

    6. 将句柄的可读取设置为 true。

      注： 只有此句柄变为 可读。针对同一条目但来自另一个 尚未通过写入的创建请求的句柄仍保持不可读。

在用于寻址 COS 条目的 FileSystemFileHandle 上调用 createWritable() 时，必须产生一个其内容初始为空的 FileSystemWritableFileStream， 无论 keepExistingData 的值如何，也无论 被寻址条目的state如何。

注： [FS] 在其他情况下将 keepExistingData 定义为以现有文件内容初始化 流。在这里遵循该行为会使调用者能够成为它从未拥有过的字节的存储 源。无论条目是否已经存在，创建请求都会返回句柄，因此调用者可以为另一个源已经存储的哈希打开可写流， 在未写入任何内容的情况下关闭它，而继承下来的字节仍会哈希为请求的值。这会在 origins、公共哈希列表和 GREASE’ing均未被检查的情况下授予读取权限： 这是由两个单独允许的操作组合出来的可用性 门控绕过。正是同样的理由使 验证和存储 要求每个创建请求都提供完整内容。

注： 因此，一个未执行任何写入便关闭的可写流 持有空字节序列，对于调用者会想要的任何条目而言，它都不会 哈希为请求的值，所以验证和存储会像对待任何其他不匹配一样，以 "DataError" DOMException 拒绝。若实现反而对这种情况报告存储或 I/O 失败， 就是在一个无关错误背后隐藏了验证结果。

文件系统标准 [FS] 尚未定义一个扩展点， 供依赖它的规范把额外的逐写入验证挂接到 FileSystemWritableFileStream 的关闭步骤中。在存在这样的挂接点之前，本节直接描述所需行为；未来版本预计将 正式与 [FS] 集成。

3.4. 存储已获取的资源

§ 9 与其他 规范的集成中列出的宿主集成会存储其 获取的资源，而无需经过 FileSystemFileHandle。 其宿主规范应当 在获取到的字节通过该集成所要求的完整性检查后，运行以下算法。

要将已获取的资源存储到跨源 存储中，给定一个响应 response、一个字节序列 bytes、一个 COS 哈希 hash、"*"、一个由字符串组成的列表 或 null origins，以及一个环境设置对象 settings：

  1. 如果以 settings 的 全局对象为参数运行检查跨源存储 权限所得的结果为 false，则返回。

  2. 如果 origins 不为 null，则令 options 为 «[ "origins" → origins ]»；否则为 «[ ]»。

  3. 如果以 hash 和 options 为参数运行验证 COS 请求所得的结果不为 null， 则返回。

  4. 令 computedValue 为 bytes 的小写十六进制摘要， 使用 hash 的algorithm 所命名的 算法，按照 [WEBCRYPTO] 计算。

  5. 如果 computedValue 与 hash 的value 不完全相等，则返回。

    注： 集成自身的完整性 元数据可以列出多个摘要，只要 匹配其中任何一个即可满足完整性检查。此步骤确保该条目是以这些 精确字节实际生成的哈希作为键。

  6. 令 requestedOrigins 为以 options["origins"] 为参数运行规范化 请求的源所得的结果。

  7. 如果 requestedOrigins 是一个列表：

    1. 如果 response 是一个经过滤响应，则令 internalResponse 为 response 的内部响应；否则为 response。

    2. 将 requestedOrigins 设置为以 requestedOrigins 和以 internalResponse 的标头列表为参数运行解析 COS 范围上限所得的结果为参数运行应用 COS 范围上限所得的结果。

    注： 上限来自已获取 资源自身的响应，因此提供字节的服务器决定 这些字节可以披露给哪些源。加载它的 Document 的 COS 范围上限不起作用：其运营方 并不控制该资源，允许它授权接收方会让任意站点把另一个站点的资源声明为可与其选择的源共享。 用户代理从内部 响应读取该标头，因此这对于不透明的经过滤响应同样有效，而且该标头 永远不会暴露给页面。

  8. 令 origin 为 settings 的源。

  9. 将以下步骤排入 跨源存储队列：

    1. 令 entry 为 COS 注册表中其 hash 等于 hash 的 COS 条目（如果存在），否则为 null。

    2. 如果 entry 为 null：

      1. 将 entry 设置为一个新的 COS 条目，其中 hash 为 hash， bytes 为 null，state 为 "pending"，origins 为 一个空列表，globally disclosable 为 false，并且 storing origins 为一个空集合。

      2. 设置 COS 注册表[hash] 为 entry。

    3. 如果 entry 的state 为 "pending"：

      1. 将 entry 的bytes 设置为 bytes。

      2. 将 entry 的state 设置为 "written"。

      注： 条目在这里可能是 "pending"，因为针对相同哈希的一个 requestFileHandle() 写入者仍在进行中。它的待处理写入者计数保持不变， 因此该写入者自身的验证和存储仍会正常完成；它的 字节 会哈希为相同的值，因此再次存储它们不会改变任何内容。

    4. 如果尚不存在，则将 origin 追加到 entry 的存储源。

    5. 以 entry 和 requestedOrigins 为参数运行 升级资源可见性。

注： 与验证和存储一样，存储操作始终要求 完整的字节，即使 条目已经是 "written"，因此它不会泄露任何此前是否存在的信息。集成在网络获取之前 执行的查找属于读取，受可用性门控以及 § 8.2 跨站探测中的探测注意事项约束。

3.5. 资源可见性升级

COS 条目的可见性可以 升级，但绝不能降级。

要升级 资源可见性，给定一个 COS 条目 entry，以及 "*"、一个由 源组成的列表 或 null requestedOrigins：

  1. 如果 requestedOrigins 为 null，返回。

    注： 省略 origins 只请求同站 可用性，而每个条目已经具有这种可用性（参见 确定 COS 披露），因此没有 任何内容需要增加。

  2. 如果 requestedOrigins 为 "*"：

    1. 将 entry 的全局可披露设置为 true。

    2. 返回。

    注： 这会增加全局授权，但不会 修改 entry 的 origins。已经具有明确 origins 列表的条目会保留它，因此该 列表上的每个源即使在条目变为 全局可披露之后，仍保留不依赖 PHL 的访问权限。这正是 两种授权必须分别存储的关键原因；参见全局可披露。

  3. 对于 requestedOrigins 中的每个 candidateOrigin：

    1. 如果 entry 的 origins 包含 candidateOrigin，则 继续。

    2. 如果 entry 的 origins 的大小 等于用户代理的 最大源列表长度，则 中断。

      注： 任何剩余的 candidateOrigin 值都会从此次升级中被静默丢弃，因为 写入本身已经成功，并且用户代理应当在控制台记录警告， 表明该条目的源列表已达到容量上限。

    3. 将 candidateOrigin 追加到 entry 的 origins。

注： 一次升级只会向 origins 添加内容， 或将全局可披露 设置为 true。请求一个列表的写入者，对于一个已经 全局可披露的条目，也会像对尚未全局可披露的条目一样扩大它， 因为两种授权是 独立的：新列出的源会获得不依赖 PHL 的访问权限，而 "*" 授权仍然保持有效。

注： 任何站点，包括原始 存储者之外的站点，都可以扩大条目的 origins，只要 它同时提供能哈希为该条目的hash 的字节。这是有意为之： 任何已经拥有某一哈希正确字节的站点，按照定义，对于该哈希所表示的内容都与原始存储者 同样具有权威性。

3.5.1. 原始存储者访问

已经成功完成写入某个 COS 条目的源 （也就是条目的存储源中的任意源） 此后始终可以通过 requestFileHandle() 获取其句柄， 无论该条目的 origins 值如何， 也无论其 hash 是否位于 PHL 上。 这与 Cache API 的模型一致，即一个源始终能够访问它自己存储的内容。

4. 跨源存储文件系统

跨源存储文件系统是一个文件系统根，与任何 源的存储桶文件系统或本地文件系统访问根不同，其 条目与 COS 注册表中的 COS 条目一一对应。

跨源存储文件系统不使用 [FS] 普通的逐调用 权限检查 模型：从中获得的每个 FileSystemFileHandle 在返回给脚本之前，都已经由 § 3.2 读取文件或§ 3.3 创建和 写入文件完全授权，因此在这样的句柄上调用 getFile() 或 createWritable() 永远不会 触发额外的权限提示。

因此，这类句柄上的 queryPermission() 和 requestPermission() 必须永远不会 报告 "prompt"，因为不会出现提示。对于一个 并非通过创建请求获得的句柄，其写入模式必须报告 "denied"， 否则报告 "granted"。

注： 写入是句柄真正可能 缺少的唯一能力。只有创建请求才会产生 可以写入的句柄，因此对其他任何句柄的写入模式报告 "granted" 会声称它具有 createWritable() 实际会拒绝的能力。读取保持 "granted"，因为持有可读句柄的调用者可以通过它读取内容。请求权限也无法 改变 任一结果，因为没有提示可显示，也没有状态可用于记录授权。

在用于寻址一个 COS 条目且其可读取为 false 的 FileSystemFileHandle 上调用 getFile() 必须以 "NotAllowedError" DOMException 拒绝。 这涵盖两种不同情况：

  • 来自创建请求的句柄，其条目仍为 "pending"；原因与针对相同哈希的并发 requestFileHandle() 调用会拒绝相同（参见 § 3.2 读取文件）：不能允许调用者把 尚未验证的占位符当作文件真实内容来观察。

  • 来自创建请求的句柄，而该条目已经由某个其他源写入。该 条目的state 为 "written"，但此调用者尚未提供这些字节，也尚未 通过可用性门控，因此它不能获知关于 该 条目的任何信息，甚至不能获知它是否存在。

一旦句柄的可读取为 true，在其上调用 getFile() 将返回一个 File， 其内容是被寻址条目的bytes；这 正是 [FS] 已经为一个文件 条目定义的行为，当其 二进制数据就是这些字节时。

用于寻址一个 COS 条目的 FileSystemFileHandle 具有一个文件系统定位器，其 路径 是一个列表， 其中包含单个字符串，即条目的 COS 哈希的 value；而其根是 跨源存储文件系统。

注： [FS] 将 name 定义为句柄 定位器路径的最后一个组成部分，因此这也确定了 name： 它就是 哈希。条目本身没有名称，而哈希是它唯一的身份，因此 报告它能够保留空字符串会丢失的信息。

条目没有名称，也没有包含它的目录，因此 [FS] 的大多数结构性接口 都没有可作用的对象。身份是例外，也是内容寻址条目始终可以回答的唯一问题： COS 注册表对于每个 COS 哈希 最多保存一个 COS 条目，因此两个 句柄恰好在其哈希相等时寻址同一个条目。

在用于寻址 COS 条目的 FileSystemFileHandle 上调用 isSameEntry()， 若参数同样寻址一个 COS 条目， 并且由同一个 源获得，则当两个句柄的 COS 哈希项相等时必须返回 true，否则返回 false。

注： 拒绝执行此操作会丢弃用户 代理已经持有的信息。

如果 isSameEntry() 的参数不是调用源获得的， 或者该参数寻址的不是跨源 存储文件系统中的文件系统，则必须拒绝。

注： 在这种情况下返回 false 会断言 两个句柄寻址的是不同条目， 这会对调用源无权检查的句柄作出判断。拒绝仅表示 无法进行比较。

在用于寻址 COS 条目的 FileSystemFileHandle 上调用 move() 和 remove() 必须以 "NotAllowedError" DOMException 拒绝，并且必须保持条目不变。

注： 条目由其存储 源中的所有源共享，因此允许 删除会让一个站点破坏其他站点所依赖的数据；删除应由 逐出以及用户自己的存储控制负责。重命名或重新设置父级也没有任何 可作用对象，因为条目由其 COS 哈希命名，并且没有包含它的目录。

注： 在编写本文时，这两个方法都没有由 [FS] 或文件系统 访问 API 定义 （WICG/file-system-access#214）， 因此错误名称沿用 removeEntry()， 即 [FS] 为删除条目 定义的操作：当未授予 readwrite 访问权限时，它以访问结果的错误名称拒绝。 在这里拒绝是准确的行为：这些操作有意义，但不被允许。

createSyncAccessHandle() 在这里不需要额外规则：当句柄不位于存储桶文件系统中时，其步骤已经会以 "InvalidStateError" DOMException 拒绝，而跨源存储文件系统是一个文件系统根，不同于任何源自己的文件系统，因此 [FS] 已经确定了 拒绝行为及其错误名称。

注： 即使独立来看，这也是本规范 所希望得到的结果。一个 FileSystemSyncAccessHandle 会向调用者提供可写文件描述符，这会允许它 修改条目的bytes， 从而使其不再匹配所依据的 COS 哈希， 而该条目可披露给的所有其他源读取的也是同一组字节。

4.1. 传输句柄

FileSystemFileHandle 是一个可序列化对象 [FS]，因此用于寻址 COS 条目的句柄可以被传递给另一个环境设置对象，例如通过 postMessage(message, options)。 这是获得这种句柄的第二种方式，另一种是 requestFileHandle()， 因此这里同样对其进行约束。

对于用于寻址 COS 条目的 FileSystemFileHandle， 给定 value 和 serialized，其序列化步骤还额外执行：

  1. 将 serialized.[[COSOrigin]] 设置为 value 的COS 源。

  2. 将 serialized.[[COSMayRead]] 设置为 value 的可读取。

给定 serialized、 value 和 realm，其反序列化步骤还额外执行：

  1. 如果 serialized.[[COSOrigin]] 与 realm 的 环境设置对象的源不同源，则抛出 "DataCloneError" DOMException。

  2. 将 value 的COS 源设置为 serialized.[[COSOrigin]]。

  3. 将 value 的可读取设置为 serialized.[[COSMayRead]]。

注： 如果没有同 源检查，传输会一次性破坏本 规范中的所有披露控制。一个其可读取为 true 的句柄 已经 针对请求它的源通过了应用可用性门控；将它发送给另一个 源，会在从未针对该源评估origins、 PHL 成员资格或 GREASE’ing的情况下，直接把条目的字节交给该源。这 与文件系统标准对句柄的现有处理方式一致，即它们同样只对 同源接收方有用。

注： 可读取会随 句柄一起传输，因此尚未通过写入的创建请求句柄在传输后仍不可读， 而读取请求句柄保持可读，无需重新门控。在到达时重新门控会让 调用者通过重复传输同一个 句柄来反复探测可用性。

5. 存储管理

5.1. 存储限制

用户代理必须限制一个源通过成功写入向 COS 注册表贡献的总字节数， 以防止单个源 通过填满缓存来试图逐出其他源的条目。具体限制 由实现定义。如果某个源的写入会超过其 限额，用户代理必须 以 "QuotaExceededError" DOMException 拒绝该写入， 并应当在 控制台记录警告。

注： 因为条目是内容寻址的，一个源重复 在相同哈希下写入相同的 字节，不会比第一次成功写入消耗更多配额；参见 § 2.2 COS 条目。

用户代理还具有一个由实现定义的最大源列表长度， 即一个正整数，用于限制单个 origins 列表中最多可以包含多少个源。 该限制既在首次提供列表时执行（参见验证 COS 请求）， 也在之后将列表合并进现有条目时执行（参见 升级资源可见性），因此无论是单次调用还是 随时间累积的多次调用，都不能让条目的 origins无限 增长。除了限制内存使用之外，这也能防止源的列表被用作 未声明的 "*" 替代形式；参见 § 8.2 跨站探测。

在上述两个位置中，超出此限制的处理方式不同，因为这两个调用 发生在一个操作中截然不同的阶段：

  • 在验证 COS 请求中，该限制在任何 文件被获取、哈希或 写入之前进行检查。超过限制的调用者会立即得到 "TypeError"， 并且不会发生其他任何事情； 其处理方式与其他任何格式错误的 origins 值相同。

  • 在升级资源可见性中，该限制只可能由于 多个独立写入调用中请求的源的累积效果而达到， 这些调用可能来自长期存在的互不相关的源，并且只有在此次调用的字节已经被哈希、 验证并持久存储之后才会检查该限制。在那个阶段拒绝写入会因为一个无关的记账限制 丢弃一个成功、已经验证、而且可能非常大的写入， 并且甚至无法归因于某个调用者的单一错误。因此该写入仍然 成功，只有超出容量的源会从 origins 中被丢弃，并 输出控制台警告。这与现有对 从宽松到更受限请求的处理一致：一个源请求 即使不能完全满足，也会被静默限制，而携带它的写入仍然 成功。与本规范其他地方的 § 8.3 可用性门控一致， 调用者事后无法可靠确认其请求的源是否 实际被加入：之后以该源调用 requestFileHandle() 仍然可能失败，即便该源已经被加入 （例如因为条目被逐出，或用户代理限制了请求），因此其结果 无论如何都不能被视作确认。

5.2. 逐出

本节为非规范性内容。

在存储压力下，用户代理可以从 COS 注册表中逐出条目， 例如可以根据最近访问每个条目的存储源， 使用最近最少使用策略。用户代理应当提供设置 UI，让 用户可以检查存储了哪些文件、哪些源访问过每个文件，并手动 删除条目或清除所有跨源存储数据。

当用户清除某个源的站点数据时，用户代理应当从该源所出现的每个 存储 源集合中移除该源。如果移除后，某个 COS 条目的 存储 源为空，用户代理可以考虑删除该条目。

5.3. 手动添加的条目

本节为非规范性内容。

上述设置 UI 可以允许用户直接把磁盘上已经拥有的文件添加到 跨源存储中（例如用户独立于任何网站下载的 AI 模型）， 而无需任何脚本调用 requestFileHandle()。 这种条目 没有可用于归因写入的请求源，这会引出两个命令式 API 本身无法回答的问题：

  • 就§ 3.5.1 原始存储者访问而言， 谁是原始存储者？没有人：该条目的存储源最初为空。 因此，没有任何源能豁免于普通的可用性门控和origins检查， 所有请求源仍然受到这些检查。这是正确结果，因为没有任何源 实际写入了这些字节。

  • 这种条目是否应该像普通省略 origins 的写入那样，仅限同站？不应该："同站"只有 相对于请求源才有意义，而手动添加没有请求源，因此没有站点可供 "同站" 指代。用户代理应当使这种条目全局 可披露， 同时保持其明确的 origins 列表为空，因为手动 预置文件只有在其他尚未访问过的源能够实际发现它时，才达到目的 （让这些站点复用用户已经在磁盘上拥有的文件）。用户代理的设置 UI 还可以允许用户选择更窄的范围。

以这种方式添加后，一个 state 为 "written" 的条目在其他方面与 网站通过 requestFileHandle() 写入的条目没有区别： 同样的可用性门控和可见性 升级规则适用于它，就像适用于具有相同授权的任何其他条目一样。 其中也包括当条目最终 全局可披露时执行的位于 PHL 上检查；这也是手动添加的默认情况。

5.4. 来源元数据

本节为非规范性内容。

COS 条目刻意不记录 其字节来自哪里。其身份只由 hash决定：相同字节 就是同一个条目，无论有多少源存储过 它们，也无论它们是从多少 URL 获取的（参见 § 2.2 COS 条目）。URL 是某个 写入者的一次获取操作的属性，因此对于由 多个源写入的条目，不存在不带任意性的方式去挑选其中一个 URL； 它也不像字节那样可验证（参见 § 8.1 资源完整性）； 而且相较于源这样粗粒度的值，URL 会携带更多关于用户浏览的信息，因为路径或查询字符串可能指向特定文档、 账户或会话。将其记录在条目上会因此绕过 origins和§ 8.3 可用性 门控旨在施加的披露限制，形成一种高熵信号。

尽管如此，希望获得这些信息的动机是真实存在的：查看 § 5.2 逐出中所述设置 UI 内数 GB 文件的用户，以及调试 requestFileHandle() 调用为何未命中的开发者，都希望知道文件 来自哪里。用户代理可以通过在条目旁维护一份实现私有的来源记录来满足这一需求 （例如其每个存储源获取这些 字节时所使用的 URL 及时间），前提是把该记录视为保存在 条目之外的用户代理状态：

  • 它绝不暴露给脚本。本规范中的任何内容都不会披露它，之后增加的内容 也不应披露：无论是 requestFileHandle() 还是它返回的 FileSystemFileHandle 都不应透露这种记录是否存在，更不用说其 内容了。尤其是，请求源不得观察不是由其自身 产生的记录。

  • 它只能通过受信任的非 Web 界面呈现：用户代理自己的设置和存储 检查 UI、其开发者工具，以及（如果用户代理具有扩展平台） 受显式用户授予权限保护的扩展 API，其权限等级应与其他 暴露浏览历史的 API 相同。有关正在考虑的扩展接口，请参见本 仓库中的 浏览器扩展集成点说明文档。

  • 它未经验证，并且应以此方式呈现。记录中的 URL 是写入 字节的源所作出的声明。只有 hash 能保证内容（参见 § 8.1 资源完整性）。两个源可能为同一条目记录不同 URL， 并且其中任意一个 都可能不准确或故意误导。

  • 它与条目以及归属于它的源具有相同的生命周期。当 条目被逐出或删除时，该记录会被丢弃；当 某个源从 存储源中被移除时，归属于该源的部分也会被丢弃， 包括用户清除该 源的站点数据时（参见 § 5.2 逐出）。

由于这种记录对内容不可见，用户代理是否保存它、保存多少， 完全由实现决定。本规范中的任何内容都不依赖它，而且站点无法检测到它 是否存在。

6. 权限策略集成

本规范定义一个策略控制特性 [permissions-policy]，由字符串 "cross-origin-storage" 标识。其默认允许列表 为 self。

[permissions-policy] 在 Document 上定义了允许使用， 但 CrossOriginStorageManager 还暴露在 WorkerGlobalScope 上，而后者没有自己的 Document。 因此该检查是针对调用全局对象表述的：worker 全局对象会传递解析到 拥有它的 Document， 并且所有这些 Document 都必须允许该特性。

要检查跨源存储权限，给定一个全局对象 global，返回一个 布尔值：

  1. 如果 global 是一个 Window 对象，则：

    1. 令 document 为 global 的关联 Document。

    2. 如果 document 为 null，返回 false。

    3. 如果 document 不允许使用 "cross-origin-storage" 策略控制特性， 返回 false。

    4. 返回 true。

  2. 如果 global 是一个 WorkerGlobalScope 对象，则：

    1. 令 owners 为 global 的所有者集合。

    2. 如果 owners 为 空，返回 false。

    3. 对于 owners 中的每个 owner：

      1. 如果 owner 是一个 Document 并且 owner 不允许使用 "cross-origin-storage" 策略控制特性， 返回 false。

      2. 如果 owner 是一个 WorkerGlobalScope 对象，并且以 owner 为参数运行 检查跨源 存储权限所得的结果为 false，则返回 false。

    4. 返回 true。

  3. 返回 false。

如果某个全局对象使此算法返回 false，则从中发出的每个 requestFileHandle() 调用都会在任何哈希验证、注册表查找或写入 发生之前，以 "NotAllowedError" DOMException 拒绝。

注： 通过所有者集合进行解析，正是防止该特性仅名义上可以 选择退出的机制。由 blob: URL 创建的 worker 在其创建页面的 源中运行，并与该页面共享完全相同的跨源存储视图（参见 § 3 CrossOriginStorageManager 接口），因此若检查只查询全局对象自身的 Document， 那么在每个 worker 中都会真空满足，而把调用移动到 new Worker(URL.createObjectURL(&hellip;)) 就可以绕过 cross-origin-storage=() 策略， 而其他任何内容都无需改变。

注： ServiceWorkerGlobalScope 的 所有者集合为空，因此此 算法在那里返回 false。这源于所有者集合本身的含义：它是一种 存活关系，在 worker 创建时填充，并用于判断该 worker 是否仍然处于活跃需要状态。service worker 刻意不与任何 Document 建立这种关系： 它的注册会被持久保存，用户代理会响应事件启动全局对象，并且它可以 在完全没有service worker 客户端的情况下运行。调用 register() 的客户端因此在注册时是可知的，但到全局对象运行时通常 已经消失，而且一个运行中的 service worker 会服务多个其策略不一定一致的 客户端。

注： 覆盖 service worker 需要一种捕获的策略， 而这项工作属于 [permissions-policy] 和 [service-workers]。本规范 倾向的形式是从 service worker 自身脚本响应上的 Permissions-Policy 标头派生其策略，就像其策略容器 已经携带该响应的 CSP 一样：这样始终处于该源的控制之下，并且在每次更新检查时 重新评估。对注册客户端的策略做快照会使选择退出 变得陈旧，因为从标头中移除该特性在注册恰好更新之前都不会生效。 在存在这种模型之前，失败时关闭权限是唯一不会被用来绕过选择退出的答案。

注： SharedWorkerGlobalScope 的 所有者集合可以包含多个具有不同策略的 Document， 并且它会在 worker 生命周期中增加或失去所有者。 要求每个所有者都允许该特性，意味着只要有一个所有者禁止它， 整个 shared worker 的跨源存储就会被禁用，而且两次 requestFileHandle() 调用之间结果也可能发生变化。另一种做法，即只要求有一个 允许的所有者，会让任何允许该特性的文档代表 禁止该特性的文档重新启用它。

7. Cross-Origin-Storage-Allow-Origin 标头

如果某个 COS 条目的 origins 列表 非空，则该条目可以向写入源无法控制的源 披露；然而，该列表由脚本（通过 origins） 或标记声明，而成功实现脚本或标记注入的攻击者 可以设置其中任一种。为了把该声明绑定到被披露字节所属源的运营方， 并以注入内容无法伪造的形式表达，本 规范定义了一个响应标头，用于限制这种声明可以指定哪些源。

Cross-Origin-Storage-Allow-Origin 响应标头携带一个 COS 范围上限： 一个由源组成的集合， 写入可以在非同站 origins 列表中指定这些源。 谁提供字节，谁就发送该标头，因此它从 被披露字节背后的响应中读取：

  • 对于 requestFileHandle() 写入，其字节可能在 脚本中生成，并没有自己的来源响应，因此使用的是用于 创建调用全局对象的 Document 的响应； 对于 worker，则使用拥有它的 Document 的响应 （参见获取 COS 范围上限）。

  • 对于宿主集成，则使用其存储字节的已获取资源的响应 （参见将已获取的资源存储到 跨源存储中）。这是资源自身服务器的响应， 它不一定与加载该资源的 Document 的服务器相同。

声明的列表 会与上限取交集（参见 应用 COS 范围上限），因此上限只可能缩小声明。

注： 该标头是提供字节的一方所作出的授权。 它所命名的源，即最终读取者，并不参与授权过程，也不发送任何内容： 列出的源只在之后像其他任何读取者一样，通过对 COS 哈希调用 requestFileHandle() 参与。它的方向与 Access-Control-Allow-Origin [FETCH] 相反， 后者由持有资源的服务器选择允许给定源读取资源。而这里， 字节提供方限制之后谁可以从跨源存储读取这些字节，并且 写入页面上的注入内容无法扩大该边界，因为它无法设置提供方的响应标头。

注： 该标头仅适用于列表形式。 同站默认值并未指定任何跨源 接收方，因此无需授权；而 "*" 形式则在读取路径上通过 可用性门控针对公共哈希列表进行控制， 每用户秘密永远无法通过这个门槛，因此它也不需要写入时上限。要求 "*" 必须携带标头还会破坏零配置的全局共享用例，而不会关闭任何公共哈希列表 尚未关闭的风险。

要解析 COS 范围上限，给定一个标头 列表 headers，返回一个由 源组成的集合：

  1. 令 value 为从 headers 中 获取、解码并拆分 "Cross-Origin-Storage-Allow-Origin" 所得的结果。

  2. 如果 value 为 null，返回一个空集合。

  3. 令 ceiling 为一个空集合。

  4. 对于 value 中的每个 token：

    1. 从 token 中去除开头和结尾的 ASCII 空白。

    2. 如果 token 为空字符串，则继续。

    3. 令 origin 为对 token 运行基本 URL 解析器所得的源。

    4. 如果 origin 为失败或是不透明源，则返回一个空集合。

      注： 这包括 token 为 "*" 的情况，因为它无法解析为源。 Cross-Origin-Storage-Allow-Origin 标头只能枚举有限集合的 具体 源；"*" 不是允许的值，因为“任意源”的上限 会让 注入内容声明任何它想要的接收方，从而彻底破坏该标头的 目的。 无界 披露只能通过 "*" origins 形式实现， 而该形式由 公共哈希列表门控，并且从不查询该 标头。格式错误或包含 "*" 的标头 不授权任何内容，与标头不存在时完全一样；它会以关闭方式失败。

    5. 将 origin 追加到 ceiling。

  5. 返回 ceiling。

注： 获取、解码并拆分会按 U+002C (,) 拆分，因此标头 值中的源使用逗号分隔，这与 Timing-Allow-Origin [RESOURCE-TIMING] 以及 列表型 HTTP 响应标头的一般 约定一致，尽管同级的 crossoriginstorage HTML 内容 属性使用空格分隔，以匹配其宿主语法。两者最终都解析成相同的 源集合。

要获取 COS 范围上限，给定一个全局对象 global，返回一个由 源组成的集合：

  1. 如果 global 是一个 Window 对象，则：

    1. 令 document 为 global 的关联 Document。

    2. 如果 document 为 null，返回一个空集合。

    3. 返回 document 的COS 范围上限。

  2. 如果 global 是一个 WorkerGlobalScope 对象，则：

    1. 令 owners 为 global 的所有者集合。

    2. 如果 owners 为 空，返回一个空集合。

    3. 令 ceiling 为 null。

    4. 对于 owners 中的每个 owner：

      1. 令 ownerCeiling 为一个空集合。

      2. 如果 owner 是一个 Document， 则将 ownerCeiling 设置为 owner 的 COS 范围上限。

      3. 否则，如果 owner 是一个 WorkerGlobalScope 对象，则将 ownerCeiling 设置为以 owner 为参数运行获取 COS 范围上限 所得的结果。

      4. 如果 ceiling 为 null，将 ceiling 设置为 ownerCeiling；否则，将 ceiling 设置为 ceiling 与 ownerCeiling 的交集。

    5. 返回 ceiling。

  3. 返回一个空集合。

要应用 COS 范围上限，给定一个由源组成的列表 requestedOrigins 和一个 由源组成的集合 ceiling，返回一个由源组成的列表或 null：

  1. 从 requestedOrigins 中移除每个 ceiling 不 包含的源。

    注： 不在COS 范围 上限中的接收方会被丢弃，而写入仍然 成功，这与升级资源可见性中超长升级丢弃超出部分的做法一致。 用户代理应当记录控制台警告，并指出 每个被丢弃的源。

  2. 如果 requestedOrigins 为 空，返回 null。

    注： 一个所有成员都被 丢弃的列表 会使该写入不再拥有任何获授权的 跨源接收方，因此回退到同站默认值。字节仍然 会被存储；只有未经授权的披露被阻止。

  3. 返回 requestedOrigins。

每个 Document 都具有一个 COS 范围上限，它是一个由 源组成的集合， 在文档创建时设置为以用于创建它的响应的 标头列表为参数运行解析 COS 范围上限 所得的结果。

注： 对 worker 的所有者集合取交集，与 检查跨源存储权限相呼应：只有当每个拥有它的 Document 以传递方式都授权某个源时，该源才位于 worker 的上限内。因为 blob: worker 与其创建页面共享完全相同的 源和跨源存储视图（参见 § 3 CrossOriginStorageManager 接口）， 如果上限只查询 worker 自身，那么每个 worker 的上限都会为空，而把列表范围写入移动到 new Worker(URL.createObjectURL(&hellip;)) 就会去掉页面已经授权的接收方； 对所有者的上限取交集可以保留该授权，同时又不允许任何单个 所有者扩大它。

从 Document 的 响应 填充其 COS 范围上限，需要 在 [HTML] 的文档 创建步骤中提供一个挂接点，就像 [permissions-policy] 和 [CSP] 在 响应处理时被填充一样。在该挂接点存在之前，本节直接描述 所需行为；未来版本预计将正式集成，并与 [FS] 中在 § 3.3 创建和写入文件里提到的挂接点一起处理。宿主集成不需要这样的 挂接点：它们会把获取到的响应传给将已获取的资源存储到跨源 存储中，而后者会从中读取 上限。

8. 隐私和安全考虑事项

除使用 RFC 2119 关键字的地方外，本节为非规范性内容；另请参见本 仓库中的安全和隐私问卷。

8.1. 资源完整性

每个 COS 条目都以 加密哈希作为键，其 字节也会依据该哈希进行验证（参见 § 3.3 创建和写入文件）。因此站点可以确信， 通过 requestFileHandle() 获得的文件与其自行获取 hash 时得到的文件 逐字节完全相同。开发者无法枚举跨源存储的内容，也无法 在事先不知道其哈希的情况下访问文件。

COS 哈希并不是秘密。它是一种 内容标识符，任何已经拥有文件的人都可以轻易计算出来， 并且对于本规范所针对的广泛分发资源，它通常本来就是公开信息， 经常会与模型或库的 版本一起发布。因此，知道哈希足以查找条目，但它本身并不会授予访问权限： 查找是否成功完全由 origins和 § 8.3 可用性门控控制。开发者不得把未公开的哈希 视为访问控制机制；对特定文件感兴趣的 攻击者不需要猜测其哈希，只需要获得文件本身 （参见 § 8.2 跨站探测）。

8.2. 跨站探测

如果一个资源只被少数站点使用，那么能够获知该资源 存在于跨源存储中的攻击者，就可以推断用户很可能访问过这些站点中的某一个。由于 requestFileHandle() 是获知是否存在的机制，因此每次调用 实际上都是一次探测。本规范中的两个独立机制会限制探测所能 获知的信息：

  • origins （参见 § 3.5 资源可见性升级）允许存储 源将 披露限制为选定的一组源，因此专有或低流行度的资源完全不必 允许全局探测。

  • § 8.3 可用性门控还会阻止 "*" 范围资源向其存储源之外的请求源披露，除非哈希位于 PHL 上， 因此以 origins: "*" 存储的资源 不会自动允许 Web 上的所有源探测。此门控仅适用于 "*" 范围 的条目；对于列表范围和同站范围条目，第一个项目的限制是唯一的 门控，因为存储源已经为它们明确限制了披露范围。

第一个项目只有在“选定的一组源”仍明显小于整个 Web 时才成立。 origins 的结构本身并不能阻止调用者 枚举非常大量的源（例如从公开的 热门站点排名中组装一个列表），而这种做法在功能上可以近似全局披露，同时绕过 只有 "*" 才要求的刻意、明确的选择加入。最大源列表 长度（参见 § 5.1 存储限制）会限制这种情况：一个足以覆盖真正的 多属性用例 （共同控制下的少数几个相关源）、但远不足以有意义地近似 “每个源”的限制，可以防止受限源形式的 origins 被用作未声明的 "*" 替代形式。

用户代理还应当对来自单一源的重复 requestFileHandle() 调用进行速率限制或其他节流，并且可以应用 设备端启发式方法（例如检测看起来是按用户生成的哈希请求模式） 来识别并阻止探测尝试，无论被探测的 哈希是否位于 PHL 上。

§ 9 与其他规范的集成中的某个宿主集成执行的查找 同样也是一次探测，即使它不会向页面暴露任何错误：站点可以观察自己的服务器是否收到 回退请求，这携带了与这里“未找到”结果相同的单个比特信息。 这种查找不会披露超出本规范门控允许范围的信息，而这些 门控同样适用于它。不过，只有当来自这些 接口的查找与 requestFileHandle() 调用一起计数时，速率限制才有效，因为可脚本化的 集成同样可以很容易地循环发出这些请求。

8.3. 可用性门控

从存储 源之外的源执行 requestFileHandle() 读取是否成功，始终取决于请求源是否 被允许读取条目，而这由 origins控制。对于 "*" 范围条目，还存在第二个、 独立的问题：用户代理是否愿意披露该条目 是否存在，这由 PHL 成员资格和GREASE’ing控制。对于这类条目， 两者都必须满足；对于列表范围或同站范围条目，只需满足第一个问题。 规范性算法参见 § 3.2 读取文件。因此，"NotFoundError" 并不能证明资源不存在：它可能意味着资源不存在、请求 源不在范围内、"*" 范围资源的哈希尚未（或永远不会）位于 PHL 上， 或者 GREASE’ing 抑制了一个真实的肯定结果。开发者不得把 "NotFoundError" 理解为比“回退到网络”更具体的任何含义。

注： 在支持第三方 Cookie 的用户代理中， "*" 授权用于跨站关联 用户访问的能力，并不会比第三方 Cookie 更强。仅靠 PHL 无法限制这一点：攻击者可以通过选择写入哪些子集，从多个分别 符合 PHL 条件的资源组合出一个跨站标识符。阻止第三方 Cookie 的用户代理仍然可以提供 "*" 授权，只要它限制跨站披露，例如通过 以顶级站点为键、页面上所有 frame 共享的少量跨站查找预算， 一个在一段时间窗口内跨重新加载持续存在的计数，以及仅在 用户手势之后共享写入的条目。README 中的 隐私考虑事项描述了这些缓解措施。

8.4. GREASE’ing

用户代理可以应用 GREASE’ing（生成随机扩展并维持 可扩展性）：偶尔假装 一个可披露条目不存在，即使 § 8.3 可用性门控 原本会 允许披露。这样会加入噪声，使站点更难区分真正不存在 和出于隐私原因产生的假阴性，这与 UA Client Hints所采用的技术类似。

GREASE’ing 只适用于仅通过全局 可披露 授权满足条件的源，也就是公共哈希列表所门控的同一情况（参见确定 COS 披露）。 用户代理不得将其应用于存储源、与它们同 站的源， 或明确 origins 列表上的源。

应用 GREASE’ing 的用户代理必须根据所涉条目的大小作出适当判断。 对于较小条目，回退到网络获取的成本很低，偶尔 出现假阴性是一种合理的隐私权衡。用户代理不得对大小使虚假重新下载 相对于所获得的隐私收益显然不成比例的条目应用 GREASE’ing （例如 GB 级的 AI 模型权重），因为在这种情况下，假阴性会迫使进行完整、 可观察且代价高昂的重新下载。

8.5. 指纹识别

攻击者通过探测跨源存储能够提取的信息，受到被探测资源流行程度的限制。 得知用户拥有一个非常流行的资源，例如常见 AI 模型 或广泛使用的 JavaScript 库，只能说明用户访问过使用它的（可能非常 多的）站点之一。得知用户拥有稀有或唯一资源则能提供更多信息。 用户代理应当应用设备端启发式方法检测那些看起来被故意设计为每用户唯一的哈希 （例如某个哈希只由一个 站点写入过，或被异常频繁地请求），并把这种模式视为探测尝试， 无论其名义上的 PHL 状态如何。

9. 与其他规范的集成

本节为非规范性内容。

这里定义的 COS 注册表 还可以通过四种宿主集成直接访问，而无需 直接经过 requestFileHandle()。 每种 集成都在各自的宿主规范中定义。本规范定义了这些集成预期构建于其上的共享 底层概念（COS 哈希、COS 条目、 可用性门控和 公共哈希 列表），以及将已获取的资源存储到跨源 存储中这一 步骤。

  • HTML：在已经具有 integrity [SRI] 的 link 和 script 元素上增加 crossoriginstorage 属性，已在 whatwg/html#12770 中向 WHATWG 提议。

  • JavaScript：一个宿主定义的 crossOriginStorage 导入属性，可 与 integrity 一起使用，构建在 导入属性 提案之上，已在 whatwg/html#12771 中向 WHATWG 提议。

  • CSS：一个 cross-origin-storage() <request-url-modifier>， 可与 integrity() 一起使用， 已在 w3c/csswg-drafts#14056 中向 CSS 工作组提议。

  • Fetch：一个 crossOriginStorage RequestInit 选项，可与 integrity [FETCH] 一起使用，已在 whatwg/fetch#1954 中向 WHATWG 提议。 这一项没有宿主定义的目标，因此从 COS 注册表提供的 Response 应如何报告其 MIME 类型、状态和其他元数据， 对该规范来说仍是一个开放问题；COS 条目只存储字节。

仅用于说明，下面展示同一个全局共享资源如何通过四种形式分别选择加入跨源存储：

<script src="popular-library.js" integrity="sha256-abc123..." crossoriginstorage="*"></script>

import data from "popular-resource.ext" with {
  integrity: "sha256-abc123...",
  crossOriginStorage: "*",
};

@font-face {
  font-family: "Popular Font";
  src: url("popular-font.woff2" integrity("sha256-abc123...") cross-origin-storage(*));
}

const response = await fetch("popular-resource.ext", {
  integrity: "sha256-abc123...",
  crossOriginStorage: "*",
});

这些代码片段仅用于说明。这些语法均不是由本规范定义的。 每种形式的权威语法，包括受限源列表如何书写， 都属于其自身宿主规范。其拼写被刻意设计为 不同：RequestInit 成员可以接受 sequence<DOMString>，与 origins 完全匹配，而属性值、 导入属性值和 CSS 修饰符参数只能携带文本。

预计所有四种形式都共享同样的处理模型：首先查询 COS 注册表以查找匹配且可披露的条目， 如果没有，则回退到网络获取；并且 将成功获取并通过完整性验证的资源存储进 COS 注册表，供其他源复用， 与 requestFileHandle() 完全一样。存储 步骤是将已获取的资源存储到跨源 存储中，每个集成都以获取到的响应运行它。因此，受限源值会受到 该资源响应上的 Cross-Origin-Storage-Allow-Origin 标头限制，而该标头由提供字节的服务器发送 （参见 § 7 Cross-Origin-Storage-Allow-Origin 标头）。关于这些 集成的讨论应当放在承载它们的宿主规范的跟踪器中， 而不是本仓库的问题跟踪器中。

公共哈希列表的检索协议、更新频率、数据格式、流行度阈值以及治理机制，作为本规范的配套产物进行了详细设计，其理念类似于公共后缀列表——即作为 [URL] Standard 的配套数据文件；参见此仓库中的 Public Hash List 说明文档。 该设计提议由 WHATWG 进行治理，参考公共后缀列表跨厂商、滚动发布的先例，并以独立验证的普遍性作为准入标准。 这是上述 k-匿名风格门槛的一个具体实例，该门槛只在哈希被纳入列表时离线应用一次，因此用户代理不会在每次查询时重复执行。 这些内容目前尚未在此提案之外建立。该列表自身的早期非规范性代码原型目前位于此仓库中的 public-hash-list/implementation/； 专用的跨厂商仓库仍然是 PHL 说明文档中描述的治理目标。 本规范仅依赖于某个哈希是否 位于 PHL 上， 因此无论该列表的检索机制、治理模型或其余设计如何演进，本规范都保持正确。 ↵
文件系统标准 [FS] 尚未为依赖规范提供一个扩展点，以便在 FileSystemWritableFileStream 的关闭步骤中挂接额外的按写入验证。 在该挂接点存在之前，本节会直接描述所需行为；未来版本预计会正式与 [FS] 集成。 ↵
