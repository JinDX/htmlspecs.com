摘要

跨源存储（COS）是一种内容寻址缓存，允许 Web 应用跨不同源存储和检索大型文件，例如 AI 模型、WebAssembly 模块和广泛使用的 JavaScript 库。文件通过其加密哈希而非 URL 进行标识，因此，某个源获取过一次的字节完全相同的资源，可以由用户代理允许的任何其他源复用，而无需再次下载。为了防止通过缓存中是否存在某个文件来推断用户访问过哪些网站，只有其哈希达到类似 k-匿名的流行度门槛时，才允许跨源披露该文件。

1. 简介

本节为非规范性内容。

存储通常按源进行分区，以保护用户的安全和隐私。这是正确的默认设置，但对于一小类体积非常大、极为流行且公开分发的资源而言并不合适——AI 模型、WebAssembly 模块、JavaScript 库、游戏引擎和大型 Web 字体——无论由哪个网站请求，它们逐字节都是同一个文件。当两个互不相关的源分别依赖同一个 8 GB 模型时，按源分区的存储会迫使用户下载并保留该模型两次，这会浪费用户的带宽、存储空间和电量，也会浪费整个网络的资源。

跨源存储（COS）是一种内容寻址缓存，它以加密哈希而非 URL 为键，使用户代理能够在选择使用它的各个源之间共享此类资源的单个已存储副本。将资源存储到 COS 中始终是存储源明确选择加入的行为，而且用户代理可以拒绝确认资源是否存在，即使对于本来允许读取它的源也可以如此；参见§ 7 隐私 和安全注意事项。

本规范的入口点是 requestFileHandle() 方法，该方法通过 crossOriginStorage 暴露： 

const hash = {
  algorithm: 'SHA-256',
  value: '8f434346648f6b96df89dda901c5176b10a6d83961dd3c1ac88b59b2dc327aa4',
};
try {
  const handle = await navigator.crossOriginStorage.requestFileHandle(hash);
  const file = await handle.getFile();
  // 对该文件执行某些操作。
} catch (err) {
  if (err.name === 'NotFoundError') {
    // 文件（可披露地）不在跨源存储中；改为从网络获取。
  }
}

本规范复用文件系统标准 [FS]中的 FileSystemFileHandle、 FileSystemWritableFileStream 以及相关基础设施，但其作用域是一个专用的、跨源共享的文件系统，而不是单个源的私有文件系统或用户可见文件系统。

本规范仅定义命令式 JavaScript API。相关提案将 相同的底层缓存集成到其他宿主规范中 — HTML 中 crossoriginstorage 属性用于 link 和 script、 JavaScript 的 crossOriginStorage 导入属性、CSS 的 cross-origin-storage() <request-url-modifier>，以及 用于 fetch() 的 crossOriginStorage RequestInit 选项 — 每一项都在其各自的宿主规范中定义；参见 § 8 与其他规范的集成。

2. 概念

2.1. 哈希

COS 哈希是一个结构，具有以下项：

算法

一个字符串， 用于命名 [WEBCRYPTO] 所识别的哈希算法，例如“SHA-256”。

值

一个字符串，它是由算法生成的摘要的小写十六进制编码。 对于“SHA-256”，其长度为 64 个字符。

algorithm 字典成员的类型是普通 DOMString，而不是 HashAlgorithmIdentifier， 即使它的值空间恰好就是 [WEBCRYPTO] 的哈希算法所接受的名称集合。HashAlgorithmIdentifier 是 (object or DOMString)——它还允许使用 object，该对象由 [WEBCRYPTO] 规范化为 Algorithm 形状的 字典，使调用方能够向需要额外参数的算法传递参数 （例如 {name: "HMAC", hash: "SHA-256"}）。哈希算法不接受这类参数； algorithm 会作为内容寻址 键的一部分被存储、比较并往返传递，而不是由单个操作一次性使用，并且本规范示例中的每一种用法都是裸字符串；在这里允许任意对象不会增加任何能力，反而会使相等性和序列化 变得不必要地复杂。因此，DOMString 是该字段更窄且更正确的类型。

如果两个 COS 哈希值的算法 值以 ASCII 不区分大小写的方式匹配，并且其值完全相等，则它们相等。

注：与大小写未受规范性约束的算法不同， 值已经被规范性地要求为小写（见上文），因此对它的比较是普通 字符串比较，而不是 ASCII 不区分大小写的比较。

内容寻址 存储是指其条目以 COS 哈希的相等性为键，而不是以 URL 或 名称为键的存储：具有相同字节且使用相同哈希算法的两个文件属于同一个条目，无论有多少个源 存储过它们，也无论它们是从多少个 URL 获取的。

2.2. COS 条目

每个用户代理都有一个 COS 注册表，它是从 COS 哈希值到 COS 条目结构的映射， 并由所有使用跨源存储的源共享。一个 COS 条目具有以下项：

哈希

一个 COS 哈希。

字节

空值，或一个 字节序列，其使用 哈希的算法计算出的摘要 等于哈希的值。在写入器完成 验证和 存储之前为空值。

状态

为“pending”或“written”。条目最初为“pending”， 并在 字节首次被设置时恰好一次变为“written”。

待处理写入器计数

一个初始值为 0 的非负整数，用于统计未完成的写入器——由完成创建请求返回的 FileSystemFileHandle 句柄，其结束写入 尚未 完成。仅在验证并存储中用于判断失败的写入是否可以安全地 清理；参见 § 3.3 创建和写入文件。

源

声明的共享范围：可以是“*”（任意源）、一个由源字符串组成的列表 （仅限这些源），或空值（仅限同站源）。由第一个写入器设置，并且 可以升级但绝不能降级。

存储源

一个由集合构成，其中包含已至少一次成功完成 写入此 条目字节的各个源。它会跨页面加载持久保存，并且会随时间 增长；除 § 5.2 驱逐中所述的情况外，绝不会缩小。位于 存储源中的源始终可以通过 requestFileHandle() 获取该条目的句柄，而不受源或 该条目的哈希是否位于公共哈希列表 （PHL）中的影响。 参见 § 3.4.1 原始存储方访问。

用户代理具有关联的 跨源存储队列，它是 启动一个新的并行队列的结果。对 COS 注册表的所有操作都必须 入队到该队列中，以便它们按照 入队 顺序执行且不会交错。

2.3. 公共哈希列表

确认某个哈希存在于跨源存储中，本身就可能泄露用户的浏览历史信息（参见§ 7.2 跨站探测）。这种风险特别针对全局作用域的条目——其源为列表或 null 的条目，其披露范围已经由存储源的明确选择加以限制，但“*”可能会将条目暴露给 Web 上的任何源。为了限制这一特定风险，作用域为“*”的资源只有在其哈希通过另一个独立门控时，才可向其存储源之外的源披露：即它必须位于 公共哈希列表 （PHL）中。该列表是一个厂商中立、由实现定义的 COS 哈希 值许可列表。只有当某个哈希达到类似 k-匿名的流行度门槛时，它才会被加入公共哈希列表——例如，以字节完全相同的形式出现在达到某个最小数量的独立源中——这样，确认它存在于共享缓存中就不会透露任何特定用户的信息。

如果一个 COS 哈希 hash 与用户代理当前公共哈希列表快照中的某个条目相等，则该哈希位于公共 哈希列表中。

公共哈希列表的检索协议、 更新频率、数据格式、流行度阈值和治理方式 作为本规范的配套产物进行了详细设计，其理念类似于 [URL] 标准的公共后缀列表是一个配套数据文件，而非 规范性文本 — 请参阅本仓库中的 公共哈希列表说明文档。该设计 提议由 WHATWG 进行治理，参考公共后缀列表跨厂商、 滚动发布的先例，并以独立验证的普遍性作为准入标准 — 这是上述 k-匿名性风格门槛的一个具体实例，该门槛仅在哈希被纳入列表时离线应用一次， 而不是用户代理针对每次查询重复执行的检查。此方案目前尚未在 本提案之外建立。列表本身的一个早期、非规范性代码原型 维护在本仓库的 public-hash-list/implementation/ 中 — 这是一个务实的 临时存放位置；一个专用的跨厂商仓库仍然是 PHL 说明文档中描述的治理目标。 本规范仅依赖于某个哈希是否 在 PHL 中，而不依赖于任何特定的 检索机制或治理模型，因此无论该设计如何 演进，本规范都保持正确。

3. CrossOriginStorageManager 接口

[Exposed=(Window,Worker), SecureContext]
interface CrossOriginStorageManager {
  Promise<FileSystemFileHandle> requestFileHandle(
      CrossOriginStorageRequestFileHandleHash hash,
      optional CrossOriginStorageRequestFileHandleOptions options = {});
};

dictionary CrossOriginStorageRequestFileHandleHash {
  required DOMString value;
  required DOMString algorithm;
};

dictionary CrossOriginStorageRequestFileHandleOptions {
  boolean create = false;
  (DOMString or sequence<DOMString>) origins;
};

interface mixin NavigatorCrossOriginStorage {
  [SameObject, SecureContext] readonly attribute CrossOriginStorageManager crossOriginStorage;
};
Navigator includes NavigatorCrossOriginStorage;
WorkerNavigator includes NavigatorCrossOriginStorage;

每个 Navigator 和 WorkerNavigator 对象都具有关联的 CrossOriginStorageManager 对象。crossOriginStorage 获取器 的步骤是返回this 的关联 CrossOriginStorageManager。

每个 CrossOriginStorageManager 对象都具有关联的源，在创建该对象时，将其设置为 this 的相关设置对象的源。

注： 从相关设置对象而不是从脚本本身的任何信息中获取源，这会对 worker 产生一个值得明确说明的后果。从 blob: URL 创建的 worker 具有创建它的上下文的源，因此它与该源完全共享同一个 跨源存储视图：这种 worker 写入的内容，其创建页面可以读回，而 页面存储的内容，worker 也可以读取。blob: URL 本身并不是一个独立的源，并且 撤销它也不会使 worker 与该视图分离。相比之下，从 data: URL 创建的 worker 具有一个不透明源。本规范目前并未定义当 调用源为不透明源时，requestFileHandle() 会执行什么操作； 不透明源规则在验证 COS 请求中约束的是 调用方所指定的源，而不是调用方自身所在的源。不透明源没有可用于作为 存储 源的键或用于同 站点比较的稳定身份，因此没有任何有意义的东西可以 授予它。

3.1. requestFileHandle() 方法

handle = await navigator . crossOriginStorage . requestFileHandle(hash)

如果由 hash 标识的文件存在于跨源存储中，并且可向调用源披露，则返回该文件的句柄。否则，将以 "NotFoundError" DOMException 拒绝。 "NotFoundError" 并不能证明该文件 实际上不存在于跨源存储中；参见§ 7.3 可用性门控。调用方可以 将其视为“改为从网络获取此文件”。

handle = await navigator . crossOriginStorage . requestFileHandle(hash, { create: true })

返回一个可用于将由 hash 标识的文件写入 跨源 存储的句柄；如果尚不存在条目，则创建一个新条目，默认情况下仅限同站点源。 无论条目是否已存在，调用方都需要通过该句柄的 createWritable() 方法写入完整的文件内容；此时，用户代理会验证写入字节的哈希是否为 hash， 否则以 "DataError" DOMException 拒绝。此要求可防止 源利用创建请求作为探测 hash 是否已存在的预言机。

handle = await navigator . crossOriginStorage . requestFileHandle(hash, { create: true, origins: "*" })

同上，此外，在写入后，使该条目可向任何其针对 hash 的请求通过§ 7.3 可用性门控的源披露。

handle = await navigator . crossOriginStorage . requestFileHandle(hash, { create: true, origins: ["https://a.example", "https://b.example"] })

同上，将披露严格限制为列出的源（此外还包括调用 源，以及已经位于存储源中的任何源）。

requestFileHandle(hash, options) 方法的 步骤如下：

  1. 令 result 为一个新的 promise。

  2. 令 realm 为此对象的相关 Realm。

  3. 令 global 为此对象的相关全局对象。

  4. 令 origin 为此对象关联的源。

  5. 如果 global 关联的 Document （如果有）不被允许使用 "cross-origin-storage" 策略控制功能，则：

    1. 在给定 global 的将全局任务排入队列到DOM 操作任务源上，以 "NotAllowedError" DOMException 拒绝 result。

    2. 返回 result。

  6. 令 validationFailure 为在给定 hash 和 options 的情况下运行验证 COS 请求的结果。

  7. 如果 validationFailure 不为 null：

    1. 在给定 global 的将全局任务排入队列到DOM 操作任务源上，以 validationFailure 拒绝 result。

    2. 返回 result。

  8. 将以下步骤排入 跨源存储队列：

    1. 如果 options["create"] 为 true：

      1. 在给定 result、hash、options、global 和 realm 的情况下，运行完成创建请求。

    2. 否则：

      1. 在给定 result、hash、origin、global 和 realm 的情况下，运行完成读取请求。

  9. 返回 result。

要在给定 CrossOriginStorageRequestFileHandleHash hash 和 CrossOriginStorageRequestFileHandleOptions options 的情况下验证 COS 请求，返回 null 或一个 TypeError：

  1. 如果 hash["algorithm"] 不是 [WEBCRYPTO] 所识别的哈希算法 名称，则返回一个新的 TypeError。

  2. 如果 hash["value"] 在 hash["algorithm"] 与 "SHA-256" 进行ASCII 大小写不敏感 匹配时，不匹配正则 表达式 /^[0-9a-f]{64}$/，则返回一个新的 TypeError。

    注： 未来的哈希算法可以定义 不同的预期摘要长度；本 规范仅对 "SHA-256" 作规范性约束，这与它在整个 示例中的 使用保持一致。

  3. 如果 options["origins"] 存在且 不为 "*"：

    1. 令 candidates 为 options["origins"]， 其中单个字符串视为仅含一个元素的列表。

    2. 如果 candidates 的大小 大于用户代理的 最大源列表长度，则返回一个 新的 TypeError。

    3. 对于每个 candidates 中的 candidate：

      1. 如果对 candidate 运行基本 URL 解析器的结果 为失败，或者解析后的 URL 的源是一个不透明源，则返回一个新的 TypeError。

  4. 返回 null。

3.2. 读取文件

要在给定一个 promise result、一个COS 哈希 hash、一个 源 origin、一个全局对象 global 和一个 Realm realm 的情况下，完成读取 请求：

  1. 令 entry 为 COS 注册表中其哈希 与 hash 相等的COS 条目（如果有），否则为 null。

  2. 如果 entry 不为 null 且 entry 的状态为 "pending"：

    1. 在给定 global 的将全局任务排入队列到DOM 操作任务源上，以 "NotAllowedError" DOMException 拒绝 result。

    2. 返回。

    注： 正在进行写入的哈希 有意不表现得像不存在的哈希，以免调用方将正在进行的写入误认为真正的缓存未命中 并开始冗余地并发下载一个非常大的文件，而唯一目的只是 将其写入。参见§ 3.3 创建和写入文件。

  3. 令 disclosableEntry 为在给定 entry 和 origin 的情况下运行应用可用性 门控的结果。

  4. 如果 disclosableEntry 为 null：

    1. 在给定 global 的将全局任务排入队列到DOM 操作任务源上，以 "NotFoundError" DOMException 拒绝 result。

    2. 返回。

  5. 令 handle 为在 realm 中创建新的 FileSystemFileHandle [FS]的结果，其 定位器指向 跨源存储文件系统内的 disclosableEntry。

  6. 将 handle 的COS 源设置为 origin。

  7. 将 handle 的可以读取设置为 true。

    注： 此句柄已经通过应用可用性门控，因此调用源 有权 获取该条目的字节。

  8. 在给定 global 的将全局任务排入队列到DOM 操作任务源上，以 handle 解决 result。

要在给定一个COS 条目 或 null entry，以及一个 源 origin 的情况下，确定 COS 披露，返回一个COS 条目或 null：

  1. 如果 entry 为 null，则返回 null。

  2. 断言：entry 的状态为 "written"。

  3. 如果 origin 位于 entry 的存储 源中，则返回 entry。

    注： 原始存储方以及任何 自身已成功写入该条目的源 始终可以将其读回。参见§ 3.4.1 原始存储方 访问。

  4. 如果 entry 的源为 "*"：

    1. 如果 entry 的哈希不在 PHL 上，则返回 null。

      注： 公共哈希列表门控 仅适用于此处，即全局范围的条目——这是 唯一一种披露原本可能触及 Web 上任何源的情况。它不适用于 下面的列表范围和同站点范围情况：存储源已经为这些情况作出了明确且 有界的披露决定，而在此基础上再要求单独的全局普遍性 会使普通的受限共享（参见§ 3.4 资源可见性升级）依赖于 与通常为专有资源的内容无关的公共策展。参见 § 7.2 跨站点探测。

    2. 返回 entry。

  5. 如果 entry 的源是一个列表：

    1. 如果 origin 的序列化是该 列表中的一个条目， 则返回 entry。

    2. 返回 null。

  6. 断言：entry 的源为 null。

  7. 如果 origin 与 entry 的存储源中的某个条目同站点，则返回 entry。

  8. 返回 null。

要在给定一个COS 条目或 null entry，以及一个 源 origin 的情况下，应用 可用性门控，返回一个COS 条目或 null：

  1. 令 disclosable 为在给定 entry 和 origin 的情况下运行确定 COS 披露的结果。

  2. 如果 disclosable 为 null，则返回 null。

  3. 如果 origin 位于 disclosable 的存储 源中，则返回 disclosable。

  4. 如果用户代理选择对此请求应用 GREASE，则返回 null。

  5. 返回 disclosable。

3.3. 创建和写入文件

由完成创建请求创建的 FileSystemFileHandle 具有一个关联的 请求的源，其值是验证并存储将在 通过句柄成功写入后，尝试将条目的源升级到的值。

每个寻址COS 条目的 FileSystemFileHandle 还具有一个关联的 COS 源，即获得该句柄的源，以及一个 关联的 可读取布尔值，它控制 getFile() 是否可以通过该特定句柄披露条目的字节。 对于由完成读取请求返回的句柄，其值为 true，因为该句柄已通过 可用性门控；对于由 完成 创建请求返回的句柄，其值为 false，直到验证并存储针对同一句柄成功完成。

注： 这被有意设计为句柄的属性 而不是条目的属性。无论条目是否已经存在以及是否已经为 "written"，创建请求 都会返回一个句柄（参见 完成 创建请求），因此如果采用每条目规则，任何源都可以调用 requestFileHandle() 并将 create: true，然后立即读取一个它 从未写入过的条目，从而在不满足源、 PHL 成员资格或GREASE要求的情况下获知其内容。本 规范中的每个披露控制都应用在读取路径上，因此按条目实施门控会使创建请求 绕过所有这些控制。要求调用方先提供正确的字节意味着，通过由创建请求获得的句柄进行的成功 读取不会披露调用方原本没有的任何内容。

要在给定一个 promise result、一个 COS 哈希 hash、一个 CrossOriginStorageRequestFileHandleOptions options、一个全局对象 global 和一个 Realm realm 的情况下，完成 创建请求：

  1. 令 requestedOrigins 为在给定 options["origins"] 的情况下运行规范化 请求的源的结果。

  2. 令 entry 为 COS 注册表中，其哈希 与 hash 相等的COS 条目（如果有），否则为 null。

  3. 如果 entry 为 null：

    1. 将 entry 设置为一个新的COS 条目，其哈希为 hash， 字节 为 null，状态为 "pending"， 源为 requestedOrigins，并且 存储源为一个空集合。

    2. 将 COS 注册表[hash] 设置为 entry。

  4. 将 entry 的待处理写入方计数增加 1。

    注： 即使调用方从未在 handle 上调用 createWritable()， 或者从未关闭由此产生的流，这也会将 handle 作为一个 尚未完成的写入方进行跟踪。这样的 废弃句柄会永久计入 entry，这与此机制存在之前，废弃的进行中写入 已经会使 entry 永久保持 "pending" 完全相同；参见 验证并 存储。

  5. 令 handle 为在 realm 中创建一个新的 FileSystemFileHandle [FS]的结果，其 定位器指向 跨源存储文件系统内的 entry。

  6. 将 handle 的COS 源设置为 global 的 相关设置对象的源。

  7. 将 handle 的请求的源设置为 requestedOrigins。

  8. 将 handle 的可读取设置为 false。

    注： 无论 entry 是否已经存在，也无论它是否 已经为 "written"，都会返回 handle。调用方仍需要通过 handle 提供完整的文件字节，这样就不能利用写入来检测先前是否存在（参见 § 7.2 跨站点探测），并且可以在兑现对更加宽松的 源 值的请求之前对其进行验证；参见 § 3.4 资源可见性升级。

  9. 在给定 global 的将全局任务排入队列到DOM 操作任务源上，以 handle 解决 result。

要在给定一个 (DOMString or sequence<DOMString>) 或 undefined origins 的情况下，规范化 请求的源，返回 "*"、一个由源组成的列表或 null：

  1. 如果 origins 不存在，则返回 null。

  2. 如果 origins 为 "*"，则返回 "*"。

  3. 令 list 为 « »。

  4. 对于每个 origins 中的 candidate（单个 字符串被视为仅含 一个元素的列表）：

    1. 令 candidateOrigin 为在 candidate 上运行基本 URL 解析器 得到的源。

      注： 验证 COS 请求已经确认每个 candidate 都解析为 非不透明源。

    2. 如果 list 不包含 candidateOrigin，则将 candidateOrigin 追加 到 list。

  5. 返回 list。

注： 在此处进行去重，而不是只在之后将其 合并 到现有条目时进行去重，可以使源从条目 首次创建的那一刻起就没有重复项，因此它之后的每个克隆也都不会包含重复项。

当通过在其定位器 指向COS 条目的句柄上调用 createWritable() 所获得的 FileSystemWritableFileStream 被关闭时 [FS]，用户代理必须在 该关闭操作的 promise 被兑现之前运行下面的验证并存储 步骤。

注： 无论关闭是如何 触发的，这都适用——显式调用 close()， 或调用 pipeTo() 并到达其 源的末尾，后者默认情况下也会关闭其目标。[STREAMS] 在 流变为关闭状态时并不区分这两种情况，本算法也不区分。

在给定由已关闭 流的句柄所寻址的COS 条目 entry、完整写入的字节序列 bytes，以及关闭操作的 相关设置对象的源 origin 的情况下，验证并存储 步骤如下：

  1. 令 computedValue 为 bytes 的小写十六进制摘要，该摘要按照 [WEBCRYPTO]，使用 entry 的算法所指定的算法计算。

  2. 如果 computedValue 与 entry 的值不完全相等：

    1. 以 "DataError" DOMException 拒绝关闭操作的 promise。

    2. 将以下步骤排入 跨源存储队列：

      1. 将 entry 的待处理写入方计数减少 1。

      2. 如果 entry 的状态为 "pending" 且 entry 的 待处理写入方计数为 0， 则从 COS 注册表中移除 entry 的 哈希。

        注： 正是这一步使 失败的写入可以自行清理，而不是留下一个 永久无法访问的 "pending" 条目：当不再有其他 写入方尚未完成时，之后针对相同哈希调用 requestFileHandle() 将完全看不到该条目，并得到普通的 "NotFoundError"， 而不是无限期的 "NotAllowedError"。 该计数可防止 删除另一个针对相同哈希并发进行中的写入方可能仍会成功写入的条目（例如， 两个标签页都发现该哈希不存在，并分别独立开始 写入）：如果该写入方仍未完成， 或者已经成功，那么要么计数尚未达到 0，要么 entry 的 状态不再是 "pending"， 因而此步骤不执行任何操作。无论后来有多少 写入方请求它并失败，已经为 "written" 的条目都绝不可能以这种方式被移除： 只有从未有过一次成功 写入的条目 才符合条件。

    3. 中止这些步骤。

  3. 将以下步骤排入 跨源存储队列：

    1. 将 entry 的字节设置为 bytes。

    2. 将 entry 的状态设置为 "written"。

    3. 如果 origin 尚不存在，则将其追加到 entry 的存储源中。

    4. 将 entry 的待处理写入方计数减少 1。

    5. 在给定 entry 和句柄的 请求的源的情况下，运行升级资源可见性。

    6. 将句柄的可读取设置为 true。

      注： 只有此句柄会变得 可读取。从同一条目的 另一个尚未通过其进行写入的不同创建请求获得的句柄，仍然不可读取。

createWritable() 在寻址某个 COS 条目的 FileSystemFileHandle 上调用时，必须生成一个 FileSystemWritableFileStream， 其内容初始为空， 无论 keepExistingData 的值为何，也无论 所寻址条目的状态为何。

注： [FS] 在其他情况下将 keepExistingData 定义为使用现有文件的内容 初始化流。在这里遵循该行为会使调用方成为其从未持有过的字节的存储源。创建请求无论条目 是否已存在都会返回句柄，因此调用方可以为由另一源存储的某个哈希打开一个可写流，随后在 未写入任何内容的情况下将其关闭，并让继承下来的字节经哈希后得到所请求的值。这会 在从未检查源、公共哈希列表以及 GREASE 操作的情况下授予其读取访问权限——这是一个由两个各自都被允许的操作组合而成的可用性 门控绕过。 这与要求 验证并存储在 每个创建请求中都提供完整内容的理由相同。

注： 因此，一个在未进行任何写入的情况下关闭的可写流 包含空字节序列，而对于调用方想要的任何条目，该序列都不会 哈希为所请求的值，因此验证并存储会像处理任何其他不匹配一样，使用 "DataError" DOMException 拒绝。如果实现 反而针对这种情况报告存储或 I/O 故障，就会将验证结果隐藏在一个 无关错误之后。

文件系统标准 [FS] 尚未定义一个 扩展点，以供依赖它的 规范将额外的逐次写入验证挂接到 FileSystemWritableFileStream 的 关闭步骤中。在这种挂钩存在之前，本节直接描述所要求的行为；预计 未来的修订将正式与 [FS] 集成。

3.4. 资源可见性升级

COS 条目的可见性可以 升级，但绝不能降级。

给定一个 COS 条目 entry，以及 "*"、一个由 源组成的列表，或者 null requestedOrigins，要升级 资源可见性：

  1. 如果 requestedOrigins 为 null，则返回。

    注： 省略 origins 绝不会缩小 现有条目的可用范围；它只请求同站点可用性，而每个条目都已经至少具有同等程度的 可用性。

  2. 如果 entry 的源为 "*"，则返回。

    注： 已经全局可用的条目 不能被后来的写入者限制。当此 注释适用且 requestedOrigins 不是 "*" 时，用户代理应当 记录一条控制台 警告，告知开发者所请求的限制未被应用。

  3. 如果 requestedOrigins 为 "*"：

    1. 将 entry 的源设置为 "*"。

    2. 返回。

  4. 如果 entry 的源为 null：

    1. 将 entry 的源设置为 requestedOrigins。

    2. 返回。

  5. 令 merged 为 entry 的源的副本。

  6. 对于 requestedOrigins 中的每个 candidateOrigin：

    1. 如果 merged 包含 candidateOrigin，则继续。

    2. 如果 merged 的大小 等于用户代理的最大源列表长度，则 中断。

      注： 任何剩余的 candidateOrigin 值都会从此次升级中被静默丢弃，而不是 导致升级失败——写入本身已经成功——但用户代理应当 记录一条控制台警告，说明该条目的源列表已达到容量上限。

    3. 将 candidateOrigin 追加到 merged。

  7. 将 entry 的源设置为 merged。

注： 一个新站点——而不仅仅是最初的存储者——可以 扩大条目的源范围，只要 它还提供哈希结果与该条目的哈希相符的字节。这是有意为之： 任何已经持有某个哈希所对应正确字节的站点，从构造上来说，对于该哈希所表示内容的权威性 都与最初的存储者相同。

3.4.1. 原始存储方访问

一个已成功完成写入COS 条目的源——也 就是该条目的存储源中的任何源——此后始终可以通过 requestFileHandle() 获取该条目的句柄， 而不受该条目的 源值影响，也 不受其哈希是否位于 PHL 上的影响。 这与 Cache API 的模型相呼应，在该模型中，源始终可以访问其所存储的内容。

4. 跨源存储文件系统

跨源存储文件系统是一个文件系统根，与任何 源的存储桶文件系统或本地文件系统访问根不同，其 条目与COS 注册表的COS 条目项一一对应。

跨源存储文件系统不使用[FS]通常的逐调用 权限检查 模型：从中获得的每个 FileSystemFileHandle 在返回给脚本之前都已经由 § 3.2 读取文件或§ 3.3 创建和 写入文件完全授权，因此在这种句柄上调用 getFile() 或 createWritable() 绝不会触发额外的权限提示。

因此，在这种句柄上调用 queryPermission() 和 requestPermission() 绝不能 报告 "prompt"，因为不可能出现提示。对于并非通过创建请求获得的句柄， 它们必须在写入模式下报告 "denied"，而在 其他情况下报告 "granted"。

注： 写入是句柄真正可能 缺少的唯一能力。只有创建请求才会产生 可通过其进行写入的句柄，因此在任何其他句柄的写入模式下报告 "granted" 会声称具有一种 createWritable() 将拒绝的能力。读取保持 "granted"，因为持有可读句柄的调用方可以通过它进行读取。请求不能 改变 任何一个答案，因为没有可显示的提示，也没有可记录授权的状态。

在寻址某个 COS 条目且其可读取为 false 的 FileSystemFileHandle 上调用 getFile() 时，必须以 "NotAllowedError" DOMException 拒绝。 这涵盖两种不同的情况：

  • 来自创建请求的句柄，其条目仍为 "pending"，原因与针对同一哈希并发调用 requestFileHandle() 会被拒绝相同（参见 § 3.2 读取文件）：调用方不得将一个 尚未验证的占位项当作 文件的真实内容来观察。

  • 来自为某个已被某个其他源写入的条目发起的创建请求的句柄。该 条目的状态为 "written"，但此调用方尚未提供这些字节，也 未通过可用性门控，因此它不得获知有关 该 条目的任何信息——包括它是否存在。

一旦句柄的可读取为 true，在其上调用 getFile() 就会返回一个 File， 其内容为所寻址条目的字节；这 正是 [FS] 已经为一个文件 条目定义的行为，其 二进制数据就是这些字节。

寻址某个COS 条目的 FileSystemFileHandle 具有一个文件系统定位器，其 路径 是一个列表， 其中包含单个字符串，即该条目的 COS 哈希的值，并且其根是 跨源存储文件系统。

注： [FS] 将 name 定义为句柄的 定位器路径的最后一个路径组成部分，因此这里确定了 name 而不是留待选择：它 就是哈希。条目本身没有名称，而哈希是它唯一的标识，因此 报告它可以携带空字符串会丢弃的信息。

条目没有名称，也没有包含它的目录，因此 [FS] 的大部分结构性接口都 没有可操作的对象。标识是例外，也是内容寻址条目 始终可以回答的一个问题：COS 注册表对于每个COS 哈希至多保存一个COS 条目，因此当且仅当两个 句柄的哈希相等时，它们才寻址同一条目。

在寻址某个 COS 条目的 FileSystemFileHandle 上调用 isSameEntry()， 并传入一个同样 寻址COS 条目且由同一 源获得的参数时，如果两个句柄的COS 哈希项相等，则必须返回 true，否则 返回 false。

注： 拒绝这样做会丢弃用户 代理已经持有的信息。

调用 isSameEntry() 时，如果传入的参数不是由调用方源获得的， 或者该参数寻址的是跨源 存储文件系统之外的文件系统，则必须拒绝。

注： 在这种情况下返回 false 会断言 两个句柄寻址不同的条目， 这是对调用源无权检查的句柄作出的断言。拒绝仅仅表示 无法进行比较。

在寻址COS 条目的 FileSystemFileHandle 上调用 move() 和 remove() 时，必须以 "NotAllowedError" DOMException 拒绝，并且必须保持该条目不变。

注： 一个条目由其存储 源中的每个源共享，因此允许 删除会使一个站点能够破坏其他站点依赖的数据；删除属于 驱逐以及用户自己的存储控制范畴。重命名或重新设置父级没有 可操作的对象，因为条目由其COS 哈希命名，并且没有包含它的目录。

注： 在撰写本文时，这两个方法均未由[FS]或文件系统 访问 API 定义 （WICG/file-system-access#214）， 因此错误名称沿用 removeEntry()， 即 [FS] 确实 为删除条目定义的操作：当未授予读写访问权限时，它会以访问结果的错误名称拒绝。 这里准确的理解是被拒绝而不是不存在——这些操作是 有意义的，只是被禁止。

createSyncAccessHandle() 在这里不需要任何规则：只要句柄不位于存储桶文件系统中，其步骤就会以 "InvalidStateError" DOMException 拒绝， 而跨源存储文件系统是一个与任何源的文件系统根均不同的文件系统根， 因此 [FS] 已经确定了 拒绝行为及其错误名称。

注： 即使独立考虑，这也是本规范 所期望的结果。一个 FileSystemSyncAccessHandle 会向调用方提供一个可写文件描述符，这会使其能够 在这些字节所对应存储的COS 哈希不变的情况下修改条目的字节， 而该条目可向其公开的所有其他源读取的也是这些相同的字节。

4.1. 传输句柄

FileSystemFileHandle 是一个可序列化对象 [FS]，因此寻址 COS 条目的句柄可以传递给另一个环境设置对象，例如使用 postMessage(message, options)。 除了 requestFileHandle() 之外，这是获得这种句柄的第二种方式， 因此这里也对其加以约束。

对于寻址COS 条目的 FileSystemFileHandle， 给定 value 和 serialized，其序列化步骤还包括：

  1. 将 serialized.[[COSOrigin]] 设置为 value 的COS 源。

  2. 将 serialized.[[COSMayRead]] 设置为 value 的可读取。

给定 serialized、 value 和 realm，反序列化步骤还包括：

  1. 如果 serialized.[[COSOrigin]] 与 realm 的 环境设置对象的源不是同源，则抛出 "DataCloneError" DOMException。

  2. 将 value 的COS 源设置为 serialized.[[COSOrigin]]。

  3. 将 value 的可读取设置为 serialized.[[COSMayRead]]。

注： 如果没有同 源检查，传递句柄将一次性绕过 本规范中的所有公开控制。一个可读取为 true 的句柄已经 针对请求它的源通过了应用可用性门控；将其发送到另一个 源会把该条目的字节交给该源，而从未针对它评估源、 PHL 成员资格或GREASE 操作。这 与文件系统标准现有的句柄处理方式一致，其中句柄同样只对 同源接收方有用。

注： 可读取随 句柄一起传递，而不是重新计算， 因此尚未通过其写入的创建请求句柄在传递后仍不可读， 而读取请求句柄仍保持可读，无需再次进行门控。到达后重新进行门控反而会 更糟，而不是更好：这会允许调用方通过反复传递同一个 句柄来探测可用性。

5. 存储管理

5.1. 存储限制

用户代理必须对某个源可通过成功写入向 COS 注册表贡献的总字节数施加限制，以 防止单个源 通过填满缓存来试图驱逐其他源的条目。具体限制由 实现定义。如果某个源的写入将超过其 限制，用户代理必须 拒绝该 写入，并使用 "QuotaExceededError" DOMException， 并且应当向 控制台记录警告。

注： 由于条目是内容可寻址的，某个源 在同一哈希下反复写入相同 字节时，除了第一次成功写入外不会消耗额外配额；参见 § 2.2 COS 条目。

用户代理还具有一个由实现定义的最大源列表长度，它是一个 正整数，用于限制单个源列表中最多可 包含多少个源。该限制既在首次提供列表时执行（参见验证 COS 请求）， 也在之后将其合并到现有条目时执行（参见 升级资源可见性），从而使单次调用以及 多次调用随时间累积产生的效果都无法无限制地扩展条目的源。除了限制内存使用之外，这还防止源列表被用作 "*" 的 未声明替代形式；参见§ 7.2 跨站点探测。

在这两个位置中，超过该限制的处理方式不同，因为这两个调用 发生在操作中完全不同的阶段：

  • 在验证 COS 请求中，会在任何 文件被获取、哈希或 写入之前检查该限制。超过该限制的调用方会立即得到 "TypeError"， 且不会发生任何其他操作——这与任何其他格式错误的 origins 值的处理方式相同。

  • 在升级资源可见性中，该限制只能通过 不同、相互独立的写入调用所请求的源的累积效果而达到，这些调用可能来自互不相关的源，并跨越 很长一段时间，而且只有在此次调用的字节已经完成哈希、 验证并持久存储之后才会检查该限制。在这个阶段拒绝写入，会由于一个无关的记录管理限制而丢弃一次成功的、 已经验证的——并且可能非常大的——写入， 而且甚至无法将其归因于某个调用方的单一错误。因此该写入仍然 成功，只有超出容量的源会从源中被丢弃，同时记录一条 控制台警告。这与现有对 从更宽松到更受限制请求的处理方式相呼应：一个源请求 如果无法被完全满足，则会被静默限制，而不会转化为承载该请求的写入 失败。与本规范其他位置的§ 7.3 可用性门控 保持一致，调用方 无法可靠地事后确认其请求的源是否 实际被添加：之后以该 源调用 requestFileHandle() 即使该源已被添加也仍可能失败——例如由于 GREASE 操作——因此其结果也不得被解读为对任一情况的确认。

5.2. 逐出

本节为非规范性内容。

在存储压力下，用户代理可以从 COS 注册表中驱逐条目， 例如，对最近访问过每个条目的存储源采用最近最少使用策略。用户代理应当提供设置 UI，使 用户能够检查存储了哪些文件、哪些源访问过每个文件，并手动 删除条目或清除所有跨源存储数据。

当用户清除某个源的站点数据时，用户代理应当从该源所在的每个 存储 源集合中移除该源。如果移除后，某个COS 条目的 存储 源为空，用户代理可以考虑删除该条目。

5.3. 手动添加的条目

本节为非规范性内容。

上述设置 UI 可以允许用户将磁盘上已有的文件直接添加到 跨源存储中——例如，他们独立于任何网站下载的 AI 模型——而无需任何 脚本调用 requestFileHandle()。 这样的条目 没有可将写入归因于其的请求源，这引出了两个命令式 API 本身无法回答的问题：

  • 就 § 3.4.1 原始存储者访问而言，谁是原始存储者？没有任何人：该条目的存储源最初为空， 而不是包含执行写入的源。因此，没有任何源可以豁免于 每个请求源在其他情况下都要遵循的普通可用性门控和源检查——这是正确的结果，因为实际上没有任何源 写入这些字节。

  • 源 是否应像省略 origins 的普通写入那样， 默认为仅同站点？不应该："同站点" 只有 相对于请求源才有意义，而手动添加没有请求源，因此不存在可供 "同站点" 指代的站点。用户代理应当改为默认将这种条目的源设为 "*"， 因为手动预置文件只有在其他源确实能够发现它时，才能实现其目的——让用户尚未 访问的站点复用用户磁盘上已有的文件。用户代理的设置 UI 还可以允许用户选择更窄的范围。

以这种方式添加后，状态为 "written" 的条目在其他方面与 网站通过 requestFileHandle() 写入的条目没有区别： 相同的 可用性门控和可见性 升级规则适用于它，就像适用于具有相同 源值的任何其他条目一样—— 包括位于 PHL 上检查，如果 该条目最终具有 "*" 范围， 这是手动添加的默认情况，但并非唯一可能的结果。

5.4. 来源元数据

本节为非规范性内容。

COS 条目有意不记录任何有关 其字节来源的信息。其身份仅由 哈希决定：相同的字节 就是相同的条目，无论有多少个源存储了 它们，也无论它们是从多少个 URL 获取的（参见§ 2.2 COS 条目）。URL 是某个 写入方获取操作的属性，而不是条目的属性，因此对于一个由 多个源写入的条目，并不存在非任意地选取其中一个 URL 的方式；它不像字节那样可验证（参见§ 7.1 资源完整性）； 而且与存储 源中粗粒度的源值相比，它携带的有关用户浏览行为的信息要多得多，因为路径或查询字符串可以指明特定文档、 帐户或会话。因此，将其记录在条目上会使一个高熵信号绕过 源和§ 7.3 可用性 门控旨在施加的公开限制。

尽管如此，需要这些信息的动机是真实存在的：一个用户在 § 5.2 驱逐中所述的设置 UI 中查看一个数 GB 大小的文件时，以及一个开发者在调试为何某次 requestFileHandle() 调用未命中时，都希望知道文件 来自哪里。用户代理可以通过在条目旁保留实现私有的溯源记录来满足这种需求 ——例如，其每个存储源从哪个 URL 获取了 这些 字节，以及获取时间——前提是该记录被视为用户代理状态，而不是 条目的一部分：

  • 它绝不会暴露给脚本。本规范中的任何内容都不会公开它，并且以后添加的任何内容 也不应这样做：无论是 requestFileHandle() 还是它返回的 FileSystemFileHandle 都不应透露这种记录是否存在，更不用说其 内容。特别是，请求源不得观察并非由其 自身产生的记录。

  • 它只通过受信任的非 Web 界面呈现：用户代理自身的设置和存储 检查 UI、其开发者工具，以及——在用户代理具有扩展平台的情况下——受 明确的、由用户授予的权限控制的扩展 API，其权限级别与其他 暴露浏览历史的 API 相同。有关正在考虑的扩展接口，请参见本 仓库中的 浏览器扩展集成点说明文档。

  • 它未经验证，并且会以这种方式呈现。其中的 URL 是写入这些 字节的源所作出的声明，而不是关于这些字节的证明——只有哈希能够保证内容（参见 § 7.1 资源完整性）。两个源可能会为同一个条目记录不同的 URL， 而其中任意一个 都可能不准确或具有故意误导性。

  • 它与条目以及它所归属的源具有相同的生命周期。当 条目被驱逐或删除时，该记录会被丢弃；当 某个源从存储源中移除时，归属于该源的部分也会被丢弃，包括用户清除 该 源的站点数据时（参见§ 5.2 驱逐）。

由于这种记录对内容不可见，因此用户代理是否保留这种记录，以及保留多少内容， 完全由实现决定。本规范中的任何内容都不依赖它，并且 站点无法检测其存在与否。

6. 权限策略集成

本规范定义了一个由字符串 "cross-origin-storage" 标识的策略控制功能 [permissions-policy]。 其默认允许列表 为 self。

一个未被允许使用此功能的Document，会导致从该 Document（或从其所有者为该Document 的 worker）发出的每次 requestFileHandle() 调用都以 "NotAllowedError" DOMException 拒绝， 并且发生在任何哈希验证、注册表查找或写入之前。

7. 隐私和安全注意事项

除使用 RFC 2119 关键词的地方外，本节均为非规范性内容；另请参见仓库中的 安全和隐私调查问卷。

7.1. 资源完整性

每个COS 条目都以密码学哈希为键，其 字节也会依据该哈希进行验证（参见 § 3.3 创建和写入文件）。因此，站点可以确定 通过 requestFileHandle() 获得的文件具有与其自行获取 hash 时 所得到的完全相同的字节。开发者无法枚举跨源存储的内容，也无法 在尚不知道文件哈希的情况下访问该文件。

COS 哈希并不是秘密。它是一个 内容标识符，任何已经拥有该文件的人都可以轻易计算出来，并且对于 本规范所针对的这类广泛分发的资源而言，它通常是公开信息——例如，会与模型或库的 发布版本一同公布。因此，知道哈希足以查找一个条目，但与能力 URL 或持有者令牌不同，它本身并不会授予任何访问权限：查找是否成功完全由 源和§ 7.3 可用性门控决定，而绝不会取决于该哈希是否碰巧一直 未公开。开发者绝不能把未公开的哈希当作访问控制机制；对某个特定文件感兴趣的 攻击者无需猜测其哈希，只需获得该文件 本身即可（参见§ 7.2 跨站点探测）。

7.2. 跨站探测

如果某个资源只被一小部分站点使用，能够获知该资源 存在于跨源存储中的攻击者就可以推断用户可能访问过这些站点中的某一个。由于 requestFileHandle() 是获知其是否存在的机制，因此每次调用 实际上都是一次探测。本规范中的两个独立机制限制了一次探测可以 获知的信息：

  • 源（参见 § 3.4 资源可见性升级）允许存储 源将 公开范围限制为一组选定的源，因此专有资源或较少使用的资源完全不必 在全局范围内可被探测。

  • § 7.3 可用性门控还会阻止向 存储源之外的请求源公开 "*" 范围的资源，除非该哈希位于 PHL 上， 从而使使用 origins: "*" 存储的资源 不会自动变得可由 Web 上的每个源探测。此门控仅适用于 "*" 范围的 条目；对于列表范围和同站点范围的条目，第一项中的限制是唯一的 门控，因为存储源已经明确限制了这些条目的公开范围。

第一项只有在“一组选定的源”仍然明显小于整个 Web 的情况下才成立。 origins 的形式本身并不能阻止调用方 枚举数量非常庞大的源——例如，根据公开的 热门站点排名构造一个列表——这在功能上会近似于全局公开，同时绕过 只有 "*" 才要求的有意且明确的选择加入。最大源列表 长度（参见 § 5.1 存储限制）对此加以限制：一个足够小、能够满足真正的 多属性使用场景 （共同控制下的少量相关源），但又远不足以有意义地近似 “每个源”的限制，可以防止源的受限源形式被用作 "*" 的未声明替代形式。

用户代理还应该对来自单个源的重复 requestFileHandle() 调用进行速率限制或以其他方式节流，并且可以应用 设备端启发式方法（例如，检测针对看似按用户 生成的哈希的请求模式）来识别并阻止探测尝试，而不论被探测的 哈希是否位于 PHL 上。

由 § 8 与其他规范的集成 中某个宿主集成执行的查找 同样属于一次探测，即使它不会向页面呈现任何错误：站点可以观察其 自己的服务器是否收到了回退请求，而该请求携带的单个比特与此处“未找到” 结果所携带的相同。此类查找不会披露本规范的门控机制原本不会披露的任何内容，并且 这些门控机制会原样适用于该查找。不过，速率限制只有在来自这些 表面的查找与 requestFileHandle() 调用一并计数时才有效，因为可脚本化的 集成同样可以轻易地在循环中发出这些查找。

7.3. 可用性门控

从存储 源之外的源发起的 requestFileHandle() 读取是否成功，始终取决于请求源是否 被允许读取该条目，这由源控制。对于范围为 "*" 的条目，还存在第二个 独立的问题：用户代理是否愿意公开该条目 确实存在，这由PHL 成员资格和GREASE 操作控制。对于这种条目，这两个条件都必须 满足；对于列表范围或同站点范围的条目，只适用第一个问题， 尽管 GREASE 操作仍可能抑制源原本 允许的公开。有关规范性算法，请参见§ 3.2 读取文件。因此，"NotFoundError" 并不能 证明资源不存在：它可能意味着资源不存在、请求 源超出范围、范围为 "*" 的资源的哈希尚未（或永远不会）位于 PHL 上，或者 GREASE 操作抑制了真正的正结果。开发者不得将 "NotFoundError" 理解为 比“回退到网络”更具体的含义。

注： 范围为 "*" 的条目的公开还 额外限制为当前上下文中能够设置或读取第三方 Cookie 的请求 源；对于无法使用第三方 Cookie 的源， 无论PHL成员资格如何，都不会公开这种 条目。这弥补了仅靠PHL 成员资格无法弥补的缺口：攻击者可以通过选择写入 哪些原本普通且各自符合 PHL 条件的资源子集，构造跨站点标识符， 而第三方 Cookie 的可用性是决定 最终探测是否会比普通跟踪 Cookie 提供更多信息的关键因素。

7.4. GREASE 处理

用户代理可以应用 GREASE 处理（生成 随机扩展并保持 可扩展性）：即使§ 7.3 可用性门控本来允许披露，也偶尔表现得像某个可披露条目不存在一样。这会添加噪声，使网站更难区分真正不存在与出于隐私目的产生的假阴性，类似于 UA 客户端 提示所采用的技术。

应用 GREASE 处理的用户代理必须根据所涉条目的大小作出适度判断。对于小型条目，回退到网络获取的成本很低，因此偶尔出现假阴性是一种合理的隐私权衡。用户代理不得对体积大到无意义的重新下载明显与其隐私收益不成比例的条目应用 GREASE 处理——例如，GB 级 AI 模型权重——因为对这类条目产生假阴性会迫使执行一次完整、可观察且成本高昂的重新下载，而不是廉价的重新下载。

7.5. 指纹识别

攻击者通过探测跨源存储能够提取的信息量，取决于被探测资源的流行程度。得知用户拥有非常流行的资源，例如常见 AI 模型或广泛使用的 JavaScript 库，只能说明用户访问过使用该资源的众多网站之一。得知用户拥有罕见或唯一的资源则更具信息量。用户代理应应用设备端启发式方法，检测其哈希看起来是刻意为每个用户唯一生成的资源（例如，仅由单个站点写入过的哈希，或以异常高的频率被请求的哈希），并将这类模式视为探测尝试，而不受名义上的 PHL 状态影响。

8. 与其他规范的集成

本节为非规范性内容。

这里定义的 COS 注册表 还可以通过四种宿主集成方式访问，而无需直接通过 requestFileHandle()。 每种 集成都在其各自的宿主规范中定义，而不是在本文档中定义；本 规范仅定义这些集成应当基于的共享底层概念（COS 哈希、COS 条目、 可用性门控以及公共哈希列表）。

  • HTML：在已经 带有 integrity [SRI] 的 link 和 script 元素上的 crossoriginstorage 属性，已在 whatwg/html#12770 中向 WHATWG 提议。

  • JavaScript：宿主定义的 crossOriginStorage 导入属性，可 与 integrity 一起使用，基于导入属性 提案构建，已在 whatwg/html#12771 中向 WHATWG 提议。

  • CSS：一个 cross-origin-storage() <request-url-modifier>， 可与 integrity() 一起使用， 已在 w3c/csswg-drafts#14056 中向 CSS 工作组提议。

  • Fetch：一个 crossOriginStorage RequestInit 选项，可与 integrity [FETCH] 一起使用，已在 whatwg/fetch#1954 中向 WHATWG 提议。 与三种声明式形式不同，这一种没有宿主定义的目标，因此从 COS 注册表提供的 Response 应如何报告其 MIME 类型、状态以及其他元数据， 对该规范而言仍是一个开放问题；COS 条目仅存储字节。

仅用于说明，下面展示了同一个全局共享资源如何通过这四种形式中的每一种选择加入跨源存储：

<script src="popular-library.js" integrity="sha256-abc123..." crossoriginstorage="*"></script>

import data from "popular-resource.ext" with {
  integrity: "sha256-abc123...",
  crossOriginStorage: "*",
};

@font-face {
  font-family: "Popular Font";
  src: url("popular-font.woff2" integrity("sha256-abc123...") cross-origin-storage(*));
}

const response = await fetch("popular-resource.ext", {
  integrity: "sha256-abc123...",
  crossOriginStorage: "*",
});

这些代码片段仅用于说明。这些语法均不是由本规范定义的，并且 每种形式的权威语法——包括受限制的、非 "*" 的 origins 值如何 表示——属于其各自的宿主规范，而不是本文档。其写法有意 不同：RequestInit 成员可以接受 sequence<DOMString>，与 origins 完全匹配，而属性值、 导入属性值以及 CSS 修饰符参数只能承载文本。

预计这四种形式都会共享这样的处理模型：首先查询COS 注册表，查找匹配且可公开的条目， 然后才回退到网络获取，并将 成功获取且通过完整性验证的资源存储到COS 注册表中，以供 其他源复用，这与 requestFileHandle() 的做法完全相同。关于 这些集成的讨论应当在承载它们的宿主规范的跟踪器中进行， 而不是在本仓库的问题跟踪器中进行。

一致性要求通过描述性断言 和 RFC 2119 术语的组合来表达。 在本文档的规范性部分中，关键词“MUST（必须）”、“MUST NOT（不得）”、“REQUIRED（要求）”、“SHALL（应）”、“SHALL NOT（不应）”、“SHOULD（应该）”、“SHOULD NOT（不应该）”、“RECOMMENDED（建议）”、 “MAY（可以）”和“OPTIONAL（可选）” 应按照 RFC 2119 中所述的方式解释。 不过，为了便于阅读， 这些词在本规范中并不全部以大写字母出现。

除明确标记为非规范性的章节、示例和注释外，本规范的所有文本均为规范性内容。[RFC2119]

IDL 索引

[Exposed=(Window,Worker), SecureContext]
interface CrossOriginStorageManager {
  Promise<FileSystemFileHandle> requestFileHandle(
      CrossOriginStorageRequestFileHandleHash hash,
      optional CrossOriginStorageRequestFileHandleOptions options = {});
};

dictionary CrossOriginStorageRequestFileHandleHash {
  required DOMString value;
  required DOMString algorithm;
};

dictionary CrossOriginStorageRequestFileHandleOptions {
  boolean create = false;
  (DOMString or sequence<DOMString>) origins;
};

interface mixin NavigatorCrossOriginStorage {
  [SameObject, SecureContext] readonly attribute CrossOriginStorageManager crossOriginStorage;
};
Navigator includes NavigatorCrossOriginStorage;
WorkerNavigator includes NavigatorCrossOriginStorage;

问题索引

公共哈希列表的检索协议、更新频率、数据格式、流行度阈值和治理方式 作为本规范的配套产物进行了详细设计，其理念类似于 [URL] 标准的公共后缀列表是一个配套数据文件，而非 规范性文本 — 请参阅本仓库中的 公共哈希列表说明文档。该设计 提议由 WHATWG 进行治理，参考公共后缀列表跨厂商、 滚动发布的先例，并以独立验证的普遍性作为准入标准 — 这是上述 k-匿名性风格门槛的一个具体实例，该门槛仅在哈希被纳入列表时离线应用一次， 而不是用户代理针对每次查询重复执行的检查。此方案目前尚未在 本提案之外建立。列表本身的一个早期、非规范性代码原型 维护在本仓库的 public-hash-list/implementation/ 中 — 这是一个务实的 临时存放位置；一个专用的跨厂商仓库仍然是 PHL 说明文档中描述的治理目标。 本规范仅依赖于某个哈希是否 在 PHL 中，而不依赖于任何特定的 检索机制或治理模型，因此无论该设计如何 演进，本规范都保持正确。 ↵
