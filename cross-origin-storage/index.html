摘要

跨源存储（COS）是一种可按内容寻址的缓存，允许 Web 应用存储和检索 大型文件，例如 AI 模型、WebAssembly 模块和广泛使用的 JavaScript 库，即使存取操作来自 不同的源。文件通过其密码学哈希值而非 URL 标识，因此，只要字节完全相同， 某个源获取过一次的资源就可由用户代理允许的任何其他源复用，无需 再次下载。默认情况下，同站的源可以读取文件。写入方可以额外指定少数几个源， 也可以与所有源共享。后一种方式仅对达到类似于 k-匿名性要求的流行度 阈值的哈希值生效。按站点设置的跨站查询预算和写入上限，限制了各站点对 其他站点所存内容的了解程度。

1. 引言

本节为非规范性内容。

为保护用户的安全和隐私，存储通常按源分区。这是合理的 默认做法，但并不适合一小类体积很大、广泛使用且公开分发的 资源（AI 模型、WebAssembly 模块、JavaScript 库、游戏引擎和大型 Web 字体）： 无论哪个站点请求这些资源，得到的文件都逐字节相同。当两个 互不相关的源都依赖同一个 8 GB 的模型时，按源分区的存储会迫使 用户将该模型下载两次并保存两份副本，既浪费用户的带宽、存储空间 和电量，也浪费整个网络的资源。

跨源存储（COS）是一种可按内容寻址的缓存，以密码学哈希值 而非 URL 为键，使用户代理能够将此类资源的一份已存储副本共享给 选择使用它的各个源。将资源存入 COS 始终需要由 存储源明确选择。用户代理可以不确认资源是否存在，即使询问的源 原本有权读取该资源。参见§ 8 隐私 和安全注意事项。

本规范的入口是 getFileHandle() 方法，可通过 crossOriginStorage 访问： 

const hash = {
  algorithm: 'SHA-256',
  value: '8f434346648f6b96df89dda901c5176b10a6d83961dd3c1ac88b59b2dc327aa4',
};
try {
  const handle = await navigator.crossOriginStorage.getFileHandle(hash);
  const file = await handle.getFile();
  // 对文件执行操作。
} catch (err) {
  if (err.name === 'NotFoundError') {
    // 跨源存储中没有可披露的此文件，改从网络获取。
  }
}

本规范复用 FileSystemFileHandle、 FileSystemWritableFileStream， 以及相关的 基础设施。它们均来自《文件系统标准》[FS]，在此仅用于一个专用文件系统，该文件系统 由多个源共享，独立于各个源的私有文件系统或用户可见的文件系统。

本规范定义了命令式 JavaScript API，以及各宿主 集成共用的存储步骤。相关提案还将同一底层缓存集成到其他宿主 规范中：HTML 属性 crossoriginstorage 用于 link 和 script， 还有 crossOriginStorage JavaScript 导入属性、CSS 的 cross-origin-storage() <request-url-modifier>，以及 crossOriginStorage 这一 RequestInit 选项，供 fetch() 使用。每一项均 由相应的宿主规范定义。参见§ 9 与其他规范 的集成。

2. 概念

2.1. 哈希值

COS 哈希值是一个结构体，具有 以下项：

算法

一个字符串， 指定的哈希算法须为 [WEBCRYPTO] 所认可，且不能是“SHA-1”， 例如“SHA-256”。

值

一个字符串，表示摘要的小写十六进制编码，该摘要由 算法生成。 对于“SHA-256”，此字符串长 64 个字符。

algorithm 字典成员的类型是普通的 DOMString，尽管其取值范围恰好是 [WEBCRYPTO] 的 哈希算法所接受的名称集合。HashAlgorithmIdentifier 的类型是 (object or DOMString)。其中的 object 分支 会由 [WEBCRYPTO] 规范化为一个具有 Algorithm 结构的 字典，让调用方能够传入额外的 参数，供需要这些参数的算法使用（例如 {name: "HMAC", hash: "SHA-256"}）。哈希 算法不接受此类参数， 算法的存储、 比较和往返传递均将其作为可按内容寻址的 键的一部分，且本规范的所有 示例都直接使用字符串。在这里允许任意对象不会增加任何功能，却会使 相等性判断和序列化 徒增复杂性。因此，DOMString 对此字段而言 是范围更窄且更恰当的类型。

两个 COS 哈希值彼此相等的条件是，它们的算法 值在不区分 ASCII 大小写的情况下匹配，且它们的值完全 相等。

注： 值按规范要求已经是小写形式（见上文），因此比较时只需 进行普通的 字符串比较。对于算法，规范未规定大小写，因此比较时 不区分 ASCII 大小写。

可按内容寻址的 存储以哈希值作为条目的键。判断键是否 相等，比较的是 COS 哈希值：两个文件只要 字节完全相同且使用相同的哈希算法，就对应同一条目，无论有多少个源 存储过它们，也无论通过多少个 URL 获取过它们。

2.2. COS 条目

COS 分区属于一个 环境设置对象 settings，其值是 以下操作的结果： 获取站点，输入为 settings 的顶层源。settings 是 第一方 COS 上下文的条件是，获取站点时以 settings 的源为输入，所得站点须与以下分区同 站：该对象的 COS 分区。

COS 共享记录 是一个结构体， 包含以下项： 源，其值为一个源；分区，其值为 COS 分区，即添加该记录的写入操作 所属的分区；以及第一方，其值为 布尔值， 记录该写入操作是否在第一方 COS 上下文中执行。记录适用于满足以下条件的读取操作：其 COS 分区须与以下分区同站：该记录的分区。参见 确定 COS 披露范围。

每个用户代理都有唯一一个 COS 注册表，它是一个映射，将 COS 哈希值映射到 COS 条目结构体， 由使用跨源存储的所有源共享。每个 COS 条目具有以下项：

哈希值

一个 COS 哈希值。

字节

一个字节序列，其摘要使用哈希值的算法计算， 等于哈希值的值。

注： 将条目加入 COS 注册表的前提是 写入方已提供这些字节，且 用户代理已验证这些字节。参见验证并存储。对于已请求但 尚未完成的写入，注册表中没有任何记录，因此在读取时，正在进行的 写入与从未发生过的写入无法区分。参见§ 8.3 正在进行的写入。

源

一个列表，其中的 COS 共享 记录明确授予跨源读取权限，不依赖于 公共哈希值 列表。每条记录的授权范围涵盖所有满足以下同站条件的源：它们与该记录的 源属于同一站点。因此，列出 https://a.example 也会允许 https://www.a.example。如果记录的第一方为 true，则该记录也适用于处在 第一方 COS 上下文中的读取方，无论顶层站点是哪个。 该列表初始为空，此后只会 增长。这是 决定谁可以读取条目的三个范围之一，这三个范围相互独立且可以叠加。 另外两个分别是条目的存储源（始终可以读取，其他源 只要 同站也可以读取）以及可全局 披露。

注： 因此，指定一个源意味着信任它所属的 整个站点。如果写入方指定了一个源， 而该源所属的站点托管了写入方不信任的内容，例如某个托管域未列入公共 后缀列表，那么该条目就会向所有这些内容披露。

注： 如果一次写入的 origins 被显式设为空 列表 （origins: []），其授权范围与写入时省略 origins 完全相同，即该条目的 存储源以及与它们同站的源。这是每个条目 都具备的基本授权范围（参见确定 COS 披露范围）。应用范围 上限 会将空列表转换为 null，因此两种写入在执行 完成创建请求的后续步骤时处于相同的状态。显式 指定的列表只会增加接收方， 绝不会阻止写入方自己的站点访问该条目。

可全局披露

一个布尔值，初始为 false，记录写入该条目时是否 提出了使其 全局可用（“*”）的请求，且该请求是否已满足 COS 用户激活 条件。当该值为 true 时，任何源均可读取该条目，只要其请求满足§ 8.4 可用性控制的要求， 即所请求的哈希值位于 PHL 中，且该请求得到跨站查询预算的允许， 并且未被 GREASE 机制抑制。该值一经 设置，就一直为 true。

注： 这是一个单独的项，独立于源。这样， 后续的 全局可用性请求就能将全局范围叠加在已有的显式 源列表之上。 如果将两者合并为一个字段，提供 字节的写入方就能将以列表为范围的条目变为以“*”为范围的条目。由于§ 8.4 可用性控制 仅适用于全局范围，原先因列在列表中而能够读取条目的源 就会开始收到“NotFoundError”， 只要该条目的哈希值 未 列入 PHL。让这些 范围相互独立，可确保可见范围每次都只能扩大， 从而满足可扩大但不可缩小 这一要求。

存储源

一个集合，其中包含 COS 共享记录。每条记录对应一个源与一个 COS 分区的组合，表示该 源曾在此分区中至少一次成功完成了对该条目字节的写入。 这些记录的第一方值在此不起作用。该集合在多次 页面加载之间持久保存，并随时间 增长；仅在§ 5.2 逐出所述情形下才会缩小。记录的源始终可以 获取该条目的句柄，方法是调用 getFileHandle()， 调用时须处于该记录的分区中， 这与源列表无关，也与该条目的哈希值是否 位于公共哈希值列表（PHL）中无关。参见§ 3.5.2 最初存储方的访问权限。

注： 以顶层 站点作为共享记录的键，使嵌入式框架所能看到的 跨源存储范围与存储分区机制下它所能看到的其他存储范围一致。如果没有这个键， 嵌入多个站点的同一框架就可以在一个站点写入小文件，再在另一个站点 以存储源的身份将其读回，从而绕过公共哈希值列表、GREASE 机制 以及 跨站查询预算，其效果相当于 第三方 cookie。顶层写入同样以顶层站点为键，因此 跟踪器无法在一次顶层访问中写入数据，然后从各处的嵌入式框架中读回。如果一条 源记录 来自第一方 COS 上下文，它也适用于 任何顶层站点下的第一方上下文，因此顶层站点之间的受限共享仍然有效。如果一次查询 在另一个顶层站点下通过此类记录得到结果，就会披露 写入方在其顶层站点下存储的内容，因此跨站查询预算会将该查询计入其中（参见应用可用性控制）。 可全局披露不以顶层站点为键，因为公共哈希值 列表、GREASE 机制 以及跨站查询预算已对其实施控制。

用户代理有一个关联的跨源存储队列，它是 启动新的并行队列的结果。对 COS 注册表执行的所有操作都要 加入此队列，以便它们按 各操作 入队的顺序执行，彼此不交错。

2.3. 公共哈希值列表

确认某个哈希值存在于跨源存储中，这一点本身就可能泄露有关 用户浏览历史的信息（参见§ 8.2 跨站探测）。这种风险 特指全局范围。条目显式指定的源列表，以及每个 条目 都具备的同站基本授权范围，其披露范围均已受存储源明确选择的限制，而 将条目标记为可全局披露，则可能将其暴露给 Web 上的任何源。为了限制这一 特定风险，可全局披露的资源要通过 此范围向其存储源之外的源披露，其哈希值还须满足一项额外的、 独立的条件，即列入公共哈希值列表 （PHL）。这是一份厂商中立、由实现定义的允许列表，以 COS 哈希值 为条目。哈希值只有达到类似 k-匿名性要求的 流行度阈值（例如，字节完全相同的资源至少出现在一定数量的独立 源中），才会被纳入公共哈希值列表。这样，即使确认它存在于共享缓存中，也几乎无法据此了解任何单个 用户的情况。

对于 COS 哈希值 hash，称其位于公共 哈希值列表中的条件是，hash 等于用户 代理当前持有的公共哈希值列表快照中的某个条目。

关于获取协议、 更新频率、数据格式、流行度阈值和治理方式， 公共哈希值列表的详细设计见本规范的配套文档。其思路 借鉴了公共后缀列表，后者是 [URL] 标准的配套数据文件。参见 本仓库中的公共哈希值列表说明文档。该设计 提议由 WHATWG 负责治理，借鉴公共后缀列表跨厂商协作、 滚动发布的先例，并以资源的广泛使用程度得到独立证实作为收录标准。 这是上述类 k-匿名性阈值的一个具体实例。该阈值只需在离线状态下检查一次， 作为收录哈希值的一个环节，因此用户代理无需在每次查询时重复检查。这些做法 均尚未在本提案之外确立。列表本身的一个早期非规范性代码原型 暂时位于本仓库的 public-hash-list/implementation/；建立一个专用的 跨厂商仓库仍是 PHL 说明文档所述的治理目标。本 规范仅依赖于哈希值是否位于 PHL 中，因此，无论 列表的获取机制、治理模式或该设计的其他部分如何演变，本规范仍然成立。

3. CrossOriginStorageManager 接口

[Exposed=(Window,Worker), SecureContext]
interface CrossOriginStorageManager {
  Promise<FileSystemFileHandle> getFileHandle(
      CrossOriginStorageGetFileHandleHash hash,
      optional CrossOriginStorageGetFileHandleOptions options = {});
};

dictionary CrossOriginStorageGetFileHandleHash {
  required DOMString value;
  required DOMString algorithm;
};

dictionary CrossOriginStorageGetFileHandleOptions {
  boolean create = false;
  (DOMString or sequence<DOMString>) origins;
};

interface mixin NavigatorCrossOriginStorage {
  [Exposed=(Window,Worker), SameObject, SecureContext]
  readonly attribute CrossOriginStorageManager crossOriginStorage;
};
Navigator includes NavigatorCrossOriginStorage;
WorkerNavigator includes NavigatorCrossOriginStorage;

每个 Navigator 和 WorkerNavigator 对象都有一个关联的 CrossOriginStorageManager 对象。crossOriginStorage 的取值器 步骤 是返回与 this 关联的 CrossOriginStorageManager。

每个 CrossOriginStorageManager 对象都有一个关联的源，其值设为 this 的相关设置对象的源；还有一个关联的 分区，其值设为如下 COS 分区，即 this 的 相关设置对象所属的分区。这些值在创建该对象时设置。

注： 源取自相关设置对象，与 脚本本身无关。这一点对工作线程的影响值得说明。通过 blob: URL 创建的工作线程继承创建它的上下文的源，因此它与该源看到的 跨源存储内容完全相同：创建该工作线程的页面可以读回它写入的内容， 工作线程也可以读取页面存储的内容。blob: URL 本身不构成独立的源， 撤销它也不会改变工作线程可见的存储范围。通过 data: URL 创建的工作线程 具有不透明源。本规范目前未定义 getFileHandle() 在调用方的源不透明时的行为。 验证 COS 请求中的源规则仅适用于 调用方指定的源。不透明源没有稳定的标识可用作 存储 源的键或同 站比较的依据，因此没有可向它授予的 有实际意义的权限。

3.1. getFileHandle() 方法

handle = await navigator . crossOriginStorage . getFileHandle(hash)

返回由 hash 标识的文件的句柄，前提是该文件存在于 跨源存储中，且可向调用源披露。否则，以一个 “NotFoundError” DOMException 拒绝。 “NotFoundError” 无法证明该文件 确实不存在于跨源存储中。参见§ 8.4 可用性控制。调用方可以 将其理解为“改从网络获取此文件”。

handle = await navigator . crossOriginStorage . getFileHandle(hash, { create: true })

返回一个句柄，可用它将 hash 标识的文件写入 跨源 存储。如果条目尚不存在，则创建新条目，默认仅允许同站的源访问。 调用方需要写入完整的文件内容，使用的是句柄的 createWritable() 方法，无论条目此前是否已经 存在。此时用户代理会验证所写字节的哈希值是否为 hash； 如果不匹配，则以一个“DataError” DOMException 拒绝。此要求可防止 源利用创建请求判断 hash 此前是否已存在。

handle = await navigator . crossOriginStorage . getFileHandle(hash, { create: true, origins: "*" })

同上。此外，条目写入后可向满足以下条件的任何源披露：该源对 hash 的请求通过了§ 8.4 可用性控制。

handle = await navigator . crossOriginStorage . getFileHandle(hash, { create: true, origins: ["https://a.example", "https://b.example"] })

同上，但披露范围仅限于列出的源以及与其中任一源同站的 各个源（此外还包括调用源、任何已列入 存储源的源，以及与这些源同站的源）。

getFileHandle(hash, options) 方法的 步骤如下：

  1. 令 result 为一个新的 promise。

  2. 令 realm 为 this 的相关领域。

  3. 令 global 为 this 的相关全局对象。

  4. 令 origin 为 this 关联的源。

  5. 令 partition 为 this 的分区。

  6. 如果运行检查跨源存储权限时， 传入 global 所得的结果为 false，则：

    1. 将一个全局任务排入队列，使用DOM 操作任务源，给定 global，以 拒绝 result，拒绝原因为一个“NotAllowedError” DOMException。

    2. 返回 result。

  7. 令 validationFailure 为运行验证 COS 请求所得的结果，传入 hash 和 options。

  8. 如果 validationFailure 不为 null：

    1. 将一个全局任务排入队列，使用DOM 操作任务源，给定 global，以 拒绝 result，拒绝原因为 validationFailure。

    2. 返回 result。

  9. 将以下步骤排入 跨源存储队列：

    1. 如果 options["create"] 为 true：

      1. 运行完成创建请求，传入 result、hash、options、global 和 realm。

    2. 否则：

      1. 运行完成读取请求，传入 result、hash、origin、partition、 global 和 realm。

  10. 返回 result。

要验证 COS 请求，给定一个 CrossOriginStorageGetFileHandleHash hash 和一个 CrossOriginStorageGetFileHandleOptions options，返回 null 或一个 TypeError：

  1. 如果 hash["algorithm"] 不是受认可的哈希算法 名称（以 [WEBCRYPTO] 为准），或者它在不区分 ASCII 大小写的情况下匹配 “SHA-1”，则 返回一个新的 TypeError。

    注： SHA-1 不具备抗碰撞性。 由于 COS 条目的键 仅由其 COS 哈希值确定，SHA-1 碰撞可能使一个源提供的字节被用来响应另一个 源对具有相同摘要的其他字节发出的读取请求。

  2. 如果 hash["value"] 不匹配正则 表达式 /^[0-9a-f]{64}$/，且 hash["algorithm"] 在不区分 ASCII 大小写的情况下 匹配“SHA-256”，则返回一个新的 TypeError。

    注： 未来的哈希算法可以定义 不同的预期摘要长度。本 规范仅对“SHA-256”施加规范性约束，这与 各个 示例中的用法一致。

  3. 如果 options["origins"] 存在且 不为“*”：

    1. 令 candidates 为 options["origins"]， 其中单个字符串视为仅含一项的列表。

    2. 如果 candidates 的大小 大于用户代理的 源列表最大长度，则返回一个 新的 TypeError。

      注： 此上限适用于 最初传入的 candidates，即尚未进行任何解析或 去重时的列表（参见规范化所请求的源），因此它 也限制了单次调用可能触发的 URL 解析量。如果列表只包含同一个源，但该源的出现次数比 源列表最大长度多一次， 则该列表也会被拒绝，即使它 规范化后只会得到一个源。

    3. 对于每个 candidate，取自 candidates：

      1. 令 url 为运行基本 URL 解析器所得的结果，输入为 candidate。

      2. 如果 url 为失败，则返回一个新的 TypeError。

        注： 只有省略 origins， 或者传入一个 空列表时，才表示请求使用默认的同站范围。空 字符串会被视为一个列表，其中唯一的 候选项无法解析，因此会像其他无效源一样被拒绝。 至于 声明式集成中表示同站的空值（参见 § 9 与其他规范 的集成），它是这些集成所用文本语法的特性，由 相应的宿主规范定义。

      3. 如果 url 的方案既不是“http” 也不是“https”，或者 url 的 源不是潜在可信的 源，则返回一个新的 TypeError。

        注： 只有自身能够 调用 getFileHandle() 的源才值得列出。该 API 仅暴露于安全上下文，因此这里允许 https: 源以及回环地址上的 http: 源，例如 http://localhost，并拒绝 其他主机上的 http: 源、ws:、wss:、 ftp:，以及所有具有 不透明源的方案，包括 chrome-extension: 这样的扩展 方案。

  4. 返回 null。

3.2. 读取文件

要完成读取 请求，给定一个 promise result、一个 COS 哈希值 hash、一个 源 origin、一个站点 partition、一个全局对象 global 和一个领域 realm：

  1. 令 entry 为符合以下条件的 COS 条目：它位于 COS 注册表中，且其哈希值 等于 hash。如果没有这样的条目，则令其为 null。

    注： 其他写入方已经 请求但尚未完成的写入不会出现在 COS 注册表中，因此 对于这样的哈希值，entry 为 null，本算法的后续处理 与处理从未有任何源写入过的哈希值完全相同。本规范允许的每一次披露都 由下文的应用可用性控制决定，没有 任何更早的分支可以 提前给出结果。参见§ 8.3 正在进行的写入。

  2. 令 disclosableEntry 为运行应用可用性 控制所得的结果，传入 entry、 origin 和 partition。

  3. 如果 disclosableEntry 为 null：

    1. 将一个全局任务排入队列，使用DOM 操作任务源，给定 global，以 拒绝 result，拒绝原因为一个“NotFoundError” DOMException。

    2. 返回。

  4. 令 handle 为创建一个新的 FileSystemFileHandle [FS] 所得的结果，其 定位器指向 disclosableEntry 的哈希值，该哈希值位于 跨源存储文件系统中，创建该句柄的领域为 realm。

  5. 将 handle 的 COS 哈希值设为 disclosableEntry 的哈希值。

  6. 将 handle 的 COS 源设为 origin。

  7. 将 handle 的可读取设为 true。

    注： 此句柄已经通过应用可用性控制步骤，因此调用源 有权 读取条目的字节。

  8. 将一个全局任务排入队列，使用DOM 操作任务源，给定 global，以 解决 result，所用的值为 handle。

要确定 COS 披露范围，给定一个 COS 条目 或 null 值 entry、一个 源 origin 和一个站点 partition，返回一个 COS 条目或 null：

  1. 如果 entry 为 null，则返回 null。

    注： 位于 COS 注册表中的条目 均已完成写入并通过验证，因此本算法无需 考虑只写入一部分的状态。如果某个哈希值唯一的一次写入仍在进行，则该哈希值 不在注册表中，传给本算法的值为 null，与从未有任何源 写入过的哈希值相同。参见§ 8.3 正在进行的写入。

  2. 令 firstParty 为 true 的条件是，获取站点时以 origin 为输入，且所得站点 同站于 partition；否则令其为 false。

  3. 如果 entry 的存储源包含一条 COS 共享 记录，其 源同站于 origin，且其分区 同站于 partition，则返回 entry。

    注： 最初存储方，以及任何其他 曾自行成功写入该条目的源， 始终可以在写入时所在的顶层站点下读回该条目。参见 § 3.5.2 最初存储方的访问权限。

    注： 每个条目都具有的同站基本授权 范围（即写入时省略 origins 选项所请求的访问权限）始终有效， 无论是否有任何源列表或全局范围 在之后添加。由于此项检查先于下文的公共哈希值列表检查， 因此同站的 源可以读取该条目，无论其哈希值是否位于 PHL 中。此处，同站的源 同属一个信任单元，因此此操作不会跨越 § 8.2 跨站探测所保护的站点边界披露任何信息。

  4. 如果 entry 的源列表包含一条 COS 共享 记录，其 源同站于 origin，且满足以下任一条件：其分区 同站于 partition，或其第一方与 firstParty 均为 true，则返回 entry。

    注： 显式源 列表中列出的源， 或与其中某个源同站的源， 都可读取该条目，无需该条目位于 PHL 中。将每个列出的源扩展至 其所在站点，符合上述同站基本授权范围：同站的源同属一个信任单元，因此指定 站点中的一个源就等于指定其中所有源。存储源通过明确 指定 该源，限定了披露范围（参见§ 3.5 扩大资源的可见范围和§ 7 Cross-Origin-Storage-Allow-Origin 标头）。若在此基础上 另行要求 资源在全球范围内广泛使用，就会使普通的受限共享依赖于无关的 公开遴选，而这类资源往往是专有的。在检查 可全局披露条件之前进行此检查，可防止 后续请求全局可用的写入 撤销已列出的源的访问权限。参见§ 8.2 跨站 探测。

  5. 如果 entry 的可全局披露为 true：

    1. 如果 entry 的哈希值未列入 PHL，则返回 null。

      注： 公共哈希值列表检查 仅适用于全局范围。只有在这种情况下， 披露才可能触及 Web 上的任意源。如果一个条目 可全局披露，但其哈希值 未列入 PHL，则不会 向仅通过此范围获得资格的源披露该条目。如果该源还 出现 在存储源、显式源列表或与两者之一 同站的源的集合中，则算法已在上文返回。

    2. 如果用户代理选择对此请求应用 GREASE 机制， 则返回 null。

      注： GREASE 机制也仅适用于 全局范围。上文检查的记录不会进入此步骤：存储源 与其同站的源同属一个信任单元，而 显式源列表中的源是 写入方有意指定的，它获得了写入方的 Cross-Origin-Storage-Allow-Origin 标头的授权，该授权还涵盖与它 同站的 各个源。

    3. 返回 entry。

  6. 返回 null。

要应用 可用性控制，给定一个 COS 条目或 null 值 entry、一个 源 origin 和一个站点 partition，返回一个 COS 条目或 null：

  1. 如果运行是否为不计入预算的查询，传入 entry、 origin 和 partition， 得到 false，且运行将一次跨站查询计入预算，传入 partition，也得到 false，则 返回 null。

    注： 因超出预算而被拒绝的查询 返回 null，完成读取请求 会将此结果转换为与未命中时相同的“NotFoundError” DOMException， 且所用时间相同。对于 需要计入预算的查询，无论是否找到条目，都会计入预算，因为未命中所披露的信息与 命中同样多。

  2. 返回运行确定 COS 披露范围所得的结果，传入 entry、 origin 和 partition。

3.2.1. 跨站查询预算

每个站点都有一份跨站查询预算，它是一个结构体，包含以下项： 计数，一个非负整数，初始为 0；以及 窗口起点，一个时间点或 null，初始为 null。 这份 预算属于用户正在访问的顶层站点，因此页面上的所有框架以及 这些框架引入的所有源都共用同一份预算。

用户代理有一个由实现定义的最大跨站查询次数，其值是一个 较小的 正整数；还有一个由实现定义的查询窗口，其值是一段时长。

注： 如果预算为约 8 到 16 次查询， 窗口为一周左右，那么在一个窗口内， 跟踪器所能获得的信息量就远低于跨站标识符所需的大约 32 位，同时 站点仍有足够的查询次数来访问它实际使用的共享文件。

用户代理必须持久保存每个站点的跨站 查询预算，使其在多次页面加载之间以及 用户的所有顶层可遍历对象之间保持一致。因此，重新加载页面或在新标签页中打开页面都不会 重置预算。用户代理必须将站点的预算重置为 初始状态，条件是用户清除了该站点的 数据，且使用的是用户代理自身的设置或存储界面。用户代理不得因 站点自身能够触发的任何操作而重置预算，例如发送 Clear-Site-Data 响应标头。

要确定一次查询是否不计入预算，给定一个 COS 条目或 null 值 entry、一个 源 origin 和一个站点 partition：

  1. 如果 entry 为 null，则返回 false。

  2. 如果 entry 的存储源包含一条 COS 共享 记录，其 源同站于 origin，且其 分区同站于 partition，则返回 true。

  3. 如果 entry 的源列表包含一条 COS 共享 记录，其 源同站于 origin，且其 分区同站于 partition，则返回 true。

  4. 返回 false。

注： 这些查询的结果取自共享 记录，此类记录写入时所在的顶层站点是读取方自己的 顶层站点，因此不会披露其他站点存储了什么。其余所有查询都 计入预算，包括未命中的查询、通过全局范围得到结果的查询，以及通过 第一方源记录得到结果的查询，如果该记录是在其他 顶层 站点下写入的。

要将一次 跨站查询计入预算，给定一个站点 partition，返回一个布尔值：

  1. 令 budget 为 partition 的跨站查询 预算。

  2. 令 now 为用户代理跨会话持久保存的时钟所示的当前时间。

  3. 如果 budget 的窗口起点不为 null，且 now 距该起点已经过去至少 一个查询窗口 的时长，则将 budget 的计数设为 0，并将其 窗口起点设为 null。

  4. 如果 budget 的计数大于或等于用户代理的 最大跨站查询次数，则返回 false。

  5. 如果 budget 的窗口起点为 null，则将其设为 now。

  6. 将 budget 的计数加 1。

  7. 返回 true。

通过任一宿主集成进行查询时，执行 应用 可用性控制的方式与 getFileHandle() 调用 相同，因此适用相同的计数条件。所有这些查询都计入同一份预算。

3.3. 创建和写入文件

一个 FileSystemFileHandle 如果由完成创建请求创建，则具有一个关联的 所请求的源值。验证并存储将 尝试把条目的可见范围扩大到该值所指定的源，前提是 已通过该句柄成功写入。

每个 FileSystemFileHandle 如果指向跨源存储文件系统，则还具有一个 关联的 COS 哈希值，即它所指向的 COS 哈希值；一个 关联的 COS 源，即获得此句柄的源；以及一个 关联的 可读取布尔值，用于决定 getFile() 是否可以披露所指条目的字节，具体取决于所用的 句柄。对于由完成读取请求返回的句柄，该值为 true，因为该句柄已经通过 可用性控制。对于由 完成 创建请求返回的句柄，该值为 false，直到验证并存储对同一句柄执行成功。

注： 句柄指向的是 COS 哈希值，而非 COS 条目。完成创建请求也会为如下哈希值返回 句柄：该哈希值在 COS 注册表中没有对应条目，且可能永远不会有。因此，没有 可供句柄引用的条目，直到验证并存储创建一个条目。

注： 将此属性设在每个句柄上是有意为之。一个 创建请求 无论该哈希值对应的条目是否已存在，都会返回句柄（参见 完成 创建请求）。因此，如果按条目控制读取，任何源都可以调用 getFileHandle()， 传入 create: true，就能立即读取一个自己 从未写入过的条目，无需满足源列表、 列入 PHL 或 GREASE 机制的要求即可获知其内容。本 规范中的所有披露控制都在读取时实施，因此按条目控制会使创建请求 绕过所有这些控制。要求调用方先提供正确的字节，意味着通过创建请求取得的句柄成功 读取时，不会披露调用方尚未持有的任何内容。

要完成 创建请求，给定一个 promise result、一个 COS 哈希值 hash、一个 CrossOriginStorageGetFileHandleOptions options、一个全局对象 global 和一个领域 realm：

  1. 令 requestedOrigins 为运行规范化 所请求的源所得的结果，传入 options["origins"]。

  2. 如果 requestedOrigins 是一个列表，则将 requestedOrigins 设为运行 应用 COS 范围上限所得的结果，传入 requestedOrigins 以及运行 获取 COS 范围上限所得的结果，后者的输入为 global。

  3. 令 handle 为创建一个新的 FileSystemFileHandle [FS] 所得的结果，其 定位器指向 hash，该哈希值位于 跨源存储文件系统中，创建该句柄的领域为 realm。

  4. 将 handle 的 COS 哈希值设为 hash。

  5. 将 handle 的 COS 源设为 global 的 相关设置对象的源。

  6. 将 handle 的所请求的源设为 requestedOrigins。

  7. 将 handle 的可读取设为 false。

    注： 本算法不查询 COS 注册表，也 不修改注册表。这两种操作都不能执行，因为 算法的结果必须与 hash 是否已存储无关，否则创建 请求本身 就会披露该哈希值此前是否存在（参见§ 8.2 跨站探测）。 因此，返回 handle 的条件完全 相同，无论条目已经存在、从未被写入，还是正由其他方 写入。在本次调用的调用方提供字节之前，该句柄不具有读取权限。

    注： 由于此处不登记任何内容，如果 调用方请求句柄后将其弃用， 从未调用 createWritable() 或者从未关闭所得的流， 注册表就会保持请求前的状态。其他源无法观察到该请求 曾经发生，也无法将任何哈希值固定在会阻碍后续读取的占位状态。 参见§ 8.3 正在进行的写入。

    注： requestedOrigins 仅由 验证 并存储应用，具体通过 扩大资源的可见范围完成，前提是字节 已写入并通过验证。正因如此， 创建请求必须先提供全部字节，才能扩大可见范围。参见 § 3.5 扩大资源的可见范围。

  8. 将一个全局任务排入队列，使用DOM 操作任务源，给定 global，以 解决 result，所用的值为 handle。

要规范化 所请求的源，给定类型为 (DOMString or sequence<DOMString>) 或 undefined 的 origins，返回“*”、一个列表（其项为源）或 null：

  1. 如果 origins 不存在，则返回 null。

  2. 如果 origins 为“*”，则返回“*”。

  3. 令 list 为 « »。

  4. 对于每个 candidate，取自 origins（单个 字符串视为一个列表，其中 仅有一项）：

    1. 令 candidateOrigin 为如下源：它是运行基本 URL 解析器解析 candidate 所得 URL 的源。

      注： 验证 COS 请求已经确认，每个 candidate 都可解析为 http: 或 https: URL，且其源为潜在可信的源。

    2. 如果 list 不包含 candidateOrigin，则追加 candidateOrigin 到 list。

  5. 返回 list。

注： 在此处去重，即在随后将这些源合并到 已有条目之前去重，可以确保源列表自条目 首次创建起就没有重复项，因此以后每次克隆它时，所得列表也不会有重复项。

如果一个 FileSystemWritableFileStream 是通过调用 createWritable() 获得的，且调用所用句柄的定位器 指向跨源存储文件系统，则关闭该流时 [FS]，用户代理必须运行 下文的 验证并存储步骤， 并传入该句柄。运行这些步骤必须在关闭操作的 promise 兑现之前。

注： 无论关闭操作是如何 触发的，此要求都适用：既可以是显式的 close() 调用，也可以是 pipeTo() 调用到达了 源流的末尾，这在默认情况下也会关闭目标流。[STREAMS] 在流进入已关闭状态时不区分 这两种情形，本算法亦然。

验证并存储 步骤的输入为：一个 FileSystemFileHandle handle，其流已经 关闭；已写入的完整字节序列 bytes；以及关闭操作的 相关设置对象 settings。步骤如下：

  1. 令 origin 为 settings 的源。

  2. 令 partition 为与以下对象关联的 COS 分区：settings。

  3. 令 firstParty 为 true，如果 settings 是第一方 COS 上下文；否则令其为 false。

  4. 令 hash 为 handle 的 COS 哈希值。

  5. 令 computedValue 为 bytes 的小写十六进制摘要，计算时 使用的 算法由 hash 的算法指定，并遵循 [WEBCRYPTO]。

  6. 如果 computedValue 不完全等于 hash 的值：

    1. 拒绝关闭操作的 promise，拒绝原因为一个“DataError” DOMException。

    2. 中止这些步骤。

    注： 写入失败后无须执行清理 操作。完成创建请求并未登记条目， 因此，从未产生通过验证的字节的写入不会更改 COS 注册表，随后 调用 getFileHandle() 查询同一哈希值，得到的仍是同一个 “NotFoundError”， 就像从未尝试写入一样。某个源 已经写入的条目也不受影响：本算法只会添加字节和共享 记录。

  7. 将以下步骤排入 跨源存储队列：

    1. 令 entry 为符合以下条件的 COS 条目：它位于 COS 注册表中，且其哈希值 等于 hash。如果没有这样的条目，则令其为 null。

    2. 如果运行检查 COS 存储上限，传入 entry、origin 和 bytes 的长度，得到 false；或者运行将一次 COS 写入计入预算， 传入 entry、origin、partition 和 bytes 的 长度，得到 false：

      1. 将一个全局任务排入队列，使用DOM 操作任务源， 给定 settings 的 全局对象，以拒绝关闭操作的 promise，拒绝原因为一个“QuotaExceededError” DOMException。

      2. 中止这些步骤。

    3. 如果 entry 为 null：

      1. 将 entry 设为一个新的 COS 条目，其哈希值为 hash， 字节为 bytes，源为一个空列表， 可全局披露为 false，且存储源为一个空 集合。

      2. 设置 COS 注册表[hash] 的值为 entry。

      注： 这是本规范中唯一 将条目添加到 COS 注册表的步骤，且只有在确认 bytes 的哈希值与 hash 一致后才会运行。如果两个 写入方都发现该哈希值不存在并且并发写入，则两者都会执行到这里； 其中 后入队的一方会找到先入队的一方创建的条目，因此只需在下文添加自己的源和 记录。两者的字节具有相同的哈希值，因此存储一次就足够了。

    4. 追加一条 COS 共享记录， 其源为 origin， 分区为 partition， 且第一方为 firstParty，追加的目标为 entry 的存储源，前提是其中尚不 存在相等的记录。

    5. 运行扩大资源的可见范围，传入 entry、handle 的 所请求的源、 partition、firstParty 和 settings 的 全局对象。

    6. 将 handle 的可读取设为 true。

      注： 只有此句柄变为 可读取。通过另一次创建请求获得的、指向同一哈希值的其他句柄， 如果尚未通过它写入数据，则仍然不可读取。

createWritable() 如果是在一个 FileSystemFileHandle 上调用的，且该句柄指向 跨源存储文件系统，则必须产生一个 FileSystemWritableFileStream， 其内容 初始为空，无论下列选项取何值：keepExistingData， 也 无论该句柄指向的 COS 哈希值是否有条目登记在 COS 注册表中。

注： [FS] 在其他情形下将 keepExistingData 定义为使用 已有文件的内容初始化流。在这里沿用该行为，会使调用方成为 自己从未持有的字节的存储源。创建请求总会返回句柄，无论条目 是否已存在，因此调用方可能为其他源存储的哈希值打开可写流，再将其关闭， 即使它未写入任何内容，沿用的字节也会产生所请求的哈希值。这样一来，调用方就能获得读取 权限，而无需检查源列表、 公共哈希值 列表或 GREASE 机制：这会使可用性 控制被绕过， 尽管所组合的两个操作各自都是允许的。出于同样的原因， 验证并存储要求 每次创建请求都提供完整的文件内容。

注： 因此，一个未经任何写入就关闭的可写流 包含的是空字节序列，其哈希值不会 匹配调用方希望获取的任何条目所请求的值，因而验证并存储会拒绝该操作， 拒绝原因为一个“DataError” DOMException， 与其他不匹配情形的处理相同。如果实现在 此情形下改为报告存储或 I/O 故障，就会以一个无关的 错误掩盖验证结果。

《文件系统标准》 [FS] 尚未定义 可供依赖该标准的 规范将针对每次写入的额外验证接入 FileSystemWritableFileStream 关闭步骤的扩展点。在有这样的扩展点之前，本节直接描述所要求的行为；预计 未来的修订版本将与 [FS] 正式集成。

3.4. 存储已获取的资源

§ 9 与其他规范 的集成中列出的宿主集成在存储其 获取的资源时，无需使用 FileSystemFileHandle。 相应的宿主规范应当 在获取的字节通过该集成所要求的完整性检查后， 运行以下算法。

要将已获取的资源存入跨源 存储，给定一个响应 response、一个字节序列 bytes、一个 COS 哈希值 hash、值为“*”、一个列表（其项为字符串） 或 null 的 origins，以及一个环境设置对象 settings：

  1. 如果运行检查跨源存储 权限时，传入 settings 的 全局对象所得的结果为 false，则返回。

  2. 令 options 为 «[ "origins" → origins ]»，条件是 origins 不为 null；否则令其为 «[ ]»。

  3. 如果运行验证 COS 请求时，传入 hash 和 options 所得的结果不为 null，则 返回。

  4. 令 computedValue 为 bytes 的小写十六进制摘要，计算时 使用的 算法由 hash 的算法指定，并遵循 [WEBCRYPTO]。

  5. 如果 computedValue 不完全等于 hash 的值，则返回。

    注： 集成自身的完整性 元数据可以列出多个摘要，只要匹配 其中任意一个就能通过检查。此步骤确保条目使用的键正是由这组 字节计算出的哈希值。

  6. 令 requestedOrigins 为运行规范化 所请求的源所得的结果，传入 options["origins"]。

  7. 如果 requestedOrigins 是一个列表：

    1. 令 internalResponse 为 response 的内部响应，条件是 response 是一个过滤响应；否则取 response 本身。

    2. 将 requestedOrigins 设为运行应用 COS 范围上限所得的结果，传入 requestedOrigins 以及运行解析 COS 范围上限所得的结果，后者的输入为 internalResponse 的标头列表。

    注： 范围上限来自已获取 资源自身的响应，因此由 提供字节的服务器决定可向哪些源披露这些字节。加载该资源的 Document 的 COS 范围上限在此不起作用，因为该文档的运营方 并不控制该资源。如果 允许它授权接收方，任何站点都可以声明其他站点的资源可与 自己选择的源共享。用户代理从内部 响应中读取标头，因此这一机制也适用于不透明的过滤响应，并且该标头 永远不会暴露给页面。

  8. 令 origin 为 settings 的源。

  9. 令 partition 为与以下对象关联的 COS 分区：settings。

  10. 令 firstParty 为 true，如果 settings 是第一方 COS 上下文；否则令其为 false。

  11. 将以下步骤排入 跨源存储队列：

    1. 令 entry 为符合以下条件的 COS 条目：它位于 COS 注册表中，且其哈希值 等于 hash。如果没有这样的条目，则令其为 null。

    2. 如果运行检查 COS 存储上限，传入 entry、origin 和 bytes 的长度，得到 false；或者运行将一次 COS 写入计入预算， 传入 entry、origin、partition 和 bytes 的 长度，得到 false，则中止 这些步骤。

    3. 如果 entry 为 null：

      1. 将 entry 设为一个新的 COS 条目，其哈希值为 hash， 字节为 bytes，源为一个空列表， 可全局披露为 false，且存储源为一个空 集合。

      2. 设置 COS 注册表[hash] 的值为 entry。

      注： 与验证并存储一样， 只有在确认 bytes 的哈希值与 hash 一致后，才会创建条目。集成的 integrity 检查已完成这项验证。通过 getFileHandle() 写入同一哈希值且尚未完成写入的 写入方不受影响：它在注册表中不持有任何状态，其自身的验证并存储 仍会 正常完成，找到该条目并将自己的源和共享记录添加到其中。

    4. 追加一条 COS 共享记录， 其源为 origin， 分区为 partition， 且第一方为 firstParty，追加的目标为 entry 的存储源，前提是其中尚不 存在相等的记录。

    5. 运行扩大资源的可见范围，传入 entry、requestedOrigins、partition、 firstParty 和 settings 的全局对象。

注： 与验证并存储一样，存储操作始终要求提供 全部字节，即使 哈希值对应的条目已存在也是如此，因此不会披露该条目此前是否存在。集成在 从网络获取资源前进行的查询属于读取操作，须通过可用性控制，并受 § 8.2 跨站探测中有关探测的注意事项约束。

3.5. 扩大资源的可见范围

COS 条目的可见范围可以 扩大，但绝不能缩小。

要扩大 资源的可见范围，给定一个 COS 条目 entry、值为“*”、一个列表（其项为 源）或 null 的 requestedOrigins、一个站点 partition、一个布尔值 firstParty， 以及一个 全局对象 global：

  1. 如果 requestedOrigins 为 null，则返回。

    注： 省略 origins 表示仅请求在同站范围内 可用，而每个条目都已具备这一权限（参见确定 COS 披露范围），因此 无需添加任何内容。

  2. 如果 requestedOrigins 为“*”：

    1. 如果 entry 的哈希值未列入 PHL，则用户代理 应当记录一条 控制台警告，或在开发者工具中报告一个问题，说明只有 同站的源以及列入该条目的源列表的源才能读取该条目。

      注： 写入本身会成功，因此 如果没有这条消息，开发者就无从得知 全局范围并未生效。参见§ 8.5 开发者 指南。

    2. 如果 entry 的可全局披露为 true， 则返回。

    3. 如果 global 具有 COS 用户激活状态，则将 entry 的 可全局披露设为 true。

    4. 否则，追加 entry 到 partition 的待全局披露的条目中。

    5. 返回。

    注： 此操作添加全局范围，但 不更改 entry 的源。如果条目 已经具有显式的源列表，则会保留该列表，因此每个 列入 该列表的源都保留其不依赖于 PHL 的访问权限，即使该条目后来变为 可全局披露也是如此。这正是 将两个范围分别 存储的原因。参见可全局披露。

  3. 对于每个 candidateOrigin，取自 requestedOrigins：

    1. 令 record 为一条 COS 共享记录，其源为 candidateOrigin， 分区为 partition， 且第一方为 firstParty。

    2. 如果 entry 的源列表包含一条与 record 相等的记录，则 继续下一次迭代。

    3. 如果 entry 的源列表的大小 等于用户代理的 源列表最大长度，则 跳出循环。

      注： 对于剩余的所有 candidateOrigin 值，本次扩大可见范围的操作会直接将其略过，因为 写入本身已经成功。用户代理应当在控制台记录一条 警告，说明该条目的源列表已满。

    4. 追加 record 到 entry 的源列表中。

注： 扩大可见范围只会向源列表添加记录，或将可全局披露 设为 true。当写入方请求一个列表时，扩大已经 可全局披露的条目的可见范围，与扩大尚不可全局披露的条目的可见范围 方式相同，因为这两个范围相互 独立：新列出的源会获得不依赖于 PHL 的访问权限，同时 全局范围仍然有效。

注： 任何站点，包括最初 存储方以外的站点，都可以扩大条目的 源列表，前提是 它也提供了字节，且这些字节计算出的哈希值等于条目的哈希值。这是有意为之的： 只要站点已经持有与哈希值对应的正确字节，根据内容寻址的定义， 它就与最初存储方一样，能够确定该哈希值所指的内容。

3.5.1. 用户激活条件

COS 用户 激活条件使写入操作的全局范围暂不生效，直到用户 与执行该写入的站点的某个页面发生交互。执行写入的页面可以立即 通过其存储源记录读取该条目。同站的源以及 显式 源列表中的源（该列表由 写入方通过其 Cross-Origin-Storage-Allow-Origin 标头授权）也可以立即 读取该条目。

每个站点都有一组待全局披露的条目，它是一个集合，其中的元素为 COS 条目，初始 为空。

每当用户代理运行 激活 通知，且目标为 Window window [HTML] 时，它必须 将以下步骤排入跨源存储 队列：

  1. 令 partition 为如下 COS 分区，即 window 的相关设置对象所属的分区。

  2. 对于每个 entry，取自 partition 的待全局披露的 条目，将 entry 的 可全局披露设为 true。

  3. 清空 partition 的待全局披露的条目。

注： 如果其他站点在弹出窗口中打开一个页面，而该窗口 在几秒内关闭，或者该页面在一连串重新加载中 被反复加载，那么该页面始终不会获得用户激活状态，因此它写入的文件对其他站点保持不可见。只有 当用户实际与该站点的某个页面交互时，写入的内容才变为可全局披露，无论交互发生在 本次访问还是以后的访问中。条目被逐出时，也会从每个 待全局披露的 条目集合中移除。

全局对象 global 具有 COS 用户激活状态的条件是： global 是一个 Window 对象， 且具有粘性激活状态；或者 global 是一个 DedicatedWorkerGlobalScope 对象，且至少有一个 所有者的相关全局对象具有 COS 用户激活状态。

注： 专用工作线程代表拥有它的页面执行操作， 因此沿用这些页面的激活状态，就像它 在检查跨源存储权限时沿用它们的策略一样。共享 工作线程的所有者则会加入或 离开，因此其全局范围的写入要等待同一顶层 站点的某个页面发生下一次用户激活才会生效。

3.5.2. 最初存储方的访问权限

如果某个源已成功完成写入一个 COS 条目的操作（也 就是说，该源是某条记录的源，而该记录位于条目的存储源中），则该源 始终 可以在之后取得该条目的句柄，方法是调用 getFileHandle()， 调用时须处于 同一顶层站点下。这与该条目的源项取何值无关，也与 其哈希值是否位于 PHL 中无关。这与 Cache API 的模型一致。在该模型中， 源始终可以访问自己存储的内容，而存储分区机制同样以顶层站点作为 Cache API 的键。在任何其他顶层站点下，该源读取条目的方式与 其他源相同。

4. 跨源存储文件系统

跨源存储文件系统是一个文件系统根，区别于任何 源的存储桶文件系统或本地文件系统访问根，其中的 条目与COS 注册表中的COS 条目一一对应。

跨源存储文件系统不采用 [FS] 中通常使用的逐次调用 权限检查 模型：每个 FileSystemFileHandle 从该文件系统取得时都已经过完整授权，授权由 § 3.2 读取文件或§ 3.3 创建和 写入文件在将句柄返回给脚本之前完成，因此调用 getFile() 或 createWritable() 时，只要使用的是这种句柄， 就绝不会触发额外的权限提示。

因此，在这种句柄上调用 queryPermission() 和 requestPermission() 时，绝不能 报告 "prompt"，因为不会出现提示。对于写入模式，这两个方法必须报告 "denied"，如果相应的 句柄 并非通过创建请求取得；而 "granted" 则是 其余情况下必须报告的值。

createWritable() 在以下 FileSystemFileHandle 上被调用时，如果该句柄指向 跨源存储文件系统，却并非 取得自 创建请求，则必须以 "NotAllowedError" DOMException 拒绝， 且不得创建 FileSystemWritableFileStream。

注： 写入是句柄确实可能 缺少的唯一能力。只有创建请求才能生成 可用于写入的句柄，因此，对任何其他句柄的写入模式报告 "granted" 就等于声称具备一项 createWritable() 会拒绝提供的能力。读取权限始终为 "granted"，因为持有可读句柄的调用方可以通过它读取。请求权限无法 改变 这两种结果，因为既没有可显示的提示，也没有可用于记录权限的状态。

调用 getFile() 时，若所用的 FileSystemFileHandle 指向 跨源存储文件系统，且其可读取为 false，则必须拒绝， 拒绝原因为 "NotAllowedError" DOMException。 这涵盖两种不同的情况：

  • 句柄来自创建请求，尚未有任何数据 通过该句柄 写入，且其指向的哈希值在COS 注册表中没有条目。此时没有经过验证的字节可供 返回，而且绝不能让调用方把自己尚未完成的写入当作 文件的实际内容来观察。

  • 句柄来自创建请求，而请求所针对的哈希值已由某个其他源写入。 已验证的 字节确实存在，但此调用方既未提供这些字节，也未通过 可用性控制，因此它不得获知该条目的任何信息， 甚至不能知道 该条目是否存在。

注： 两种情况下的拒绝完全相同，因此 不会披露任何信息。这也解释了为何 "NotAllowedError" 在这里是安全的，尽管读取路径刻意避免使用它：此句柄 归调用方自己所有，通过它自己的创建请求取得，而句柄无法在任何 其他源中反序列化（见§ 4.1 传递句柄）。因此，该结果 绝不会跨越源边界，而且 不随注册表的内容变化。对照§ 8.3 进行中的写入，在那种情况下， 读取路径上可区分的错误确实会跨越这一边界。

一旦句柄的可读取为 true，getFile() 在该句柄上被调用时就会返回一个 File， 其内容是所指向条目的字节。这 正是 [FS] 已经为这类文件 条目定义的行为，即其 二进制数据就是这些字节。

一个 FileSystemFileHandle 若指向跨源存储文件系统，便具有一个 文件系统定位器，其路径是一个列表，其中包含 单个 字符串，即该句柄的COS 哈希值的值，而定位器的 根 是跨源存储文件系统。

注： [FS] 将 name 定义为句柄的定位器路径中的最后一个 路径分量，因此这也确定了 name： 它就是 哈希值。条目没有自己的名称，哈希值是它唯一的标识，因此 报告该值可以传达使用空字符串便会丢失的信息。

条目既没有名称，也没有所在目录，因此 [FS] 中大多数涉及文件系统结构的操作 都没有作用对象。标识是个例外，按内容寻址的条目总能判断 标识是否相同：COS 注册表至多保存一个 COS 条目与每个 COS 哈希值对应，因此两个 句柄指向同一条目，当且仅当它们的哈希值相等。

isSameEntry() 在一个 FileSystemFileHandle 上被调用时，若该句柄指向 跨源存储文件系统，且传入的实参 也指向该文件系统，并且两者均由 同一个源取得，则必须返回 true，如果两个句柄的 COS 哈希值相等；否则必须返回 false。

注： 拒绝这种比较会丢弃用户 代理已经掌握的信息。

isSameEntry() 在一个 FileSystemFileHandle 上被调用时，若该句柄指向 跨源存储文件系统，而传入的实参 并非由调用源取得，或者 该实参指向的文件系统并非跨源存储文件系统，则必须拒绝， 拒绝原因为 "NotAllowedError" DOMException。 对于指向其他文件系统的句柄，例如 由 getDirectory() 返回的句柄，仍保留 [FS] 为其定义的调用行为，即使传入的 FileSystemFileHandle 实参指向跨源存储文件系统，也是如此。

注： 在这种情况下返回 false 就是断言 两个句柄指向不同的条目， 这等于对调用源无权检查的句柄作出判断。拒绝仅表示 无法进行比较。

调用 move() 和 remove() 时，若所用的 FileSystemFileHandle 指向跨源存储文件系统，则必须以 "NotAllowedError" DOMException 拒绝， 且必须使所指向的任何条目保持不变。

注： 一个条目由其存储 源中的所有源共享，因此，若执行 移除操作，一个站点就能销毁其他站点赖以运行的数据。删除应由 逐出机制和用户自己的存储控件处理。重命名或更改父目录都没有 作用对象，因为条目以其 COS 哈希值命名，并且没有所在目录。

注： 截至撰写本文时，[FS] 和文件系统 访问 API 都未定义这两个方法 （WICG/file-system-access#214）， 因此错误名称沿用了 removeEntry()， 这是 [FS] 明确 为删除条目定义的操作：如果未获授读写访问权限，它会以访问结果的错误名称 拒绝。在这里，拒绝准确反映了实际情况：这些操作有明确定义的含义，但被 禁止执行。

createSyncAccessHandle() 在这里无需单独规定：其步骤会以 "InvalidStateError" DOMException 拒绝，只要句柄不在存储桶文件系统中， 而跨源存储文件系统是一个文件系统根，区别于任何源的文件系统根， 因此 [FS] 已经确定了 应当拒绝以及拒绝时使用的错误名称。

注： 即使单独考虑本规范，这也是 所期望的结果。一个 FileSystemSyncAccessHandle 会将可写的文件描述符交给调用方，使其能够 更改条目的字节， 却不改变这些字节所对应的 COS 哈希值， 而这些字节正是以该值为键存储的， 并且可获披露该条目的每个其他源读取的都是同一份字节。

4.1. 传递句柄

一个 FileSystemFileHandle 是一个可序列化对象 [FS]，因此，指向 COS 条目的句柄可以传给另一个环境设置对象，例如通过 postMessage(message, options)。 这是取得这种句柄的另一种途径，与 getFileHandle() 并列， 因此本节也对其作出限制。

以下序列化步骤适用于 FileSystemFileHandle， 若它指向 跨源存储文件系统，则给定 value 和 serialized，还要执行以下步骤：

  1. 将 serialized.[[COSHash]] 设为 value 的 COS 哈希值。

  2. 将 serialized.[[COSOrigin]] 设为 value 的 COS 源。

  3. 将 serialized.[[COSMayRead]] 设为 value 的可读取。

在反序列化步骤中，给定 serialized、 value 和 realm，还要执行以下步骤：

  1. 如果 serialized.[[COSOrigin]] 不与以下源同源，即 realm 的 环境设置对象的源，则抛出 "DataCloneError" DOMException。

  2. 将 value 的 COS 哈希值设为 serialized.[[COSHash]]。

  3. 将 value 的 COS 源设为 serialized.[[COSOrigin]]。

  4. 将 value 的可读取设为 serialized.[[COSMayRead]]。

注： 如果没有同 源检查，传递句柄就会使 本规范中的所有披露控制同时失效。一个句柄的可读取为 true，意味着 它已经 通过了应用可用性控制的检查，而该检查只针对请求该句柄的 源；将它发送给另一个 源，就会直接交给该源条目的字节，而不会为它评估源、 是否在 PHL 上，也不会对它应用 GREASE 机制。这 与《文件系统标准》对句柄的现有处理一致：其中的句柄同样只有 对同源接收方才有用。

注： 可读取随 句柄一同传递，因此，通过创建请求取得且尚未用于写入的句柄，在 传递后仍不可读， 而通过读取请求取得的句柄仍然可读，无需再次接受可用性控制。若接收时再次执行检查， 调用方就能通过反复传递同一个 句柄来探测可用性。

注： 如果在原始句柄用于写入之前克隆了它， 克隆得到的句柄将一直不可读。持有者可以 调用 getFileHandle()， 不指定 create， 从而取得可读句柄，所凭借的是 最初存储方的访问权限。

5. 存储管理

5.1. 存储限制

用户代理必须限制单个源可以向 COS 注册表通过成功写入存储的字节总数，以 防止单个源 填满缓存，试图逐出其他源的条目。具体限制 由实现定义。

要检查 COS 存储限制，给定一个 COS 条目或 null entry、一个源 origin 和一个非负整数 length，返回一个布尔值：

  1. 如果 entry 不为 null，且其存储源包含一条 COS 共享 记录，该记录的源为 origin，则返回 true。

    注： 条目是可按内容寻址的，因此 写入此源已存储的字节不会增加 该源持有的数据量。

  2. 令 held 为以下长度之和：计算字节长度时，计入每个 COS 条目，条件是该条目位于 COS 注册表中，并且其 存储源包含一条 COS 共享 记录，该记录的源为 origin。

  3. 如果 held 加上 length 超过 origin 的存储限制，则将一条 警告记录到控制台，并 返回 false。

  4. 返回 true。

存储限制约束的是单个源在任一时刻持有的数据量，因此，一个页面引入多少个源， 就能得到多少份额度。用户代理因此还必须维护一个 COS 写入限制，针对每个 站点，统计以该站点为 COS 分区的所有写入，无论由哪个源或 框架发起。该限制有由实现定义的最大写入次数和最大 字节 数，均以由实现定义的时间窗口为单位，并按相同条件持久保存和重置， 这些条件 与跨站查询预算相同。

要将一次 COS 写入计入额度，给定一个 COS 条目或 null entry、一个源 origin、一个 站点 partition 和一个非负整数 length，返回 一个布尔值：

  1. 如果 entry 不为 null，且其存储源包含一条 COS 共享 记录，该记录的源为 origin，且其 分区为 partition，则返回 true。

    注： 如果此源已在当前顶级站点下存储了这些字节， 再次写入不会增加存储量，因此 不消耗额度，这与按源计算的存储限制相同。这项豁免仅取决于此 源自己先前的写入，因此不会披露其他源存储了什么。

  2. 如果再写入一次或再增加 length 个字节就会超出 partition 的 COS 写入 限制，其中额度按 当前窗口计算，则将一条警告记录到控制台并返回 false。

  3. 将一次写入和 length 个字节计入 partition 的 COS 写入 限制。

  4. 返回 true。

注： 字节一经验证，写入就计入额度；消耗的额度相同，无论另一个 源是否已经存储了该哈希值， 也无论此源是否已在另一个顶级站点下存储了它，因此，该限制不会泄露 其他站点存储了什么。两种额度分别约束不同的使用方式：一个站点存储 一个 大型 AI 模型会消耗字节额度，却几乎不消耗次数额度；而跟踪器若存储数十个微小的 标记文件来编码标识符，则会立即耗尽次数额度。

用户代理还有一个由实现定义的源列表最大长度，它是一个 正整数，限定了源的数量，即单个源列表最多可以 包含多少个源。该限制既在列表首次提供时执行（见验证 COS 请求）， 也在随后将列表合并到已有条目时执行（见 扩大资源的可见范围），因此，无论是单次调用， 还是多次调用随时间积累的效果，都不能让条目的源无限 增长。除了限制内存用量，这还可以防止列表中的源被用作 一种 未声明的 "*" 替代形式；见§ 8.2 跨站探测。

上述两处对超出限制的情况采取不同的处理方式，因为这两处调用 发生在操作的不同阶段：

  • 在验证 COS 请求时，会先检查限制，之后才会对任何 文件进行获取、哈希计算或 写入。超出限制的调用方会立即收到 "TypeError"， 且不会再执行任何操作， 这与任何其他格式错误的 origins 值的处理方式相同。

  • 在扩大资源的可见范围时，只有累积起来才可能 达到该限制：所累积的是 多次独立写入调用所请求的源，这些调用可能来自互不相关的源，时间跨度也可能 很长。此项检查只在本次调用的字节已经过哈希计算、 验证并持久存储之后进行。此时拒绝写入，将会丢弃一次已成功、 已验证且数据量可能很大的写入，仅仅因为触及了一项无关的记录数量限制，而且 甚至无法将其归咎于某个调用方的失误。因此，写入仍然 成功，仅从源中舍弃超出容量的源，同时 在控制台发出警告。这与既有的 从宽松改为更严格的请求处理方式一致：对于源请求， 如果无法完全满足，就在不向调用方报错的情况下对其设限，而携带该请求的写入仍然 成功。与本规范其他部分的§ 8.4 可用性控制一致， 在这种情况下， 调用方事后无法可靠地确认所请求的源是否 确实已被添加：后续的 getFileHandle() 调用即使由该 源发起，也仍可能失败，即便该源已被添加（例如，因为条目已被 逐出，或读取方的站点已耗尽跨站查询预算），因此不能根据调用结果 确认该源是否已被添加。

5.2. 逐出

本节为非规范性内容。

在存储空间紧张时，用户代理可以逐出条目，将其从 COS 注册表中移除， 例如采用最近最少使用策略，考虑各个存储源中 最近一次访问每个条目的时间。用户代理应提供设置界面，使 用户可以查看存储了哪些文件、哪些源访问过各个文件，并可手动 删除条目或清除所有跨源存储数据。

当用户清除某个源的站点数据时，用户代理应移除所有符合以下条件的共享记录：其 源为该源；应从每个存储源集合中移除这些记录。如果 移除后，某个 COS 条目的 存储 源为空，则用户代理可以考虑删除该条目。

5.3. 派生产物

用户代理可以保留派生产物：即根据 字节计算并保留以供复用的数据，这些字节来自一个或多个 COS 条目。 例如，已编译的 WebAssembly 模块、GPU 管线或已编译的机器学习图。派生产物具有 以下项：

来源

一个非空列表，其中的 COS 哈希值标识提供字节以计算该产物的条目。

页面选择的输入

所有其他会影响结果且脚本可以自由设置的输入，例如编译 选项、本身并非来源的代码或图结构，以及常量或算子选项。 此项可以为空。

生成方

一个集合，其元素为站点， 即用户代理计算该产物所在的 COS 分区 所对应的站点。

用户代理推导派生产物的键时，使用其来源、其 页面选择的输入，以及由实现定义的用户 代理和设备属性。用户代理不得让脚本选择或读取该键，也不得 将派生 产物的内容暴露给脚本。

派生产物必须 仅取决于其键。它不得包含从下述过程派生的数据： 执行触发该产物计算的内容。

注： 否则，优化热点代码的编译器便可能 记录生成该产物的页面运行过哪些函数， 而复用产物则会将这一执行特征披露给另一个站点。

用户代理不得复用派生产物，如果所处的 COS 分区不属于其 生成方，并且某个站点的内容可以通过 该产物的键以外的途径影响它。

注： 对于在运行某站点内容的进程中编译的代码， 该站点的内容有可能篡改它，只要这个 进程已被攻陷。在另一个顶级站点下复用这种代码，就会让一个站点能够在 另一个站点的进程中运行代码。

用户代理必须移除派生产物，只要它将该产物的任何一个 来源 从 COS 注册表中移除。当 用户清除某个站点的数据时，用户 代理应从每个生成方集合中移除该站点，并可以删除 任何其生成方因此变为空集的产物。

要确定是否复用派生产物，给定一个派生产物 artifact、一个站点 partition 和一个列表 obtained，其中的 COS 哈希值对应的字节由请求 上下文提供，这些字节读取自 COS 注册表，返回一个布尔值：

  1. 如果 artifact 的生成方包含一个 站点，该站点 同站于 partition，则返回 true。

    注： 这就是用户 代理已有的按站点缓存行为。

  2. 如果 obtained 没有包含 每一项，其中各项取自 artifact 的 来源，则返回 false。

    注： 读取时已经执行过应用可用性控制，该操作会扣减 跨站查询预算。若接受其他任何来源的字节， 页面就能在未经这两项检查的情况下，仅凭计算耗时 得知某个条目是否存在。

  3. 如果 artifact 的页面选择的输入为空，则返回 true。

  4. 如果运行将一次跨站查询计入预算，给定 partition，结果为 true，则返回 true。

  5. 返回 false。

当确定是否复用派生产物返回 false 时， 用户代理必须将该产物 重新计算，视同该产物不存在，然后将发起请求的 COS 分区添加到其 生成方中，从而使 拒绝复用与未命中无法区分。见§ 8.7 派生 产物计时。

宿主规范定义哪些输入属于来源，哪些输入由页面选择：

  • WebAssembly：使用 WebAssembly.compileStreaming() 或 WebAssembly.instantiateStreaming() 从一个 File 编译模块时，如果该文件读取自跨源存储，该模块便以相应 条目为来源。非默认的编译选项由页面选择。

  • WebGPU：从 COS 条目读取的着色器代码是来源。其他着色器代码、 可由管线覆盖的常量以及管线布局由页面选择。见 gpuweb/gpuweb#11110。

  • WebNN：从 COS 条目读取的常量是来源。图结构、算子 选项以及其他常量由页面选择。见 webmachinelearning/webnn#971。

WebGPU 和 WebNN 需要由宿主集成将输入的 COS 来源信息传递给编译器。

5.4. 手动添加的条目

本节为非规范性内容。

上述设置界面可以允许用户将磁盘上已有的文件直接添加到 跨源存储中（例如，用户自行下载、与任何网站无关的 AI 模型）， 整个过程无需任何脚本调用 getFileHandle()。 这样的条目 没有可将写入归属到的请求源，这带来了两个问题，而 命令式 API 本身无法回答：

  • 谁是最初存储方，可以适用 § 3.5.2 最初存储方的访问权限？没有任何源：条目的存储源初始为空。 因此，没有任何源可以免于 常规的可用性控制和源检查， 每个请求源原本都要接受这些检查。这一结果是正确的，因为没有任何源 实际写入这些字节。

  • 这种条目是否应该仅限同站，就像普通写入省略 origins 时那样？不应该：“同站”只有在 相对于某个请求源时才有意义，而手动添加没有请求源，因此“同站”没有可供 比较的站点。用户代理应使这种条目可全局 披露， 并将其显式源列表留空，因为手动 预置文件只有 在其他源确实能发现它的情况下，才能达到目的（使用户尚未访问的站点复用用户磁盘上 已有的文件）。用户代理的设置界面还可以 允许用户选择较窄的范围。

以这种方式添加后，该条目在其他方面无法与 网站通过以下方法写入的条目区分：getFileHandle()。 同样的 可用性控制和可见范围 扩大规则适用于该条目，与适用于具有相同共享记录的任何其他条目的规则完全一样。 其中包括是否在 PHL 上的检查， 只要该条目最终 可全局披露，就要执行该检查，而这正是手动添加的默认状态。

5.5. 来源元数据

本节为非规范性内容。

COS 条目特意不记录 其字节来自何处。条目的唯一标识是 哈希值：相同的字节 就是同一条目，无论有多少个源存储过 它们，也无论它们是从多少个 URL 获取的（见§ 2.2 COS 条目）。URL 是某一次 写入方的 获取操作的属性，因此，对于一个由多个源写入的条目， 选取任何一个 URL 都难免武断。URL 无法像字节那样进行验证（见§ 8.1 资源完整性）， 而且，相比粒度较粗的源值，也就是 存储 源中的值，URL 会透露更多用户浏览信息，因为路径或查询字符串可以指明特定的文档、 账户或会话。将其记录在条目上，会使一个高熵信号绕过 披露限制，而源和§ 8.4 可用性 控制正是用来实施这些限制的。

不过，了解来源确实有实际用途：用户可能正在 § 5.2 逐出所述的设置界面中查看一个数 GB 的文件，而开发者可能正在排查一次 getFileHandle() 调用未命中的原因，两者都希望知道文件 来自何处。为此，用户代理可以保留一份仅供实现内部使用的来源记录， 将其与条目一同保存（例如，记录各个存储源获取 这些 字节时使用的 URL 及获取时间），前提是将该记录视为保存在 条目之外的用户代理状态：

  • 记录绝不向脚本暴露。本规范中的任何机制都不会披露它，今后新增的机制 也不应披露它：无论是 getFileHandle()， 还是它返回的 FileSystemFileHandle， 都不应透露这种记录是否存在，更不应透露记录的 内容。特别是，请求源绝不能观察到并非由它 自己产生的记录。

  • 记录只能通过可信的非 Web 界面提供：用户代理自身的设置和存储 检查界面、开发者工具，以及（如果用户代理拥有扩展平台） 需要用户明确授予权限才可使用的扩展 API，其权限要求与其他 暴露浏览历史记录的 API 相同。有关 浏览器扩展集成点说明，请参阅本 代码库 中正在考虑的扩展接口。

  • 记录未经验证，呈现时也要明确这一点。其中的 URL 是写入 这些字节的源所作的声明。只有哈希值才能保证内容一致（见§ 8.1 资源完整性）。两个源可能为同一条目记录不同的 URL， 而其中任何一个 都可能不准确，也可能有意误导。

  • 记录的生命周期取决于条目及记录所归属的源。它会在 条目被逐出或删除时丢弃；归属于某个源的部分则在 该源的共享记录从存储源中移除时丢弃， 包括用户清除该 源的站点数据的情况（见§ 5.2 逐出）。

由于这种记录对内容不可见，用户代理是否保留记录，以及保留 多少信息，完全由实现决定。本规范中的任何行为都不依赖这种记录，站点也无法 检测它是否存在。

6. 与权限策略集成

本规范定义了一个受策略控制的特性 [permissions-policy]，由 字符串 "cross-origin-storage" 标识。其默认允许列表 为 self。按照工作线程权限策略 [WORKERS-PERMISSIONS-POLICY] 的规定，该特性 无法在服务工作线程中启用。

本节依赖 工作线程权限策略 [WORKERS-PERMISSIONS-POLICY]，如同 它已经是 [permissions-policy] 和 [HTML] 的一部分。该提案仍是一份说明文档，目前 尚无规范定义本节提及的工作线程策略、SharedWorker 的 allow 选项，或“可在服务工作线程中 启用”这一布尔值。 截至撰写本文时，Chromium 已实现共享工作线程部分，但需要启用功能标志 （PermissionsPolicyForSharedWorkers），且尚无引擎默认提供该功能。待这项工作纳入规范后，本 节应调用其中的钩子，无需再自行描述这些钩子。

[permissions-policy] 定义的允许使用以 Document 为对象， 但 CrossOriginStorageManager 也暴露在 WorkerGlobalScope 上， 而后者没有 Document 归其自身所有。因此，这里的检查以发起调用的全局对象为对象， 遵循 [WORKERS-PERMISSIONS-POLICY]：专用 工作线程继承下列对象的策略，即 Document 中直接或间接拥有它的那些对象；共享工作线程有自己的策略；服务 工作线程则绝不能启用此特性。

要检查跨源存储权限，给定一个全局对象 global，返回一个 布尔值：

  1. 如果 global 是一个 Window 对象，则：

    1. 令 document 为 global 的关联 Document。

    2. 如果 document 为 null，则返回 false。

    3. 如果 document 不被允许使用 "cross-origin-storage" 这一受策略控制的特性， 则返回 false。

    4. 返回 true。

  2. 如果 global 是一个 DedicatedWorkerGlobalScope 对象，则：

    1. 令 owners 为 global 的所有者集合。

    2. 如果 owners 为 空，则返回 false。

    3. 对于每个 owner（属于 owners）：

      1. 如果 owner 是一个 Document， 且 owner 不被允许使用 "cross-origin-storage" 这一受策略控制的特性， 则返回 false。

      2. 如果 owner 是一个 WorkerGlobalScope 对象，且运行 检查跨源 存储权限时，给定 owner 的结果为 false，则返回 false。

    4. 返回 true。

  3. 如果 global 是一个 SharedWorkerGlobalScope 对象，则在以下条件成立时返回 true： "cross-origin-storage" 已在 global 的权限 策略中启用 [WORKERS-PERMISSIONS-POLICY]；否则 返回 false。

    注： 该策略仅包含创建方 通过 allow 成员委派的特性，该成员属于 SharedWorker 构造函数的选项，同时还要排除工作线程脚本本身的 Permissions-Policy 响应标头禁用的特性。无法委派 这些 特性的上下文，例如自身策略禁用了跨源存储的上下文，将无法连接， 因此，该策略在工作线程运行期间不会改变。

  4. 返回 false。

    注： 这涵盖 ServiceWorkerGlobalScope， 在其中 "cross-origin-storage" 无法启用 [WORKERS-PERMISSIONS-POLICY]。

对于一个全局对象，如果本算法对其返回 false，那么每次 getFileHandle() 调用只要从该对象发起，就会以 "NotAllowedError" DOMException 拒绝， 此时尚未进行任何哈希值验证、注册表查询或写入 操作。

注： 通过所有者集合确定权限，才能确保禁用该特性 确实有效。通过 blob: URL 创建的工作线程在创建它的页面的 源中运行，且与该页面共享完全相同的跨源存储视图（见 § 3 CrossOriginStorageManager 接口），因此，如果 检查只查看全局对象自身的 Document， 那么每个工作线程都会因没有文档需要检查而自动通过，将调用移入 new Worker(URL.createObjectURL(&hellip;)) 就能绕过 cross-origin-storage=() 策略， 而无需对调用作任何其他改动。

注： 服务工作线程不能使用跨源存储， 因为 "cross-origin-storage" 不属于可以在 服务工作线程中启用的特性 [WORKERS-PERMISSIONS-POLICY]。这是 每个受策略控制的 特性的默认行为，跨源存储沿用了这一默认行为。服务工作线程的注册会持久保存，用户 代理在响应事件时启动它，而一个运行中的服务工作线程可为多个客户端提供服务，这些客户端的 策略未必一致，因此不存在一个可供统一查询策略的 Document 对象。该 API 仍然在此处暴露，因此调用会以 "NotAllowedError" 拒绝， 就像此 算法拒绝的其他调用一样。另见 explainers-by-googlers/workers-permissions-policy#4。

注： 一个 SharedWorkerGlobalScope 的 所有者集合可以包含多个 Document， 它们的策略可能各不相同，且工作线程在其生命周期内会增加和失去所有者。 查询工作线程自身的策略（该策略在创建时即已确定），可以确保结果 在两次 getFileHandle() 调用之间保持稳定。也无法借此 绕过禁用决定：如果文档的策略禁用了跨源存储，该文档就无法委派 此特性，因此既无法创建具有该特性的共享工作线程，也无法连接到这样的线程。

7. Cross-Origin-Storage-Allow-Origin 标头

一个 COS 条目，如果其源列表 非空，就可以向不受写入源控制的其他源披露， 然而这个列表由脚本声明（通过 origins） 或由标记声明，而攻击者只要 成功注入脚本或标记，就能设置其中任意一种。为了以注入内容无法伪造的形式，将此声明与 被披露字节所属源的运营方关联起来，本 规范定义了一个响应标头，用来限制此类声明可以指定哪些源。

Cross-Origin-Storage-Allow-Origin 响应标头携带一个 COS 范围上限，即一个 集合， 其中的源可由写入操作指定在不限于同站的 源列表中。谁 提供字节，谁就发送标头，因此标头读取自 被披露字节所对应的响应：

  • 对于 getFileHandle() 写入，由于字节可能是在 脚本中生成的，没有自己的原始响应，因此这里所指的是这样一个响应：它用于 创建发起调用的全局对象的 Document； 对于工作线程，则是创建相应 Document 的响应，该文档直接或通过其他工作线程创建了当前工作线程（见 获取 COS 范围上限）。

  • 对于宿主集成，这里所指的响应来自已获取的资源，所存储的字节正是该资源的字节 （见将已获取的资源存入 跨源存储）。该响应由资源的服务器提供，而该服务器 未必就是提供相应 Document 的服务器，此文档负责加载该资源。

声明的列表要与上限 取交集（见 应用 COS 范围上限），因此，上限只可能缩小声明的范围。

注： 该标头代表字节 提供方的授权。它指定的源 是最终读取方，既不会被征询，也不发送任何内容：列出的源只有在之后 调用 getFileHandle() 请求相应的 COS 哈希值时才会参与，这与其他 读取方相同。这与 Access-Control-Allow-Origin [FETCH] 的方向相反：后者由 持有资源的服务器明确允许给定的源读取该资源。这里则由字节的提供方 限定稍后谁可以从跨源存储读取这些字节，而注入写入 页面的内容无法扩大该范围，因为它无法设置提供方的响应标头。

注： 该标头仅适用于列表形式。 默认的同站范围不指定任何跨源 接收方，因而无需授权；"*" 形式则在读取路径上受到 可用性控制，检查依据是公共哈希值列表，而 每个用户独有的秘密绝无可能通过该检查，因此这种形式同样不需要写入时的上限。若要求 "*" 必须配有标头，还会破坏零配置的全局共享用例，却不能填补任何 公共哈希值列表尚未堵住的缺口。

要解析 COS 范围上限，给定一个标头 列表 headers，返回一个集合，其元素为 源：

  1. 令 value 为执行获取、解码并拆分的结果， 目标是 headers 中的 "Cross-Origin-Storage-Allow-Origin"。

  2. 如果 value 为 null，则返回一个空集合。

  3. 令 ceiling 为一个空集合。

  4. 对于每个 token（属于 value）：

    1. 去除首尾的 ASCII 空白，操作对象为 token。

    2. 如果 token 为空字符串，则继续。

    3. 令 url 为运行基本 URL 解析器解析 token 的结果。

    4. 如果 url 为失败，或 url 的方案既不是 "http" 也不是 "https"，或 url 的源不是潜在可信源， 则返回一个空集合。

      注： 这包括 token 为 "*" 的情况，该值无法解析为源。 Cross-Origin-Storage-Allow-Origin 标头只能枚举有限数量的 具体 源；不允许使用 "*"，因为将上限设为“任意源” 会让 注入的内容能够随意声明接收方，从而使该标头完全失去 作用。 不限范围的 披露只能通过 "*" 源形式实现，这种形式 受到 公共哈希值列表控制，并且从不查询此 标头。格式错误或含有 "*" 的标头 与缺少标头一样，不授予任何权限；失败时默认拒绝授权。

    5. 追加 url 的源到 ceiling。

  5. 返回 ceiling。

注： 获取、解码并拆分以 U+002C (,) 为分隔符， 因此标头 值中的源以逗号分隔，这与 Timing-Allow-Origin [RESOURCE-TIMING] 一致，也符合 以下通用约定： 取列表值的 HTTP 响应标头使用逗号分隔，而与之对应的 crossoriginstorage HTML 内容 属性则使用空格分隔，以匹配其宿主语法。两者最终都解析为同一个 源集合。

要获取 COS 范围上限，给定一个全局对象 global，返回一个集合，其元素为 源：

  1. 如果 global 是一个 Window 对象，则：

    1. 令 document 为 global 的关联 Document。

    2. 如果 document 为 null，则返回一个空集合。

    3. 返回 document 的 COS 范围上限。

  2. 如果 global 是一个 WorkerGlobalScope 对象，则返回 global 的 COS 范围上限。

  3. 返回一个空集合。

要应用 COS 范围上限，给定一个列表，其元素为源，记为 requestedOrigins，以及一个 集合， 其元素为源，记为 ceiling，返回一个列表，其元素为源，或者返回 null：

  1. 移除 requestedOrigins 中的每个源，条件是 ceiling 不 包含该源。

    注： 未列入 COS 范围 上限的接收方会被舍弃，而写入仍然 成功；这与扩大可见范围时舍弃超长列表中多余部分的做法一致，见 扩大资源的可见范围。用户代理 应在控制台记录警告，指明 每个被舍弃的源。

  2. 如果 requestedOrigins 为 空，则返回 null。

    注： 如果一个列表的所有 成员都被舍弃，此次写入就没有任何已获授权的 跨源接收方，因此会回退到默认的同站范围。字节仍会 存储，只是不进行未经授权的披露。

  3. 返回 requestedOrigins。

每个 Document 都有一个 COS 范围上限，它是一个集合，其元素为源， 在创建文档时设为运行解析 COS 范围上限的结果， 传入的 标头列表取自相应的响应，该响应用于 创建此文档。

每个 WorkerGlobalScope 都有一个 COS 范围上限，它是一个 集合， 其元素为源。在创建工作线程时，运行 工作线程将它设为 运行获取 COS 范围上限的结果，传入的全局对象 属于 outside settings，即传给运行 工作线程的外部设置。对于专用工作线程， 这是构造它的全局对象。对于共享工作线程，则是通过 SharedWorker 构造函数调用创建该工作线程的全局对象；之后连接到 正在运行的工作线程的上下文不会改变其上限。

注： 工作线程采用其创建方的上限，绝不会 从其自身脚本的响应中取得上限。 blob: 工作线程与创建它的页面共享完全相同的源和跨源存储视图 （见§ 3 CrossOriginStorageManager 接口）， 而它的响应不含标头，因此， 如果从工作线程自身读取上限，则每个 blob: 工作线程的上限都会为空；将一次 范围由列表指定的写入移入 new Worker(URL.createObjectURL(&hellip;))，就会移除 该 页面已授权的接收方。在创建时固定上限与检查 跨源存储权限的做法一致：共享工作线程的策略只包含其创建方 已委派的特性，结果 在两次 getFileHandle() 调用之间始终相同，不论各上下文 如何连接和断开。每个能够连接到共享工作线程的上下文都具有该工作线程的 源，所以，即使后来连接的上下文上限较窄，运行它的 仍是当初授权 创建方上限的同一个运营方。

要填充 Document 的 COS 范围上限，并从其响应中取得该值， 需要 在 [HTML] 的文档 创建步骤中设置钩子，就像 [permissions-policy] 和 [CSP] 那样， 在处理响应时填充。在有这样的钩子之前，本节直接描述 所需行为；预计在今后的修订中正式集成它，同时集成 [FS] 的钩子，见§ 3.3 创建和写入文件。一个 WorkerGlobalScope 的 COS 范围上限需要同类钩子，位置在 运行工作线程中。宿主集成无需这种钩子： 它们将获取的响应传给将已获取的资源存入跨源 存储，该算法会从响应中读取 上限。

8. 隐私和安全注意事项

除使用 RFC 2119 关键词的内容外，本节为非规范性内容；另见 安全与隐私调查问卷，位于本 代码库中。

代码库中的隐私分析描述了这些注意事项所针对的攻击， 以及每项缓解措施能够在多大程度上防范这些攻击。

8.1. 资源完整性

每个 COS 条目都以密码学哈希值为键，其 字节也依据该哈希值进行验证（见 § 3.3 创建和写入文件）。因此，站点可以确信， 它通过 getFileHandle() 取得的文件所含字节与它自行 获取 hash 所得的字节完全相同。开发者无法枚举跨源存储的内容，也无法在 事先不知道文件哈希值的情况下访问文件。

COS 哈希值并非秘密。它是一个 内容标识符，任何已经持有文件的人都可以 轻易计算。对于本规范所针对的广泛分发的 资源，这类哈希值通常是公开信息，往往随模型或库的 版本一同发布。因此，知道哈希值就足以查询条目，但这本身并不授予访问权限： 查询是否成功完全取决于源和 § 8.4 可用性控制。开发者不得把未公布的哈希值 当作访问控制机制；对特定文件感兴趣的 攻击者不需要猜测其哈希值，只需要取得文件 本身（见§ 8.2 跨站探测）。

8.2. 跨站探测

如果只有少数站点使用某个资源，攻击者一旦得知该资源 存在于跨源存储中，就能推断用户很可能访问过其中一个站点。由于 getFileHandle() 是获知资源是否存在的机制，因此每次调用 实际上都是一次探测。本规范通过三种机制限制探测所能获知的信息：

  • 源（见 § 3.5 扩大资源的可见范围）允许存储 源将 披露范围限制为一组选定的源，以及与它们同站的源，因此，专有或使用率较低的资源 完全无需 向全球开放探测。

  • § 8.4 可用性控制还会阻止披露 以 "*" 为范围的资源，如果 请求源不属于其存储源，除非哈希值在 PHL 上， 因此，存储资源时使用 origins: "*" 并不会 自动让 Web 上的每个源都能探测该资源。此项控制只适用于 "*" 范围的 条目；对于列表范围和同站范围的条目，第一项所述的限制是唯一的 控制，因为存储源已经为这些条目明确限定了披露范围。

  • 跨站查询预算限制了一个 顶级站点在每个 查询窗口内能够进行的探测次数，因此 即使每个文件单独来看都很常见，也无法任意测试它们的组合。

第一项限制只有在“选定的一组源”确实比整个 Web 小得多时才有效。 单凭 origins 的形式，无法阻止调用方 枚举数量极大的源（例如，根据公开的热门站点排名整理出一份 列表），这样在效果上将接近全局披露，却绕过了 只有 "*" 才要求的、有意且明确的选择。源列表最大 长度（见 § 5.1 存储限制）对此加以约束：上限应足以容纳实际存在的 多站点使用场景 （由同一方控制的少数相关源），却远不足以在任何实际意义上接近 “所有源”。这样就能防止受限的源形式被用作 未声明的 "*" 替代形式。

注： 由§ 9 与其他规范集成所述的任一宿主集成执行的查询 同样是一次探测，即使它不会向页面报告错误：站点可以观察自己的 服务器是否收到了回退请求，这与 "NotFoundError" 携带的是同一比特的信息。同样的控制 也适用于这种查询，且跨站查询预算会将它与 getFileHandle() 调用一并计数，因为可由脚本驱动的集成同样可以轻易地 循环发起查询。

8.3. 进行中的写入

对于每个源，已请求但尚未完成的写入必须无法与 从未写入过的哈希值区分。本规范通过结构设计来保证这一点： COS 条目只会被添加到 COS 注册表中，执行添加的操作仅限于验证并存储或 将已获取的资源存入跨源 存储，而且在这两种情况下，都必须先用哈希值验证全部字节， 才会添加条目。完成创建请求既不读取也不写入 注册表。因此， 不存在读取时可观察的占位状态，读取路径上也没有任何分支能够 早于应用可用性控制给出结果。

另一种做法是在发起创建请求时注册一个占位条目，并以可区分的错误拒绝并发的 读取请求。这样，调用方就会得知某个源此刻正在写入 给定的哈希值。这个比特看似无关紧要，实际影响却很大。这一信息将：

  • 对任何源可知，包括对条目没有任何访问权限的源，因为占位条目不带 任何共享记录，而且读取请求会在应用可用性 控制运行之前得到答复；

  • 适用于任何哈希值，包括不在 PHL 上且永远不可能列入其中的哈希值，因此攻击者可能 使用根据每个用户独有的值派生的哈希值（见§ 8.8 指纹识别）；

  • 不经过 GREASE 机制，因为它只适用于到达可用性控制 步骤的披露， 所以这一比特将不含噪声；

  • 无需提供任何字节，因此，无论是按源计算的存储限制、 每个站点的 COS 写入限制， 还是§ 5.2 逐出，都无法限制一个源能够创建多少这样的比特。

因此，嵌入两个站点的跟踪器就可能在第一个站点上生成任意位数的标识符， 并在第二个站点上将其读回，而不消耗存储空间，同时绕过源、 公共哈希值 列表和 GREASE 机制。占位条目还可能成为拒绝服务攻击的 途径：占住某个确实广受使用的资源的哈希值，就会阻止所有其他源读取 该资源，直至占位条目消失。

注： 这种设计的代价是，一个调用方无法 发现另一个调用方已经在下载 某个大文件，因而无法据此避免重复下载。这确实是一项代价，也是 本规范的早期草案曾在此处使用可区分错误的原因。在最重要的场景下， 即在同一个源内，仍可借助以下机制实现这一能力： Web 锁、BroadcastChannel 或共享工作线程， 这些机制都不会 跨越源边界披露任何信息。跨源时可节省的开销多半只存在于理论上：两个互不相关的 源必须在同一时刻争用同一个哈希值，而且，如果两者都还没有写入该条目， 那么无论如何，都不能向另一方披露它，除非它已在 PHL 上。

注： "NotAllowedError" 仍是调用 getFile() 时得到的响应，如果所用的是 通过创建请求取得且尚未用于写入的句柄（见§ 4 跨源存储文件系统）。这一结果 不随注册表的内容而变化，并且只会返回给发出请求的源，因为 句柄无法跨源反序列化（见§ 4.1 传递 句柄），因此不会形成信息通道。

8.4. 可用性控制

一次 getFileHandle() 读取，如果发起它的源不属于 存储 源，其能否成功始终取决于请求源是否 获准读取该条目，而这由源决定。对于 "*" 范围的条目，还需要考虑第二个 独立的问题：用户代理是否愿意披露该条目 确实存在，而这取决于PHL 收录情况和 GREASE 机制。这两项条件必须 同时满足才能读取这类条目；对于列表范围或同站范围的条目，则只需考虑第一个问题。 规范性算法见§ 3.2 读取文件。因此，"NotFoundError" 并不能 证明资源不存在：它可能意味着资源不存在、请求 源不在范围内、"*" 范围资源的哈希值尚未（或永远不会）列入 PHL， 或者 资源仍在等待满足 COS 用户激活条件，或者发出请求的顶级站点 已 用尽其跨站查询预算，又或者 GREASE 机制抑制了一次 真阳性结果。开发者不得将 "NotFoundError" 解读为 比“回退到网络获取”更具体的任何含义。

注： 仅凭公共哈希值列表并不足以 约束全局范围：攻击者可以构造一个 跨站标识符，方法是从各自符合 PHL 收录条件的资源中选择要写入的子集。 跨站查询预算、COS 用户激活条件 和 COS 写入限制 对此加以约束。这些机制均不依赖用户的第三方 Cookie 设置。

注： 跨站查询预算 只在以下情况下不对查询计数：查询是 通过读取方自己的顶级站点下写入的共享记录得到答复的（见 是否为不计入预算的 查询）。这可以是一条存储源记录，或一条源记录，其分区与以下分区同 站，即 读取方的 COS 分区。其他每次 查询均计入预算，无论是否找到条目。这 包括通过第一方源记录得到答复的查询，如果该记录写入于 另一个顶级站点下。Cross-Origin-Storage-Allow-Origin 标头阻止注入的内容 指定这样的读取方。但写入站点的运营方仍可以指定任何源，因此，如果不将这种查询 计入预算，两个相互配合的站点就可能在其中一个站点上生成标记文件，用一个列表指定另一个站点，并 在后者读回任意位数的标识符，即使访问发生在不同时间也不受限制。一次查询 若因超出预算而遭拒绝，会以 "NotFoundError" DOMException 拒绝， 与一次 未命中完全相同。COS 用户激活条件与 GREASE 机制一样，只适用于 仅凭全局范围获得读取资格的源。对于存储源、列入显式源列表的源，以及 同站于 两者之一的源，只要确定 COS 披露范围返回条目，就能立即读取它。

8.5. 开发者指南

某些泄露并不需要攻击者出现在发生泄露的站点上。如果一个站点只为已登录用户存储某个文件， 或者文件的字节因用户而异，它就会向每个能够查询该文件的站点披露这一状态， 而其自身的遥测数据完全不会显示这一点。用户代理应在开发者 执行写入时，通过控制台警告或开发者工具告知这次写入会暴露哪些信息。值得 提示的情况包括：

  • 写入为某个哈希值请求 "*"，但该哈希值不在 PHL 上，因而仍限于同站（见 扩大资源的可见范围）；

  • 一个源列表 被 COS 范围 上限裁减（见 应用 COS 范围上限），或已达到源列表最大长度；

  • 一次写入因按源计算的存储限制或 COS 写入限制而被拒绝。

8.6. GREASE 机制

用户代理可以应用 GREASE 机制（生成随机扩展并维持 可扩展性）：偶尔作出这样的响应，仿佛 一个可披露的条目并不存在，即使§ 8.4 可用性控制 在通常情况下 会允许披露。这会引入噪声，使站点更难将真正不存在的情况 与出于隐私考虑产生的假阴性区分开来，类似于 用户代理客户端 提示所用的技术。

GREASE 机制只适用于仅凭全局范围获得资格的源，这也正是公共哈希值 列表所控制的情况（见确定 COS 披露范围）。 用户代理不得将其应用于存储源、列入显式 源列表的源，或 同站于两者之一的源。

用户代理应用 GREASE 机制时，必须根据所涉及条目的大小 作出适度判断。对于较小的条目，回退到网络获取的开销很低，此时偶尔产生 假阴性是合理的隐私权衡。用户代理不得将 GREASE 机制应用于以下条目： 其大小使得无谓地重新下载的代价与所获隐私收益明显不成比例 （例如，GB 级的 AI 模型权重），因为此时一次假阴性就会迫使调用方进行完整、 可观察且开销很大的重新下载。跨站查询预算会限制对这些 条目的查询，并将每一次为了看穿 GREASE 机制而重复进行的查询计入预算。

8.7. 派生产物计时

复用派生 产物是可观察的，因为复用比重新计算更快。一个产物如果 没有页面选择的输入，便不会披露额外信息，所能获知的仅限于 那些读取操作已经披露的信息，即提供其 来源的读取操作。 页面选择的输入则可能携带 标识符：相互配合的脚本在一个站点上为每个置位的比特计算一个产物，各自使用一个 不常见的算子选项，再在另一个站点上根据哪些计算较快来读出这些比特。 将每一次这种复用计入跨站查询预算，就能将披露量限制在查询原本就会 披露的信息范围内。

8.8. 指纹识别

攻击者探测跨源存储所能提取的信息量，受限于被探测资源的 普及程度。得知某个用户持有非常流行的资源，例如常见的 AI 模型 或广泛使用的 JavaScript 库，只能说明其访问过使用该资源的站点之一（此类站点可能 非常多）。而得知用户持有罕见或独有的资源，则能透露多得多的信息。

罕见或每个用户独有的哈希值不在 PHL 上，因此其他站点要读取相应条目，只能通过 源列表，且该列表须由 写入方的运营方授权；而 跨站 查询预算会将其他任何顶级站点下的这些读取计入预算。剩余的风险 是 PHL 上的某个哈希值仅对应极少数设备持有的资源，例如通过人工维护的 AI 模型部分收录的小众模型：此时，一次查询就可能指向某个人，而只需一次查询的攻击 无法靠预算加以限制。由于列入 PHL 只意味着允许披露，用户代理可以 随时从其快照中移除这样的条目，也可以完全不纳入人工维护的部分。 用户代理还可以在设备上使用启发式方法检测并阻止探测行为模式。

9. 与其他规范集成

本节为非规范性内容。

此处定义的 COS 注册表 还可以通过四种宿主集成访问，无需 调用 getFileHandle() 来直接访问。每种 集成都在其自身的宿主规范中定义。本规范定义共用的 基础概念（COS 哈希值、COS 条目、可用性控制和 公共哈希值 列表），以及将已获取的资源存入跨源 存储的步骤。 这些集成预期都以此为基础。

  • HTML：为以下元素提供 crossoriginstorage 属性： link 和 script 元素，前提是它们已经 带有 integrity [SRI]。提交给 WHATWG 的提案见 whatwg/html#12770。

  • JavaScript：由宿主定义的 crossOriginStorage 导入属性，可 配合 integrity 使用，以导入属性 提案为基础。提交给 WHATWG 的提案见 whatwg/html#12771。

  • CSS：一种名为 cross-origin-storage() 的 <request-url-modifier>， 可与 integrity() 同时使用。 提交给 CSS 工作组的提案见 w3c/csswg-drafts#14056。

  • Fetch：一个名为 crossOriginStorage 的 RequestInit 选项，可与 integrity 同时使用 [FETCH]。提交给 WHATWG 的提案见 whatwg/fetch#1954。 这种集成没有由宿主定义的目的地，而一个 COS 条目只存储字节， 因而由该规范定义相应的 Response， 它由 COS 注册表提供。其预期 形式为成功响应：状态为 200，状态消息为 OK，而其 主体是由相应字节组成的流。它的 Content-Type 标头是 由 调用方声明的 MIME 类型，且不带任何其他标头，因为未发生网络获取。 该选项预计要求使用 GET 方法：命中时会直接答复请求， 无需将其发出，只有当相应方法的请求既没有主体也没有副 作用时，这样做才是安全的，因此 Request 构造函数会抛出 TypeError， 如果使用的是其他任何方法。

以下仅作示例，展示同一个全局共享的资源如何选择使用跨源存储， 分别采用上述四种形式：

<script src="popular-library.js" integrity="sha256-abc123..." crossoriginstorage="*"></script>

import data from "popular-resource.ext" with {
  integrity: "sha256-abc123...",
  crossOriginStorage: "*",
};

@font-face {
  font-family: "Popular Font";
  src: url("popular-font.woff2" integrity("sha256-abc123...") cross-origin-storage(*));
}

const response = await fetch("popular-resource.ext", {
  integrity: "sha256-abc123...",
  crossOriginStorage: "*",
});

这些片段仅作示例。本规范不定义其中的任何语法。 各种形式的权威文法，包括如何表示受限的源列表， 都由相应的宿主规范定义。不同形式有意采用 不同的写法：RequestInit 成员可以接受 sequence<DOMString>，与 origins 完全一致，而属性值、 导入属性值和 CSS 修饰符的实参只能包含文本。

这四种形式预计采用同一处理模型：先查询 COS 注册表以查找匹配且可披露的条目， 然后才回退到网络获取；此外，还会 将成功获取并通过完整性验证的资源存入 COS 注册表，以供 其他源复用，与 getFileHandle() 的行为完全相同。存储步骤 是将已获取的资源存入跨源 存储，每种集成都运行这一步骤，并传入 已获取的响应。因此，受限的源值受资源响应中的 Cross-Origin-Storage-Allow-Origin 标头约束，该标头由 提供字节的服务器发送（见§ 7 Cross-Origin-Storage-Allow-Origin 标头）。有关 这些集成的讨论应放在各自宿主规范的问题跟踪器中， 不属于本代码库的问题跟踪器。

9.1. 资源计时

上述任一种集成从 COS 注册表提供的资源，都会被报告给 资源计时 [RESOURCE-TIMING]，与其他已获取的资源相同。此类命中所提供的响应 应将其缓存状态设为 "local"，因为没有发生网络 获取；应设置其计时许可检查通过标志，因为没有服务器 参与， 无需保护任何服务器的计时信息；并应将其主体信息的 编码大小和解码大小设为相应 字节的长度，正如 Cache API 对其存储的响应所做的那样 [SERVICE-WORKERS]。 集成应将 "cross-origin-storage" 作为交付类型传给 标记资源计时。这样，该条目的 deliveryType 为 "cross-origin-storage"，其 transferSize 为 0，而其 encodedBodySize 为所存储资源的大小。

注： 命中本来就可以通过计时以及 服务器未收到请求这一事实 观察到，因此，此处披露的信息都已在§ 8.4 可用性控制的 管辖范围内。
