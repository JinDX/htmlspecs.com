摘要

跨源存储（COS）是一种内容寻址缓存，允许 Web 应用跨不同源存储和检索大型文件，例如 AI 模型、WebAssembly 模块和广泛使用的 JavaScript 库。文件通过其加密哈希而非 URL 进行标识，因此，某个源获取过一次的字节完全相同的资源，可以由用户代理允许的任何其他源复用，而无需再次下载。为了防止通过缓存中是否存在某个文件来推断用户访问过哪些网站，只有其哈希达到类似 k-匿名的流行度门槛时，才允许跨源披露该文件。

1. 简介

本节为非规范性内容。

存储通常按源进行分区，以保护用户的安全和隐私。这是正确的 默认做法，但它并不适合一小类体积非常大、高度流行且公开分发的 资源——AI 模型、WebAssembly 模块、JavaScript 库、游戏引擎和大型 Web 字体 ——无论哪个站点请求它们，它们逐字节都是同一个文件。当两个 互不相关的源各自依赖同一个 8 GB 模型时，按源分区的存储会迫使 用户下载并保留该模型两次，这会浪费用户的带宽、存储空间和 电池电量，也会浪费整个网络的资源。

跨源存储（COS）是一个内容寻址缓存，它以加密哈希而不是 URL 作为键，使用户代理能够在选择使用它的多个源之间共享此类资源的 单个已存储副本。在 COS 中存储资源始终是存储源明确选择加入的行为， 而且用户代理可以拒绝确认某资源是否存在，即使对于原本 被允许读取该资源的源也是如此；参见§ 8 隐私 和安全注意事项。

本规范的入口点是 requestFileHandle() 方法，该方法通过 crossOriginStorage 暴露： 

const hash = {
  algorithm: 'SHA-256',
  value: '8f434346648f6b96df89dda901c5176b10a6d83961dd3c1ac88b59b2dc327aa4',
};
try {
  const handle = await navigator.crossOriginStorage.requestFileHandle(hash);
  const file = await handle.getFile();
  // 对该文件执行某些操作。
} catch (err) {
  if (err.name === 'NotFoundError') {
    // 不（可披露地）存在于跨源存储中；改为从网络获取。
  }
}

本规范复用了 FileSystemFileHandle、 FileSystemWritableFileStream 以及文件系统标准 [FS] 中的相关 基础设施，但其作用域限定于专用的、跨源共享的 文件系统，而不是单个源的私有文件系统或用户可见文件系统。

本规范仅定义命令式 JavaScript API。相关提案将 同一底层缓存集成到其他宿主规范中——HTML 中 crossoriginstorage 属性用于 link 和 script， JavaScript 的 crossOriginStorage 导入属性、CSS 的 cross-origin-storage() <request-url-modifier>，以及用于 fetch() 的 crossOriginStorage RequestInit 选项——每项均在其各自的宿主规范中定义；参见 § 9 与其他规范的集成。

2. 概念

2.1. 哈希

COS 哈希是一个结构体，具有 以下项：

算法

一个字符串， 用于命名 [WEBCRYPTO] 所识别的哈希算法，例如“SHA-256”。

值

一个字符串，它是由 算法生成的摘要的小写十六进制编码。 对于“SHA-256”，其长度为 64 个字符。

algorithm 字典成员的类型是普通的 DOMString，而不是 HashAlgorithmIdentifier， 尽管其值空间恰好就是 [WEBCRYPTO] 的哈希算法所接受的名称集合。HashAlgorithmIdentifier 是 (object or DOMString)——它还允许使用 object，该对象会由 [WEBCRYPTO] 规范化为 一个 Algorithm 形状的 字典，以便调用者可以向需要额外参数的算法传递 这些参数（例如 {name: "HMAC", hash: "SHA-256"}）。哈希算法不接受此类参数， 算法会作为内容寻址 键的一部分被存储、比较并往返传递，而不是仅由单个操作使用一次，并且本规范 示例中的每种用法都是纯字符串；允许在此使用任意对象不会增加任何能力，反而会使 相等性和序列化 变得不必要地复杂。因此，DOMString 是该字段 更窄且更正确的类型。

如果两个 COS 哈希值的 算法 值以 ASCII 不区分大小写方式匹配，并且它们的 值完全 相等，则这两个值相等。

注：与算法不同，后者的大小写没有受到规范性 约束， 值已经被规范性要求为 小写（见上文），因此比较它时使用普通的 字符串比较，而不是ASCII 不区分大小写比较。

内容寻址 存储是指其条目以 相等的 COS 哈希为键，而不是以 URL 或 名称为键：两个具有 相同字节且使用相同哈希算法的文件属于同一条目，而不论有多少个源 存储了它们，也不论它们是从多少个 URL 获取的。

2.2. COS 条目

每个用户代理都有一个唯一的COS 注册表，它是一个从 COS 哈希值到 COS 条目结构体的映射， 由所有使用跨源存储的源共享。一个 COS 条目具有以下项：

哈希

一个 COS 哈希。

字节

Null，或者一个字节序列，使用 哈希的 算法计算出的摘要 等于 哈希的 值。在写入器完成 验证和 存储之前为 Null。

状态

“pending”或“written”。条目最初为“pending”， 并且仅在 字节首次被设置时变为“written” 一次。

待处理写入器计数

一个非负整数，初始值为 0，用于计算未完成的写入器数量——由完成创建请求返回的 FileSystemFileHandle 句柄，其关闭写入 尚未 敲定。仅用于在验证并存储中决定失败的写入是否可以安全地 清理；参见§ 3.3 创建和写入文件。

源

一个列表，其中包含被授予显式跨源读取权限的源，此权限独立于 公共哈希 列表。初始为空。只会增长，绝不会 缩小。这是决定谁可以读取条目的三个相互独立且可叠加的授权之一， 另外两个是其存储源（始终可读取，以及与它们 同站点的源）和全局 可披露状态。

全局可披露

一个布尔值，初始为 false，用于记录该条目是否是在请求 全局（“*”）可用性的情况下写入的。当为 true 时，该条目可由请求通过 § 8.3 可用性门控的任何源读取——也就是说，其哈希位于 PHL 中，并且 GREASE 处理没有将其抑制。只会被设置，绝不会 清除。

注：这是与项 源分开的一个 项，而不是其中的哨兵 值，因此后续的全局可用性请求会在 现有的显式源列表之上添加“*”授权，而不是替换它。 如果将这两者合并 到一个字段中，则提供字节的写入器可能会把作用域限定为列表的条目变成 作用域为“*”的条目，而且——由于§ 8.3 可用性 门控适用于“*”授权，但不适用于 显式的源列表——此前可通过该 列表读取该条目的源 会在哈希不 位于 PHL 中时开始收到“NotFoundError”。 将这些授权保持独立，可确保每次可见性变更都严格是叠加式的， 这正是可升级但绝不可降级 所要求的。

存储源

一个集合，其中包含每个都至少成功完成过一次 该条目字节写入的源。它会跨页面加载持久保存，并且会随着时间 增长；除§ 5.2 驱逐中所述的情况外，绝不会缩小。位于 存储源中的源始终可以通过 requestFileHandle() 获取该条目的句柄，而不受源或 该条目的哈希是否位于公共哈希列表 （PHL）中的影响。 参见§ 3.4.1 原始存储者访问。

用户代理具有关联的跨源存储队列，它是 启动新的并行队列的结果。对 COS 注册表的所有操作都要 入队到此队列中，从而使它们按照 它们 入队的顺序执行，并且不会交错执行。

2.3. 公共哈希列表

确认某个哈希存在于跨源存储中，本身就可能泄露有关 用户浏览历史的信息（参见§ 8.2 跨站点探测）。这种风险 专门针对全局授权——条目的显式 源列表以及每个条目都具有的 同站点基线，其披露范围已经由存储源的显式选择 限定，但使一个条目 全局可披露则可能会将其暴露给 Web 上的任何 源。为了限制这种 特定风险，一个全局可披露资源仅能通过该 授权向其存储源之外的源披露，前提是其哈希通过额外的、 独立的门控：属于公共哈希列表 （PHL），这是一个供应商中立、实现定义的COS 哈希 值允许列表。只有当哈希通过类似 k-匿名性的 流行度门槛时，它才会被加入公共哈希列表——例如，以逐字节相同的形式出现在某个最小数量的独立 源中——从而确保确认它存在于共享缓存中不会泄露任何有关 单个用户的信息。

如果一个 COS 哈希 hash 与用户 代理当前的公共哈希列表快照中的某个条目 相等，则 hash 位于公共 哈希列表中。

公共哈希列表的检索协议、 更新频率、数据格式、流行度阈值和治理机制 将作为本规范的配套产物进行详细设计，其思路类似于 [URL] 标准的公共后缀列表是一个配套数据文件，而不是 规范性文本——参见本仓库中的 公共哈希列表说明文档。该设计 提议由 WHATWG 进行治理，并以公共后缀列表跨供应商、 滚动发布的先例为模型，同时采用以独立佐证的普遍性为依据的准入标准——这是上述类似 k-匿名性门槛的一个具体 实例，该门槛只在离线情况下作为哈希准入流程的一部分应用一次，而不是作为 用户代理对每次查询重复执行的检查。这些内容目前均尚未 在本提案之外正式确立。列表本身的一个早期、非规范性代码原型 维护在本仓库的 public-hash-list/implementation/ 中——这是一个实用的 临时位置；PHL 说明文档中描述的治理目标仍然是建立一个专用的、跨供应商仓库。 本规范仅依赖某个哈希是否位于 PHL 中，而不依赖任何特定的 检索机制或治理模型，因此无论该设计如何 演进，本规范都仍然正确。

3. CrossOriginStorageManager 接口

[Exposed=(Window,Worker), SecureContext]
interface CrossOriginStorageManager {
  Promise<FileSystemFileHandle> requestFileHandle(
      CrossOriginStorageRequestFileHandleHash hash,
      optional CrossOriginStorageRequestFileHandleOptions options = {});
};

dictionary CrossOriginStorageRequestFileHandleHash {
  required DOMString value;
  required DOMString algorithm;
};

dictionary CrossOriginStorageRequestFileHandleOptions {
  boolean create = false;
  (DOMString or sequence<DOMString>) origins;
};

interface mixin NavigatorCrossOriginStorage {
  [SameObject, SecureContext] readonly attribute CrossOriginStorageManager crossOriginStorage;
};
Navigator includes NavigatorCrossOriginStorage;
WorkerNavigator includes NavigatorCrossOriginStorage;

每个 Navigator 和 WorkerNavigator 对象都有一个关联的 CrossOriginStorageManager 对象。crossOriginStorage getter 的步骤 是返回this 的关联 CrossOriginStorageManager。

每个 CrossOriginStorageManager 对象都有一个关联的源，在创建该对象时，将其设置为 this 的相关设置对象的源。

注：从相关设置对象获取源，而不是从 脚本本身的任何信息获取，这会对 worker 产生一个值得明确说明的结果。通过 blob: URL 创建的 worker 具有创建它的上下文的源，因此它与该源共享完全相同的 跨源存储视图：此类 worker 写入的内容，其创建页面可以读回，而 页面存储的内容，worker 也可以读取。blob: URL 本身不是一个源， 撤销它也不会使 worker 脱离该视图。相比之下，通过 data: URL 创建的 worker 具有不透明源。本规范目前并未定义当 调用源是不透明源时，requestFileHandle() 会执行什么操作； 不透明源规则位于验证 COS 请求中，它约束的是调用者 指定的源，而不是调用者自身所在的源。不透明源没有稳定的身份可用于作为 存储 源的键，也无法用于同 站点比较，因此没有任何有意义的内容可以 授予它。

3.1. requestFileHandle() 方法

handle = await navigator . crossOriginStorage . requestFileHandle(hash)

如果由 hash 标识的文件存在于跨源存储中，并且可向调用 源披露，则返回该文件的句柄。否则，这会以一个 “NotFoundError” DOMException 拒绝。 “NotFoundError” 并不能证明该文件在 跨源存储中实际上不存在；参见§ 8.3 可用性门控。调用者可以 将其视为“改为从网络获取此文件”。

handle = await navigator . crossOriginStorage . requestFileHandle(hash, { create: true })

返回一个可用于将由 hash 标识的文件写入 跨源 存储的句柄，如果尚不存在条目，则创建一个新条目；默认情况下仅限同站点源访问。 无论条目是否已经 存在，调用者都需要通过该句柄的 createWritable() 方法写入完整文件内容；此时用户代理会验证写入的字节是否哈希为 hash， 否则以一个“DataError” DOMException 拒绝。这一要求可防止 源使用创建请求作为探测 hash 是否已经存在的预言机。

handle = await navigator . crossOriginStorage . requestFileHandle(hash, { create: true, origins: "*" })

同上，并且在写入完成后，还会使该条目可向其对 hash 的请求通过§ 8.3 可用性门控的任何源披露。

handle = await navigator . crossOriginStorage . requestFileHandle(hash, { create: true, origins: ["https://a.example", "https://b.example"] })

同上，但将披露严格限制为所列出的源（此外还包括调用 源以及已经位于存储源中的任何源）。

requestFileHandle(hash, options) 方法 的步骤如下：

  1. 令 result 为一个新的 promise。

  2. 令 realm 为this 的相关 Realm。

  3. 令 global 为this 的相关全局对象。

  4. 令 origin 为this 的关联源。

  5. 如果给定 global 运行检查跨源存储权限 的结果为 false，则：

    1. 给定 global，在DOM 操作任务源上排入一个全局任务，以 一个“NotAllowedError” DOMException 拒绝 result。

    2. 返回 result。

  6. 令 validationFailure 为给定 hash 和 options 运行验证 COS 请求的结果。

  7. 如果 validationFailure 不为 null：

    1. 给定 global，在DOM 操作任务源上排入一个全局任务，以 validationFailure 拒绝 result。

    2. 返回 result。

  8. 将以下步骤入队到 跨源存储队列：

    1. 如果 options["create"] 为 true：

      1. 给定 result、hash、options、global 和 realm，运行完成创建请求。

    2. 否则：

      1. 给定 result、hash、origin、global 和 realm，运行完成读取请求。

  9. 返回 result。

要在给定一个 CrossOriginStorageRequestFileHandleHash hash 和一个 CrossOriginStorageRequestFileHandleOptions options 时验证 COS 请求，返回 null 或一个 TypeError：

  1. 如果 hash["algorithm"] 不是 [WEBCRYPTO] 所识别的哈希算法 名称，则返回一个新的 TypeError。

  2. 如果 hash["value"] 在 hash["algorithm"] 与“SHA-256”以ASCII 不区分大小写 方式匹配时，不匹配正则 表达式 /^[0-9a-f]{64}$/，则返回一个新的 TypeError。

    注：未来的哈希算法可以定义 不同的预期摘要长度；本 规范仅对“SHA-256”施加规范性约束，这与其在所有 示例中的使用一致。

  3. 如果 options["origins"] 存在且 不是“*”：

    1. 令 candidates 为 options["origins"]， 其中单个字符串被视为只有一个元素的列表。

    2. 如果 candidates 的大小 大于用户代理的 最大源列表长度，则返回一个 新的 TypeError。

    3. 对于 candidates 中的每个 candidate：

      1. 如果在 candidate 上运行基本 URL 解析器的结果为失败，或者 已解析 URL 的源是不透明源，则返回一个新的 TypeError。

  4. 返回 null。

3.2. 读取文件

要在给定一个 promise result、一个 COS 哈希 hash、一个 源 origin、一个全局对象 global 和一个 Realm realm 时完成读取 请求：

  1. 令 entry 为 COS 注册表中，其哈希 与 hash 相等的COS 条目（如果有），否则为 null。

  2. 如果 entry 不为 null 且 entry 的状态为“pending”：

    1. 给定 global，在DOM 操作任务源上排入一个全局任务，以一个“NotAllowedError” DOMException 拒绝 result。

    2. 返回。

    注：正在进行写入的哈希 被刻意设计为不表现得像一个 不存在的哈希，以免调用者将进行中的写入误认为真正的缓存未命中， 并仅仅为了 写入这个非常大的文件而开始一次冗余的并发下载。参见§ 3.3 创建和写入文件。

  3. 令 disclosableEntry 为给定 entry 和 origin 运行应用可用性 门控的结果。

  4. 如果 disclosableEntry 为 null：

    1. 给定 global，在DOM 操作任务源上排入一个全局任务，以一个“NotFoundError” DOMException 拒绝 result。

    2. 返回。

  5. 令 handle 为在 realm 中创建一个新的 FileSystemFileHandle [FS] 的结果，其 定位器指向 跨源存储文件系统中的 disclosableEntry。

  6. 将 handle 的 COS 源设置为 origin。

  7. 将 handle 的可读取设置为 true。

    注：此句柄已经通过应用可用性门控，因此调用源 有权访问该条目的字节。

  8. 给定 global，在DOM 操作任务源上排入一个全局任务，以 handle 兑现 result。

要在给定一个 COS 条目 或 null entry，以及一个 源 origin 时确定 COS 披露，返回一个 COS 条目或 null：

  1. 如果 entry 为 null，则返回 null。

  2. 断言：entry 的状态为“written”。

  3. 如果 origin 位于 entry 的存储 源中，则返回 entry。

    注：原始存储者以及任何 自身已经成功写入该条目的源， 始终可以将其读回。参见§ 3.4.1 原始存储者 访问。

  4. 如果 origin 与 entry 的存储源中的某一项同站点，则返回 entry。

    注：每个条目都具有的同站点基线 ——即未指定 origins 选项的写入所请求的授权——始终有效， 不受之后添加的任何源列表或全局可披露授权 的影响。由于它在下面的公共哈希列表门控 之前检查，同站点 源无论该条目的哈希是否位于 PHL 中，都可以读取该条目。这里的同站点 被视为一个信任单元，因此这不会跨越§ 8.2 跨站点探测所保护的站点边界 披露任何内容。

  5. 如果 origin 的序列化是 entry 的源中的一项，则返回 entry。

    注：位于显式源 列表 中的源无需该条目 位于 PHL 中即可读取它。存储源通过指定 该源作出了有界披露决定（参见§ 3.4 资源可见性升级和§ 7 Cross-Origin-Storage-Allow-Origin 标头），而 在此基础上还要求单独的 全局普遍性，会使普通的受限共享依赖于对通常属于专有资源的内容进行无关的 公共策展。在 全局可披露门控之前检查这一点，正是为了防止后续的全局可用性写入 撤销已列出源的访问权限。参见§ 8.2 跨站点 探测。

  6. 如果 entry 的全局可披露为 true：

    1. 如果 entry 的哈希不位于 PHL 中，则返回 null。

      注：公共哈希列表门控 仅适用于全局授权——这是唯一一种 否则可能向 Web 上任何源进行披露的情况。一个 全局可披露但其哈希 不位于 PHL 中 的条目，不会 向仅凭此授权获得资格的源披露；同时也 位于存储源、其同站点集合或显式 源列表中的源已经 在上面的步骤中返回。

    2. 返回 entry。

  7. 返回 null。

要在给定一个 COS 条目或 null entry，以及一个 源 origin 时应用 可用性门控，返回一个 COS 条目或 null：

  1. 令 disclosable 为给定 entry 和 origin 运行确定 COS 披露的结果。

  2. 如果 disclosable 为 null，则返回 null。

  3. 如果 origin 位于 disclosable 的存储 源中，则返回 disclosable。

  4. 如果用户代理选择对此请求应用GREASE 处理，则返回 null。

  5. 返回 disclosable。

3.3. 创建和写入文件

由完成创建请求创建的 FileSystemFileHandle 有一个关联的 请求的源，其值是当通过该 句柄成功完成写入后，验证并存储将尝试用于升级该条目的源的值。

每个指向 COS 条目的 FileSystemFileHandle 还具有一个关联的 COS 源，即获取它的源，以及一个 关联的 可读取布尔值，它控制 getFile() 是否可以通过该特定句柄披露条目的字节。 对于由完成读取请求返回的句柄，该值为 true，因为它已经通过 可用性门控；对于由 完成 创建请求返回的句柄，该值为 false，直到验证并存储对同一句柄成功完成。

注：这被刻意设计为句柄的属性， 而不是条目的属性。无论条目是否已经存在并且已经是“written”，创建请求 都会返回一个句柄（参见 完成 创建请求），因此如果采用每条目规则，任何源都可以调用 requestFileHandle() 并令 create: true，然后立即读取一个它 从未写入的条目，从而在不满足源、 PHL 成员资格或GREASE 处理的情况下得知其内容。本 规范中的所有披露控制都应用在读取路径上，因此按条目进行门控会使创建请求绕过 所有这些控制。要求调用者先提供正确的字节，意味着通过由创建请求获得的句柄成功 读取时，不会披露调用者原本没有的任何内容。

要在给定一个 promise result、一个 COS 哈希 hash、一个 CrossOriginStorageRequestFileHandleOptions options、一个全局对象 global 和一个 Realm realm 时完成 创建请求：

  1. 令 requestedOrigins 为给定 options["origins"] 运行规范化 请求的源的结果。

  2. 如果 requestedOrigins 是一个列表：

    1. 令 ceiling 为给定 global 运行获取 COS 作用域上限的结果。

    2. 从 requestedOrigins 中移除 ceiling 不 包含的每个源。

      注：这就是与COS 作用域上限的交集，即 § 7 Cross-Origin-Storage-Allow-Origin 标头 所描述的情况：披露源的 Cross-Origin-Storage-Allow-Origin 标头未授权的接收者会被丢弃， 而不是导致 写入失败，这与在升级资源可见性中，超出长度的升级会丢弃其多余项 的做法一致。用户 代理预计会记录一条控制台警告，并指出 每个被丢弃的源。

    3. 如果 requestedOrigins 为空，则将 requestedOrigins 设置为 null。

      注：如果一个列表的所有成员都 被丢弃，则该写入不再有任何获得授权的 跨源接收者，因此它会回退到同站点默认值，而不是回退到严格更窄的空列表（后者甚至会 排除同站点读取者）。这些字节 仍会被存储；只有未经授权的披露会被阻止。

  3. 令 entry 为 COS 注册表中，其哈希 与 hash 相等的COS 条目（如果有），否则为 null。

  4. 如果 entry 为 null：

    1. 将 entry 设置为一个新的 COS 条目，其中哈希为 hash， 字节 为 null，状态为“pending”，源为一个 空列表，全局可披露为 false，并且 存储源为一个空集合。

    2. 将 COS 注册表[hash] 设置为 entry。

    注：新条目开始时没有显式的 源 授权，并且不是 全局可披露的； 在字节写入并 验证后，下面的验证并 存储会通过升级资源可见性将 requestedOrigins 应用于它， 这与找到现有条目的请求完全相同。正是这一点使创建 请求必须先提供完整字节，才能扩大可见性（参见§ 3.4 资源可见性升级）。

  5. 将 entry 的待处理写入器计数增加 1。

    注：即使调用者从未在 handle 上调用 createWritable()， 或从未关闭生成的流，这仍会将 handle 作为一个 未完成的写入器进行跟踪。此类 被放弃的句柄会永久计入 entry，这与该机制出现之前，被放弃的进行中 写入已经会使 entry 永久保持“pending”完全相同；参见 验证并 存储。

  6. 令 handle 为在 realm 中创建一个新的 FileSystemFileHandle [FS] 的结果，其 定位器指向 跨源存储文件系统中的 entry。

  7. 将 handle 的COS 源设置为 global 的 相关设置对象的源。

  8. 将 handle 的请求的源设置为 requestedOrigins。

  9. 将 handle 的可读取设置为 false。

    注：无论 entry 是否已经存在，也无论它是否 已经是“written”，都会返回 handle。调用者仍然需要通过 handle 提供完整文件字节，因此写入不能用于检测先前是否已经存在（参见 § 8.2 跨站点探测），同时也能确保在允许更宽松的 源 值请求之前可以对其进行验证；参见 § 3.4 资源可见性升级。

  10. 给定 global，在DOM 操作任务源上排入一个全局任务，以 handle 兑现 result。

要在给定一个 (DOMString or sequence<DOMString>) 或 undefined origins 时规范化 请求的源，返回“*”、一个由源组成的列表，或 null：

  1. 如果 origins 不存在，则返回 null。

  2. 如果 origins 是“*”，则返回“*”。

  3. 令 list 为 « »。

  4. 对于 origins 中的每个 candidate（单个 字符串被视为只有 一个元素的列表）：

    1. 令 candidateOrigin 为在 candidate 上运行基本 URL 解析器 所得到的源。

      注：验证 COS 请求已经确认每个 candidate 都会解析为一个 非不透明源。

    2. 如果 list 不包含 candidateOrigin，则将 candidateOrigin 追加到 list。

  5. 返回 list。

注：在这里去重，而不是仅在之后 合并 到现有条目时去重，可使源从条目 首次创建的那一刻起就保持无重复，因此之后对它进行的每次克隆也会保持无重复。

当在一个句柄上调用 createWritable() 获得的 FileSystemWritableFileStream 被关闭时，如果该句柄的定位器 指向一个 COS 条目 [FS]，则用户代理必须在 该关闭操作的 promise 被兑现之前运行下面的验证并存储 步骤。

注：无论关闭是如何 触发的，这都适用——无论是显式 close() 调用，还是到达其 源末尾的 pipeTo() 调用，后者默认也会关闭其目标。[STREAMS] 在 流变为关闭状态时并不区分这两种情况，本算法也不区分。

给定由已关闭 流的句柄所指向的 COS 条目 entry、完整写入的字节序列 bytes，以及关闭操作的 相关设置对象的源 origin，验证并存储 的步骤如下：

  1. 令 computedValue 为 bytes 的小写十六进制摘要，该摘要按照[WEBCRYPTO]，使用 entry 的算法所指定的算法计算。

  2. 如果 computedValue 与 entry 的值不完全相等：

    1. 以一个“DataError” DOMException 拒绝关闭操作的 promise。

    2. 将以下步骤入队到 跨源存储队列：

      1. 将 entry 的待处理写入器计数减 1。

      2. 如果 entry 的状态为“pending”，并且 entry 的 待处理写入器计数为 0， 则从 COS 注册表中移除 entry 的 哈希。

        注：这正是使 失败的写入能够自行清理，而不是留下一个 永久无法访问的“pending”条目的机制：一旦没有其他 写入器仍未完成，之后针对同一哈希的 requestFileHandle() 调用将完全看不到该条目，并获得普通的 “NotFoundError”， 而不是无限期的“NotAllowedError”。 该计数用于防止 删除另一个针对同一哈希并发进行中的写入器可能仍会成功写入的条目 （例如，两个标签页都发现该哈希不存在，并各自独立开始 写入它）：如果该写入器仍未完成， 或已经成功，则要么计数尚未达到 0，要么 entry 的 状态已不再是“pending”， 因而此步骤不执行任何操作。一个 已经是“written”的条目绝不会通过这种方式被移除，无论之后有多少 写入器请求它并失败：只有从未成功 写入过一次的条目 才符合条件。

    3. 中止这些步骤。

  3. 将以下步骤入队到 跨源存储队列：

    1. 将 entry 的字节设置为 bytes。

    2. 将 entry 的状态设置为“written”。

    3. 如果尚不存在，则将 origin 追加到 entry 的存储源。

    4. 将 entry 的待处理写入器计数减 1。

    5. 给定 entry 和句柄的请求的源，运行升级资源可见性。

    6. 将句柄的可读取设置为 true。

      注：只有此句柄变得 可读取。通过另一个 尚未完成写入的不同创建请求为同一条目获得的句柄仍然不可读取。

在一个指向 COS 条目的 FileSystemFileHandle 上调用 createWritable() 时，必须生成一个 FileSystemWritableFileStream， 其内容从空开始， 无论 keepExistingData 的值如何，也无论 所指向条目的状态如何。

注：[FS] 在其他情况下将 keepExistingData 定义为使用现有文件的内容初始化 流。在这里遵循这一行为会让调用者能够成为它从未拥有过的字节的存储 源。无论条目 是否已经存在，创建请求都会返回句柄，因此调用者可以针对另一个源存储的哈希打开一个可写流， 在未写入任何内容的情况下关闭它，然后让继承来的字节哈希为请求的值。这将 在从未检查源、公共哈希列表和 GREASE 处理的情况下授予它读取权限——这是由两个各自都被允许的操作组合而成的可用性 门控绕过。 这与使验证并存储 要求每个创建请求都提供完整内容的理由相同。

注：因此，在没有任何写入的情况下关闭的可写流 包含空字节序列，该序列不会 哈希为调用者想要的任何条目的请求值，因此验证并存储会像处理任何其他不匹配情况一样，以一个“DataError” DOMException 拒绝它。对于这种情况，如果实现 改为报告存储或 I/O 失败，就会用一个 无关错误掩盖验证结果。

文件系统标准 [FS] 尚未定义一个 扩展点，以供依赖它的 规范将额外的逐写入验证挂接到 FileSystemWritableFileStream 的 关闭步骤中。在这样的挂接点存在之前，本节直接描述所需行为；未来的 修订预计会正式与 [FS] 集成。

3.4. 资源可见性升级

COS 条目的可见性可以 升级，但绝不能降级。

要在给定一个 COS 条目 entry 和“*”、一个由 源组成的列表或 null requestedOrigins 时升级 资源可见性：

  1. 如果 requestedOrigins 为 null，则返回。

    注：省略 origins 仅请求同站点 可用性，而每个条目已经具有这种可用性（参见确定 COS 披露），因此没有 任何内容需要添加。

  2. 如果 requestedOrigins 是“*”：

    1. 将 entry 的全局可披露设置为 true。

    2. 返回。

    注：这会添加全局授权；它不会 修改 entry 的源。已经 具有显式源列表的条目会保留它，因此 该列表上的每个源即使在条目变为 全局可披露之后，仍保留其独立于 PHL 的访问权限。这正是 为什么这两种授权要分别存储的关键所在；参见全局可披露。

  3. 对于 requestedOrigins 中的每个 candidateOrigin：

    1. 如果 entry 的源包含 candidateOrigin，则 继续。

    2. 如果 entry 的源的大小 等于用户代理的 最大源列表长度，则 中断。

      注：任何剩余的 candidateOrigin 值都会从此次升级中被静默丢弃，而不是 导致升级失败——写入本身已经成功——但用户代理应当 在控制台记录一条警告，说明该条目的源列表已达到容量上限。

    3. 将 candidateOrigin 追加到 entry 的源。

注：升级只会向源中添加内容，或将全局可披露 设置为 true；这两种授权都绝不会被移除或缩小。请求一个列表的写入器会扩大 已经全局可披露的条目，就像扩大尚未全局可披露的条目一样 ——新列出的源会获得独立于 PHL 的访问权限，即使“*”授权仍然 有效——因为这两种授权彼此独立，而不是存在先后等级关系。

注：新站点——而不仅仅是原始存储者——可以 扩大条目的源，只要 它还提供哈希为该条目哈希的字节。这是有意如此设计的： 根据构造，任何已经拥有某个哈希所对应正确字节的站点，对于该哈希所表示内容的权威性 都与原始存储者相同。

3.4.1. 原始存储者访问

已成功完成写入一个 COS 条目的源——即 该条目的存储源中的任何源——之后始终可以通过 requestFileHandle() 获取该条目的句柄，而不受条目的 源值影响，也不受其哈希是否位于 PHL 中的影响。 这与 Cache API 的模型相呼应，在该模型中，一个源始终可以访问它自己存储的内容。

4. 跨源存储文件系统

跨源存储文件系统是一个文件系统根，不同于任何 源的存储桶文件系统或本地文件系统访问根，其 条目与COS 注册表中的COS 条目项一一对应。

跨源存储文件系统不使用 [FS] 的普通逐调用 权限检查 模型：从中获得的每个 FileSystemFileHandle 在返回给脚本之前，都已经通过 § 3.2 读取文件或§ 3.3 创建和 写入文件获得完全授权，因此在这种句柄上调用 getFile() 或 createWritable() 绝不会触发额外的权限提示。

因此，这种句柄上的 queryPermission() 和 requestPermission() 绝不能 报告 “prompt”，因为不会出现提示。对于不是通过创建请求获得的句柄， 其写入模式必须报告“denied”，其他情况则必须报告 “granted”。

注：写入是句柄确实可能 缺少的唯一一种能力。只有创建请求才会产生 可用于写入的句柄，因此若在任何其他句柄的写入模式下报告“granted”， 就会声称具有一种 createWritable() 实际会拒绝的能力。读取保持 “granted”，因为持有可读句柄的调用者可以通过它读取。请求权限不能 改变 任何一个结果，因为没有可显示的提示，也没有可记录授权的状态。

在一个指向 COS 条目且其可读取为 false 的 FileSystemFileHandle 上调用 getFile() 时，必须以一个“NotAllowedError” DOMException 拒绝。 这涵盖两种不同情况：

  • 来自创建请求的句柄，其条目仍处于 “pending”状态，原因与针对同一哈希并发调用 requestFileHandle() 时拒绝相同（参见 § 3.2 读取文件）：调用者绝不能将一个 尚未验证的占位符当作 文件的真实内容来观察。

  • 来自针对某个已经由其他源写入的条目的创建请求的句柄。该 条目的状态为 “written”，但此调用者尚未提供这些字节，也 尚未通过可用性门控，因此它不能得知关于 该 条目的任何信息——包括它是否存在。

一旦句柄的可读取为 true，在其上调用 getFile() 就会返回一个 File， 其内容为所指向条目的字节；这 正是 [FS] 已经为文件 条目定义的行为，其中 二进制数据就是这些字节。

指向 COS 条目的 FileSystemFileHandle 具有一个文件系统定位器，其 路径 是一个列表， 其中包含单个字符串，即该条目的 COS 哈希的值，并且其根是 跨源存储文件系统。

注：[FS] 将 name 定义为句柄 定位器路径的最后一个路径组件，因此这确定了 name， 而不是任其选择：它 就是哈希。条目本身没有名称，而哈希是它唯一的身份，因此 报告哈希保留了空字符串会丢弃的信息。

条目没有名称，也没有包含它的目录，因此 [FS] 的大部分结构性表面 都没有可操作的对象。身份是例外，而且它是内容寻址条目 始终能够回答的唯一问题：COS 注册表对于每个 COS 哈希至多保存一个COS 条目，因此两个 句柄恰好在它们的哈希相等时指向同一条目。

在一个指向 COS 条目的 FileSystemFileHandle 上调用 isSameEntry()， 并传入一个同样 指向 COS 条目且由同一 源获得的参数时，如果两个句柄的COS 哈希项相等，则必须返回 true，否则 返回 false。

注：拒绝执行此操作会丢弃用户 代理已经持有的信息。

调用 isSameEntry() 时，如果传入的参数不是由调用源获得的， 或者它指向的文件系统不是跨源 存储文件系统，则必须拒绝。

注：在这种情况下返回 false 等于断言 两个句柄指向不同的条目， 而这是对调用源无权检查的句柄作出的声明。拒绝仅表示 无法进行比较。

在一个 指向 COS 条目的 FileSystemFileHandle 上调用 move() 和 remove() 时，必须以一个“NotAllowedError” DOMException 拒绝， 并且必须保持条目不变。

注：一个条目由其存储 源中的每个源共享，因此允许 移除会使一个站点能够销毁其他站点所依赖的数据；删除应由 驱逐以及用户自己的存储控制负责。重命名或重新指定父级没有任何 可操作的对象，因为条目由其COS 哈希命名，并且没有包含它的目录。

注：在撰写本文时，这两个方法都没有由 [FS] 或 File System Access API 定义 （WICG/file-system-access#214）， 因此错误名称遵循 removeEntry()， 即 [FS] 确实 定义的用于删除条目的操作：当未授予读写访问权限时，它会以访问结果的错误名称拒绝。 此处准确的理解是操作被拒绝，而不是操作不存在——这些操作 是有意义的，只是被禁止。

createSyncAccessHandle() 在这里不需要额外规则：只要句柄不位于存储桶文件系统中，其步骤就会以一个 “InvalidStateError” DOMException 拒绝， 而跨源存储文件系统是一个与任何源的文件系统不同的文件系统根， 因此 [FS] 已经确定了 拒绝行为及其错误名称。

注：即使独立考虑，这也是本规范 所希望的结果。FileSystemSyncAccessHandle 会向调用者提供一个可写文件描述符，这将允许其 在COS 哈希所对应的存储关系之外修改条目的字节， 而该条目可向其披露的所有其他源读取的正是这些相同的字节。

4.1. 传输句柄

FileSystemFileHandle 是一个可序列化对象 [FS]，因此指向 COS 条目的句柄可以传递给另一个环境设置对象，例如通过 postMessage(message, options)。 这是除 requestFileHandle() 之外获得这种句柄的第二种方式， 因此这里也对其进行约束。

对于一个指向 COS 条目的 FileSystemFileHandle， 给定 value 和 serialized，其序列化步骤还包括：

  1. 将 serialized.[[COSOrigin]] 设置为 value 的COS 源。

  2. 将 serialized.[[COSMayRead]] 设置为 value 的可读取。

给定 serialized、 value 和 realm，反序列化步骤还包括：

  1. 如果 serialized.[[COSOrigin]] 与 realm 的 环境设置对象的源不同源，则抛出一个 “DataCloneError” DOMException。

  2. 将 value 的COS 源设置为 serialized.[[COSOrigin]]。

  3. 将 value 的可读取设置为 serialized.[[COSMayRead]]。

注：如果没有同 源检查，传输将一次性击败本规范中的所有披露控制。一个其可读取为 true 的句柄已经 针对请求它的源通过了应用可用性门控；将它发送给另一个 源，会在从未为该源评估源、 PHL 成员资格或GREASE 处理的情况下，把条目的字节交给该源。这 与文件系统标准对句柄的现有处理方式一致，这些句柄同样只有对同源接收者才有用。

注：可读取会随 句柄一起传输，而不是重新计算， 因此尚未完成写入的创建请求句柄在传输后仍然不可读取， 而读取请求句柄仍然可读，无需重新进行门控。在到达时重新进行门控会 更糟，而不是更好：这将允许调用者通过重复传输同一个 句柄来反复探测可用性。

5. 存储管理

5.1. 存储限制

用户代理必须对一个源通过成功写入可向 COS 注册表贡献的总字节数施加限制，以 防止单个源 通过淹没缓存来尝试驱逐其他源的条目。具体限制由 实现定义。如果一个源的写入会超过其 限制，用户代理必须 以一个“QuotaExceededError” DOMException 拒绝该 写入，并应当向 控制台记录警告。

注：由于条目是内容寻址的，因此一个源 反复在相同哈希下写入相同 字节时，不会在第一次成功写入之外消耗额外配额；参见 § 2.2 COS 条目。

用户代理还具有一个实现定义的最大源列表长度，它是一个 正整数，用于限制单个源列表中可以 包含多少个源。这一限制既在首次提供列表时强制执行（参见验证 COS 请求）， 也在之后将一个列表合并到现有条目中时强制执行（参见 升级资源可见性），从而保证无论是单次调用还是 多次调用随时间累积产生的效果，都不能使条目的源无限 增长。除了限制内存使用之外，这也防止一个由源组成的列表被用作 未声明的“*”替代方案；参见§ 8.2 跨站点探测。

在上述两个位置中，超出这一限制的处理方式不同，因为这两个调用 发生在一次操作中截然不同的阶段：

  • 在验证 COS 请求中，会在任何 文件被获取、哈希或 写入之前检查该限制。超出限制的调用者会立即得到一个“TypeError”， 并且不会发生其他任何事情——与任何其他格式错误的 origins 值采用相同处理方式。

  • 在升级资源可见性中，只有在 多个独立写入调用所请求的源产生累积效果时才可能达到该限制，这些调用甚至可能由彼此无关的源在 很长一段时间内发起，而且只有在当前调用的字节已经完成哈希、 验证并持久存储之后才会检查该限制。此时拒绝写入会因为一个无关的记账限制 而丢弃一次成功的、 已经验证的——并且可能非常大的——写入，而且 甚至无法将其归因于某个调用者的单一错误。因此写入仍会 成功，只会将超出容量的源从源中丢弃，并发出 控制台警告。这与现有对 从宽松到更受限制请求的处理方式一致：无法完全满足的源请求 会被静默限制，而不会导致承载该请求的写入失败。 与本规范其他部分的§ 8.3 可用性门控 一致，调用者事后无法可靠地确认其请求的源是否 实际被添加：之后以该 源调用 requestFileHandle() 即使该源已被添加也仍可能失败——例如由于 GREASE 处理——因此其结果无论如何都不能被视为确认。

5.2. 驱逐

本节为非规范性内容。

在存储压力下，用户代理可以从COS 注册表中驱逐条目， 例如，在最近访问每个条目的存储源之间采用最近最少使用策略。用户代理应当提供设置 UI，使 用户能够检查存储了哪些文件、哪些源访问过每个文件，并手动 删除条目或清除所有跨源存储数据。

当用户清除某个源的站点数据时，用户代理应从其出现的每个 存储 源集合中移除该源。如果移除后，一个 COS 条目的 存储 源为空，则用户代理可以考虑删除该条目。

5.3. 手动添加的条目

本节为非规范性内容。

上述设置 UI 可以允许用户直接将磁盘上已有的文件添加到 跨源存储中——例如用户独立于任何网站下载的 AI 模型——而无需任何 脚本调用 requestFileHandle()。 此类条目 没有可将写入归因于它的请求源，这引出了命令式 API 本身无法回答的两个问题：

  • 就 § 3.4.1 原始存储者访问而言，谁是原始存储者？没有人：该条目的存储源初始为空， 而不是包含执行写入的某个源。因此，没有任何源可以免于 每个请求源通常都要接受的可用性门控和源检查——这是正确的结果，因为实际上没有任何源 写入这些字节。

  • 这种条目是否应该像省略 origins 的普通写入那样，仅限同站点访问？不应该：“同站点”只有 相对于请求源才有意义，而手动添加没有请求源，因此不存在可供“同站点” 指代的站点。用户代理应当改为使这种条目全局 可披露， 同时保持其显式源列表为空，因为手动 预先放入一个文件只有在其他源确实可以发现它时，才能实现其目的——让用户尚未访问过的站点复用用户 磁盘上已有的文件。用户代理的设置 UI 还可以 允许用户选择更窄的作用域。

通过这种方式添加后，一个状态为“written”的条目，在其他方面与 网站通过 requestFileHandle() 写入的条目没有区别： 对它适用相同的 可用性门控和可见性 升级规则，与任何具有相同授权的其他条目完全一样 ——包括位于 PHL 中检查， 如果该条目最终变为全局可披露；这是手动添加的默认行为，但 并不是唯一可能的结果。

5.4. 来源元数据

本节为非规范性内容。

COS 条目有意不记录 其字节来自何处的任何信息。其身份仅由 哈希决定：无论多少个源存储了 相同字节，或者这些字节从多少个 URL 获取，相同字节就是同一个条目（参见§ 2.2 COS 条目）。URL 是某一个 写入器获取操作的属性，而不是条目的属性，因此对于 由多个源写入的条目，没有一种非任意方式可以选择其中一个 URL； 它不像字节那样可验证（参见§ 8.1 资源完整性）； 并且它携带的用户浏览信息比 存储 源中的粗粒度源值多得多，因为路径或查询字符串可能标识特定文档、 账户或会话。因此，将其记录在条目上会让一个高熵信号绕过 源和§ 8.3 可用性 门控所用于施加的披露限制。

然而，想要这些信息的动机确实存在：在§ 5.2 驱逐中所述设置 UI 中查看一个数 GB 大小文件的用户，以及调试为什么 requestFileHandle() 调用未命中的开发者，都希望知道文件 来自何处。用户代理可以通过在条目旁保留一份实现私有的来源记录 来满足这种需求——例如，它的每个存储源获取 字节时所用的 URL 以及时间——前提是该记录被视为用户代理状态，而不是 条目的一部分：

  • 它绝不会暴露给脚本。本规范中没有任何内容会披露它，之后添加的任何内容也 不应披露：无论是 requestFileHandle() 还是它返回的 FileSystemFileHandle 都不应揭示这种记录是否存在，更不用说其 内容。尤其是，请求源不得观察到不是由它 自己产生的记录。

  • 它只通过受信任的非 Web 表面公开：用户代理自身的设置和存储 检查 UI、其开发者工具，以及——如果用户代理具有扩展平台——在明确的、用户授予的权限后受控的扩展 API，其地位与其他 暴露浏览历史的 API 相同。有关正在考虑的扩展表面，参见本 仓库中的 浏览器扩展集成点说明文档。

  • 它未经验证，并且以此方式呈现。其中的 URL 是写入这些 字节的源提出的声明，而不是对这些字节的证明——只有哈希能保证内容（参见 § 8.1 资源完整性）。两个源可以为同一条目记录不同的 URL， 其中任意一个 都可能不准确或故意产生误导。

  • 它与条目以及它所归属的源具有相同的生命周期。当 条目被驱逐或删除时，它会被丢弃；当 某个源从存储源中移除时，归属于该源的部分也会被丢弃，包括用户清除 该 源的站点数据时（参见§ 5.2 驱逐）。

由于这种记录对内容不可见，因此用户代理是否保留这种记录，以及保留多少内容， 完全由实现决定。本规范中的任何内容都不依赖它，而且站点无法检测 它是否存在。

6. 权限策略集成

本规范定义了一个由字符串“cross-origin-storage”标识的策略控制特性 [permissions-policy]。其默认允许列表 为 self。

[permissions-policy] 针对 Document 定义了允许使用，但 CrossOriginStorageManager 也暴露在 WorkerGlobalScope 上，而后者自身没有 Document。 因此，该检查针对调用方全局对象来表述：worker 全局对象会传递地解析到拥有它的 Document， 并且其中每一个 都必须允许该特性。

要在给定一个全局对象 global 时检查跨源存储权限，返回一个 布尔值：

  1. 如果 global 是一个 Window 对象，则：

    1. 令 document 为 global 的关联 Document。

    2. 如果 document 为 null，则返回 false。

    3. 如果 document 不允许使用 “cross-origin-storage” 策略控制特性， 则返回 false。

    4. 返回 true。

  2. 如果 global 是一个 WorkerGlobalScope 对象，则：

    1. 令 owners 为 global 的所有者集合。

    2. 如果 owners 为 空，则返回 false。

    3. 对于 owners 中的每个 owner：

      1. 如果 owner 是一个 Document 且 owner 不允许使用 “cross-origin-storage” 策略控制特性， 则返回 false。

      2. 如果 owner 是一个 WorkerGlobalScope 对象，并且给定 owner 运行 检查跨源 存储权限的结果为 false，则返回 false。

    4. 返回 true。

  3. 返回 false。

对于此算法返回 false 的全局对象，从该对象发出的每个 requestFileHandle() 调用都会以一个 “NotAllowedError” DOMException 拒绝，并且发生在任何哈希验证、注册表查找或写入 之前。

注：通过所有者集合进行解析，正是防止该特性 仅在名义上可选择退出的机制。由 blob: URL 创建的 worker 运行在其创建页面的 源中，并与该页面共享完全相同的跨源存储视图（参见 § 3 CrossOriginStorageManager 接口），因此 如果检查仅查阅全局对象自身的 Document， 那么在每个 worker 中都会因条件为空而自动满足，而将调用移动到 new Worker(URL.createObjectURL(&hellip;)) 中就会绕过 cross-origin-storage=() 策略， 而无需改变其他任何内容。

注：ServiceWorkerGlobalScope 的 所有者集合为空，因此本 算法在那里返回 false。这是结构上的结果，而不是 [HTML] 中的遗漏。 所有者集合是一种活跃性关系，会在 worker 创建时填充，并 用于判断该 worker 是否仍然被主动需要，而 service worker 刻意不与任何 Document 建立此类关系： 它的注册会被持久保存，用户 代理会响应事件启动该全局对象，而不是由页面启动它，并且它可以在完全没有 service worker 客户端的情况下运行。调用 register() 的客户端因此在注册时是可知的，但在全局对象运行时通常 已经不存在，而且一个正在运行的 service worker 会服务多个策略 未必一致的客户端。

注：覆盖 service worker 需要捕获的策略， 而不是遍历所有者，这属于 [permissions-policy] 和 [service-workers] 的工作，而不是 本规范的工作。本 规范倾向的形式是根据 service worker 自身脚本响应上的 Permissions-Policy 标头派生其策略，就像其策略容器 已经携带该响应的 CSP 一样：这样它仍受源控制，并且在 每次更新检查时重新评估，而不是冻结在注册时。若改为对 注册客户端的策略创建快照，会使选择退出状态过时，因为从标头中移除该特性 要到注册碰巧更新时才会生效。在这种 模型存在之前，默认拒绝是唯一不会被用于绕过选择退出的答案。

注：SharedWorkerGlobalScope 的 所有者集合可以包含多个具有不同策略的 Document， 并且在 worker 的生命周期中会增加和失去所有者。 要求每个所有者都允许该特性，意味着只要一个所有者不允许它，就会为整个 shared worker 禁用 跨源存储，并且两次 requestFileHandle() 调用之间的结果可能发生变化。另一种选择，即只要求一个 宽松的所有者，则会使任何允许该特性的 document 能够代表 不允许该特性的 document 重新启用它。

7. Cross-Origin-Storage-Allow-Origin 标头

一个其源列表非空的COS 条目 可以向写入源无法控制的源披露，然而该列表是由脚本（通过 origins） 或标记声明的，而已实现脚本或标记注入的攻击者 可以设置这两者中的任一种。为了使该声明可归因于其字节被披露之源的 运营者，而不是归因于注入的内容，本 规范定义了一个响应标头，用于限定这种声明可以指定哪些源。

Cross-Origin-Storage-Allow-Origin 响应标头携带一个 COS 作用域上限：一个 由源组成的集合， 从披露环境发出的 requestFileHandle() 写入，或加载 到披露环境中的宿主集成，可以在非同站点源列表中指定这些源。声明的列表不会 按原样采用；它会与上限取交集 （参见完成创建请求），因此该上限只可能 缩小声明，绝不会 扩大或创建声明。

注：该标头仅适用于列表形式。同站点默认值不会指定任何跨源 接收者，因此无需授权，而“*”形式在读取路径上由 可用性门控根据公共哈希列表进行控制，而每用户私密内容绝不可能通过该列表，因此它也不需要写入时上限。 要求“*”必须提供标头，还会破坏零配置的全局共享用例，却不会关闭任何 公共哈希列表尚未关闭的情况。

要在给定一个标头 列表 headers 时解析 COS 作用域上限，返回一个由 源组成的集合：

  1. 令 value 为从 headers 中获取、解码并拆分 “Cross-Origin-Storage-Allow-Origin”的结果。

  2. 如果 value 为 null，则返回一个空集合。

  3. 令 ceiling 为一个空集合。

  4. 对于 value 中的每个 token：

    1. 从 token 中移除前导和尾随的 ASCII 空白。

    2. 如果 token 是空字符串，则继续。

    3. 令 origin 为在 token 上运行基本 URL 解析器所得到的源。

    4. 如果 origin 为失败或是一个不透明源，则返回一个空集合。

      注：这包括值为“*”的 token，因为它无法解析为源。Cross-Origin-Storage-Allow-Origin 标头只能枚举有限的一组具体 源；“*”不是允许的值，因为“任何源”这样的上限会让 注入的内容声明任意其希望的接收者，从而破坏该标头的全部 用途。 无界 披露只能通过“*”源形式实现，而该形式 由公共哈希列表进行门控，并且绝不会查询此 标头。格式错误或包含“*”的标头 不授权任何内容，与缺少标头完全相同；失败时采用封闭策略。

    5. 将 origin 追加到 ceiling。

  5. 返回 ceiling。

注：获取、解码并拆分会在 U+002C (,) 处分割， 因此标头 值中的源以逗号分隔，这与 Timing-Allow-Origin [RESOURCE-TIMING] 以及 HTTP 响应标头中列表值的一般 约定一致，尽管同属一组的 crossoriginstorage HTML 内容 属性使用空格分隔，以匹配其宿主语法。两者都会解析为相同的 源集合。

要在给定一个全局对象 global 时获取 COS 作用域上限，返回一个由 源组成的集合：

  1. 如果 global 是一个 Window 对象，则：

    1. 令 document 为 global 的关联 Document。

    2. 如果 document 为 null，则返回一个空集合。

    3. 返回 document 的COS 作用域上限。

  2. 如果 global 是一个 WorkerGlobalScope 对象，则：

    1. 令 owners 为 global 的所有者集合。

    2. 如果 owners 为 空，则返回一个空集合。

    3. 令 ceiling 为 null。

    4. 对于 owners 中的每个 owner：

      1. 令 ownerCeiling 为一个空集合。

      2. 如果 owner 是一个 Document， 则将 ownerCeiling 设置为 owner 的 COS 作用域上限。

      3. 否则，如果 owner 是一个 WorkerGlobalScope 对象，则将 ownerCeiling 设置为给定 owner 运行获取 COS 作用域上限 的结果。

      4. 如果 ceiling 为 null，则将 ceiling 设置为 ownerCeiling； 否则，将 ceiling 设置为 ceiling 与 ownerCeiling 的交集。

    5. 返回 ceiling。

  3. 返回一个空集合。

每个 Document 都有一个COS 作用域上限，即一个由源组成的集合， 在创建 document 时，将其设置为给定用于创建该 document 的响应的 标头列表运行解析 COS 作用域上限 所得的结果。

注：对 worker 的所有者集合取交集，与 检查跨源存储权限相呼应：一个源只有在每个拥有它的 Document 都传递地授权它时，才位于 worker 的上限中。由于 blob: worker 与其创建页面共享完全相同的 源和跨源存储视图（参见 § 3 CrossOriginStorageManager 接口），如果 上限仅查阅 worker 自身， 那么每个 worker 的上限都会为空，而将一个限定为列表作用域的写入移动到 new Worker(URL.createObjectURL(&hellip;)) 中会移除接收者，而不是保留 页面 的授权；对所有者的上限取交集可以保留它，同时不会允许任何单个 所有者扩大它。

从 Document 的 响应中填充其 COS 作用域上限，并且从其字节被存储的响应中为每个宿主集成 建立等效上限，需要在宿主规范中添加挂接点，就像 [permissions-policy] 和 [CSP] 在响应处理时被填充一样。在这些挂接点 存在之前，本节直接描述所需行为；未来的修订预计会 正式集成这些行为，同时集成§ 3.3 创建 和写入文件中提到的 [FS] 挂接点。

8. 隐私和安全注意事项

除使用 RFC 2119 关键词之处外，本节均为非规范性内容；另请参见仓库中的 安全和隐私问卷。

8.1. 资源完整性

每个 COS 条目都以加密哈希为键，并使用该哈希 验证其字节（参见 § 3.3 创建和写入文件）。因此，站点可以确信，通过 requestFileHandle() 获得的文件与其自行获取 hash 时得到的字节完全相同。开发者无法枚举跨源存储的内容，也无法 在不知道文件哈希的情况下访问它。

COS 哈希不是秘密。它是一个 内容标识符，任何 已经拥有该文件的人都可以轻易计算，而且对于本规范所针对的广泛分发 资源而言，它通常是公开信息——例如与模型或库的 发行版本一起发布。因此，知道哈希足以查找条目，但与能力 URL 或持有者令牌不同，它本身不授予访问权限：查找是否成功完全 由源和§ 8.3 可用性门控决定，而绝不会取决于哈希是否碰巧保持 未公开。开发者不得将未公开的哈希视为访问控制机制；对 特定文件感兴趣的攻击者无需猜测其哈希，只需获得文件 本身（参见§ 8.2 跨站点探测）。

8.2. 跨站点探测

如果一个资源仅由少数站点使用，那么能够得知该资源 存在于跨源存储中的攻击者，可以推断用户很可能访问过这些站点之一。由于 requestFileHandle() 是获知是否存在的机制，因此每次调用 实际上都是一次探测。本规范中的两种独立机制限制了一次探测能够 得知的信息：

  • 源（参见 § 3.4 资源可见性升级）允许存储 源将 披露限制为选定的一组源，因此专有或低流行度资源完全不必 可被全局探测。

  • § 8.3 可用性门控还会阻止向其存储源之外的请求源披露 “*”作用域资源，除非其哈希位于 PHL 中， 从而使以 origins: “*”存储的资源 不会自动被 Web 上的每个源探测。此门控仅适用于 “*”作用域 的条目；对于列表和同站点作用域的条目，第一项中的限制是唯一的 门控，因为存储源已经明确限定了这些条目的披露范围。

第一项只有在“选定的一组源”仍明显小于整个 Web 时才成立。 origins 的形式本身并不能阻止调用者 枚举数量非常大的源——例如从公开的 热门站点排名构造的列表——这实际上会近似于全局披露，同时绕过 只有“*”才要求的刻意且明确的选择加入。最大源列表 长度（参见 § 5.1 存储限制）对此进行限制：一个足以满足真正 多资产用例 （共同控制下的少数几个相关源），但远不足以对“每个源”形成任何有意义近似的限制， 可以防止源的受限源形式被用作 未声明的“*”替代方案。

用户代理还应当对来自单个源的重复 requestFileHandle() 调用进行速率限制或其他节流，并可以应用 设备端启发式方法（例如，检测请求看似为每个用户 生成的哈希的模式）来识别和阻止探测尝试，而不论被探测的 哈希是否位于 PHL 中。

由§ 9 与其他规范的集成中的某个宿主集成执行的查找 同样是一种探测，即使它不会向页面暴露错误：站点可以观察其 自己的服务器是否收到回退请求，而该请求携带的单个比特信息与这里“未找到” 结果所携带的信息相同。此类查找不会披露本规范的门控不会披露的任何信息，并且 这些门控会原封不动地应用于它。不过，只有当来自这些 表面的查找与 requestFileHandle() 调用一起计入时，速率限制才有效，因为可脚本化的 集成同样可以轻易地在循环中发出这些调用。

8.3. 可用性门控

来自存储 源之外的源的 requestFileHandle() 读取是否成功，始终取决于请求源是否 被允许读取该条目，这由源控制。对于“*”作用域的条目，还有第二个 独立问题：用户代理是否愿意披露该条目 究竟是否存在，这由PHL 成员资格和GREASE 处理控制。对于这种条目，这两个条件都必须 成立；对于列表作用域或同站点作用域的条目，只适用第一个问题， 不过 GREASE 处理仍然可以抑制原本会被源允许的披露。有关规范性算法，参见§ 3.2 读取文件。“NotFoundError” 因此并不能 证明资源不存在：它可能意味着资源不存在、请求 源不在作用域内、“*”作用域资源的哈希尚未（或者永远不会）位于 PHL 中，或者 GREASE 处理抑制了一个真正例。开发者不得将“NotFoundError” 视为 比“回退到网络”更具体的任何含义。

注："*" 作用域条目的披露 还仅限于在当前上下文中能够设置或读取第三方 Cookie 的请求 源；如果某个源无法使用第三方 Cookie， 则不会向其披露这种条目， 不论其PHL成员资格如何。这弥补了仅靠PHL 成员资格无法弥补的漏洞：攻击者可以通过选择写入 哪些原本普通且分别符合 PHL 条件的资源子集，构建跨站点标识符，而第三方 Cookie 的可用性是决定 由此产生的探测是否比普通跟踪 Cookie 提供更多信息的因素。

8.4. GREASE 处理

用户代理可以应用GREASE 处理（生成 随机扩展并保持 可扩展性）：即偶尔表现得仿佛 一个可披露条目不存在，即使§ 8.3 可用性门控原本 会允许披露。这会增加噪声，使站点更难区分真正不存在 与出于隐私动机产生的假阴性，类似于 UA 客户端 提示所应用的技术。

应用 GREASE 处理的用户代理必须根据相关条目的大小作出适度判断。 对于较小的条目，回退到网络获取的代价不高，偶尔的 假阴性是一种合理的隐私权衡。用户代理不得对条目大小使虚假的重新下载成本 与所获得的隐私收益明显不成比例的条目应用 GREASE 处理——例如 GB 级的 AI 模型权重——因为那里的假阴性会迫使发生一次完整、 可观察且成本高昂的重新下载，而不是廉价的重新下载。

8.5. 指纹识别

攻击者通过探测跨源存储能够提取的信息，受被探测 资源流行程度的限制。得知用户拥有非常流行的资源，例如常见的 AI 模型 或广泛使用的 JavaScript 库，只能表明用户访问过使用它的（可能非常 多的）站点之一。得知用户拥有罕见或唯一的资源则提供了多得多的信息。 用户代理应当应用设备端启发式方法，检测其哈希看起来 被刻意设计为每用户唯一的资源（例如，仅由单个 站点写入过的哈希，或以异常高频率被请求的哈希），并将此类模式视为探测尝试， 不论其名义上的 PHL 状态如何。

9. 与其他规范的集成

本节为非规范性内容。

这里定义的COS 注册表 也可以从四种宿主集成访问，而无需 直接通过 requestFileHandle()。 每种 集成都在其自身的宿主规范中定义，而不是在本文档中定义；本 规范仅定义这些集成预计基于的共享底层概念（COS 哈希、COS 条目、 可用性门控以及公共哈希列表）。

  • HTML：在已经具有 integrity [SRI] 的 link 和 script 元素上添加一个 crossoriginstorage 属性，该提案已在 whatwg/html#12770 中提交给 WHATWG。

  • JavaScript：一个由宿主定义的 crossOriginStorage 导入属性，可与 integrity 一起使用，构建在导入属性 提案之上，该提案已在 whatwg/html#12771 中提交给 WHATWG。

  • CSS：一个 cross-origin-storage() <request-url-modifier>， 可与 integrity() 一起使用， 已在 w3c/csswg-drafts#14056 中提交给 CSS 工作组。

  • Fetch：一个 crossOriginStorage RequestInit 选项，可与 integrity [FETCH] 一起使用，已在 whatwg/fetch#1954 中提交给 WHATWG。 与三种声明式形式不同，这一种没有宿主定义的目标，因此从 COS 注册表提供的 Response 如何报告其 MIME 类型、状态和其他元数据， 对该规范而言仍是一个待解决的问题；COS 条目仅存储字节。

仅作说明，下面展示同一个全局共享资源如何通过四种形式分别选择加入跨源存储：

<script src="popular-library.js" integrity="sha256-abc123..." crossoriginstorage="*"></script>

import data from "popular-resource.ext" with {
  integrity: "sha256-abc123...",
  crossOriginStorage: "*",
};

@font-face {
  font-family: "Popular Font";
  src: url("popular-font.woff2" integrity("sha256-abc123...") cross-origin-storage(*));
}

const response = await fetch("popular-resource.ext", {
  integrity: "sha256-abc123...",
  crossOriginStorage: "*",
});

这些代码片段仅用于说明。本规范并未定义其中任何语法，并且 每种形式的权威语法——包括受限的、非“*”源值如何 表示——属于其自身的宿主规范，而不是本文档。它们的写法有意 不同：RequestInit 成员可以接受一个 sequence<DOMString>，与 origins 完全匹配，而属性值、 导入属性值和 CSS 修饰符参数只能承载文本。

预计所有四种形式都会共享这样的处理模型：首先查询COS 注册表中匹配且可披露的条目， 然后才回退到网络获取，并将 成功获取且通过完整性验证的资源存储到COS 注册表中，供其他源复用， 与 requestFileHandle() 的做法完全相同。关于 这些集成的讨论应当放在承载它们的宿主规范的跟踪器中， 而不是本仓库的问题跟踪器中。
