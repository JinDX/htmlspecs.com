摘要

跨源存储（COS）是一种内容寻址缓存，允许 Web 应用跨不同源存储和检索大型文件，例如 AI 模型、WebAssembly 模块和广泛使用的 JavaScript 库。文件通过其加密哈希而非 URL 进行标识，因此，某个源获取过一次的字节完全相同的资源，可以由用户代理允许的任何其他源复用，而无需再次下载。为了防止通过缓存中是否存在某个文件来推断用户访问过哪些网站，只有其哈希达到类似 k-匿名的流行度门槛时，才允许跨源披露该文件。

1. 简介

本节是非规范性的。

存储通常按源分区，以保护用户的安全和隐私。这是正确的 默认做法，但对于一小类体积非常大、极受欢迎且公开分发的 资源（AI 模型、WebAssembly 模块、JavaScript 库、游戏引擎和大型 Web 字体） 来说并不合适，因为无论哪个站点请求它们，这些资源逐字节都是同一个文件。当两个 互不相关的源都依赖同一个 8 GB 模型时，按源分区的存储会迫使 用户下载并保留该模型两次，这会浪费用户的带宽、存储空间和电量， 也浪费整个网络的资源。

跨源存储（COS）是一个内容寻址缓存，它以加密哈希而不是 URL 作为键，使用户代理能够在选择使用它的多个 源之间共享此类资源的一份已存储副本。将资源存入 COS 始终是由 存储源明确选择加入的操作，并且用户代理可以拒绝确认资源是否存在，即使面对 原本被允许读取该资源的源也是如此；参见§ 8 隐私 和安全注意事项。

本规范的入口点是 getFileHandle() 方法，它通过 crossOriginStorage 暴露： 

const hash = {
  algorithm: 'SHA-256',
  value: '8f434346648f6b96df89dda901c5176b10a6d83961dd3c1ac88b59b2dc327aa4',
};
try {
  const handle = await navigator.crossOriginStorage.getFileHandle(hash);
  const file = await handle.getFile();
  // 对文件执行一些操作。
} catch (err) {
  if (err.name === 'NotFoundError') {
    // （可披露地）不在跨源存储中；改为从网络获取。
  }
}

本规范复用了 FileSystemFileHandle、 FileSystemWritableFileStream 以及文件系统标准 [FS] 中的相关 基础设施，并将其限定到一个专用文件系统中，该文件系统 跨源共享，并与任何源的私有或用户可见文件系统分离。

本规范定义命令式 JavaScript API，以及主机 集成所构建于其上的共享存储步骤。相关提案把同一个底层缓存集成到其他主机 规范中：HTML 的 crossoriginstorage 属性用于 link 和 script， JavaScript 的 crossOriginStorage 导入属性、CSS cross-origin-storage() <request-url-modifier>，以及用于 fetch() 的 crossOriginStorage RequestInit 选项。每一种都在各自的主机规范中 定义；参见§ 9 与其他 规范的集成。

2. 概念

2.1. 哈希

COS 哈希是一个结构体，具有 以下项：

算法

一个字符串， 命名由 [WEBCRYPTO] 识别的哈希算法，例如“SHA-256”。

值

一个字符串，它是由 算法 生成的摘要的小写十六进制编码。 对于“SHA-256”，其长度为 64 个字符。

algorithm 字典成员的类型是普通 DOMString，尽管其值空间恰好是 [WEBCRYPTO] 所接受的哈希算法名称集合。HashAlgorithmIdentifier 是 (object or DOMString)，而其 object 分支 会由 [WEBCRYPTO] 规范化为一个形如 Algorithm 的 字典，使调用者能够向需要它们的算法传入额外 参数（例如 {name: "HMAC", hash: "SHA-256"}）。哈希 算法不采用此类参数， 算法会作为 内容寻址 键的一部分被存储、比较并往返传递，而且本规范 示例中的每次使用都是裸字符串；允许任意对象不会增加任何能力，反而会使 相等性和序列化 变得不必要地复杂。因此，DOMString 是该字段 更窄且更正确的类型。

两个COS 哈希值在以下情况下相等：它们的算法 值以ASCII 不区分大小写方式匹配，并且它们的值完全 相等。

注：值在规范上已经要求为小写（见上文），因此对它的比较是普通的 字符串比较。算法没有规范规定的大小写形式，因此使用 ASCII 不区分大小写方式比较。

内容寻址 存储是指其条目以 相等性的COS 哈希作为键：两个具有 相同字节并使用相同哈希算法的文件属于同一条目，而不论有多少源 存储了它们，也不论它们是从多少 URL 获取的。

2.2. COS 条目

每个用户代理都有一个单独的COS 注册表，它是一个映射，将COS 哈希值映射到 COS 条目结构体， 并由所有使用跨源存储的源共享。一个 COS 条目具有以下项：

哈希

一个COS 哈希。

字节

一个字节序列，其使用哈希的算法 计算出的摘要等于哈希的值。

注：只有在写入者提供这些字节且 用户代理完成验证之后，条目才会被添加到COS 注册表； 参见验证并存储。已请求但 尚未完成的写入在注册表中完全没有表示，这使进行中的 写入在读取路径上与不存在的条目无法区分。参见§ 8.3 进行中的写入。

源

一个列表，其中包含被授予显式跨源读取访问权限的源，该权限独立于 公共哈希 列表。授权会扩展到与该 列表中某项同站点的每个源，因此 列出 https://a.example 也会允许 https://www.a.example。它初始为空， 并且只会增长。这是决定谁可以读取条目的三个彼此独立且可叠加的授权之一， 另外两个是其存储源（始终可读，并且与其 同站点的源也可读）以及全局 可披露。

注：如果一次写入的 origins 是显式的空 列表 （origins: []），它所授予的权限与省略 origins 的写入完全相同：即条目的 存储源以及与它们同站点的源，这是每个条目 都具有的基线（参见确定 COS 披露）。应用 上限 会把空列表转为 null，因此两种写入在进入 完成创建请求的后续步骤时状态相同。显式的列表只会增加接收方； 它永远不会阻止写入者自己的站点访问该条目。

全局可披露

一个布尔值，初始为 false，用于记录该条目是否曾以请求 全局（“*”）可用性的方式写入。当为 true 时，该条目可由任何请求通过 § 8.4 可用性门控的源读取，也就是说，其哈希必须位于 PHL 中，并且 GREASE 不会抑制该请求。一旦设置，它就会保持为 true。

注：这是与项 源相分离的一个 项，这样后续的 全局可用性请求可以在现有显式 源列表之上添加“*”授权。 如果将两者合并到一个字段中，提供 字节的写入者就可以把一个列表作用域的条目变成“*”作用域条目。由于 § 8.4 可用性门控 只适用于“*”授权，原本可以通过 列表 读取条目的源，在哈希 不 位于 PHL 中时就会开始收到“NotFoundError”。 保持这些授权彼此独立，可确保每次可见性变化都严格是增量的， 这正是只能升级而不能降级所要求的。

存储源

一个集合，其中包含各自至少一次成功完成 该条目字节写入的源。它会跨页面加载持久保存，并随时间 增长；除§ 5.2 逐出中所述情况外绝不会缩小。位于 存储源中的源始终可以通过 getFileHandle() 获取该条目的句柄，而不依赖源，也不依赖 该条目的哈希是否位于公共哈希列表 （PHL）中。 参见§ 3.5.1 原始存储者访问。

用户代理具有关联的跨源存储队列，它是 启动新的并行队列的结果。对COS 注册表的所有操作都必须 排入该队列，以使它们按照 被排入的 顺序执行，并且不会交错。

2.3. 公共哈希列表

确认某个哈希存在于跨源存储中本身就可能泄露有关 用户浏览历史的信息（参见§ 8.2 跨站点探测）。这种风险 尤其存在于全局 授权中。条目的显式源列表以及每个 条目都具有的同站点基线，其披露范围已经受到存储源显式选择的限制，而 使条目全局可披露则可能将其暴露给 Web 上的任何 源。为限制这种 特定风险，全局可披露资源通过该 授权向其存储源之外的源披露时，只有在其哈希通过额外的、 独立门槛后才可以：即加入公共哈希列表 （PHL），这是一个厂商中立、由实现定义的COS 哈希 值允许列表。只有在哈希通过类似 k-匿名性的 流行度门槛（例如，以逐字节相同的形式出现在一定最小数量的独立 源中）之后，才会被加入公共哈希列表，从而确保确认其存在于共享缓存中不会泄露任何 单个用户的信息。

如果COS 哈希 hash 等于用户 代理当前公共哈希列表快照中的某个条目，则称该哈希位于公共 哈希列表中。

公共哈希列表的获取协议、 更新频率、数据格式、流行度阈值和治理 将作为本规范的配套工件详细设计，其理念类似公共后缀列表——后者是 [URL] 标准的配套数据文件；参见本仓库中的 公共哈希列表说明文档。该设计 提议由 WHATWG 负责治理，参考公共后缀列表的跨厂商、 滚动发布先例，并采用基于独立佐证普遍性的准入标准。 这是上文所述类似 k-匿名性门槛的一个具体实例，在哈希被加入时离线 一次性应用，因此用户代理无需在每次查询时重复执行。所有这些内容 尚未在本提案之外得到确立。列表本身的一个早期、非规范性代码原型 目前位于本仓库中的 public-hash-list/implementation/；PHL 说明文档所描述的治理目标仍然是建立一个专门的、 跨厂商仓库。本 规范只依赖某个哈希是否位于 PHL 中，因此无论 列表的获取机制、治理模型或其余设计如何演变，本规范都仍然正确。

3. CrossOriginStorageManager 接口

[Exposed=(Window,Worker), SecureContext]
interface CrossOriginStorageManager {
  Promise<FileSystemFileHandle> getFileHandle(
      CrossOriginStorageGetFileHandleHash hash,
      optional CrossOriginStorageGetFileHandleOptions options = {});
};

dictionary CrossOriginStorageGetFileHandleHash {
  required DOMString value;
  required DOMString algorithm;
};

dictionary CrossOriginStorageGetFileHandleOptions {
  boolean create = false;
  (DOMString or sequence<DOMString>) origins;
};

interface mixin NavigatorCrossOriginStorage {
  [SameObject, SecureContext] readonly attribute CrossOriginStorageManager crossOriginStorage;
};
Navigator includes NavigatorCrossOriginStorage;
WorkerNavigator includes NavigatorCrossOriginStorage;

每个 Navigator 和 WorkerNavigator 对象都有一个关联的 CrossOriginStorageManager 对象。crossOriginStorage getter 步骤 是返回this 关联的 CrossOriginStorageManager。

每个 CrossOriginStorageManager 对象都有一个关联的源，在对象创建时被设置为 this 的相关设置对象的源。

注：从相关设置对象取得源，而不依赖脚本 本身的任何信息，这对 worker 有一个值得明确说明的结果。由 blob: URL 创建的 worker 具有创建它的上下文的源，因此它与该源完全共享 跨源存储视图：这种 worker 写入的内容，其创建页面可以读回，而 页面存储的内容，worker 也可以读取。blob: URL 自身并不是一个源， 撤销它也不会使 worker 与该视图分离。由 data: URL 创建的 worker 具有不透明源。本规范当前并未定义当 getFileHandle() 的调用源是不透明源时应执行什么； 不透明源规则在验证 COS 请求中 只管控调用者 指定的源。不透明源没有可用于键控 存储 源或进行同 站点比较的稳定身份，因此没有任何有意义的对象可以向 它授予权限。

3.1. getFileHandle() 方法

handle = await navigator . crossOriginStorage . getFileHandle(hash)

如果由 hash 标识的文件存在于跨源存储中，并且 可向调用源披露，则返回该文件的句柄。否则，以 “NotFoundError” DOMException 拒绝。 “NotFoundError” 并不能证明该文件 在物理上不存在于跨源存储中；参见§ 8.4 可用性门控。调用者可以 将其视为“改为从网络获取此资源”。

handle = await navigator . crossOriginStorage . getFileHandle(hash, { create: true })

返回一个可用于把由 hash 标识的文件写入 跨源 存储的句柄；如果尚不存在条目，则创建新条目，并默认限制为同站点源。 无论条目是否已经存在，调用者都需要通过句柄的 createWritable() 方法写入完整文件内容；届时用户代理会验证写入的字节是否哈希为 hash， 否则以“DataError” DOMException 拒绝。此要求可防止 源利用创建请求作为探测 hash 是否已经存在的预言机。

handle = await navigator . crossOriginStorage . getFileHandle(hash, { create: true, origins: "*" })

同上，并且在写入后，使条目可以向任何对 hash 的请求通过§ 8.4 可用性门控的源披露。

handle = await navigator . crossOriginStorage . getFileHandle(hash, { create: true, origins: ["https://a.example", "https://b.example"] })

同上，但将披露限制为列出的源以及与 其中每个源同站点的源 （另外还包括调用源、已位于 存储源中的任何源，以及与这些源同站点的源）。

getFileHandle(hash, options) 方法 的步骤如下：

  1. 令 result 为一个新的 promise。

  2. 令 realm 为this 的相关 Realm。

  3. 令 global 为this 的相关全局对象。

  4. 令 origin 为this 关联的源。

  5. 如果以 global 为参数运行检查跨源存储权限 所得到的结果为 false，则：

    1. 在给定 global 的DOM 操作任务源上排入一个全局任务，以 拒绝 result，并使用“NotAllowedError” DOMException。

    2. 返回 result。

  6. 令 validationFailure 为以 hash 和 options 为参数运行验证 COS 请求的结果。

  7. 如果 validationFailure 不为 null：

    1. 在给定 global 的DOM 操作任务源上排入一个全局任务，以 拒绝 result，并使用 validationFailure。

    2. 返回 result。

  8. 将以下步骤排入 跨源存储队列：

    1. 如果 options["create"] 为 true：

      1. 以 result、hash、options、global 和 realm 为参数运行完成创建请求。

    2. 否则：

      1. 以 result、hash、origin、global 和 realm 为参数运行完成读取请求。

  9. 返回 result。

要在给定一个 CrossOriginStorageGetFileHandleHash hash 和一个 CrossOriginStorageGetFileHandleOptions options 的情况下验证 COS 请求，返回 null 或一个 TypeError：

  1. 如果 hash["algorithm"] 不是 [WEBCRYPTO] 识别的哈希算法 名称，则返回一个新的 TypeError。

  2. 如果 hash["value"] 在 hash["algorithm"] 与“SHA-256”以ASCII 不区分大小写 方式匹配时，不匹配正则 表达式 /^[0-9a-f]{64}$/，则返回一个新的 TypeError。

    注：未来的哈希算法可以定义 不同的预期摘要长度；本 规范只对“SHA-256”施加规范性约束，与其在 示例中的使用一致。

  3. 如果 options["origins"] 存在且 不为“*”：

    1. 令 candidates 为 options["origins"]， 其中单个字符串按只有一项的列表处理。

    2. 如果 candidates 的大小大于 用户代理的 最大源列表长度，则返回一个 新的 TypeError。

    3. 对 candidates 中的每个 candidate 执行：

      1. 如果在 candidate 上运行基本 URL 解析器的结果 是失败，或者解析出的 URL 的源是不透明源，则返回一个新的 TypeError。

  4. 返回 null。

3.2. 读取文件

要在给定一个 promise result、一个COS 哈希 hash、一个 源 origin、一个全局对象 global 和一个Realm realm 的情况下完成读取 请求：

  1. 令 entry 为COS 注册表中其哈希 等于 hash 的COS 条目（如果存在），否则为 null。

    注：其他写入者已 请求但尚未完成的写入不在 COS 注册表中，因此 对此类哈希而言 entry 为 null，而该算法会完全按照 一个从未被任何源写入过的哈希来继续处理。本规范允许的所有披露都由下方的 应用可用性门控决定；不存在任何 更早可以给出答案的分支。参见§ 8.3 进行中的写入。

  2. 令 disclosableEntry 为以 entry 和 origin 为参数运行应用可用性 门控的结果。

  3. 如果 disclosableEntry 为 null：

    1. 在给定 global 的DOM 操作任务源上排入一个全局任务，以 拒绝 result，并使用“NotFoundError” DOMException。

    2. 返回。

  4. 令 handle 为创建新的 FileSystemFileHandle [FS] 的结果，其 定位器在 跨源存储文件系统中寻址 disclosableEntry 的哈希，并位于 realm 中。

  5. 将 handle 的COS 哈希设置为 disclosableEntry 的哈希。

  6. 将 handle 的COS 源设置为 origin。

  7. 将 handle 的可读取设置为 true。

    注：此句柄已经通过应用可用性门控，因此调用源 有权 获取该条目的字节。

  8. 在给定 global 的DOM 操作任务源上排入一个全局任务，以 兑现 result，并使用 handle。

要在给定一个COS 条目 或 null entry，以及一个 源 origin 的情况下确定 COS 披露，返回一个COS 条目或 null：

  1. 如果 entry 为 null，则返回 null。

    注：COS 注册表中的条目 始终已经完成写入和验证，因此该算法无需考虑 半写入状态。仅有一次仍在进行中的写入的哈希不在注册表中，并以 null 到达该算法， 与从未被任何源写入过的哈希相同；参见§ 8.3 进行中的写入。

  2. 如果 origin 位于 entry 的存储 源中，则返回 entry。

    注：原始存储者以及任何 自己成功写入该条目的源 始终可以将其读回。参见§ 3.5.1 原始存储者 访问。

  3. 如果 origin 与 entry 的存储源中的某一项同站点，则返回 entry。

    注：每个条目都具有的同站点基线 （即没有 origins 选项的写入所请求的授权）始终有效， 无论之后是否添加任何源列表或全局可披露授权。 由于它在下方的公共哈希列表门槛之前检查， 同站点 源无论其哈希是否位于 PHL 中都能读取该条目。这里的同站点 是一个信任单元，因此这不会跨越§ 8.2 跨站点探测所防护的站点边界 披露任何内容。

  4. 如果 origin 与 entry 的源中的某一项同站点，则 返回 entry。

    注：位于显式源 列表中的源， 或与其中某个源同站点的源， 无需该条目位于 PHL 中即可读取。把每个列出的源扩展到 其站点，与上方的同站点基线相呼应：同站点源属于同一个信任单元，因此指定 一个站点中的一个源就等同于指定该站点的所有源。存储源已经通过指定 它作出了有界的披露决定（参见§ 3.5 资源可见性升级和§ 7 Cross-Origin-Storage-Allow-Origin 标头），而 再要求额外满足全局普遍性，会使普通受限共享依赖于对通常为专有资源的、 与其无关的公开策展。先于 全局可披露门槛执行此检查，正是防止后续 全局可用性写入 撤销已列出源访问权限的机制。参见§ 8.2 跨站点 探测。

  5. 如果 entry 的全局可披露为 true：

    1. 如果 entry 的哈希不位于 PHL 中，则返回 null。

      注：公共哈希列表门槛 只适用于全局授权，也就是若无该门槛 披露原本可能触达 Web 上任何源的唯一情况。一个 全局可披露但其哈希 不位于 PHL 中的条目，不会 向仅通过该授权取得资格的源披露；而同时 位于存储源、显式源列表或任一者 同站点集合中的源已经在上方返回。

    2. 如果用户代理选择对此请求应用GREASE， 则返回 null。

      注：GREASE 也只 适用于全局授权。上方检查过的授权永远不会 到达此步骤：存储源及其同站点源是一个信任单元，而 显式源列表中的源是由 某个其 Cross-Origin-Storage-Allow-Origin 标头授权它的写入者有意指定的，该授权也涵盖其 同站点源。

    3. 返回 entry。

  6. 返回 null。

要在给定一个COS 条目或 null entry，以及一个 源 origin 的情况下应用 可用性门控，返回一个COS 条目或 null：

  1. 返回以 entry 和 origin 为参数运行确定 COS 披露所得的结果。

3.3. 创建和写入文件

由完成创建请求创建的 FileSystemFileHandle 具有一个关联的 请求的源，其值是在句柄 成功完成写入后，验证并存储将尝试把条目的源升级到的值。

每个寻址跨源存储文件系统的 FileSystemFileHandle 还具有一个关联的 COS 哈希，即它所寻址的COS 哈希；一个 关联的 COS 源，即获取它的源；以及一个 关联的 可读取布尔值，它决定 getFile() 是否可以通过该特定 句柄披露所寻址条目的字节。对于由完成读取请求返回的句柄，该值为 true，因为它已经通过 可用性门控；对于由 完成 创建请求返回的句柄，该值为 false，直到验证并存储针对同一句柄成功为止。

注：句柄寻址的是COS 哈希，而不是COS 条目。完成创建请求会为一个在COS 注册表中没有条目且可能永远不会有条目的哈希返回 一个句柄，因此在验证并存储创建条目之前，没有 可供它引用的条目。

注：这被刻意设计成每个句柄的属性。创建 请求 无论该哈希的条目是否已经存在都会返回句柄（参见 完成 创建请求），因此按条目制定规则会使任何源都能调用 getFileHandle() 并将 create: true，然后立即读取一个它 从未写入的条目，在不满足源、 PHL 成员资格或 GREASE的情况下获知其内容。本规范中的每项披露控制 都应用在读取路径上，因此按条目进行门控会使创建请求绕过 所有这些控制。要求调用者先提供正确字节，意味着通过创建所得句柄成功 读取时不会披露调用者原本没有的任何内容。

要在给定一个 promise result、一个 COS 哈希 hash、一个 CrossOriginStorageGetFileHandleOptions options、一个全局对象 global 和一个Realm realm 的情况下完成 创建请求：

  1. 令 requestedOrigins 为以 options["origins"] 为参数运行规范化 请求的源所得的结果。

  2. 如果 requestedOrigins 是一个列表，则把 requestedOrigins 设置为以 requestedOrigins 和以 global 为参数运行获取 COS 作用域上限所得结果为参数运行 应用 COS 作用域上限所得的结果。

  3. 令 handle 为创建新的 FileSystemFileHandle [FS] 的结果，其 定位器在 跨源存储文件系统中寻址 hash，并位于 realm 中。

  4. 将 handle 的COS 哈希设置为 hash。

  5. 将 handle 的COS 源设置为 global 的 相关设置对象的源。

  6. 将 handle 的请求的源设置为 requestedOrigins。

  7. 将 handle 的可读取设置为 false。

    注：此算法不查询COS 注册表， 也不修改它。它不能这样做： 它的结果必须与 hash 是否已经存储无关，否则创建 请求本身就会披露此前是否存在（参见§ 8.2 跨站点探测）。 因此，无论条目已经存在、从未写入，还是此刻正由其他人写入， handle 都会以完全 相同的条件返回，并且在该调用者提供字节之前不具有任何读取访问权。

    注：由于这里没有注册任何内容， 如果调用者请求一个句柄后将其放弃， 从未调用 createWritable() 或从未关闭由此得到的流， 注册表将保持与此前完全相同。其他源无法观察到该请求 曾经发生，并且任何哈希都不会被固定在某种会抑制后续读取的占位状态中。 参见§ 8.3 进行中的写入。

    注：requestedOrigins 仅在字节 已写入并验证后，才由验证 并存储通过 升级资源可见性来应用。这正是 使创建请求必须先提供完整字节才能扩大可见性的机制；参见 § 3.5 资源可见性升级。

  8. 在给定 global 的DOM 操作任务源上排入一个全局任务，以 兑现 result，并使用 handle。

要在给定一个 (DOMString or sequence<DOMString>) 或 undefined origins 的情况下规范化 请求的源，返回“*”、一个列表形式的源或 null：

  1. 如果 origins 不存在，则返回 null。

  2. 如果 origins 是“*”，则返回“*”。

  3. 令 list 为 « »。

  4. 对 origins 中的每个 candidate 执行（单个 字符串按只有 一项的列表处理）：

    1. 令 candidateOrigin 为在 candidate 上运行基本 URL 解析器 所得到的源。

      注：验证 COS 请求已经确认每个 candidate 都可解析为 非不透明源。

    2. 如果 list 不包含 candidateOrigin，则将 candidateOrigin追加 到 list。

  5. 返回 list。

注：在之后合并到 现有条目之前就在这里去重，可以确保源从条目 首次创建起就没有重复项，因此之后每次对它进行克隆也都保持无重复项。

当通过在定位器寻址跨源存储文件系统的句柄上调用 createWritable() 而获得的 FileSystemWritableFileStream 按照 [FS] 被关闭时，用户代理必须在 该关闭操作的 promise 被兑现之前，以该句柄为参数运行下方的 验证并存储步骤。

注：无论关闭是如何 触发的，此规则都适用：显式 close() 调用，或者其 源到达末尾的 pipeTo() 调用；后者默认也会关闭其目标。[STREAMS] 在流变为关闭状态时并不区分这两种情况， 此算法也同样不区分。

给定其流已被 关闭的 FileSystemFileHandle handle、完整写入的字节序列 bytes，以及关闭操作的 相关设置对象的源 origin，验证并存储 步骤如下：

  1. 令 hash 为 handle 的COS 哈希。

  2. 令 computedValue 为 bytes 的小写十六进制摘要，按照 [WEBCRYPTO]，使用 hash 的算法所命名的 算法计算。

  3. 如果 computedValue 与 hash 的值不完全相等：

    1. 使用“DataError” DOMException 拒绝关闭操作的 promise。

    2. 中止这些步骤。

    注：失败的写入没有任何需要清理的内容。 完成创建请求没有注册任何条目， 因此从未产生已验证字节的写入不会改动COS 注册表，而后续 针对同一哈希的 getFileHandle() 调用会得到与从未尝试过该写入时相同的 “NotFoundError”。 某个源已经写入的条目同样不会受到影响：该算法只会添加字节和授权。

  4. 将以下步骤排入 跨源存储队列：

    1. 令 entry 为COS 注册表中其哈希 等于 hash 的COS 条目（如果存在），否则为 null。

    2. 如果 entry 为 null：

      1. 将 entry 设置为一个新的COS 条目，其哈希为 hash， 字节为 bytes，源为空列表， 全局可披露为 false，并且存储源为空 集合。

      2. 将COS 注册表[hash] 设置为 entry。

      注：这是本 规范中唯一会向 COS 注册表添加条目的步骤，而且它只会在 bytes 已针对 hash 验证之后运行。两个 都发现该哈希不存在并并发写入的写入者都会到达这里； 后入队的那个 会发现前一个创建的条目，并只在下方添加自己的源和 授权。它们的字节哈希为相同值，因此只存储一次即可。

    3. 如果尚不存在，则把 origin追加到 entry 的存储源。

    4. 以 entry 和 handle 的 请求的源为参数运行升级资源可见性。

    5. 将 handle 的可读取设置为 true。

      注：只有此句柄变为 可读。另一个针对同一哈希、通过 尚未完成写入的不同创建请求获得的句柄仍然不可读。

在寻址 跨源存储文件系统的 FileSystemFileHandle 上调用的 createWritable() 必须生成一个 FileSystemWritableFileStream， 其内容 初始为空，而不论 keepExistingData 的值如何，也 不论所寻址的COS 哈希是否在COS 注册表中有条目。

注：[FS] 在其他情况下把 keepExistingData 定义为使用 现有文件内容初始化流。在这里遵循该行为会使调用者成为它从未持有之字节的存储 源。创建请求无论条目是否已经存在都会返回句柄，因此调用者可以为另一个源存储的哈希 打开可写流，什么也不写就将其关闭，并让继承的字节哈希为请求的值。这会 在从未查询源、公共哈希列表和 GREASE的情况下授予其读取访问权：这是由两个分别允许的操作组合出的可用性 门控绕过。 这与验证并存储要求 每次创建请求都提供完整内容的理由相同。

注：因此，一个在没有任何写入的情况下关闭的可写流 持有空字节序列，而它不会 哈希为调用者真正想要的任何条目的请求值，所以验证并存储会像处理其他任何不匹配一样 以“DataError” DOMException 拒绝。如果实现 反而针对这种情况报告存储或 I/O 失败，就会把验证结果隐藏在一个 无关错误之后。

文件系统标准 [FS] 尚未定义可供依赖 规范挂接额外逐次写入验证到 FileSystemWritableFileStream 关闭步骤中的扩展点。在这样的挂钩存在之前，本节直接描述所需行为； 未来修订预计会正式与 [FS] 集成。

3.4. 存储已获取的资源

§ 9 与其他 规范的集成中列出的主机集成会存储它们 获取的资源，而不经过 FileSystemFileHandle。 它们的主机规范应当 在获取到的字节通过相应集成要求的完整性检查之后运行以下算法。

要在给定一个响应 response、一个字节序列 bytes、一个COS 哈希 hash、“*”、一个列表形式的字符串 或 null origins，以及一个环境设置对象 settings 的情况下把已获取的资源存入跨源 存储：

  1. 如果以 settings 的 全局对象为参数运行检查跨源存储 权限所得的结果为 false，则返回。

  2. 如果 origins 不为 null，则令 options 为 «[ "origins" → origins ]»； 否则为 «[ ]»。

  3. 如果以 hash 和 options 为参数运行验证 COS 请求所得结果不为 null， 则返回。

  4. 令 computedValue 为 bytes 的小写十六进制摘要，按照 [WEBCRYPTO]，使用 hash 的算法所命名的 算法计算。

  5. 如果 computedValue 与 hash 的值不完全相等，则返回。

    注：集成自身的完整性 元数据可以列出多个摘要，只要匹配 其中任意一个即可满足完整性检查。此步骤确保条目使用这些 精确字节实际产生的哈希作为键。

  6. 令 requestedOrigins 为以 options["origins"] 为参数运行规范化 请求的源所得的结果。

  7. 如果 requestedOrigins 是一个列表：

    1. 如果 response 是过滤响应，则令 internalResponse 为 response 的内部响应，否则为 response。

    2. 将 requestedOrigins 设置为以下结果：以 requestedOrigins 和以 internalResponse 的标头列表为参数运行解析 COS 作用域上限所得的结果为参数运行应用 COS 作用域上限。

    注：该上限来自已获取 资源自身的响应，因此提供 字节的服务器决定这些字节可以向哪些源披露。加载 Document 的 COS 作用域上限不起作用：其运营方 并不控制该资源，而且 若允许它授权接收方，任何站点都可以把另一个站点的资源声明为可与其选定的源 共享。用户代理从内部 响应读取标头，因此这同样适用于不透明的过滤响应，并且该标头 永远不会暴露给页面。

  8. 令 origin 为 settings 的源。

  9. 将以下步骤排入 跨源存储队列：

    1. 令 entry 为COS 注册表中其哈希 等于 hash 的COS 条目（如果存在），否则为 null。

    2. 如果 entry 为 null：

      1. 将 entry 设置为一个新的COS 条目，其哈希为 hash， 字节为 bytes，源为空列表， 全局可披露为 false，并且存储源为空 集合。

      2. 将COS 注册表[hash] 设置为 entry。

      注：与验证并存储一样， 只有在 bytes 已针对 hash 验证后才创建条目， 而集成的 integrity 检查已经完成了这种验证。针对同一哈希、仍在 进行中的 getFileHandle() 写入者不受影响：它不持有任何注册表状态，而其自己的验证并存储会 正常完成， 找到该条目并向其中添加自己的源和授权。

    3. 如果尚不存在，则把 origin追加到 entry 的存储源。

    4. 以 entry 和 requestedOrigins 为参数运行升级资源可见性。

注：与验证并存储一样，存储操作始终需要 完整字节，即使 条目已经“written”也是如此，因此不会泄露此前是否存在。集成在 网络获取之前进行的查找属于读取操作，受可用性门控和 § 8.2 跨站点探测中的探测注意事项约束。

3.5. 资源可见性升级

COS 条目的可见性可以 升级，但绝不能降级。

要在给定一个COS 条目 entry，以及“*”、一个列表形式的 源或 null requestedOrigins 的情况下升级 资源可见性：

  1. 如果 requestedOrigins 为 null，则返回。

    注：省略 origins 只请求同站点 可用性，而每个条目已经具有这种可用性（参见确定 COS 披露），因此没有 任何需要添加的内容。

  2. 如果 requestedOrigins 是“*”：

    1. 将 entry 的全局可披露设置为 true。

    2. 返回。

    注：这会添加全局授权；它不会 修改 entry 的源。已经 带有显式源列表的条目会保留它，因此该 列表中的每个源即使在条目变为 全局可披露之后，也会保持与PHL 无关的访问权限。这是 两种授权必须分开存储的核心原因；参见全局可披露。

  3. 对 requestedOrigins 中的每个 candidateOrigin 执行：

    1. 如果 entry 的源包含 candidateOrigin，则 继续。

    2. 如果 entry 的源的大小 等于用户代理的 最大源列表长度，则 跳出。

      注：任何剩余的 candidateOrigin 值都会从此次升级中被静默丢弃，因为 写入本身已经成功，而且用户代理应当在控制台记录 一条警告，说明该条目的源列表已经达到容量上限。

    3. 将 candidateOrigin追加到 entry 的源。

注：升级只会向源添加内容，或者把全局可披露 设置为 true。请求一个列表的写入者，会像扩展一个尚未 全局可披露的条目一样，扩展一个已经全局可披露的条目，因为两种授权彼此 独立：即使 “*”授权仍然有效，新列出的源也会获得与PHL 无关的访问权限。

注：任何站点，包括原始 存储者之外的站点，只要 同时提供哈希为该条目哈希的字节，就可以扩大条目的 源。这是有意如此设计的： 任何已经拥有某个哈希正确字节的站点，从构造上来说，对于该哈希所表示的内容都与 原始存储者同样具有权威性。

3.5.1. 原始存储者访问

已经成功完成写入某个COS 条目的源（也就是 该条目存储源中的任何源）之后始终可以通过 getFileHandle() 为其获取句柄，而不依赖条目的 源值，也 不依赖其哈希是否位于 PHL 中。 这与 Cache API 的模型相呼应，在该模型中，源始终可以访问自己存储的内容。

4. 跨源存储文件系统

跨源存储文件系统是一个文件系统根，不同于任何 源的存储桶文件系统或本地文件系统访问根，其 条目与COS 注册表的COS 条目项一一对应。

跨源存储文件系统不使用[FS]的普通逐次调用 权限检查 模型：从中获得的每个 FileSystemFileHandle 在返回给脚本之前都已经由 § 3.2 读取文件或§ 3.3 创建和 写入文件完全授权，因此在这种句柄上调用 getFile() 或 createWritable() 永远不会触发额外的 权限提示。

因此，此类句柄上的 queryPermission() 和 requestPermission() 永远不能 报告 “prompt”，因为不会出现提示。对于未通过创建请求获得的句柄，其写入模式必须报告“denied”， 否则 报告“granted”。

注：写入是句柄真正可能 不具备的唯一能力。只有创建请求会产生 可用于写入的句柄，因此在任何其他句柄的写入模式上报告“granted” 会声称拥有 createWritable() 实际会拒绝的能力。读取保持 “granted”，因为持有可读句柄的调用者可以通过它读取。请求权限不能 改变 任一答案，因为没有提示可显示，也没有可以记录授权的状态。

在一个寻址 跨源存储文件系统且其可读取为 false 的 FileSystemFileHandle 上调用 getFile() 必须以“NotAllowedError” DOMException 拒绝。 这涵盖两种不同情况：

  • 来自尚未完成写入的创建请求的句柄， 其所寻址的哈希在COS 注册表中没有条目。没有已验证的字节可 返回，并且调用者不能观察自己尚未完成的写入，就好像它是 文件的真实内容一样。

  • 来自针对某个由其他源已经写入的哈希的创建请求的句柄。 已验证的 字节存在，但该调用者既未提供这些字节，也未通过 可用性门控，因此它不能获知有关该条目的任何信息， 甚至 不能知道它是否存在。

注：两种情况下的拒绝完全相同，因此 不会披露任何内容。这就是为什么 “NotAllowedError” 在这里是安全的，尽管读取路径刻意避免使用它：该句柄属于 调用者自身，是通过它自己的创建请求获得的，而且句柄不能在任何 其他源中反序列化（参见§ 4.1 传输句柄）。因此该答案 永远不会跨越源边界，并且 相对于注册表内容保持恒定。对比§ 8.3 进行中的写入，在那里读取路径上的 不同错误会跨越该边界。

一旦句柄的可读取为 true，在其上调用的 getFile() 就返回一个 File， 其内容是所寻址条目的字节；这 正是 [FS] 已为文件 条目定义的行为，其 二进制数据即为这些字节。

寻址跨源存储文件系统的 FileSystemFileHandle 具有一个 文件系统定位器，其路径是一个只包含 单个 字符串的列表，即其COS 哈希的值，其 根 是跨源存储文件系统。

注：[FS] 将 name 定义为句柄 定位器路径的最后一个组件，因此这也确定了 name： 它就是 哈希。条目本身没有名称，而哈希是它拥有的唯一身份，因此 报告它所携带的信息不会像空字符串那样被丢弃。

条目没有名称，也没有包含它的目录，因此 [FS] 的大多数结构性表面 都没有可操作的对象。身份是例外，也是内容寻址条目 始终可以回答的唯一问题：COS 注册表对每个COS 哈希至多保存一个COS 条目，因此两个 句柄恰好在它们的哈希相等时寻址同一条目。

在一个寻址 跨源存储文件系统的 FileSystemFileHandle 上调用 isSameEntry()， 如果参数也寻址该系统，并由 同一个源获得，则当两个句柄的 COS 哈希项相等时必须返回 true，否则返回 false。

注：拒绝这样做会丢弃用户 代理已经掌握的信息。

如果传给 isSameEntry() 的参数不是由调用源获得， 或者它寻址的文件系统不是跨源 存储文件系统，则必须拒绝。

注：在这种情况下返回 false 会断言 两个句柄寻址不同条目， 这是关于调用源无权检查之句柄的断言。拒绝只表示 无法进行比较。

在寻址跨源存储文件系统的 FileSystemFileHandle 上调用的 move() 和 remove() 必须以 “NotAllowedError” DOMException 拒绝，并且必须保持任何所寻址条目不变。

注：条目由其存储 源中的每个源共享，因此允许 删除会使一个站点能够销毁其他站点所依赖的数据；删除应由 逐出以及用户自己的存储控制负责。重命名或重新设定父级没有任何 可操作对象，因为条目由其COS 哈希命名，并且没有包含它的目录。

注：撰写本文时，这两个方法都未由[FS]或文件系统 访问 API 定义 （WICG/file-system-access#214）， 因此错误名称沿用 removeEntry()， 这是 [FS] 为删除条目定义的操作：当未授予 readwrite 访问权限时，它会使用访问结果的错误名称拒绝。 在这里拒绝是准确的行为：这些操作有意义，但 被拒绝。

createSyncAccessHandle() 在这里无需额外规则：当句柄不位于存储桶文件系统中时，其步骤会以 “InvalidStateError” DOMException 拒绝，而跨源存储文件系统是一个与任何源 不同的文件系统根， 因此 [FS] 已经决定了 拒绝行为及其名称。

注：即使独立考虑，这也是本规范 所希望得到的结果。FileSystemSyncAccessHandle 会把可写文件描述符交给调用者，这会使其能够 修改条目的字节， 使之不再与其存储所依据的COS 哈希相符， 而该条目可以向其披露的其他每个源读取的都是同一份字节。

4.1. 传输句柄

FileSystemFileHandle 是一个可序列化对象 [FS]，因此寻址 COS 条目的句柄可以传递到另一个环境设置对象，例如使用 postMessage(message, options)。 这是获得这种句柄的第二种方式，另一种是 getFileHandle()， 因此这里也对它施加约束。

对于寻址 跨源存储文件系统的 FileSystemFileHandle， 给定 value 和 serialized，其序列化步骤还包括：

  1. 将 serialized.[[COSHash]] 设置为 value 的COS 哈希。

  2. 将 serialized.[[COSOrigin]] 设置为 value 的COS 源。

  3. 将 serialized.[[COSMayRead]] 设置为 value 的可读取。

给定 serialized、 value 和 realm，其反序列化步骤还包括：

  1. 如果 serialized.[[COSOrigin]] 与 realm 的 环境设置对象的源不是同源，则抛出一个 “DataCloneError” DOMException。

  2. 将 value 的COS 哈希设置为 serialized.[[COSHash]]。

  3. 将 value 的COS 源设置为 serialized.[[COSOrigin]]。

  4. 将 value 的可读取设置为 serialized.[[COSMayRead]]。

注：如果没有同 源检查，传输会一次性绕过本 规范中的所有披露控制。一个其可读取为 true 的句柄已经 针对请求它的源通过应用可用性门控；把它发送到另一个 源，会在从未针对该源评估源、 PHL 成员资格或 GREASE的情况下，把条目的字节交给它。这与 文件系统标准对句柄的现有处理方式一致，句柄同样只对 同源接收方有用。

注：可读取会随 句柄一起传输，因此尚未完成写入的创建请求句柄在传输后仍然不可读， 而读取请求句柄仍然可读，无需重新进行门控。在到达时重新门控，会使 调用者可以通过反复传输同一个 句柄来探测可用性。

5. 存储管理

5.1. 存储限制

用户代理必须限制一个源通过成功写入可向 COS 注册表贡献的总字节数，以 防止单个源 通过淹没缓存来尝试逐出其他源的条目。具体限制是 由实现定义的。如果某个源的写入将超过其 限制，用户代理必须 以“QuotaExceededError” DOMException 拒绝该写入， 并应向 控制台记录警告。

注：由于条目是内容寻址的，因此源 在同一哈希下反复写入相同 字节，不会在首次成功写入之外额外消耗配额；参见 § 2.2 COS 条目。

用户代理还具有一个由实现定义的最大源列表长度，即一个 正整数，用于限制单个源列表可以 包含多少源。该限制既在首次提供列表时执行（参见验证 COS 请求）， 也在之后把列表合并到现有条目时执行（参见 升级资源可见性），因此无论是一次调用还是 多次调用随时间累积产生的效果，都不能让条目的源无限 增长。除了限制内存使用之外，这也防止一个源列表被用作 未声明的“*”替代方案；参见§ 8.2 跨站点探测。

在这两个位置超过此限制时采用不同处理方式，因为两种调用 发生在操作中截然不同的阶段：

  • 在验证 COS 请求中，会在任何文件被获取、哈希或 写入之前检查该限制。超过限制的调用者会立即得到“TypeError”， 并且不会发生其他任何操作， 与其他任何格式错误的 origins 值的处理相同。

  • 在升级资源可见性中，该限制只能由于 多次独立写入调用所请求源的累积效果而达到，这些调用可能由彼此无关的源在 很长时间内发起，而且只有在本次调用的字节已经完成哈希、 验证并持久存储之后才会检查。在这个阶段拒绝写入会因为一个无关的记录维护限制而丢弃 一次成功、已经验证且可能体积很大的写入，而且 甚至无法归因于某个单独调用者的错误。因此写入会保持 成功，只有超过容量的源会从源中被丢弃，并记录 控制台警告。这与对 从更宽松到更受限请求的现有处理相呼应：一个源请求 如果无法完全满足，则会被静默截断，而携带它的写入仍然 成功。与本规范其他位置的§ 8.4 可用性门控一致， 调用者事后没有可靠方法确认其请求的源是否 实际被添加：以后以该 源调用 getFileHandle() 即使源已经添加也仍可能失败（例如，因为条目已 被逐出或用户代理限制了请求），因此其结果也不能被解释为 任一方向上的确认。

5.2. 逐出

本节是非规范性的。

在存储压力下，用户代理可以从COS 注册表中逐出条目， 例如根据最近访问各条目的存储源， 对条目采用最近最少使用策略。用户代理应当提供设置 UI，使 用户能够检查存储了哪些文件、哪些源访问过每个文件，以及手动 删除条目或清除所有跨源存储数据。

当用户清除某个源的站点数据时，用户代理应从所有包含该源的 存储 源集合中移除该源。如果移除后，某个COS 条目的 存储 源为空，用户代理可以考虑删除该条目。

5.3. 手动添加的条目

本节是非规范性的。

上述设置 UI 可以允许用户把磁盘上已经拥有的文件直接添加到 跨源存储中（例如，用户独立于任何网站下载的 AI 模型）， 而无需任何脚本调用 getFileHandle()。 这样的条目 没有可用于归因此次写入的请求源，这带来两个命令式 API 本身无法回答的问题：

  • 就§ 3.5.1 原始存储者访问而言， 谁是原始存储者？没有人：该条目的存储源初始为空。 因此，没有任何源可以免于 每个请求源原本都要遵守的普通可用性门控和源检查。 这是正确的结果，因为实际上没有任何源 写入这些字节。

  • 这样的条目是否应像省略 origins 的普通写入那样仅限制为同站点？不应：“同站点”只有相对于 请求源才有意义，而手动添加没有请求源，因此没有可供“同站点” 指代的站点。用户代理应当使这样的条目全局 可披露， 并让其显式源列表保持为空，因为手动 预置文件只有在其他源实际上能够发现它时 才能达到其目的（即让用户尚未访问的站点复用用户磁盘上已经拥有的文件）。 用户代理的设置 UI 还可以让用户选择更窄的作用域。

以这种方式添加后，一个条目在其他方面与网站通过 getFileHandle() 写入的条目没有区别： 相同的 可用性门控和可见性 升级规则适用于它，与具有相同授权的任何其他条目完全相同。 这包括当条目最终 全局可披露时进行位于 PHL 中检查， 而全局可披露正是手动添加的默认值。

5.4. 来源元数据

本节是非规范性的。

COS 条目刻意不记录 其字节来自何处。身份仅由 哈希决定：无论有多少源存储 相同字节，或这些字节是从多少 URL 获取的，它们都是同一条目（参见§ 2.2 COS 条目）。URL 是 某个写入者一次 获取的属性，因此对于多个源写入的条目，不存在非任意方式选择其中一个 URL； 它不像字节那样可验证（参见§ 8.1 资源完整性）； 而且与源中较粗粒度的值相比，它携带了更多关于用户浏览的信息， 因为路径或查询字符串可能标识特定文档、账户或会话。在条目上记录它因此会绕过 源和§ 8.4 可用性 门控所施加的披露限制，形成一个高熵信号通道。

不过，想要这些信息的动机确实存在：用户在§ 5.2 逐出中所述的 设置 UI 中查看一个数 GB 大小的文件，以及开发者调试为什么某次 getFileHandle() 调用未命中时，都希望知道文件 来自何处。用户代理可以通过在条目旁保存实现私有的来源记录来满足这一需求 （例如，其每个存储源从哪个 URL 获取 字节，以及何时获取），前提是该记录被视为保存在 条目之外的用户代理状态：

  • 它永远不会暴露给脚本。本规范没有任何内容会披露它， 以后添加的任何内容也不应这样做：无论是 getFileHandle() 还是它 返回的 FileSystemFileHandle 都不应暴露此类记录是否存在，更不用说其 内容。特别是，请求源不得观察到并非由其自身 产生的记录。

  • 它只能通过受信任的非 Web 表面显示：用户代理自身的设置和存储 检查 UI、开发者工具，以及（如果用户代理有扩展平台） 受显式用户授予权限保护的扩展 API，与其他 暴露浏览历史的 API 处于同一级别。参见本 仓库中的浏览器扩展集成点说明文档，了解 正在考虑的扩展表面。

  • 它未经验证，并且会以此方式呈现。其中的 URL 是写入 字节的源所作的声明。只有哈希才能保证内容（参见§ 8.1 资源完整性）。两个源可以为同一条目记录不同 URL， 而其中任一个 都可能不准确或具有故意误导性。

  • 它与条目及其归属源具有相同的生命周期。当 条目被逐出或删除时，它也会被丢弃；当某个源从存储源中移除时，归属于该源的部分也会被丢弃， 包括用户清除 该源的站点数据时（参见§ 5.2 逐出）。

由于此类记录对内容不可见，因此用户代理是否保存以及保存多少 完全由实现决定。本规范中的任何内容都不依赖它，而站点也无法检测 它是否存在。

6. 权限策略集成

本规范定义一个由字符串“cross-origin-storage”标识的策略控制功能 [permissions-policy]。其默认允许列表 为 self。

[permissions-policy]在 Document 上定义了允许使用， 但是 CrossOriginStorageManager 也暴露在 WorkerGlobalScope 上， 而它没有自己的 Document。 因此，该检查针对调用的全局对象来表述：worker 全局会传递解析到拥有它的 Document， 并且每一个文档 都必须允许该功能。

要在给定一个全局对象 global 的情况下检查跨源存储权限，返回一个 布尔值：

  1. 如果 global 是一个 Window 对象，则：

    1. 令 document 为 global 的关联 Document。

    2. 如果 document 为 null，则返回 false。

    3. 如果 document 不允许使用 “cross-origin-storage” 策略控制功能， 则返回 false。

    4. 返回 true。

  2. 如果 global 是一个 WorkerGlobalScope 对象，则：

    1. 令 owners 为 global 的所有者集合。

    2. 如果 owners为 空，则返回 false。

    3. 对 owners 中的每个 owner 执行：

      1. 如果 owner 是一个 Document 并且 owner 不允许使用 “cross-origin-storage” 策略控制功能， 则返回 false。

      2. 如果 owner 是一个 WorkerGlobalScope 对象，并且以 owner 为参数运行 检查跨源 存储权限所得结果为 false，则返回 false。

    4. 返回 true。

  3. 返回 false。

对于该算法返回 false 的全局对象，从其中发起的每次 getFileHandle() 调用都会在任何哈希验证、注册表查找或写入 发生之前，以 “NotAllowedError” DOMException 拒绝。

注：通过所有者集合进行解析，正是防止该功能 只在名义上可选择退出的机制。由 blob: URL 创建的 worker 运行在其创建页面的 源中，并与该页面完全共享跨源存储视图（参见 § 3 CrossOriginStorageManager 接口），因此如果 检查只查询全局对象自身的 Document， 那么在每个 worker 中都会平凡地满足检查，而把调用移到 new Worker(URL.createObjectURL(&hellip;)) 就会绕过 cross-origin-storage=() 策略， 而其他方面完全不变。

注：ServiceWorkerGlobalScope 的 所有者集合为空，因此 此算法在那里返回 false。这源自所有者集合的定义：它是一个 活跃性关系，在创建 worker 时填充，用于判断该 worker 是否仍然被活跃地需要。service worker 刻意不与任何 Document 具有此类关系： 它的注册会被持久保存，用户代理会响应事件启动该全局对象，而且它可以在完全没有 service worker 客户端的情况下运行。调用 register() 的客户端因此在注册时可知，但在该全局对象运行时 通常已经消失，并且一个运行中的 service worker 会服务多个 策略可能不一致的客户端。

注：覆盖 service worker 需要捕获策略， 而这项工作属于 [permissions-policy]和[service-workers]。本规范 更倾向的形式是，从 service worker 自身脚本响应上的 Permissions-Policy 标头派生其策略，就像其策略容器 已经携带该响应的 CSP 一样：它始终由该源控制，并在每次更新检查时 重新评估。对注册客户端策略做快照会使选择退出 变得陈旧，因为从标头中删除该功能要等到注册碰巧更新时才会生效。在这样的 模型存在之前，失败关闭是唯一不会被用来绕过选择退出的答案。

注：SharedWorkerGlobalScope 的 所有者集合可以包含多个 具有不同策略的 Document， 并且在 worker 的生命周期中会不断获得和失去所有者。 要求每个所有者都允许该功能，意味着只要一个所有者不允许它，就会对整个共享 worker 禁用 跨源存储，而且两个 getFileHandle() 调用之间的答案可能发生变化。另一种方案——只要求有一个 宽松的所有者——会使任何允许该功能的文档都可以代表 不允许它的文档重新启用该功能。

7. Cross-Origin-Storage-Allow-Origin 标头

一个其源列表非空的COS 条目 可以向写入源不控制的源披露，然而该列表是由脚本（通过 origins） 或标记声明的，而成功实现脚本或标记注入的攻击者可以设置这两者。为了把该声明 与其字节被披露之源的运营者绑定，并采用被注入内容无法伪造的形式，本 规范定义了一个响应标头，用于限制这种声明可以指定哪些源。

Cross-Origin-Storage-Allow-Origin 响应标头携带一个 COS 作用域上限：一个 集合， 其中包含写入可以在非同站点 源列表中指定的源。提供字节的一方发送 该标头，因此它从所披露字节背后的响应中读取：

  • 对于 getFileHandle() 写入，其字节可能由 脚本生成，并且没有自己的来源响应，则使用创建调用全局对象的 Document 所使用的响应；对于 worker，则使用 拥有它的 Document 的响应（参见获取 COS 作用域上限）。

  • 对于主机集成，则使用其字节被存储之已获取资源的响应 （参见把已获取的资源存入 跨源存储）。这是资源自身服务器的响应，而它 不一定是加载该资源的 Document 所在服务器。

声明的列表会与 上限进行交集运算（参见 应用 COS 作用域上限），因此上限永远只能缩小声明范围。

注：该标头是提供字节的一方作出的授权。 它指定的源，即最终读取者，不会被查询，也不会发送任何内容：列出的源只会在稍后 像其他读取者一样调用 getFileHandle() 来读取COS 哈希。 这与 Access-Control-Allow-Origin [FETCH] 的方向相反，后者由 持有资源的服务器选择允许特定源读取。这里则由字节提供方 限定以后谁能从跨源存储读取这些字节，而且写入 页面上的注入内容无法扩大该范围，因为它不能设置提供方的响应标头。

注：该标头仅适用于列表形式。 同站点默认值不会指定任何跨源 接收者，因此无需授权，而“*”形式在读取路径上由 可用性门控根据公共哈希列表进行约束，而每用户秘密值 永远无法通过该列表，因此也不需要写入时上限。要求“*”提供标头还会破坏 零配置全局共享场景，却没有关闭公共哈希列表尚未关闭的任何途径。

要在给定一个标头 列表 headers 的情况下解析 COS 作用域上限，返回一个集合形式的 源：

  1. 令 value 为从 headers 中 获取、解码并拆分 “Cross-Origin-Storage-Allow-Origin”所得的结果。

  2. 如果 value 为 null，则返回一个空集合。

  3. 令 ceiling 为一个空集合。

  4. 对 value 中的每个 token 执行：

    1. 从 token 中去除前导和尾随 ASCII 空白。

    2. 如果 token 是空字符串，则继续。

    3. 令 origin 为在 token 上运行基本 URL 解析器所得的源。

    4. 如果 origin 是失败或是一个不透明源，则返回一个空集合。

      注：这包括值为“*”的 token，因为它无法解析为源。 Cross-Origin-Storage-Allow-Origin 标头只能枚举有限数量的具体 源；“*”不是允许的值，因为“任意源”的上限 会使 注入内容能够声明它想要的任何接收者，从而破坏该标头的全部 目的。 无界 披露只能通过“*”源形式实现，该形式 由 公共哈希列表进行门控，并且从不查询此 标头。格式错误或含有“*”的标头 不授权任何内容，与缺少标头完全相同；即失败关闭。

    5. 将 origin追加到 ceiling。

  5. 返回 ceiling。

注：获取、解码并拆分会按 U+002C (,) 拆分， 因此标头 值中的源使用逗号分隔，与 Timing-Allow-Origin [RESOURCE-TIMING]以及 列表值 HTTP 响应标头的一般 惯例一致，尽管同级 crossoriginstorage HTML 内容 属性为了匹配其宿主语法而使用空格分隔。两者最终都会解析为相同的 源集合。

要在给定一个全局对象 global 的情况下获取 COS 作用域上限，返回一个集合形式的 源：

  1. 如果 global 是一个 Window 对象，则：

    1. 令 document 为 global 的关联 Document。

    2. 如果 document 为 null，则返回一个空集合。

    3. 返回 document 的COS 作用域上限。

  2. 如果 global 是一个 WorkerGlobalScope 对象，则：

    1. 令 owners 为 global 的所有者集合。

    2. 如果 owners为 空，则返回一个空集合。

    3. 令 ceiling 为 null。

    4. 对 owners 中的每个 owner 执行：

      1. 令 ownerCeiling 为一个空集合。

      2. 如果 owner 是一个 Document， 则将 ownerCeiling 设置为 owner 的 COS 作用域上限。

      3. 否则，如果 owner 是一个 WorkerGlobalScope 对象，则将 ownerCeiling 设置为以 owner 为参数运行获取 COS 作用域上限 所得的结果。

      4. 如果 ceiling 为 null，则将 ceiling 设置为 ownerCeiling； 否则将 ceiling 设置为 ceiling 与 ownerCeiling 的交集。

    5. 返回 ceiling。

  3. 返回一个空集合。

要在给定一个列表形式的源 requestedOrigins 和一个 集合 形式的源 ceiling 的情况下应用 COS 作用域上限，返回一个列表形式的源或 null：

  1. 从 requestedOrigins 中移除每个 ceiling 不包含的源。

    注：缺少于COS 作用域 上限中的接收方会被丢弃，而写入仍然 成功，这与在升级资源可见性中丢弃超长升级的多余部分相同。用户代理应当 记录控制台警告，并指出 每个被丢弃的源。

  2. 如果 requestedOrigins为 空，则返回 null。

    注：如果一个列表的所有 成员都被丢弃，那么写入将不再有任何已授权的 跨源接收方，因此回退到同站点默认值。字节仍会被 存储；只有未经授权的披露会被阻止。

  3. 返回 requestedOrigins。

每个 Document 都有一个COS 作用域上限，即一个集合形式的源， 在创建文档时，它会被设置为以用于 创建该文档的响应的标头列表为参数运行解析 COS 作用域上限 所得到的结果。

注：对 worker 的所有者集合取交集，与 检查跨源存储权限相呼应：只有当每个拥有它的 Document 直接或间接都授权某个源时，该源才位于 worker 的上限中。由于 blob: worker 与其创建页面共享相同 源和完全相同的跨源存储视图（参见 § 3 CrossOriginStorageManager 接口），如果上限 只查询 worker 自身， 那么每个 worker 的上限都会为空，把列表作用域的写入移入 new Worker(URL.createObjectURL(&hellip;)) 就会移除页面授权的接收方； 对所有者的上限求交集，可以保留该授权，同时又不允许任何单个 所有者扩大它。

从 Document 的 COS 作用域上限所对应的响应中填充该上限， 需要 在 [HTML] 的文档 创建步骤中加入挂钩，就像[permissions-policy]和[CSP]在 响应处理时填充一样。在这样的挂钩存在之前，本节直接描述 所需行为；未来修订预计会正式集成它，并同时处理[FS]在§ 3.3 创建和写入文件中指出的挂钩。主机集成不需要这样的 挂钩：它们 会把获取到的响应传给把已获取的资源存入跨源 存储，后者从中读取 上限。

8. 隐私和安全注意事项

除使用 RFC 2119 关键词的地方外，本节是非规范性的；另请参见 仓库中的安全和隐私问卷。

8.1. 资源完整性

每个COS 条目都以加密哈希作为键， 并根据该哈希验证其字节（参见 § 3.3 创建和写入文件）。因此，站点可以确信 通过 getFileHandle() 获得的文件，与它自己获取 hash 时得到的 字节完全相同。开发者无法枚举跨源存储的内容，也无法 在不知道文件哈希的情况下访问文件。

COS 哈希不是秘密。它是一个 内容标识符，任何已经拥有文件的人都可以轻易计算出来， 而且对于本规范面向的这类广泛分发资源，它通常属于公开信息， 经常会与模型或库的发布一起公布。因此，知道哈希足以查找条目， 但它本身不授予任何访问权限：查找是否成功完全由源和 § 8.4 可用性门控决定。开发者不得把未公开的哈希 当作访问控制机制；对某个特定文件感兴趣的 攻击者无需猜测其哈希，只需获得该文件本身 （参见§ 8.2 跨站点探测）。

8.2. 跨站点探测

如果某个资源只被少量站点使用，那么能够获知该资源 存在于跨源存储中的攻击者，就可以推断用户很可能访问过这些站点中的某一个。由于 getFileHandle() 是获知资源是否存在的机制，因此每次调用 实际上都是一次探测。本规范中的两个独立机制限制探测可以 获知什么：

  • 源（参见 § 3.5 资源可见性升级）允许存储 源把披露限制为选定的一组源以及与它们同站点的源，因此专有或低流行度资源 完全不必 在全局范围内可探测。

  • § 8.4 可用性门控还会阻止把一个 “*”作用域资源披露给其存储源之外的 请求源，除非哈希位于 PHL 中， 因而用 origins: “*”存储的资源 不会自动变得可由 Web 上每个源探测。此门槛只适用于 “*”作用域 条目；对于列表作用域和同站点作用域的条目，第一个项目符号中的限制是唯一 门槛，因为存储源已经显式限制了这些条目的披露范围。

第一个项目符号只有在“选定的一组源”仍明显小于整个 Web 时才成立。 origins 的形式本身并不能阻止调用者 枚举非常大量的源（例如，根据公开热门站点排行组装的列表）， 这在功能上会近似全局披露，同时绕过只有“*”才要求的 刻意、显式选择加入。最大源列表 长度（参见 § 5.1 存储限制）对此进行约束：一个足以满足真正 多站点用例 （共同控制下少量相关源）但远小于任何有意义的 “每个源”近似值的限制，可以防止源的受限源形式被用作 未声明的“*”替代方案。

用户代理还应当对来自单个源的重复 getFileHandle() 调用进行速率限制或其他节流，并可以应用 设备端启发式方法（例如检测对看起来按用户生成的哈希的请求模式） 来识别并阻止探测尝试，而不论被探测的 哈希是否位于 PHL 中。

由§ 9 与其他规范的集成中的主机集成之一执行的查找 同样是一次探测，即使它不会向页面暴露任何错误：站点可以观察到自己的 服务器是否收到回退请求，而这携带的单个位信息与这里的“未找到” 结果相同。这种查找不会披露本规范门槛之外的任何内容，而且 这些门槛同样适用于它。不过，只有当来自这些 表面的查找也与 getFileHandle() 调用一起计数时，速率限制才有效，因为 可脚本化的集成同样可以轻易地在循环中发出它们。

8.3. 进行中的写入

对每个源而言，已经请求但尚未完成的写入必须与 从未被写入过的哈希无法区分。本规范通过结构设计实现这一点：COS 条目只有通过验证并存储或 把已获取的资源存入跨源 存储才会被加入COS 注册表， 而在两种情况下都只有在完整字节 已针对哈希验证后才会发生。完成创建请求既不读取也不写入 注册表。因此 没有可供读取观察的占位状态，也没有读取路径上的任何分支可以在 应用可用性门控之前 给出答案。

另一种方案——在发出创建请求时注册占位符，并用可区分的错误拒绝 对它的并发读取——会使调用者获知某个源此刻正在写入 特定哈希。这一个比特看似无关紧要，但事实并非如此。它将：

  • 对任何源可用，包括对该条目完全没有任何授权的源，因为占位符 不携带授权，而且读取会在确定 COS 披露运行之前就得到回答；

  • 适用于任何哈希，包括不位于 PHL 中且永远也不可能位于其中的哈希，因此攻击者可以 使用从每用户值派生的哈希，而这正是§ 8.6 指纹识别 所要发现的模式；

  • 不经过GREASE，因为它只应用于到达门控 步骤的披露， 所以这个比特完全没有噪声；

  • 无需提供任何字节，因此无论是每源存储限制 还是 § 5.2 逐出都无法限制一个源可以创建多少这样的比特。

因此，嵌入两个站点的跟踪器可以在第一个站点生成任意宽度的标识符， 并在第二个站点读回它，而且没有任何存储成本，同时绕过源、 公共哈希 列表和 GREASE。占位符还会成为拒绝服务 向量：固定某个真正热门资源的哈希，会在占位符存活期间阻止所有其他源读取 该资源。

注：这种设计的代价是，一个调用者无法 发现另一个调用者已经正在下载 大型文件，从而无法避免开始一次重复下载。这确实是代价，也是 本规范早期草案在这里使用可区分错误的原因。真正重要的场景中， 可以在单个源内使用 Web Locks、BroadcastChannel 或共享 worker 来弥补， 它们都不会 跨越源边界披露任何信息。跨源情况下，这种节省基本只是理论上的：两个互不相关的 源必须恰好同时竞争同一个哈希，而且在双方都尚未 写入条目时，它也不会向另一方披露，除非它位于 PHL 中。

注：“NotAllowedError” 仍然是针对 尚未完成写入的创建所得句柄上 getFile() 的响应（参见§ 4 跨源存储文件系统）。该答案 相对于注册表保持恒定，而且只会到达发出该请求的源，因为 句柄不能跨源反序列化（参见§ 4.1 传输 句柄），因此它不是一个通道。

8.4. 可用性门控

来自存储 源之外源的 getFileHandle() 读取是否成功，始终取决于请求源是否 被允许读取该条目，这由源控制。对于“*”作用域条目，还有第二个 独立问题：用户代理是否愿意披露该条目 是否存在，这由PHL 成员资格和GREASE控制。对于这种条目，两者都必须 成立；对于列表作用域或同站点作用域条目，只适用第一个问题。 规范性算法参见§ 3.2 读取文件。因此，“NotFoundError” 并不能 证明资源不存在：它可能表示资源不存在、请求 源超出作用域、“*”作用域资源的哈希尚未（或永远不会）位于 PHL 中，或者 GREASE 抑制了真实阳性。开发者不得把“NotFoundError” 理解为 比“回退到网络”更具体的含义。

注：在支持第三方 cookie 的用户代理中， “*”授权使跟踪器跨站点关联 用户访问的能力不会比第三方 cookie 已经能够做到的更强。单独的PHL 无法限制这一点：攻击者可以通过选择写入哪些单独 符合 PHL 条件的资源子集来构造跨站点标识符。阻止第三方 cookie 的用户代理仍然可以提供“*”授权，只要它限制跨站点披露，例如使用 以顶层站点为键、页面上所有 frame 共享的小规模 跨站点查找预算，让计数在一个时间窗口内跨重载持续存在，并且只在 用户手势之后共享已写入条目。README 中的 隐私注意事项描述了这些缓解措施。

8.5. GREASE

用户代理可以应用GREASE（生成随机扩展并保持 可扩展性）：偶尔像 可披露条目不存在一样响应，即使§ 8.4 可用性门控原本 允许披露。这样会加入噪声，使站点更难区分真实不存在 与出于隐私目的产生的假阴性，类似于 UA Client Hints所采用的技术。

GREASE 只适用于仅通过全局 可披露 授权取得资格的源，也就是公共哈希列表所门控的同一种情况（参见确定 COS 披露）。用户 代理不得把它应用于存储源、显式 源列表中的源，或与其中任一者同站点的源。

应用 GREASE 的用户代理必须根据相关条目的大小作出适度判断。 对于小条目，回退到网络获取的成本很低，偶尔出现 假阴性是合理的隐私权衡。用户代理不得对那些大小使虚假重新下载的成本 明显与隐私收益不成比例的条目应用 GREASE （例如 GB 级 AI 模型权重），因为那里的假阴性会迫使进行完整、 可观察且成本高昂的重新下载。

8.6. 指纹识别

攻击者通过探测跨源存储能够提取的信息量，受到被探测资源 流行度的限制。获知用户拥有非常热门的资源，例如常见 AI 模型 或广泛使用的 JavaScript 库，只能说明用户访问过使用它的（可能非常 多的）站点之一。获知用户拥有稀有或唯一资源则更具信息量。 用户代理应当应用设备端启发式方法，检测其哈希看起来 刻意对每个用户保持唯一的资源（例如，只被单个 站点写入过的哈希，或以异常高频率请求的哈希），并将这种模式视为探测尝试， 而不依赖名义上的 PHL 状态。

9. 与其他规范的集成

本节是非规范性的。

这里定义的COS 注册表也可以 通过四种主机集成访问，而不需要直接经过 getFileHandle()。 每种 集成都在各自的主机规范中定义。本规范定义共享的 底层概念（COS 哈希、COS 条目、可用性门控以及 公共哈希 列表），以及这些集成应当基于的把已获取的资源存入跨源 存储步骤。

  • HTML：在已经 带有 integrity [SRI]的 link 和 script 元素上的 crossoriginstorage 属性，已通过 whatwg/html#12770 向 WHATWG 提议。

  • JavaScript：一个由主机定义的 crossOriginStorage 导入属性，可与 integrity 一起使用，基于 导入属性 提案，已通过 whatwg/html#12771 向 WHATWG 提议。

  • CSS：一个 cross-origin-storage() <request-url-modifier>， 可与 integrity() 一起使用， 已通过 w3c/csswg-drafts#14056 向 CSS 工作组提议。

  • Fetch：一个 crossOriginStorage RequestInit 选项，可与 integrity [FETCH] 一起使用，已通过 whatwg/fetch#1954 向 WHATWG 提议。 这一种形式没有由主机定义的目标，因此从COS 注册表提供的 Response 如何报告其 MIME 类型、状态和其他元数据 是该规范需要解决的开放问题；COS 条目只存储字节。

仅为说明，下面展示同一个全局共享资源通过四种形式分别选择加入 跨源存储：

<script src="popular-library.js" integrity="sha256-abc123..." crossoriginstorage="*"></script>

import data from "popular-resource.ext" with {
  integrity: "sha256-abc123...",
  crossOriginStorage: "*",
};

@font-face {
  font-family: "Popular Font";
  src: url("popular-font.woff2" integrity("sha256-abc123...") cross-origin-storage(*));
}

const response = await fetch("popular-resource.ext", {
  integrity: "sha256-abc123...",
  crossOriginStorage: "*",
});

这些代码片段仅用于说明。本规范没有定义这些语法中的任何一种。 每种形式的权威语法，包括受限源列表如何书写， 都属于各自的主机规范。这些拼写方式刻意 不同：RequestInit 成员可以接受 sequence<DOMString>，与 origins 完全匹配，而属性值、 导入属性值和 CSS 修饰符参数都只能携带文本。

预计这四种形式都共享同一种处理模型：首先查询COS 注册表中是否存在匹配且可披露的条目， 然后才回退到网络获取；并把 成功获取且通过完整性验证的资源存入COS 注册表，供其他源复用， 与 getFileHandle() 的做法完全相同。存储步骤 是把已获取的资源存入跨源 存储，每种集成都使用获取到的 响应运行该步骤。因此，受限源值受到该资源响应上的 Cross-Origin-Storage-Allow-Origin 标头限制，该标头由提供字节的服务器发送 （参见§ 7 Cross-Origin-Storage-Allow-Origin 标头）。有关 这些集成的讨论属于将承载它们的主机规范的跟踪器， 而不是本仓库的问题跟踪器。
