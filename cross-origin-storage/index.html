摘要

跨源存储（COS）是一种内容寻址缓存，允许 Web 应用跨不同源存储和检索大型文件，例如 AI 模型、WebAssembly 模块和广泛使用的 JavaScript 库。文件通过其加密哈希而非 URL 进行标识，因此，某个源获取过一次的字节完全相同的资源，可以由用户代理允许的任何其他源复用，而无需再次下载。为了防止通过缓存中是否存在某个文件来推断用户访问过哪些网站，只有其哈希达到类似 k-匿名的流行度门槛时，才允许跨源披露该文件。

1. 引言

本节是非规范性的。

存储通常按源分区，以保护用户的安全和隐私。这是正确的 默认做法，但对于一小类体积庞大、使用广泛且公开分发的 资源（AI 模型、WebAssembly 模块、JavaScript 库、游戏引擎和大型 Web 字体），这种做法并不适合， 因为无论哪个站点请求这些资源，它们都是逐字节完全相同的文件。当两个 互不相关的源分别依赖同一个 8 GB 模型时，按源分区的存储会迫使 用户将该模型下载并保存两次，这会浪费用户的带宽、存储空间 和电量，也会浪费整个网络的资源。

跨源存储（COS）是一种内容可寻址缓存，以密码学哈希值而非 URL 为键，使用户代理能够在选择使用此类资源的各个源之间， 共享该资源的一份存储副本。将资源存入 COS 始终是存储源明确选择执行的 行为，而且用户代理可以拒绝确认某个资源是否存在，即使对于原本 获准读取该资源的源也是如此；参见§ 8 隐私 和安全注意事项。

本规范的入口点是 requestFileHandle() 方法，通过 crossOriginStorage 暴露： 

const hash = {
  algorithm: 'SHA-256',
  value: '8f434346648f6b96df89dda901c5176b10a6d83961dd3c1ac88b59b2dc327aa4',
};
try {
  const handle = await navigator.crossOriginStorage.requestFileHandle(hash);
  const file = await handle.getFile();
  // 对该文件执行某些操作。
} catch (err) {
  if (err.name === 'NotFoundError') {
    // 跨源存储中没有（可披露的）该文件；改为从网络获取。
  }
}

本规范复用 FileSystemFileHandle、 FileSystemWritableFileStream， 以及文件系统标准中的相关 基础设施 [FS]，将其作用域限定于一个专用文件系统，该文件系统 跨源共享，并且独立于任何源的私有文件系统或用户可见的文件系统。

本规范定义命令式 JavaScript API，以及供宿主集成使用的共享存储步骤。 相关提案将同一个底层缓存集成到其他宿主 规范中：HTML 的 crossoriginstorage 属性，用于 link 和 script， 以及 crossOriginStorage JavaScript 导入属性、CSS cross-origin-storage() <request-url-modifier>，以及 crossOriginStorage RequestInit 选项，用于 fetch()。每一项均在 各自的宿主规范中定义；参见§ 9 与其他规范 的集成。

2. 概念

2.1. 哈希值

一个 COS 哈希值是一个结构体，包含 以下项：

algorithm

一个字符串， 指定一个由 [WEBCRYPTO] 识别的哈希算法名称，例如 "SHA-256"。

value

一个字符串，是以下算法生成的摘要的小写十六进制编码： algorithm。 对于 "SHA-256"，其长度为 64 个字符。

该 algorithm 字典成员的类型是普通的 DOMString，尽管其取值空间恰好是 [WEBCRYPTO] 的 哈希算法所接受的名称集合。一个 HashAlgorithmIdentifier 的类型是 (object or DOMString)，而其 object 分支 会由 [WEBCRYPTO] 规范化为具有 Algorithm 结构的 字典，使调用者能够向需要额外参数的算法传递 这些参数（例如 {name: "HMAC", hash: "SHA-256"}）。哈希 算法不接受此类参数， algorithm 的存储、 比较和往返传递都将其视为内容可寻址 键的一部分，而且本规范 示例中的每次使用都是一个纯字符串；此处允许任意对象不会增加任何能力，却会使 相等性判断和序列化 变得不必要地复杂。因此，DOMString 是此字段 更受限且更正确的类型。

两个 COS 哈希值称为相等，条件是它们的 algorithm 值以不区分 ASCII 大小写的方式匹配，且它们的 value 值完全 相等。

注： value 已经被规范性地要求使用小写形式（见上文），因此对它的比较 就是普通的 字符串比较。algorithm 没有规范性规定的大小写形式，因此对它的比较采用 不区分 ASCII 大小写的方式。

一个内容可寻址 存储以以下判定作为其条目的键匹配依据： 相等性，其比较对象是 COS 哈希值：两个具有 相同字节和相同哈希算法的文件属于同一个条目，无论有多少个源 存储了它们，也无论它们是从多少个 URL 获取的。

2.2. COS 条目

每个用户代理都有一个唯一的 COS 注册表，它是一个映射，将 COS 哈希值映射到 COS 条目结构体， 由所有使用跨源存储的源共享。一个 COS 条目具有以下项：

hash

一个 COS 哈希值。

bytes

一个字节序列，其使用 hash 的 algorithm 计算得到的摘要等于 hash 的 value。

注：条目只有在满足以下条件后才会添加到 COS 注册表： 写入方已提供这些字节，并且 用户代理已验证这些字节；参见验证并存储。已经请求但 尚未完成的写入在注册表中完全没有表示，因此，在读取路径上，正在进行的 写入与不存在的写入无法区分。参见§ 8.3 正在进行的写入。

origins

一个列表，其中的源被明确授予跨源读取访问权限，此授权独立 于 公共哈希 列表。该列表初始为空，并且只会增长。这是 决定谁可以读取条目的三种相互独立、可叠加的授权之一， 另外两种是其存储源（始终可以读取，同样可以读取的还包括 与这些源 同站的源）和可全局 披露。

注：如果一次写入的 origins 被显式指定为空 列表， 即（origins: []），则其授予的权限与省略 origins 的写入完全相同：允许条目的 存储源以及与这些源同站的源读取，这是每个条目 都具备的基线权限（参见确定 COS 披露）。应用 上限 会将空列表转换为 null，因此两种写入都会以相同状态进入 完成创建请求的其余步骤。显式 指定的列表只会增加接收方； 它永远不会阻止写入方自身的站点访问该条目。

可全局披露

一个布尔值，初始为 false，用于记录该条目写入时是否请求了 将其设为 全局（"*"）可用。为 true 时，任何请求通过了 § 8.4 可用性门控的源都可以读取该条目，即其 hash 在 PHL 中，且该请求 未被 GREASE 处理抑制。一旦设置，它就始终为 true。

注：这是一个单独的项，与 origins 分开， 以便后续的 全局可用性请求在现有的显式 origins 列表基础上添加 "*" 授权。 如果将这两者合并为一个字段，提供了 字节的写入方就能将作用域为列表的条目转换为作用域为 "*" 的条目。由于§ 8.4 可用性门控 仅适用于 "*" 授权，此前能够凭借该 列表 读取条目的源，此后就会开始收到 "NotFoundError"， 只要其 hash 不 在 PHL 中。保持这些 授权相互独立，可确保每次可见性变更都严格地只增加权限， 这正是可升级但永不可降级 所要求的。

存储源

一个集合，其中的源都已至少成功完成过一次 对此条目字节的写入。此 集合跨页面加载持久保存，并且 会随时间推移而增长；除§ 5.2 逐出中描述的情况外，永不缩小。位于 存储源中的源始终可以获取该 条目的句柄，方法是调用 requestFileHandle()， 无论 origins 如何，也无论 该条目的 hash 是否在公共哈希列表 （PHL）中。 参见§ 3.5.1 原始存储方访问。

用户代理具有关联的跨源存储队列，它是执行 启动新的并行队列所得的结果。对 COS 注册表的所有操作都要 入队到此队列，以便它们按 其 入队顺序执行，且不会交错。

2.3. 公共哈希列表

确认某个哈希值存在于跨源存储中，本身就可能泄露用户的 浏览历史信息（参见§ 8.2 跨站探测）。这是一种 专门针对全局 授权的风险。条目的显式 origins 列表，以及每个条目都具备的同站基线 权限， 其披露范围已受到存储源的明确选择的限制，而 将条目设为可全局披露则可能将其暴露给 Web 上的任何 源。为了限制这种 特定风险，可全局披露的资源只有满足以下条件，才能通过 该 授权向其存储源以外的源披露：其哈希值通过一个额外的、 独立的门控，即属于公共哈希列表 （PHL），这是一个厂商中立、由实现定义的允许列表，其中包含 COS 哈希值 。哈希值只有达到类似 k-匿名性的普及程度门槛，才会被纳入公共哈希列表 （例如，以字节完全相同的形式出现在至少一定数量的独立 源中），从而使确认它存在于共享缓存中这一行为，不会透露任何 单个用户的信息。

一个 COS 哈希值 hash 称为在公共 哈希列表中，如果 hash 等于用户代理当前持有的 公共哈希列表快照中的一个条目。

公共哈希列表的获取协议、 更新频率、数据格式、普及程度阈值和治理 方式，作为本规范的配套产物进行了详细设计， 借鉴了公共后缀列表的理念，后者是 [URL] 标准的配套数据文件；参见 本仓库中的公共哈希列表说明文档。该设计 提议由 WHATWG 负责治理，借鉴公共后缀列表跨厂商、 滚动发布的先例，并以经过独立佐证的广泛使用程度作为准入标准。 这是上述类似 k-匿名性门槛的一种具体实现，作为哈希值准入流程的一部分， 离线应用一次，因此用户代理不会在每次查询时重复执行。上述安排 目前均尚未在本提案之外确立。列表本身的一个早期、非规范性代码原型 目前位于本仓库中的 public-hash-list/implementation/；建立一个专用的、 跨厂商仓库，仍然是 PHL 说明文档中描述的治理目标。本 规范仅依赖哈希值是否在 PHL 中，因此，无论该 列表的获取机制、治理模型或该设计的其他部分如何演变，本规范都仍然成立。

3. 该 CrossOriginStorageManager 接口

[Exposed=(Window,Worker), SecureContext]
interface CrossOriginStorageManager {
  Promise<FileSystemFileHandle> requestFileHandle(
      CrossOriginStorageRequestFileHandleHash hash,
      optional CrossOriginStorageRequestFileHandleOptions options = {});
};

dictionary CrossOriginStorageRequestFileHandleHash {
  required DOMString value;
  required DOMString algorithm;
};

dictionary CrossOriginStorageRequestFileHandleOptions {
  boolean create = false;
  (DOMString or sequence<DOMString>) origins;
};

interface mixin NavigatorCrossOriginStorage {
  [SameObject, SecureContext] readonly attribute CrossOriginStorageManager crossOriginStorage;
};
Navigator includes NavigatorCrossOriginStorage;
WorkerNavigator includes NavigatorCrossOriginStorage;

每个 Navigator 和 WorkerNavigator 对象都具有关联的 CrossOriginStorageManager 对象。该 crossOriginStorage 获取器 的步骤 是返回 this 关联的 CrossOriginStorageManager。

每个 CrossOriginStorageManager 对象都具有关联的源，设置为 this 的相关设置对象的源，该设置在对象 创建时进行。

注：从相关设置对象获取源，而不考虑 脚本本身的任何信息，会对 worker 产生一个值得明确说明的结果。从 blob: URL 创建的 worker 具有创建它的上下文的源，因此它与该源共享完全相同的 跨源存储视图：此类 worker 写入的内容，其创建页面可以读回，而 页面存储的内容，worker 也可以读取。blob: URL 本身并不是一个独立的源， 撤销该 URL 也不会使 worker 脱离该视图。从 data: URL 创建的 worker 具有不透明源。本规范目前尚未定义 requestFileHandle() 在调用方的源是不透明源时的行为； 该不透明源规则位于验证 COS 请求中， 仅约束 调用方指定的源。不透明源没有稳定的标识来作为 存储 源或同 站比较的依据，因此没有任何有意义的权限 可以授予它。

3.1. 该 requestFileHandle() 方法

handle = await navigator . crossOriginStorage . requestFileHandle(hash)

返回由 hash 标识的文件的句柄，前提是该文件存在于跨源存储中， 且可以从中向调用源披露。否则，以一个 "NotFoundError" DOMException 拒绝。 一个 "NotFoundError" 并不能证明该文件 实际上不存在于跨源存储中；参见§ 8.4 可用性门控。调用方可以 将其视为“改为从网络获取此文件”。

handle = await navigator . crossOriginStorage . requestFileHandle(hash, { create: true })

返回一个句柄，可用于将由 hash 标识的文件写入 跨源 存储；如果尚无条目，则创建一个新条目，默认仅限同站源访问。 调用方需要通过该句柄的 createWritable() 方法写入完整的文件内容，无论条目是否已经 存在；用户代理会在此时验证写入字节的哈希值是否为 hash， 否则以一个 "DataError" DOMException 拒绝。此要求可防止 源利用创建请求来探知 hash 是否已经存在。

handle = await navigator . crossOriginStorage . requestFileHandle(hash, { create: true, origins: "*" })

同上，此外，一旦写入，任何源只要其针对 hash 的请求通过§ 8.4 可用性门控，就可以获知该条目。

handle = await navigator . crossOriginStorage . requestFileHandle(hash, { create: true, origins: ["https://a.example", "https://b.example"] })

同上，将披露范围严格限制为列出的源（此外还包括调用 源，以及任何已经位于存储源中的源）。

该 requestFileHandle(hash, options) 方法 的步骤如下：

  1. 令 result 为一个新的 promise。

  2. 令 realm 为 this 的相关领域。

  3. 令 global 为 this 的相关全局对象。

  4. 令 origin 为 this 关联的源。

  5. 如果运行检查跨源存储权限， 给定 global，所得的结果为 false，则：

    1. 将一个全局任务排入队列，使用DOM 操作任务源和给定的 global，以便 拒绝 result，原因为一个 "NotAllowedError" DOMException。

    2. 返回 result。

  6. 令 validationFailure 为运行验证 COS 请求，给定 hash 和 options，所得的结果。

  7. 如果 validationFailure 不为 null：

    1. 将一个全局任务排入队列，使用DOM 操作任务源和给定的 global，以便 拒绝 result，原因为 validationFailure。

    2. 返回 result。

  8. 将以下步骤排入 跨源存储队列：

    1. 如果 options["create"] 为 true：

      1. 运行完成创建请求，给定 result、hash、options、global 和 realm。

    2. 否则：

      1. 运行完成读取请求，给定 result、hash、origin、global 和 realm。

  9. 返回 result。

要验证 COS 请求，给定一个 CrossOriginStorageRequestFileHandleHash hash 和一个 CrossOriginStorageRequestFileHandleOptions options，返回 null 或一个 TypeError：

  1. 如果 hash["algorithm"] 不是一个哈希算法 名称，且该名称由 [WEBCRYPTO] 识别，则返回一个新的 TypeError。

  2. 如果 hash["value"] 不匹配正则 表达式 /^[0-9a-f]{64}$/，且 hash["algorithm"] 以不区分 ASCII 大小写 的方式匹配 "SHA-256"，则返回一个新的 TypeError。

    注：未来的哈希算法可以定义 不同的预期摘要长度；本 规范仅对 "SHA-256" 作出规范性约束，与其在所有 示例 中的使用保持一致。

  3. 如果 options["origins"] 存在且 不为 "*"：

    1. 令 candidates 为 options["origins"]， 将单个字符串视为仅含一个元素的列表。

    2. 如果 candidates 的大小 大于用户代理的 最大源列表长度，则返回一个 新的 TypeError。

    3. 对于每个 candidate，其属于 candidates：

      1. 如果运行基本 URL 解析器来解析 candidate 所得的结果为失败，或者 解析得到的 URL 的源是不透明源，则返回一个新的 TypeError。

  4. 返回 null。

3.2. 读取文件

要完成读取 请求，给定一个 promise result、一个 COS 哈希值 hash、一个 源 origin、一个全局对象 global 和一个领域 realm：

  1. 令 entry 为以下 COS 条目：位于 COS 注册表中，且其 hash 等于 hash，如果存在这样的条目；否则为 null。

    注：其他写入方已经 请求但尚未完成的写入不在 COS 注册表中，因此 对于这样的哈希值，entry 为 null，本算法会以与 处理从未被任何源写入的哈希值完全相同的方式继续执行。本规范允许的每次披露都 由下文的应用可用性门控决定；不存在 更早的分支能够 提前给出响应。参见§ 8.3 正在进行的写入。

  2. 令 disclosableEntry 为运行应用可用性 门控，给定 entry 和 origin，所得的结果。

  3. 如果 disclosableEntry 为 null：

    1. 将一个全局任务排入队列，使用DOM 操作任务源和给定的 global，以便 拒绝 result，原因为一个 "NotFoundError" DOMException。

    2. 返回。

  4. 令 handle 为创建一个新的 FileSystemFileHandle [FS] 所得的结果，其 定位器定位到 disclosableEntry 的 hash，位置在 跨源存储文件系统中，创建所用的领域为 realm。

  5. 将 handle 的 COS 哈希值设置为 disclosableEntry 的 hash。

  6. 将 handle 的 COS 源设置为 origin。

  7. 将 handle 的可读取设置为 true。

    注：此句柄已经通过应用可用性门控，因此调用源 有权 获取该条目的字节。

  8. 将一个全局任务排入队列，使用DOM 操作任务源和给定的 global，以便 解决 result，值为 handle。

要确定 COS 披露，给定一个 COS 条目 或 null entry，以及一个 源 origin，返回一个 COS 条目或 null：

  1. 如果 entry 为 null，则返回 null。

    注：COS 注册表中的条目 始终都已完成写入和验证，因此本算法无需 考虑写入了一部分的状态。一个哈希值如果其唯一一次写入仍在进行中，则 不存在于注册表中，并以 null 传入本算法，这与从未被任何源 写入的哈希值相同；参见§ 8.3 正在进行的写入。

  2. 如果 origin 位于 entry 的存储 源中，则返回 entry。

    注：原始存储方，以及任何 自身已成功写入该条目的源， 始终可以将其读回。参见§ 3.5.1 原始存储方 访问。

  3. 如果 origin 与以下集合中的某一项同站：entry 的存储源，则返回 entry。

    注：每个条目都具备的同站基线 权限（未提供 origins 选项的写入所请求的授权）始终成立， 无论之后添加了什么 origins 列表或可全局披露授权 。由于此项检查发生在下文的公共哈希列表门控 之前，同站 源可以读取条目，无论其 hash 是否在 PHL 中。这里，同站 构成一个信任单元，因此这不会跨越以下章节所保护的站点边界而披露任何信息： § 8.2 跨站探测。

  4. 如果 origin 的序列化结果是 entry 的 origins 中的一项，则返回 entry。

    注：位于显式 origins 列表 中的源可以读取该条目，而无需该条目 在 PHL 中。存储源通过指定该源，作出了有界限的披露 决定（参见§ 3.5 资源可见性升级和§ 7 Cross-Origin-Storage-Allow-Origin 标头），而 在此基础上另外要求 全局范围内的广泛使用，会使普通的受限共享依赖于无关的、 公开进行的收录筛选，而被筛选的资源往往是专有资源。在 可全局披露门控之前检查这一点，可以防止 后续请求全局可用的写入 撤销列表中源的访问权限。参见§ 8.2 跨站 探测。

  5. 如果 entry 的可全局披露为 true：

    1. 如果 entry 的 hash 不在 PHL 中，则返回 null。

      注：公共哈希列表门控 仅适用于全局授权，只有在这种情况下， 披露范围才可能扩展到 Web 上的任何源。对于一个 可全局披露但其 hash 不在 PHL 中的条目， 不会向仅凭此授权符合条件的源披露；如果一个源同时 还出现 在存储源、与其同站的源集合，或 显式 origins 列表中，则已经 在上文返回了结果。

    2. 如果用户代理选择对该请求应用GREASE 处理， 则返回 null。

      注：GREASE 处理也仅适用 于全局授权。上文检查过的授权永远不会 执行到这一步：存储源及其同站源构成一个信任单元，而 显式 origins 列表中的源是 写入方有意指定的，且该写入方的 Cross-Origin-Storage-Allow-Origin 标头已授权该源。

    3. 返回 entry。

  6. 返回 null。

要应用 可用性门控，给定一个 COS 条目或 null entry，以及一个 源 origin，返回一个 COS 条目或 null：

  1. 返回运行确定 COS 披露，给定 entry 和 origin，所得的结果。

3.3. 创建和写入文件

一个 FileSystemFileHandle 如果由完成创建请求创建，则具有关联的 请求的源，此值是验证并存储 尝试升级条目的 origins 时使用的目标值，前提是已通过该 句柄成功写入。

每个 FileSystemFileHandle 如果定位到跨源存储文件系统，则还具有 关联的 COS 哈希值，即其定位的 COS 哈希值；一个 关联的 COS 源，即获取该句柄的源；以及一个 关联的 可读取布尔值，用于控制 getFile() 是否可以通过该特定句柄披露所定位条目的 字节。对于由完成读取请求返回的句柄，该值为 true，因为它已经通过 可用性门控；对于由 完成 创建请求返回的句柄，该值为 false，直到验证并存储对同一个句柄成功执行。

注：句柄定位的是 COS 哈希值，而不是 COS 条目。完成创建请求会为一个哈希值返回 句柄，即使该哈希值在 COS 注册表中没有条目，且可能永远不会有条目，因此在 验证并存储创建条目之前，没有可供该句柄引用的条目。

注：这里有意将其设为每个句柄各自的属性。一个 创建请求 无论该哈希值的条目是否已经存在，都会返回一个句柄（参见 完成 创建请求），因此，按条目制定规则会允许任何源调用 requestFileHandle() 并传入 create: true，然后立即读取它 从未写入的条目，在不满足 origins、 PHL 成员资格或GREASE 处理要求的情况下获知其内容。本 规范中的每一项披露控制都应用于读取路径，因此按条目进行门控会让创建请求 绕过所有这些控制。要求调用方先提供正确的字节，意味着通过创建请求获取的句柄进行 成功读取，不会披露任何调用方尚未拥有的内容。

要完成 创建请求，给定一个 promise result、一个 COS 哈希值 hash、一个 CrossOriginStorageRequestFileHandleOptions options、一个全局对象 global 和一个领域 realm：

  1. 令 requestedOrigins 为运行规范化 请求的源所得的结果，给定 options["origins"]。

  2. 如果 requestedOrigins 是一个列表，则将 requestedOrigins 设置为运行 应用 COS 作用域上限所得的结果，给定 requestedOrigins 和运行 获取 COS 作用域上限所得的结果，后者给定 global。

  3. 令 handle 为创建一个新的 FileSystemFileHandle [FS] 所得的结果，其 定位器定位到 hash，位置在 跨源存储文件系统中，创建所用的领域为 realm。

  4. 将 handle 的 COS 哈希值设置为 hash。

  5. 将 handle 的 COS 源设置为 global 的 相关设置对象的源。

  6. 将 handle 的请求的源设置为 requestedOrigins。

  7. 将 handle 的可读取设置为 false。

    注：本算法不查询 COS 注册表， 也不修改它。本算法不能这样做： 其结果必须独立于 hash 是否已存储，否则创建 请求 本身就会披露它此前是否存在（参见§ 8.2 跨站探测）。 因此，无论条目是否存在、 从未被写入，还是此刻正由其他方写入，都会在完全相同的条件下返回 handle，并且在此调用方提供字节之前，该句柄不具有读取访问权限。

    注：由于此处没有注册任何内容， 调用方如果请求句柄后将其弃用， 从不调用 createWritable() 或从不关闭所得的流， 注册表就会保持原样。其他任何源都无法观察到该请求 曾经发生，也不会有哈希值被固定在阻止后续读取的占位状态。 参见§ 8.3 正在进行的写入。

    注：requestedOrigins 仅由 验证 并存储通过 升级资源可见性应用，且仅在字节 已写入并通过验证之后。正是这一点 要求创建请求必须先提供完整字节，才能扩大可见性；参见 § 3.5 资源可见性升级。

  8. 将一个全局任务排入队列，使用DOM 操作任务源和给定的 global，以便 解决 result，值为 handle。

要规范化 请求的源，给定一个 (DOMString or sequence<DOMString>) 或 undefined origins，返回 "*"、一个列表（其中包含源），或 null：

  1. 如果 origins 不存在，则返回 null。

  2. 如果 origins 为 "*"，则返回 "*"。

  3. 令 list 为 « »。

  4. 对于每个 candidate，其属于 origins（单个 字符串被视为一个列表， 其中仅含一个元素）：

    1. 令 candidateOrigin 为所得的源，其获取方式是运行基本 URL 解析器 来解析 candidate。

      注：验证 COS 请求已经确认，每个 candidate 都会解析为 非不透明源。

    2. 如果 list 不包含 candidateOrigin，则追加 candidateOrigin 到 list。

  5. 返回 list。

注：在此处去重，也就是在后续合并到 现有条目之前去重，可以使 origins 从条目首次 创建时起就不含重复项，因此后续每次对其进行的克隆也都不含重复项。

当一个 FileSystemWritableFileStream 是通过调用 createWritable() 获得的，且调用所用句柄的定位器 定位到跨源存储文件系统，则在该流被关闭时 [FS]，用户代理必须运行 下文的 验证并存储步骤， 给定该句柄，并且必须在该关闭操作的 promise 兑现之前执行。

注：无论关闭是如何 触发的，此要求都适用：显式的 close() 调用，或一个 pipeTo() 调用到达了其 源的末尾，而这默认也会关闭其目标。[STREAMS] 在流变为关闭状态时 不区分这两种情况，本算法也不区分。

验证并存储 的步骤，给定一个 FileSystemFileHandle handle，其流已被 关闭；完整写入的字节序列 bytes；以及关闭操作的 相关设置对象的源 origin，如下：

  1. 令 hash 为 handle 的 COS 哈希值。

  2. 令 computedValue 为 bytes 的小写十六进制摘要，其计算 使用的 算法由 hash 的 algorithm 指定，并遵循 [WEBCRYPTO]。

  3. 如果 computedValue 与 hash 的 value 不完全相等：

    1. 拒绝关闭操作的 promise，原因为一个 "DataError" DOMException。

    2. 中止这些步骤。

    注：失败的写入没有任何需要清理的 内容。完成创建请求没有注册任何条目， 因此，从未产生通过验证的字节的写入，会使 COS 注册表保持不变，后续针对同一哈希值的 requestFileHandle() 调用会得到相同的 "NotFoundError"， 就像从未尝试过该写入一样。某个源 已经写入的条目同样不受影响：本算法只会添加字节和授权。

  4. 将以下步骤排入 跨源存储队列：

    1. 令 entry 为以下 COS 条目：位于 COS 注册表中，且其 hash 等于 hash，如果存在这样的条目；否则为 null。

    2. 如果 entry 为 null：

      1. 将 entry 设置为一个新的 COS 条目，其 hash 为 hash， bytes 为 bytes，origins 为一个空列表， 可全局披露为 false，且存储源为一个空 集合。

      2. 设置 COS 注册表[hash] 为 entry。

      注：这是本规范中唯一一个 向 COS 注册表添加条目的步骤，而且只有在 bytes 已依据 hash 通过验证后才会运行。两个 写入方如果都发现该哈希值不存在，并发地写入它，就会各自执行到这里； 无论哪一个 第二个入队，都会找到第一个写入方创建的条目，并仅在下文添加自身的源和 授权。它们的字节产生相同的哈希值，因此只存储一次就足够了。

    3. 追加 origin 到 entry 的存储源，如果它尚未 存在。

    4. 运行升级资源可见性，给定 entry 和 handle 的 请求的源。

    5. 将 handle 的可读取设置为 true。

      注：只有此句柄变为 可读取。针对同一哈希值的另一个句柄，如果是从 另一个创建请求获得的，且尚未通过该句柄写入，则仍然不可读取。

createWritable() 如果在一个 FileSystemFileHandle 上调用，而该句柄定位到 跨源存储文件系统，则必须产生一个 FileSystemWritableFileStream， 其内容 初始为空，无论 keepExistingData 的值为何， 也 无论所定位的 COS 哈希值是否在 COS 注册表中具有条目。

注：[FS] 在其他情况下将 keepExistingData 定义为使用 现有文件的内容初始化流。在此处遵循该定义，会让调用方成为其从未 拥有过的字节的存储源。创建请求无论条目是否已经存在，都会返回句柄， 因此调用方可以针对另一个源存储的哈希值打开可写流，在 未写入任何内容的情况下关闭它，而沿用的字节会产生请求的哈希值。这样会 在从未检查 origins、公共哈希列表和 GREASE 处理的情况下授予其读取访问权限：这是对可用性 门控的绕过， 由两个分别获准执行的操作组合而成。同样的理由也使得 验证并存储要求 每个创建请求都提供完整内容。

注：因此，一个未进行任何写入就关闭的可写流 包含的是空字节序列，对于调用方想要的任何条目，它都不会 产生请求的哈希值，所以验证并存储会拒绝， 原因为一个 "DataError" DOMException， 就像处理其他任何不匹配情况一样。如果实现 在这种情况下改为报告存储或 I/O 失败，就会将验证结果隐藏在一个 无关的错误背后。

文件系统标准 [FS] 尚未定义一个 扩展点，供依赖它的 规范将每次写入的额外验证接入 FileSystemWritableFileStream 的 关闭步骤。在存在这样的钩子之前，本节直接描述所需行为；预计 未来的修订将正式与 [FS] 集成。

3.4. 存储获取的资源

§ 9 与其他 规范的集成中列出的宿主集成会存储其 获取的资源，而不通过 FileSystemFileHandle。 预期其宿主规范 会在获取的字节通过该集成所要求的完整性检查之后， 运行以下算法。

要将获取的资源存入跨源 存储，给定一个响应 response、一个字节序列 bytes、一个 COS 哈希值 hash、"*"、一个列表（其中包含字符串） 或 null origins，以及一个环境设置对象 settings：

  1. 如果运行检查跨源存储 权限，给定 settings 的 全局对象，所得的结果为 false，则返回。

  2. 令 options 为 «[ "origins" → origins ]»，如果 origins 不为 null；否则为 «[ ]»。

  3. 如果运行验证 COS 请求，给定 hash 和 options，所得的结果不为 null， 则返回。

  4. 令 computedValue 为 bytes 的小写十六进制摘要，其计算 使用的 算法由 hash 的 algorithm 指定，并遵循 [WEBCRYPTO]。

  5. 如果 computedValue 与 hash 的 value 不完全相等，则返回。

    注：该集成自身的完整性 元数据可以列出多个摘要，匹配 其中任意一个即可满足要求。此步骤确保条目的键是这些 确切字节所产生的哈希值。

  6. 令 requestedOrigins 为运行规范化 请求的源所得的结果，给定 options["origins"]。

  7. 如果 requestedOrigins 是一个列表：

    1. 令 internalResponse 为 response 的内部响应，如果 response 是一个过滤响应；否则为 response 。

    2. 将 requestedOrigins 设置为运行应用 COS 作用域上限所得的结果，给定 requestedOrigins 和运行解析 COS 作用域上限所得的结果，后者给定 internalResponse 的标头列表。

    注：该上限来自所获取 资源自身的响应，因此由提供 字节的服务器决定可以向哪些源披露这些字节。加载资源的 Document 的 COS 作用域上限不参与此过程：其运营方 并不控制该资源， 允许其授权接收方，就会让任何站点都能声明另一个站点的资源可以 与其选择的源共享。用户代理从内部 响应读取该标头，因此这同样适用于不透明过滤响应，而且该标头 永远不会暴露给页面。

  8. 令 origin 为 settings 的源。

  9. 将以下步骤排入 跨源存储队列：

    1. 令 entry 为以下 COS 条目：位于 COS 注册表中，且其 hash 等于 hash，如果存在这样的条目；否则为 null。

    2. 如果 entry 为 null：

      1. 将 entry 设置为一个新的 COS 条目，其 hash 为 hash， bytes 为 bytes，origins 为一个空列表， 可全局披露为 false，且存储源为一个空 集合。

      2. 设置 COS 注册表[hash] 为 entry。

      注：与验证并存储相同， 只有在 bytes 已依据 hash 通过验证后，才会创建条目，而该集成的 integrity 检查已经完成了这一验证。一个 requestFileHandle() 写入方，如果对同一哈希值的写入仍在 进行中，则不受影响：它没有任何注册表状态，其自身的验证并存储 会 正常完成，找到此条目，并向其添加该写入方的源和授权。

    3. 追加 origin 到 entry 的存储源，如果它尚未 存在。

    4. 运行升级资源可见性，给定 entry 和 requestedOrigins。

注： 与验证并存储相同，存储始终要求 提供完整字节，即使 条目已经是 "written" 也是如此，因此不会透露它此前是否存在。该集成的 查找 在其网络获取之前执行，属于读取操作，受可用性门控以及 § 8.2 跨站探测中的探测注意事项约束。

3.5. 资源可见性升级

一个 COS 条目的可见性可以 升级，但永远不能降级。

要升级 资源可见性，给定一个 COS 条目 entry，以及 "*"、一个列表（其中包含 源），或 null requestedOrigins：

  1. 如果 requestedOrigins 为 null，则返回。

    注：省略 origins 仅请求同站 可用性，而每个条目都已具备这一点（参见确定 COS 披露），因此 无需添加任何内容。

  2. 如果 requestedOrigins 为 "*"：

    1. 将 entry 的可全局披露设置为 true。

    2. 返回。

    注：这会添加全局授权；它 不会更改 entry 的 origins。一个条目 如果已具有显式 origins 列表，则会保留该列表，因此 其中的每个源 都会保留该列表所授予的、独立于 PHL 的访问权限，即使条目之后变为 可全局披露也是如此。这正是 将两种授权 分开存储的关键原因；参见可全局披露。

  3. 对于每个 candidateOrigin，其属于 requestedOrigins：

    1. 如果 entry 的 origins 包含 candidateOrigin，则 继续。

    2. 如果 entry 的 origins 的大小 等于用户代理的 最大源列表长度，则 跳出循环。

      注：任何剩余的 candidateOrigin 值都会在本次升级中被静默丢弃，因为 写入本身已经成功，预期用户代理会在控制台记录一条 警告，指出该条目的源列表已达到容量上限。

    3. 追加 candidateOrigin 到 entry 的 origins。

注：升级只会向 origins 添加内容，或将可全局披露 设置为 true。写入方请求一个列表时，会扩大一个已经 可全局披露的条目的可见性，与扩大尚未 可全局披露的条目的可见性相同，因为两种授权 相互独立：新列入的源会获得独立于 PHL 的访问权限，同时 "*" 授权仍然有效。

注：任何站点，包括原始存储方以外的 站点，都可以扩大条目的 origins，只要 它同时提供的字节产生的哈希值等于条目的 hash。这是有意为之的： 任何已经拥有某个哈希值所对应的正确字节的站点，根据这一设计，在该哈希值所表示的内容方面， 都与原始存储方具有同等的权威性。

3.5.1. 原始存储方访问

一个源，如果已成功完成写入一个 COS 条目（也就 是，任何源，只要位于该条目的存储源中），就 始终可以在之后 通过 requestFileHandle() 获取其句柄， 无论该条目的 origins 值为何， 也无论其 hash 是否在 PHL 中。 这与 Cache API 的模型一致，在该模型中，源始终可以访问其存储的内容。

4. 跨源存储文件系统

跨源存储文件系统是一个文件系统根，独立于任何 源的存储桶文件系统或本地文件系统访问根，其 条目与 COS 注册表中的 COS 条目项一一对应。

跨源存储文件系统不使用 [FS] 通常采用的每次调用都检查 权限的 模型：从中获取的每个 FileSystemFileHandle 都已经获得了充分授权，授权依据为 § 3.2 读取文件或§ 3.3 创建和 写入文件，且授权在返回给脚本之前完成，因此调用 getFile() 或 createWritable() 时，如果使用的是此类句柄， 就永远不会触发额外的权限提示。

因此，此类句柄上的 queryPermission() 和 requestPermission() 必须永远不 报告 "prompt"，因为不可能出现提示。对于写入模式，如果句柄 并非 通过创建请求获得，则它们必须报告 "denied"； 否则必须报告 "granted" 。

注：写入是句柄确实可能 缺少的一项能力。只有创建请求才会产生 可以通过其写入的句柄，因此，对任何其他句柄的写入模式报告 "granted" 就是在声称具有一项 createWritable() 会拒绝提供的能力。读取保持为 "granted"，因为持有可读句柄的调用方可以通过它读取。请求权限不能 改变 任何一个结果，因为没有可显示的提示，也没有可记录授权的状态。

调用 getFile() 时，如果所用的 FileSystemFileHandle 定位到 跨源存储文件系统，且其可读取为 false，则必须拒绝， 原因为一个 "NotAllowedError" DOMException。 这涵盖两种不同的情况：

  • 来自创建请求的句柄，尚未通过它 完成 写入，且它所定位的哈希值在 COS 注册表中没有条目。没有经过验证的字节可供 返回，而且必须禁止调用方将其自身尚未完成的写入观察为 文件的实际内容。

  • 来自创建请求的句柄，其哈希值已经由某个其他源写入。 经过验证的 字节确实存在，但此调用方尚未提供这些字节，也尚未通过 可用性门控，因此不得让它获知关于该条目的任何信息， 甚至不能获知 该条目是否存在。

注：这两种情况下的拒绝完全相同，因此 不会披露任何信息。这就是为什么 "NotAllowedError" 在此处是安全的，尽管读取路径有意避免使用它：此句柄 属于调用方自身，由其自身的创建请求获得，而且句柄无法在任何 其他源中反序列化（参见§ 4.1 转移句柄）。因此，该响应 永远不会跨越源边界，而且 不随注册表内容而改变。对比§ 8.3 正在进行的写入，其中 读取路径上一个不同的错误会跨越该边界。

一旦句柄的可读取为 true，在其上调用 getFile() 就会返回一个 File， 其内容为所定位条目的 bytes；这 正是 [FS] 已经为以下文件 条目定义的行为：其 二进制数据就是这些字节。

一个 FileSystemFileHandle 如果定位到跨源存储文件系统，则具有一个 文件系统定位器，其路径是一个列表，其中包含 单个 字符串，即其 COS 哈希值的 value，并且其 根 为跨源存储文件系统。

注：[FS] 将 name 定义为句柄的 定位器路径中的最后一个路径分量，因此这也确定了 name： 它就是 哈希值。条目没有自身的名称，哈希值是它唯一的标识，因此 报告该值可以保留空字符串会丢弃的信息。

条目没有名称，也没有包含它的目录，因此 [FS] 中大部分涉及结构的功能 都没有可操作的对象。标识是例外，而且它是内容寻址条目 始终能够回答的一个问题：COS 注册表对于每个 COS 条目所对应的 COS 哈希值，最多只保留一个条目，因此两个 句柄恰好在其哈希值相等时定位到同一个条目。

isSameEntry() 如果在一个 FileSystemFileHandle 上调用，而该句柄 定位到跨源存储文件系统，传入的参数 也定位到该文件系统，并且由 同一个源获取，则当两个句柄的 COS 哈希值项相等时，必须返回 true，否则返回 false。

注：拒绝执行此操作会丢弃用户 代理已经持有的信息。

isSameEntry() 如果在调用时传入的参数并非由调用源获取， 或者参数定位到的文件系统并非跨源 存储文件系统，则必须拒绝。

注：在这种情况下返回 false，就会断言 两个句柄定位到不同的条目， 而这是在对一个调用源无权检查的句柄作出断言。拒绝仅表示 无法进行比较。

move() 和 remove() 如果在一个 FileSystemFileHandle 上调用，而该句柄定位到跨源存储文件系统，则必须以一个 "NotAllowedError" DOMException 拒绝， 并且必须使所定位的任何条目保持不变。

注：条目由其存储 源中的每个源共享，因此允许 移除会让一个站点破坏其他站点所依赖的数据；删除应由 逐出机制和用户自身的存储控制功能负责。重命名或更改父目录没有 可操作的对象，因为条目由其 COS 哈希值命名，而且没有包含它的目录。

注：在撰写本文时，这两个方法均未由 [FS] 或文件系统 访问 API 定义 （WICG/file-system-access#214）， 因此错误名称遵循 removeEntry()， 这是 [FS] 确实 定义了的删除条目的操作：未获授予读写访问权限时，它会以访问结果的错误名称 拒绝。在此处拒绝是准确的行为：这些操作有意义，但 不获允许。

createSyncAccessHandle() 在此处无需另设规则：其步骤会以一个 "InvalidStateError" DOMException 拒绝，只要句柄不在一个存储桶文件系统中， 而跨源存储文件系统是一个文件系统根，独立于任何源的文件系统根， 因此 [FS] 已经确定了 拒绝行为及其错误名称。

注：即使独立考虑，这也是本规范所 期望的结果。一个 FileSystemSyncAccessHandle 会向调用方提供一个可写文件描述符，这会使其能够 更改条目的 bytes， 却不改变存储这些字节时所关联的 COS 哈希值 ， 而可以获知该条目的其他每个源读取的都是这些相同的字节。

4.1. 转移句柄

一个 FileSystemFileHandle 是一个可序列化对象 [FS]，因此，定位到一个 COS 条目的句柄可以传递给另一个环境设置对象，例如通过 postMessage(message, options)。 这是获取此类句柄的第二种方式，与 requestFileHandle() 并存， 因此本节也对它加以约束。

以下序列化步骤，适用于一个 FileSystemFileHandle， 该句柄定位到 跨源存储文件系统，给定 value 和 serialized，额外执行：

  1. 将 serialized.[[COSHash]] 设置为 value 的 COS 哈希值。

  2. 将 serialized.[[COSOrigin]] 设置为 value 的 COS 源。

  3. 将 serialized.[[COSMayRead]] 设置为 value 的可读取。

以下反序列化步骤，给定 serialized、 value 和 realm，额外执行：

  1. 如果 serialized.[[COSOrigin]] 不同源于 realm 的 环境设置对象的源，则抛出一个 "DataCloneError" DOMException。

  2. 将 value 的 COS 哈希值设置为 serialized.[[COSHash]]。

  3. 将 value 的 COS 源设置为 serialized.[[COSOrigin]]。

  4. 将 value 的可读取设置为 serialized.[[COSMayRead]]。

注：如果没有同 源检查，转移就会一次性绕过 本规范中的所有披露控制。一个句柄如果其可读取为 true， 就已经 通过了应用可用性门控，但这是针对请求该句柄的 源而言的；将其发送给另一个 源，会把该条目的字节交给该源，而无需为其评估 origins、 PHL 成员资格或GREASE 处理。这 与文件系统标准现有的句柄处理方式一致，其中句柄同样仅对 同源接收方有用。

注：可读取随句柄 一同传递，因此，尚未通过其写入的创建请求句柄在 转移后 仍然不可读取，而读取请求句柄保持可读取，无需重新进行门控。接收时重新进行门控，会让 调用方通过转移同一个 句柄来反复探测可用性。

5. 存储管理

5.1. 存储限制

用户代理必须限制一个源可以向 COS 注册表通过成功写入贡献的字节总数，以 防止单个源 灌满缓存，试图逐出其他源的条目。具体限制 由实现定义。如果某个源的写入将超出其 限制，用户代理必须 拒绝该 写入，原因为一个 "QuotaExceededError" DOMException， 并且应该在 控制台记录一条警告。

注：由于条目是内容可寻址的，一个源如果 在同一哈希值下反复写入相同的 字节，除了首次成功写入外，不会消耗额外配额；参见 § 2.2 COS 条目。

用户代理还具有一个由实现定义的最大源列表长度，这是一个 正整数，用于限定源的数量，即单个 origins 列表可以 包含多少个源。此限制既在首次提供列表时实施（参见验证 COS 请求）， 也在之后将列表合并到现有条目时实施（参见 升级资源可见性），从而使单次调用以及 多次调用随时间累积的效果都无法令条目的 origins 无 限增长。除了限制内存使用量，这还可以防止源列表被用作 一个 未明确声明的 "*" 替代品；参见§ 8.2 跨站探测。

在这两个位置，超出此限制的处理方式不同，因为这两次调用 发生在操作中非常不同的阶段：

  • 在验证 COS 请求中，会在获取任何 文件、计算哈希值或 写入之前检查该限制。超出限制的调用方会立即得到一个 "TypeError"， 并且不会发生任何其他操作， 这与处理任何其他格式错误的 origins 值相同。

  • 在升级资源可见性中，只有通过 多个单独且相互独立的写入调用所请求的源的累积效果，才可能 达到该限制，这些调用可能由互不相关的源在很长一段时间内发起， 而且只有在本次调用的字节已经计算哈希值、 通过验证并持久存储之后，才会检查此限制。此时拒绝写入，会因为一个无关的记录管理限制， 丢弃一次成功、已通过验证且可能非常庞大的写入， 甚至无法将其归因于某个调用方的错误。因此，写入仍然 成功，仅将超出容量的源从 origins 中丢弃，同时 在控制台发出警告。这与现有的 从宽松变为更受限请求的处理方式一致：一个源请求 如果无法被完全满足，就会被静默限制，而携带该请求的写入仍然 成功。这与本规范其他部分的§ 8.4 可用性门控一致： 调用方 无法在事后可靠地确认其请求的源是否 确实已添加：之后以该源调用 requestFileHandle() 时， 即使该源已经添加，调用仍然可能失败（例如，条目 已被逐出，或用户代理对请求进行了限流），因此不得将其结果解释为对 任一情况的确认。

5.2. 逐出

本节是非规范性的。

在存储压力下，用户代理可以将条目从 COS 注册表中逐出， 例如，对最近访问过各条目的存储源采用 最近最少使用策略。预期用户代理会提供设置界面，让 用户能够查看存储了哪些文件、哪些源访问过各个文件，并手动 删除条目或清除全部跨源存储数据。

当用户清除某个源的站点数据时，用户代理应该将该源从其出现的每个 存储 源集合中移除。如果移除后，一个 COS 条目的 存储 源为空，用户代理可以考虑删除该条目。

5.3. 手动添加的条目

本节是非规范性的。

上述设置界面可以让用户将磁盘上已有的文件直接添加到 跨源存储中（例如，独立于任何网站下载的 AI 模型）， 而无需任何脚本调用 requestFileHandle()。 此类条目 没有可将写入归属到的请求源，这引出了两个命令式 API 本身无法回答的问题：

  • 就 § 3.5.1 原始存储方访问而言，谁是原始存储方？没有：该条目的存储源初始为空。 因此，没有任何源可以免于 通常的可用性门控和 origins 检查， 每个请求源都必须接受这些检查。这是正确的结果，因为没有任何源 实际写入了这些字节。

  • 此类条目是否应该像省略 origins 的普通写入那样，被限制为仅同站可用？不应该：“同站”只有 相对于请求源才有意义，而手动添加没有请求源，因此“同站” 无所指。预期用户代理会将此类条目设为可全局 披露， 并使其显式 origins 列表保持为空，因为手动 预先添加文件，只有 在其他源确实能够发现它时，才能实现其目的（让用户尚未访问的站点复用用户磁盘上 已有的文件）。用户代理的设置界面还可以 让用户选择更窄的作用域。

一旦通过这种方式添加，条目在其他方面就无法区分于 网站通过 requestFileHandle() 写入的条目： 相同的 可用性门控和可见性 升级规则适用于它，与适用于任何具有相同授权的其他条目的规则完全一致。 其中包括在 PHL 中检查， 只要该条目最终成为 可全局披露，而这正是手动添加的默认设置。

5.4. 来源元数据

本节是非规范性的。

一个 COS 条目有意不记录 其字节来自何处的任何信息。其标识仅为 hash：相同的字节 就是同一个条目，无论有多少个源存储了 它们，也无论它们是从多少个 URL 获取的（参见§ 2.2 COS 条目）。URL 是某个 写入方的一次 获取操作的属性，因此，对于多个源写入的条目，没有一种不带任意性的方式 来选择一个 URL；它不能像字节那样得到验证（参见§ 8.1 资源完整性）； 而且，与粗粒度的源值相比，即 存储 源中的值，URL 包含多得多的用户浏览信息，因为路径或查询字符串可以指明特定文档、 账户或会话。因此，将其记录在条目上，会使一个高熵信号绕过 披露限制，而这些限制正是 origins 和§ 8.4 可用性 门控存在的目的。

然而，对它的需求确实存在：用户在 § 5.2 逐出描述的设置界面中查看一个数 GB 的文件时，以及开发者在调试为何一次 requestFileHandle() 调用未命中时，都希望知道文件 来自何处。用户代理可以通过在条目之外保留一份实现私有的来源记录来满足此需求 （例如，记录每个存储源从哪个 URL 获取了 这些 字节，以及获取时间），前提是该记录被视为保存在条目之外的用户代理 状态：

  • 它永远不会暴露给脚本。本规范中的任何内容都不会披露它，之后添加的任何内容 也不应该披露它：无论是 requestFileHandle() 还是它返回的 FileSystemFileHandle， 都不应该透露此类记录是否存在，更不用说其 内容。特别是，必须禁止请求源观察并非由其 自身产生的记录。

  • 它仅通过可信的非 Web 界面或接口提供：用户代理自身的设置和存储 检查界面、开发者工具，以及（在用户代理具有扩展平台的情况下） 受用户明确授予的权限控制的扩展 API，其权限要求与其他 暴露浏览历史的 API 相同。有关正在考虑的扩展接口， 请参见 本仓库中的浏览器扩展集成点说明文档 所作的 介绍。

  • 它未经验证，并且以未经验证的状态呈现。其中的 URL 是写入 字节的源所作的声明。只有 hash 能保证内容（参见§ 8.1 资源完整性）。两个源可能为同一个条目记录不同的 URL， 而其中任意一个 都可能不准确或有意误导。

  • 它与条目以及其所归属的源具有相同的生命周期。当 条目被逐出或删除时，它会被丢弃；当某个源从 存储源中移除时，归属于该源的部分也会被丢弃，包括用户清除 该 源的站点数据时（参见§ 5.2 逐出）。

由于这种记录对内容不可见，用户代理是否保存它、保存多少， 完全由实现决定。本规范中的任何内容都不依赖它，而且站点无法检测到它 是否存在。

6. 权限策略集成

本规范定义了一个策略控制的特性 [permissions-policy]，由 字符串“cross-origin-storage”标识。其默认允许列表 为 self。

[permissions-policy] 定义了允许使用，其适用对象为 Document， 但 CrossOriginStorageManager 也在 WorkerGlobalScope 上暴露， 而后者没有自己的 Document 。因此，此检查针对调用方的全局对象定义： 对于 worker 全局对象，会沿所有权关系传递查找到拥有它的 Document， 而其中的每一个 都必须允许该特性。

要检查跨源存储权限，给定一个全局对象 global，返回一个 布尔值：

  1. 如果 global 是一个 Window 对象，则：

    1. 令 document 为 global 的关联 Document。

    2. 如果 document 为 null，则返回 false。

    3. 如果 document 不被允许使用 “cross-origin-storage” 这一策略控制的特性， 则返回 false。

    4. 返回 true。

  2. 如果 global 是一个 WorkerGlobalScope 对象，则：

    1. 令 owners 为 global 的所有者集合。

    2. 如果 owners 为 空，则返回 false。

    3. 对于每个 owner（属于 owners）：

      1. 如果 owner 是一个 Document 且 owner 不被允许使用 “cross-origin-storage” 这一策略控制的特性， 则返回 false。

      2. 如果 owner 是一个 WorkerGlobalScope 对象，且运行 检查跨源存储 权限（给定 owner）的结果为 false，则返回 false。

    4. 返回 true。

  3. 返回 false。

对于一个全局对象，如果此算法返回 false，则从该对象发起的每次 requestFileHandle() 调用都会以 “NotAllowedError” DOMException 拒绝， 且这会在任何哈希验证、注册表查找或写入 发生之前完成。

注： 沿所有者集合进行查找，才能避免禁用该特性的机制 徒有其名。通过 blob: URL 创建的 worker 在其创建页面的 源中运行，并与该页面共享完全相同的跨源存储视图（参见 § 3 CrossOriginStorageManager 接口），因此， 如果检查仅考察全局对象自身的 Document， 那么每个 worker 都会因不存在此对象而使检查条件空泛地成立，而将调用移入 new Worker(URL.createObjectURL(&hellip;)) 就能绕过 cross-origin-storage=() 策略， 无须对该调用作任何其他更改。

注： 一个 ServiceWorkerGlobalScope 的 所有者集合为空，因此 此算法会对它返回 false。这源于所有者集合的本质： 它是一种存活关系，在创建 worker 时填充，并用于判断该 worker 是否仍被实际需要。service worker 在设计上就不与任何 Document 建立这种关系： 其注册会被持久化，用户代理会响应事件启动其全局对象，而且它可以 在完全没有service worker 客户端的情况下运行。因此，调用了 register() 的客户端虽然在注册时可以确定， 但在全局对象运行时通常早已不存在，而且一个运行中的 service worker 会为多个客户端提供服务， 这些客户端的策略不一定一致。

注： 要将 service worker 纳入支持范围，需要捕获并保存策略， 而这项工作属于 [permissions-policy] 和 [service-workers] 的范畴。 本规范倾向的方案是，从 service worker 自身脚本响应中的 Permissions-Policy 响应头推导其策略，就像其策略容器 已经承载该响应的 CSP 一样：这样，策略始终处于该源的控制之下，并且 每次检查更新时都会重新求值。为注册客户端的策略制作快照，会使禁用设置 过时，因为从响应头中移除该特性 要等到注册恰好更新时才会生效。在建立这样的 模型之前，默认拒绝是唯一无法被用来绕过禁用设置的处理方式。

注： 一个 SharedWorkerGlobalScope 的 所有者集合可以包含多个 Document， 它们可能具有不同的策略，而且在 worker 的生命周期内，所有者会不断加入或离开。 要求每个所有者都允许该特性，意味着只要有一个所有者不允许，就会为整个共享 worker 禁用跨源存储，而且在两次 requestFileHandle() 调用之间，检查结果可能发生变化。另一种做法是只要求一个 所有者允许，但这会让任何允许该特性的文档代替 不允许该特性的文档重新启用它。

7. Cross-Origin-Storage-Allow-Origin 响应头

一个 COS 条目，若其 origins 列表 非空，则可向 写入源无法控制的源披露，而该列表由脚本（通过 origins） 或标记声明，而攻击者 一旦实现脚本或标记注入，就能设置其中任意一种声明。为了以注入内容无法伪造的形式， 将该声明与被披露字节所属源的运营者绑定，本 规范定义了一个响应头，用于限制此类声明可以指定哪些源。

Cross-Origin-Storage-Allow-Origin 响应头携带一个 COS 作用域上限：这是一个 集合， 其中包含源，写入操作可以在非同站的 origins 列表中指定这些源。字节的 提供方负责发送该响应头，因此应从 待披露字节所源自的响应中读取它：

  • 对于 requestFileHandle() 写入，其字节可能由 脚本生成，并无对应的原始响应，此时应使用的响应是用于 创建调用方全局对象的 Document 的响应； 或者，对于 worker，则是拥有它的 Document 所对应的响应（参见获取 COS 作用域上限）。

  • 对于宿主集成，使用的是响应，它来自所获取的、其字节将被存储的资源 （参见将获取的资源存储到 跨源存储中）。该响应来自资源的服务器，该服务器 不一定与加载该资源的 Document 所在的服务器相同。

所声明的列表会与作用域上限 求交集（参见 应用 COS 作用域上限），因此该上限只能缩小声明的范围。

注： 该响应头是字节 提供方作出的授权。它所指定的源， 即最终的读取方，不会被征询，也不发送任何内容：列出的源只会在之后参与， 通过调用 requestFileHandle() 来请求该 COS 哈希值，与其他 读取方一样。这与 Access-Control-Allow-Origin [FETCH] 的运作方向相反：后者由 持有资源的服务器主动允许某个指定的源读取该资源。这里，字节的提供方 限定了之后谁能从跨源存储读取这些字节，而写入页面上的注入 内容无法扩大这一范围，因为它无法设置提供方的响应头。

注： 该响应头仅适用于列表形式。 同站默认形式不指定任何跨源 接收方，因此不需要授权；而“*”形式在读取路径上受到 可用性门控的约束，该门控依据公共哈希列表，而 每位用户特有的秘密永远无法通过该门控，因此这种形式也不需要写入时的作用域上限。要求 “*”形式提供响应头，还会破坏零配置的全局共享场景，却无法封堵任何 公共哈希列表尚未封堵的漏洞。

要解析 COS 范围上限，给定一个标头 列表 headers，返回一个由 源组成的集合：

  1. 令 value 为从 headers 中 获取、解码并拆分 "Cross-Origin-Storage-Allow-Origin" 所得的结果。

  2. 如果 value 为 null，返回一个空集合。

  3. 令 ceiling 为一个空集合。

  4. 对于 value 中的每个 token：

    1. 从 token 中去除开头和结尾的 ASCII 空白。

    2. 如果 token 为空字符串，则继续。

    3. 令 origin 为对 token 运行基本 URL 解析器所得的源。

    4. 如果 origin 为失败或是不透明源，则返回一个空集合。

      注： 这包括 token 为 "*" 的情况，因为它无法解析为源。 Cross-Origin-Storage-Allow-Origin 标头只能枚举有限集合的 具体 源；"*" 不是允许的值，因为“任意源”的上限 会让 注入内容声明任何它想要的接收方，从而彻底破坏该标头的 目的。 无界 披露只能通过 "*" origins 形式实现， 而该形式由 公共哈希列表门控，并且从不查询该 标头。格式错误或包含 "*" 的标头 不授权任何内容，与标头不存在时完全一样；它会以关闭方式失败。

    5. 将 origin 追加到 ceiling。

  5. 返回 ceiling。

注： 获取、解码并拆分会按 U+002C (,) 拆分，因此标头 值中的源使用逗号分隔，这与 Timing-Allow-Origin [RESOURCE-TIMING] 以及 列表型 HTTP 响应标头的一般 约定一致，尽管同级的 crossoriginstorage HTML 内容 属性使用空格分隔，以匹配其宿主语法。两者最终都解析成相同的 源集合。

要获取 COS 范围上限，给定一个全局对象 global，返回一个由 源组成的集合：

  1. 如果 global 是一个 Window 对象，则：

    1. 令 document 为 global 的关联 Document。

    2. 如果 document 为 null，返回一个空集合。

    3. 返回 document 的COS 范围上限。

  2. 如果 global 是一个 WorkerGlobalScope 对象，则：

    1. 令 owners 为 global 的所有者集合。

    2. 如果 owners 为 空，返回一个空集合。

    3. 令 ceiling 为 null。

    4. 对于 owners 中的每个 owner：

      1. 令 ownerCeiling 为一个空集合。

      2. 如果 owner 是一个 Document， 则将 ownerCeiling 设置为 owner 的 COS 范围上限。

      3. 否则，如果 owner 是一个 WorkerGlobalScope 对象，则将 ownerCeiling 设置为以 owner 为参数运行获取 COS 范围上限 所得的结果。

      4. 如果 ceiling 为 null，将 ceiling 设置为 ownerCeiling；否则，将 ceiling 设置为 ceiling 与 ownerCeiling 的交集。

    5. 返回 ceiling。

  3. 返回一个空集合。

要应用 COS 范围上限，给定一个由源组成的列表 requestedOrigins 和一个 由源组成的集合 ceiling，返回一个由源组成的列表或 null：

  1. 从 requestedOrigins 中移除每个 ceiling 不 包含的源。

    注： 不在COS 范围 上限中的接收方会被丢弃，而写入仍然 成功，这与升级资源可见性中超长升级丢弃超出部分的做法一致。 用户代理应当记录控制台警告，并指出 每个被丢弃的源。

  2. 如果 requestedOrigins 为 空，返回 null。

    注： 一个所有成员都被 丢弃的列表 会使该写入不再拥有任何获授权的 跨源接收方，因此回退到同站默认值。字节仍然 会被存储；只有未经授权的披露被阻止。

  3. 返回 requestedOrigins。

每个 Document 都具有一个 COS 范围上限，它是一个由 源组成的集合， 在文档创建时设置为以用于创建它的响应的 标头列表为参数运行解析 COS 范围上限 所得的结果。

注： 对 worker 的所有者集合取交集，与 检查跨源存储权限相呼应：只有当每个拥有它的 Document 以传递方式都授权某个源时，该源才位于 worker 的上限内。因为 blob: worker 与其创建页面共享完全相同的 源和跨源存储视图（参见 § 3 CrossOriginStorageManager 接口）， 如果上限只查询 worker 自身，那么每个 worker 的上限都会为空，而把列表范围写入移动到 new Worker(URL.createObjectURL(&hellip;)) 就会去掉页面已经授权的接收方； 对所有者的上限取交集可以保留该授权，同时又不允许任何单个 所有者扩大它。

从 Document 的 响应 填充其 COS 范围上限，需要 在 [HTML] 的文档 创建步骤中提供一个挂接点，就像 [permissions-policy] 和 [CSP] 在 响应处理时被填充一样。在该挂接点存在之前，本节直接描述 所需行为；未来版本预计将正式集成，并与 [FS] 中在 § 3.3 创建和写入文件里提到的挂接点一起处理。宿主集成不需要这样的 挂接点：它们会把获取到的响应传给将已获取的资源存储到跨源 存储中，而后者会从中读取 上限。

8. 隐私和安全注意事项

除使用 RFC 2119 关键词的部分外，本节是非规范性的；另请参阅 仓库中的安全和隐私调查问卷 。

8.1. 资源完整性

每个 COS 条目都以密码学哈希值为键，并且其 字节会根据该哈希值进行验证（参见 § 3.3 创建和写入文件）。因此，网站可以确信， 通过 requestFileHandle() 获得的文件，其字节与 自行获取 hash 所得到的字节完全相同。开发者无法枚举跨源存储的内容，也无法 在事先不知道文件哈希值的情况下访问该文件。

COS 哈希值不是秘密。它是一个 内容标识符，任何已经拥有该文件的人 都能轻松计算出来；对于本规范所针对的广泛分发的资源， 它通常是公开信息，往往会随模型或库的 版本一同发布。因此，知道哈希值就足以发起条目查找，但它本身并不授予任何 访问权限：查找能否成功完全由 origins 和 § 8.4 可用性门控决定。开发者不得将未公开的哈希值 视为访问控制机制； 对特定文件感兴趣的攻击者无须猜测其哈希值，只需获得文件 本身即可（参见§ 8.2 跨站探测）。

8.2. 跨站探测

如果某个资源只被少数网站使用，能够获知该资源 存在于跨源存储中的攻击者，就可以推断用户很可能访问过这些网站中的某一个。由于 requestFileHandle() 是获知资源是否存在的机制，因此每次调用 实际上都是一次探测。本规范中的两种独立机制限制了探测能够 获知的信息：

  • origins（参见 § 3.5 资源可见性升级）允许存储资源的 源将披露范围 限制为选定的源集合，因此专有资源或普及程度较低的资源完全不必 能被全局探测。

  • § 8.4 可用性门控还会阻止将 作用域为“*”的资源 披露给其存储源之外的请求源，除非该哈希值在 PHL 中， 因此，使用 origins: “*”存储的资源 并不会自动变得可被 Web 上的每个源探测。此门控仅适用于 作用域为“*”的 条目；对于列表作用域和同站作用域的条目，第一项中的限制是唯一的 门控，因为存储源已经为这些条目明确限定了披露范围。

第一项只有在“选定的源集合”的规模确实远小于整个 Web 时才成立。 origins 的形式本身 并不能阻止调用方 枚举数量庞大的源（例如，根据公开的热门网站排名 汇编的列表），这在功能上会近似于全局披露，同时绕过 只有“*”才要求的有意且明确的主动选择。源列表最大 长度（参见 § 5.1 存储限制）对此作出限制：该上限应足够小，既能满足实际的 多站点使用场景 （由同一主体控制的少数相关源），又远不足以实质上近似于 “所有源”，从而防止 origins 的受限源形式被用作 “*”的未声明替代形式。

用户代理还应当对来自同一源的重复 requestFileHandle() 调用施加速率限制或以其他方式进行节流，并且可以采用 设备端启发式方法（例如，检测针对看似为每位用户单独生成的 哈希值的请求模式）来识别并阻止探测尝试，无论被探测的 哈希值是否在 PHL 中。

§ 9 与其他规范的集成中的某个宿主集成所执行的查找， 同样是一次探测，即使它不会向页面暴露错误：网站可以观察其 自己的服务器是否收到了回退请求，而这携带的单比特信息与此处“未找到” 结果所携带的信息相同。此类查找不会披露任何超出本规范门控所允许范围的信息， 而且这些门控会原样应用于它。不过，只有将这些 途径发起的查找与 requestFileHandle() 调用一并计数，速率限制才有效，因为 可通过脚本控制的集成同样能够轻易地在循环中发起这些查找。

8.3. 进行中的写入

对于每个源，已经请求但尚未完成的写入，必须与 从未写入过的哈希值无法区分。本规范从结构上实现了这一点： COS 条目只能通过以下算法添加到 COS 注册表中：验证并存储，或 将获取的资源存储到跨源 存储中；在这两种情况下，都必须先根据哈希值 验证完整字节。完成创建请求既不读取也不写入 注册表。因此， 不存在可供读取操作观察的占位状态，读取路径上也不存在能够 在应用可用性门控之前作出响应的分支。

另一种做法是在发起创建请求时登记占位条目，并以可区分的错误拒绝对它的 并发读取，这会让调用方获知某个源正在写入 给定的哈希值。这一个比特的信息听起来微不足道，实际上并非如此。它将具有以下特征：

  • 任何源都能获取，包括对该条目没有任何授权的源，因为占位条目 不携带授权，而且读取操作会在确定 COS 披露运行之前得到响应；

  • 任何哈希值都适用，包括不在 PHL 中且永远不可能进入 PHL 的哈希值，因此攻击者可以 使用根据每位用户特有的值派生的哈希值，而这正是§ 8.6 指纹识别 旨在检测的模式；

  • 不受 GREASE’ing 影响，因为它仅适用于到达门控 步骤的披露， 因此该比特不含噪声；

  • 无须提供任何字节，因此每个源的存储限制 和 § 5.2 逐出都无法限制一个源能够创建多少这样的比特。

因此，嵌入两个网站的跟踪器可以在第一个网站上生成任意位数的标识符， 然后在第二个网站上读回它，不产生任何存储开销，同时绕过 origins、 公共哈希 列表和 GREASE’ing。占位条目还会成为一种拒绝服务 攻击途径：占住某个广受欢迎资源的哈希值，就能在占位条目存续期间 一直阻止其他所有源读取该资源。

注： 这样做的代价是，调用方无法 发现另一个调用方已经在下载 某个大文件，从而避免启动重复下载。这确实是一项代价，也正是 本规范早期草案在此处使用可区分错误的原因。在最需要这种能力的场景， 即同一源内部，可以通过 Web Locks、BroadcastChannel 或共享 worker 恢复这种能力， 这些机制都不会 跨越源边界披露任何信息。跨源场景中的节省主要是理论上的：两个无关的 源必须恰好在同一时刻争相处理同一个哈希值，而且对于双方都尚未 写入的条目，无论如何，只有它在 PHL 中时，才可以向另一方披露。

注： “NotAllowedError” 仍然会作为以下 getFile() 调用的响应返回： 针对通过创建请求获得且尚未通过其进行写入的句柄的调用（参见§ 4 跨源存储文件系统）。该响应 不随注册表状态而变化，且只会到达发起请求的源，因为 句柄无法跨源反序列化（参见§ 4.1 转移 句柄），因此它不会构成信息传递信道。

8.4. 可用性门控

一次 requestFileHandle() 读取，若来自 存储 源之外的源，其是否成功始终取决于请求源是否被 允许读取该条目，这由 origins 决定。对于作用域为“*”的条目，还需要考虑第二个 独立的问题：用户代理是否愿意披露该条目 的存在，这由 PHL 成员资格和 GREASE’ing 决定。对于此类条目， 两项条件都必须满足；对于列表作用域或同站作用域的条目，则只需考虑第一个问题。 规范性算法参见§ 3.2 读取文件。因此，“NotFoundError” 并不能 证明资源不存在：它可能意味着资源不存在、请求 源不在作用域内、作用域为“*”的资源的哈希值尚未进入或永远不会进入 PHL，或者 GREASE’ing 抑制了一个真阳性结果。开发者不得将“NotFoundError” 理解为 比“回退到网络”更具体的任何含义。

注： 在支持第三方 Cookie 的用户代理中， “*”授权让跟踪器关联 用户跨站访问的能力，并不超过第三方 Cookie 已经具备的能力。仅靠 PHL 并不能限制这一点：攻击者可以从各自符合 PHL 条件的资源中 选择一个子集进行写入，以此构造跨站标识符。阻止第三方 Cookie 的用户代理仍然可以提供“*”授权，前提是它限制跨站披露，例如： 为跨站查找设置一个较小的次数配额，以顶层站点为键，并由页面上的每个框架共享； 使计数在一个时间窗口内跨重新加载保持有效；以及仅在用户做出手势后 才共享已写入的条目。README 中的 隐私注意事项介绍了这些缓解措施。

8.5. GREASE’ing

用户代理可以应用 GREASE’ing（生成随机扩展并保持 可扩展性）：偶尔作出响应， 表现得仿佛某个可披露的条目不存在，即使§ 8.4 可用性门控 原本 允许披露。这样会引入噪声，使网站更难区分真正不存在的情况 与出于隐私保护而产生的假阴性结果，类似于 用户代理客户端 提示所采用的技术。

GREASE’ing 仅适用于单凭可全局 披露 授权而获得资格的源，这也正是公共哈希列表所门控的情况（参见确定 COS 披露）。 用户代理不得将其应用于存储源、与这些源同 站的源， 或明确列于 origins 列表中的源。

应用 GREASE’ing 的用户代理必须根据相关条目的大小， 作出合乎比例的判断。对于小条目，回退到网络获取的成本较低，偶尔出现 假阴性是合理的隐私权衡。用户代理不得对以下条目应用 GREASE’ing： 其大小使无谓的重新下载所带来的代价与由此获得的隐私收益明显不成比例 （例如，GB 级的 AI 模型权重），因为这种情况下的假阴性会迫使用户进行完整、 可被观察且代价高昂的重新下载。

8.6. 指纹识别

攻击者通过探测跨源存储能够提取的信息，受到被探测资源 普及程度的限制。获知用户拥有某个非常流行的资源，例如常见的 AI 模型 或广泛使用的 JavaScript 库，只能说明用户访问过使用该资源的 网站之一，而这些网站的数量可能非常多。获知用户拥有某个罕见或独有的资源，则能提供多得多的信息。 预期用户代理会采用设备端启发式方法，检测那些哈希值看似 被刻意设计为每位用户独有的资源（例如，某个哈希值始终只被一个 网站写入，或被异常频繁地请求），并将这些模式视为探测尝试， 无论其名义上的 PHL 状态如何。

9. 与其他规范的集成

本节是非规范性的。

此处定义的 COS 注册表 还可以通过四种宿主集成访问，而无须 直接调用 requestFileHandle() 。每种 集成都在其各自的宿主规范中定义。本规范定义了共享的 底层概念（COS 哈希值、COS 条目、可用性门控，以及 公共哈希 列表），以及将获取的资源存储到跨源 存储中这一步骤， 预期这些集成会以此为基础构建。

  • HTML：一个 crossoriginstorage 属性，用于 link 和 script 元素，这些元素已经 带有 integrity [SRI]；此提案通过以下议题提交给 WHATWG： whatwg/html#12770。

  • JavaScript：一个由宿主定义的 crossOriginStorage 导入属性，可以 配合 integrity 使用，基于导入属性 提案构建；此提案通过以下议题提交给 WHATWG： whatwg/html#12771。

  • CSS：一个 cross-origin-storage() <request-url-modifier>， 可以配合 integrity() 使用， 此提案通过以下议题提交给 CSS 工作组： w3c/csswg-drafts#14056。

  • Fetch：一个名为 crossOriginStorage 的 RequestInit 选项，可以配合 integrity [FETCH] 使用；此提案提交给了 WHATWG，对应议题为 whatwg/fetch#1954。 这一形式没有由宿主定义的目标，因此，一个 Response 由 COS 注册表提供时，应如何报告其 MIME 类型、状态和其他元数据， 仍是该规范中一个尚待解决的问题；一个 COS 条目仅存储 bytes。

以下仅作说明，展示如何通过这四种形式， 分别为同一个全局共享资源启用跨源存储：

<script src="popular-library.js" integrity="sha256-abc123..." crossoriginstorage="*"></script>

import data from "popular-resource.ext" with {
  integrity: "sha256-abc123...",
  crossOriginStorage: "*",
};

@font-face {
  font-family: "Popular Font";
  src: url("popular-font.woff2" integrity("sha256-abc123...") cross-origin-storage(*));
}

const response = await fetch("popular-resource.ext", {
  integrity: "sha256-abc123...",
  crossOriginStorage: "*",
});

这些代码片段仅用于说明。本规范并未定义其中任何语法。 每种形式的权威语法，包括受限源列表的写法， 均由其各自的宿主规范定义。这些写法有意 保持不同：RequestInit 成员可以接受 sequence<DOMString>，与 origins 完全一致，而 HTML 属性值、 导入属性值和 CSS 修饰符参数只能承载文本。

预期这四种形式都采用相同的处理模型：首先查询 COS 注册表，寻找匹配且可披露的条目， 然后才回退到网络获取；并且 将成功获取且通过完整性验证的资源存储到 COS 注册表中，供 其他源复用，与 requestFileHandle() 的行为完全一致。存储步骤 即将获取的资源存储到跨源 存储中，每种集成都以 获取到的响应运行此步骤。因此，受限源值会受到该资源响应中的 Cross-Origin-Storage-Allow-Origin 响应头的限制，该响应头由提供 字节的服务器发送（参见§ 7 Cross-Origin-Storage-Allow-Origin 响应头）。关于 这些集成的讨论应在将承载它们的宿主规范的问题跟踪器中进行， 而不是在本仓库的问题跟踪器中进行。
