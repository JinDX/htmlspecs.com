摘要

跨源存储（COS）是一种内容寻址缓存，允许 Web 应用跨不同源存储和检索大型文件，例如 AI 模型、WebAssembly 模块和广泛使用的 JavaScript 库。文件通过其加密哈希而非 URL 进行标识，因此，某个源获取过一次的字节完全相同的资源，可以由用户代理允许的任何其他源复用，而无需再次下载。为了防止通过缓存中是否存在某个文件来推断用户访问过哪些网站，只有其哈希达到类似 k-匿名的流行度门槛时，才允许跨源披露该文件。

1. 简介

本节为非规范性内容。

存储通常按源进行分区，以保护用户安全和隐私。这是正确的默认设置，但对于一小类非常大的、极其流行的、公开分发的资源（AI 模型、WebAssembly 模块、JavaScript 库、游戏引擎和大型 Web 字体）来说，这种设置并不适合；无论哪个网站请求它们，它们逐字节都是相同的文件。当两个互不相关的源都依赖同一个 8 GB 模型时，按源分区的存储会迫使用户两次下载并保留该模型，这会浪费用户的带宽、存储空间和电池，也会浪费整个网络的资源。

跨源存储（COS）是一个内容寻址缓存，它以加密哈希而不是 URL 作为键，使用户代理能够在选择使用它的多个源之间共享此类资源的 单个已存储副本。在 COS 中存储资源始终是存储源明确选择加入的行为， 而且用户代理可以拒绝确认某资源是否存在，即使对于原本 被允许读取该资源的源也是如此；参见§ 8 隐私 和安全注意事项。

本规范的入口点是 requestFileHandle() 方法，该方法通过 crossOriginStorage 暴露： 

const hash = {
  algorithm: 'SHA-256',
  value: '8f434346648f6b96df89dda901c5176b10a6d83961dd3c1ac88b59b2dc327aa4',
};
try {
  const handle = await navigator.crossOriginStorage.requestFileHandle(hash);
  const file = await handle.getFile();
  // 对该文件执行某些操作。
} catch (err) {
  if (err.name === 'NotFoundError') {
    // 不（可披露地）存在于跨源存储中；改为从网络获取。
  }
}

本规范重用 FileSystemFileHandle、 FileSystemWritableFileStream、 以及文件系统标准 [FS] 中的相关基础设施，这些内容作用于一个专用文件系统，该文件系统在源之间共享，并且与任何源的私有或用户可见文件系统分离。

本规范定义了命令式 JavaScript API，以及宿主集成所基于的共享存储步骤。相关提案将相同的底层缓存集成到其他宿主规范中：HTML crossoriginstorage 属性用于 link 和 script， crossOriginStorage JavaScript 导入属性，CSS cross-origin-storage() <request-url-modifier>，以及用于 fetch() 的 RequestInit 选项。每项内容都在其各自的宿主规范中定义；参见 § 9 与其他规范的集成。

2. 概念

2.1. 哈希

一个 COS 哈希 是一个具有以下 结构 项的结构体：

algorithm

一个 字符串， 用于命名一个由 [WEBCRYPTO] 识别的哈希算法，例如 "SHA-256"。

value

一个 字符串，它是由 algorithm 生成的摘要的小写十六进制编码。对于 "SHA-256"，其长度为 64 个字符。

algorithm 字典成员的类型为普通的 DOMString，即使其值空间恰好是 [WEBCRYPTO] 的 哈希算法所接受的名称集合。一个 HashAlgorithmIdentifier 是 (object or DOMString)，并且其 object 分支由 [WEBCRYPTO] 规范化为一个形状类似 Algorithm 的 字典，使调用者可以向需要额外参数的算法传递额外参数（例如，{name: "HMAC", hash: "SHA-256"}）。哈希 算法不接受此类参数， algorithm 会作为 内容寻址键的一部分进行存储、比较和往返转换，并且本规范示例中的所有使用方式都是裸字符串；在此处允许任意对象不会增加任何能力，反而会使 相等性和序列化变得不必要地复杂。因此，DOMString 是此字段更窄且更正确的类型。

两个 COS 哈希值如果其 algorithm 值是 ASCII 不区分大小写匹配，并且其 value 值完全相等，则为 相等。

注：value 已经规范性地为小写（见上文），因此比较它时只是普通的 字符串比较。algorithm 没有规范规定的大小写，因此比较时采用 ASCII 不区分大小写方式。

一个 内容寻址 存储是这样一种存储：其条目通过一个 相等性的 COS 哈希作为键：具有相同字节和相同哈希算法的两个文件是同一个条目， 无论有多少源存储了它们，或者它们是从多少个 URL 获取的。

2.2. COS 条目

每个用户代理都有一个唯一的COS 注册表，它是一个从 COS 哈希值到 COS 条目结构体的映射， 由所有使用跨源存储的源共享。一个 COS 条目具有以下项：

hash

一个 COS 哈希。

bytes

为 Null，或一个 字节序列，其摘要在 hash 的 algorithm 下等于 hash 的 value。在写入者完成 验证和存储 之前为 Null。

state

为 "pending" 或 "written" 之一。一个条目初始状态为 "pending"， 并且仅在首次设置 bytes 时，恰好一次变为 "written"。

pending writer count

一个非负整数，初始值为 0，用于统计未完成的写入者数量：由 完成创建请求返回的 FileSystemFileHandle 句柄，其 关闭写入 尚未完成。仅用于在 验证和存储 中决定失败的写入是否可以安全清理；参见 § 3.3 创建和写入文件。

origins

一个 列表， 包含被授予明确跨源读取访问权限的 源，独立于 公共哈希列表。 初始为空，并且只会增长。这是决定谁可以读取一个条目的三个独立且可叠加的授权之一， 另外两个是其 存储源（始终可读取，同时包括与它们同站的源）以及 可全局公开。

globally disclosable

一个 布尔值，初始为 false，用于记录该条目是否已通过请求全局（"*"）可用性进行写入。 当为 true 时，任何请求通过 § 8.3 可用性门控 的源都可以读取该条目， 即其 hash 位于 PHL 上， 且 GREASE 不会抑制该请求。一旦设置，它将保持为 true。

注：这是与 项 不同的独立 origins 字段， 因此后续的全局可用性请求会在现有明确的 origins 列表 上添加 "*" 授权。如果将两者合并为一个字段，提供 § 8.3 可用性门控 的写入者可能会将一个列表范围的条目转换为 "*" 范围的条目。 由于 § 8.3 可用性门控 仅适用于 "*" 授权， 一个之前可以从该列表读取该条目的源， 随后会在 hash 不位于 PHL 上时收到 "NotFoundError"。 保持这些授权彼此独立，可以使每次可见性更改都严格为添加式，这正是可升级但永不可降级所要求的。

storing origins

一个 有序集合，包含每个至少成功完成一次此条目字节写入的 源。跨页面加载持久保存，并随着时间增长；除非按照 § 5.2 驱逐 中的描述，否则永不缩减。 storing origins 中的源始终可以通过 requestFileHandle() 获取该条目的句柄，与 origins 或该条目的 hash 是否位于公共哈希列表（PHL）无关。 参见 § 3.5.1 原始存储者访问。

用户代理具有关联的跨源存储队列，它是 启动新的并行队列的结果。对 COS 注册表的所有操作都要 入队到此队列中，从而使它们按照 它们 入队的顺序执行，并且不会交错执行。

2.3. 公共哈希列表

确认某个哈希是否存在于跨源存储中本身可能泄露用户的浏览历史信息（参见 § 8.2 跨站探测）。这是一项专门针对全局授权的风险。条目的显式 origins 列表，以及每个条目都具有的同站基线，其披露范围已经受到存储源明确选择的限制；而使一个条目变为 可全局公开 则可能使其暴露给 Web 上的任何源。为了限制这一特定风险，一个 可全局公开 资源只有在其哈希通过一个额外的、独立的门控条件后，才能通过该授权向其 存储源之外的源公开：即加入 公共哈希列表 （PHL）。PHL 是一个供应商中立的、实现定义的 COS 哈希值允许列表。只有当某个哈希通过类似 k-匿名性的流行度门槛后，它才会被加入公共哈希列表（例如，在一定数量的独立源中以逐字节相同的形式出现），从而使确认其存在于共享缓存中不会提供有关任何单个用户的信息。

如果 hash 等于用户代理当前快照中的 公共哈希列表中的某个条目，则一个 COS 哈希 hash 位于 公共哈希列表 上。

公共哈希列表的获取协议、更新频率、数据格式、流行度阈值和治理方式，作为本规范的配套产物进行详细设计，其理念类似于公共后缀列表（Public Suffix List），后者是 [URL] 标准的配套数据文件；参见此仓库中的 公共哈希列表说明文档。该设计提议由 WHATWG 进行治理，以公共后缀列表的跨供应商、滚动发布先例为模型，并采用基于独立确认的普遍性的准入标准。这是上述类似 k-匿名性门槛的一个具体实例，它在哈希被加入列表时离线执行一次，因此用户代理不会在每次查询时重复执行该过程。目前，这些内容尚未在此提案之外建立。该列表自身的早期、非规范性代码原型目前位于此仓库中的 public-hash-list/implementation/；一个专门的跨供应商仓库仍然是 PHL 说明文档中描述的治理目标。本规范仅依赖于某个哈希是否 位于 PHL 上，因此无论该列表的获取机制、治理模型或其余设计如何演变，本规范仍然保持正确。

3. CrossOriginStorageManager 接口

[Exposed=(Window,Worker), SecureContext]
interface CrossOriginStorageManager {
  Promise<FileSystemFileHandle> requestFileHandle(
      CrossOriginStorageRequestFileHandleHash hash,
      optional CrossOriginStorageRequestFileHandleOptions options = {});
};

dictionary CrossOriginStorageRequestFileHandleHash {
  required DOMString value;
  required DOMString algorithm;
};

dictionary CrossOriginStorageRequestFileHandleOptions {
  boolean create = false;
  (DOMString or sequence<DOMString>) origins;
};

interface mixin NavigatorCrossOriginStorage {
  [SameObject, SecureContext] readonly attribute CrossOriginStorageManager crossOriginStorage;
};
Navigator includes NavigatorCrossOriginStorage;
WorkerNavigator includes NavigatorCrossOriginStorage;

每个 Navigator 和 WorkerNavigator 对象都有一个关联的 CrossOriginStorageManager 对象。crossOriginStorage getter 的步骤 是返回this 的关联 CrossOriginStorageManager。

每个 CrossOriginStorageManager 对象都有一个关联的源，在创建该对象时，将其设置为 this 的相关设置对象的源。

注：从 相关设置对象获取源，而不考虑脚本自身的任何信息，对于 worker 有一个值得说明的后果。由 blob: URL 创建的 worker 具有创建它的上下文的 源，因此它与该源的跨源存储视图完全共享：这样的 worker 写入的内容，其创建页面可以读取；页面存储的内容，worker 也可以读取。 blob: URL 本身不是一个源，撤销它也不会使 worker 与该视图分离。由 data: URL 创建的 worker 具有一个 不透明源。本规范目前尚未定义当 调用方 源为不透明源时， requestFileHandle() 的行为； 不透明源规则位于 验证 COS 请求 中，仅规定调用者 命名的源。不透明源没有可用于作为键的稳定身份，无法用于 存储源 或 同站 比较，因此没有任何有意义的授权可以授予它。

3.1. requestFileHandle() 方法

handle = await navigator . crossOriginStorage . requestFileHandle(hash)

如果由 hash 标识的文件存在于跨源存储中，并且可向调用 源披露，则返回该文件的句柄。否则，这会以一个 “NotFoundError” DOMException 拒绝。 “NotFoundError” 并不能证明该文件在 跨源存储中实际上不存在；参见§ 8.3 可用性门控。调用者可以 将其视为“改为从网络获取此文件”。

handle = await navigator . crossOriginStorage . requestFileHandle(hash, { create: true })

返回一个可用于将由 hash 标识的文件写入 跨源 存储的句柄，如果尚不存在条目，则创建一个新条目；默认情况下仅限同站点源访问。 无论条目是否已经 存在，调用者都需要通过该句柄的 createWritable() 方法写入完整文件内容；此时用户代理会验证写入的字节是否哈希为 hash， 否则以一个“DataError” DOMException 拒绝。这一要求可防止 源使用创建请求作为探测 hash 是否已经存在的预言机。

handle = await navigator . crossOriginStorage . requestFileHandle(hash, { create: true, origins: "*" })

同上，并且在写入完成后，还会使该条目可向其对 hash 的请求通过§ 8.3 可用性门控的任何源披露。

handle = await navigator . crossOriginStorage . requestFileHandle(hash, { create: true, origins: ["https://a.example", "https://b.example"] })

同上，但将披露严格限制为所列出的源（此外还包括调用 源以及已经位于存储源中的任何源）。

requestFileHandle(hash, options) 方法 的步骤如下：

  1. 令 result 为一个新的 promise。

  2. 令 realm 为this 的相关 Realm。

  3. 令 global 为this 的相关全局对象。

  4. 令 origin 为this 的关联源。

  5. 如果给定 global 运行检查跨源存储权限 的结果为 false，则：

    1. 给定 global，在DOM 操作任务源上排入一个全局任务，以 一个“NotAllowedError” DOMException 拒绝 result。

    2. 返回 result。

  6. 令 validationFailure 为给定 hash 和 options 运行验证 COS 请求的结果。

  7. 如果 validationFailure 不为 null：

    1. 给定 global，在DOM 操作任务源上排入一个全局任务，以 validationFailure 拒绝 result。

    2. 返回 result。

  8. 将以下步骤入队到 跨源存储队列：

    1. 如果 options["create"] 为 true：

      1. 给定 result、hash、options、global 和 realm，运行完成创建请求。

    2. 否则：

      1. 给定 result、hash、origin、global 和 realm，运行完成读取请求。

  9. 返回 result。

要在给定一个 CrossOriginStorageRequestFileHandleHash hash 和一个 CrossOriginStorageRequestFileHandleOptions options 时验证 COS 请求，返回 null 或一个 TypeError：

  1. 如果 hash["algorithm"] 不是 [WEBCRYPTO] 所识别的哈希算法 名称，则返回一个新的 TypeError。

  2. 如果 hash["value"] 在 hash["algorithm"] 与“SHA-256”以ASCII 不区分大小写 方式匹配时，不匹配正则 表达式 /^[0-9a-f]{64}$/，则返回一个新的 TypeError。

    注：未来的哈希算法可以定义 不同的预期摘要长度；本 规范仅对“SHA-256”施加规范性约束，这与其在所有 示例中的使用一致。

  3. 如果 options["origins"] 存在且 不是“*”：

    1. 令 candidates 为 options["origins"]， 其中单个字符串被视为只有一个元素的列表。

    2. 如果 candidates 的大小 大于用户代理的 最大源列表长度，则返回一个 新的 TypeError。

    3. 对于 candidates 中的每个 candidate：

      1. 如果在 candidate 上运行基本 URL 解析器的结果为失败，或者 已解析 URL 的源是不透明源，则返回一个新的 TypeError。

  4. 返回 null。

3.2. 读取文件

要在给定一个 promise result、一个 COS 哈希 hash、一个 源 origin、一个全局对象 global 和一个 Realm realm 时完成读取 请求：

  1. 令 entry 为 COS 注册表中，其哈希 与 hash 相等的COS 条目（如果有），否则为 null。

  2. 如果 entry 不为 null 且 entry 的状态为“pending”：

    1. 给定 global，在DOM 操作任务源上排入一个全局任务，以一个“NotAllowedError” DOMException 拒绝 result。

    2. 返回。

    注：正在进行写入的哈希 被刻意设计为不表现得像一个 不存在的哈希，以免调用者将进行中的写入误认为真正的缓存未命中， 并仅仅为了 写入这个非常大的文件而开始一次冗余的并发下载。参见§ 3.3 创建和写入文件。

  3. 令 disclosableEntry 为给定 entry 和 origin 运行应用可用性 门控的结果。

  4. 如果 disclosableEntry 为 null：

    1. 给定 global，在DOM 操作任务源上排入一个全局任务，以一个“NotFoundError” DOMException 拒绝 result。

    2. 返回。

  5. 令 handle 为在 realm 中创建一个新的 FileSystemFileHandle [FS] 的结果，其 定位器指向 跨源存储文件系统中的 disclosableEntry。

  6. 将 handle 的 COS 源设置为 origin。

  7. 将 handle 的可读取设置为 true。

    注：此句柄已经通过应用可用性门控，因此调用源 有权访问该条目的字节。

  8. 给定 global，在DOM 操作任务源上排入一个全局任务，以 handle 兑现 result。

要根据一个 COS 条目 或 null entry，以及一个 源 origin， 确定 COS 披露， 返回一个 COS 条目 或 null：

  1. 如果 entry 为 null，则返回 null。

  2. 断言：entry 的 state 为 "written"。

  3. 如果 origin 位于 entry 的 storing origins 中，则返回 entry。

    注：原始存储者，以及任何自身成功写入该条目的源，都始终可以读取该条目。参见 § 3.5.1 原始存储者访问。

  4. 如果 origin 与 entry 的 storing origins 中的某个项同站，则返回 entry。

    注：每个条目都具有的同站基线（没有 origins 选项的写入请求所授予的权限）始终存在， 无论之后是否添加任何 origins 列表或 globally disclosable 授权。 由于它在下面的 公共哈希列表门控之前检查， 同站源无论其 hash 是否 位于 PHL 上，都可以读取该条目。 同站在此处是一个信任单元，因此不会跨越 § 8.2 跨站探测所保护的站点边界泄露信息。

  5. 如果 origin 的 序列化 是 entry 的 origins 中的一项，则返回 entry。

    注：显式 origins 列表中的源无需条目 位于 PHL 上 即可读取该条目。存储源通过指定它做出了受限披露决定（参见 § 3.5 资源可见性升级和 § 7 Cross-Origin-Storage-Allow-Origin 标头）， 而要求额外的全局普遍性会使普通受限共享依赖于通常是专有资源的无关公共管理。 在 globally disclosable门控之前检查这一点， 可以防止后续的全局可用性写入撤销已列出源的访问权限。参见 § 8.2 跨站探测。

  6. 如果 entry 的 globally disclosable 为 true：

    1. 如果 entry 的 hash 不 位于 PHL 上， 则返回 null。

      注：公共哈希列表门控仅适用于全局授权，即唯一一个否则可能向 Web 上任何源披露信息的情况。 一个 globally disclosable 条目如果其 hash 不 位于 PHL 上， 则不会仅通过此授权向源披露；同时属于 storing origins、 其同站集合，或显式 origins 列表中的源，已经在上面的步骤中返回。

    2. 如果用户代理选择对此请求应用 GREASE 化，则返回 null。

      注：GREASE 化也仅适用于全局授权。 上面检查的授权永远不会到达此步骤：存储源及其同站源属于一个信任单元，而显式 origins 列表中的源是由其 Cross-Origin-Storage-Allow-Origin 标头授权的写入者有意指定的。

    3. 返回 entry。

  7. 返回 null。

要根据一个 COS 条目 或 null entry， 以及一个 源 origin， 应用可用性门控， 返回一个 COS 条目 或 null：

  1. 返回运行 确定 COS 披露（给定 entry 和 origin）的结果。

3.3. 创建和写入文件

由完成创建请求创建的 FileSystemFileHandle 有一个关联的 请求的源，其值是当通过该 句柄成功完成写入后，验证并存储将尝试用于升级该条目的源的值。

每个指向 COS 条目的 FileSystemFileHandle 还具有一个关联的 COS 源，即获取它的源，以及一个 关联的 可读取布尔值，它控制 getFile() 是否可以通过该特定句柄披露条目的字节。 对于由完成读取请求返回的句柄，该值为 true，因为它已经通过 可用性门控；对于由 完成 创建请求返回的句柄，该值为 false，直到验证并存储对同一句柄成功完成。

注：这有意地作为每个句柄的属性。创建请求无论条目是否已经存在并且已经为 "written" 状态（参见 完成创建请求），都会返回一个句柄，因此，如果采用按条目的规则，则任何源都可以调用 requestFileHandle() 并传入 create： true，然后立即读取一个它从未写入过的条目，在不满足 origins、 PHL 成员资格或 GREASE 化条件的情况下获知其内容。本规范中的每个披露控制都应用于读取路径，因此按条目进行门控会使创建请求绕过所有这些控制。要求调用者首先提供正确的字节意味着，通过创建获得的句柄进行成功读取时，不会披露调用者原本并不拥有的信息。

要根据 一个 promise result、一个 COS 哈希 hash、一个 CrossOriginStorageRequestFileHandleOptions options、一个全局对象 global，以及一个 Realm realm， 完成创建请求：

  1. 令 requestedOrigins 为运行 规范化请求的源 （给定 options["origins"]） 所得到的结果。

  2. 如果 requestedOrigins 是一个 列表，则将 requestedOrigins 设置为运行 应用 COS 范围上限（给定 requestedOrigins 和运行 获取 COS 范围上限（给定 global）的结果）。

  3. 令 entry 为 COS 注册表中其 hash 等于 hash 的 COS 条目（如果存在），否则为 null。

  4. 如果 entry 为 null：

    1. 将 entry 设置为一个新的 COS 条目，其 hash 为 hash， bytes 为 null， state 为 "pending"， origins 为一个空的 列表， globally disclosable 为 false， 并且 storing origins 为一个空的 集合。

    2. 设置 COS 注册表[hash] 为 entry。

    注：新条目开始时没有显式的 origins 授权，并且不是 globally disclosable； requestedOrigins 会在下面通过 验证和存储中的 升级资源可见性应用于它， 一旦字节被写入并验证，就与查找到现有条目的请求完全相同。这正是创建请求必须先提供完整字节，然后才能扩大可见性的原因（参见 § 3.5 资源可见性升级）。

  5. 将 entry 的 pending writer count 增加 1。

    注：这会跟踪 handle 作为未完成写入者，即使调用者从未在其上调用 createWritable() 或从未关闭生成的流。这样的废弃句柄会永久计入 entry，正如在此机制存在之前，一个废弃的进行中写入已经使 entry 永久保持 "pending" 一样；参见 验证和存储。

  6. 令 handle 为通过创建新的 FileSystemFileHandle [FS]所得的结果， 其 定位器在 Cross-Origin Storage 文件系统中寻址 entry，并位于 realm 中。

  7. 将 handle 的 COS origin 设置为 global 的 相关设置对象的 origin。

  8. 将 handle 的 requested origins 设置为 requestedOrigins。

  9. 将 handle 的 may read 设置为 false。

    注：无论 entry 是否已经存在，以及是否已经为 "written"，都会返回 handle。调用者仍需要通过 handle 提供完整文件字节，以便写入不能用于检测之前是否存在（参见 § 8.2 跨站探测），并且可以在接受更宽松的 origins 值之前验证它；参见 § 3.5 资源可见性升级。

  10. 将全局任务排入队列到 DOM 操作任务源， 给定 global，以 resolve result 为 handle。

要根据一个（DOMString 或 sequence<DOMString>）或 undefined 的 origins， 规范化请求的源， 返回 "*"、一个 列表的 源，或 null：

  1. 如果 origins 不存在，则返回 null。

  2. 如果 origins 是 "*"，则返回 "*"。

  3. 令 list 为 « »。

  4. 对于 origins 中的每个 candidate（单个 字符串被视为包含一个元素的 列表）：

    1. 令 candidateOrigin 为在 candidate 上运行 基本 URL 解析器所得结果中的 origin。

      注：验证 COS 请求 已经确认每个 candidate 都解析为非不透明源。

    2. 如果 list 不包含 candidateOrigin， 则将 candidateOrigin 追加到 list。

  5. 返回 list。

注：在之后任何向现有条目进行合并之前先在此处去重，可以使 origins 从条目首次创建时起就保持无重复，因此之后对其进行的每次 克隆也同样保持无重复。

当通过在一个句柄上调用 createWritable() 获得的 FileSystemWritableFileStream， 其 定位器 指向一个 COS 条目，被关闭时，用户代理必须在该关闭操作的 promise 被兑现之前运行下面的 验证和存储步骤。

注：这适用于关闭由任何方式触发的情况：显式的 close() 调用，或者到达其源末尾的 pipeTo() 调用，后者默认也会关闭其目标。 [STREAMS]不会在流变为关闭状态的时刻区分两者，本算法也不会。

验证和存储步骤， 给定由已关闭流的句柄寻址的 COS 条目 entry、完整写入的 字节序列 bytes，以及关闭操作的 相关设置对象的 origin origin，执行以下步骤：

  1. 令 computedValue 为使用 entry 的 algorithm 指定的算法，根据 [WEBCRYPTO] 计算 bytes 得到的小写十六进制摘要。

  2. 如果 computedValue 不完全等于 entry 的 value：

    1. 拒绝关闭操作的 promise，并返回一个 "DataError" DOMException。

    2. 将以下步骤加入队列到 Cross-Origin Storage 队列：

      1. 将 entry 的 pending writer count 减少 1。

      2. 如果 entry 的 state 为 "pending"， 并且 entry 的 pending writer count 为 0，则从 COS 注册表中移除 entry 的 hash。

    3. 中止这些步骤。

  3. 将以下步骤加入队列到 Cross-Origin Storage 队列：

    1. 将 entry 的 bytes 设置为 bytes。

    2. 将 entry 的 state 设置为 "written"。

    3. 如果尚未存在，则将 origin 追加到 entry 的 storing origins。

    4. 将 entry 的 pending writer count 减少 1。

    5. 给定 entry 和句柄的 requested origins， 运行 升级资源可见性。

    6. 将句柄的 may read 设置为 true。

      注：只有此句柄变为可读。同一条目的另一个句柄，如果来自尚未通过写入完成的不同创建请求，仍然不可读。

createWritable() 在寻址一个 COS 条目的 FileSystemFileHandle 上调用时，必须生成一个 FileSystemWritableFileStream， 其内容初始为空， 无论 keepExistingData 的值为何，也无论被寻址条目的 state为何。

注：[FS] 另外将 keepExistingData 定义为使用现有文件的内容初始化流。在此处遵循该行为会使调用者成为其从未拥有过的字节的存储源。 创建请求无论条目是否已经存在都会返回一个句柄，因此调用者可以为另一个源存储的哈希值打开一个可写流， 在没有写入任何内容的情况下关闭它，并使保留下来的字节哈希到请求的值。这样会在从未检查 origins、 公共哈希列表以及 GREASE 化的情况下，授予其读取访问权限： 这是由两个各自允许的操作组合而成的 可用性门控绕过。 这也是 验证和存储要求每个创建请求都提供完整内容的原因。

注：因此，没有任何写入就关闭的可写流会包含空字节序列， 对于调用者希望获取的任何条目，该序列都不会哈希为请求的值，因此 验证和存储会像处理其他任何不匹配情况一样， 返回一个 "DataError" DOMException。 如果实现反而针对这种情况报告存储或 I/O 失败，则会将验证结果隐藏在无关错误之后。

文件系统标准 [FS] 尚未为依赖规范定义扩展点， 以便将额外的逐写入验证挂接到 FileSystemWritableFileStream 的关闭步骤中。在存在这样的挂接点之前，本节会直接描述所需行为； 未来的修订预计将与 [FS]正式集成。

3.4. 存储已获取的资源

§ 9 与其他规范的集成 中列出的主机集成会存储它们 获取的资源，而不会经过 FileSystemFileHandle。 它们的主机规范应在获取的字节通过集成要求的完整性检查后，运行以下算法。

To 将已获取的资源存储到跨源存储 given a response response, a byte sequence bytes, a COS hash hash, "*", a list of strings, or null origins, and an environment settings object settings:

  1. 如果针对 settings 的 检查跨源存储权限 的 全局对象 运行结果为 false，则返回。

  2. 如果 origins 不为 null，则令 options 为 «[ "origins" → origins ]»，否则令其为 «[ ]»。

  3. 如果针对 hash 和 options 运行 验证 COS 请求 的结果不是 null， 则返回。

  4. 令 computedValue 为使用 hash 的 算法 所命名的算法， 根据 [WEBCRYPTO] 对 bytes 计算得到的小写十六进制摘要。

  5. 如果 computedValue 不与 hash 的 value 完全相等，则返回。

    Note: 集成自身的完整性元数据可以列出多个摘要， 与其中任意一个匹配都能满足要求。此步骤确保该条目由这些确切字节生成的哈希作为键。

  6. 令 requestedOrigins 为针对 options["origins"] 运行 规范化请求的 origins 的结果。

  7. 如果 requestedOrigins 是一个 list：

    1. 如果 response 是一个 filtered response， 则令 internalResponse 为 response 的 internal response， 否则令其为 response。

    2. 将 requestedOrigins 设置为针对 requestedOrigins 和 针对 internalResponse 的 header list 运行 解析 COS 范围上限 后，再运行 应用 COS 范围上限 的结果。

    Note: 上限来自已获取资源自身的 response， 因此提供字节的服务器决定它们可以向哪些 origins 公开。加载中的 Document 的 COS 范围上限 不起作用： 它的操作方不控制该资源，并且允许它授权接收方会使任何站点都能声明另一个站点的资源可与其选择的 origins 共享。用户代理从内部 response 中读取该标头， 因此这同样适用于不透明的 filtered response， 并且该标头永远不会暴露给页面。

  8. 令 origin 为 settings 的 origin。

  9. 将以下步骤加入 跨源存储队列：

    1. 令 entry 为 COS 注册表 中其 hash equals hash 的 COS entry， 如果存在，则为该条目，否则为 null。

    2. 如果 entry 为 null：

      1. 将 entry 设置为新的 COS entry， 其 hash 为 hash， bytes 为 null， state 为 "pending"， origins 为一个空的 list， globally disclosable 为 false， 并且 storing origins 为一个空的 set。

      2. 设置 COS 注册表[hash] 为 entry。

    3. 如果 entry 的 state 为 "pending"：

      1. 将 entry 的 bytes 设置为 bytes。

      2. 将 entry 的 state 设置为 "written"。

      Note: 这里的条目可以处于 "pending" 状态，因为相同 hash 的 requestFileHandle() 写入器仍在执行。其 pending writer count 保持不变，因此该写入器自身的 verify and store 仍会正常完成；其 bytes 的 hash 计算结果相同，因此再次存储不会产生变化。

    4. 如果尚未存在，则将 origin 追加 到 entry 的 storing origins 中。

    5. 针对 entry 和 requestedOrigins 运行 升级资源可见性。

Note: 与 verify and store 一样， 存储始终需要完整的 bytes，包括条目已经为 "written" 的情况，因此它不会透露先前是否存在。 集成在网络获取之前执行的 lookup 是一次读取，受 availability gating 以及 § 8.2 跨站探测 中探测相关考虑的约束。

3.5. 资源可见性升级

COS entry 的可见性可以升级，但绝不会降级。

To 升级 resource visibility given a COS entry entry and "*", a list of origins, or null requestedOrigins:

  1. 如果 requestedOrigins 为 null，则返回。

    Note: 省略 origins 只请求同站点可用性，而每个条目已经具有该可用性（参见 确定 COS disclosure），因此没有需要添加的内容。

  2. 如果 requestedOrigins 为 "*"：

    1. 将 entry 的 globally disclosable 设置为 true。

    2. 返回。

    Note: 这会添加全局授权；它不会影响 entry 的 origins。 已经具有显式 origins list 的条目会保留该列表，因此即使条目变为 globally disclosable 后， 该 list 中的每个 origin 仍保持其 PHL-独立访问权限。 这正是两个授权被分别存储的核心原因；参见 globally disclosable。

  3. 对于 requestedOrigins 中的每个 candidateOrigin：

    1. 如果 entry 的 origins contains candidateOrigin，则 continue。

    2. 如果 entry 的 origins 的 size 等于用户代理的 maximum origins list length， 则中断。

      Note: 由于写入操作本身已经成功， 此升级中剩余的 candidateOrigin 值会被静默丢弃， 因为用户代理应记录控制台警告，说明条目的 origins 列表已达到容量。

    3. 将 candidateOrigin Append 到 entry 的 origins。

Note: 升级操作只会向 origins 添加内容， 或将 globally disclosable 设置为 true。请求一个 list 的写入器会扩展已经 globally disclosable 的条目， 就像扩展未全局公开的条目一样，因为两个授权是独立的：新列出的 origins 会获得 PHL-独立访问权限， 即使 "*" 授权仍然有效。

Note: 任何站点，包括原始存储者之外的站点， 只要同时提供哈希值与条目 hash 匹配的字节，就可以扩展条目的 origins。 这是有意设计的：任何已经拥有某个 hash 对应正确字节的站点， 根据构造，它对于该 hash 所表示内容的权威性与原始存储者相同。

3.5.1. 原始存储者访问

已经成功完成 writing 一个 COS entry 的 origin （即条目的 storing origins 中的任意 origin） 随后始终可以通过 requestFileHandle() 获取其句柄， 不受条目的 origins 值影响， 也不受其 hash 是否 on the PHL 影响。 这与 Cache API 的模型相一致，在该模型中，origin 始终可以访问自己存储的内容。

4. 跨源存储文件系统

跨源存储文件系统 是一个文件系统根，不同于任何 origin 的存储桶文件系统或本地文件系统访问根，其 条目与COS 注册表的COS 条目项目一一对应。

跨源存储文件系统不使用[FS] 的普通逐调用 权限检查 模型：从该文件系统获取的每个FileSystemFileHandle 在返回给脚本之前，已经由 § 3.2 读取文件或§ 3.3 创建和 写入文件完全授权，因此对这类句柄调用 getFile()或createWritable() 永远不会触发额外的权限提示。

因此，对这类句柄调用queryPermission()和requestPermission()绝不能报告 "prompt"，因为不会出现提示。对于 不是通过创建请求获取的句柄，在写入模式下必须报告 "denied"；否则必须报告 "granted"。

注：写入是句柄确实可能缺少的唯一能力。只有创建请求才能产生一个 可以通过它写入的句柄，因此对于任何其他句柄的写入模式报告 "granted" 会声称createWritable() 不会拒绝。读取则保持为 "granted"，因为持有可读句柄的调用方可以通过它进行读取。请求无法 改变任一答案，因为没有要显示的提示，也没有可记录授权的状态。

对getFile() 调用一个FileSystemFileHandle，其指向的 COS 条目的may read为 false 时，必须拒绝并抛出一个 "NotAllowedError" DOMException。 这涵盖两种不同的情况：

  • 来自创建请求的句柄，其条目仍处于 "pending" 状态，原因与针对相同哈希的并发 requestFileHandle() 调用被拒绝的原因相同（见 § 3.2 读取文件）：调用方不得将尚未验证的占位符 作为文件的真实内容进行观察。

  • 来自针对某个条目的创建请求的句柄，而该条目已经由某个其他 origin 写入。该 条目的状态为 "written"，但此调用方没有提供字节，也没有通过可用性门控， 因此它不得获知有关该条目的任何信息，甚至不能知道它是否存在。

一旦句柄的may read为 true，对其调用getFile() 就会返回一个File， 其内容是所指向条目的字节；这正是[FS]已经为文件 条目定义的行为，该条目的 二进制数据就是这些字节。

指向COS 条目的FileSystemFileHandle具有一个文件系统定位器，其 路径 是一个列表， 其中包含一个字符串，即该条目的 COS 哈希的值；其根是 跨源存储文件系统。

注：[FS] 将name 定义为句柄定位器路径的最后一个路径组成部分，因此这也确定了name： 它就是 哈希。条目没有自己的名称，而哈希是它唯一的身份，因此报告哈希可以携带信息，而空字符串会丢失这些信息。

条目没有名称，也没有包含它的目录，因此[FS]的大多数结构性接口都没有可操作的对象。身份是例外，而且这是内容寻址条目 始终能够回答的唯一问题：COS 注册表针对每个COS 哈希最多持有一个COS 条目，因此两个句柄恰好在其哈希相等时指向同一个条目。

在指向COS 条目的isSameEntry() 上调用该方法时，如果参数也指向一个COS 条目，并且由同一 origin获取，则当两个句柄的COS 哈希项目相等时必须返回 true，否则返回 false。

注：拒绝这样做会丢弃用户代理已经持有的信息。

使用调用origin未获取的参数调用isSameEntry()， 或使用一个指向并非跨源存储文件系统的文件系统的参数调用， 都必须拒绝。

注：在这种情况下返回 false 会断言两个句柄指向不同的条目， 这涉及调用 origin 无权检查的句柄。拒绝只表示无法进行比较。

对指向COS 条目的 FileSystemFileHandle调用 move()和remove()时，必须拒绝并抛出一个"NotAllowedError" DOMException， 且必须保持条目不变。

注：条目由其存储 origin中的每个 origin 共享，因此执行移除会使一个站点能够销毁其他站点所依赖的数据；删除属于 驱逐和用户自己的存储控制。重命名或重新挂接没有可操作的对象，因为条目由其COS 哈希命名，并且没有包含它的目录。

注：在撰写本文时，[FS]或 File System Access API 都没有定义这两个方法 (WICG/file-system-access#214)， 因此错误名称遵循removeEntry()， 即[FS]为删除条目所定义的操作：当未授予读写访问权限时，它会使用访问结果的错误名称拒绝。此处拒绝是准确的行为：这些操作具有实际意义，但被禁止。

createSyncAccessHandle() 在此无需额外规则：当句柄不位于存储桶文件系统中时，其步骤会拒绝并抛出一个 "InvalidStateError" DOMException； 而跨源存储文件系统是一个文件系统根，不同于任何 origin 的文件系统根， 因此[FS]已经确定了拒绝行为及其名称。

注：这也正是本规范独立地希望得到的结果。一个 FileSystemSyncAccessHandle 会向调用方提供可写文件描述符，从而允许它在其所存储的COS 哈希之下 修改条目的字节， 而该条目对其他所有可披露的 origin 都可见，它们读取的正是相同的字节。

4.1. 传输句柄

一个FileSystemFileHandle 是一个可序列化对象 [FS]，因此，指向一个 COS 条目的句柄可以传递给另一个环境设置对象，例如通过 postMessage(message, options)。 这是获得此类句柄的第二种方式，另一种方式是 requestFileHandle()， 因此这里同样对其加以限制。

对于指向序列化步骤的FileSystemFileHandle， 给定value和serialized，还需执行以下步骤：

  1. 将serialized.[[COSOrigin]]设置为value的COS origin。

  2. 将serialized.[[COSMayRead]]设置为value的may read。

给定serialized、value和realm时，反序列化步骤还需执行以下步骤：

  1. 如果serialized.[[COSOrigin]]与realm的同源不相同，则抛出一个 "DataCloneError" DOMException。

  2. 将value的COS origin设置为 serialized.[[COSOrigin]]。

  3. 将value的may read设置为 serialized.[[COSMayRead]]。

注：如果没有同源检查， 传递句柄将一次性破坏本规范中的所有披露控制。其may read为 true 的句柄已经 为请求它的 origin通过了应用可用性门控；将其发布给另一个 origin 会使该 origin 直接获得条目的字节，而无需对该 origin 的origins、 PHL 成员资格或GREASE进行评估。这与 File System Standard 对句柄的现有处理方式一致，因为句柄同样仅对 同源接收方有用。

注：may read会随句柄一起传递， 因此，尚未通过写入完成的创建请求句柄在传递后仍然不可读，而读取请求句柄则保持可读，无需重新进行门控。到达后重新进行门控会使 调用方能够通过传递同一个句柄来反复探测可用性。

5. 存储管理

5.1. 存储限制

用户代理必须对一个origin通过成功写入可以贡献给 COS 注册表的总字节数施加限制，以防止单个 origin 通过泛洪缓存来试图驱逐其他 origin 的条目。具体限制是 实现定义的。如果某个 origin 的写入将超出其 限制，用户代理必须 拒绝该 写入，并抛出一个 "QuotaExceededError" DOMException， 并且应当向控制台记录警告。

注：由于条目是内容可寻址的，某个 origin 在同一哈希下反复写入相同的 字节不会消耗第一次成功写入之外的额外配额；参见 § 2.2 COS 条目。

用户代理还有一个实现定义的最大 origins 列表长度，一个 正整数，限定单个origins列表可以 包含多少个origin。这在列表首次提供时（见校验一个 COS 请求） 以及之后合并到现有条目中时（见 升级资源可见性）都会被强制执行，因此无论是单次调用还是 随时间推移多次调用的累积效果，都无法让一个条目的origins无限 增长。除了限制内存使用之外，这还防止origins 列表被用作 "*"的未声明替代品；参见§ 8.2 跨站探测。

超出此限制在这两处的处理方式不同，因为这两次调用发生在操作中截然不同的阶段：

  • 在校验一个 COS 请求中，该限制是在任何文件被获取、哈希化或 写入之前被检查的。超出限制的调用方会立即得到一个 "TypeError"， 此外不会发生任何其他事情， 这与任何其他格式错误的origins 值所受到的处理相同。

  • 在升级资源可见性中，该限制只能通过跨越多次独立、分开的写入调用（可能来自 彼此无关的 origin，跨越很长一段时间）所请求的 origin 的累积效果才能触及，并且它仅在此次调用的字节已经被哈希化、 验证并持久存储之后才被检查。此时拒绝写入会丢弃一次成功的、已经验证过的、可能非常大的写入，只因为一个与之无关的记账限制， 而且甚至无法归咎于单个调用方的错误。因此该写入被允许成功，只有超出容量的那些 origin 会从origins中被丢弃，并附带一条 控制台警告。这与现有的 从宽松到更严格请求的处理方式相呼应：一个origin请求 如果无法被完全满足，就会被静默地截断上限，而携带该请求的写入仍然会成功。与本规范其他部分中的 § 8.3 可用性门控保持一致， 调用方事后没有可靠的方法来确认其请求的origin是否实际被 添加：即使该 origin 已被添加，之后以该 origin 身份发起的requestFileHandle() 调用仍然可能失败（例如，因为该条目 已被驱逐或用户代理对请求进行了节流），因此其结果不能被解读为对该问题任何一方向的确认。

5.2. 驱逐

本节为非规范性内容。

在存储压力下，用户代理可以驱逐条目， 使其脱离COS 注册表， 例如在最近访问过每个条目的存储 origins之间使用最近最少使用策略。用户代理应当提供设置界面， 用户可以通过该界面查看存储了哪些文件、哪些 origin 访问过每个文件，并手动 删除条目或清除所有跨源存储数据。

当用户清除某个 origin 的站点数据时，用户代理应当将该 origin 从其出现的每个 存储 origins集合中移除。如果在移除之后，某个COS 条目的 存储 origins为空，则用户代理可以考虑删除该条目。

5.3. 手动添加的条目

本节为非规范性内容。

上述设置界面可以允许用户直接将磁盘上已有的文件添加到 跨源存储中（例如，用户独立于任何网站下载的 AI 模型），而无需任何脚本调用过requestFileHandle()。 这样的条目 没有可归因于写入操作的请求origin，这就引出了两个命令式 API 本身无法回答的问题：

  • 就§ 3.5.1 原始存储者访问而言，谁是原始存储者？没有人：该条目的存储 origins起初为空。 因此，没有任何 origin 可以免于所有请求 origin 通常都必须接受的普通可用性门控和 origins检查。这是正确的结果，因为实际上没有任何 origin 写入这些字节。

  • 这样的条目是否应当像省略 origins 的普通写入一样，仅限于同站点？不应当："同站点"只有相对于请求 origin 才有意义，而手动添加没有请求 origin，因此不存在可供"同站点"所指的站点。用户代理应当使这样的条目对全局可披露， 并将其显式的origins列表保留为空，因为手动预置文件只有在其他 origin 实际上能够发现它时才有意义（这样用户尚未访问过的站点才能复用用户磁盘上已有的文件）。用户代理的设置界面还可以允许用户选择更窄的范围。

以这种方式添加后，状态为 "written" 的条目在其他方面与网站通过requestFileHandle()写入的条目没有区别： 相同的可用性门控和可见性升级规则同样适用于它，正如适用于任何具有相同授权的其他条目一样。 其中包括：每当该条目最终对全局可披露时，都要执行位于 PHL 上检查；对于手动添加的条目而言，这是默认情况。

5.4. 来源元数据

本节为非规范性内容。

一个COS 条目有意不记录其字节的来源。其身份仅由 哈希确定：无论有多少个 origin 存储了 相同的字节，也无论这些字节是从多少个 URL 获取的，它们都属于同一个条目（见§ 2.2 COS 条目）。URL 是某个 写入者执行获取操作时的属性，因此对于由多个 origin 写入的条目，不存在非任意的方式来选择其中一个 URL；URL 也无法像字节那样被验证 （见§ 8.1 资源完整性）；而且，与 origin相比，它携带的用户浏览信息要多得多，因为路径或查询字符串可以指明特定的文档、 账户或会话。因此，将其记录在条目上会绕过origins和§ 8.3 可用性 门控旨在施加的披露限制，传递高熵信号。

尽管如此，想要获得该信息的动机确实存在：在§ 5.2 驱逐所述的设置界面中查看一个数 GB 大小文件的 用户，以及调试为何requestFileHandle() 调用未命中的开发者，都希望知道文件的来源。用户代理可以通过在条目旁保留一份实现私有的来源记录来满足这一需求 （例如，每个存储 origin从哪个 URL 获取了 字节，以及获取时间），但必须确保该记录被视为保存在条目之外的用户代理状态：

  • 它永远不会暴露给脚本。本规范中的任何内容都不会披露它，今后添加的任何内容也不应披露：无论是requestFileHandle() 还是其返回的 FileSystemFileHandle 都不应揭示此类记录是否存在，更不应揭示其内容。特别是，请求的origin不得观察到不是由其自身生成的记录。

  • 它只能通过受信任的非 Web 界面展现：用户代理自身的设置和存储检查界面、其开发者工具，以及（如果用户代理具有扩展平台） 在明确获得用户授权的权限控制下提供的扩展 API，其权限级别应与其他会暴露浏览历史的 API 相同。有关正在考虑的扩展界面， 请参见本仓库中的浏览器扩展集成点说明。

  • 它未经验证，并且会以未经验证的状态呈现。其中的 URL 是写入字节的 origin 所作的声明。只有哈希能够保证内容（见§ 8.1 资源完整性）。两个 origin 可能为同一个条目记录不同的 URL，而任一 URL 都可能不准确或故意误导。

  • 它与条目以及归属于该条目的 origin 具有相同的生命周期。当条目被驱逐或删除时，该记录也会被丢弃；当某个 origin 从存储 origins中移除时，归属于该 origin 的部分也会被丢弃，包括用户清除该 origin 的站点数据时（见§ 5.2 驱逐）。

由于此类记录对内容不可见，用户代理是否保留记录以及保留多少记录，完全由实现决定。本规范中的任何内容都不依赖于它，网站也无法检测到其 存在或缺失。

6. 权限策略集成

本规范定义了一个策略控制特性 [permissions-policy]，其标识字符串为 "cross-origin-storage"。其默认允许列表 为self。

[permissions-policy]针对Document定义了允许使用，但 CrossOriginStorageManager 也暴露在WorkerGlobalScope上， 而后者自身没有 Document。 因此，该检查是针对调用方的全局对象表述的：worker 全局对象会传递性地解析到拥有它的 Document， 并且其中每一个都必须允许该特性。

给定一个全局对象global，检查跨源存储权限，返回一个 布尔值：

  1. 如果global是一个Window 对象，则：

    1. 令document为global的关联 Document。

    2. 如果document为 null，则返回 false。

    3. 如果document不允许使用 "cross-origin-storage" 策略控制特性， 则返回 false。

    4. 返回 true。

  2. 如果global是一个WorkerGlobalScope 对象，则：

    1. 令owners为global的所有者集合。

    2. 如果owners为空，则返回 false。

    3. 对owners中的每个owner进行遍历：

      1. 如果owner是一个Document， 并且owner不允许使用 "cross-origin-storage" 策略控制特性， 则返回 false。

      2. 如果owner是一个WorkerGlobalScope 对象，并且给定owner运行检查跨源存储权限的结果为 false，则返回 false。

    4. 返回 true。

  3. 返回 false。

对于该算法返回 false 的全局对象，从其发起的每个 requestFileHandle() 调用都会在任何哈希验证、注册表查找或写入发生之前，以一个 "NotAllowedError" DOMException 拒绝。

注：通过所有者集合进行解析，才能防止该特性仅仅在名义上可选择退出。由blob: URL 创建的 worker 在其创建页面的origin中运行，并且完全共享该页面的跨源存储视图（见 § 3 CrossOriginStorageManager 接口），因此，如果只检查全局对象自身的 Document， 则每个 worker 都会因为没有自身的 Document 而无条件通过检查；而将调用移入 new Worker(URL.createObjectURL(&hellip;))就会在不改变其他任何内容的情况下绕过 cross-origin-storage=()策略。

注：ServiceWorkerGlobalScope的 所有者集合为空，因此该算法会在此返回 false。这是由所有者集合的定义决定的：它是一种 活跃关系，在创建 worker 时建立，并用于判断该 worker 是否仍然被主动需要。service worker 则有意不与任何Document建立这种关系： 其注册信息会持久保存，用户代理响应事件启动该全局对象，而且它完全可以在没有任何service worker 客户端的情况下运行。调用 register() 的客户端在注册时是已知的，但到全局对象运行时通常早已不存在，而一个正在运行的 service worker 会服务于多个客户端，这些客户端的策略不必一致。

注：要覆盖 service worker，需要捕获策略，而这项工作属于 [permissions-policy]和[service-workers]。本规范倾向采用的形式是：从其自身脚本响应中的 Permissions-Policy标头推导 service worker 的策略，就像其策略容器已经携带该响应的 CSP 一样：策略仍由 origin 控制，并且会在每次更新检查时重新评估。将注册客户端的策略快照保存下来会使退出选择失效，因为从标头中移除该特性要等到注册恰好更新后才会生效。在这种模型存在之前，默认拒绝是唯一无法被用来绕过退出选择的答案。

注：SharedWorkerGlobalScope的 所有者集合可以包含具有不同策略的多个 Document， 并且会在 worker 的生命周期内增加和移除所有者。要求每个所有者都允许该特性，意味着一个不允许该特性的所有者会为整个共享 worker 禁用跨源存储，而且两次 requestFileHandle() 调用之间的结果可能发生变化。另一种做法是只要求一个允许使用的所有者，这会使任何允许该特性的文档都能代表不允许该特性的文档重新启用它。

7. Cross-Origin-Storage-Allow-Origin 标头

其COS 条目的origins列表非空时，可以向写入 origin 不控制的 origin 披露该条目， 但该列表是由脚本（通过 origins） 或标记声明的，而已经实现脚本或标记注入的攻击者可以设置其中任意一种。为了将该声明以注入内容无法伪造的形式绑定到其字节被披露的 origin 的运营者，本规范定义了一个响应标头，用于限定此类声明可以指定哪些 origin。

Cross-Origin-Storage-Allow-Origin 响应标头携带一个 COS 范围上限：一个集合，其中包含写入可以在非同站点 origins列表中指定的origin。提供字节的一方发送该标头，因此应从承载所披露字节的响应中读取：

  • 对于requestFileHandle() 写入，其字节可能在脚本中生成，并且没有自身的来源响应，该响应是用于创建调用方全局对象的Document的 响应；对于 worker，则是拥有它的 Document的响应（见获取 COS 范围上限）。

  • 对于宿主集成，该响应是所获取资源的响应，所获取资源的字节将被存储 （见将获取的资源存储到跨源存储）。这是资源服务器的响应，该服务器不一定是加载该资源的Document的服务器。

声明的列表会与上限进行交集运算（见应用 COS 范围上限），因此上限只能缩小声明范围。

注：该标头是提供字节的一方所作的授权。它指定的 origin，即最终的读取者，不会被询问，也不会发送任何内容：列出的 origin 仅在稍后像其他读取者一样，通过针对该COS 哈希调用requestFileHandle()时参与其中。这与Access-Control-Allow-Origin[FETCH]的方向相反，后者中，持有资源的服务器选择允许某个 origin 读取资源。在此处，字节提供者限定谁之后可以从跨源存储读取这些字节，而写入页面上的注入内容无法扩展该限制，因为它无法设置提供者的响应标头。

注：该标头仅适用于列表形式。同站点默认值不指定跨源接收者，因此不需要授权；而"*"形式在读取路径上由针对可用性门控的公共哈希列表进行管理，用户专属密钥永远无法绕过该列表，因此写入时也不需要范围上限。要求"*"提供标头还会破坏零配置的全局共享情形，却无法关闭公共哈希列表尚未关闭的任何内容。

给定一个标头列表headers，解析 COS 范围上限并返回一个包含 origin的集合：

  1. 令value为从headers中对"Cross-Origin-Storage-Allow-Origin"执行获取、解码并拆分的结果。

  2. 如果value为 null，则返回一个空的集合。

  3. 令ceiling为空的集合。

  4. 对value中的每个token进行遍历：

    1. 从token中移除开头和结尾的 ASCII 空白。

    2. 如果token是空字符串，则继续。

    3. 令origin为对token运行基本 URL 解析器的结果所产生的origin。

    4. 如果origin为失败或为不透明 origin，则返回空的集合。

      注：这包括值为"*"的token，因为它无法解析为 origin。Cross-Origin-Storage-Allow-Origin标头只能枚举有限的具体 origin；"*"不是允许的值，因为"任意 origin"的上限会使注入内容能够声明其任意选择的接收者，从而破坏该标头的全部目的。只有通过由公共哈希列表进行门控、且永远不查询此标头的"*"origins形式，才能实现无界披露。格式错误或包含"*"的标头不授权任何内容，处理方式与缺少标头完全相同；遇到失败时采取封闭策略。

    5. 将origin追加到ceiling。

  5. 返回ceiling。

注：获取、解码并拆分会在 U+002C（,）处拆分，因此标头值中的 origin 以逗号分隔，这与Timing-Allow-Origin[RESOURCE-TIMING]以及列表型 HTTP 响应标头的一般约定相匹配，尽管同级的crossoriginstorage HTML 内容属性使用空格分隔，以匹配其宿主语法。两者最终都会得到相同的origin集合。

给定一个全局对象global，获取 COS 范围上限并返回一个包含 origin的集合：

  1. 如果global是一个Window 对象，则：

    1. 令document为global的关联 Document。

    2. 如果document为 null，则返回空的集合。

    3. 返回document的COS 范围上限。

  2. 如果global是一个WorkerGlobalScope 对象，则：

    1. 令owners为global的所有者集合。

    2. 如果owners为空，则返回空的集合。

    3. 令ceiling为 null。

    4. 对owners中的每个owner进行遍历：

      1. 令ownerCeiling为空的集合。

      2. 如果owner是一个Document，则将ownerCeiling设置为owner的 COS 范围上限。

      3. 否则，如果owner是一个WorkerGlobalScope 对象，则将ownerCeiling设置为以下结果： 给定owner运行获取 COS 范围上限。

      4. 如果ceiling为 null，则将ceiling设置为ownerCeiling； 否则将ceiling设置为ceiling与ownerCeiling的交集。

    5. 返回ceiling。

  3. 返回空的集合。

给定一个包含origin的列表requestedOrigins以及一个包含origin的集合ceiling，应用 COS 范围上限并返回包含origin的列表或 null：

  1. 从requestedOrigins中移除ceiling不包含的每个origin。

    注：不在COS 范围上限中的接收者会被丢弃，但写入仍然成功，这与升级资源可见性中超出长度上限时丢弃多余项的处理方式一致。用户代理应当记录控制台警告，并列出每个被丢弃的origin。

  2. 如果requestedOrigins为空，则返回 null。

    注：其中每个成员都被丢弃的列表会使写入不再具有获得授权的跨源接收者，因此回退到同站点默认值。字节仍然会被存储；仅未授权的披露被阻止。

  3. 返回requestedOrigins。

每个Document 都有一个COS 范围上限，即一个包含origin的集合。当文档创建时，将其设置为以下结果：给定用于创建它的响应的标头列表运行解析 COS 范围上限。

注：对 worker 的所有者集合取交集，与检查跨源存储权限相一致：只有每个拥有该 worker 的 Document都以传递方式授权了某个 origin，该 origin 才会处于 worker 的范围上限中。由于blob: worker 完全共享其创建页面的origin和跨源存储视图（见§ 3 CrossOriginStorageManager 接口），只查询 worker 自身的范围上限会使每个 worker 的范围上限都为空；而将列表范围的写入移入 new Worker(URL.createObjectURL(&hellip;))会移除页面授权的接收者；对所有者的范围上限取交集，可以在不允许任何单个所有者扩大范围的情况下保留该授权。

从Document的COS 范围上限的响应中填充该上限，需要在[HTML]的文档创建步骤中添加一个钩子，就像[permissions-policy]和[CSP]在响应处理时被填充一样。在该钩子存在之前，本节直接描述所需行为；预计未来修订版会正式集成该钩子，并与[FS]钩子一并集成，后者见§ 3.3 创建和写入文件。宿主集成不需要这样的钩子：它们将获取的响应传递给将获取的资源存储到跨源存储，该算法会从响应中读取范围上限。

8. 隐私和安全注意事项

除使用 RFC 2119 关键词之处外，本节均为非规范性内容；另请参见仓库中的 安全和隐私问卷。

8.1. 资源完整性

每个COS 条目都由一个加密哈希作为键，并根据该哈希验证其 字节（见§ 3.3 创建和写入文件）。因此，网站可以确定，通过 requestFileHandle() 获取的文件，其字节与直接获取hash本身所得到的字节完全相同。开发者无法枚举跨源存储的内容，也无法在事先不知道文件哈希的情况下访问文件。

COS 哈希不是秘密。它是一个内容标识符，任何已经拥有该文件的人都可以轻易计算出来；对于本规范所针对的广泛分发资源而言，它通常也是公开知悉的信息，并且经常会与模型或库的发布一同公布。因此，知道哈希足以查找条目，但哈希本身并不授予任何访问权限：查找是否成功完全由origins和§ 8.3 可用性门控决定。开发者不得将未公布的哈希视为访问控制机制；对特定文件感兴趣的攻击者不需要猜测其哈希，只需获取文件本身即可（见§ 8.2 跨站探测）。

8.2. 跨站点探测

如果某个资源仅被一小部分站点使用，那么能够获知该资源存在于跨源存储中的攻击者就可以推断出，用户很可能访问过其中某个站点。由于 requestFileHandle() 是获知资源是否存在的机制，因此每次调用 实际上都是一次探测。本规范中有两种独立的机制限定了一次探测能够获知的信息：

  • origins（见 § 3.5 资源可见性升级）允许存储 origin 将披露范围限制在一组选定的 origin 内，因此专有的或低流行度的资源根本无需能够被全局探测。

  • § 8.3 可用性门控还会对"*"范围的资源，向不属于其存储 origins的请求 origin 隐瞒披露，除非该哈希位于 PHL 上， 因此以origins: "*"存储的资源 不会自动被 web 上的每个 origin 探测到。此门控仅适用于 "*"范围的条目；对于列表范围和同站点范围的条目，第一条要点中的限制是唯一的门控，因为存储 origin 已经为这些条目明确限定了披露范围。

第一条要点只有在"选定的 origin 集合"始终保持明显小于整个 web 的情况下才成立。origins的形式本身 没有任何东西能阻止调用方 枚举数量非常庞大的 origin（例如，由公开的热门站点排名汇总而成的列表），这实际上会近似于全局披露，同时绕过仅"*"才要求的、经过深思熟虑的明确选择性加入。最大 origins 列表长度（见 § 5.1 存储限制）限定了这一点：一个足够小以容纳真正的多属性使用场景（受共同控制的少数相关 origin） 、但远远达不到对"每个 origin"进行有意义近似的限制，可以防止origins的受限 origin 形式被用作 "*"的未声明替代品。

用户代理还应当对来自单个 origin 的重复 requestFileHandle() 调用进行速率限制或以其他方式加以节流，并且可以应用 设备端启发式方法（例如，检测看似按用户逐一生成的哈希请求模式），以识别并阻止探测尝试，而不论被探测的 哈希是否位于 PHL 上。

由§ 9 与其他规范的集成中某个宿主集成执行的查找同样是一种探测，即便它不会向页面呈现任何错误：站点可以观察其 自身的服务器是否收到了回退请求，而该请求携带的信息位与此处"未找到"结果所携带的相同单个信息位相同。此类查找不会披露本规范的门控原本不会披露的任何内容， 这些门控原封不动地适用于它。然而，速率限制只有在这些界面的查找与 requestFileHandle() 调用一并计数时才有效，因为 可脚本化的集成同样可以轻易地在循环中发出这些查找。

8.3. 可用性门控

从存储 origins之外的 origin 发起的requestFileHandle() 读取是否成功，始终取决于请求 origin 是否获准读取该条目，这由origins决定。对于"*"范围的条目，还存在第二个相互独立的问题：用户代理是否愿意披露该条目确实存在，这由PHL 成员资格和GREASE决定。对于此类条目，这两个条件都必须满足；对于列表范围或同站点范围的条目，仅适用第一个问题。 规范性算法见§ 3.2 读取文件。因此，"NotFoundError" 并不能证明资源不存在：它可能意味着资源不存在、请求 origin 超出了范围、"*"范围资源的哈希尚未（或永远不会）位于 PHL 上，或者 GREASE 抑制了本应为真的结果。开发者不得将"NotFoundError" 理解为比"回退到网络"更具体的任何含义。

注：""*""范围条目的披露范围还受到限制，仅适用于在当前上下文中能够设置或读取第三方 cookie 的请求 origin；无论PHL成员资格如何，对于不可使用第三方 cookie 的 origin，都不会披露此类条目。这弥补了仅靠PHL成员资格无法解决的漏洞：攻击者可以通过选择要写入的资源子集，利用其他方面普通且单独符合 PHL 条件的资源构建跨站标识符，而第三方 cookie 的可用性决定了由此产生的探测是否比普通跟踪 cookie 提供更多信息。

8.4. GREASE 处理

用户代理可以应用GREASE（生成 随机扩展并保持 可扩展性）：即使§ 8.3 可用性门控原本会 允许披露，也偶尔表现得如同一个可披露的条目不存在。这会增加噪声，使站点更难区分真实的 不存在与出于隐私考虑而产生的假阴性，类似于 UA Client Hints所采用的技术。

GREASE 仅适用于仅凭对全局可披露 授权而合格的 origin，这与公共哈希列表门控的情形相同（见确定 COS 披露）。用户代理不得将其应用于存储 origins、与其同站点的 origin，或者位于显式origins列表中的 origin。

应用 GREASE 的用户代理必须根据相关条目的大小按比例作出判断。对于小型条目，回退到网络获取的成本较低，偶尔出现假阴性是合理的隐私权衡。用户代理不得对以下大小的条目应用 GREASE：其大小使得虚假的重新下载明显与由此获得的隐私收益不成比例 （例如，GB 级别的 AI 模型权重），因为在这种情况下产生假阴性会强制进行一次完整的、可被观察到的、代价高昂的重新下载。

8.5. 指纹识别

攻击者通过探测跨源存储能够提取的信息，受被探测 资源流行程度的限制。得知用户拥有非常流行的资源，例如常见的 AI 模型 或广泛使用的 JavaScript 库，只能表明用户访问过使用它的（可能非常 多的）站点之一。得知用户拥有罕见或唯一的资源则提供了多得多的信息。 用户代理应当应用设备端启发式方法，检测其哈希看起来 被刻意设计为每用户唯一的资源（例如，仅由单个 站点写入过的哈希，或以异常高频率被请求的哈希），并将此类模式视为探测尝试， 不论其名义上的 PHL 状态如何。

9. 与其他规范的集成

本节为非规范性内容。

此处定义的COS 注册表还可通过四种宿主集成访问，而无需直接经过 requestFileHandle()。 每种 集成都在其自身的宿主规范中定义。本规范定义了共享的底层概念（COS 哈希、COS 条目、可用性门控以及 公共哈希列表）和将获取的资源存储到跨源存储步骤， 这些集成应当以此为基础构建。

  • HTML：link和 script元素上的 crossoriginstorage属性；这些元素已经带有 integrity [SRI]，并已向 WHATWG 提议，见 whatwg/html#12770。

  • JavaScript：由宿主定义的crossOriginStorage导入属性，可与 integrity配合使用，基于Import Attributes 提案构建，并已向 WHATWG 提议，见 whatwg/html#12771。

  • CSS：cross-origin-storage()<request-url-modifier>， 可与integrity()配合使用，并已向 CSS 工作组提议，见 w3c/csswg-drafts#14056。

  • Fetch：crossOriginStorageRequestInit 选项，可与 integrity [FETCH]配合使用，并已向 WHATWG 提议，见 whatwg/fetch#1954。 这一形式没有宿主定义的目标，因此，对于从COS 注册表提供的Response如何报告其 MIME 类型、状态和其他元数据， 是该规范尚未解决的问题；COS 条目仅存储字节。

以下仅用于说明：同一个全局共享资源通过以下四种形式选择加入跨源存储：

<script src="popular-library.js" integrity="sha256-abc123..." crossoriginstorage="*"></script>

import data from "popular-resource.ext" with {
  integrity: "sha256-abc123...",
  crossOriginStorage: "*",
};

@font-face {
  font-family: "Popular Font";
  src: url("popular-font.woff2" integrity("sha256-abc123...") cross-origin-storage(*));
}

const response = await fetch("popular-resource.ext", {
  integrity: "sha256-abc123...",
  crossOriginStorage: "*",
});

这些代码片段仅用于说明。本规范不定义其中任何语法。每种形式的权威语法，包括受限 origins 列表的书写方式，都属于其自身的宿主规范。这些书写形式有意不同：RequestInit成员可以接受sequence<DOMString>，与 origins完全匹配，而属性值、导入属性值和 CSS 修饰符参数只能携带文本。

预计四种形式都会共享以下处理模型：首先查询COS 注册表，查找匹配且可披露的条目；如果没有找到，再回退到网络获取；并且将成功获取且通过完整性验证的资源存储到COS 注册表中，以供其他 origin 复用，其行为与requestFileHandle()完全相同。存储步骤是将获取的资源存储到跨源存储，每种集成都使用获取的响应运行该步骤。因此，受限 origins 值会受到该资源响应中的 Cross-Origin-Storage-Allow-Origin标头限制，该标头由提供字节的服务器发送（见§ 7 Cross-Origin-Storage-Allow-Origin 标头）。这些集成的讨论应当放在将承载它们的宿主规范的跟踪器中，而不是本仓库的议题跟踪器中。

IDL 索引

[Exposed=(Window,Worker), SecureContext]
interface CrossOriginStorageManager {
  Promise<FileSystemFileHandle> requestFileHandle(
      CrossOriginStorageRequestFileHandleHash hash,
      optional CrossOriginStorageRequestFileHandleOptions options = {});
};

dictionary CrossOriginStorageRequestFileHandleHash {
  required DOMString value;
  required DOMString algorithm;
};

dictionary CrossOriginStorageRequestFileHandleOptions {
  boolean create = false;
  (DOMString or sequence<DOMString>) origins;
};

interface mixin NavigatorCrossOriginStorage {
  [SameObject, SecureContext] readonly attribute CrossOriginStorageManager crossOriginStorage;
};
Navigator includes NavigatorCrossOriginStorage;
WorkerNavigator includes NavigatorCrossOriginStorage;

公共哈希列表的检索协议、更新频率、数据格式、流行度阈值以及治理机制，作为本规范的配套产物进行了详细设计，其理念类似于公共后缀列表——即作为 [URL] Standard 的配套数据文件；参见此仓库中的 Public Hash List 说明文档。 该设计提议由 WHATWG 进行治理，参考公共后缀列表跨厂商、滚动发布的先例，并以独立验证的普遍性作为准入标准。 这是上述 k-匿名风格门槛的一个具体实例，该门槛只在哈希被纳入列表时离线应用一次，因此用户代理不会在每次查询时重复执行。 这些内容目前尚未在此提案之外建立。该列表自身的早期非规范性代码原型目前位于此仓库中的 public-hash-list/implementation/； 专用的跨厂商仓库仍然是 PHL 说明文档中描述的治理目标。 本规范仅依赖于某个哈希是否 位于 PHL 上， 因此无论该列表的检索机制、治理模型或其余设计如何演进，本规范都保持正确。 ↵
