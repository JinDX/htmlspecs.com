摘要

本文档定义了 SHACL 配置文件化.

SHACL，即形状约束语言，是一种用于描述 RDF 图结构的语言。 SHACL 可用于多种用途，例如验证、推理、 领域建模、生成本体以告知其他代理、构建用户 界面、生成代码，以及集成数据。

SHACL 配置文件化定义了 SHACL 形状约束语言中的元素，用于描述 SHACL 的配置文件以及使用 SHACL 进行配置文件化。本文档的范围仅限于 RDF 图的配置文件化，包括包含 SHACL 形状的图。

本规范由 数据形状工作组发布。

1.1 什么是 SHACL 配置文件化？

根据定义，SHACL 对 RDF 数据施加约束，因此，任何根据某个 形状图 有效的数据，都将是该 数据图的一个配置文件。如果某个 形状图 验证了 数据图的所有元素，则得到的有效数据将是该 数据图的“空”配置文件，这意味着它与原始数据 图相同。

配置文件词汇表 将 配置文件 定义为：

一种标准，对其他标准的使用施加约束、进行扩展或组合，或提供指导或解释

如果一个 形状图 被视为“标准”，那么不仅根据该 形状图 有效的数据是 被验证的 数据图的配置文件，而且 该 形状图 本身也充当以下对象所用数据模型的配置文件： 数据图.

本文档说明如何打包 SHACL 信息以便最佳地进行配置文件化，并以为各个下述规范创建的 RDF 数据的打包为例： SHACL 规范.

上述用例的指导由以下建议提供，这些建议建立在成熟的 W3C 实践之上，相关实践来自 RDF Schema 1.1, OWL 2 Web 本体语言文档概览（第二版） 和 PROV-O：PROV 本体 规范：

以下各小节详细说明这些建议。

2.3 标识 SHACL 元素

以下类的实例： sh:ShapesGraph SHOULD 用于对以下实例进行分组： SHACL 元素 （用于验证的元素）.

SHACL 元素与许多其他 RDF 定义性数据一样，过去 通常被分组在 OWL 2 Web 本体语言基于 RDF 的语义（第二版）的 owl:Ontology 类实例中。

例如， 开放地理空间联盟的 GeoSPARQL 1.1 空间 RDF 数据标准 提供了一个 SHACL 验证器 ， 其中在一个 Turtle 文件内包含 27 个 sh:NodeShape 实例以及数量相近的 sh:PropertyShape 实例。该文件还包含一个 owl:Ontology 实例，用于呈现该 验证资源的元数据，例如其 修改日期、使用许可证等等。

本建议取代该实践，并建议使用 sh:ShapesGraph，这是一个专门的类，定义于 SHACL 1.2 核心 ，专门用于分组 SHACL 元素，应改用此类。

对于混合的 SHACL 和 OWL 元素，例如 NodeShape 和类定义， owl:Ontology SHOULD 仍应继续使用。

2.4 指示元素定义

一个用于验证的 SHACL 元素 实例 SHOULD 指示定义它的 sh:ShapesGraph 实例，使用 rdfs:isDefinedBy 谓词.

将 SHACL 元素 放入用 owl:Ontology 实例标识的组中时，常见做法是将元素与本体实例一同放入 RDF 文件。这对数据交换而言是合理的，但当交换的文件存入 RDF 数据库时，容器实例与其定义的 SHACL 元素 之间的关联可能丢失。如果加载到 命名图中， 该关联可能会通过命名图保留下来，该命名图对本体和 SHACL 元素 进行分组，但这是一种非语义的 关联，即不能直接在图中看到的关联。

本建议要求以下元素的创建者： SHACL 元素 SHOULD 指示定义以下元素的组： SHACL 元素 。此类 RDF 断言的示例如下：

ex:sg-M a sh:ShapesGraph ; . ex:shape-1 a sh:NodeShape ; rdfs:isDefinedBy ex:sg-M ; .
[ { "@id": "http://example.com/ns#ont-M", "@type": [ "http://www.w3.org/ns/shacl#ShapesGraph" ] }, { "@id": "http://example.com/ns#shape-1", "@type": [ "http://www.w3.org/ns/shacl#NodeShape" ], "http://www.w3.org/2000/01/rdf-schema#isDefinedBy": [ { "@id": "http://example.com/ns#ont-M" } ] } ]
注

在 2.5 形状与类的语法变体 的 SHACL 1.2 核心中有一项警告：虽然 属性形状 可以声明为 空白节点，但最好将它们声明为 IRI ，因为 这能在图之间实现更好的复用。如果按本节加入有关 形状的信息，则 SHOULD 使用 IRI。

2.5 指示元素使用

一个 sh:ShapesGraph 实例若使用某个 SHACL 元素 进行验证，但未定义该元素，则 SHOULD 将该 SHACL 元素 指示为成员，使用 rdfs:member 谓词.

当一个 SHACL 元素 在某个元素组内被使用但并非由该组 定义时， SHOULD NOT 将其指示为由该组定义，因此上一节中的建议并不适用。在其他组中复用 SHACL 元素 ，即在并未定义它们的组中复用，是关联数据原则所预期并鼓励的 [LDP].

以下示例展示了如何使用 rdfs:member 谓词来指示某个 SHACL 元素 被包含在一个 并不定义它的组中，同时也展示了如上例所示的 rdfs:isDefinedBy的使用：

2.6 指示组依赖

sh:ShapesGraph 实例若用于对 SHACL 元素 （用于验证）进行分组，则 SHOULD 指示对其他 SHACL 元素 组的依赖；这些组通过 sh:ShapesGraph 实例标识，依赖关系使用 owl:imports 谓词.

在 SHACL 验证工具中，导入 SHACL 元素 ，即通过以下指令将其从一个集合（例如包含 RDF 数据的文件）导入另一个集合，已是成熟实践： owl:imports 。许多 SHACL 验证引擎都这样做，例如 pySHACL [PYSH]，本规范建议用此做法表示从一个集合或分组到另一个的依赖，即使预计该断言不会触发任何特定验证引擎操作：它也很可能为 SHACL 数据管理提供有用信息。

以下给出 owl:imports 的示例。

# 'Shapes Graph N' imports 'Shapes Graph M' ex:sg-M a sh:ShapesGraph ; . ex:sg-N a sh:ShapesGraph ; owl:imports ex:sg-M ; .

# 'Shapes Graph N' imports 'Version 4.2 of Shapes Graph M' ex:sg-M a sh:ShapesGraph ; owl:versionIRI ex:sg-M-4.2 ; . ex:sg-N a sh:ShapesGraph ; owl:imports ex:sg-M-4.2 ; .

FILTER (?sg1 != ?sg2) # exclude self-dependencies } # dependency through importing # rule linking means un-versioned importing only runs if versioned importing does not RULE { ?sg1 dcterms:requires ?sg2 . } WHERE { ?sg1 owl:imports ?sg2 . 根据此公理、本文给出的以下概念的定义： conformsToShapesGraph 以及下节中的建模： 持久保存验证结果，可以推导出另一条推理规则，它在下面的词汇表中定义： 符合标准.

提出此规则，是为了将声明为根据某个 形状图 有效的数据，理解为符合该形状图所依据的标准。此规则对于使用 SHACL 创建空配置文件很重要，见 4.2.4 创建空配置文件.

议题 1419：确保至少在一个空配置文件声明中使用“符合标准”规则 配置文件化
 

4.2.3 配置文件层级

如果必须测试数据是否符合以 SHACL 定义的配置文件，以及该配置文件所依据的标准，而这些标准本身也以 SHACL 定义，或提供角色为 验证 且用 SHACL 创建的资源，则可以创建一个 形状图 ，它是该配置文件与这些标准或其验证器的组合。

这在复杂的配置文件化情形中预计很重要，例如对多个标准进行配置文件化，或创建其他配置文件的配置文件；从标准和配置文件自动组合这些 形状图，可能远比手工组合更合适。

4.2.4 创建空配置文件

SHACL 出现之前，没有标准化方式来表达封闭世界 RDF 数据模型或 RDF 模型的验证器。现在有了 SHACL，我们可以为标准创建一个 空配置文件 ，以便为使用如下建模系统创建的标准补充验证机制： OWL 2 Web 本体语言文档概览（第二版）.

按照 配置文件词汇表 和 4.1 引言、 空配置文件 不对原标准施加额外规则，并尝试实现该标准的全部规则。

尽管可以使用 SHACL 以外的建模或规则系统创建标准的空配置文件，这里只关注 SHACL 的使用。

议题 1420：完成对“空配置文件”一节的审阅 配置文件化
 

使用 SHACL 创建标准的空配置文件，主要目的是通过 SHACL 验证来测试对该标准的符合性。之所以存在这一目的，是因为许多 RDF 数据模型具有模型标准，可能是 OWL 模型，也可能只是描述模型的自然语言文档，但没有提供 SHACL 验证器这样的数据验证机制。这类模型的例子包括： 数据目录词汇表（DCAT）——第 3 版, Schema.org, RDF 数据立方体词汇表，以及许多 W3C 标准。

注

一个用于 RDF 数据、充当空配置文件的非 SHACL 验证器示例，是 W3C的 PROV 数据模型的约束 ，它提供一组约束，适用于按照下述规范表示的来源数据： PROV-O：PROV 本体. PROV 数据模型的约束 并未实现超出 PROV-O：PROV 本体 和概念性 PROV-DM：PROV 数据模型中所述或所暗示的约束之外的 任何约束；不过 它确实包含针对模型没有明确建模但 正确使用时需要的事项的测试，例如时间实体的排序。那些 约束的实现 已经制作出来 ，形式为执行 SPARQL 查询的 Python 脚本，从而允许对 RDF 数据进行验证。

无法为标准的空配置文件创建过程提供通用且精确的方法，因为从任务本身的性质来看，标准规则的定义可能不精确，所以用精确的 SHACL 来刻画这些规则的方法，也会随不精确的规则定义而变化。

参见 B. 空配置文件示例 ，以查看其他标准的空配置文件示例。

5.7 规则：符合形状图

“符合形状图”规则是一条推理规则，允许一个 数据图 被指示为符合一个 形状图 ，条件是存在一个验证报告（ Validation Report ），该报告对应的验证使用了该 数据图 和 形状图 ，且该报告的 sh:conforms 属性指示 true。

由于需要测试 sh:conforms 属性值，因此这条推理规则不能表述为 OWL 属性链公理。这里将它同时表示为 SPARQL 1.2 查询语言 规则和 SPARQL 1.2 RL 规则。

CONSTRUCT { ?dg sh:conformsToShapesGraph ?sg } WHERE { ?va sh:usedDataGraph ?dg ; sh:usedShapesGraph ?sg ; prov:generated ?vr ; . ?vr sh:conforms true . }
RULE { ?dg sh:conformsToShapesGraph ?sg } WHERE { ?va sh:usedDataGraph ?dg ; sh:usedShapesGraph ?sg ; prov:generated ?vr ; . ?vr sh:conforms true . }

5.8 规则：符合标准

“符合标准”规则是一条推理规则，允许一个 数据图 被指示为符合一个 标准 ，如果该 数据图 符合一个 形状图 ，而后者是一个 配置文件 ，派生自该标准。这种推理允许对数据符合标准的配置文件及标准本身作出静态声明；对于必须知道其是否符合这些要求、但无法持续验证的数据，这将很有用。

这里将此推理规则同时表示为 SPARQL 1.2 查询语言 规则和 SPARQL 1.2 RL 规则。

A.2.3 禁止递归约束的配置文件

此配置文件确立了定义 SHACL 形状的结构验证规则，明确禁止编写递归约束。虽然 SHACL 核心规范允许结构递归，但也承认不同实现可能以不同方式求值递归定义。当处理器遇到循环数据图时，这种差异常常导致不确定的行为或无限验证循环。为确保所有符合要求的处理器都产生可预测且一致的验证结果，此配置文件定义了不允许的具体形状编写模式，例如自引用形状、相互依赖的形状以及递归树结构。

递归约束的定义

一个 SHACL 形状图 SG 符合非递归约束配置文件 当且仅当 其 形状引用图 （定义如下）是 无环的.

设 R(SG) 是一个有向图，其中：

  • 每个节点都是 SG 中的一个形状（任何属于以下类型的 RDF 节点： sh:Shape, sh:NodeShape，或 sh:PropertyShape，或者用于下述表示形状的位置）。
  • 在以下图中存在有向边 s → t： R(SG) ，当且仅当在 SG 中，形状 s 引用形状 t ，引用通过一个 SHACL 属性建立，该属性值直接标识一个形状，或标识一个包含形状引用的 RDF 列表。

为确定形状图是否符合此配置文件，实现 MUST 在构建形状引用图并检查其是否存在环时，将以下各属性和列表构造视为形状引用关系：

  • sh:node
  • sh:property （指向所引用属性形状的边）
  • sh:qualifiedValueShape
  • 以下各项的列表成员： sh:and, sh:or和 sh:xone
  • sh:not
  • sh:memberShape
  • sh:reifierShape
  • sh:someValue

如果形状图包含任何环 s → ⋯ → s，则违反此配置文件，包括：

  • 直接自引用 （形状引用自身），以及
  • 间接自引用 （形状引用另一个形状，后者最终又引用原形状）
  • 自引用否定 （形状否定自身）

C. 安全与隐私 考量

本节为非规范性内容。

与大多数基于 RDF 的技术一样，SHACL 处理器可能会操作由 各种来源组装而成的图。一些应用可能具有开放的“链接数据”（“LD”）架构，并动态 组装来自组织信任网络之外来源的 RDF 三元组。 由于 RDF 允许任何人添加关于任何资源的语句，三元组可能会修改形状定义或 数据图 中节点原本 预期的语义，从而导致误导性结果。 通过只使用受信任且已验证的 RDF 来源，并消除通过 owl:imports 和 sh:shapesGraph.

创建其他标准的配置文件时，创建者需要确保其约束不违反那些标准的规则。如果有约束违反标准，且无论出于疏忽还是有意，仅用配置文件的规则而非标准的规则检查数据有效性，就可能错误地判定数据有效。这可能导致意外的数据发布或使用，从而引入安全问题。
