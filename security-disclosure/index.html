摘要

本文档定义了如何报告 W3C 标准和 规范（技术报告）中疑似存在的安全漏洞，以便问题能够通过 适当的 W3C 流程进行分流、确认和解决。
它不适用于报告软件实现或 W3C 运营基础设施中的漏洞（见范围之外）。

1. 引言

1.1 概述

W3C 标准和规范可能包含设计 问题，从而给用户、实现者或 Web 平台带来安全风险。研究人员和更广泛社区提交的报告有助于 W3C 识别这些问题，并将其转交给 能够评估和解决这些问题的人员。

1.2 目的

本政策说明 W3C 如何接收、分类、转交 并协调有关其标准和规范中疑似漏洞的报告， 这些报告涉及 W3C 标准和规范。

2. 范围和适用

W3C是一个标准制定组织，发布描述Web技术和规范的技术报告，包括W3C推荐标准、说明和注册表。

本政策适用于 W3C 规范中所描述的设计漏洞或安全问题。

本政策不涵盖：

  • 实现、工具或配置漏洞存在于可能实现W3C标准的产品、开源项目或服务中。应向相应的供应商或维护者报告这些问题。
  • 支持 w3.org 域名的 W3C 基础设施和 服务中的漏洞。这些漏洞由 W3C Systems 负责，其拥有自己的漏洞披露政策。

3. 流程和政策

W3C的响应取决于发现问题的技术报告类型、问题的严重程度和响应的复杂性。W3C将努力解决已确认的安全问题，不作不必要的拖延。本政策参考了[ISO-IEC-29147]和[ISO-IEC-30111]。

W3C 根据所报告安全问题所在文档的类型和 成熟度来处理和转交报告。

3.1 报告 W3C 标准中的漏洞

如果你认为在 W3C 文档中发现了漏洞，请联系 vulnerability-disclosure@w3.org 以进行 协调 披露。

此电子邮件地址作为 W3C 团队进行初步分类的联系点。完成分类后，W3C 团队 将根据报告和受影响的规范让适当的小组参与处理。通常 包括 团队联系人、主席和编辑，并且在需要其他人员提供意见时也可能包括他们。

发往此地址的报告不会被公开归档。如果 W3C 已为报告邮箱公布 PGP 公钥，建议用它加密报告。

为便于处理，你的通报应包含[ISO-IEC-29147]和[NIST-SP-800-216]所建议的资料，例如：

  • 存在漏洞的具体文档（例如，其标题、 稳定 URL 和 发布日期）。
  • 对漏洞类型的简要描述（例如，使用不安全的 加密 算法）。
  • 漏洞的复现步骤，最好提供一个无害、非破坏性的概念 验证。
  • 利用此漏洞造成的影响，以及它如何被用于攻击 场景。
  • 建议的纠正或缓解措施（如有）。
  • 你的联系方式（可选；接收确认和状态更新需要可用的回复渠道，但报告者不必披露身份）。

请注意：

  • 无“漏洞赏金”： W3C 不会为报告的 漏洞支付“漏洞赏金”。
  • 保密：非公开漏洞信息通过受限渠道处理，仅在评估或协调报告所需的范围内共享。在保密协调期间，请报告者使用约定的受限渠道。协调员将告知参与方何时可转入适当的公开流程。
  • 研究人员保护：W3C无意仅因报告者依照本政策善意提交报告而对其采取法律行动。本政策不授权测试第三方控制的系统、服务或产品，也不授权违反适用法律的行为。

3.2 安全问题的接收 与确认（VD）

W3C力争在3个工作日内确认收到安全问题，并与报告者建立沟通渠道。W3C团队将指定负责该报告的协调员。

3.3 安全问题的 验证（VH）

确认收到后，将对该安全问题进行评估，以确定其有效性、技术 严重程度、 相关性和潜在影响。

W3C力争在15个工作日内向报告者提供初步评估。如果届时尚未完成评估，W3C将改为告知当前状态及下次复核日期。如果需要更多信息，W3C将请报告者补充细节。

W3C 团队负责跟踪这些响应 目标，并在需要更多时间、 协调或权限时升级处理该报告。

3.4 核实后的处理流程与报告者状态更新（VH/VD）

安全问题得到确认后，对于每份确认受影响且由W3C协调应对的文件，协调员将使用适当的受限协调渠道或跟踪机制，记录当前阶段、下次复核时间及当前负责应对的W3C小组或其他方。如果使用仓库安全公告，同一公告可兼作记录和非公开讨论渠道，无须另建记录。

不要求采用固定的状态模型。记录可描述应对规划或工作、多方协调、协调披露、后续跟进或结案。这些描述不是必须遵循的线性顺序，并可同时适用。

有可用的回复渠道时，协调员将告知报告者当前所处阶段、当前由谁协调响应、是否需要补充信息，以及下次复核日期或适合该个案的更新频率。在W3C仍负责协调期间，协调员会在这些时间点通过约定渠道提供状态更新。复核时间逐案确定，需考虑严重程度、复杂性及参与方数量。简单告知“无变化”即可，也可以通过现有的仓库安全公告发出，无须披露敏感的实现细节。

结案前，协调员将记录每份确认受影响且由W3C协调应对的文件的处理结果。结果可以是文件更新、安全公告或缓解措施、移交其他负责流程或协调员，或者注明理由后不作更改而结案。只要还有一份确认受影响且由W3C协调处理的文件未记录结果，仅完成最初被报告文件的工作并不能结案。这些要求确立的是复核和更新节点，而非统一的修复期限。

3.5 处理和 解决方案制定（VH）

协调员随后将与负责受影响文件的小组合作；如有可用的回复渠道，也会与报告者合作。大多数情况下，解决办法主要是更新相关文件。

在非公开协调期间，协调员将使用适当的受限渠道。披露之后，可转到负责的小组或其他方通常使用的公开议题或邮件列表流程开展后续工作。

3.5.1 W3C 推荐标准 - 已发布

这些是已经完成并经过社区审阅的标准。

  • 如果制定该推荐标准的工作组仍活跃，就把报告转交该工作组，以确定最合适的处理方式。漏洞可通过以下方式处理：

    • 发布勘误（针对轻微问题或不改变规范性内容的更正）。W3C工作组必须保留公开的错误记录，记载有关推荐标准的已报告错误。此类错误报告的汇编频率不应低于每季度一次。
    • 更新推荐标准文件（修订该推荐标准）。
    • 另行制定全新的文件处理该问题。

  • 如果工作组已关闭，可采用无工作组维护机制等W3C流程所规定的方式。可采用哪些措施取决于问题的严重程度：

    • 轻微问题可通过勘误处理（如未设小组，可由W3C团队维护）。
    • 对于较重大的更新，W3C团队可考虑其他方式。

根据 W3C 流程，第 3 类或第 4 类变更可能触发 更广泛的审查和专利政策影响。

3.5.2 候选推荐标准（CR）和工作草案（WD）- 制定中

这些是已被 W3C 工作组采纳、 但尚未最终确定的文档。

  • W3C工作组应及时正式回应有关技术报告的任何实质性审查意见。

3.5.3 编辑草案 - 早期阶段/个人贡献

这些不是 W3C 正式采用的文档。 尚未作为 W3C 规范发布的编辑草案不具有官方地位。

  • 该问题应由文档编辑处理并与其讨论。

3.5.4 已停止、过时或已撤销的文档

  • 已标记为 停止、过时或撤销的 W3C 技术报告，在收到安全问题报告后不太可能 对其采取措施。不过，团队 应评估是否在文档状态（SOTD）中将其列出。

3.5.5 社区小组报告

这些不是 W3C 中正式采纳的文档， 并且由社区和业务小组 流程规范 它们。

  • 发现的任何问题都应与文档编辑一起处理和讨论。

3.5.6 成员提交

这些不是 W3C 中正式采纳的文档。 成员提交是由成员提出以供考虑的文档。

  • 发现的任何问题都应与文档编辑一起处理和讨论。

该问题将根据该成员的政策处理。

3.6 发布和传播（VD）

协调员将与报告者和受影响方共同记录披露计划。如果计划公开披露，待获得足够信息后，计划将明确目标日期，并考虑问题的严重程度、可采取的缓解措施、受影响文件的成熟度以及是否需要多方协调。如果提早披露会显著增加风险，可以在上述复核节点修改计划。公开披露不要求所有相关文件或实现都更新完毕。

公开披露可包含漏洞说明、供用户识别受影响标准的信息、影响和严重程度，以及可帮助实现者和用户缓解或修复问题的信息。如果W3C发布公告，而报告者要求公开署名，通常会予以致谢。

已发布的仓库安全公告列在面向W3C小组仓库的公开安全公告索引中。
