摘要

本规范定义了一种将字体从服务器增量传输 到客户端的方法。客户端仅加载其实际需要的字体 部分，从而显著减少数据传输量。同一字体可以进行多次增量 补充，例如用户代理可以在用户 浏览多个页面时更新字体。与 unicode-range 相比，增量传输不会破坏布局（字距调整、连字等）规则， 因此可以高效支持对拉丁文字和 印度系文字或阿拉伯文字等复杂文字体系进行细粒度增量更新。

1. 引言

本节不具有规范性。

增量字体传输（IFT）是一种用于改善 Web 上远程字体（或“Web 字体”）加载延迟的技术。 如果没有这项技术，浏览器必须下载字体的全部字节，才能使用该字体渲染 任何字符。IFT 允许浏览器只下载文件中的部分字节， 从而 缩短从浏览器确定需要某种字体到 能够使用该字体渲染所需文本之间的感知延迟。与传统的字体子集化方法不同，增量 字体传输 保留了各部分之间布局规则的编码（渐进式字体增强：评估报告 § fail-subset）。

Web 字体的成功应用并不均衡。本规范使 Web 字体能够应用于 目前因网络速度缓慢、字体体积过大或子集化要求复杂而无法使用的场景。例如， 即使使用 WOFF 2 [WOFF2]，中日韩（CJK）语言的字体仍可能过大而难以实际使用。

1.1. 技术动机：评估报告

有关促成本规范制定的研究，请参阅《渐进式字体增强：评估报告》[PFE-report]。

1.2. 概述

增量字体是 一种经过重新格式化以包含增量功能的常规 OpenType 字体， 这部分得益于两个额外的表。利用 这些新表，可以通过加载和应用补丁来扩充字体， （例如，覆盖更多码点）。

IFT 技术主要由四个部分组成：

  • § 4 扩展字体子集：提供客户端用于 选择和应用补丁的算法。

  • § 5 字体格式扩展：定义包含 可应用于字体的补丁列表的新表。

  • § 6 字体补丁格式：定义两种不同类型的 可用补丁。一种是“通用”二进制补丁，另一种 专门针对字体存储字形数据所采用的格式。

  • § 7 编码：创建构成 增量字体的字体及其关联补丁。

概括而言，增量 字体的使用方式如下：

  1. 客户端下载一个初始字体文件，其中包含完整 字体版本中的部分初始数据子集，以及 描述可用于扩展该字体的嵌入数据，其中列出了 可用的补丁。

  2. 客户端根据需要渲染的内容选择、下载 并应用补丁，以扩展 字体，使其覆盖额外的字符、布局特性和/或变体空间。每当出现新 内容时，都会重复执行此步骤。

1.3. 创建增量字体

预计生成增量字体最常见的方法是转换现有字体， 使其使用本规范定义的增量 编码。概括而言，将现有字体转换为增量字体的过程 如下：

  1. 选择初始子集的内容，这些内容将包含在 客户端加载的初始字体文件中， 通常由预计始终需要的原始字体数据组成。

  2. 选择一种或多种补丁类型。不同补丁类型具有不同的特性，因此不同的使用 场景可能需要不同的 补丁类型，某些情况下也可能需要混合使用两种类型。

  3. 选择字体的分段方式。客户端将通过补丁把各个分段 添加到基础子集中。选择 合适的分段方式是生成高效编码最重要的环节之一。

  4. 根据这些选择生成一组补丁，每个补丁都添加特定 分段的数据，且以 初始字体文件或先前的补丁为基础。

  5. 生成包含初始子集和补丁映射的初始字体文件。该映射 列出所有可用的补丁文件、它们所在的 URL，以及 补丁将向字体添加哪些数据的信息。

注：以上只是对 创建增量字体过程的高度简化描述。有关生成编码的更深入讨论及 编码要求，请参阅§ 7 编码。

1.4. 性能考虑因素与增量字体传输的使用

增量传输并非总能带来好处，这取决于字体、 网络以及正在渲染的内容的特性。本节提供非规范性指导，帮助确定 何时应使用增量传输。

增量字体通常会触发多个补丁的并行加载。因此，为了最大限度地提高 性能，在 提供增量字体时，建议使用支持多路复用的 HTTP 服务器（例如 [rfc9113] 或 [rfc9114]）。

与加载整个字体相比，增量加载字体存在根本性的性能权衡。 简单来说，增量传输可以减少传输的字节数，但代价可能是 增加网络请求总数和/或增加请求处理 延迟。一般而言，当减少传输字节数所带来的延迟降低 超过增量传输方法引入的额外延迟时，增量字体传输才会带来好处。

首先需要考虑的因素是待渲染内容所使用的语言。评估报告 包含对三类语言模拟增量字体传输的结果 （渐进式字体增强：评估报告 § langtype）。有关不同语言类别下增量字体传输 预期性能的讨论，请参阅其结论部分渐进式字体增强：评估报告 § conclusions。

接下来，需要考虑预计会使用多少字体数据。如果预计渲染内容时 需要字体的大部分数据，那么增量字体传输不太可能带来好处。但在许多情况下， 预计只需要字体的一部分。例如：

  • 如果字体支持多种语言，但预计用户只会渲染 其中部分语言的内容。

  • 如果待渲染内容仅使用字体所含全部字符中的一小部分。这种情况 在中文、日文、韩文、表情符号和图标字体中很常见。

  • 只需要渲染少量文本。例如，仅用于 标题的字体。

增量传输的一种替代方法是将字体拆分成不同的子集（通常按文字体系划分）， 并使用 @font-face 的 unicode-range 特性仅加载所需的子集。但是，如果不同 子集中的字符之间存在布局规则，这可能会改变部分内容的渲染结果渐进式字体 增强：评估报告 § fail-subset。增量字体传输不会遇到这个问题，因为它能够包含 原始字体及其所有布局规则。

1.4.1. 减少网络请求数量

如上一节所述，与传统字体加载相比，增量字体传输的最基本实现 往往会增加请求总数。由于每次扩充 通常至少需要一次往返时间，因此如果发出过多 请求， 性能可能受到负面影响。根据可用的补丁类型以及 补丁映射提供的信息量，客户端可能会提前请求 当前尚不需要、 但预计将来会需要的码点所对应的补丁。实现中合理利用这一 功能有助于减少请求总数。评估报告通过测试一种基于基本字符频率的 码点预测 方案的性能对此进行了研究，并发现该方案改善了整体性能。

2. 选择启用机制

网页可以在 ''@font-face'' 块中使用 CSS 字体技术 关键字（CSS Fonts 4 § 11.1 字体技术），选择启用字体增量传输。 关键字 incremental 用于表明引用的字体包含 IFT 数据，并且 只有支持增量字体传输的用户代理才应加载该字体。 

@font-face {
    font-family: "MyCoolWebFont";
    src: url("MyCoolWebFont-Incremental.otf") tech(incremental);
}

@font-face {
    font-family: "MyCoolWebFont";
    src: url("MyCoolWebFont-Incremental.otf") tech(incremental);
    unicode-range: U+0000-00FF;
}

如第二个示例所示，unicode-range 可以与 IFT 字体结合使用。 Unicode 范围应设置为与完全扩展后的字体的覆盖范围相匹配。这使客户端 能够避免在字体不支持任何所需码点时 尝试加载 IFT 字体。

另一种方法是使用 CSS supports 机制，该机制可以根据 字体技术进行选择：

@when font-tech(incremental) {
  @font-face {
    font-family: "MyCoolWebFont";
    src: url("MyCoolWebFont-Incremental.otf");
  }
}
@else {
  @font-face {
    font-family: "MyCoolWebFont";
    src: url("MyCoolWebFont.otf");
  }
}

注：每个独立的 @font-face 块都可以 选择启用或不启用 IFT。这是因为 网页使用字体的方式多种多样。作者可以控制哪些字体使用 这项技术，哪些字体不使用。

注：IFT 技术关键字可以与 其他字体技术说明符结合使用，以进行 字体特性选择。例如，一个 @font-face 可以包含两个 URL，其中一个带有 tech(incremental, color-COLRv1)，另一个带有 tech(incremental, color-COLRv0)。

2.1. 离线使用

在某些情况下，用户代理可能希望保存网页以供离线使用。保存的页面可能在 没有网络连接时被查看， 因此无法请求增量字体引用的任何额外补丁。由于 内容发生变化（例如，由 JavaScript 执行引起）时将无法扩展 增量字体，因此页面保存机制应 通过调用 完全扩展字体子集来完全扩展增量字体，并将 对增量字体的引用替换为对完全扩展后的字体的引用。

3. 定义

3.1. 字体子集

字体子集是字体文件的修改 版本 [iso14496-22]， 其中只包含渲染以下内容的某个子集 所需的数据：

  • 码点，

  • 布局 特性，

  • 以及设计变体 空间。

这些内容均由原始字体支持。当使用正确构建的字体子集渲染文本时，只要使用 子集码点、布局 特性或设计变体 空间 的任意组合，其渲染结果就与原始字体完全相同。这也包括使用 渲染器可能选择从原始字体使用的任何可选 排版特性（如微调指令）进行渲染。设计 变体空间 使用用户轴刻度指定（OpenType 规范 § otvaroverview#coordinate-scales-and-normalization）。

字体子集 定义描述字体 子集所支持的最小数据范围（码点、布局特性、 变体轴空间）。

注：为方便起见，本文档其余部分 链接到 [open-type] 规范，该规范是 [iso14496-22] 的副本。

3.2. 字体补丁

字体补丁是一种文件， 用于编码要对经过 IFT 编码的字体进行的更改。补丁用于扩展 现有的字体子集， 以扩大其覆盖范围。

补丁格式是一种 指定的编码方式，用于表示相对于字体子集所应用的更改。按照该格式编码的一组 更改称为字体补丁。每种补丁格式都有一个关联的 补丁 应用算法，该算法以 字体子集和按照该补丁格式编码的字体补丁作为输入， 并输出扩展后的 字体子集。

3.3. 补丁映射

补丁映射是一个OpenType 表，其中编码了一组 从字体子集定义到托管补丁的 URL 的映射，这些补丁用于 扩展增量 字体。补丁映射表编码了 一组补丁映射 条目，其中每个 条目都具有键和值。条目的键定义其覆盖范围，即有关 哪些子集 定义与其匹配的信息。值指定在 条目 匹配时应应用哪些补丁的信息。补丁映射 条目概述：

键 值

  • 字体子集定义：定义 基础覆盖范围。

  • 对零个或多个子补丁映射条目的引用：
    这些子条目用于扩展覆盖范围。

  • 子条目匹配模式，可以是合取或析取。

  • 一个或多个补丁URL字符串

  • 补丁格式

  • 兼容性 ID

有关补丁映射格式的更多详细信息，请参阅§ 5 字体格式 扩展。

3.4. 数据类型说明

本规范其余部分的编码数据结构使用 OpenType 规范 § otff#data-types 中定义的数据类型进行描述。与 OpenType 的其余部分一样，所有字段都使用“大端” 字节序。

4. 扩展字体子集

本节定义客户端用于扩展增量字体子集的算法，使其覆盖额外的 码点、布局特性和/或设计空间。这是一个迭代算法，会反复：

  • 将字体子集的补丁映射解析为可用补丁列表。

  • 检查是否有可用补丁与待渲染内容匹配。

  • 选择一个可用补丁，加载并应用它。

此过程会重复执行，直到不再存在相关补丁。由于应用补丁可能会改变 嵌入字体文件中的补丁 映射，因此每次迭代都会重新解析当前版本字体子集中的补丁映射， 以确定还剩余哪些补丁。 因此，在每次迭代中，字体子集都是有关可用补丁的权威信息来源，并且 完整封装了扩充过程的当前 状态。

4.1. 补丁失效

嵌入字体子集中的补丁映射为每个补丁编码了一种失效模式。补丁的 失效模式 标识应用该补丁后哪些其他补丁将不再有效。扩展 算法使用这种失效 模式来确定哪些补丁彼此兼容，并影响选择顺序。补丁 应用过程中的有效性 由§ 5.3 补丁映射 表中的兼容性 ID 强制保证。每个补丁内部都编码有一个兼容性 ID， 该 ID 必须与列出此补丁的§ 5.3 补丁映射表 中的兼容性 ID 相匹配。

失效模式共有三种：

  • 完全 失效：应用此补丁时，当前列在字体子集中的所有其他补丁都会 失效。 'IFT ' 和 'IFTX' 两个§ 5.3 补丁映射 表中的兼容性 ID 都将改变。

  • 部分 失效：应用此补丁时，同一个§ 5.3 补丁映射表中的所有其他补丁都将失效。 只有包含 此补丁的§ 5.3 补丁映射表的兼容性 ID 会改变。

  • 不 失效：应用此补丁不会使任何其他补丁失效。 'IFT ' 和 'IFTX' § 5.3 补丁映射表的兼容性 ID 不会改变。

特定补丁的失效模式编码在其格式编号中，详见§ 6.1 格式概述。

4.2. 默认布局特性

大多数文本塑形器都有一组布局特性， 这些特性始终处于启用状态，因此在 增量加载的字体中始终是必需的。附录 A：默认特性标签汇总了 在编写本文档时已知常见塑形器实现默认需要的 特性列表。在构建作为扩展算法输入的字体子集定义时，客户端 通常应将附录 A：默认特性 标签中的所有特性包含在子集定义中。不过，在某些情况下，客户端可能 知道将使用的特定塑形器不会使用附录 A：默认特性标签中的某些特性，因此可以 选择从子集定义中排除这些未使用的特性。

4.3. 增量 字体扩展算法

客户端使用以下算法扩展增量字体子集，使其覆盖额外的 码点、布局特性和/或设计空间。该算法逐个选择并应用补丁， 根据需要加载 它们。作为减少网络往返次数的一项重要优化，它允许提前启动 所有最终 需要的补丁的加载。这些补丁分为两种情况：

  • 首先，补丁映射条目 可以列出多个 URL 字符串，其中第一个之后的每个 URL 字符串也应加载， 因为后续迭代将需要它们。

  • 其次，使用§ 4.1 补丁失效来确定 可以为哪些补丁启动加载。任何与目标子集 定义匹配，且不会被根据§ 4.1 补丁失效规定即将应用的下一个补丁 使之失效的补丁，都可以预期会在后续迭代中 被需要。

扩展增量字体子集

此算法的输入为：

  • font subset：一个增量字体子集。

  • initial font URL：一个URL， 用于标识 font subset 所来源的初始增量字体的位置。

  • target subset definition：客户端希望扩展 font subset 以覆盖的字体子集定义。

此算法的输出为：

  • extended font subset：font subset 的扩展版本。它可能是，也可能不是 增量 字体。

算法步骤：

  1. 将 extended font subset 设为 font subset。

  2. 从 extended font subset 加载 'IFT ' 和 'IFTX'（如果存在）映射表。 这两个表都采用 § 5.3 补丁映射表的格式。检查它们是否 符合§ 5.3 补丁映射表中的要求。如果 任一表无效，则调用处理 错误。如果 extended font subset 不包含 'IFT ' 表，则它 不是增量 字体，无法扩展，返回 extended font subset。

  3. 如果 'IFT ' 中的兼容性 ID 等于 'IFTX' 中的兼容性 ID，则属于错误，调用 处理错误。

  4. 对于 'IFT ' 和 'IFTX'（如果存在）中的每个表： 通过调用解释补丁映射，将该表转换为条目列表。将 返回的条目列表连接为一个列表， entry list。

  5. 对于 entry list 中的每个 entry，以 entry 和 target subset definition 为输入，调用检查条目交集。 如果返回 false，则从 entry list 中移除 entry。此外，还应移除 entry list 中补丁 URL 字符串所指向的补丁已在本算法的先前执行过程中 加载并应用过的所有条目。

  6. 如果 entry list 为空，则扩展操作完成，返回 extended font subset。

  7. 根据各条目补丁格式的失效模式，将 entry list 中的条目分为三个列表： full invalidation entry list、partial invalidation entry list 和 no invalidation entry list。

  8. 按照以下过程选取一个 entry：

    • 如果 full invalidation entry list 不为空，则从 其中恰好选择一个条目。按照 § 4.4 选择使补丁失效的补丁中的准则 选择该条目。

    • 否则，如果 partial invalidation entry list 不为空，则从 其中恰好选择一个条目。 按照§ 4.4 选择使补丁失效的 补丁中的准则选择该条目。

    • 否则，选择 no invalidation entry list 中在 补丁映射中最先列出的条目（即 entries 数组中最先出现的条目）。如果 IFT 和 IFTX 两个表中的条目都是候选条目，则认为 IFT 中的所有条目都排在 IFTX 中的条目之前。

  9. 通过调用加载补丁文件启动 patch file 的加载（如果之前尚未启动）， 其中将 initial font URL 作为初始字体 URL，将 entry 中的第一个补丁 URL 字符串作为补丁 URL 字符串。 如果 entry 中还有其他 URL 字符串， 则使用相同的过程启动对它们的加载。它们可能在 本算法后续迭代中使用。 此外，客户端还可以选择使用相同的过程，启动加载 entry list 中任何不会被 entry 使之失效的条目。客户端在本算法的一次执行过程中 能够加载和应用的补丁总数受到以下限制：

    • 最多 100 个属于部分失效或完全失效类型的补丁。

    • 任何类型的补丁总数最多为 2000 个。

    这些补丁可以在本算法的一次调用过程中加载并应用。如果任一数量 超过限制，则属于错误，调用 处理错误。

  10. 当 patch file 加载完成后，使用§ 6 字体补丁格式中 与 entry 中补丁格式相匹配的适当应用 算法， 以 entry 中的补丁 URL 字符串和兼容性 ID 为依据，将 patch file 应用于 extended font subset。如果 patch file 的加载 发生错误，则按照 处理错误进行处理。

  11. 转至步骤 2。

注：在步骤 9 中，客户端可以选择并行启动加载 不会被当前所选 条目使之失效的补丁。此类补丁几乎总会在后续迭代中需要（因为它们不会 失效），因此并行加载 可以消除网络往返，从而显著提高性能。以这种方式启动加载时， 请求启动的顺序 必须遵循步骤 8 中指定的顺序。

注：如果剩余的相交条目全部都是 不使其他补丁失效的条目，那么在后续迭代中无需重复执行步骤 5 的 相交检查（这是因为不使其他补丁失效的补丁在应用后不会改变 可用补丁 列表，除了移除其自身的条目）。此外，作为一项优化， 客户端可能 希望将剩余相交且不使其他补丁失效的条目的补丁应用操作作为单个批次 执行。由于按字形索引的补丁具有自身特性，可以直接在一次遍历中构造 依次应用 多个补丁的最终结果。这样可避免为每个单独的补丁反复重新合成 glyf/loca/CFF/CFF2 表，从而显著减少所需的计算 总量。

处理 错误

如果扩展字体子集的过程因错误而失败，则字体中的部分数据可能 尚未完全加载， 因此渲染依赖这些缺失数据的内容可能产生错误的渲染结果。客户端 可以选择继续使用 该字体，但应仅将其用于渲染根据 § 4.6 确定字体可以渲染哪些内容已完全加载的码点、特性和设计空间。 所有其他内容的渲染都应按照客户端的正常回退逻辑回退到其他字体。

如果错误发生在加载补丁文件过程中，则客户端可以继续尝试 扩展字体子集。在 扩展增量字体子集的步骤 8 中， 在每个失效分组内，任何加载失败的补丁都将被排除在候选范围之外。 如果某个失效分组不为空且需要从中选择补丁，但其中只包含加载失败的补丁， 则扩展已经失败，无法 继续。

对于所有其他错误，客户端 不得尝试进一步扩展字体子集。

4.4. 选择使补丁失效的补丁

在执行扩展增量字体子集 算法期间，某些情况下需要从候选条目列表中选择一个使其他补丁失效（完全失效或部分失效）的 补丁条目。所使用的选择准则会直接影响完成 扩展所需的网络往返总次数。由于网络往返代价较高，为获得最佳性能，应以 尽量减少所需网络 往返总次数的方式选择补丁。

以下选择准则 可最大限度地减少网络往返次数，客户端在 扩展增量字体 子集的步骤 8 中选择单个部分失效或完全失效补丁时必须使用这些准则：

  1. 如果一个或多个候选条目关联的补丁文件此前已由 扩展增量字体 子集的步骤 9 加载， 则在以下步骤中仅考虑补丁文件已经加载或 当前正在加载的候选条目。否则，考虑所有 候选条目。

  2. 对于每个候选条目：通过对该条目的子集 定义以及通过所引用子条目构成的图可到达的所有子条目的子集定义取并集，计算总体子集定义。

  3. 对于每个候选条目：计算总体子集定义与 目标子集定义的集合交集。

  4. 找到一个条目，使其在步骤 2 中计算得到的交集不是任何其他交集的真子集。

  5. 找出位于同一补丁映射中、且与步骤 3 找到的条目具有相同交集的所有其他条目。从这组 条目（包括步骤 3 选出的条目）中，最终选择在补丁映射中最先列出的条目（即 entries 数组中最先出现的条目）。

注：找到满足步骤 3 准则的条目的一种快速高效的方法是： 先按码点集合交集的大小降序排列条目，再按特性标签集合交集的大小排序，最后按设计空间 交集的大小排序。排序后的第一个条目 保证不会是任何其他条目的真子集，因为任何真超集都必须至少 多包含一个元素。这种方法还具有 额外的好处，即它会选择能够添加最多客户端当前 请求的数据的补丁。

4.5. 目标子集定义

扩展增量字体子集 算法接收一个目标子集定义作为输入，该定义基于客户端 希望渲染的某些内容。客户端可以选择为整个内容构建一个统一的子集定义，并 运行一次扩展算法。 或者，客户端也可以将内容拆分为更小的文本片段，为每个片段构建一个子集 定义，并针对每个较小的子集定义 运行扩展算法。只要满足以下条件，两种方法最终都会生成 能够以相同方式 渲染全部内容的字体：

  • 用于生成子集定义的每个文本片段都只由一个或多个完整的塑形单元组成。

  • 其中，塑形单元 是客户端在塑形过程中作为单个单元 一起处理的文本片段。

4.6. 确定字体可以渲染哪些内容

对于某个增量字体（无论是初始字体还是已经部分扩展的字体），客户端可能 希望了解该字体在 当前状态下能够渲染哪些内容。当客户端需要确定 文本的哪些部分 应使用回退字体时，这一点尤为重要。

在回退处理过程中，客户端通常会检查字体的cmap 表，以确定 支持哪些码点；然而，在 IFT 字体中，由于§ 6.3 按字形索引补丁的工作方式， cmap 表可能包含 某些码点的映射， 尽管这些码点对应的字形数据尚未加载。因此，客户端不应 仅依赖 cmap 表来确定码点 是否存在。客户端可以改用以下过程检查增量字体能够渲染 某些内容的哪些部分：

  • 将内容拆分为文本塑形过程中处理这些内容所依据的塑形单元（参见§ 4.5 目标子集定义）。

  • 对于每个塑形单元，执行以下两项检查：

    • 首先，如果塑形单元中的任何码点在cmap 中没有对应条目， 或者该条目映射到字形 0，则增量字体无法完整支持该塑形单元的渲染。

    • 其次，计算相应的字体子集定义，并执行扩展增量 字体子集算法， 在步骤 6 停止。如果条目列表不为空，则增量字体无法完整 支持该塑形单元的渲染。

  • 通过两项检查的任何塑形单元 都可以使用该字体完整渲染。

客户端也可能希望以比塑形单元更细的粒度了解字体能够渲染哪些内容。 以下伪代码 展示了一种可能的方法，可将未通过上述检查的塑形单元拆分为 能够使用 增量字体渲染的文本片段：

4.7. 完全扩展 字体

本节定义一种算法，可用于将增量字体转换为完全扩展的 非增量字体。此 过程会加载增量字体提供的所有可用数据，并生成一个 不再包含任何 待应用补丁的静态字体文件。

完全扩展字体子集

此算法的输入为：

  • font subset：一个增量字体子集。

此算法的输出为：

  • expanded font：一个非增量的 [open-type] 字体。

算法步骤：

  1. 以 font subset 调用扩展增量字体 子集。输入的目标子集定义是一个特殊定义， 它 在检查条目交集步骤中被视为与所有条目相交。将 得到的字体子集作为 expanded font 返回。

4.8. 缓存已扩展的增量字体

已经扩展的增量字体包含按照本节过程执行任何后续扩展 操作所需的全部状态。 因此，如果客户端需要存储或缓存增量字体以供将来使用， 只需 存储最近一次执行扩展算法所生成的字体二进制文件即可。无需保留初始 字体或先前扩展生成的任何版本。

5. 字体格式扩展

增量字体 遵循现有的 OpenType 格式，但包含两个新的 表， 分别由四字节标签 'IFT ' 和 'IFTX' 标识。这两个新表都是 补丁映射。所有增量字体 至少包含一个 'IFT ' 表。'IFTX' 表是可选的。当两个表 同时存在时，整个字体的映射是这两个表映射的并集。这两个新 表仅用于本 规范，不会被添加到 OpenType 规范中。

注：允许将映射拆分到两个 不同的表中，使增量字体能够更方便地使用多种 补丁类型。例如，可以在 'IFT ' 表中指定一种类型的所有补丁，并在 'IFTX' 表中指定第二种类型的所有补丁。 这些补丁可以只更新其中一个映射表，从而避免产生相互冲突的 更新。

5.1. 增量字体传输与字体压缩格式

在 Web 上使用字体时，通常会采用 [WOFF] 或 [WOFF2] 等压缩格式对其进行压缩。只要 满足以下条件，就可以使用这些格式压缩增量字体传输编码所使用的初始字体文件：

  1. 通过压缩格式对字体进行编码和解码的过程不会修改每个表 的字节。

  2. 由于增量字体传输扩展算法（§ 4 扩展字体子集）专门针对未压缩的字体 文件执行操作，因此在尝试扩展压缩字体之前，需要先对其解码。

对于 [WOFF2]，需要特别 注意。如果增量字体将使用 WOFF2 编码后进行传输：

  1. 如果 WOFF2 编码将包含经过转换的 glyf 和 loca 表（WOFF 2.0 § 5.1 转换后的 glyf 表格式），那么增量 字体不应包含修改 glyf 或 loca 表的§ 6.2 按表索引补丁。WOFF2 格式 不保证解码经过转换的 glyf 和 loca 表后所得的具体字节。§ 6.3 按字形索引补丁可以 与经过转换的 glyf 和 loca 表结合使用。

  2. WOFF2 编码器可以按照 WOFF 2.0 § 5 压缩数据 格式中定义的标准过程，处理 'IFT ' 和 'IFTX' 表并使用 Brotli 对其进行编码。

注：鉴于即使禁用 glyf/loca 转换，WOFF2 的压缩效果仍优于 WOFF， 通常建议 使用 WOFF2 压缩 IFT 字体；当编码使用按表索引的补丁更新 这些表时，应禁用 glyf/loca 转换。

5.2. CFF 和 CFF2 增量字体

对于字形轮廓存储在CFF 或 CFF2 表中的增量字体，还存在一些 额外限制：

  • 增量字体中的 CFF 和 CFF2 表 必须将 CharStrings INDEX 数据结构置于 表的最后（其后只能有用于填充至四字节字边界的 0）。

  • 增量字体中的 CFF 和 CFF2 表 不得包含与 CharStrings INDEX 数据 结构重叠的任何其他数据元素。

  • 'IFT ' 补丁映射表必须 包含一个偏移量 （cffCharStringsOffset 或 cff2CharStringsOffset）， 指向 CFF 和/或 CFF2 表的 CharStrings INDEX 数据起始位置。

这三项要求使得在 CFF 和 CFF2 表上实现按字形索引的补丁应用过程能够 得到显著 简化。它们允许在不改变 CFF/CFF2 表中编码的任何 其他数据元素偏移量的情况下，将字形数据插入 CFF/CFF2 表。 存储的 CFF/CFF2 偏移量使客户端无需 解析 CFF/CFF2 表的其他部分即可定位 CharStrings INDEX。

注：在某些情况下，CFF 或 CFF2 表可能 由按表索引的补丁添加或修改。在这些情况下，补丁 还需要添加或更新 charstrings 偏移量，以反映新增或修改后的内容。

CFF 或 CFF2 子程序化与增量字体传输兼容。但是，简单的 子程序化往往 会在减小补丁大小的同时增加初始文件的大小。此外，WOFF2 通常被证明能够 比对经过子程序化处理的等效字体更有效地压缩 未经子程序化处理的字体（但代价是显著增大 未压缩文件的大小）。因此，建议避免子程序化、适度使用子程序化，或 根据 IFT 的特定需求对其进行定制。

5.3. 补丁映射表

5.3.1. 解释补丁映射

此算法用于将补丁 映射转换为补丁映射条目列表。

解释补丁映射

此算法的输入为：

  • patch map：一个补丁映射表。

此算法的输出为：

  • entry list：一个补丁映射条目列表。

算法步骤：

  1. 检查 patch map 的format 是否等于 2，且是否满足 § 5.3 补丁映射表中的要求（要求以“必须”标记）。如果 不满足，则返回错误。

  2. 如果entryIdStringData 偏移量为 0，则 将 last entry id 初始化为 0。否则，将 其初始化为空字节字符串。将 current byte 设为 0，并将 current id string byte 设为 0。

  3. 将 entry list 和 prior entry list 初始化为空列表。

  4. 调用解释补丁映射条目 entryCount 次。对于每次调用：

    • 传入 prior entry list、patch map 中从entries[current byte] 开始到 patch map 末尾的字节， 如果entryIdStringData 不为零，则还传入 patch map 中从 entryIdStringData[current id string byte] 开始到 patch map 末尾的字节，以及 last entry id、 defaultPatchFormat 和 urlTemplate。

    • 将 last entry id 设为返回的条目 ID。

    • 将返回的已消耗字节数加到 current byte。

    • 将返回的已消耗 ID 字符串字节数加到 current id string byte。

    • 将返回的条目添加到 prior entry list。

    • 如果返回的 ignored 值为 false，则将返回条目的兼容性 ID 设为 compatibilityId，并将该条目添加到 entry list。

  5. 返回 entry list。

解释补丁映射条目

此算法的输入为：

  • prior entry list：此条目之前的条目列表。

  • entry bytes：包含一个已编码映射条目的字节数组。

  • id string bytes（可选）：包含条目 ID 字符串的字节数组。

  • last entry id：最后生成的条目 ID。

  • default patch format：未指定补丁格式时使用的默认补丁格式。

  • url template：用于定位补丁的 URL 模板。

此算法的输出为：

  • entry id：此条目最后生成的数字或字符串 ID。

  • entry：单个条目。

  • consumed bytes：用于编码该条目的字节数。

  • consumed id string bytes：用于编码条目 ID 字符串的字节数。

  • ignored：如果为 true，则应忽略此条目。

算法步骤：

  1. 在所有步骤中，每当从 entry bytes 加载数据时，都将读取的 字节数 加到 consumed bytes。

  2. 将 entry id = last entry id，consumed id string bytes = 0。

  3. 将 entry 的补丁格式设为 default patch format。

  4. 向 entry 添加一个字体子集定义，并将其中所有 集合初始化为空。

  5. 从 entry bytes 读取formatFlags。

  6. 如果formatFlags 的位 0 被设置，则存在特性标签和 设计空间列表：

    • 从 entry bytes 读取由featureCount 和featureTags 指定的特性标签列表， 并将加载的标签添加到 entry 中的第一个字体子集定义。

    • 从 entry bytes 读取由designSpaceCount 和designSpaceSegments 指定的设计空间区间列表，并将这些区间添加到 entry 中的第一个字体子集定义中。每个 区间定义了由tag 标识的轴上从start 到end（包含两端）的区间。 如果任何区间的start 大于 end，则此编码无效，返回 错误。

  7. 如果formatFlags 的位 1 被设置，则存在复制索引 列表：

    • 如果childEntryMatchModeAndCount 的最高有效位被设置，则将 entry 的匹配模式设为合取， 否则设为析取。

    • 从 entry bytes 读取由childEntryMatchModeAndCount 和childEntryIndices 指定的 子条目索引列表。

    • 子条目索引引用先前加载的条目。0 表示 prior entry list 中的第一个映射条目， 1 表示第二个， 依此类推。对于childEntryIndices 中的每个值，在 prior entry list 中找到索引匹配的条目。 将对该条目的引用添加到 entry。如果某个childEntryIndices 值大于或 等于 prior entry list 的长度，则此编码无效，返回错误。

  8. 如果formatFlags 的位 2 被设置，则存在 ID 差值或 ID 字符串长度：

    • 如果 id string bytes 不存在，则：

      • 读取下一个entryIdDelta 值。

      • 将 entry id 设为 entry id + 1 + floor(delta value / 2)。 如果 entry id 为负数或大于 4,294,967,295，则此编码 无效，返回错误。

      • 通过以 url template 和 entry id 为输入调用展开 URL 模板，将 entry id 转换为 URL 字符串。如果模板展开发生错误， 则返回错误。

      • 将生成的补丁 URL 字符串添加到 entry。

      • 如果读取的差值的最低有效位被设置，则重复步骤 8。

    • 否则，如果 id string bytes 存在，则：

      • 读取下一个entryIdStringLength 值。

      • 将最低 23 位解释为无符号整数，并从 id string bytes 中读取相应数量的字节。 将 entry id 设为结果。将读取的字节数 加到 consumed id string bytes。

      • 通过以 url template 和 entry id 为输入调用展开 URL 模板，将 entry id 转换为 URL 字符串。如果模板展开发生错误， 则返回错误。

      • 将生成的补丁 URL 字符串添加到 entry。

      • 如果读取的长度值的最高有效位被设置，则重复步骤 8。

  9. 如果formatFlags 的位 2 未设置：

    • 如果 id string bytes 不存在，则：

      • 将 entry id 设为 entry id + 1。

      • 通过以 url template 和 entry id 为输入调用展开 URL 模板，将 entry id 转换为 URL 字符串。如果模板展开发生错误， 则返回错误。

      • 将生成的补丁 URL 字符串添加到 entry。

    • 否则，如果 id string bytes 存在，则：

      • 通过以 url template 和 entry id 为输入调用展开 URL 模板，将 entry id 转换为 URL 字符串。如果模板展开发生错误， 则返回错误。

      • 将生成的补丁 URL 字符串添加到 entry。

  10. 如果formatFlags 的位 3 被设置，则存在补丁格式。 从 entry bytes 读取由 patchFormat 指定的格式，并将 entry 的补丁格式设为读取的值。 如果patchFormat 不是§ 6.1 格式概述中的某个值，则此编码无效， 返回错误。

  11. 如果formatFlags 的位 4 和位 5 中有一个或两个被设置，则存在码点 列表：

    • 如果formatFlags 的位 4 为 0 且位 5 为 1，则 从 entry bytes 读取 2 字节（uint16）的bias 值。

    • 如果formatFlags 的位 4 为 1 且位 5 为 1，则 从 entry bytes 读取 3 字节（uint24）的bias 值。

    • 否则，bias 为 0。

    • 按照§ 5.3.3 稀疏位集合，使用偏移值 从 entry bytes 读取稀疏位集合codePoints。 将得到的码点集合添加到 entry 中的第一个字体子集 定义。如果稀疏位集合解码 失败，则此编码无效，返回错误。

  12. 如果formatFlags 的位 6 被设置，则将 ignored 设为 true。否则，ignored 为 false。

  13. 返回 entry id、entry、consumed bytes、 consumed id string bytes 和 ignored。

5.3.2. 从补丁映射中移除条目

此算法用于从补丁映射中移除条目。此移除操作会修改补丁映射的字节， 但不会 改变字节数量。

从补丁映射中移除条目

此算法的输入为：

  • patch map：一个补丁映射表。此过程可以修改它。

  • patch URL string：用于标识要移除条目的补丁 URL 字符串。

此算法是解释 补丁映射的修改版本，以 patch map 为输入调用解释补丁映射， 但作出以下更改：

  • 在解释补丁映射条目的步骤 8 和 9 中： 仅将为第一个差值/长度值生成的 URL 字符串与 patch URL string 进行比较。如果相等，则将formatFlags 的位 6 设为 1。 此时停止解释过程。

  • 不使用解释补丁映射的返回值。

5.3.3. 稀疏位集合

稀疏位集合是一种以紧凑方式存储不同无符号整数集合的数据结构。该集合 表示为一棵树，其中 每个节点具有固定数量的子节点，这些子节点递归地将一个区间划分为大小相等的部分。 高度为 H、 分支因子为 B 的树可以存储区间 [0 到 BH-1]（包含两端）内整数的集合成员关系。该树 被编码为字节数组以供传输。

在补丁映射表中，稀疏位集合用于存储Unicode 码点集合。因此， 稀疏位集合中存储的整数 值仅限于 0 到 0x10FFFF 范围内的Unicode 码点值。

稀疏位集合编码：

类型 名称 描述
uint8 header 位 0（最低有效位）和位 1 通过分支因子编码表示树的分支因子 B。位 2 至位 6 是 一个 5 位无符号整数，用于编码 H 的值。位 7 设为 0，保留供 将来使用。
uint8 treeData[variable] 树的二进制编码。

treeData 的确切长度最初是未知的，其长度通过执行 解码算法确定。使用 分支因子 2 或 4 时，最后一个节点可能只使用一个字节中的部分位。在这种情况下，所有 剩余的位均未使用， 并被忽略。

分支因子 编码：

位 1 位 0 分支因子（B） 最大高度（H）
0 0 2 31
0 1 4 16
1 0 8 11
1 1 32 7

如果稀疏位集合编码的高度（H）大于上表中 对应编码分支因子（B）的最大高度， 则该编码无效。

解码稀疏位集合 treeData

此算法的输入为：

  • treeData：要解码的字节数组。

  • bias：添加到每个解码后集合成员的无符号整数值。

此算法的输出为：

  • S：一个无符号整数集合。

算法使用一个 FIFO（先进先出）队列 Q：

  1. 从 treeData 中移除第一个字节。这是标头字节。按照 稀疏位集合确定树高度 H 和 分支因子 B。

  2. 如果 H 大于分支因子编码 表中 B 所在行的“最大高度”，则 编码无效，返回错误。

  3. 如果 H 等于 0，则这是一个空集合，不再消耗 treeData 的其他字节。 返回空集合。

  4. 将元组 (0, 1) 插入 Q。

  5. 将 S 初始化为空集合。

  6. 将 treeData 解释为位字符串，其中 treeData[0] 的最低有效位是该 字符串的第一位，treeData[0] 的最高有效位是第 8 位，依此类推。

  7. 如果在以下步骤中向 S 添加的值大于 Unicode 码点的最大值（0x10FFFF），则 忽略该值，不将其添加到 S。

  8. 如果 Q 为空，则返回 S。

  9. 从 Q 中取出下一个元组 t。t 中的第一个值 是 start，第二个值是 depth。

  10. 从 treeData 位字符串中移除接下来的 B 位。移除的第一位是 v1， 第二位是 v2，依此类推，直到最后一位 vB。如果移除前 treeData 中剩余的位少于 B 位，则 treeData 格式错误， 返回错误。

  11. 如果从 v1 到 vB 的所有位均为 0，则将 区间 [start + bias, start + bias + BH - depth + 1) 内的所有整数插入 S。转至步骤 5。

  12. 对于从 v1 到 vB 中每个等于 1 的 vi： 如果 depth 等于 H，则将 整数 start + bias + i - 1 添加到 S。否则，将 元组 (start + (i - 1) * BH - depth, depth + 1) 插入 Q。

  13. 转至步骤 8。

注：编码稀疏位集合时，编码器可以使用 任何允许的分支因子，但建议 使用 4，因为已有研究 表明， 对于通常遇到的大多数 Unicode 码点集合，它能生成最小的编码。

5.3.4. URL 模板

URL 模板用于压缩与每个补丁映射条目关联的 URL 字符串。每个补丁映射 表 提供一个 URL 模板，然后以每个条目的 ID 作为输入，展开该通用模板来生成各条目的 URL 字符串。 模板展开的输出是一个使用[UTF-8] 编码的字符串。

URL 模板被编码为一系列单字节操作码，这些操作码或者插入字面值， 或者根据 输入的条目 ID 插入值。

解码和展开 URL 模板的算法如下。

展开 URL 模板

此算法的输入为：

  • url template bytes：包含 URL 模板的字节数组。

  • entry ID：条目的 ID。可以是无符号整数或字节数组。

此算法的输出为：

  • URL string：表示 URL 字符串的字节数组。采用[UTF-8] 编码。

算法步骤：

  1. 将 URL string 初始化为空字节数组。在后续步骤中，将 url template bytes 作为 队列使用。 读取操作从队列前端移除字节（从索引 0 处的字节开始）。

  2. 从 url template bytes 中读取下一个字节到 op code。如果没有 剩余字节，则 展开完成，返回 URL string。

  3. 如果 op code 的最高有效位未设置，则：

    • 将 op code 的最低 7 位解释为无符号整数， number of literals。

    • 如果 number of literals 为 0，则返回错误。

    • 从 url template bytes 中读取接下来的 number of literals 个字节到 literal bytes。 如果 url template bytes 中剩余的字节不足，则返回 错误。

    • 按照UTF-8，ISO 10646 的一种转换格式 § section-4，检查 literal bytes 是否是有效的 UTF-8 编码字符串。 如果不是，则返回错误。

    • 将 literal bytes 追加到 URL string 的末尾。

    • 转至步骤 2。

  4. 如果 op code 的最高有效位被设置，则：

    • 在下方的操作码参考表中查找 op code。执行 “插入操作”列中指定的操作。如果在表中找不到 op code，则 返回错误。

    • 转至步骤 2。

6. 字体补丁格式

在增量字体传输中，通过应用补丁来扩展字体 子集。 本规范定义了两种补丁格式，每种格式都适用于各自的一组扩充场景。单个 编码 可以使用多种补丁格式。

6.1. 格式概述

本规范定义了以下补丁格式：

  • § 6.2 按表索引：一组使用 字体子集中的表 作为基础的 Brotli 编码二进制差异数据。

  • § 6.3 按字形索引：一组不透明的二进制数据块，每个数据块都与 一个字形 ID 和一个表关联。

有关每种算法的更详细说明，请参阅以下各节。

以下格式编号用于在§ 5.3 补丁映射表中标识补丁格式和失效模式：

格式编号 名称 失效模式
1 § 6.2 按表索引 完全 失效
2 § 6.2 按表索引 部分 失效
3 § 6.3 按字形索引 不失效

6.2. 按表索引

按表索引的补丁包含一组补丁，这些补丁分别应用于输入字体文件中的各个 字体表。 每个表补丁都使用 Brotli 压缩进行编码，并使用输入字体文件中的对应表作为 共享 LZ77 字典。按表索引编码的补丁由一个简短的标头以及 一个或多个 Brotli 编码的补丁组成。除修补表之外，补丁还可以替换（不使用现有 表数据） 或移除字体 子集中的表。

6.2.1. 应用 按表索引的补丁

此补丁应用算法用于应用按表索引的 补丁，以扩展字体子集，使其 覆盖额外的码点、 特性和/或设计变体空间。

应用按表索引的补丁

此算法的输入为：

  • base font subset：一个待扩展的字体子集。

  • patch：要应用于 base font subset 的按表索引的补丁。

  • compatibility id：base font subset 的 'IFT ' 或 'IFTX' 表中列出此补丁的 ID 编号。

此算法的输出为：

  • extended font subset：通过 patch 扩展后的字体子集。

算法步骤：

  1. 将 extended font subset 初始化为一个不包含任何表的空字体。

  2. 检查 patch 是否符合§ 6.2 按表索引中的要求（要求以 “必须”标记），以及所有TablePatch 是否都包含在 patch 中。否则，返回错误。

  3. 检查 patch 中的compatibilityId 字段是否 等于 compatibility id。 如果两者不匹配，或者 base font subset 既没有 'IFT ' 表也没有 'IFTX' 表， 则补丁应用 失败，返回错误。

  4. 在以下步骤中，向 extended font subset 添加一个表，是指将 该表的数据添加到字体中，并 按照 OpenType 规范的要求，在表 目录中插入一个新条目。该条目包含表数据的校验和。当现有表 未经修改而直接复制时，客户端 可以重用源字体中该条目的校验和。否则，需要 计算新的校验和。

  5. 对于patches 中索引为 i 的每个条目：

    • 找到与索引 i 关联的TablePatch。 该对象从偏移量 patches[i]（包含）开始，到 偏移量 patches[i+1]（不包含）结束。两个偏移量都 相对于 patch 的起始位置。

    • 如果此前已应用patches 中的某个条目，且其 tag 与 当前条目相同，则忽略当前条目并继续迭代处理下一个条目。条目按照 它们在 patches 数组中列出的顺序处理。

    • 如果flags 的位 1 被设置，则不要向 extended font subset 复制或添加由 tag 标识的表。 继续处理下一个条目。

    • 如果flags 的位 0（最低有效位）被设置，则按照 Brotli 压缩数据 格式 § 10 解码算法解码brotliStream。 不使用共享字典。如果 解码后的数据大于maxUncompressedLength， 则返回错误。如果brotliStream 中存在 解码过程未使用的任何数据，则返回错误。 向 extended font subset 添加一个由 tag 标识的表， 并将其内容设为解码后的brotliStream。继续处理下一个条目。

    • 否则，按照Brotli 压缩数据 格式 § 10 解码算法解码brotliStream，并使用 base font subset 中由tag 标识的表 作为共享 LZ77 字典。如果不存在这样的表，则返回错误。如果解码后的数据 大于maxUncompressedLength，则返回 错误。如果brotliStream 中存在 解码过程未使用的任何数据，则返回错误。向 extended font subset 添加一个由tag 标识的表， 并将其内容设为解码后的 brotliStream。

  6. 对于 base font subset 中标签未出现在步骤 5 所处理 条目中的每个表， 将该表的副本添加到 extended font subset。

6.3.1. 应用 按字形索引的补丁

此补丁应用算法用于应用按字形索引的 补丁，以扩展字体子集，使其 覆盖额外的码点、 特性和/或设计变体空间。

应用按字形索引的补丁

此算法的输入为：

  • base font subset：一个待扩展的字体子集。

  • patch：要应用于 base font subset 的按字形索引的补丁。

  • patch URL string：补丁数据所在位置的 URL 字符串。

  • compatibility id：base font subset 的 'IFT ' 或 'IFTX' 表中列出此补丁的兼容性 ID。

此算法的输出为：

  • extended font subset：通过 patch 扩展后的字体子集。

算法步骤：

  1. 检查 patch 是否符合§ 6.3 按字形索引中的要求（要求以 “必须”标记）。否则，返回错误。

  2. 检查 patch 中的compatibilityId 字段是否 等于 compatibility id。 如果两者不匹配，或者 base font subset 既没有 'IFT ' 表也没有 'IFTX' 表， 则补丁应用 失败，返回错误。

  3. 按照Brotli 压缩数据 格式 § 10 解码算法解码brotliStream 中的 Brotli 编码数据。 解码后的数据是一个GlyphPatches 表。如果解码后的数据大于 maxUncompressedLength，则返回 错误。

  4. 对于字体 表中列在tables 中、索引为 i 的每个表：

    • 使用 base font subset 中的对应表，合成 一个新表，其中每个字形的数据在存在对应数据时替换为 glyphData 中该字形索引对应的数据， 否则从 base font subset 中的对应表复制 该字形索引的数据。

    • 通过查找等于该字形索引的glyphIds[j]， 定位该字形索引的补丁字形数据。 关联字形数据的偏移量为glyphDataOffsets[i * glyphCount + j]。 关联字形数据的长度 等于glyphDataOffsets[i * glyphCount + j + 1] 减去 glyphDataOffsets[i * glyphCount + j]。

    • 合成新表的具体过程取决于指定的 表格式。 任何不与字形关联的数据都应从 base font subset 中的表复制。支持类型为glyf、 gvar、CFF 或 CFF2 的表。 任何其他类型 表的条目 都必须忽略。更新glyf 时， 也必须更新 loca 表。此步骤不得修改字体中的其他表。 特别是，这意味着补丁不能添加字形索引 超出maxp 中指定的 numGlyphs 的字形。

      CFF、CFF2 和 gvar 具有 可变大小的逐字形数据偏移量。如果 在合成新表时有必要，可以根据需要增大偏移量的大小。对于glyf/loca， 偏移量的大小不能改变，因为偏移量大小在head 表中指定。 如果合成过程中生成的偏移量 超过最大可能的偏移值（在可能的情况下增大偏移量大小 之后），则补丁应用 失败。返回错误。

    • 如果 base font subset 没有匹配的表，则返回错误。

    • 将合成的表插入 extended font subset。

  5. 找到§ 5.3 补丁映射表中compatibilityId 与 compatibility id 相同的表。以 该补丁映射表和 patch URL string 为输入，调用 从补丁映射中移除条目。 将修改后的补丁映射 表复制到 extended font subset。

  6. 对于 base font subset 中标签未出现在步骤 4 或 5 所处理 条目中的每个表， 将该表的副本添加到 extended font subset。

  7. 如果前述步骤修改了任何字体 表的内容，则 对于每个修改后的表：更新字体 表目录中的校验和，使其与该表的 新内容一致。

7. 编码

编码器是一种生成增量字体及一组关联补丁的工具。“编码”是指 使用编码器的过程，包括编码器要求或允许用来影响特定 情况下 结果的任何参数。 符合规范的编码器生成的增量字体 及关联补丁：

  1. 必须满足 § 5 字体格式扩展和§ 6 字体补丁格式中的所有要求。

  2. 必须具有一致性，即： 对于任何可能的字体子集定义，以该子集定义和 增量字体为输入调用扩展增量字体 子集， 无论在扩展增量字体 子集的步骤 8 中选择哪一种具体的补丁顺序，结果都必须相同。

  3. 必须 遵守补丁失效准则。IFT 编码中的任何补丁 在应用于兼容的字体子集时， 对补丁映射兼容性 ID 所作的更改必须仅限于符合 § 4.1 补丁失效中针对关联 补丁映射条目所声明失效模式的准则的更改。

  4. 当使用编码器将现有字体转换为增量字体时，关联的 完全扩展后的字体应 与现有字体等效。等效的完全扩展字体 应包含与现有字体相同的所有表 （不包括增量 IFT/IFTX 表），并且每个表在功能上都应与现有字体中的对应表等效。注：完全 扩展后的字体不一定总能与现有字体在二进制层面完全一致。

  5. 应在整个扩充过程中保留完全扩展后字体的功能， 即： 给定从增量 字体派生的完全扩展后的字体 以及任意内容，通过以 增量 字体和覆盖该内容的最小子集定义为输入，调用扩展增量字体 子集所生成的字体子集，应对该内容产生与完全扩展后的字体相同的渲染结果。

当使用编码器将现有字体文件转换为增量字体，且客户端按照 本文档其他章节 实现时，IFT 规范的目标是使客户端中的字体外观和行为 与将整个字体文件传输到客户端时 相同。IFT 规范的一个主要目标是让 IFT 格式和协议能够 作为类似 WOFF2 的字体传输中立媒介。如果编码器从 满足上述所有 要求（1 至 5）的源字体生成编码，那么该编码将保留 原始字体的全部功能。上述要求 4 确保原始字体中的所有功能均可获得。它与 要求 5 配合，后者要求 IFT 字体的部分版本在渲染属于 用于派生该部分字体的子集定义范围内的内容时，具有与完整版本（此处为原始字体）等效的功能。

这对于字体铸造厂或字体的其他权利人希望确信 使用 IFT 对该字体进行编码和传输 不会改变其行为，从而不会改变字体创作者的设计意图的情况可能很重要。许可或 合同因此可能包含 关于 IFT 符合性的要求，而由于 WOFF2 的 内容中立性，将字体重新编码为 WOFF2 格式实际上被允许的情况，也可能允许对该字体进行 IFT 编码。

不过，这些编码符合性要求并不意味着要排除或弃用 无法保留源字体全部功能的 编码及其实际用途。任何满足最低要求（上述 1、2 和 3） 的编码都是有效的，并且可能具有适当的用途。在某些情况下，即使原始字体文件包含 某些功能或数据，也可能希望编码后的字体 在其所有补丁文件中省略对这些 功能或数据的支持。在其他情况下，字体可能 直接从字体创作源文件编码为 IFT 格式。如果编码器选择不 满足上述要求 4， 仍强烈建议满足要求 5，以确保字体在整个 扩充过程中的行为保持一致。

7.1. 编码考虑因素

本节不具有规范性。

编码过程的细节可能因编码器而异，且超出了本文档的范围。不过， 本节提供了一些 编码器实现可能需要考虑的指导建议，这些建议对于在生成现有字体文件的 增量版本时重现其外观和行为可能很重要。本 节提供的指导建议 基于本规范制定期间构建编码器实现的经验。 它代表了在 编写本文档时，对于如何生成满足 § 7 编码中要求 1 至 4 的高性能编码，并因此保留 原始字体全部功能和行为的最佳理解。

关于§ 6.2 按表索引补丁

§ 6.2 按表索引补丁可以更改某些字体表的内容，而不更改 其他表。每个被修补的表通常需要 以特定的表内容为基础，但其他表可以具有不同的内容。因此，只要 § 6.2 按表索引 补丁不修改包含字形数据的表，它就可以与§ 6.3 按字形索引补丁兼容，从而仅产生 部分 失效（即它会使其他§ 6.2 按表索引补丁失效， 但不会使 § 6.3 按字形索引补丁失效）。此外，如果两组§ 6.2 按表索引补丁不修改任何相同的表，它们就可以彼此独立。 例如，可以使用§ 6.2 按表索引 补丁处理除字形表之外的所有 内容，然后对这些表使用另一组§ 6.2 按表索引 补丁，而不是使用 § 6.3 按字形索引补丁。理论上，这两组补丁都可以是部分 失效的，从而使它们 各自具有内部依赖关系，但彼此独立。

应用§ 6.2 按表索引补丁通常会修改列出该补丁的 IFT 或 IFTX 表，以添加一组新的 补丁来进一步扩展字体。这意味着所有§ 6.2 按表 索引补丁构成一个图， 其中分段中的每个字体子集是一个节点，每个补丁是一条边。这也意味着 此类补丁 通常需要串行下载和应用，因此这种补丁 类型在延迟方面存在性能影响。

关于§ 6.3 按字形索引补丁

§ 6.3 按字形索引补丁与其他补丁类型有明显区别。首先，§ 6.3 按字形索引补丁只能修改 包含字形轮廓数据的表，因此仅使用§ 6.3 按字形 索引的增量字体必须在初始字体文件中包含所有 其他字体表的数据。其次，§ 6.3 按字形索引补丁 不会使其他补丁失效， 因此可以独立下载和应用。这种独立性意味着可以 并行下载多个补丁， 与使其他补丁失效的类型相比，可显著减少所需的网络往返次数。

为编码选择补丁格式

所有编码都必须选择使用一种或多种补丁类型。§ 6.2 按表索引补丁允许 修补字体中的所有类型的数据，但由于这种类型至少会造成部分失效， 所需补丁总数会随分段数量呈指数增长，而不是线性增长。 § 6.3 按字形索引补丁 只能更新轮廓和变体增量数据，但所需补丁数量随 分段数量线性增长。

除了补丁数量之外，编码器还应考虑获取 典型内容所需补丁的网络往返次数。 对于使其他补丁失效的类型，必须串行发出补丁请求。这意味着，如果某些 内容需要多个分段，就可能需要多次网络往返。另一方面，按字形索引的补丁 不会使其他补丁失效， 因此可以并行获取这些补丁，只需要一次网络往返。

在这两种类型的极端情况下，§ 6.2 按表索引补丁最适合 包含大量非轮廓数据且只需要 少量补丁的字体。§ 6.3 按字形索引补丁最适合 绝大部分数据由字形 轮廓组成的字体，许多现有的 CJK 字体都属于这种情况。

对于介于两种极端情况之间的字体，或者希望对字形数据进行细粒度分段， 但仍需要对其他表中的数据 进行分段的情况，可以考虑按照以下方式混合使用§ 6.2 按表索引 和§ 6.3 按字形索引补丁类型：

  1. 将所有按表索引的补丁条目放在一个映射表中，将所有按字形索引的条目放在另一个 映射表中。

  2. 使用按表索引的补丁更新除按字形索引的补丁所涉及的表之外的所有表 （轮廓、 变体增量和按字形索引的补丁映射表）。这些补丁应使用少量 较大的分段，以使 补丁数量保持合理。

  3. 由于按字形索引的补丁引用了被更新字形的具体 ID，因此按表索引的 补丁不得更改 原始字体中使用的字形与字形 ID 之间的对应关系；否则，按字形索引的补丁中列出的字形 ID 可能 不再正确。在字体子集化工具中，这通常是一个名为“保留字形 ID”的选项。

  4. 最后，使用按字形索引的补丁更新剩余的表，此时可以使用更小、粒度更细的 分段，而不会 需要过多的补丁。

预计混合补丁类型编码会成为一种常用方法，因为许多字体处于这两种 极端情况之间。

使用使其他补丁失效的补丁减少网络往返次数

对于使用某种使其他补丁失效的 补丁类型进行分段的情况，减少所需网络往返次数的一种方法是提供 能够一次添加多个分段的补丁（此外还提供单个分段的补丁）。例如， 考虑一个包含 4 个分段的字体： A、B、C 和 D。补丁表可以列出添加以下内容的补丁：A、B、C、D、A + B、A + C、A + D、B + C、B + D 和 C + D。这将 允许在一次网络往返中添加任意两个分段。这种方法的缺点是会进一步 增加所需的不同 补丁数量。

编码后的补丁映射中的条目顺序

在§ 4.4 选择使补丁失效的补丁中，客户端使用 补丁映射中的条目顺序，在选择要加载和应用的补丁时打破平局。 客户端旨在减少总传输大小，因此当多个条目的交集大小相同时， 选择总传输大小最小的补丁通常更符合客户端的利益。因此，编码器应按照 字节大小从小到大的顺序排列补丁映射中的条目。 这将确保客户端遵循§ 4.4 选择使补丁失效的补丁时倾向于选择较小的补丁，从而最大限度地提高性能。

管理补丁数量

同时使用§ 6.2 按表索引补丁和大量分段，可能导致 所需补丁数量非常庞大，从而产生两个 负面影响。首先，存储所有预生成补丁所需的空间可能 过大。其次，更多 补丁通常意味着更低的 CDN 缓存性能，因为更多补丁意味着 从某个子集到另一个子集存在更多不同的路径， 而不同用户会根据其访问的内容采用不同的路径。 可以使用以下技术减少预生成补丁的总数：

  1. 为补丁图设置最大深度，一旦达到该限制，就通过补丁添加完整 原始字体的所有剩余部分。 这会使字体在添加一定数量的 分段后加载所有剩余内容。限制 图的深度可以减少较深层级上补丁数量的组合爆炸。

  2. 或者，在较深层级，编码器可以开始将多个分段合并为单个 补丁，以减少每个 层级的分支数量。

选择分段方式

编码器需要作出的最重要且最复杂的决定之一，是如何对 编码字体中的数据进行分段。上述讨论 侧重于分段数量，但增量字体的性能在更大程度上取决于 分段内部的数据 分组方式。为了最大限度地提高效率，编码器需要将经常一起 使用的数据（例如码点）归入同一 分段。这会减少客户端扩展字体时加载的不必要数据量。编码器 还必须决定分段的大小。 较小的分段会产生更多补丁，因此需要更多 网络请求，产生更高的开销，但与较大的分段相比， 通常每个分段包含的不必要数据更少。在对码点进行分段时， 码点使用频率的数据 可以帮助指导分段。

某些码点可能具有显而易见的分段方式，或者至少很容易确定 哪些码点应归为一组。 例如，拉丁字母的大写和小写字母自然构成一组。其他情况可能更 复杂。例如， 中文、日文和韩文共享某些码点，但在日文中高频使用的码点 在中文中可能使用频率较低。 在某些情况下，可以选择针对单一语言优化编码。另一种方法是 生成折衷的 编码。例如，在分段时，编码器可以将日文、 中文和韩文中均高频使用的码点放入一个 分段，然后将仅在日文和中文中高频使用的码点放入另一个分段， 依此类推。之后， 仅在一种语言中高频使用的码点可以按照通常方式处理。 这会导致分段大小不那么均匀，但意味着 加载任何一种语言的高频补丁时，都不会同时加载低频字形。

包含默认布局特性

附录 A：默认特性标签汇总了一组 通常默认使用的布局特性。由于此列表中的特性 通常始终会被塑形器使用，因此为了获得最佳性能，编码器通常不应 在字体编码中将这些特性 设为可选。

保持功能等效性

如§ 7 编码所述，编码器应保留 原始字体的功能。字体结构复杂， 而且码点之间往往存在相互作用，因此使用字体的部分副本保持功能等效性 可能很棘手。 以下两个小节讨论如何使用不同的补丁类型保持功能等效性。

按表索引的补丁

在准备§ 6.2 按表索引补丁时，实现功能 等效性的一种方法是利用 现有的字体子集化工具实现，生成能够保留原始字体功能的字体子集。 然后可以从这些子集中派生 IFT 补丁。

字体子集化工具根据所需的字体子集定义，从输入字体生成一个字体 子集。可靠地 对字体进行子集化的方法已经得到充分理解，并且存在多个开源实现（完整的形式化描述 超出了本文档的范围）。这通常涉及可达性分析，即检查表中的 数据， 根据字体子集定义确定其中哪些部分可由该定义覆盖的 任何可能内容访问。 所有可达数据都会保留在生成的字体子集中，而不可达数据则可以移除。

以下伪代码示例使用字体子集化工具生成一个仅使用 按表索引的补丁的 IFT 编码字体：

# 将字体（full_font）编码为从 base_subset_def 开始的增量字体
# 并可增量添加 subset_definitions 中的任意定义。返回 IFT 编码字体
# 及一组关联的补丁。
encode_as_ift(full_font, base_subset_def, subset_definitions):
  base_font = subset(full_font, base_subset_def)
  base_font, patches  = encode_node(full_font, base_font, base_subset_def, subset_definitions)
  return base_font, patches

# 更新 base_font，添加所有能够到达任意
# subset_definitions 的 IFT 补丁映射，并生成关联的补丁。
encode_node(full_font, base_font, cur_def, subset_definitions):
  patches = []
  next_fonts = []

  for each subset_def in subset_definitions not fully covered by cur_def:
    next_def = subset_def union cur_def
    next_font = subset(full_font, next_def)
    let patch_url be a new unique url

    add a mapping from, (subset_def - cur_def) to patch_url, into base_font 
    next_font, patches += encode_node(full_font, next_font, next_def, subset_definitions)

    next_fonts += (next_font, next_def, patch_url)

  for each (next_font, next_def, patch_url) in next_fonts:
    patch = table_keyed_patch_diff(base_font, next_font)
    patches += (patch, patch_url)

  return base_font, patches

在此实现示例中，如果输入的基础子集定义与子集 定义列表的并集完整覆盖了输入的 完整字体，并且所使用的子集化工具实现正确保留了所有功能，那么上述 实现应满足 § 7 编码中关于中立编码的要求。这个基本编码器 实现仅用于演示，并不意味着 它能够代表所有可能的编码器实现。特别是，它既未使用，也未 演示如何使用按字形索引的 补丁。大多数编码器可能更为复杂，需要考虑其他因素，其中一些将在 后续 章节中讨论。

§ 6.3 按字形索引补丁

特别是，由于按字形索引的补丁以码点和特性标签为参数， 但可以彼此独立地应用， § 6.3 按字形索引补丁具有额外要求，无法 直接通过子集化工具实现派生。不过， 此类实现可以帮助明确编码器在生成这种 补丁时为保持功能等效性需要做什么。考虑根据给定的字体子集定义生成字体子集的结果。我们可以 将该字体 子集定义的字形闭包 定义为子集中包含的完整字形集合，子集化工具 已确定这些字形是渲染所描述码点和布局 特性的任意组合所必需的。

根据上述定义，完整的§ 6.3 按字形索引补丁集合必须满足的字形闭包要求为：

  • 通过补丁映射表为某个字体子集定义 加载的补丁所包含的字形集合，必须是该字体子集定义的字形 闭包中字形集合的超集。

假设子集化工具准确完成工作，那么字形闭包要求是 行为等效性要求的结果： 假设存在某个字体子集定义，子集化工具在其子集中包含字形 *i*，但生成 § 6.3 按字形索引补丁的编码器却从与该定义对应的补丁集合中省略了字形 *i*。 如果子集化工具的判断 正确，那么在渲染该定义中的码点和特性的某种 组合时，要保持等效行为就必须包含该字形， 这意味着增量字体在渲染该 组合时将无法表现出等效行为。

因此，在生成使用按字形索引补丁的编码时，编码器必须确定如何 在所有补丁之间分配字形， 以满足字形闭包要求。这主要涉及查看分配给 某个分段的码点，并确定对应补丁还必须包含哪些其他字形。例如，当一个字形变体 可以通过替换分段中码点对应的字形 而出现时，就需要将其包含在补丁中。在某些情况下，某个字形可能只有在 加载多个分段 后才需要，此时可以将该字形添加到任意一个对应分段的补丁中。 （连字或预组合的重音字符可能属于这种 情况。）最后，在对分段进行初步分析后，同一个字形可能 在加载两个或多个分段的补丁时都需要。 处理这种情况主要有五种策略：

  1. 可以将两个或多个分段合并到一个补丁中。这样可以避免重复 公共字形，但 会增加分段大小。

  2. 可以将公共字形放入其自身的补丁中，然后设置映射条目，使 任何需要该公共补丁的分段在加载时 同时触发该公共补丁的加载。例如，如果 'c' 是分段 'a' 和 'b' 都需要的公共分段，则可以 使用以下映射条目：

    • 子集定义 a → 分段 a

    • 子集定义 b → 分段 b

    • 子集定义 a 与子集定义 b 的并集 → 分段 c

  3. 在某些情况下，例如Unicode 变体选择符，存在一种 修饰性码点，当它与许多其他码点配对时，会触发字形替换。 由于替代 字形数量众多，最好将它们保存在单独的补丁中，只有当修饰性 码点和相应的基础 码点同时存在时才加载这些补丁。可以通过 childEntryIndices 实现多个条目的匹配。有关 如何进行设置的示例，请参阅示例 2：带有子条目的按字形索引的补丁。

  4. 或者，可以将该字形包含在与这些分段对应的多个 补丁中，但代价是将 该字形的数据重复存储在多个补丁中。

  5. 最后，可以将公共字形移入初始字体。这样既能避免增加分段大小， 又能避免重复字形数据， 但会增加初始字体的大小。这也意味着该字形的数据始终 会被加载，即使并不需要。 对于许多分段都需要的字形，或者会使 分段变得复杂的字形，这种方法可能很有用。

在初始字体中预加载数据

在某些情况下，可能希望避免向初始文件应用补丁所产生的开销。 例如， 可能希望公司主页加载的字体已经能够渲染该页面上的内容。 此类文件的主要好处 是减少渲染延迟：只需一次网络往返即可渲染内容。

在下载的字体文件中包含数据有两种方法。一种是直接对整个 增量字体 进行编码，使数据包含在初始文件中。任何此类数据都会始终存在于字体的任何 已修补版本中。 当相同数据原本需要出现在多个不同分段中时，这种方法很有用。

另一种方法是下载已经应用过补丁的字体。也就是说，可以编码一个 “基础”文件中几乎没有或完全没有 数据的字体，然后在服务器端对该文件应用补丁，使下载的文件已经包含 这些补丁中的 数据。

如果只需要一个字体的预加载版本，这两种策略的结果大致相同， 但第一种方法既 更简单，在某些情况下也更有针对性。然而，如果需要多个预加载字体， 预先应用补丁的方法通常 更好。使用第一种方法时，需要为每个 预加载文件生成单独的编码。使用 第二种方法时，所有预加载文件仍共享同一个完整的补丁图，这既能 减少存储补丁所需的总空间， 又能提高 CDN 缓存效率，因为所有预加载文件都将从 同一组补丁中选择后续补丁。

表的排列顺序

在初始字体文件中（无论是否编码为 WOFF2），都可以自定义 文件内部实际表字节的顺序。 编码器应考虑将映射表（IFT 和 IFTX）以及解码 映射表所需的任何其他表（cmap）尽可能靠前地放在文件中。 这样，经过优化的客户端实现便能在收到所有字体数据之前 访问 补丁映射，并可能更早地发起所需补丁的请求。

同样，按表索引的补丁为每个被修补的表提供独立的 Brotli 流，而且该格式 允许这些流以 任意顺序放置在补丁文件中。因此，基于相同原因，编码器应考虑将 映射表的更新以及 解码映射表所需的任何其他表尽可能靠前地放在补丁文件中。

选择输入 ID 编码

本规范支持两种在 URL 模板中嵌入补丁 ID 的编码方式。第一种是base32hex， 它非常适合通常存储在文件系统中的预生成补丁。Base32hex 编码只使用 字符 0-9 和 A-V，这些字符在所有常用文件系统中都可安全用于文件名， 不会因 大小写不敏感而发生冲突。由于该字符串在嵌入时不包含填充， 因此无法可靠地解码，所以它可能不 适合动态生成的补丁。另一种编码是base64url，它是 base64 编码的一种变体， 适合嵌入 URL 或区分大小写的文件系统。使用这种编码时，ID 会 连同填充一起嵌入，从而 可以可靠地解码该值。

单个字符选择符 d1 至 d4 仅相对于经过 base32hex 编码的 ID。这些选择符 通常用于 根据 ID 编码的末尾字符，将相关文件分散到一个或多个层级的 子目录中，从而减少单个文件系统目录中存储的文件数量。 使用整数 ID 时，这些字符往往会均匀分布在各个数字 之间，但对于字符串 ID，它们的分布可能不均匀，甚至保持不变。希望 将字符串 ID 与 d1 至 d4 一起使用的编码器应注意使 ID 字符串的末尾发生变化。允许将 d1 至 d4 与经过 base64url 编码的 ID 混合使用。

8. 隐私 考虑因素

8.1. 根据字符集推断内容

IFT 会向托管 Web 字体的服务器暴露有关浏览器希望使用该字体 渲染的字符集合的信息（有关 详细信息，请参阅§ 4 扩展字体子集）。

对于某些使用非常庞大字符集的语言（例如中文和日文），传输的 总字节数大幅减少， 意味着 Web 字体首次变得切实可用，包括在移动网络上。 然而，对于这些语言， 恶意字体服务器有可能分析单个请求，以获取 关于正在阅读的内容 类型的信息。除非 所请求的字符非常罕见，否则尚不清楚这种攻击有多大可行性，以及利用它所需的计算复杂度。

更具体地说，IFT 字体包含一组 Unicode 码点组，浏览器会 请求与正在渲染的内容 相交的组。这会向托管服务器透露某个组中至少需要一个码点， 但不会 包含有关该组内具体需要哪些码点的信息。这在功能上与现有的 CSS Fonts 4 § 4.5 字符 范围：unicode-range 描述符非常相似，并具有相同的隐私影响。有关 unicode-range 隐私影响的讨论， 可在 CSS Fonts 4 规范中找到：

  • CSS Fonts 4 § 15.1 此特性 可能向网站或其他方暴露哪些信息，以及为什么 必须暴露这些信息？对于隐私特别敏感的场景，该节建议用户代理 下载文档中的所有 Web 字体。 对于 IFT 字体，使用§ 4.7 完全扩展字体可以 获取整个可用的 IFT 字体，而不会提供任何有关 具体内容的信息。或者，在隐私敏感的场景中，用户代理可以 随机选择额外的补丁， 即使当前内容并不需要这些补丁，以此混淆实际 需要哪些补丁。

  • CSS Fonts 4 § 15.8 本规范 向源暴露哪些数据？还请说明哪些数据与 其他特性在相同或不同上下文中暴露的数据相同。

当内容和/或网站作者选择使用 IFT 字体时，他们必然对 编码 该字体的人员以及提供该字体的服务给予一定程度的信任，因为如上所述， 在扩展 IFT 字体的过程中， 会传输一定量与正在渲染的内容有关的信息。（这两者之间存在权衡， 因为 如下文所述，对编码越谨慎，就越不需要信任提供字体的服务。） 因此， 对于隐私敏感的情况，建议自行托管 IFT 字体，因为这可以防止 有关内容的任何信息 被传输给第三方。此外，在这种情况下，建议配置 内容 安全策略设置，禁止从其他源加载字体。

8.2. IFT 字体编码与隐私

IFT 字体的编码方式会显著影响从补丁文件的传输中 可以推断出多少有关内容的信息。本节提供一些通用指导，说明如何 评估 IFT 字体编码过程中所作选择的隐私影响。

IFT 字体被拆分为一组具有相关激活条件的补丁。当 发出补丁请求时， 这表明内容中存在与该补丁激活条件相交的内容。 因此， 字体中激活条件的结构是评估 编码隐私 特性时最重要的方面。

字体支持的每个不同码点、特性和设计空间配置都可能提供一个 信号： 它是否存在。激活条件可以是析取或合取条件。析取 条件 会引入不确定性，因为激活仅表示条件中的各个项目至少有一个 存在。 另一方面，合取补丁不会增加不确定性，因为它们要求 每个项目同时 存在。

码点或特性的典型出现频率会影响其存在所传达的 信息量。高频出现的项目所传达的信息少于 低频项目。低频码点的存在会更大程度地缩小 可能的内容范围。从 整体上看，这意味着对于包含低频 项目的条件，应使用更大、粒度更粗的条件。

模拟研究 在本规范的制定过程中发现，最小组大小（针对析取 条件） 为 4 至 7 个项目时，可以产生良好的模糊效果。在编码中使用最小组大小， 从 性能角度来看也是一种好方法，因为粒度过细的补丁会引入过多开销， 从而导致性能 下降。由于低频项目很少被需要，对包含这些项目的补丁 使用最小组大小 对整体性能影响很小。整体性能往往主要由高频项目决定。

编码器应评估生成的编码中的每个条件，并确定其有效组大小。 有效组 大小是指在有助于触发该条件的各个项目（码点、布局标签、设计 空间）中， 最小的析取子条件的大小。对于面向隐私敏感使用场景的编码， 编码器 应确保所有条件的最小组大小至少为 4 至 7。例如，考虑以下 情况：

  • A or B or C or D：有效组大小为 4，符合最低要求。

  • A and B and C AND D：有效组大小为 1，不符合最低 要求。

  • (A or B or C or D) AND (E or F)：由于 (D or E) 子条件，有效组大小为 2。因此 不符合最低要求。

编码器应提供配置控件，用于设置生成编码的隐私保护级别，因为 不同的使用场景 需要不同的级别。例如，为通过 HTTPS 自行托管而编码的字体不会引入 隐私 问题，而准备托管在公共第三方字体服务上的 IFT 字体则不同。对于 隐私敏感程度较低的 情况，编码器可以选择执行违反建议的最小组大小要求的优化。 例如： 设置一个用于添加可选布局特性数据的条件，其有效组 大小为 1。

当编码器提供这种灵活性，允许调整给定编码的隐私保护程度时， 建议 其文档和/或用户界面充分传达本节的信息，使 进行编码的用户能够作出适当选择。同样，建议托管 IFT 字体的网站 在编码自己的字体或从第三方获取已编码字体时考虑隐私问题。

8.3. 按源限制可避免指纹识别

按照[css-fonts-4]的要求：

“Web 字体 不得被除与 @font-face 规则关联或拥有 FontFaceSet 的文档之外的 任何其他文档访问。设备上的其他应用程序不得 访问 Web 字体。”——CSS Fonts 4 § 10.2 Web 字体

由于 IFT 字体在 CSS 中与普通字体采用相同的处理方式（§ 2 选择启用机制）， 因此这些要求同样适用，并可避免信息在不同 源之间泄露。

类似的要求也适用于字体调色板值：

“作者定义的 字体调色板只能供引用它的文档使用。在 引用该调色板的文档之外使用作者定义的调色板， 将构成安全信息泄露，因为一个页面的内容将能够 影响其他页面，而攻击者可以利用这一点作为攻击途径。”——CSS Fonts 4 § 9.2 用户定义的字体调色板：@font-palette-values 规则

9. 安全 考虑因素

一个安全问题是 IFT 字体可能会为补丁生成大量 网络请求。这可能 给客户端或托管补丁的服务带来问题。IFT 规范包含一些 缓解措施，用于限制过多 请求：

  1. § 4 扩展字体子集：禁止多次请求相同的 URL，并限制扩展过程中 可以发出的请求总数。

  2. 加载补丁文件：规定实现 Web 浏览器时使用[FETCH]， 并与初始字体加载使用的 CORS 设置保持一致。 因此，除非托管服务通过适当的 访问控制标头明确允许，否则不允许跨源请求补丁文件。

优化后的扩展示例

注：此执行示例按照 优化后的客户端实现进行描述，该实现旨在减少为目标子集定义 扩展字体所需的网络往返次数。此优化后的执行过程完全符合 扩展算法，但 比扩展算法指定的时间更早加载某些 URL（按字形索引的 URL）。这是允许的， 因为这些补丁 不会被前面的按表索引补丁使之失效。

输入：

  • 包含上述 IFT 和 IFTX 表的初始字体。

  • 目标子集定义：code points = {'f', 'P'}

迭代 1：

  • 步骤 1 至 6：对初始字体中的所有 条目应用检查条目交集，以下补丁条目相交：

    • //foo.bar/01.tk

    • //foo.bar/02.tk

    • //foo.bar/04.tk

    • //foo.bar/05.tk

    • //foo.bar/01.gk

    • //foo.bar/04.gk

  • 步骤 8：必须从该集合中选择一个条目。不存在完全失效条目，因此必须 选择一个部分失效条目（//foo.bar/*.tk）。 按照§ 4.4 选择使补丁失效的补丁， 候选条目与目标子集定义的交集如下：

    • //foo.bar/01.tk - {'f'}

    • //foo.bar/02.tk - {'P'}

    • //foo.bar/04.tk - {'f', 'P'}

    • //foo.bar/05.tk - {'f', 'P'}

    //foo.bar/01.tk 和 //foo.bar/02.tk 的交集都是 //foo.bar/04.tk 和 //foo.bar/05.tk 的真子集，因此它们不符合选择 准则。剩下 //foo.bar/04.tk 或 //foo.bar/05.tk。由于 //foo.bar/04.tk 在补丁映射中 排在前面，因此选择它。

  • 步骤 9：获取选定的补丁 //foo.bar/04.tk。此外，作为一项优化，同时 开始获取两个按字形索引的 补丁 //foo.bar/01.gk 和 //foo.bar/04.gk。按表索引的补丁 //foo.bar/04.tk 会造成部分 失效，这意味着两个按字形索引的补丁 在应用 //foo.bar/04.tk 后仍然有效。因此，客户端可以预期 后续迭代将需要这两个按字形索引的补丁， 并在此时开始加载这两个补丁。

  • 步骤 10：将获取的补丁 //foo.bar/04.tk 应用于初始字体。此补丁更新 除 glyf 和 loca 之外的所有表， 以添加对码点 'a' 至 'Z' 的支持。此外，"IFT " 表中的映射 更新如下：

    表 = "IFT " 兼容性 ID = 0x0000_0000_0000_0006
    子集定义 URL 格式编号 
    code points: { '0', '1', ..., '9' }
    		//foo.bar/08.tk 2，按表索引 - 部分失效

    请注意以下更改：

    • 所有包含 'a'、...、'z' 和 'A'、...、'Z' 数据的条目均已移除，只留下 一个用于剩余 '0'、...、'9' 码点的条目。

    • 字体二进制文件已更改，因此先前列出的按表索引补丁不再 有效。因此，兼容性 ID 已更改， 剩余 '0'、...、'9' 条目的 URL 也已更改。新 URL //foo.bar/08.tk 对应的补丁与更新后的字体兼容。

迭代 2：

  • 步骤 2 至 6：对上一轮迭代更新后的字体中的所有 条目应用检查条目交集，以下补丁 条目相交：

    • //foo.bar/01.gk

    • //foo.bar/04.gk

  • 步骤 8：必须从该集合中选择一个条目。只剩下不会使其他补丁失效的补丁，客户端 可以自由选择其中任意一个。在此示例中，它选择 第一个补丁 //foo.bar/01.gk。

  • 步骤 9：在迭代 1 期间已经开始获取 //foo.bar/01.gk。

  • 步骤 10：将获取的补丁 //foo.bar/01.gk 应用于当前字体子集。此补丁向 glyf 和 loca 表添加码点 'a' 至 'm' 的字形数据。此外，"IFTX" 表中的映射也会更新，以移除 //foo.bar/01.gk 对应的条目。兼容性 ID 和其他条目的 URL 保持不变。

迭代 3：

  • 步骤 2 至 6：对上一轮迭代更新后的字体中的所有 条目应用检查条目交集，以下补丁 条目相交：

    • //foo.bar/04.gk

  • 步骤 8：只剩下一个条目，选择该条目。

  • 步骤 9：在迭代 1 期间已经开始获取 //foo.bar/04.gk。

  • 步骤 10：将获取的补丁 //foo.bar/04.gk 应用于当前字体子集。此补丁向 glyf 和 loca 表添加码点 'N' 至 'Z' 的字形数据。此外，"IFTX" 表中的映射也会更新，以移除 //foo.bar/04.gk 对应的条目。兼容性 ID 和其他条目的 URL 保持不变。

迭代 4：

  • 步骤 2 至 6：不再存在相交的条目，因此算法终止。返回字体 子集，此时它已准备好渲染 目标子集定义覆盖的任何内容。
