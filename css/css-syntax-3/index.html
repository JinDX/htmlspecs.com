摘要

本模块从总体上描述 CSS 样式表的基本结构和语法。它定义了 CSS 的详细语法和解析方式——即如何将字节流转换为有意义的样式表。

CSS 是一种用于描述结构化文档渲染方式的语言 （例如 HTML 和 XML） 用于屏幕、纸张等。

1. 引言

本节不是规范性的。

本模块定义 CSS 样式表的抽象语法和解析 以及其他使用 CSS 语法的内容 （例如 HTML style 属性）。

它定义了用于将 Unicode 代码点流 （换言之，即文本） 转换为 CSS 标记流的算法， 然后进一步转换为 CSS 对象， 例如样式表、规则和声明。

1.1. 模块交互

本模块定义 CSS 样式表的语法和解析。 它取代 CSS 2.1 中定义的词法扫描器和语法。

2. CSS 语法说明

本节不是规范性的。

CSS 文档是一系列样式 规则——它们是将样式应用于文档中元素的限定规则——以及 at-rule——它们为 CSS 文档定义特殊处理 规则或值。

限定规则以 前奏开始 然后具有一个由 {} 包裹、包含一系列声明的块。 前奏的含义会根据规则出现的上下文而变化——对于样式规则，它是一个选择器，用于指定 声明将应用于哪些元素。 每个声明都有一个名称， 后跟冒号和声明值。 声明之间以分号分隔。

典型的规则可能如下所示：

p > a {
  color: blue;
  text-decoration: underline;
}

在上述规则中，"p > a" 是选择器， 如果源文档是 HTML， 它会选择所有 a 元素，这些元素是 p 元素的子元素。

"color: blue" 是一个声明，它指定 对于匹配该选择器的元素， 它们的 color 属性应具有值 blue。 类似地，它们的 text-decoration 属性应具有值 underline。

At-rule 各不相同，但它们具有 共同的基本结构。 它们以 "@" 代码点开始，后跟作为 CSS 关键字的名称。 某些 at-rule 是简单语句， 名称后跟更多 CSS 值以指定其行为， 最后以分号结束。 另一些则是块； 它们可以在名称后跟 CSS 值， 但以一个由 {} 包裹的块结束， 类似于限定规则。 甚至这些块的内容也由给定的 at-rule 决定： 有时它们包含一系列声明，就像限定 规则； 其他时候，它们可能包含其他块、at-rule，或完全不同的其他结构。

下面是几个 at-rule 示例， 用于展示它们可能包含的各种语法。

@import "my-styles.css";

@import at-rule 是一个简单语句。 在其名称之后，它接受单个字符串或 url() 函数 以指示它应导入的样式表。

@page :left {
  margin-left: 4cm;
  margin-right: 3cm;
}

@page at-rule 由可选的页面选择器（:left 伪类）组成， 后跟一个属性块，这些属性会在打印时应用于页面。 因此，它与普通样式规则非常相似， 不同之处在于其属性不应用于任何“元素”， 而是应用于页面本身。

@media print {
  body { font-size: 10pt }
}

@media at-rule 以媒体类型开始 并后跟一个可选媒体查询列表。 其块包含完整的规则， 这些规则仅在 @media 的 条件满足时应用。

属性名称和 at-rule 名称始终是 ident 序列， 它们必须以 ident-start 代码点、两个连字符， 或一个连字符后跟 ident-start 代码点开始， 然后可以包含零个或多个 ident 代码点。 你可以包含任意 代码点， 即使是 CSS 在其语法中使用的代码点， 只要对其进行转义即可。

选择器的语法在选择器规范中定义。 类似地，各种 CSS 值的语法在值与单位规范中定义。 各个 at-rule 的特殊语法可在定义它们的规范中找到。

2.1. 转义

本节不是规范性的。

任何 Unicode 代码点都可以包含在 ident 序列或带引号的字符串中 方法是对其进行转义。 CSS 转义序列以反斜杠 (\) 开始，并继续为：

  • 任何不是代码点中的 十六进制数字或换行符的 Unicode 代码点。 转义序列会被该 代码点替换。
  • 或一个到六个十六进制数字，后跟 一个可选的空白。 转义序列会被 Unicode 代码点替换， 其值由十六进制数字给出。 此可选空白允许十六进制转义序列 后跟“真正的”十六进制数字。

    值为 "&B" 的 ident 序列 可以写成 \26 B 或 \000026B。

    转义序列后的“真正”空格必须写两次。

2.2. 错误处理

本节不是规范性的。

当 CSS 中发生错误时， 解析器会尝试平稳恢复， 仅丢弃最少量的内容， 然后恢复正常解析。 这是因为错误并不总是错误操作——新语法对于旧解析器而言看起来像错误， 而能够向语言添加新语法 而不必担心包含它的样式表在旧 UA 中完全失效是很有用的。

精确的错误恢复行为在解析器本身中有详细说明， 但它足够简单，因此简短描述也相当准确。

  • 在样式表的“顶层”， <at-keyword-token> 会开始一个 at-rule。 其他任何内容都会开始一个限定规则， 并被包含在规则的前奏中。 这可能会产生无效选择器， 但这不是 CSS 解析器所关心的——最坏情况下，这意味着该选择器不会匹配任何内容。
  • 一旦 at-rule 开始， 从解析器的角度看就不存在无效内容； 所有内容都是 at-rule 前奏的一部分。 遇到 <semicolon-token> 会立即结束 at-rule， 而遇到左花括号 <{-token> 则开始 at-rule 的主体。 at-rule 会向前查找，同时匹配块（由 ()、{} 或 [] 包围的内容）， 直到找到一个未与其他任何内容匹配 且不位于另一个块内的右花括号 <}-token>。 然后根据 at-rule 自身的语法解释其内容。
  • 限定规则的工作方式类似， 但分号不会结束它们； 相反，分号只会作为规则前奏的一部分被接收。 找到第一个 {} 块时， 其内容始终会被解释为声明列表。
  • 解释声明列表时， 任何位置出现未知语法都会导致解析器丢弃当前正在 构建的声明， 并向前查找直到找到分号（或块的结尾）。 然后它会重新开始，再次尝试解析声明。
  • 如果样式表结束时仍有任何规则、声明、函数、字符串等处于打开状态， 所有内容都会自动闭合。 这不会使它们无效， 尽管它们可能不完整， 因而在根据其语法进行验证时被丢弃。
    例如，translateX() 函数的语法是： 
    translateX( <translation-value> )

    但是，样式表可能在函数尚未闭合时结束，例如：

    .foo { transform: translate(50px

    CSS 解析器会将其解析为包含一个声明的样式规则， 其值是一个名为 "translate" 的函数。 这与上述语法匹配， 即使结束标记没有出现在标记流中， 因为当解析器完成时， 已无法再确定结束标记是否存在； 你所拥有的只是存在一个块和一个函数这一事实。

解析每个构造（声明、样式规则、at-rule）之后， 用户代理会根据其预期语法对其进行检查。 如果它不匹配该语法， 则它是无效的， 并会被 UA 忽略， UA 会将其视为完全不存在。

3. CSS 的标记化和解析

用户代理必须使用本规范中描述的解析规则 从 text/css 资源生成 [CSSOM] 树。 这些规则共同定义了所谓的 CSS 解析器。

本规范定义 CSS 文档的解析规则， 无论它们在语法上是否正确。 解析算法中的某些位置被称为解析错误。 解析错误的错误处理有明确的定义： 用户代理在遇到此类问题时必须按照下文描述采取行动， 或者必须在遇到其不希望应用下述 规则的第一个错误时中止处理。

如果文档中存在一个或多个解析错误条件， 一致性检查器必须向用户报告至少一个解析错误条件， 并且如果文档中不存在解析错误条件， 则不得报告解析错误条件。 如果存在多个解析错误条件，一致性检查器可以报告多个解析错误条件。 一致性检查器不要求从解析错误中恢复， 但如果进行恢复， 则必须以与用户代理相同的方式恢复。

3.1. 解析模型概述

CSS 解析过程的输入由 Unicode 代码点流组成， 它先经过标记化阶段，然后经过树构建阶段。 输出是一个 CSSStyleSheet 对象。

注：不支持脚本的实现 不必实际创建 CSSOM CSSStyleSheet 对象， 但在这种情况下，CSSOM 树仍会被用作规范其余部分的模型。

3.2. 输入字节流

解析样式表时， 构成标记化阶段输入的 Unicode 代码点流 最初可能被用户代理视为字节流 （通常来自网络或本地文件系统）。 如果是这样，用户代理必须根据特定的字符编码 将这些字节解码为 代码点。

要将 stylesheet 的字节流解码为代码 点流：

  1. 确定回退编码 stylesheet 的， 并令 fallback 为结果。

  2. 使用回退编码 fallback 解码 stylesheet 的字节流， 并返回结果。

注：解码算法 优先采用字节顺序标记（BOM）， 只有在未找到 BOM 时才使用回退编码。

要确定 回退编码一个 stylesheet 的：
  1. 如果 HTTP 或等效协议为 stylesheet 提供了编码标签（例如通过 Content-Type 标头的 charset 参数）， 则从 encoding label 获取编码。 如果该操作未返回失败， 则返回它。
  2. 否则，检查 stylesheet 的字节流。 如果该流的前 1024 个字节以如下十六进制序列开头： 
    40 63 68 61 72 73 65 74 20 22 XX* 22 3B

    其中每个 XX 字节都是介于 016 和 2116（含）之间的值 或介于 2316 和 7F16（含）之间的值， 则获取编码 从由 XX 字节序列组成的字符串， 并将其解释为 ASCII。

    该字节序列是什么意思？

    上述字节序列 按 ASCII 解码时， 是字符串 "@charset "…";"， 其中 "…" 是与编码标签相对应的字节序列。

    如果返回值为 utf-16be 或 utf-16le， 则返回 utf-8； 如果它不是失败的其他任何值， 则返回它。

    为什么声明为 utf-16 时使用 utf-8？

    编码声明的字节在 ASCII 中拼写为“@charset "…";”， 但 UTF-16 与 ASCII 不兼容。 要么你输入了完全乱码的内容（例如 䁣桡牳整•utf-16be∻）以获得文档中 正确的字节， 而我们不希望鼓励这种做法， 要么你的文档实际上采用与 ASCII 兼容的编码， 而你的编码声明是在撒谎。

    无论哪种情况，默认使用 UTF-8 都是一个合理的答案。

    此外，这也模仿了 HTML 的 <meta charset> 属性的行为。

    注：请注意，编码 声明的语法看起来像一个名为 at-rule 的 @charset， 但实际上并不存在这样的规则， 而且其书写规则比通常用于 识别这种规则的规则严格得多。 你可以在 CSS 中执行的许多操作，如果确实存在这样的规则，会产生有效的 @charset 规则， 例如使用多个空格、注释或单引号， 都会导致编码声明无法被识别。 此行为使编码声明尽可能简单， 从而最大程度提高其被正确实现的可能性。

  3. 否则，如果引用 文档提供了环境编码， 则返回它。
  4. 否则，返回 utf-8。

尽管 UTF-8 是 Web 的默认编码， 并且许多较新的基于 Web 的文件格式假定或要求使用 UTF-8 编码， 但 CSS 创建于尚不清楚哪种编码最终会占据主导地位的时期， 因此不能自动假定样式表采用 UTF-8。

样式表作者应该使用 UTF-8 编写其样式表， 并确保 HTTP 标头（或等效方法）声明样式表的编码 为 UTF-8， 或者引用文档声明其编码为 UTF-8。 （在 HTML 中，这通过向 head 添加 <meta charset=utf-8> 元素 来完成。）

如果这些选项均不可用， 作者应以 UTF-8 BOM 开始样式表 或以下确切字符

@charset "utf-8";

引用从字节解码的 CSS 样式表的文档语言 可以为每个此类样式表定义环境 编码， 当其他编码提示不可用或无法使用时，将其用作回退编码。

环境编码这一概念仅为与旧版 内容兼容而存在。 新格式和新的链接机制不应该提供环境编码， 这样在缺少更明确的信息时，样式表就会改为默认使用 UTF-8。

注：[CSSOM] 定义了<xml-stylesheet?> 的 环境编码。

3.3. 预处理输入流

输入流由 随输入字节流被解码而推入其中的经过筛选的 代码点 组成。

  • 将 input 中所有 U+000D CARRIAGE RETURN (CR) 代码点、 U+000C FORM FEED (FF) 代码点， 或由 U+000D CARRIAGE RETURN (CR) 后跟 U+000A LINE FEED (LF) 组成的序列 替换为单个 U+000A LINE FEED (LF) 代码点。

4. 标记化

要将代码点流 input 标记化为 CSS 标记流， 重复从 input 中消费一个标记 直到遇到 <EOF-token>， 将每个返回的标记推入一个流中。

注：每次调用消费一个标记算法 都会返回单个标记， 因此它也可以“按需”用于标记化代码点流， 即在解析期间， 如果需要的话。

标记化步骤的输出是由以下零个或多个标记组成的流： <ident-token>、 <function-token>、 <at-keyword-token>、 <hash-token>、 <string-token>、 <bad-string-token>、 <url-token>、 <bad-url-token>、 <delim-token>、 <number-token>、 <percentage-token>、 <dimension-token>、 <unicode-range-token>、 <whitespace-token>、 <CDO-token>、 <CDC-token>、 <colon-token>、 <semicolon-token>、 <comma-token>、 <[-token>、 <]-token>、 <(-token>、 <)-token>、 <{-token>， 以及 <}-token>。

  • <ident-token>、<function-token>、<at-keyword-token>、<hash-token>、<string-token>，以及 <url-token> 都具有由零个或多个代码 点组成的值。 此外，hash 标记还有一个类型标志，其值设置为 "id" 或 "unrestricted"。若未另行设置，则类型标志默认为 "unrestricted"。
  • <delim-token> 具有由单个代码 点组成的值。
  • <number-token>、<percentage-token> 和 <dimension-token> 具有数值， 以及一个可选的符号字符， 设置为 "+"、"-" 或不存在。

    <number-token> 和 <dimension-token> 还具有一个类型标志，设置 为 "integer" 或 "number"。如果未另行设置，则类型标志默认为 "integer"。 <dimension-token> 还具有由一个或多个代码点组成的单位。

  • <unicode-range-token> 具有起始和结束代码 点。 它表示一个包含端点的代码点范围 （包括起始点和结束点）。 如果结束代码点位于起始代码点之前， 则它表示空范围。

注：hash 标记的类型标志用于 选择器语法 [SELECT]。 只有类型为 "id" 的 hash 标记才是有效的 ID 选择器。

标记 流是一个结构， 表示标记和/或组件值的流。 它具有以下项：

标记

CSS 中有少数位置 需要引用 为声明值解析的精确文本 （而不只是从该文本产生了哪些标记）。 这里的算法结构没有显式描述这一点， 但标记流 因此必须 能够按需重现声明的原始文本。 有关何时需要这样做的详细信息，请参阅消费一个 声明 。

下一个标记

标记中位于索引处的项。

空

消费一个标记

令 token 为下一个标记。 将索引加一， 然后返回 token。

丢弃一个标记

  • “解析 样式表”旨在作为普通解析器入口点， 用于解析样式表。
  • “解析样式表内容”旨在供 CSSStyleSheet replace() 方法 及类似方法使用， 这些方法将文本解析为 现有样式表的内容。
  • “解析规则”旨在 供 CSSStyleSheet insertRule() 方法 及类似方法使用， 这些方法将文本解析为单个规则。 CSSStyleSheet#insertRule 方法 以及可能存在的类似函数， 都将文本解析为单个规则。

  • “解析 块的内容”旨在用于解析 CSS 中任何块的内容 （包括 style 属性之类的内容）， 以及诸如 CSSStyleDeclaration cssText 属性之类的 API。

  • “解析组件值列表”用于 表现属性的内容， 这些内容将文本解析为单个声明的值， 或用于解析独立选择器 [SELECT] 或媒体查询列表 [MEDIAQ]， 例如在选择器 API 或 media HTML 属性中。

5.4.1. 根据 CSS 语法解析某内容

通常需要解析字符串或标记列表 以查看它是否匹配某个 CSS 语法， 如果匹配， 则根据该语法将其解构。 本节为此类操作提供一个通用钩子。 它应以类似如下方式调用： “将 foo 解析为 CSS <color>”，或类似方式。

如果输入不匹配提供的语法， 此算法返回失败， 否则返回根据该语法解析输入的结果， 这是与所提供语法规范相对应的未指定结构。 返回值只能由规范文本进行交互， 在这种情况下，表示形式的歧义不会造成问题。 如果其目的是在规范语言之外公开， 使用结果的规范必须明确将其转换为明确定义的表示形式， 例如通过调用 CSS 序列化算法 （例如“序列化为 CSS <string> 值”）。

注：此算法 以及根据 CSS 语法解析逗号分隔列表 通常是其他规范唯一想要调用的解析算法。 其余解析算法主要用于 [CSSOM] 以及相关的“显式构造 CSS 结构”情况。 如果你认为需要使用其他算法之一， 请先向 CSSWG 咨询指导。

给定 input 和一个 CSS grammar 产生式，要根据 CSS 语法解析某内容 （也简称为解析） ：
  1. 规范化 input， 并将 input 设置为结果。
  2. 从 input 解析组件值列表， 并令 result 为返回值。
  3. 尝试将 result 与 grammar 匹配。 如果成功， 返回匹配结果； 否则，返回失败。

5.4.2. 根据 CSS 语法解析逗号分隔列表

当然可以根据包含逗号的语法 解析一个值， 但如果值的任何部分解析失败， 整个内容都会解析失败， 并返回失败。

有时这正是所需行为 （例如在列表值 CSS 属性中）； 但在其他时候， 最好让值中每个逗号分隔的子部分单独解析， 对成功解析的部分采用一种处理方式， 对解析失败的部分采用另一种处理方式 （通常忽略它们， 例如在 <img sizes> 中）。

此算法提供了一个简单的钩子来实现这一点。 它返回一个由“顶层”逗号分割的值列表， 其中每个值要么是失败 （如果解析失败） 要么是解析结果 （一种未指定结构， 如解析算法中所述）。

给定 input 和一个 CSS grammar 产生式，要根据 CSS 语法解析逗号分隔列表 （也称为解析列表） ：
  1. 规范化 input， 并将 input 设置为结果。
  2. 如果 input 仅包含 <whitespace-token>， 则返回一个空列表。
  3. 从 input 解析逗号分隔的组件值 列表， 并令 list 为返回值。
  4. 对 list 中的每个 item， 将 item 替换为 使用 grammar 解析 item 的结果。
  5. 返回 list。

5.4.3. 解析样式表

给定可选的 url location，要从 input 解析样式表：
  1. 如果 input 是样式表的字节流， 则从 input 解码字节， 并将 input 设置为结果。
  2. 规范化 input， 并将 input 设置为结果。
  3. 创建一个新的样式表， 将其位置设置为 location （如果未传入 location，则为 null）。
  4. 从 input 消费样式表内容， 并将样式表的规则设置为结果。
  5. 返回样式表。

5.4.4. 解析样式表内容

要从 input 解析 样式表内容：
  1. 规范化 input， 并将 input 设置为结果。
  2. 从 input 消费样式表内容， 并返回结果。

声明和限定规则 在允许的语法中通常不会重叠。 当前定义的 CSS 属性都不允许其值中包含 {}-block， 因此 foo:bar {}; 肯定是规则， 而 foo: bar; 肯定是属性。 即使未来某个 CSS 属性允许其值中包含 {}-block， 所允许的语法也会限制为 {}-block 构成整个值， 例如 foo: {...};， 它保证不会是有效规则， 因为 : 后面没有 ident 或函数 来将其标记为伪类。

这使我们能够在同一上下文中混合声明和规则： 我们首先尝试将某内容解析为声明， 如果这样不能得到有效声明， 则改为重新将其解析为规则。 意外无效的声明会改为解析成规则， 但这没有问题： 解析器会在声明的结束分号处停止 并将其视为无效规则。 （或者，如果属性包含 {}-block， 会在分号*之前*停止， 仍将其视为无效规则， 然后下一次尝试解析某内容时 会将孤立的分号作为无效内容丢弃。） 因此，无论哪种情况，消费的标记总量都相同。

然而，自定义属性并没有 CSSWG 仔细审查其语法。 作者可以编写一个自定义属性， 其值接受 {}-block， 甚至与其他内容组合； 如果该自定义属性随后无效 （例如由于错误编写的 var() 函数）， 当它被重新解析为规则时 会在 {}-block 处提前停止。 自定义属性值中剩余的标记 随后会作为新的构造进行解析， 可能导致意外的声明或规则 被创建。

为了避免这种（诚然非常边缘的）情况， 我们从自定义属性的语法 中减去限定规则的语法； 如果你处于允许属性和规则混合的上下文中， 并且不知何故最终解析出一个 看起来像自定义属性的规则， 那就说明你弄错了， 应改为消费整个自定义属性 （一直到结束分号）。

（如果我们处于不允许属性的上下文中， 那么如果规则看起来像自定义属性， 我们就直接丢弃该规则。 这确保 --foo:hover { color: blue; } 在任何地方都始终无效， 而不会为了寻找不存在的结束分号 而可能消费样式表的大量内容。）

实现注释

本规范与许多 CSS 规范一样， 编写时优先考虑可理解性 而不是效率。 许多算法， 尤其是上述“先解析为声明，再解析为规则”的行为， 如果按描述直接实现， 可能相当低效。

不过，该行为经过精心编写， 以尽可能允许“提前退出”。 特别是， 大致按可能发生退出的顺序：

  • 如果第一个非空白标记 不是已识别属性名称（或自定义属性名称）的 <ident-token>， 你可以立即停止将其解析为声明 而改为重新解析为规则。 如果下一个非空白标记不是 <colon-token>， 同样可以立即停止将其解析为声明。

    （也就是说，font+ ... 保证不是属性， not-a-prop-name: ... 也不是。）

  • 如果前两个非空白标记 是自定义属性名称和冒号， 那么它肯定是自定义属性， 永远不会产生有效规则， 因此即使该自定义属性最终无效， 也无需尝试重新将其解析为规则。

    （也就是说，--foo:hover {...} 保证是自定义属性， 而不是规则。）

  • 如果前三个非空白标记 是有效属性名称、冒号以及除 <{-token> 之外的任何内容， 然后在解析声明值时遇到一个 <{-token>， 你可以立即停止将其解析为声明 而改为重新解析为规则。

    （也就是说，font:bar {... 保证是无效属性。）

  • 如果看到已识别的属性名称、冒号和一个 {}-block， 但该块之后的第一个非空白标记 既不是紧接着的最终分号， 也不是 !important 后跟分号， 你可以立即停止将其解析为声明 而改为重新解析为规则。

    （也就是说，font: {} bar ... 保证是无效属性； 无需继续解析直到遇到分号。）

类似地， 即使解析要求被指定为 在解析过程中依赖于检查声明的语法， 一个通用处理器 若尝试在通用 CSS 语法之上 实现非 CSS 语言， 仍然只需验证声明 是否以 ident、冒号开头， 然后要么仅包含一个 {}-block， 要么完全不包含 {}-block。 在类似 foo:hover ... {} 的情况下， 它们只会比了解语法的实现 多花一点解析时间， 因为它们无法在第一个标记处提前退出。

6. An+B 微语法

CSS 中有若干内容， 例如 :nth-child() 伪类， 需要指示列表中的索引。 An+B 微语法对此很有用， 它允许作者轻松指示单个元素 或列表中以固定间隔出现的所有元素。

An+B 表示法定义一个整数 步长（A）和偏移量（B）， 并表示列表中的第 An+B 个元素， 对于 n 的每个正整数或零值， 列表中的第一个元素的索引为 1（而不是 0）。

对于大于 0 的 A 和 B 值， 这实际上会将列表划分为每组 A 个元素 （最后一组包含余数）， 并选择每组中的第 B 个元素。

An+B 表示法还接受 even 和 odd 关键字， 它们分别与 2n 和 2n+1 具有相同含义。

示例： 

2n+0   /* 表示列表中的所有偶数序号元素 */
even   /* 相同 */
4n+1   /* 表示列表中的第 1、5、9、13 等个元素 */

A 和 B 的值可以为负数， 但只使用 An+B 的正数结果， 对于 n ≥ 0， 。

示例： 

-1n+6   /* 表示列表中的前 6 个元素 */
-4n+10  /* 表示列表中的第 2、6 和 10 个元素 */

7.1. 定义块内容：<block-contents>、<declaration-list>、<qualified-rule-list>、<declaration-rule-list> 和 <rule-list> 产生式

CSS 解析器并不关心块的内容——它们都使用相同的 算法进行解析， 并且仅通过哪些构造有效来彼此区分。

编写规则语法时， <block-contents> 表示这种不区分内容的解析。 它只能作为块中的唯一值使用， 并表示不会隐式施加任何限制 来约束块中可以包含的内容。

随附的规范文本必须定义在此上下文中哪些内容有效、哪些无效。 如果任何声明有效， 并且是属性声明， 则必须定义它们是否与层叠交互； 如果交互，则必须定义其优先级 以及它们如何使用 !important。

然而，在许多情况下， 一个块无法有效包含给定类型的任何构造。 为了更明确地表示这些情况， 可以使用以下产生式

  • <declaration-list>： 只允许声明； at-rule 和限定规则 自动无效。

  • <qualified-rule-list>： 只允许限定 规则； 声明和at-rule自动 无效。

  • <at-rule-list>： 只允许at-rule； 声明和限定规则 自动无效。

  • <declaration-rule-list>： 允许声明和at-rule； 限定规则 自动无效。

  • <rule-list>： 允许限定规则和 at-rule； 声明 自动无效。

就解析而言，所有这些都与 <block-contents> 完全等价， 但随附的规范文本只需为 不会自动无效的类别定义有效性。

以下是各种产生式的一些示例：

  • 顶层 @media 的块使用 <rule-list>， 而嵌套的 [CSS-NESTING-1] 使用 <block-contents>。

  • 样式规则使用 <block-contents>。

  • @font-face 使用 <declaration-list>。

  • @page 使用 <declaration-rule-list>。

  • @keyframes 使用 <qualified-rule-list>

例如，@font-face 的语法可以写为： 
<@font-face> = @font-face { <declaration-list> }

然后随附的规范文本定义块中允许的有效描述符 。

@keyframes 的语法可以写为：

<@keyframes> = @keyframes { <qualified-rule-list> }
<keyframe-rule> = <keyframe-selector> { <declaration-list> }

然后随附的规范文本定义只有 <keyframe-rule> 才允许出现在 @keyframes 中， 并且 <keyframe-rule> 接受所有可动画的 CSS 属性， 以及 animation-timing-function 属性， 但它们不参与层叠。

7.2. 定义任意内容：<declaration-value> 和 <any-value> 产生式

在某些语法中， 允许语法接受任何合理的输入很有用， 然后手动对内容执行更具体的错误处理 （而不是简单地使构造无效， 因为语法不匹配通常会这样做）。

例如，自定义 属性允许任何合理的值， 因为它们可以包含其他 CSS 属性的任意片段， 或用于完全不属于现有 CSS 的内容。 再例如，媒体查询中的 <general-enclosed> 产生式 定义未来 MQ 语法所允许内容的边界， 并使用特殊逻辑来处理“未知”值。

为此，定义了两个额外的产生式：

<declaration-value> 产生式匹配由 一个或多个标记组成的任何序列， 只要该序列不包含 <bad-string-token>、 <bad-url-token>、 不匹配的 <)-token>、<]-token> 或 <}-token>， 或顶层 <semicolon-token> 标记，或值为 "!" 的 <delim-token> 标记。 它表示有效声明的值可以包含的全部内容。

<any-value> 产生式与 <declaration-value> 相同， 但还允许顶层 <semicolon-token> 标记 和值为 "!" 的 <delim-token> 标记。 它表示在任何上下文中有效 CSS 可以包含的全部内容。

8. CSS 样式表

要解析 CSS 样式表， 首先解析 样式表。 将所有所得的顶层限定规则解释为下文定义的样式规则。

如果任何样式规则无效， 或任何 at-rule 无法识别，或根据其语法或上下文无效， 则这是一个解析错误。 丢弃该规则。

8.1. 样式规则

样式规则是一个限定规则， 它将一个选择器列表 与一个属性声明列表 以及可能的一个嵌套规则列表相关联。 它们在 [CSS2] 中也称为 规则集。 CSS 层叠与继承 [CSS-CASCADE-3] 定义样式规则中的声明如何 参与层叠。

限定规则的前奏会被解析 为 <selector-list>。 如果返回失败， 则整个样式规则无效。

限定规则的块内容被解析为 <declaration-list>。 此块中的限定规则也是样式规则。 除非其他规范或本规范的未来级别另有定义， 该列表中的 at-rule 无效 并且必须被忽略。

注：[CSS-NESTING-1] 定义条件分组规则 和一些其他at-rule 允许出现在样式规则内部。

未知 CSS 属性的声明 或其值不匹配该属性定义语法的声明无效 并且必须被忽略。 样式规则内容的有效性不会影响样式规则本身的有效性。 除非另有规定，属性名称进行 ASCII 大小写不敏感匹配。

注：自定义属性 [CSS-VARIABLES] 的名称 区分大小写。

CSS 样式表顶层的限定规则是样式 规则。 其他上下文中的限定规则可能是，也可能不是样式规则， 具体由上下文定义。

例如，@media 规则 [CSS3-CONDITIONAL] 内的限定规则是 样式规则， 但 @keyframes 规则 [CSS3-ANIMATIONS] 内的限定规则不是。

8.2. At-rule

at-rule 是一个以 at-keyword 开始的规则， 因此可以将它与同一上下文中的样式 规则区分开来。

At-rule 用于：

  • 对样式规则和其他 at-rule 进行分组和结构化， 例如在条件分组规则中

  • 声明不与特定元素关联的样式信息， 例如定义计数器样式

  • 管理语法构造， 例如导入和命名空间关键字映射

  • 以及服务于样式规则无法满足的其他各种用途

At-rule 有多种形式，具体取决于特定规则及其用途， 但大体上分为两种： 语句 at-rule ，它们是以分号结束的较简单构造， 以及 块 at-rule ，它们以 {}-block 结束， 其中可以包含嵌套的限定规则、at-rule 或声明。

块 at-rule通常 包含一组 （通用或特定于 at-rule 的） at-rule、限定规则和/或描述符声明， 并受该 at-rule 定义的限制约束。 描述符类似于属性 （并使用相同语法声明）， 但与特定类型的 at-rule 相关联， 而不是与树中的元素和框相关联。

9. 序列化

本规范中描述的标记器不会为注释生成标记， 也不会以其他方式保留它们。 实现可以保留注释内容及其在标记流中的位置。 如果这样做，这些保留的信息不得对解析步骤产生任何影响。

本规范不定义通常如何序列化 CSS， 而是将该任务留给 [CSSOM] 和各个特性规范。 特别是，注释和空白的序列化方式未定义。

序列化的唯一要求是它必须能够与解析“往返”， 即解析样式表必须产生与 解析、序列化并再次解析相同的数据结构， 连续的 <whitespace-token> 除外， 它们可以折叠为单个标记。

注：此例外之所以可行，是因为 CSS 语法始终将任意数量的空白解释为与单个空格相同。

为满足此要求：
  • 包含 U+005C REVERSE SOLIDUS (\) 的 <delim-token> 必须序列化为 U+005C REVERSE SOLIDUS 后跟一个换行符。 （标记器只会发出这样的标记，且其后跟随一个 <whitespace-token> ，该标记以换行符开头。）
  • 类型标志为 "unrestricted" 的 <hash-token> 可能不 需要像类型标志为 "id" 的相同标记那样多的转义。
  • <dimension-token> 的单位可能需要转义， 以消除与科学计数法的歧义。
  • 对于任意一对连续标记， 如果第一个标记出现在下表的行标题中， 第二个标记出现在列标题中， 且所选行和列交叉对应的单元格中有 ✗， 则这对标记必须在它们之间插入注释后进行序列化。

12.6. 自 CSS 2.1 和选择器第 3 级以来的更改

注：本规范的目标是与现实相符； 相较 CSS2.1 的更改几乎总是因为 CSS 2.1 指定的内容与实际浏览器 行为不符， 或者遗漏了某些规定。 如果某些细节与浏览器不符， 请告诉我， 因为这几乎肯定不是有意为之。

从字节流解码方面的更改：

  • 仅在与 ASCII 兼容的字节模式中检测 @charset 规则。
  • 忽略指定与 ASCII 不兼容编码的 @charset 规则， 因为这会导致规则本身无法正确解码。
  • 字符编码改为引用 [ENCODING] 而不是 IANA 注册表。

标记化更改：

  • CSS 源中的任何 U+0000 NULL 代码点都会替换为 U+FFFD REPLACEMENT CHARACTER。
  • 任何求值结果为零的十六进制转义序列，例如 \0， 都会产生 U+FFFD REPLACEMENT CHARACTER，而不是 U+0000 NULL。
  • 非 ASCII ident 代码点的定义已更改， 以与 HTML 的有效自定义元素名称保持一致。
  • 标记化不再发出 COMMENT 或 BAD_COMMENT 标记。 BAD_COMMENT 现在被视为与普通标记相同（不是错误）。 序列化负责 根据需要在必须分隔的标记之间插入注释， 例如两个连续的 <ident-token>。
  • <unicode-range-token> 已被移除， 因为它价值较低，并且偶尔会造成实际危害。 （例如，u+a { font-weight: bold; } 是无效选择器……）

    作为替代，添加了基于标记模式的 <urange> 产生式 。 从技术上说，它比 2.1 所允许的更宽松 （允许任意数量的数字和 ? 字符）， 但不会以任何方式影响其实际使用。

  • 在标记器中应用 EOF 错误处理规则 ， 并发出普通的 <string-token> 和 <url-token> ，而不是 BAD_STRING 或 BAD_URI ， 当遇到 EOF 时。
  • BAD_URI 标记（现为 <bad-url-token>）是“自包含的”。 换言之，一旦标记器意识到它处于 <bad-url-token> 而不是 <url-token> 中， 它只会向前查找结束的 )， 并忽略其他所有内容。 这种行为比将其视为 <function-token> 并关注已打开的块等内容更简单。 只有 WebKit 表现出这种行为， 但似乎没有因此产生任何兼容性错误。
  • 已添加 <comma-token>。
  • <number-token>、<percentage-token> 和 <dimension-token> 已更改， 以将前面的 +/- 符号包含为其值的一部分 （而不是作为单独的 <delim-token>，每次在其他规范中 提及该标记时都需要手动处理）。 唯一后果是，现在无法再在符号和数字之间插入注释。
  • 数字/百分比/维度支持科学计数法，以匹配 SVG， 根据 WG 决议。
  • 代理项的十六进制转义现在会发出替换字符，而不是代理项。 这使实现能够安全地在内部使用 UTF-16。

解析更改：

  • 任何声明列表现在也接受 at-rule，例如 @page， 根据 WG 决议。 即使尚未定义此类 at-rule， 这也会对错误处理产生影响： 无论 at-rule 有效与否，它都会在不带 <semicolon-token> 的 {} 块处结束， 并允许下一个声明开始。
  • 对语法中各处出现的一些杂项“特殊”标记 （例如不匹配的 <}-token>） 的处理 已指定为至少一个浏览器所表现出的某种合理行为。 此前，在这些位置带有这些标记的样式表根本不匹配样式表语法， ， 因此其处理完全未定义。 具体而言：
    • [] 块、() 块和函数现在可以包含 {} 块、<at-keyword-token> 或 <semicolon-token>
    • 限定规则前奏现在可以包含分号
    • 限定规则和 at-rule 前奏现在可以包含 <at-keyword-token>

An+B 相较选择器第 3 级 [SELECT] 的更改：

  • An+B 微语法现在已正式根据 CSS 标记定义， 而不是使用单独的标记器。 这导致了一些细微差异：
    • 在某些情况下，减号或数字可以被转义 （当它们作为 <dimension-token> 的单位或 <ident-token> 的一部分出现时）。

    一致性类别

    本规范的一致性 针对三种一致性类别定义：

    样式表
    一个 CSS 样式表。
    渲染器
    一个 UA ，它解释样式表的语义并渲染 使用这些样式表的文档。
    创作工具
    一个 UA ，它编写样式表。

    如果样式表中所有使用本模块所定义语法的语句 根据通用 CSS 语法以及每个 本模块中定义的特性的独立语法均有效， 则该样式表符合本规范。

    如果渲染器除按照 相应规范定义的方式解释样式表外，还支持本规范定义的所有特性， 并正确解析它们 且相应地渲染文档，则该渲染器符合本规范。但是， UA 因设备限制而无法正确渲染文档 并不会使该 UA 不符合规范。（例如，UA 无需在单色显示器上渲染颜色。）

    如果创作工具编写的样式表 根据通用 CSS 语法以及每个特性的独立语法 在本模块中均语法正确，并满足样式表的所有其他一致性要求 ，如本模块所述， 则该创作工具符合本规范。

    部分实现

    为了使作者能够利用向前兼容的解析规则 指定回退值，CSS 渲染器必须 将其没有可用支持级别的任何 at-rule、属性、属性值、关键字 和其他语法构造视为无效（并按适当方式 忽略）。特别是，用户代理不得选择性地 忽略不支持的组件值并接受单个 多值属性声明中的受支持值：如果任何值被视为无效 （不支持的值必须如此），CSS 要求忽略整个声明。

    不稳定和专有特性的实现

    为了避免与未来稳定的 CSS 特性发生冲突， CSSWG 建议对 CSS 的实现遵循最佳实践，以处理 不稳定特性和专有扩展。

    非实验性实现

    规范达到候选推荐标准阶段后， 即可进行非实验性实现，实现者应该 发布其能够证明根据规范正确实现的任何 CR 级特性的 无前缀实现。

    为了建立并维护 CSS 在各实现之间的互操作性， CSS 工作组要求非实验性 CSS 渲染器在发布任何 CSS 特性的无前缀实现之前， 向 W3C 提交实现报告（如有必要，还包括 该实现报告所使用的测试用例）。提交给 W3C 的测试用例 须由 CSS 工作组审查和修正。

    有关提交测试用例和实现报告的更多信息 可在 CSS 工作组的网站上找到： https://www.w3.org/Style/CSS/Test/。 问题应发送至 public-css-testsuite@w3.org 邮件列表。

    CR 退出标准

    要使本规范进入提议推荐标准阶段， 每项特性必须至少有两个独立且可互操作的实现。 每项特性可以由不同的一组产品实现， 不要求所有特性都由 单个产品实现。就此标准而言，我们定义 以下术语：

    独立
    每个实现必须由 不同的主体开发，并且不得共享、重用或派生自 另一个符合条件的实现所使用的代码。与 本规范实现无关的代码部分 不受此要求约束。
    可互操作
    通过 官方 CSS 测试套件中的相应测试用例；或者，如果实现不是 Web 浏览器，则通过等效测试。测试中的每个相关测试 套件都应创建等效测试，如果这样的用户 代理（UA）将被用于声称互操作性。此外， 如果要使用这样的 UA 声称互操作性，则 必须有一个或多个其他 UA 也能通过这些 等效测试，并以相同方式用于 互操作性。等效测试必须公开 提供，以供同行评审。
    实现
    符合以下条件的用户代理：
    1. 实现本规范。
    2. 向公众开放。该实现可以 是正式发布的产品或其他公开可用的版本 （即 beta 版本、预览版或“nightly build”）。 非正式发布的产品版本必须已经实现 相关特性至少一个月，以 证明稳定性。
    3. 不是实验性的（即不是专门设计 用于通过测试套件且不打算 在未来用于正常使用的版本）。

    本规范将保持候选推荐标准状态至少 六个月。
