摘要

本规范基于已广泛部署的 WOFF 1.0 的经验， 旨在提高压缩率， 从而降低网络带宽使用量，同时仍能 在移动设备上快速解压。其实现方式 是结合感知内容的预处理步骤 与改进的熵编码，优于 WOFF 1.0 使用的 Flate 压缩。

1. 引言

本文档规定 WOFF2 字体封装格式。该格式旨在 以相对容易实现的方式压缩字体数据， 并获得显著优于以往技术的压缩率，适用于 CSS @font-face 规则。相比此前开发的 WOFF 1.0 格式 [WOFF1]，压缩率的提高 得益于改进的熵编码，以及字体数据的预处理和 优化步骤，这些步骤减少了各种字体数据结构中的固有冗余。 WOFF 2.0 开发历史的详细信息见 WOFF 2.0 评估报告 [WOFF2ER]。

2. 一般要求

WOFF2 格式的主要目的是高效封装通过 CSS @font-face 规则链接到 Web 文档的字体。支持 WOFF2 链接字体文件格式的用户代理必须遵守 CSS3 Fonts 规范的要求 （[CSS3-Fonts] 第 4.1 节：@font-face 规则）。特别是， 此类链接字体 仅可供引用它们的文档使用；不得 供用户系统上的其他应用程序或文档使用。

输入字体文件可包含多种字体数据表，这些表描述于 [OFF] 规范第 5 章。字体文件中 表的顺序可能不同，虽然表目录中的条目 必须按标签升序排列，但实际的表可以在字体文件中 以任意顺序存放。

解压 WOFF2 文件时，解码器必须将表目录中的条目 按表标签的字母升序排列，并且应按照 [OFF] 的建议（第 8.1 小节“优化表顺序”） 安排字体文件中的表顺序。

3. 整体文件结构与基本数据类型

WOFF2 文件的结构与 SFNT 和 WOFF 1.0 字体文件类似， 即文件头后是表目录，再后是这些表的 数据。SFNT 结构的完整说明见 TrueType [TrueType]、OpenType [OpenType] 和 ISO“开放字体格式” [OFF] 规范。不过， WOFF2 在一些重要方面与 SFNT 不同。最显著的是， 所有字体表的数据被压缩在包含全部字体表的单一数据流中。 与 WOFF 1.0 类似，可选的扩展元数据块和私有数据块分别 作为独立数据块表示，并拼接成 WOFF 2.0 文件。 压缩字体数据流和扩展元数据块使用的 压缩算法均为 Brotli [Brotli]。

完整的 WOFF2 文件由多个数据块组成：48 字节的文件头，其后立即 依次跟随可变大小的表目录、可选的集合 目录（仅当输入字体文件为字体集合时存在）、压缩字体数据块、 可选的扩展元数据块，以及可选的私有数据块。除了 在规定表长度或块偏移按 4 字节对齐的位置 填充至多三个零字节外， 数据块之间、 WOFF2 文件头与表目录之间，或最后一个 数据块或表之后，不得有任何无关数据。 如果存在此类无关数据， 符合规范的用户代理必须将该文件作为无效文件拒绝。此外， 如果任何数据块或字体表的偏移和长度 指示文件中重叠的字节范围， 或超出文件末尾的范围，也必须将该文件作为无效文件拒绝。

255UInt16 数据类型

255UInt16 是范围为 0 到 65535（含两端）的 无符号整数的变长编码。此数据类型旨在作为各种 字体值的中间表示；这些值通常以 UInt16 表示， 但实际数值较小。根据编码值的不同， 数据字段长度可为一到三个字节，其中第一个字节的值 要么表示较小数值本身，要么作为代码，定义 附加字节的格式。下方的类 C 伪代码描述了 如何读取 255UInt16 格式：

    Read255UShort( data )
    {
        UInt8 code;
        UInt16 value, value2;

        const oneMoreByteCode1    = 255;
        const oneMoreByteCode2    = 254;
        const wordCode            = 253;
        const lowestUCode         = 253;

        code = data.getNextUInt8();
        if ( code == wordCode ) {
            /* Read two more bytes and concatenate them to form UInt16 value*/
            value = data.getNextUInt8();
            value <<= 8;
            value &= 0xff00;
            value2 = data.getNextUInt8();
            value |= value2 & 0x00ff;
        }
        else if ( code == oneMoreByteCode1 ) {
            value = data.getNextUInt8();
            value = (value + lowestUCode);
        }
        else if ( code == oneMoreByteCode2 ) {
            value = data.getNextUInt8();
            value = (value + lowestUCode*2);
        }
        else {
            value = code;
        }
        return value;
    }

注意，编码并不唯一。例如，数值 506 可 编码为 [255, 253]、[254, 0] 或 [253, 1, 250]。编码器可以生成 其中任一种，而 解码器必须接受所有这些形式。编码器应选择较短的 编码，并且对同一数值必须始终选择同一种编码， 因为这通常会获得更好的压缩效果。

UIntBase128 数据类型

UIntBase128 是另一种无符号整数的变长编码， 适用于最大为 232-1 的数值。UIntBase128 编码的数 由一串字节组成，除最后一个字节外，所有字节的最高位 均置位，最后一个字节的最高位清零。数值本身以 128 为基数， 编码在每个字节的低 7 位中。因此，UIntBase128 的 解码过程为：从 value = 0 开始。读取一个字节，将 value 设为 原 value 乘以 128 加上（该字节与 127 按位与的结果）。重复上一步，直到 该字节的最高位为 false。

UIntBase128 编码格式可能出现非最优编码，例如 同一数值可以用不同数量的字节表示（利用 前导零）。例如，数值 63 可以编码为一个字节 0x3F， 也可以编码为两个（或更多）字节：[0x80, 0x3f]。编码器不得这样做， 必须生成尽可能短的编码。解码器 如果遇到带前导零的 UintBase128 编码值 （以字节 0x80 开始的值）、长度超过 5 字节的 UintBase128 序列，或超过 232-1 的 UintBase128 编码值，必须拒绝该字体文件。下面的类 C 伪代码 描述如何读取 UIntBase128 格式：

    bool ReadUIntBase128( data, *result )
    {
        UInt32 accum = 0;

        for (i = 0; i < 5; i++) {
            UInt8 data_byte = data.getNextUInt8();

            // No leading 0's
            if (i == 0 && data_byte == 0x80) return false;

            // If any of top 7 bits are set then << 7 would overflow
            if (accum & 0xFE000000) return false;

            *accum = (accum << 7) | (data_byte & 0x7F);

            // Spin until most significant bit of data byte is false
            if ((data_byte & 0x80) == 0) {
                *result = accum;
                return true;
            }
        }
        // UIntBase128 sequence exceeds 5 bytes
        return false;
    }

WOFF2 文件头的解释方式与 [WOFF1] 中的 WOFF 文件头相同，仅增加一个 totalCompressedSize 字段。 WOFF2 文件头中的 signature 字段 必须为 0x774F4632（'wOF2'），用于 与 WOFF 1.0 文件区分。如果该字段 不含此值，用户代理必须将文件作为无效文件拒绝。 有效的 WOFF 2.0 文件 必须将保留字段设为“零”，但解码器 不得因为文件头保留字段的值非零 而拒绝下载的字体文件。用户代理 不得因为正确解码后所得字体文件的大小 与 WOFF2 文件头中编码的 totalSfntSize 值不符而拒绝该字体文件。

WOFF2 文件头中的“totalSfntSize”值仅供 参考。它可能表示未压缩输入字体文件的大小，但如果存在变换后的 'glyf' 和 'loca' 表，重建表的未压缩大小及 解压后的字体总大小可能与 WOFF2 文件头所指定的原始总大小 有很大差异。

4. 字体目录

字体目录部分包含表目录，输入字体文件中的每个唯一字体表 对应一个条目；当输入文件为字体集合时，还可包含 可选的集合目录表。

4.1. 表目录格式

表目录是下文定义的 WOFF2 表目录条目 数组。目录紧接 WOFF2 文件头之后，因此 文件头中没有指向此块的显式偏移。 其大小取决于具体内容；因此，最佳解码策略 是按流处理文件，而不是尝试 随机访问。每个表目录条目指定一个字体数据表的 原始大小；对于应用了额外变换的表， 还指定变换后的大小。变换后的表通过 'flags' 字段识别， 该字段组合已知表标签（位 0–5，见“已知表标签”）和变换 版本号（位 6 和 7，见下文说明），以确定所用变换。 表标签与变换版本号的组合确定了 对表应用的具体变换。目前定义的变换详见 本规范第 5 章。

与原始输入字体文件中的表目录条目 按字母升序排列不同， WOFF2 表目录条目定义了各表被处理 并编码到压缩字体数据流中的物理顺序。 字体文件解压时，解码器负责对重建的表目录 排序并重新排列。

为简化字体解码过程，编码器 必须重新排列变换后的 表，使关联的 'glyf' 和 'loca' 表始终成对出现， 且 'loca' 表跟在 'glyf' 表之后。 注意，变换后的 'loca' 表条目只是占位符，指示 重建该表所需的大小，而不占用数据流中的字节。 因此，要求表目录中的 'loca' 条目紧接变换后的 'glyf' 表，可以简化 'loca' 表重建步骤的实现， 该步骤在对 'glyf' 表应用逆变换（详见第 5.1 小节） 时执行。表顺序约束的更多信息见 第 5.5 小节。

各个表目录条目的格式如下：

TableDirectoryEntry
UInt8flags表类型和标志
UInt32tag4 字节标签（可选）
UIntBase128origLength原始表长度
UIntBase128transformLength变换后长度（若适用）

flags 字段的解释如下。位 [0..5] 包含“已知标签” 表的索引，该表列出字体中可能出现的标签。如果标签 不在表中，此位字段的值为 63。位 6 和 7 指示 对各表应用的预处理变换版本号（0–3）。 对于除 'glyf' 和 'loca' 之外的所有字体表，变换版本 0 表示空变换，即原始表数据 直接交给 Brotli 压缩器，纳入压缩数据流。 对于 'glyf' 和 'loca' 表，变换版本 3 表示空 变换，即原始表数据直接交给 Brotli 压缩器， 不应用第 5.1 小节和 第 5.3 小节定义的预处理。 变换后的表格式及相应的变换版本号 详见本规范第 5 章。

若某个表定义了多个变换版本，编码器通常应 选择使变换后表长度最小的版本， 除非减少量微不足道。

若某个表标签定义了多个变换版本，编码器 可使用适用于输入数据的任何已定义变换；解码器 必须能够接受 任何已定义的变换。 如果解码器 遇到指定未知变换版本号的表条目， 则必须拒绝整个字体，因为无法正确解码。

字体表采用已知表标签编码，还是显式包含 四字节标签，在语义上没有区别；这只是旨在提高压缩效率的 编码选择。同样，某个四字节 标签是否出现在“已知表标签”表中，也不是关于 此标签是否应包含在 Web 字体中的规范性声明。编码器在编码标签已列于 “已知表标签”表中的输入字体表时，必须使用已知表标志。

对于未列入已知标签列表的自定义表标签 （或未来可能定义的新标准标签），存在预定义的扩展机制。 如果 flags 字节的位 [0..5] 为 63（0x3f）， 则标志字节之后跟随一个任意的 4 字节标签值。否则， TableDirectoryEntry 结构省略 tag 字段，并根据标志字节的位 [0..5] 从下方固定的“已知表标签”表推导标签。解码器 可以接受以自定义表标签 定义的表条目，即使其后跟随的标签被识别为 某个已知表标签。

flags（及可选 tag 字段）之后是一或两个长度值，均以 UIntBase128 无符号整数编码。origLength 字段指定 字体未压缩版本中该表的长度。对于还要进行额外 变换的表， 必须包含 transformLength 字段， 指定该表变换后版本的长度。

当且仅当表在 Brotli 压缩前经过非空变换时， 表目录条目中才存在 transformLength 字段。 未变换的表，其目录条目不含 transformLength 字段。

变换后长度字段提供该表在经过 [Brotli] 压缩前的变换后大小。 此字段可选，仅在某些表中存在（见下文 “压缩数据格式”说明）。注意，虽然变换后长度 可用于确定解压后的表大小，但变换后字体表的 原始表长度应谨慎对待。

变换后表的重建过程保证保留表的功能， 但可能产生与原始数据不同的二进制 结果。例如，'glyf' 表记录可使用一或两个字节的格式 编码轮廓点坐标，重复值可以在坐标流中 显式重复，也可以省略（由控制点的 标志字节指示）。因此，字形轮廓点可有多种表示， 均产生相同的渲染结果；然而，重建字形记录的 二进制数据可能与原始数据相差很大。详见 ISO“开放字体格式”[OFF] 规范第 5.3.3 小节。

因此，变换后表的 origLength 字段值应仅作为 参考，在解码 WOFF2 数据时，不应据此决定 内存分配。

4.2. 集合目录格式

集合目录仅在输入字体为集合时存在，即 WOFF2 文件头的“flavor”字段为 0x74746366（'ttcf'）时。若存在，集合目录紧接 表目录之后，由一个 CollectionHeader 和一或 多个 CollectionFontEntry 记录组成。

如果输入字体为集合，表目录对 整个集合中的每个唯一表包含一个条目，无论该表 是否由集合中的不同字体共享。因此，使用 WOFF2 压缩的 字体集合，其表目录包含该集合文件中 所有字体的全部表。

处理字体集合时，编码器 必须保留输入集合中各嵌套字体的原有顺序，并且 必须为每个字体将匹配的 TableDirectoryEntry 索引记录到 CollectionFontEntry 中。

解码器必须还原 字体数量相同、并含相应偏移表的集合。输出集合文件 各字体的偏移表 必须具有与输入集合相同的 numTables；若原始输入偏移表含 DSIG， 则该值少一。如果 CollectionHeader 中 TTC 头的版本字段 设为“2.0”，解码器必须将输出集合的 TTC 头字段 {ulDsigTag, ulDsigLength, ulDsigOffset} 设为 null，或将 TTC 头格式转换为版本 1（0x00010000）。

处理字体集合时，解码器 必须重建输入集合中各嵌套字体的原有顺序。各嵌套字体 内部的表可以重排。处理存在多对 'glyf'/'loca' 表的集合时，解码器 必须检查 CollectionFontEntry 索引，确保所引用的 'glyf' 和 'loca' 表彼此配对， 并在发现配对不匹配时拒绝该集合。表配对的更多 信息见表目录格式说明。 符合规范的用户代理必须能加载 并使用 WOFF2 解码器生成的格式正确的字体集合文件。

5. 压缩数据格式

WOFF2 文件的 CompressedFontData 字段包含各字体表数据的拼接， 其顺序与 WOFF2 表目录中的条目顺序一致。 解压后的数据流中，表条目之间 不得存在表目录定义之外的无关数据。 若存在此类数据， 符合规范的用户代理必须将文件作为无效文件拒绝。 CompressedFontData 流必须使用 Brotli 压缩算法 [Brotli] 压缩。如果数据块因任何 原因解压失败，WOFF2 文件均为无效， 不得加载。

WOFF2 字体表数据的解码过程可规定为： 先解除 CompressedFontData 字段的字节级压缩， 得到“表数据块”，再应用下文描述的 附加解码步骤。实际实现可合并这些步骤， 或以增量或流式方式执行其中部分步骤，但 结果必须与此处规定的顺序过程一致。

某些表（如 glyf、loca 和 hmtx，由各自标签标识）会进行 额外变换。若表未变换，其数据以原样 出现在压缩流中，占表数据块的 origLength 字节。是否变换以及所用变换版本号，由 标志的最高两位定义（详见第 4.1 小节）， 表数据还须按下文指定的变换处理。 在这种情况下，变换后的表占表数据块的 transformLength 字节。

解压并重建后的 表数据必须按 [OFF] 规范指定的格式存储。每个 重建的表目录条目必须包含有效的 'checkSum' 值， 解码器必须重新计算每个解码后表的 checkSum。 此外，由于对 glyf 和 loca 表应用了修改性变换，解码器 必须重新计算整个字体的 checkSumAdjustment 值，并将更新后的值存储在 head 表中。

不应依赖已知表标志值来判断是否存在 变换后的表。例如，glyf 表可在 目录中表示为 flag = 10 且无 tag，或 flag = 63 并后跟 'glyf' 标签。应结合定义变换 版本号的 flags 值和表标签来确定所用变换。

表目录中 origLength （未变换表）与 transformLength（变换后表）字段的 总和，必须等于使用 [Brotli] 解压后的字体数据块大小。若 解压后的大小与上述表目录 定义的长度总和不符， 则不得加载该 WOFF2 文件。

根据当前 WOFF2 版本，可对三种表应用变换： 表示轮廓数据的 glyf，loca， 用于表示 glyf 表内各个字形的偏移，以及 表示字形水平度量的 hmtx，前提是字体包含这些表。 创作工具可使用任何适用的变换，同时考虑 第 5.3 小节和 第 5.5 小节的额外约束。glyf 表变换 规定于第 5.1 小节，loca 表变换规定于第 5.3 小节， hmtx 表变换规定于 第 5.4 小节。

CFF 表处理与去子例程化。

多数使用 CFF 轮廓的 OpenType 字体，通过将 CFF 数据子例程化来 更紧凑地存储数据。WOFF2 开发与评估 中的实验表明，若在 WOFF2 编码前对 CFF 轮廓数据 进行去子例程化，Brotli 压缩可更高效地工作， 并获得更好的压缩率，平均减少压缩数据大小 约 5–10%。不过，CFF 去子例程化同时会使 输出文件大小增加约 10%。

CFF 预处理／去子例程化视为可在 WOFF2 编码前 实现的外部步骤，因此不属于本规范范围。 字体生产者可优化生产流程，选择 减小压缩字体大小以实现最快的 Web 字体传输，代价是 增大输出 CFF 字体大小（但也会改善渲染性能）； 或保留子例程化的 CFF 数据，以最小化输入／输出字体大小。

WOFF 2.0 对某些表应用的变换，旨在减少和／或 消除 SFNT 格式中的固有冗余，并重组字体数据 流以提高熵编码效率。因此，重建后的字体数据 将保留输入字体的全部功能，但由于可能存在 编码差异（例如 'glyf' 表中轮廓点坐标的 不同优化程度，和／或 'loca' 表偏移 计算的差异），不同 WOFF2 解码器生成的输出文件可能 与输入文件不逐位一致。输入字体的表还可能 在编码过程中重排， 或由解码器重排以符合 [OFF] 规范推荐的表顺序 – 因此， 即使表内容不变，其偏移也可能改变。 编码前后字体数据结构中的二进制差异 （即使很小，且主要源于解码器优化和表重排） 会使已有的 'DSIG' 表失效。因此，符合规范的 WOFF2 编码器 必须从输入字体数据中移除 DSIG 表，然后再应用变换与熵编码。

WOFF 2.0 编码器还必须设置 head 表 'flags' 字段的第 11 位 （见 [OFF] 规范），表明 重建字体经过无损的修改性变换。

5.1. 变换后的 glyf 表格式

glyf 表数据可采用两种格式之一存入 WOFF2， 格式由变换版本号定义（编码在表目录标志位中， 详见第 4.1 小节）。变换版本“3” 定义空变换，glyf 表内容 以原始、未修改格式表示。下文指定的变换版本“0” 可选，用于消除 glyf 表数据中的某些冗余。

本小节指定的 glyf 表变换版本“0” （由表目录标志位定义，详见第 4.1 小节） 旨在减少冗余信息， 更高效地编码字形的实际 TrueType 轮廓。 此修改后的变换基于 MicroType Express [MTX] 规范中描述的类似变换。 MTX 引用为资料性内容；修改后变换的细节 规定于下文，本节为规范性内容。

虽然 glyf 表变换保留字体中每个字形的功能与渲染保真度， 但很可能生成一组新的字形记录， 其二进制数据与原始字体不一致。依据 [OFF] 第 5.3.3 小节的编码规则， 一个字形记录可能有多种有效重建方式。根据具体情形 以及对重建 glyf 数据应用的优化程度，重建表的大小可能大于、小于或等于 WOFF2 所压缩的输入字体原始 glyf 表大小。 本规范和 [OFF] 标准均不强制 对字体数据进行特定优化。因此，WOFF2 解码器 实现有责任确保从文件重建字形记录时分配 足够内存 – 原始 glyf 表大小， 即为变换后的 glyf 表提供的 origLength 值， 只能作为参考。

无论字形记录重建过程的实现细节如何， 也无论对重建 'glyf' 数据采用何种优化程度， 用户代理不得 因重建 'glyf' 表的大小不匹配 WOFF2 表目录 'glyf' 条目中编码的 origLength 值，而拒绝正确解码的字体文件。

为提高压缩效率，将 glyf 表拆分为 多个子流，把同类数据分组。变换后的表由 若干指定各子流大小的字段组成，随后 依次排列各子流。解码时进行逆变换， 将不同子流中的数据重新组合，为原始 glyf 表的每个条目创建完整字形记录。

字形记录的重建

重建过程首先执行以下步骤，确定 编码的字形类型（简单、复合或空字形）：

从 nContour 流读取一个 Int16，存入重建 TrueType 字形的 numberOfContours 字段。其解释与 TrueType 规范 相同：为零时，字形为空；为 正值时，字形为简单字形，且该值为轮廓 数量；nContour 为 -1（0xffff）时，字形为复合字形。

空字形的解码

空字形（nContour = 0）的重建很简单： 增加字形记录计数，并在 loca 表中创建新条目，满足 loca[n] = loca[n-1]。若 bboxBitmap 标志指示边界框值已显式编码在 bboxStream 中，解码器 必须将 WOFF2 文件 作为无效文件拒绝。

简单字形的解码

对于简单字形（nContour > 0），继续如下处理：

  1. 从 nPoints 流读取 numberOfContours 个 255UInt16 值，每个 值表示对应轮廓的点数。通过计算累积和再减去 一，将它们转换为 endPtsOfContours[] 数组。例如，流中的值若为 [2, 4]，则 endPtsOfContours 为 [1, 5]。此外，读取的值的 总和就是字形的总点数 nPoints。在本例 中，nPoints 为 6。
  2. 从 flags 流读取 nPoints 个 UInt8 值，每个对应重建 字形轮廓中的一个点。标志 字节的解释详见第 5.2 小节。
  3. 对每个点（即 nPoints 次），从 glyph 流读取若干坐标 字节。字节数由前一步读取的标志 字节决定：(flag < 0x7f) 在 0–83 范围内时为一个字节，84–119 时为两个字节， 120–123 时为三个字节，124–127 时为四个字节（各范围均含端点）。按 第 5.2 小节的过程解码这些字节，重建 字形点坐标的 delta-x 和 delta-y。使用标准 TrueType 字形 编码，将这些值存入重建字形， 详见 [OFF] 第 5.3.3 小节。
  4. 从 glyph 流读取一个 255UInt16 值，即 instructionLength，表示指令字节数。
  5. 从 instructionStream 读取 instructionLength 个字节， 作为指令存入重建的字形。

optionFlags 第 0 位指示是否存在额外的 overlapSimpleBitmap[] 位数组。其他位均保留，应清零。 如果输入字体的所有简单字形都将 OVERLAP_SIMPLE 标志设为零， 编码器必须清除 optionFlags 第 0 位并省略 overlapSimpleBitmap[] 位数组。 如果输入字体中至少一个简单字形 的标志第 6 位已设置， 编码器必须将 optionFlags 第 0 位设为 “1”，且必须创建额外的 overlapSimpleBitmap[] 位数组，其中 相应位必须设置为输入字体中各 简单字形的标志第 6 位的值。

解码器 必须检查 optionFlags 第 0 位， 以确定额外的 overlapSimpleBitmap[] 是否包含在变换后的 'glyf' 表中。若不存在该位数组， 则在重建简单字形标志时， 解码器必须将全部 OVERLAP_SIMPLE 标志值设为零。 若包含 overlapSimpleBitmap[]，解码器 必须使用其位设置重建 OVERLAP_SIMPLE， 并将相应位值设置为输出字体每个简单字形 首个标志字节的第 6 位。

复合字形的解码

对于复合字形（nContour == -1），以下步骤取代 上述步骤 1–5：

1a. 从 compositeStream 读取一个 UInt16，按 TrueType 规范 解释为组件标志字。根据标志值，另有 4 到 14 个参数字节，解释为字形索引、 arg1、arg2，以及可选的缩放或仿射矩阵。

2a. 从 composite 流读取步骤 1a 确定数量的 参数字节，存入重建字形。如果步骤 1a 的 标志字设置了 FLAG_MORE_COMPONENTS（位 5）， 返回步骤 1a。

3a. 如果任何标志字设置了 FLAG_WE_HAVE_INSTRUCTIONS （位 8），则从 glyph 读取指令，并按 上述步骤 4 和 5 的过程 存入重建字形。

边界框的解码

对于简单和复合字形，如果边界框位向量中 相应位已设置，还需从 bbox 流读取 4 个 Int16， 分别表示 xMin、yMin、xMax 和 yMax， 并记录到重建字形的相应字段。 对于简单字形，如果边界框位向量中 相应位未设置，则计算轮廓中 x 和 y 坐标的 最小值与最大值，以推导并存储边界框。

复合字形必须显式提供边界框。 原因是计算边界框更复杂， 需要解析对组件字形的引用，同时考虑 复合字形指令及各组件指定的缩放， 这会与纯流式字体解码实现冲突。 解码器必须 检查复合字形记录中是否存在边界框信息， 不得加载缺少复合字形边界框数据的字体文件。

5.2. 变长 X 和 Y 坐标的解码

简单字形数据结构定义 组成字形轮廓的全部轮廓，表示为一系列 曲线上和曲线外的坐标点。这些坐标编码为增量值， 表示前一点与当前点相应 X 和 Y 坐标的差值；每个轮廓的第一个点 相对于 (0,0)。为尽量减小点坐标 数据集，每个点表示为 (flag, xCoordinate, yCoordinate) 三元组。标志值存于独立数据流， 坐标值作为字形数据流的一部分，以 变长格式编码，每点总计占 2–5 字节。

标志的最高位指示该点位于曲线上 还是曲线外 （最高位为 0 时， 该点在曲线上）， 其余七位确定 X 和 Y 坐标值的格式， 指定 128 种可能的索引组合；这些组合 根据 TrueType 字体数据的典型统计分布 分配。X 和 Y 坐标使用半字节记录时 （每坐标 4 位或 12 位），位在字节流中紧凑排列， 先放 X 坐标（最高位在前），再放 Y 坐标 （最高位在前）。这样显著减小字形数据集的大小， 而把同类值（标志、坐标）分组到独立、连续的 数据流中，则可更高效地应用 编码第二阶段的熵编码。

  • 用于表示 Y 坐标值的位数（Y bits）。
  • 加到 X bits 值上的额外增量（delta X）。
  • 加到 Y bits 值上的额外增量（delta Y）。
  • X 坐标值的符号（X sign）。

5.3. 变换后的 loca 表格式

loca 表可采用两种格式之一存入 WOFF2， 由变换版本号定义（编码于表目录标志位， 详见第 4.1 小节）。版本“3” 定义空变换，loca 表内容 以原始、未修改格式表示。版本“0”虽可选， 对于 loca 表，只要 glyf 表数据经过变换，就必须应用此变换。换言之，glyf 和 loca 要么均以变换后的格式存在， 要么均应用空变换。

loca 表变换版本“0” （由表目录标志位定义，详见第 4.1 小节） 规定如下。

变换后 loca 表的 transformLength 必须始终为零。 origLength 必须是适当大小（numGlyphs+1 乘以每字形大小； 若 indexFormat，定义见 第 5.1 小节 变换后的 glyf 表格式，为零， 每字形大小为两字节，否则为四字节）。若变换后的 loca 表的 transformLength 非零，或编码的 origLength 与上述计算 大小不符，解码器必须将 WOFF2 文件作为无效文件拒绝。

loca 表必须在 glyf 表解码时重建。 重建 loca 表的过程 规定于第 5.1 小节，作为 变换后 glyf 表解码的一部分。对于 重建的字形记录， 解码器必须存储各字形相应的偏移， 采用的格式由变换后表的 indexFormat 字段指定，该表为 glyf。

5.4. 变换后的 hmtx 表格式

hmtx 表数据可采用两种格式之一存入 WOFF2， 格式由变换版本号定义（编码在表目录标志位中， 详见第 4.1 小节）。变换版本“0” 定义空变换，hmtx 表内容 以原始、未修改格式表示。下文指定的变换版本“1” 可选，用于消除 hmtx 表数据中的某些冗余。

变换版本“1”利用 TrueType 字形的固有冗余： 按 TrueType 建议设计的字形轮廓，其左侧边距 很可能等于边界框的 xMin。 hmtx 表格式规定于第 5.2.4 小节，参见 [OFF]； 该表含两个左侧边距信息数组，分别用于比例和等宽 字形段。满足某些条件时，每个数组都可从原始数据中移除， 并从字形边界框信息重建。

5.5. 表顺序约束

以下对有效 WOFF2 文件的约束，旨在 支持节省内存的 WOFF 2.0 文件传输与解码。

表目录中的 loca 必须位于 glyf 之后。 WOFF2 包含单独编码的字体文件时，表目录可以 在 glyf 与 loca 之间插入其他表；但若包含字体集合，每个 loca 必须紧接其对应的 glyf。 例如顺序 'cmap', 'glyf', 'hhea', 'hmtx', 'loca', 'maxp' ... 对单独编码的字体可接受；但集合 必须将 glyf / loca 彼此配对，虽然 各对不必形成连续表块，例如 'cmap', 'glyf', 'loca', 'hhea', 'hmtx', 'glyf', 'loca', 'maxp', 'post' ... 是可接受的。 loca 的额外约束见第 5.3 小节。

6. 扩展元数据块

WOFF2 文件可以包含扩展元数据块。其解释 与 [WOFF 1] 完全相同。

不过，WOFF 1 使用 zlib 压缩存储扩展元数据块， 而WOFF2 中， 若存在元数据，必须用 [Brotli] 压缩并存为独立流。 此变更旨在尽量减少实现 WOFF2 所需的字节级压缩 算法数量，也因为预计 Brotli 在多数情况下能 获得优于 zlib 的压缩率。

元数据块必须 紧接压缩字体数据流之后。其起始位置 必须始终按 4 字节对齐； 存在扩展元数据时，若需达到 4 字节边界， 必须在压缩数据块末尾填充至多三个零字节。 若元数据块是 WOFF 文件的最后 一个块，则块末尾之后不应有额外填充。

7. 私有数据块

WOFF2 可以包含 任意数据块，允许字体创建者纳入其希望 提供的任何信息。 这些数据的内容不得影响用户代理的字体使用或 加载行为。用户代理不应对私有块内容作任何假设； 它可能包含 ASCII 或 Unicode 文本，或 供应商定义的二进制数据，也可能压缩或加密，但 没有公开定义的格式。符合规范的用户代理不会 对其结构作任何假设。只有负责该私有块的字体 开发者或供应商才应了解其内容。

私有数据块 若存在，必须是 WOFF 文件最后一个块，位于压缩字体 数据流及扩展元数据块（若有）之后。 私有数据块必须 在文件中的 4 字节边界开始；为此可在前一块之后 按需插入至多三个零字节作为填充。 私有数据块的末尾 必须对应 WOFF2 文件末尾。
