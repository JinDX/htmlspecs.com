摘要

1. 引言

本文档介绍 SPARQL-RL。它是一种通过声明式规则 从现有 RDF 数据派生新 RDF 三元组的机制。 本文档定义了基于规则的推理的语法和语义。

SPARQL-RL 的实现提供以下一种或两种操作： 推理和查询。 推理操作将规则应用于给定的 基础图，并生成一个推理图，其中包含 由规则求值派生且未出现在基础图中的 RDF 三元组。 是否将推理图与基础图合并是可选的，并 由用户决定。 查询操作确定给定的 目标模式是否可以以及如何使用规则 从基础图派生出来。

SPARQL-RL 允许创建新的 RDF 术语，包括空白节点， 这些术语可以用于规则头中的三元组模板。

SPARQL-RL 还支持失败即否定，这可能导致 根据规则求值顺序的不同而产生 不同的推理图。为避免这种情况，规则使用 分层技术进行求值，该技术在规则之间建立顺序， 从而确保始终生成相同的推理图。

当上下文明确时，SPARQL-RL 可以称为 SRL。

3. SPARQL-RL 概述

本节为非规范性的。

给定一个 基础图和一个 规则集，SPARQL-RL 会推理出新的三元组。 求值的输出是一个 推理图，其中包含派生出的 未出现在基础图中的三元组。

每个 规则都有一个模式，称为主体，以及一个结果 模板，称为头部。 执行规则时，会查找主体中变量的值 使主体与合并后的基础图以及 到当前执行阶段为止的所有推理三元组相匹配。 然后使用这些值实例化 规则头中的三元组模板，以生成新的推理三元组。

规则会一直执行，直到不再推理出新的三元组， 并且随着新的推理三元组 可用，规则可能会执行多次。

SPARQL-RL 的执行定义确保规则执行顺序 在创建新的 RDF 术语时不会导致不同结果， 包括新的空白节点，或在测试某个 模式是否不存在时。换言之，都会生成相同的推理图， 无论规则执行顺序如何。

SPARQL-RL 具有受 SPARQL 1.2 查询语言启发的易于人类使用的语法。 规则集求值包含与 SPARQL 类似的元素，但在 细节上有所不同，以确保生成相同的推理图， 无论规则执行顺序如何。

本节中的示例描述软件组件及其 依赖关系：一个前端调用应用服务器，而 应用服务器查询一个存在已知 漏洞的数据库。

3.1 三元组模式

三元组模式与三元组数据进行匹配，以为 变量赋值。该模式具有 三个元素，每个元素都是 RDF 术语、变量， 或是一个包含变量的三元组术语的模式。

在第一个示例中，基础图和规则集中有以下数据：

示例 1：基本示例 
:frontend :callsService :app .
:app      :queriesDatabase :db .
:db       :hasVulnerability :vuln1 .
RULE { ?x :dependsOn ?y } WHERE { ?x :callsService ?y }
RULE { ?x :dependsOn ?y } WHERE { ?x :queriesDatabase ?y }
:frontend :dependsOn :app .
:app      :dependsOn :db .

将上述规则应用于数据后，会得出 :frontend 依赖于 :app，并且 :app 依赖于 :db，无论依赖关系的种类如何。

然后，我们可以通过添加一条依赖于其他规则生成的 :dependsOn 三元组的规则来派生 :exposedTo 关系 （另请参见下文的 4.3 规则 依赖）：

示例 2：依赖推理三元组 
:frontend :callsService :app .
:app      :queriesDatabase :db .
:db       :hasVulnerability :vuln1 .
RULE { ?x :dependsOn ?y } WHERE { ?x :callsService ?y }
RULE { ?x :dependsOn ?y } WHERE { ?x :queriesDatabase ?y }
RULE { ?x :exposedTo ?v } WHERE { ?x :dependsOn ?y . ?y :hasVulnerability ?v }
:app      :exposedTo :vuln1 .
:frontend :dependsOn :app .
:app      :dependsOn :db .

3.2 递归

上一节中的 :exposedTo 规则只能到达直接 依赖项：:frontend 并不直接依赖 :db，因此 不会为 :frontend 推理出 :exposedTo 三元组。 为了沿任意长度的依赖链传播暴露关系，我们 将该规则替换为两条规则：组件暴露于它自身具有的 漏洞，并且组件暴露于其任何 直接依赖项所暴露的漏洞：

示例 3：规则递归 
:frontend :callsService :app .
:app      :queriesDatabase :db .
:db       :hasVulnerability :vuln1 .
RULE { ?x :dependsOn ?y } WHERE { ?x :callsService ?y }
RULE { ?x :dependsOn ?y } WHERE { ?x :queriesDatabase ?y }
RULE { ?x :exposedTo ?v } WHERE { ?x :hasVulnerability ?v }
RULE { ?x :exposedTo ?v } WHERE { ?x :dependsOn ?y . ?y :exposedTo ?v }
:db       :exposedTo :vuln1 .
:app      :exposedTo :vuln1 .
:frontend :exposedTo :vuln1 .
:frontend :dependsOn :app .
:app      :dependsOn :db .

与前一个示例相比，这增加了 :db :exposedTo :vuln1 —— 数据库暴露于其 自身的漏洞 —— 以及 :frontend :exposedTo :vuln1： 暴露关系通过依赖链到达 :frontend， 无论该链有多长。

最后一条规则是一条递归规则：规则的主体 依赖于规则的头部。

3.3 过滤

我们可以在规则主体中使用表达式来限制变量的值 以进行主体匹配。 例如，给定每个漏洞的严重程度， 我们可以为暴露于严重 漏洞的组件赋予一个状态：

示例 4： 过滤 
:app1 :exposedTo :vuln1 .
:app2 :exposedTo :vuln2 .
:vuln1 :severity 9.1 .
:vuln2 :severity 4.3 .
RULE { ?x :status :criticallyExposed }
WHERE {
    ?x :exposedTo ?v .
    ?v :severity ?s .
    FILTER(?s >= 9.0)
}
:app1 :status :criticallyExposed .

FILTER 对表达式求值，并保留当前 变量绑定集（如果表达式求值为 true），如果表达式求值为 false，则丢弃 当前变量绑定集。 这与 SPARQL 的 FILTER 操作 相同，并且 SPARQL-RL 提供许多与 SPARQL 相同的函数和运算符。

3.4 否定

否定用于指定一个不得匹配的模式。 这称为“失败即否定”。

为了对否定元素进行求值，规则集求值算法 会确保所有可能产生与模式匹配的三元组的规则 在否定元素中均已执行完成。这称为 分层，并确保否定基于 所有相关的可能三元组，无论它们来自数据还是 其他规则。包含否定的规则 被称为依赖于生成这些三元组的规则 （参见下文的 4.3 规则 依赖）。

示例 5：失败即否定 
:app rdf:type :Component ;
    :status :criticallyExposed .

:logger rdf:type :Component .
RULE { ?x :status :safeToDeploy }
WHERE {
    ?x rdf:type :Component .
    NOT { ?x :status :criticallyExposed }
}
:logger :status :safeToDeploy .

3.5 赋值和创建 RDF 术语

赋值允许你将表达式的结果赋给一个变量 在规则主体中。这可用于根据 数据创建新的 RDF 术语。

示例 6：赋值 
RULE { ?v :riskScore ?r }
WHERE {
    ?v :severity ?s .
    ?v :exploitLikelihood ?p .
    SET ( ?r := ?s * ?p )
}

空白节点可以用于规则头中，并且每个都会生成一个新的空白节点 每当规则求值生成三元组时。

示例 7：规则头中的空白节点 
RULE { [] rdf:type :Notification ; :concerns ?x }
WHERE { ?x :status :criticallyExposed }

涉及 赋值的规则、创建空白节点的规则 通过对规则头求值，以及具有模板的规则 该模板涉及包含三元组术语，其中包含变量 的规则都是单次运行规则。 此类规则会在所有可能产生其所依赖数据的规则之后运行， 并在任何依赖于其所产生数据的规则之前运行。

此条件确保此类规则不会循环回自身 并导致创建无限数量的 RDF 术语。

注

RDF 术语常量出现在规则头中并不会 使规则成为 单次运行规则，即使该术语没有出现在 基础图中也是如此：该规则每次 求值都会提供相同的术语，因此它只能添加有限数量的术语。

如果对赋值中的表达式求值时发生错误， 则当前解映射会被该赋值拒绝。

3.6 导入规则集

SPARQL-RL 规则集可以通过 在该规则集的规则集导入中包含其他规则集的 URL。 这允许将规则组织成由多个规则集共享的库。

规则集的 IMPORTS 语句会在任何规则 在该规则集中求值之前处理。在导入步骤期间，如果被导入的规则集 有自己的导入，则也会递归处理这些导入。 在处理规则集期间遍历 IMPORTS 语句可能 遇到循环导入。一个规则集只会导入一次； 导入语句图中的循环不会导致无限循环。

对于 SPARQL-RL 处理器，支持导入规则集是可选的。 更多详细信息请参见 4.5 处理 导入。

3.7 数据块

数据块允许直接向规则集求值简洁地提供 RDF 三元组。 数据块中的三元组会被添加到推理图中，并可用于 规则主体中的匹配。

例如，规则集可以附带已知的已断言事实 直接提供，而不是从数据中派生：

示例 8：在规则集中包含数据 
DATA {
    # 2.0.0 及更早版本存在已知漏洞
    # 并被假定为严重暴露。
    :appV2 rdf:type :Component ;
            :version "2.0.0" ;
            :status :criticallyExposed .
}
注

数据块等同于主体为空的规则： 它的三元组无需对任何规则进行 求值即可成为推理图的一部分。

3.8 规则集求值

规则被组织到规则集中。 一个规则集和一个数据图（即基础图）是求值的输入。 输出是一个图，称为推理图， 它是求值过程产生的三元组集合 且未出现在基础图中。

在求值期间，基于一条规则推理出的三元组 可用于其他规则中的匹配。 规则集求值会持续进行，直到推理图 包含由以下输入所能产生的所有可能三元组： 规则集和基础图。

求值从以下步骤开始，以 准备规则集 然后再对规则本身求值：

  1. 在支持的情况下，会解析输入规则集的导入，以形成一个 包含所有 被导入规则集的全部规则的规则集。 如果任何导入对处理器而言不可接受 处理器会发出错误信号（4.5 处理导入）。
  2. 检查每条规则是否为良构规则。
  3. 计算依赖图。
  4. 计算一个分层 （4.4 分层） 使否定元素和单次运行规则产生一致且 可预测的结果。分层涉及检查 依赖关系 规则之间的 （4.3.1 依赖 图）。

一旦规则集准备完成，求值就会继续 按顺序获取分层中的每一层， 将该层中的规则求值至完成， 然后继续下一层。

3.9 匹配基础数据

在规则集求值期间，可能 需要仅针对原始基础图进行模式匹配， 而不针对任何推理三元组。

一个示例是设置默认值。 规则必须测试基础图是否已经包含一个值，如果没有， 则规则可以计算默认值。

示例 9：使用 NOT 的基础数据 
:A :distanceMiles 5 .
:A :distanceKilometers 8 .
:B :distanceMiles 10 .
RULE  { ?x :distanceKilometers ?kilometers }
WHERE {
    ?x :distanceMiles ?miles .
    NOT DATA { ?x :distanceKilometers ?km }
    SET ( ?kilometers := xsd:integer(?miles *  1.60934))
}
:B :distanceKilometers 16 .

使用 NOT DATA 允许规则主体的其他部分匹配推理三元组。 也可以执行所有规则主体匹配，针对基础图，通过 使用 WHERE DATA。 这样的规则便仅依赖来自基础图的匹配。

示例 10：使用 WHERE 的基础数据 
RULE  { ?x :distanceKilometers ?kilometers }
WHERE DATA {
    ?x :distanceMiles ?originalMiles .
    NOT { ?x :distanceKilometers ?km }
    SET ( ?kilometers := xsd:integer(?originalMiles *  1.60934))
}
注

本节中的匹配针对基础图。 它不包括由 规则集求值 从规则集的 DATA 块中添加的三元组 （3.7 数据块）。

4. SPARQL-RL 抽象语法

SPARQL-RL 抽象语法是 SPARQL-RL 的逻辑结构。 它用于定义 SPARQL-RL 的执行算法。

4.1 抽象语法的元素

变量
变量表示三元组模式中一个可能的 RDF 术语。 变量也用于表达式中。
表达式
表达式是一个 RDF 术语、一个变量， 或对函数或函数形式应用实参， 其中每个实参本身都是一个表达式。 表达式相对于一个解映射进行求值，得到 一个 RDF 术语作为结果，或者求值导致 错误。 表达式与 SPARQL 表达式兼容。
数据块
数据块是一组三元组。 这些三元组作为附加事实添加到推理图中，并 包含在推理过程中。
三元组模式
三元组模式是一个 3 元组，其中每个元素是 一个变量、一个 RDF 术语，或一个 包含变量的三元组术语模式。 该元组的第二个元素必须是一个 IRI 或一个 变量。 三元组模式出现在规则的主体中， 并用于匹配 RDF 三元组。
三元组模板

三元组模板是一个 3 元组，其中每个元素是 一个变量、一个 RDF 术语，或一个 包含变量的三元组术语模板。 该元组的第二个元素必须是一个 IRI 或一个变量。 三元组模板出现在规则的头部中，并 用于生成 RDF 三元组。

注

一个三元组术语的模式或模板，如果其中没有 变量出现，则它是一个三元组术语，因此也是 一个 RDF 术语。

过滤元素
过滤元素是一个表达式， 它作为规则元素出现。 它用于限制模式匹配中 变量的值。
三元组模式元素
三元组模式元素是一个三元组模式， 它作为规则元素出现。
否定元素
否定元素是一个规则元素。 它具有一个否定元素主体， 由一系列三元组模式元素和 过滤元素组成。 否定元素具有一个 标志， .evaldata， 用于指示使用哪个图来匹配 否定元素主体。
赋值 元素
赋值元素是一个规则元素，它是 一个由 一个变量（称为赋值变量） 和一个表达式（称为赋值表达式）组成的对。
规则元素
一个规则元素是以下任意一种： 三元组模式元素、 过滤元素、 否定元素，或 赋值元素。
规则头
规则头是一个三元组 模板序列。
规则主体
规则主体是一个规则元素序列； 也就是说，每个序列元素都是以下之一： 一个三元组模式元素、 一个过滤元素、 一个否定元素， 或一个赋值元素。
规则集导入
规则集导入（通常简称“导入”）是 来自 IMPORTS 语句的 URL 集合， 这些语句指向 将在求值期间包含的其他规则集。
规则
一个规则包含一个规则头（通常简称 “头部”）、 一个规则主体（通常简称“主体”）， 以及一个标志 .evaldata， 用于指示使用哪个 图来匹配主体中的三元组模式。 可以为规则提供 URI 或空白节点，以帮助标识它。
单次运行规则

单次运行规则是在规则集求值的 特定时刻仅运行一次的规则。 如果满足以下任一条件，一个规则就是一个单次运行 规则：

  • 规则主体具有一个赋值元素；
  • 规则头的一个三元组模板具有一个空白节点；
  • 规则头的一个三元组模板具有一个 三元组术语模板，其中出现了一个变量。
一般规则
一般规则是一个不是单次运行规则的规则。 一般规则在规则集求值期间可以运行多次。
规则集
规则集是零个或多个规则的集合、 零个或多个数据块的集合， 以及零个或多个规则集导入的集合。 已解析 规则集是一个规则集， 它没有导入。 已解析规则集通过对另一个规则集 应用导入过程来创建。
基础图
基础图是作为 求值过程输入给出的RDF 图。
推理 图
推理图是一个由 规则集求值产生的RDF 图。 它包含所有不在 基础图中， 且通过将 规则集应用于基础图而推理出的三元组。
规则集 求值
规则集求值是将一个规则集 应用于一个基础图以产生一个推理 图的过程。 规则 求值是对规则求值一次的过程。 对规则求值会通过对规则主体的求值，产生规则头给出的所有三元组， 无论某个三元组是在基础图中、已在规则集求值期间推理出， 还是一个新推理出的三元组。 在规则集求值期间，一个规则可以被求值 多次。

SPARQL-RL 提供两种操作：推理和查询。

推理
推理是将一个规则集应用于给定 基础图并产生一个包含推理 三元组的推理图的操作。它应用完整的规则集求值。
查询

查询是确定给定模式是否 可以使用规则集从基础图派生， 并返回一个解序列的操作，其中每个解映射 都为变量给出 RDF 术语。

查询的效果相当于执行一个推理操作， 然后将目标模式与合并后的 基础图和推理 图进行匹配。

查询操作可能不会对所有规则求值；相反，它 可以只对回答查询 目标所必需的规则求值。

SPARQL-RL 处理器
SPARQL-RL 处理器是一个实现 SPARQL-RL 规范、能够对规则集求值，并提供以下一种或两种 操作的系统：推理和查询。

在三元组模式或三元组 模板中， 元组的位置 1 非正式地称为主语， 位置 2 非正式地称为谓语，而 位置 3 非正式地称为宾语。

一个规则元素序列中的元素从 1 开始编号。

4.2 良构性条件

良构性是对 一个规则集的抽象语法的一组条件。这些条件共同确保 规则头部中的一个 变量具有在规则主体中定义的值； 过滤元素 或赋值表达式中的每个变量 在求值时都有值； 并且规则中的每个 赋值都会引入一个新变量， 即一个此前未在规则主体中使用过的变量。

给定一个初始变量集合，为一系列规则元素 定义良构性。

令 elti 为一个规则元素序列的第 i 个元素。

令 varsi 为 elti 定义的变量集合，如下所示：

  • 如果 elti 是一个三元组模式元素，则
    • varsi 是 三元组模式 元素中出现的变量集合。
  • 如果 elti 是一个赋值元素，则
    • varsi 是包含该赋值变量的集合。
  • 否则，
    • varsi 是空集。

令 V0 为该序列的初始变量。

令 Vi 为 V0 与所有 varsj 的并集， 其中 j 从 1 到 i。

令 Vall 为 VN 的值， 其中 N 是该序列的长度。

给定一个变量集合 V0，如果对于从 1 到 N 的每个 i 都满足以下条件，则一个良构 序列是一个规则元素序列：

  • 如果 elti 是一个过滤 元素，则
    • 过滤元素中提到的每个变量 都是 Vi-1 的元素。
  • 如果 elti 是一个赋值元素，则
    • 赋值表达式中提到的每个变量 都是 Vi-1 的元素
    • 赋值变量 不是 Vi-1 的元素。
  • 如果 elti 是一个否定元素，则
    • 否定元素 主体中的规则元素序列是一个良构 序列， 其中将 V0 设置为该规则元素的 Vi-1 的值。

如果一个规则的规则主体的规则元素序列 是一个良构序列，并以 V0 为空集开始， 且规则头的每个三元组模板中的每个变量 都是 Vall 的元素，则该规则是一个良构 规则。

当且仅当一个规则集的所有 规则都是良构规则时，该规则集才是良构规则集。

4.3 规则依赖

如果第二个规则的输出影响第一个规则主体的求值，则规则 R1 依赖于规则 R2。 也就是说，R2 的头部具有一个可以生成与 R1 主体中的三元组模板匹配的三元组的 三元组模式， 该模式可能作为三元组模式元素，也可能位于一个否定元素内部。

有两种依赖： 闭合依赖和开放 依赖。 闭合依赖确保规则 R2 在规则 R1 执行之前已经生成其所有可能的输出。 如果规则依赖不是闭合的，则它是开放依赖， 这允许第一个规则 R1 在 规则 R2 可能再次运行以生成更多三元组时执行， 随后这些三元组可能导致使用来自 R2 的新三元组重新对 R1 求值。

标志 .evaldata 设置为 false 的规则使用 基础图进行匹配，并且该规则没有依赖。

在第一个示例中，第一个规则对 第二个规则具有开放依赖。

示例 11：开放依赖 
RULE { ?x :exposedTo ?v } WHERE { ?x :dependsOn ?y . ?y :hasVulnerability ?v }
RULE { ?x :dependsOn ?y } WHERE { ?x :callsService ?y }

在第二个示例中，第一个规则对 第二个规则具有闭合依赖：三元组模式 ?x :status :criticallyExposed 出现在第一个规则的一个否定元素内部，并且 与第二个规则头中的三元组模板匹配。 在第二个规则 生成其所有可能输出之前，不能对第一个规则求值。

示例 12：闭合依赖 
RULE { ?x :status :safeToDeploy }
WHERE { ?x rdf:type :Component . NOT { ?x :status :criticallyExposed } }

RULE { ?x :status :criticallyExposed } WHERE { ?x :exposedTo ?v }
三元组模式匹配

如果一个三元组模板可以生成一个与 三元组模式匹配的三元组，则该三元组模式与该三元组模板匹配。

三元组模式依赖

如果一个三元组模式可以 匹配 一个三元组模板，则该三元组模式 依赖于 该三元组模板。

规则依赖

如果 R1.evaldata 为 true，并且 R1 主体中的任何三元组 模式， 无论是作为三元组模式元素还是 位于 否定元素 neg 中（其中 neg.evaldata 为 true）， 都依赖于 R2 头中的一个三元组模板，则规则 R1 依赖 于 规则 R2。

闭合依赖

如果满足以下任一条件，则规则 R1 对规则 R2 的一个规则依赖是一个闭合依赖：

  • 出现在 R1 的一个否定元素内部的一个三元组模式，其中该否定元素标志 .evaldata 为 true， 与 R2 的规则头中的一个三元组模板匹配。
  • 规则 R1 依赖于规则 R2， 且 R1 是一个单次运行规则。
开放依赖

如果规则 R1 对规则 R2 的一个规则依赖 不是闭合依赖，则它 是一个开放依赖。

如果存在三元组模板变量的值，使得在模板中用值替换变量 得到一个三元组 T2，其中 T2 与 T1 相等，则一个三元组模板可以生成一个 RDF 三元组 T1。

类似地，如果存在 三元组模式变量的值，使得在模式中用这些值替换变量 得到一个三元组 T2，其中 T2 等于 T1，则一个三元组模式匹配一个三元组 T1。

如果一个变量在三元组 模板 或三元组模式中使用多次，则使用相同的 RDF 术语 作为替换项。

在三元组模式中用 RDF 术语替换变量 包括替换三元组术语内部的变量。

4.3.1 依赖图

规则之间的依赖表示为一个有向图， 称为依赖图。 图的顶点是规则集中的规则，而边 根据依赖是开放依赖还是闭合依赖， 分别标记为开放或闭合。

依赖图
一个规则集的依赖图是一个有向图，其中每个 顶点都是该规则集中的一个规则，并且如果规则 R1 依赖于规则 R2，则存在一条从规则 R1 到规则 R2 的边。 该边根据依赖 是开放依赖还是闭合依赖， 分别标记为开放 或闭合。
传递规则依赖
如果在依赖图中存在一条从 R1 到 R2 的路径， 则规则 R1 对规则 R2 具有传递依赖。
递归规则依赖

如果依赖图中存在一条涉及 R 的 循环路径，则规则 R 具有递归依赖。

注

依赖图不受基础图影响。

4.3.2 依赖图算法

以下算法给出了 从一个规则集构建依赖 图的一种可能方法。一致性取决于生成符合依赖图定义的依赖图， 而不是使用此过程。 

define mergeLabel(oldLabel, newLabel):
    # 闭合依赖覆盖开放依赖。
    if oldLabel == "open" and newLabel == "open":
        the result is "open"
    else:
        the result is "closed"
    endif
enddefine

# 输出 -- 带有规则顶点和已标记边的依赖图。
define buildDependencyGraph(ruleSet):
    # edgeLabelMap 将 (R1, R2) 映射到 "open" 或 "closed"
    let edgeLabelMap be a map from pair (rule, rule) to label

    foreach rule R1 in ruleSet.rules:
        let bodyDependencies = {}

        if R1.evaldata then:
            # 将规则中的每个三元组模式 TP 分类为需要 "open" 或 "closed"
            # 具体取决于它是否位于否定元素中。
            foreach rule element RBE in R1.body:
                if RBE is a negation element:
                    if RBE.evaldata then:
                        foreach triple pattern TP in RBE.inner:
                            let item be a pair (TP, "closed")
                            add item to bodyDependencies
                        endfor
                    endif
                else if RBE is a triple pattern element of triple pattern TP:
                    let item be a pair (TP, "open")
                    add item to bodyDependencies
                else if RBE is a filter element:
                    # 不执行任何操作
                else if RBE is an assignment element:
                    # 不执行任何操作
                endif
            endfor
        endif

        foreach pair (triple pattern TP, depLabel) in bodyDependencies:
            if R1 is a run-once rule:
              set depLabel to "closed"
            endif
            # 查找此三元组模式元素或否定元素的依赖。
            foreach rule R2 in ruleSet.rules:
                foreach triple template TT in R2.head:
                    if triple pattern TP matches triple template TT:
                        let key = (R1, R2)
                        if edgeLabelMap contains key:
                            let oldLabel = edgeLabelMap.get(key)
                            let merged = mergeLabel(oldLabel, depLabel)
                            edgeLabelMap.set(key, merged)
                        else:
                            edgeLabelMap.set(key, depLabel)
                        endif
                    endif
                endfor
            endfor
        endfor
    endfor

    let DP = { }
    foreach entry ((R1, R2), label) in edgeLabelMap:
        add an edge (R1 -> R2) labeled with label to DP
    endfor

    the result is DP
enddefine

4.4 分层

分层是将一个规则集 划分为一个有序的分层层级序列（也称为 “层”，单数为“层”）的过程。较低层中的规则 会在较高层中的规则之前求值。

分层对规则之间的依赖施加约束， 以确保否定元素和单次运行规则 仅依赖于 使用较早（较低）的层和 基础图计算出的结果。 这保证了对给定基础图上的一个规则集求值会得到唯一、明确定义且有限的 结果。

注

分层过程也可以用于作出其他求值 决策。本文档描述了一致 求值的必要条件，并给出了一种形成 分层的可能方法。实现需要满足此处 描述的条件以获得兼容行为，但不 要求按所给方式实现该算法。

分层层级

一个分层层级 SL 是由 两个互不相交的规则集合组成的对 （SL.once、SL.general）。 SL.once 恰好是该层级的单次运行 规则； 这些规则各自在分层层级求值开始时 恰好求值一次。 SL.general 是该层级中剩余规则的集合， 这些规则会重复求值，直到不再推理出新的三元组。

分层

一个规则集的分层是一个分层层级序列。 一个规则集中的每个规则恰好出现在其中一个 分层层级的一个集合中。

一个分层的分层层级从 零开始编号。一个规则的层号是 包含该规则的分层层级的编号。 层号较小的规则处于 较低层； 层号较大的规则处于 较高层。

对于规则集的依赖图中从规则 R1 到规则 R2 的每条边：

  • 如果该边标记为闭合，则 R1 的层 号 严格大于 R2 的层 号。
  • 如果该边标记为开放，则 R1 的层 号 大于或等于 R2 的层 号。
注

一个规则集可以具有多个分层。 实现可以使用该规则集的任何分层。

4.4.1 分层条件

只有满足以下 条件时，才定义分层。如果一个规则集不满足此条件，则本 规范不会为此类规则集的求值定义结果。

分层条件
分层条件要求 一个闭合依赖所涉及的 递归依赖 不存在于一个规则集的依赖图中。
注

分层条件恰好就是 分层存在的条件：当且仅当 规则集的依赖图中没有循环路径包含一个闭合依赖时，才能 为一个规则集形成一个分层。

4.4.2 分层算法

以下算法给出了一种仅基于 规则集的可能分层。 

define stratification(ruleSet):

    let DP = Dependency graph for the rule set.
    let stratumMap be a map from rule to integer

    # 依赖图应满足分层条件。
    # 对无界分层的检查是一项防护措施，
    # 用于处理违反分层条件的情况。
    let limit = num rules + 1
    let maxStratum = 0

    # 初始化 stratumMap
    foreach rule in ruleSet.rules:
        stratumMap.set(rule, 0)
    endfor

    boolean changed = true
    while changed:
        changed = false
        foreach edge E in DP:
            # 从 pRule 到 qRule 且带有标签的边
            let pRule = source of edge
            let qRule = destination of the edge
            let label = edge label

            if label == "open":
                if stratumMap.get(pRule) < stratumMap.get(qRule):
                    stratumMap.set(pRule, stratumMap.get(qRule))
                    changed = true
                endif
            endif
            if label == "closed":
                if stratumMap.get(pRule) <= stratumMap.get(qRule):
                    let xStratum = 1 + stratumMap.get(qRule)
                    if xStratum > limit:
                        # 违反分层要求
                        error "Stratification error"
                    endif
                    stratumMap.set(pRule, xStratum)
                    maxStratum = max(maxStratum, xStratum)
                    changed = true
                endif
            endif
        endfor
    endwhile

    # 初始化结果映射。
    let stratumRules be a map from integer to rules.
    foreach i = 0 to maxStratum
        stratumRules.set(i, {})
    endfor

    # 收集 stratumMap 中层级编号相同的规则
    foreach rule R in map stratumMap:
        let stratumNum = stratumMap.get(R)
        add R to stratumRules.get(stratumNum)
    endfor

    # 将每个层级划分为 once 和 general
    let stratumLevels be a sequence of pairs of sets of rules.
    for i = 0 to maxStratum:
        let rules = stratumRules.get(i)
        let once = { R in rules | R is a run-once rule }
        let general = rules \ once
        stratumLevels.set(i, pair(once, general))
    endfor

    the result is stratumLevels
enddefine
注

分层条件的一个结果 是，一旦一个 单次运行规则被求值， 用于确定该规则结果的数据在 后续求值期间将不会改变。

对一个完整规则集逐步应用依赖分析和 分层，并一直进行到 求值的过程见 6.6 完整 示例。

4.5 处理导入

从 Web 读取文档具有安全影响。 对于SPARQL-RL 处理器，支持导入规则集是可选的。 此外，实现可以提供部分支持， 例如支持导入某些规则集而不支持其他规则集， 并且可能从经过验证的副本导入。

以下条件适用于导入处理：

  • 不支持导入规则集的实现必须拒绝 包含 IMPORTS 语句的规则集，并 发出错误信号。
  • 提供部分支持的实现 如果遇到其不支持的导入，必须发出错误信号。
  • 如果实现无法解析导入 文档， 或该文档在语法上无效，则实现必须发出错误信号。
  • 处理器在处理 IMPORTS 语句时必须仅导入一个规则集一次，以避免无限循环。

已解析规则集通过 递归读取另一个规则集的导入中提到的所有规则集， 从该另一个规则集产生。

一个示例算法见 A. 导入示例 算法。

5. SPARQL-RL 与 SPARQL 之间的关系

本节为非规范性的。

SRL 与 SPARQL 密切相关。SRL 被设计为与 SPARQL 兼容， 并且 SRL 中的许多构造取自或受到 SPARQL 模式匹配的启发。不过，两者之间存在一些差异。

在 SRL 中，RULE 变量在使用前始终已绑定，无论是在 FILTER 或 SET 的表达式中使用，还是在 三元组模板 中使用，这些模板位于 规则头中。SPARQL CONSTRUCT 查询和 INSERT 更新在以下情况下会 产生部分结果：变量出现在 CONSTRUCT 或 INSERT 模板中，但在 WHERE 子句中没有被赋值。

  • 良构性条件确保 变量在被用于过滤元素或赋值 元素 之前，至少出现在一个三元组模式元素中， 或作为一个赋值变量， 这些元素位于规则主体中。
  • SRL 的 SET 形式与 SPARQL 的 BIND 形式具有不同的 错误处理行为。在 SET 中遇到错误会导致 当前解被过滤掉，而 BIND 不会 在当前解中设置该变量，而是继续传递该解。 SET(?var := expr) 等同于 SPARQL 中的 BIND(expr AS ?var)，后跟 FILTER(BOUND(?var))。
  • 规则主体 WHERE 子句的语法 不包括 UNION 或 OPTIONAL 语法。 这些 SPARQL 元素可能导致未绑定变量。 UNION 或 OPTIONAL 的效果可以使用 良构规则实现。

其他差异包括：

  • NOT 的语法将内部主体限制为三元组 模式和过滤器，并且不允许嵌套模式。 NOT 在规则主体中书写它的位置作为过滤器执行， 这与 SPARQL FILTER NOT EXISTS 不同。
  • 属性路径语法仅涵盖包含 / 和 ^ 的路径。 这些路径可以展开为三元组模式。 它不允许任意长度运算符 * 和 +。 在 SPARQL-RL 中，可以通过递归这种更通用的方法 表达任意长度路径。
  • SRL 语法中不包含某些函数。没有 COALESCE 或 BOUND。也没有哈希函数。没有 RAND，因为它每次被 调用时都会产生不同的结果。
    注
    NOW() 是允许的，并被定义为在整个规则集求值过程中返回相同的 时间点。
  • 使用 BNODE 会在每次调用时产生不同的空白节点。 规则集求值的结果将产生彼此 图同构的推理图。

  • UUID 和 STRUUID 可用于生成唯一标识符。 规则不应检查这些生成的标识符，而只应使用它们 来生成三元组。

    可以使用专用生成器来测试可重现性， 类似于测试 NOW 的结果。

6. 规则集求值

本节定义对给定数据上的规则集进行求值的结果。 它并不规定必须将该算法作为实现方法。 实现可以使用任何能生成相同结果的算法。 

Inputs: graph G, called the base graph, and a rule set RS.
Output: an RDF graph GI of inferred triples

推理出的三元组不包括 基础图三元组集合中已有的三元组。

6.1 求值定义

解映射
一个解映射 μ 是一个偏 函数 μ : V → T， 其中 V 是所有变量的集合， T 是所有 RDF 术语的集合。 μ 的定义域表示 为 dom(μ)，它是 V 中 μ 有定义的子集。当明确指的是解映射时，可以使用术语 解。 用 μ0 表示满足以下条件的解映射： dom(μ0) 为空集。
替换函数

替换函数，或简称替换， 是一个函数 subst(μ, 三元组模式)， 它返回一个三元组模式， 其中该三元组模式中变量 var 的每次出现，如果该变量位于 dom(μ) 中，则会被 解映射为 var 给出的 RDF 术语替换。 如果所得三元组模式没有变量，那么它就是一个 RDF 三元组。

函数 subst(μ, 三元组模板) 也以类似方式定义。三元组模板中变量的每次出现 都会被 解映射为 var 给出的 RDF 术语替换。

模板实例函数
模板实例函数是一个函数 replaceBlankNodes(list of triple templates) ，它 返回一个三元组模板列表，其中参数中的每个空白节点 都被一个新的空白节点替换。 同一空白节点的多次出现 会被同一个新的空白节点替换。
求值 图
求值图是一个 RDF 图，它合并了基础图 以及规则集求值期间产生的所有三元组。
图匹配
图匹配查找将 三元组模式映射到 RDF 图中三元组的方式。

令 G 为一个 RDF 图，TP 为一个三元组模式。 函数 graphMatch(G, TP) 返回所有可能的 解的集合，这些解 应用于三元组模式时，会产生一个位于 图 G 中的三元组。

令 G 为一个 RDF 图，TP 为一个三元组模式， V 为 TP 中出现的变量集合。 

graphMatch(G, TP) = { μ | dom(μ) = V and subst(μ, TP) is a triple in G }
解兼容
如果两个解 S1 和 S2 在共同变量上取值一致，则它们是兼容的。

令 S1 和 S2 为解。 

compatible(μ1, μ2) = true
                       if forall v in dom(μ1) intersection dom(μ2)
                           μ1(v) = μ2(v)
compatible(μ1, μ2) = false otherwise
解 序列
解序列是解的多重集。 该序列没有定义顺序。 它等同于无序列表，并且可以包含重复项。
解合并
如果两个解兼容，则两个解的合并是这样一个解： 它将每个解的变量映射到 两个解中任一解所提供的 RDF 术语。
令 μ1、μ2 为解映射，S1 和 S2 为解序列。 
merge(μ1, μ2) = μ such that
                    μ(v) = μ1(v) if v in dom(μ1)
                    μ(v) = μ2(v) otherwise
merge(S1, S2) = { μ |
                    μ1 in S1, μ2 in S2
                    and compatible(μ1, μ2)
                    μ = merge(μ1, μ2) }
注

merge(μ1, μ2) 的定义域 是 domain(μ1) ∪ domain(μ2)。

如果两个解没有共同变量，那么它们是兼容的， 并且这两个解的合并是 μ1 和 μ2 的并集。

有效布尔值
函数 EBV(x) 返回一个 RDF 术语的有效布尔值。

6.2 求值准备

规则集求值涉及收集所有导入的规则集， 按照 4.5 处理 导入中所述构建一个单一的组合规则集。

接下来，使用以下步骤准备组合规则集 以进行求值。

  1. 检查每个规则是否是良构规则，如 4.2 良构性 条件中所述。
  2. 计算依赖图，如 4.3.2 依赖图算法中所述。
  3. 计算组合规则集的一个分层，如 4.4 分层中所述。 4.4.2 分层算法 给出了一种计算分层的方法。

6.3 表达式求值

一个表达式，无论用于过滤元素还是 赋值元素，都相对于 一个解映射进行求值。该解映射为 表达式中的每个变量提供 RDF 术语值。 4.2 良构性条件的良构性要求 确保表达式中的所有变量 都出现在解映射中。 

define evalFunction(F, μ):
    # F 是一个表达式：RDF 术语、变量或 op(expr1, ..., exprN)
    # 其中 op 是函数或函数形式。
    # μ 是解映射
    if F is an RDF term:
        return F
    if F is a variable:
        # 根据良构性，F ∈ dom(μ)。
        return μ(F)
    # F 的形式为 F = op(expr1, ..., exprN)
    if op is a functional form (e.g., IF, logical-or):
        # 专门针对 op 求值；op 可能只对部分实参求值。
        # 例如，IF(c, t, f) 对 c 求值，然后恰好对 t 或 f 中的一个求值。
        return the value defined for op over expr1, ..., exprN under μ
    # op 是普通函数：先对所有实参求值。
    return op(evalFunction(expr1, μ), ..., evalFunction(exprN, μ))
enddefine

6.4 规则求值

对一个规则求值时，首先根据规则主体计算一个解 序列， 然后使用该解序列中的每个解映射， 通过规则头生成三元组。

三元组模式中的空白节点表现得像变量。 这与 SPARQL 图模式匹配兼容。 

# 对规则主体求值
# 此函数返回一个解序列

define evalRuleElements(B, SEQ, G, GD):
    where
        B is a sequence of rule elements
        SEQ is a solution sequence
        G and GD are RDF graphs

    foreach rule element rElt in B:

        if rElt is a triple pattern element TP:
            X = graphMatch(G, TP)
            SEQ1 = {}
            foreach μ1 in X:
                foreach μ2 in SEQ:
                    if compatible(μ1, μ2):
                      μ3 = merge(μ1, μ2)
                      add μ3 to SEQ1
                    endif
                endfor
            endfor
        endif

        if rElt is a filter element F:
            SEQ1 = {}
            foreach solution μ in SEQ:
                let x = evalFunction(F.expr, μ)
                if EBV(x) is true:
                    add μ to SEQ1
                endif
            endfor
        endif

        if rElt is a negation element N:
            SEQ1 = {}
            foreach solution μ in SEQ:
                S = sequence{ μ }
                if N.evaldata:
                    NEG = evalRuleElements(N.inner, S, G, GD)
                else:
                    NEG = evalRuleElements(N.inner, S, GD, GD)
                endif
                if NEG is empty:
                    add μ to SEQ1
                endif
            endfor
        endif

        if rElt is an assignment A:
            SEQ1 = {}
            foreach solution μ in SEQ:
                let x = evalFunction(A.expr, μ)
                if x is not an error:
                    # 向解 μ 添加映射 A.var -> x
                    let μ2 be a solution mapping μ ∪ { (A.var, x) }
                    add μ2 to SEQ1
                else:
                    # 错误：丢弃解 μ
                endif
            endfor
        endif

        SEQ = SEQ1
    endfor

    return SEQ
enddefine

define evalRule(R, G, GD):
    where
        R is a well-formed rule
        G and GD are RDF graphs
    let B be R.body
        where each blank node in a triple pattern in R.body
        is replaced by a variable which is not used in the rule.
        The same variable is used for each occurrence of the
        same blank node, and a different variable is used for
        each different blank node.

    # 由一个不映射任何变量的解构成的解序列。
    let SEQ0: Solution sequence = { μ0 }

    if R.evaldata:
        let SEQ = evalRuleElements(B, SEQ0, G, GD)
    else:
        let SEQ = evalRuleElements(B, SEQ0, GD, GD)
    endif

    # 对规则头求值
    let OUT = empty set
    foreach μ in SEQ:
        let S = {}
        # 规则头中的每个空白节点都替换为一个新的空白节点
        let HT = replaceBlankNodes(R.head)
        foreach triple template TT in HT
            let triple = subst(μ, TT)
            Add triple to S
        endfor
        OUT = OUT ∪ S
    endfor
    return OUT
enddefine
注

OUT 可能包含同时也位于基础图中的三元组。

6.5 规则集求值

对一个规则集的求值被定义为执行该规则集一个 分层中的每个层，其中每个层都会被 完整地 按顺序执行，然后才进入下一个层。 对一个层求值时，首先对该层中的 每个单次运行规则求值，然后重复对该层中的 一般规则求值，直到不再产生新的三元组。 

let G0 be the input base graph
let RS be the rule set
let D be the graph of all DATA triples in RS

Apply stratification to RS

let LS be the sequence of layers after stratification

# 推理图
let GI = { t ∈ D | t ∉ G0 }

# 求值图和数据块
let GE = G0 ∪ D

foreach stratum ST in LS:
    foreach rule R in ST.once:
        let X = evalRule(R, GE, G0)
        let Y = { t ∈ X | t ∉ GE }
        GI = GI ∪ Y
        GE = GE ∪ Y
    endfor

    let finished = false
    while ! finished:
        finished = true
        foreach rule R in ST.general:
            let X = evalRule(R, GE, G0)
            let Y = { t ∈ X | t ∉ GE }
            if Y is not empty:
                finished = false
                GI = GI ∪ Y
                GE = GE ∪ Y
            endif
        endfor
    endwhile
endfor
the result is GI

6.6 完整示例

本节为非规范性的。

本节逐步展示一个完整 规则集的求值过程：确定规则依赖 （4.3 规则 依赖）、 计算分层 （4.4 分层）， 并依次对每个层求值以产生 推理图 （6.5 规则集 求值）。

该示例描述了软件组件及其依赖关系： 一个前端依赖于应用服务器，而应用服务器依赖于 数据库和日志库。数据库存在一个已知 漏洞。规则沿依赖链传播漏洞暴露关系， 为暴露于严重漏洞的组件赋予 :criticallyExposed 状态，为不严重的组件赋予 :safeToDeploy 状态，并为每个严重暴露的组件创建 通知。 （实际中，一个漏洞是否影响组件 取决于部署的版本；该示例省略了版本信息，并 直接声明漏洞。） 为简洁起见，基础图直接声明 :dependsOn 三元组， 而不是像 3.1 三元组 模式中那样从更具体的关系派生它们。

示例 13：完整示例：数据和规则 
:frontend rdf:type :Component ;
          :dependsOn :app .
:app      rdf:type :Component ;
          :dependsOn :db ;
          :dependsOn :logger .
:db       rdf:type :Component ;
          :hasVulnerability :vuln1 .
:logger   rdf:type :Component .
:vuln1    :severity 9.1 .
# R1
RULE { ?x :exposedTo ?v } WHERE { ?x :hasVulnerability ?v }

# R2
RULE { ?x :exposedTo ?v } WHERE { ?x :dependsOn ?y . ?y :exposedTo ?v }

# R3
RULE { ?x :status :criticallyExposed }
WHERE { ?x :exposedTo ?v . ?v :severity ?s . FILTER(?s >= 9.0) }

# R4
RULE { ?x :status :safeToDeploy }
WHERE { ?x rdf:type :Component . NOT { ?x :status :criticallyExposed } }

# R5
RULE { [] rdf:type :Notification ; :concerns ?x }
WHERE { ?x :status :criticallyExposed }

这些规则在注释中标记为 R1 到 R5，本节其余部分 使用这些标签引用它们。 它们是从 3.2 递归到 3.5 赋值 和创建 RDF 术语中引入的规则。 该规则集没有 IMPORTS，因此导入处理 不会改变它；也没有 DATA 块，因此求值仅 从基础图开始。

6.6.1 确定 依赖

将每个规则主体中的每个三元组模式与 每个规则头中的三元组模板进行比较，以确定哪些规则 依赖于哪些规则 （4.3 规则 依赖）。

  • R1 的主体是单个三元组模式 ?x :hasVulnerability ?v。没有任何规则头包含能 生成谓语为 :hasVulnerability 的三元组的三元组模板， 因此该模式只能匹配数据。 R1 没有依赖。
  • R2 的主体有两个三元组模式。 ?x :dependsOn ?y 无法匹配任何规则头，因此它只能匹配 数据。?y :exposedTo ?v 与 R1 的头模板 ?x :exposedTo ?v 匹配，也与 R2 自身的头匹配。 两次出现都是三元组模式元素 （它们不出现在否定元素内部，并且 R2 不是单次运行规则），因此 R2 对 R1 具有开放依赖，并且 对自身具有开放依赖。 R2 对自身的依赖使 R2 成为递归规则。
  • 在 R3 的主体中，模式 ?x :exposedTo ?v 与 R1 和 R2 的头匹配，因此 R3 对它们各自具有开放 依赖。模式 ?v :severity ?s 不匹配任何 规则头。
  • 在 R4 的主体中，模式 ?x rdf:type :Component 不匹配任何规则头：唯一一个谓语为 rdf:type 的头模板位于 R5 中，而它的宾语 :Notification 是 与 :Component 不同的 RDF 术语，因此任何生成的 三元组都无法匹配。 模式 ?x :status :criticallyExposed 出现在 否定元素 NOT { ?x :status :criticallyExposed } 中，并且 与 R3 的头模板匹配。因为该模式 出现在否定元素中，所以 R4 对 R3 具有闭合 依赖。
  • 在 R5 的主体中，模式 ?x :status :criticallyExposed 与 R3 的头匹配。R5 的头包含一个 空白节点，因此它对 R3 的依赖是闭合 依赖，即使该模式是普通的 三元组模式元素。 任何规则主体中的模式都不匹配 R5 的头模板， 因此没有规则依赖于 R5。

因此，依赖图有五个顶点和六条 边：

  • R2 → R1（开放）
  • R2 → R2（开放）
  • R3 → R1（开放）
  • R3 → R2（开放）
  • R4 → R3（闭合）
  • R5 → R3（闭合）

尽管 R4 和 R5 都不直接依赖于 R1 或 R2，但它们各自通过 R3 对二者都具有传递依赖。

图中唯一的循环是自环 R2 → R2， 它是开放依赖。没有循环涉及闭合 依赖，因此满足分层条件， 并且该规则集具有明确定义的结果。

6.6.2 计算 分层

按照 分层算法， 每个规则都从第 0 层开始。然后反复检查各条边， 直到没有任何变化：

  • 一条开放边要求源规则处于 与其目标相同或更高的层。所有四条开放边在 每个规则都处于第 0 层时已经满足此条件，因此它们 不会引起任何变化。
  • 一条闭合边要求源规则处于 严格高于其目标的层，因为目标 必须先运行至完成。边 R4 → R3 （闭合）发现 R4 和 R3 都处于第 0 层，因此 R4 被 移到第 1 层。同样，边 R5 → R3 （闭合）将 R5 移到第 1 层。

再次遍历各条边不会产生变化，因此这些层 已最终确定。然后将每个层划分为 单次运行规则和一般规则。 R5 的头中有一个空白 节点，因此它是单次运行规则；该规则集的其他规则 都不是单次运行规则。 分层如下：

  • 第 0 层：一般规则 R1、R2、R3；没有单次运行规则
  • 第 1 层：单次运行规则 R5；一般规则 R4

此顺序体现了较高 层中规则的意图。一个组件是否可以安全部署，以及哪些 组件需要通知，只有在 所有 :status :criticallyExposed 三元组都已派生后才能确定 —— 而派生这些三元组的规则 R3 会在 较低的层中完成，同时完成的还有向它提供数据的规则 R1 和 R2。

6.6.3 对各层求值

求值遵循 6.5 规则集 求值的算法。 求值图 GE 以基础图开始，而 推理图 GI 初始为空。每个层都会按顺序求值至 完成：该层的规则按轮次求值， 并重复这些轮次，直到某一轮不产生新的三元组。 该算法并未固定同一轮中 对一个层内规则求值的顺序；此处跟踪使用 R1、R2、R3 的顺序。不同的顺序可能会将相同的 推理分散到不同数量的轮次中，但由于 第 0 层会运行至完成，因此会产生相同的最终图。

由于此规则集没有 DATA 块，因此在求值的每个时刻，GE 都是 G0 加 GI。因此，下面的跟踪 只记录 GI，显示求值进行时它的状态，并 用产生每个新三元组的规则进行标记。

第 0 层，第一轮。

  • R1：主体匹配 :db :hasVulnerability :vuln1，绑定 ?x = :db 和 ?v = :vuln1。 头部产生 :db :exposedTo :vuln1。 该三元组不在 GE 中，因此被添加到 GE 和 GI 中。
  • R2：主体将 ?x :dependsOn ?y 与 ?y :exposedTo ?v 连接。GE 现在包含 :db :exposedTo :vuln1，因此连接得到一个解： ?x = :app、?y = :db 和 ?v = :vuln1 （来自 :app :dependsOn :db）。 头部产生 :app :exposedTo :vuln1，这是新的， 因而被添加。此时还没有 :frontend 的解，因为 在此次对 R2 的求值开始时， :app :exposedTo :vuln1 尚不在 GE 中。
  • R3：?x :exposedTo ?v 现在匹配 :db 和 :app； 与 :vuln1 :severity 9.1 连接并应用 FILTER(?s >= 9.0) 后保留两个解。 头部产生 :db :status :criticallyExposed 和 :app :status :criticallyExposed，两者都是新的。

:app :exposedTo :vuln1 .                    # 新增 (R2)
:db  :status :criticallyExposed .           # 新增 (R3)
:app :status :criticallyExposed .           # 新增 (R3)

产生了新的三元组，因此第 0 层的求值 继续进行下一轮。

第 0 层，第二轮。

  • R1：与之前一样进行匹配；:db :exposedTo :vuln1 已经 在 GE 中，因此不会产生新内容。
  • R2：连接现在还会得到 ?x = :frontend、?y = :app 和 ?v = :vuln1，产生 新的三元组 :frontend :exposedTo :vuln1。 暴露关系用了两轮沿依赖链传播了两步。
  • R3：产生新的三元组 :frontend :status :criticallyExposed。 
# 第 0 层第二轮后的 GI
:db       :exposedTo :vuln1 .
:app      :exposedTo :vuln1 .

第 0 层，第三轮。 现在每个规则的每个解都只产生已经 位于 GE 中的三元组。GI 保持不变。 没有新的三元组意味着第 0 层已经完成：所有 能够派生的 :exposedTo 三元组以及所有 :status :criticallyExposed 三元组 都已经派生出来。

第 1 层，单次运行规则。 首先对该层的单次运行规则求值， 每条规则恰好求值一次。

  • R5：主体匹配三个 :status :criticallyExposed 三元组，得到解 ?x = :db、?x = :app 和 ?x = :frontend。对于每个解，实例化头部 会创建一个新的空白节点，每个解产生两个三元组， 它们构成每个严重暴露 组件的通知。即使该层中的 一般规则随后会被 重复求值，R5 也不会再次求值。

第 1 层，一般规则的第一轮。

  • R4：模式 ?x rdf:type :Component 匹配 :frontend、:app、:db 和 :logger。 （它不会匹配刚刚由 R5 创建的 rdf:type :Notification 三元组。） 否定元素 NOT { ?x :status :criticallyExposed } 拒绝 :frontend、:app 和 :db 的解，因为 GE 中分别包含它们的 :status :criticallyExposed 三元组。 只有解 ?x = :logger 保留下来，产生新的 三元组 :logger :status :safeToDeploy。

7. SPARQL-RL 语法

一个 SPARQL-RL 文档 是一个采用 UTF-8 [RFC3629] 编码并以 RuleSet 产生式开始，且符合 7.6 语法中定义的附加约束的 RDF 字符串。 仅允许Unicode 标量值， 其范围为 U+0000 到 U+D7FF 以及 U+E000 到 U+10FFFF。 这排除了 代理代码点， 即范围 U+D800 到 U+DFFF。

7.1 版本声明

一个 版本标签是标识 SPARQL-RL 语法和语义 一致性的字符串。

版本标签
版本标签
"1.2"

版本声明应该在文档的较前位置给出。

多个 VERSION 指令 可以出现在一个SPARQL-RL 文档中。 每个指令适用于该指令之后的文档部分， 直到遇到另一个指令或到达文档末尾。

版本标签也可以由 媒体类型的 version 参数给出。在没有当前 VERSION 指令的情况下， 会采用作为媒体类型一部分指定的版本。

7.2 空白字符

空白字符 （产生式 WS）用于 分隔两个否则会被（错误地）识别为一个 终结符的终结符。下面以大写字母表示的规则名称指示空白字符 具有重要意义的位置；这些规则构成了用于构建 SPARQL-RL 解析器的一种可能的终结符选择。

空白字符在产生式 String中具有重要意义。

7.3 注释

注释以位于 IRIREF、 STRING_LITERAL1、 STRING_LITERAL2、 STRING_LITERAL_LONG1 或 STRING_LITERAL_LONG2 之外的 # 开始， 并持续到行尾（由 LF 或 CR 标记）， 如果注释标记之后没有行尾，则持续到文件末尾。 注释被视为空白字符。

7.4 IRI 引用

相对 IRI 引用使用基 IRI 按照 统一资源标识符（URI）：通用 语法 [RFC3986] 进行解析，仅使用 第 5.2 节中的基本算法。 不执行基于语法的规范化或基于方案的规范化 （RFC3986 第 6.2.2 节和第 6.2.3 节中所述）。 IRI 引用中额外允许的字符按照与 URI 引用中非保留字符相同的方式处理，依据 国际化资源标识符 （IRI） [RFC3987] 第 6.5 节。

BASE 指令定义用于解析 相对 IRI 引用的基 IRI，依据 [RFC3986] 第 5.1.1 节，“嵌入内容中的基 URI ”。 第 5.1.2 节，“来自封装 实体的基 URI” 定义作用域内基 IRI 如何来自封装文档， 例如具有 xml:base 指令的 SOAP 信封或具有 Content-Location 标头的 MIME 多部分文档。 在 5.1.3，“来自检索 URI 的基 URI”中标识的“检索 URI”， 是从中检索特定SPARQL-RL 文档的 URL。 如果上述内容均未指定基 URI，则使用默认 基 URI（第 5.1.4 节，“默认基 URI”）。 每个 BASE 指令都会设置一个新的作用域内基 URI， 相对于前一个基 URI。

7.5 转义序列

SPARQL-RL 文档中使用三种形式的转义：

  • 一个 数字转义序列表示 一个 Unicode 代码点的值。

    一个数字转义序列不得产生 范围为 U+D800 到 U+DFFF 的代码点值， 这是 Unicode 代理的范围。

    \u hex hex hex hex 一个 Unicode 代码点 位于 U+0000 到 U+D7FF 以及 U+E000 到 U+FFFF 的范围内， 对应于由四个十六进制数字编码的值，按 从最高有效位到最低有效位的顺序解释。

A. 导入示例算法

本节为非规范性的。

以下算法展示了通过 递归访问所有引用的文档来解析 IMPORTS 语句的一种方法。

两个规则集 RS1 和 RS2 的规则集合并 会产生一个规则集 MR，其定义如下： 

let RS be a rule set

let V = {}

if RS has a location:

    V = { location of RS }

endif



define ruleSetMerge(rule set RS1, rule set RS2):

    let MR be a rule set

    MR.rules = RS1.rules ∪ RS2.rules

    MR.data = rdf_merge(RS1.data, RS2.data)

    MR.imports = {}

    the result is MR

enddefine



define imports(rule set RS):

    let RS2 be a rule set formed from RS.rules and RS.data

    foreach URL x in RS.imports:

        if x ∉ V:

            V = V ∪ { x }

            read rule set RS3 from URL x

            RS2 = ruleSetMerge(RS2, imports(RS3))

        endif

    endfor

    the result is RS2

enddefine



result is imports(RS)

其中 rdf_merge 是 RDF 合并 操作。

C. 安全注意事项

本节为非规范性的。

SPARQL-RL 文档可能包含引用其他 SPARQL-RL 文档并将其内容导入当前 文档的 IMPORTS 语句。 如果导入的文档本身包含自己的 IMPORTS 语句， 那些文档也会被导入。

虽然 IMPORTS 语句有助于将规则集模块化，但其使用可能 引入安全风险。 风险包括但不限于规则集 在求值时无论出于恶意还是意外而导致过度计算； 以及 HTTP 请求被拦截并返回不同的文档， 包括过时的副本。

将 SPARQL-RL 规则集应用于 RDF 图可能导致 大量计算和内存使用，这可能被利用 来造成拒绝服务。 应用程序应注意限制应用 SPARQL-RL 规则集可能导致的计算量和 内存使用量。

SPARQL-RL 语法采用 UTF-8 [RFC3629] 编码，并 允许 在字符串数据中使用未转义的控制字符。 尽管本规范不会直接向最终用户公开此内容， 但它可能会通过用户代理呈现，这可能导致所呈现的文本 因此类字符而产生误导。

SPARQL-RL 可用于处理和创建任意应用程序数据； 安全注意事项会因使用领域而异。 适用于文本的安全工具和协议 （例如 PGP 加密、校验和验证、密码保护的压缩） 也可以用于SPARQL-RL 文档。 必须实施安全/隐私协议，以反映 SPARQL-RL 规则集求值结果中 信息的敏感性。

SPARQL-RL 的安全注意事项包括 RDF 数据以及 诸如 RDF Turtle 等格式的安全注意事项。

D. 隐私注意事项

本节为非规范性的。

SPARQL-RL 文档可以包含附加的应用程序数据， 其中可能包括个人身份信息（PII）的表达 或其他可被视为敏感的信息。 建议发布包含此类信息的规则集的作者仔细 考虑发布此类信息的必要性和用途， 以及数据预计被使用并可能被披露的地区 所适用的法规（例如 GDPR、 CCPA、 其他法规）， 尤其应考虑访问这些数据是否需要授权措施。
