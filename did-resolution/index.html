摘要

去中心化标识符（DID）解析是为特定 DID 获取 DID 文档及随附元数据的过程。该过程以一个 DID 和一组选项作为输入，并返回一个 DID 文档以及 有关已解析文档和解析请求的相关元数据。已解析的 DID 文档 是一组信息，可支持与 DID 主体进行可通过密码学验证的 交互，包括密码学公钥等机制。本规范涵盖 DID 解析所使用的算法和指南，并依赖于核心 DID 规范 去中心化 标识符（DID）v1.0，该规范完整详细地描述了底层 DID 架构。

1. 引言

DID 解析是为给定 DID 获取 DID 文档 的过程。这是可对任何 DID 执行的四项必需 操作之一（“读取”；其他操作为 “创建”、“更新”和“停用”）。这些操作的细节会因 DID 方法而异。在 DID 解析的基础上，DID URL 解引用是为给定 DID URL 检索资源 表示的过程。能够执行这些过程的软件 和/或硬件称为 DID 解析器。

本规范定义了一个标准接口，客户端可使用该接口来执行 DID 解析和 DID URL 解引用请求，而不依赖于 DID 解析器 所支持的任何特定 DID 方法的 “Resolve” 操作。此外，本规范还定义了实现 DID 解析器或 DID URL 解引用器时相关的要求、 算法（包括其输入和结果）、架构选项，以及 各种安全和隐私考量。

请注意，虽然本规范为 DID 解析定义了一些基础级功能，但与 DID 的 可验证数据 注册表通信所需的实际步骤由适用的 DID 方法规范定义。

1.1 实现者概览

本节为非规范性内容。

通过使用标准 resolve(did, resolutionOptions) 接口（如 DID 解析一节中所定义）调用 DID 解析器，即可获得 DID 文档 以及随附元数据（例如 contentType、证明、版本信息），应用程序 可使用这些信息来验证用户的密码学密钥、服务端点 或状态。

例如，若要检索 DID did:example:123 在过去某个 时间点的状态，客户端应用可以使用 versionTime 解析选项来解析该 DID，如下所示：
resolve("did:example:123", {"versionTime":"2021-05-10T17:00:00Z"}) 或者，客户端可以解引用 诸如 did:example:123?service=files&relativeRef=/resume.pdf 的 DID URL， 以获取通过 DID 文档中声明的服务存储的用户简历。

此外，本规范的 DID URL 解引用算法 展示了客户端如何跟随片段（例如 #key-1）提取特定的 验证方法，该方法位于 DID 文档中。 建议实现者使用 DID 解析测试套件 验证其解析器，该测试套件会测试规范性的 MUST 要求和错误条件（例如无效的 DID、 已停用的 DID、不支持的方法、相对 URL 展开等），从而使 客户端应用能够可靠地依赖不同 DID 方法之间正确的解析行为。

1.2 一致性

除标记为非规范性的章节外，本规范中的所有编写指南、图表、示例和注释均为非规范性内容。除此之外，本规范中的所有内容均为规范性内容。

本文档中的关键词 MAY、MUST、MUST NOT、NOT REQUIRED、OPTIONAL、RECOMMENDED、REQUIRED 和 SHOULD 应按 BCP 14 [RFC2119] [RFC8174] 中的说明解释，且仅当它们如本文所示全部以 大写字母出现时才如此解释。

一致性 DID 解析器是指任何 以软件和/或硬件实现、并符合 4. DID 解析中相关规范性陈述的算法。

一致性基于网络的 DID 解析器 是一种 一致性 DID 解析器，并且还符合 10.1 HTTP(S) 绑定中的 规范性陈述。

一致性 DID URL 解引用器是指 任何以软件和/或硬件实现、并符合 5. DID URL 解引用中相关规范性陈述的算法。

1.3 受众

本节为非规范性内容。

本规范有三类主要受众：一致性 DID 方法的实现者；一致性 DID 解析器的实现者；以及希望使用 DID 解析器 解析 DID 的系统和服务实现者。预期 受众包括但不限于软件架构师、数据建模人员、 应用开发人员、服务开发人员、测试人员、运维人员以及用户 体验（UX）专家。参与去中心化身份、可验证凭证和安全 存储相关广泛标准化工作的其他人员也可能有兴趣阅读本规范。

1.4 用例

本节为非规范性内容。

DID 解析规范旨在通过定义标准化接口来支持广泛的用 例，该接口可独立于任何特定 DID 的 DID 方法来解析 DID 并解引用 DID URL。这些用例 包括：

  • 去中心化地址簿：通过在地址簿中使用 DID 作为人员和 组织的标识符，这些 DID 的控制者可以 独立更新其 DID 文档的内容。通过 DID 解析，可以解析这些 DID，以获取任意给定联系人的 DID 文档当前状态， 从而提供持久稳定的标识符，以及支持持续可验证 交互所需的可更新服务和验证材料。
  • 验证可验证凭证：可验证凭证由 签发者签名并交给持有者。持有者随后可以创建 可验证表达，并将其呈现给验证者。通过使用 DID 标识凭证中的签发者 和持有者，签发者使验证者能够使用 DID 解析来解析所标识签发者和持有者的 DID 文档，以 获取验证可验证表达上的签名所需的验证材料。
  • 可审计性：DID 解析可用于获取 DID 文档在特定时间点或特定版本的历史状态。这可 用于审计 DID 控制者的历史可验证操作；例如， 签发可验证收据或签署合同。
  • 基于 DID URL 的资源检索：DID 控制者可以向其 DID 文档添加服务端点， 这些端点指向其控制的资源；例如个人资料 图片。如果使用 DID URL 来引用这些资源，Web 应用可以 使用 DID 解析和 DID URL 解引用来检索该资源的当前版本。 DID URL 可用作这些资源的持久、可解引用 标识符，而 DID 控制者可以独立地 随时间更改该资源。

2. 术语

本节定义了本规范以及整个 去中心化标识符 基础设施中使用的术语。每当这些术语在本规范中出现时， 都会包含指向这些术语的链接。

绑定
客户端调用 DID 解析器的具体机制。这可以是 本地绑定，例如本地命令行工具或库 API；也可以是 远程绑定，例如 HTTP(S) 绑定。参见第 7.2 解析器架构节。
客户端
调用 DID 解析器 以执行 DID 解析的软件和／或硬件。也称为 支持 DID 的应用程序。
支持 DID 的应用程序
调用 DID 解析器 以执行 DID 解析的软件和／或硬件。也称为 客户端.
DID 解析结果
表示 DID 解析算法结果的数据结构。 可以包含 DID 文档。参见第 8. DID 解析结果节。
DID URL 用户
支持 DID 的应用程序的最终用户，该应用程序使用 DID URL 来实现某种目的。这可以是使用 DID URL 验证可验证凭证、发送 DIDComm 消息，或基本上任何由 DID 和 DID URL 支持的功能。交互可以是直接用户输入的结果（用户在其中输入 DID URL），也可以是更复杂的用户流程的一部分，在该流程中 DID URL 用户甚至可能看不到 DID，就像万维网的许多用户乐于点击链接而不理会所用的 URL 一样。
资源
如 [RFC3986] 所定义：“……术语 ‘资源’以一般意义使用，指任何可由 URI 标识的事物。”同样，任何资源都可以作为 DID 主体， 并由 DID 标识。
表示
如 [RFC9110] 针对 HTTP 所定义：“旨在反映 给定资源过去、当前或期望状态的信息，其格式可通过协议 方便地传达。表示由一组 表示元数据和一个可能无界的表示 数据流组成。”DID 文档是描述 DID 主体的信息表示。参见 去中心化标识符（DID）v1.0。
本地绑定
一种 绑定，其中 客户端调用运行在同一 网络主机上的 DID 解析器，例如通过本地命令行工具或库 API。 在这种情况下，DID 解析器有时也称为“本地 DID 解析器”。 参见第 7.2 解析器 架构节。
远程绑定
一种 绑定，其中 客户端调用运行在 不同网络主机上的 DID 解析器，例如通过 HTTP(S) 绑定。 在这种情况下，DID 解析器有时也称为“远程 DID 解析器”。 参见第 7.2 解析器 架构节。
服务
通过一个或多个 DID 服务端点 与 DID 主体或 相关实体进行通信或交互的手段。 示例包括发现服务、代理服务、社交网络 服务、文件存储服务以及可验证凭证仓库服务。
不可验证解析
DID 方法的 “Resolve” 操作在 DID 解析器 与 可验证数据 注册表之间的一种低置信度实现，用于获取 DID 文档。 对结果的完整性和正确性没有保证。参见第 7.1 方法 架构节。
验证方法

一组参数，可与某个过程一起使用，以独立 验证证明。例如，密码学公钥可作为 数字签名的验证方法；在这种用法中，它 验证签名者拥有相关联的密码学私钥。

此定义中的“验证”和“证明”旨在作广义理解。例如， 密码学公钥可在 Diffie-Hellman 密钥 交换期间用于协商用于加密的共享对称密钥。这保证了 密钥协商过程的完整性。因此，即使对该过程的描述可能不使用 “验证”或“证明”这些词，它也是另一类验证 方法。

可验证解析
DID 方法的 “Resolve” 操作在 DID 解析器 与 可验证数据 注册表之间的一种高置信度实现，用于获取 DID 文档。 在适用 DID 方法所能达到的范围内， 对结果的完整性和正确性有保证。 参见第 7.1 方法 架构节。
通用唯一标识符 (UUID)
一类由 [RFC4122] 定义的全局唯一标识符。UUID 与 DID 类似，因为它们不需要集中式注册机构。UUID 与 DID 的不同之处在于，它们不可解析，也不可通过密码学验证。
统一资源标识符 (URI)
万维网上所有资源的标准标识符格式，如 [RFC3986] 所定义。DID 是一种 URI 方案。

3. DID 参数

DID URL 语法支持 一种简单的参数格式（见 [DID-CORE] 中的 Query 一节）。向 DID URL 添加 DID 参数，意味着该参数 成为 资源标识符的一部分。

示例 1：带有 'versionTime' DID 参数的 DID URL 
did:example:123?versionTime=2021-05-10T17:00:00Z
示例 2：带有 'service' 和 'relativeRef' DID 参数的 DID URL 
did:example:123?service=files&relativeRef=/resume.pdf

对于存在的每个 DID 参数，其关联值 MUST 是一个 标量值 字符串，并根据 RFC3987 第 3.1 节序列化为 ASCII。

一些 DID 参数完全独立于任何特定 DID 方法，并且对所有 DID 都以相同方式发挥作用。其他 DID 参数并非由所有 DID 方法支持。在支持 可选参数的地方，预期这些参数会在支持它们的 DID 方法之间 统一运作。下表提供了常见 DID 参数，它们 在所有 DID 方法中以相同方式发挥作用。支持所有 DID 参数是 OPTIONAL。

参数 名称 描述
service 通过服务 ID 标识 DID 文档中的一个 服务。
serviceType 通过服务类型标识 服务集合中的一个或多个 服务，这些服务来自 DID 文档。
relativeRef 根据 RFC3986 第 4.2 节的相对 URI 引用，它标识 DID 服务端点上的 一个 资源， 该服务端点通过使用 service 参数从 DID 文档中选择。
versionId 标识要解析的 DID 文档 的特定版本（该版本 ID 可以是顺序编号、或 UUID， 或方法特定的）。
versionTime 标识要解析的 DID 文档的某个版本时间戳。也就是说，在指定 versionTime 之前，对某个 DID 有效的 DID 文档的最新 版本。如果存在，关联值 MUST 以 3.1 日期时间 中定义的日期时间格式表示。

实现者以及 DID 方法规范作者 可以使用此处未列出的其他 DID 参数。为实现最大 互操作性，RECOMMENDED DID 参数使用 DID Document Properties Extensions 机制 [DID-EXTENSIONS-PROPERTIES]，以避免 与同一 DID 参数在不同语义下的其他用法发生 冲突。

向 DID 解析器传递 DID 解析选项可以影响 DID 解析和 DID URL 解引用函数。此类选项不是 DID或 DID URL的一部分。这与 HTTP 类似，其中某些参数既可以包含在 HTTP URL 中，也可以作为 HTTP 标头传递。

3.1 日期时间

本规范中的所有日期时间值 MUST 是一个 ASCII 字符串，且是 [VC-DATA-MODEL] 在 可验证凭证数据模型 v2.0中定义的有效 XML 日期时间值。 此外，DID Resolution 中使用的时间戳 MUST 调整为 UTC，且不得具有亚秒十进制精度。例如： 2020-12-20T19:17:47Z

3.2 查询规范化

DID URL 查询字符串 通常会在解析流水线中的多个独立组件之间被构造、解析、 记录、缓存和比较——例如客户端、缓存代理、下游 解析器以及 DID 方法特定解析器（见 7.2 解析器 架构）。这些组件之间对 DID URL 查询字符串 的规范化不一致，可能会 悄然产生错误的解析结果、缓存污染或破坏 互操作性。本节列举了鼓励实现者和 DID 方法规范作者明确处理的边界情形。

注：DID URL 查询 字符串规范化

本节中的指南涉及如何为 解析、比较和转发的目的规范化 DID URL 查询字符串。它不同于 哪些参数应作为解析选项传递、哪些应 嵌入到 DID URL 中这一问题；该问题已在 3. DID 参数末尾关于 DID 参数与解析选项区别的注释中处理。

3.2.1 百分号编码 规范化

本节为非规范性内容。

DID URL 查询 字符串中字符的百分号编码不会改变被标识资源的身份，但 同一逻辑值的不同编码可能会被执行朴素字符串比较的实现 视为不同字符串。

鼓励比较、缓存或转发 DID URL 的实现，在比较或存储之前 规范化百分号编码。以下规则 与 RFC3986 第 6.2.2 节：基于语法的规范化一致， 可作为基线：

  1. 与非保留字符（如 RFC3986 第 2.3 节：非保留 字符中定义）相对应的百分号编码八位组， 可以解码为其字面字符形式。
  2. 所有剩余的百分号编码八位组最好使用大写 十六进制数字表示（例如使用 %2F 而不是 %2f）。
  3. 避免解码作为查询组件内保留分隔符的百分号编码字符 （例如 %26 表示 &，%3D 表示 =），因为这样做会 改变查询字符串的已解析结构。

鼓励 DID 方法规范记录其 方法特定 DID 参数中哪些字符可在规范化期间安全解码。

注： relativeRef 百分号编码

relativeRef DID 参数值通常会包含百分号编码的路径分隔符和查询字符（例如 relativeRef=%2Fresume.pdf%3Fversion%3D2）。避免将这些字符作为查询级规范化的一部分进行解码，因为编码形式是有意的，并且是该值在解引用期间被正确解释为相对引用所必需的。

3.2.2 重复参数 处理

DID URL 语法 并不禁止在单个 DID URL 中重复出现 同一个查询参数名（例如 did:example:123?service=files&service=agent）。当存在重复参数时， 解析和解引用函数的行为在其他方面未由本文档规定。

鼓励实现者定义并记录其实现 在 DID URL 包含重复查询 参数名时的行为。由于本规范中定义的所有 DID 参数都具有 标量值（见 3. DID 参数），因此这些参数的任何重复出现都表示 一个歧义输入，没有明确定义的 解析行为。一种合理做法是将这样的 DID URL 视为无效， 并返回 INVALID_DID_URL 错误 （见 9. 错误）。

鼓励定义方法特定查询参数的 DID 方法规范 明确说明这些参数是否允许重复出现， 若允许，则定义解析语义（例如第一个值 优先、最后一个值优先、集合并集）。

3.2.3 按 DID 方法规范化

3. DID 参数中定义的查询参数集合并非 穷尽。DID 方法可以定义其他方法特定查询参数， 而这些参数的规范形式（包括其名称、值 格式和顺序）可能因方法而异。

鼓励 DID 方法规范为其定义的任何 方法特定查询参数指定规范形式，涵盖以下 考量：

  1. 值格式： 每个参数所期望的编码、字符 集以及有效值范围。
  2. 参数顺序： 查询参数的相对顺序 是否具有语义意义；若有，规范 顺序是什么。在没有明确指南的情况下， 在比较 DID URL 的逻辑等价性时，将参数顺序视为无关紧要 是合理的。
  3. 大小写敏感性： 参数名或 值是否区分大小写。本 规范中定义的参数名是区分大小写的 ASCII 字符串。在缺少 DID 方法规范相反指南的情况下，参数 值最好视为区分大小写。

需要测试两个 DID URL 逻辑等价性的实现（例如，用于 缓存查找）在应用 3.2.1 百分号编码规范化所述的百分号编码 规范化之后，鼓励采用与参数顺序无关的比较， 除非适用的 DID 方法规范定义了具有语义意义的规范参数 顺序。

4. DID 解析

DID 解析 函数通过使用适用 DID 方法的 “Resolve” 操作， 将一个 DID 解析为 DID 文档，如 方法操作中 所述。

DID 解析是 DID URL 解引用的一部分，如 5. DID URL 解引用中所述。

注

要能够解引用 DID URL，首先需要一个 DID 文档，它 是 DID 解析 过程的结果。DID 文档会在 DID URL 解引用过程中以多种方式使用。 术语 DID 解析 与 RFC3986 第 1.2.2 节中定义的 “URI 解析”一致，因为它提供了 “解引用 URI 所必需的适当参数”。

所有 一致性 DID 解析器都实现以下函数， 其抽象形式如下： 

resolve(did, resolutionOptions) →
   « didResolutionMetadata, didDocument, didDocumentMetadata »

所有 一致性 DID 解析器 MUST 至少为一个 DID 方法实现 DID 解析 函数，并且 MUST 能够返回一个 DID 文档。

一致性 DID 解析器 实现不得以任何方式更改 此函数的签名。 DID 解析器 实现可以将 resolve 函数映射到特定方法的内部函数，以 执行实际的 DID 解析过程。 DID 解析器 实现除了此处指定的 resolve 函数外，还可以实现并 暴露具有不同签名的其他函数。

resolve 函数的输入变量如下：

did
这是要解析的 DID。此输入 是 REQUIRED， 且该值 MUST 是 去中心化标识符（DID）v1.0中定义的一致性 DID。
resolutionOptions
一个 元数据结构，由传递给 resolve 函数的 输入选项组成，并且包含 did 本身之外的内容。此结构在 4.1 DID 解析 选项中进一步定义。此输入是 REQUIRED，但该 结构 MAY 为空。

此函数返回多个值，且不限制 这些值如何一起返回。 resolve 的返回值为 didResolutionMetadata、 didDocument 和 didDocumentMetadata。 这些值说明如下：

didResolutionMetadata
一个 元数据结构，由与 DID 解析过程结果相关的值组成。此结构 是 REQUIRED，并且在解析过程中发生错误时， 此结构 MUST NOT 为空。此结构在 4.2 DID 解析 元数据中进一步定义。如果解析不成功， 此结构 MUST 包含一个描述 错误的 error 属性。参见第 9. 错误节。
didDocument
如果解析成功，此值 MUST 是一个 DID 文档，且 能够以 去中心化标识符（DID）v1.0 规范的一种一致性 表示 来表示。已解析 DID 文档中的 id 值 MUST 与已解析的 DID 字符串相等。如果 解析不成功，此值 MUST 为空。
didDocumentMetadata
如果解析成功，此值 MUST 是一个 元数据结构。 此结构包含关于 didDocument 属性中所含 DID 文档的元数据。 如果解析不成功，此输出 MUST 是一个 空的 元数据结构。 此结构在 4.3 DID 文档元数据中进一步定义。

4.1 DID 解析选项

这是一个 元数据结构，其中包含 DID 解析过程的输入选项。

此结构中的可能属性及其可能值 SHOULD 注册到 DID Resolution Extensions [DID-EXTENSIONS-RESOLUTION]。 本规范定义以下常见输入选项：

accept
调用者首选的 DID 文档 表示的媒体类型。 该值 MUST 按 HTTP 语义 第 12.5.1 节中定义的 Accept 标头值来表示。DID 解析器 实现 SHOULD 使用此值来确定返回的 didDocument 的 表示， 前提是此类 表示 受支持且可用。此属性是 OPTIONAL。
expandRelativeUrls
一个布尔标志，指示 DID 解析器将 相对 DID URL 在 DID 文档中展开为符合 DID URL 语法的一致性绝对 DID URL。
versionId
定义见 3. DID 参数。
versionTime
定义见 3. DID 参数。

4.2 DID 解析元数据

这是一个 元数据结构，其中包含关于 DID 解析过程的元数据。

此元数据通常会在每次调用 DID 解析 函数时发生变化，因为它表示关于 解析过程本身的数据。

此元数据的来源是 DID 解析器。

DID 解析元数据的示例包括：

  • 返回内容的媒体类型（contentType）。
  • 错误对象（error）（见第 9. 错误节）。
  • 由 DID 解析器生成的证明，例如用于 建立可信解析（proof）。
  • DID 解析过程的持续时间。
  • 缓存信息（见第 11.2 缓存节）。
  • DID 解析过程中所使用的 可验证数据注册表 的 URL、IP 地址和/或其他网络信息。

此结构中的可能属性及其可能值 SHOULD 注册到 DID Resolution Extensions [DID-EXTENSIONS-RESOLUTION]。 本规范定义以下常见元数据属性：

contentType
返回的 didDocument 的媒体类型。此 属性是 OPTIONAL。如果存在，此属性的值 MUST 是 一个 ASCII 字符串，并且是 一致性 表示的媒体类型。在这种情况下， resolve 函数的调用者 MUST 在 确定如何解析和处理 didDocument 时使用此值。
error
错误数据结构定义于 [RFC9457]。本 规范定义的错误可见第 9. 错误节。 其他错误 SHOULD 注册到 DID Resolution Extensions [DID-EXTENSIONS-RESOLUTION]，并附上定义该错误的规范为其指定的 URL（参见第 9. 错误节）。
proof

一些 DID 解析器和 DID URL 解引用器 在执行 DID 解析或 DID URL 解引用 函数时使用证明。详情见 7.2 解析器架构。

DID 解析元数据 MAY 包含 proof 属性。 如果存在，该值 MUST 是一个 集合，其中每个 项都是表示证明的 映射。此属性的使用 和证明类型与 DID 方法无关。

4.3 DID 文档元数据

这是一个 元数据结构，其中包含关于 DID 解析过程的元数据。

此元数据通常不会在每次调用 DID 解析 函数时发生变化，除非 DID 文档 发生变化，因为它表示关于 DID 文档的数据。

此元数据的来源是 DID 控制者和/或 DID 方法。由 DID 控制者证明的 DID 文档元数据本身并不天然保证准确性。建议客户端在依赖 DID 文档元数据来指导业务 逻辑时谨慎行事。

DID 文档元数据的示例包括：

  • DID 及其关联 DID 文档 被创建或更新时的时间戳（例如 created、 updated、nextUpdate）。
  • 关于 DID 文档的版本信息（例如 versionId、 nextVersionId）。
  • 由 DID 控制者添加的证明，或由 DID 方法的 可验证数据 注册表生成的证明，这些证明可能 用于建立控制权限或启用 可验证 解析 （例如 proof）。
  • 关于控制者、能力、委托等的元数据。
  • 方法特定元数据，例如区块链或其他 可验证数据 注册表中某条记录的区块号、索引、交易哈希、确认数等。

此结构中的可能属性及其可能值 SHOULD 注册到 DID Document Properties Extensions [DID-EXTENSIONS-PROPERTIES]。本 规范定义以下常见 元数据属性。

created
DID 文档 元数据 SHOULD 包含 created 属性， 用于指示 Create 操作的时间戳。该 属性的值 MUST 以 3.1 日期时间中定义的日期时间格式表示。
updated
DID 文档 元数据 SHOULD 包含 updated 属性，用于指示已解析文档版本的最后一次 Update 操作 的时间戳。该属性的值 MUST 以 3.1 日期时间中定义的日期时间格式表示。 如果从未对该 DID 文档执行过 Update 操作，则省略 updated 属性。如果存在 updated 属性，当两个时间戳之间的差异 小于一秒时，它可以与 created 属性具有相同值。
deactivated
如果 DID 已被 停用， DID 文档 元数据 MUST 包含此属性， 且布尔值为 true。如果 DID 尚未被停用， 此属性是 OPTIONAL，但如果包含，则 MUST 具有布尔值 false。
nextUpdate
如果已解析文档版本不是文档的最新版本， DID 文档 元数据 MAY 包含 nextUpdate 属性。它表示下一次 Update 操作的时间戳。 该属性的值 MUST 以 3.1 日期时间中定义的日期时间格式 表示。
versionId
DID 文档 元数据 SHOULD 包含 versionId 属性，用于指示已解析文档 版本的最后一次 Update 操作的版本。该属性的值 MUST 是 ASCII 字符串。
nextVersionId
如果已解析文档版本 不是文档的最新版本，DID 文档 元数据 MAY 包含 nextVersionId 属性。它表示下一次 Update 操作的版本。 该属性的值 MUST 是 ASCII 字符串。
equivalentId

DID 方法 可以定义逻辑等价的 DID的不同形式。 一个示例是，当某个 DID 在注册到 可验证数据 注册表之前采用一种形式， 而在完成此类注册之后采用另一种形式。在这种情况下， DID 方法 规范可能需要将一个或多个与已解析 DID逻辑等价的 DID 表达为 DID 文档的属性。这就是 equivalentId 属性的目的。

DID 文档元数据 MAY 包含 equivalentId 属性。如果存在，该值 MUST 是 一个 集合，其中每一项都是符合 字符串规则且符合 去中心化标识符（DID） v1.0一节的字符串。该关系是一项 声明，表示每个 equivalentId 值都与 id 属性值在逻辑上 等价，因此指向同一 DID 主体。每个 equivalentId DID 值 MUST 由与 id 属性 值相同的 DID 方法 产生，并且是该方法的一种形式。（例如 did:example:abc == did:example:ABC）

一致性 DID 方法规范 MUST 保证每个 equivalentId 值都与 id 属性值在逻辑上 等价。

请求方预期保留 id 和 equivalentId 属性中的值，以确保 与它们包含的任何值的后续交互 都会被正确处理为逻辑等价（例如，在数据库中保留所有 变体，以便与其中任意一个的交互都映射到同一 底层账户）。

注： 更强的等价性

equivalentId 是一种比 alsoKnownAs 强得多的等价形式，因为 这种等价性 MUST 由管辖性的 DID 方法保证。使用 equivalentId 意味着同一个 DID 文档 同时描述 equivalentId DID 和 id 属性的 DID。

如果请求方不保留 id 和 equivalentId 属性中的值，并确保 与它们包含的任何值的后续交互 都被正确处理为逻辑等价，则可能会 出现负面或意外问题。强烈建议实现者 遵守与此元数据属性相关的指令。

canonicalId

canonicalId 属性与 equivalentId 属性相同，但有以下区别：a) 它关联的是单个值而不是一个集合；b) 该 DID 被定义为 所含 DID 文档范围内该 DID 主体的规范 ID。

DID 文档元数据 MAY 包含 canonicalId 属性。 如果存在，该值 MUST 是一个 字符串，且 符合 去中心化标识符（DID）v1.0一节中的规则。 该关系是一项声明，表示 canonicalId 值与 id 属性值在逻辑上等价，并且 该 canonicalId 值由 DID 方法 定义为所含 DID 文档范围内 DID 主体的规范 ID。一个 canonicalId 值 MUST 由与 id 属性值相同的 DID 方法产生，并且是该方法的一种形式。 （例如 did:example:abc == did:example:ABC）。

一致性 DID 方法规范 MUST 保证 canonicalId 值与 id 属性值在逻辑上等价。

请求方预期将 canonicalId 值用作该 DID 主体的主要 ID 值，并将所有 其他等价值视为次要别名（例如，更新 其系统中的相应主要引用，以反映新的 规范 ID 指令）。

注： 规范等价性

canonicalId 与 equivalentId 是相同的等价性声明， 只是它被限制为单个值， 且该值被定义为 DID 主体在 DID 文档范围内的规范值。与 equivalentId 一样，使用 canonicalId 意味着同一个 DID 文档 同时描述 canonicalId DID 和 id 属性的 DID。

如果解析方不将 canonicalId 值用作 DID 主体的主要 ID 值，并将所有其他等价值 视为次要别名，则可能会出现与用户体验相关的负面或意外问题。 强烈建议实现者遵守与此元数据 属性相关的指令。

proof

许多 DID 方法在执行 方法操作时使用证明。详情见 7.1 方法 架构。

DID 文档元数据 MAY 包含 proof 属性。如果存在，该值 MUST 是一个 集合，其中每一项都是表示证明的 映射。此属性的使用 以及证明类型是 DID 方法特定的。

4.4 DID 解析算法

DID 解析器 实现以下 DID 解析 算法。

  1. 验证 input DID 是否符合 DID 语法的 did 规则。 如果不符合，DID 解析器 MUST 返回以下结果：
    1. didResolutionMetadata：error object，其 type 设为 https://www.w3.org/ns/did#INVALID_DID
    2. didDocument：null
    3. didDocumentMetadata：«[ ]»
  2. 确定实现此算法的 DID 解析器 是否支持 input DID 的 DID 方法。如果 不支持，DID 解析器 MUST 返回以下 结果：
    1. didResolutionMetadata：error object，其 type 设为 https://www.w3.org/ns/did#METHOD_NOT_SUPPORTED
    2. didDocument：null
    3. didDocumentMetadata：«[ ]»
  3. 确定 input DID 解析选项 是否受实现此算法的 DID 解析器支持。 如果不支持，DID 解析器 MUST 返回以下结果：
    1. didResolutionMetadata：error object，其 type 设为 https://www.w3.org/ns/did#FEATURE_NOT_SUPPORTED
    2. didDocument：null
    3. didDocumentMetadata：«[ ]»
  4. 确定 input DID 解析选项 是否有效。如果无效，DID 解析器 MUST 返回以下结果：
    1. didResolutionMetadata：error object，其 type 设为 https://www.w3.org/ns/did#INVALID_OPTIONS
    2. didDocument：null
    3. didDocumentMetadata：«[ ]»
  5. 通过执行由 input DID 方法定义的 Resolve 操作，获取 input DID 的 DID 文档：
    1. 如果 input DID 不存在，则返回以下结果：
      1. didResolutionMetadata：error object，其 type 设为 https://www.w3.org/ns/did#NOT_FOUND
      2. didDocument：null
      3. didDocumentMetadata：«[ ]»
    2. 如果 input DID 已被 停用，则返回以下结果：
      1. didResolutionMetadata：«[ ... ]»
      2. didDocument：null
      3. didDocumentMetadata：«[ "deactivated" → true, ... ]»
    3. 否则，Resolve 操作的结果称为 output DID 文档。 此结果 MUST 以 一致性表示来表示。
  6. 如果 input DID 解析选项 包含值为 true 的 expandRelativeUrls 选项：
    1. 遍历 output DID 文档中的所有 服务、 验证方法、 验证 关系 以及任何扩展定义的属性。
    2. 对于每一项，如果该项是对象，并且 id 属性的值是 相对 DID URL， 或者如果某个 验证 关系是 相对 DID URL：
      1. 根据 去中心化标识符（DID） v1.0中 相对 DID URL一节的规则，将该 相对 DID URL 解析为符合 DID URL 语法的一致性绝对 DID URL。
    3. 通过将 相对 DID URL替换为已解析的 绝对 DID URL，更新 output DID 文档。
  7. 返回以下结果：
    1. didResolutionMetadata: «[ "contentType" → 输出 DID 文档媒体类型, ... ]»
    2. didDocument：output DID document
    3. didDocumentMetadata: «[ ... ]»

如果 DID 解析器 在执行 DID 解析算法期间 遇到任何意外错误，它 必须 返回以下 结果：

  1. didResolutionMetadata：error object，其 type 设 为 https://www.w3.org/ns/did#INTERNAL_ERROR
  2. didDocument：null
  3. didDocumentMetadata：«[ ]»

5. DID URL 解引用

解引用是指获取资源的引用，并将该资源引入当前计算上下文，通常通过调用特定于该资源类型的处理器来完成。

对 HTTP(S) URL 解引用是指从 Web 服务器检索资源的表示，并调用特定于所检索资源的媒体类型的处理器。对于网页，这意味着在浏览器中使用适当的渲染视图显示检索到的 HTML。

对 DID URL 解引用是指检索 DID URL 所引用的资源，并调用适当的函数，将其应用于当前上下文。

DID 支持多种不同的处理策略，使 DID URL 能够引用通过各种方式提供的资源，包括基于 Web 的资源、嵌入 DID 文档中的资源、由 DID 文档中的完整性证明保护的资源，以及使用去中心化系统存储在“链上”的资源。

无论适用何种处理策略，所有 DID URL 解引用都需要解析嵌入 DID URL 中的 DID，并使用 Resolve 的结果（通常是 DID 文档）来确定并随后调用适当的处理器。

以下 DID URL 解引用算法描述了符合规范的 客户端 如何准备、执行对符合规范的 DID 解析器 的 Resolve 调用，并处理其响应。

所有符合规范的客户端 必须 执行此算法中的步骤。唯一必需的输入是要解引用的 DID URL、使用该 DID URL 的上下文，以及有关首选解析器和可用处理器的配置详情。解引用的预期副作用是调用处理器，将任何检索到的资源应用于当前上下文。此类处理器的接口不在本规范的范围内。

所有符合规范的客户端 必须 允许 DID URL 用户 为任意特定的 DID 方法设置要使用的特定解析器。同样，符合规范的客户端 应该 允许 DID URL 用户 为任意特定处理策略设置要使用的处理器。如何向用户提供这些设置不在本规范的范围内。

注意

工作组目前正在探索这一新的 DID URL 解引用算法。它比先前的算法更加模块化，并使用 DID URL 和解析结果来确定处理策略并调用适当的处理器。

5.1 DID URL 解引用算法

  1. 准备解析
  2. 解析 DID
  3. 确定处理策略
  4. 调用处理器
  5. 使用处理器结果

5.1.1 准备解析

  1. 验证 input DID URL 符合 did-url 规则，该规则定义于 DID URL 语法。否则，DID URL 客户端 必须 结束处理，不再进行后续处理，并指明因以下原因而失败： https://www.w3.org/ns/did#INVALID_DID_URL
  2. 选择 能够处理该 DID 方法的解析器。实现者 必须 允许用户为特定 DID 方法选择其信任的解析器。预期实现将通过某种配置机制提供此功能，其细节不在本规范的范围内。
  3. 从 DID 所在的 DID URL中提取该 DID。例如，DID URL did:ex:abc#key-1 包含 DID did:ex:abc.
  4. 准备 DID 解析选项。这些选项可以由 DID URL 查询参数提升而来，也可以由对 DID URL 解引用的上下文中的业务规则确定。客户端执行此算法时所处的业务上下文决定是否应将任一给定查询参数提升为解析选项。有关解析选项及其含义的详情，请参见 解析算法 。

5.1.2 解析 DID

  1. 调用 所选解析器的 resolve 函数，传入准备好的解析选项和 DID，以获取以下对象对应的权威 DID 文档 ： input DID URL。
  2. 解释 resolve 的响应，以考量任何错误或警告。如适用，则直接返回而不再处理，并引发 DEREFERENCING_ERROR_RESOLUTION_ERROR ，其中包含 Resolve 操作返回的错误。否则，如果响应提供了足够的信息，则继续处理。
  3. 重复 上述过程，直到返回最终解析结果。当初始解析结果不完整或失败时，客户端可以根据解引用发生的上下文调整解析参数并重试。例如，解析器可能需要更多输入，或者客户端可以启发式地尝试其他解析器选项以找到更合适的 DID 文档，例如请求特定时间点的 DID 文档版本。

5.1.3 确定处理策略

成功解析 DID 文档及随附的元数据后，下一步是确定用于处理 DID URL的适当策略。这涉及分析 DID 解析结果的内容（包括 DID 文档及其元数据），以及 DID URL 的路径和查询组成部分，以确定检索资源的方法。

使用解析结果，从 服务步骤 开始执行以下步骤，直到确定处理策略。一旦设置策略，就立即结束处理。

  1. 服务步骤

    如果 service 作为 DID 查询参数存在，首先检查 DID URL中是否存在多个 service 参数。如果存在，则引发错误 DEREFERENCING_ERROR_MULTIPLE_SERVICE_PARAMETERS 并继续执行 默认 DID 文档步骤。如果只有一个 service 参数，则使用 服务选择算法 选择适当的服务对象。然后，如果没有匹配的服务对象，则引发错误 DEREFERENCING_ERROR_SERVICE_NOT_FOUND 并继续执行 默认 DID 文档步骤。如果所选对象的服务类型定义了处理策略，则将策略设置为该策略。如果服务类型未定义处理策略，则将策略设置为 默认服务处理器 策略。否则，继续执行 PathHandlers 步骤.

  2. PathHandlers 步骤

    如果 DID URL 包含非空路径部分，则使用 PathHandler 路径匹配算法 选择路径处理器对象。如果未选中任何路径处理器对象，则继续执行 文档属性步骤。如果选中了多个处理器对象，则引发错误 DEREFERENCING_ERROR_MULTIPLE_MATCHING_PATH_HANDLERS 并继续执行 默认 DID 文档步骤。如果唯一选中的路径处理对象具有定义了处理器策略的次要类型，则将策略设置为该策略。如果没有，则引发错误 DEREFERENCING_ERROR_PATH_HANDLER_HANDLER_NOT_DEFINED 并继续执行 默认 DID 文档步骤.

  3. 文档属性步骤

    如果 DID 文档包含任何已知会定义处理器策略的属性，则检查这些属性中是否有任何属性适用于该 DID URL。如果没有，则继续执行 方法特定步骤。如果 DID 文档包含多个适用于该 DID URL的属性，则引发错误 DEREFERENCING_ERROR_MULTIPLE_DOCUMENT_PROPERTIES 并继续执行 默认 DID 文档步骤。如果 DID 文档包含一个具有已知处理器策略且适用于该 DID URL的属性，则将策略设置为该属性定义的策略。否则，继续执行 方法特定步骤.

  4. 方法特定步骤

    如果 DID 方法定义了方法特定的处理器策略，则检查该处理器是否适用于该 DID URL。如果适用，则将处理器策略设置为 DID 方法所指定的策略。如果没有适用的方法特定处理器策略，则继续执行 查询参数步骤.

  5. 查询参数步骤

    如果存在要求特定处理策略的查询参数，则检查此类参数是否多于一个。如果是，则引发错误 DEREFERENCING_ERROR_MULTIPLE_QUERY_PARAMETERS 并继续执行 默认 DID 文档步骤。如果只有一个此类查询参数，则将策略设置为查询参数规范所定义的策略。否则，继续执行 元数据步骤.

    并非所有查询参数都会改变处理策略。例如， versionTime 和 versionId 仅改变解析结果，而不影响解引用步骤。

  6. 元数据步骤

    如果 DID 解析元数据或 DID 文档元数据包含任何已知会定义处理器策略的属性，则检查这些属性是否适用于该 DID URL。如果只有一个此类属性，则将策略设置为该属性定义的策略。如果有多个适用属性，则引发错误 DEREFERENCING_ERROR_MULTIPLE_METADATA_PROPERTIES 并继续执行 默认 DID 文档步骤。否则，继续执行 默认 DID 文档步骤.

  7. 默认 DID 文档步骤 如果尚未确定其他处理器策略，则将策略设置为 返回 DID 文档.

5.1.4 调用处理器

  1. 执行 已确定的处理器策略，使用实现该策略的处理器。如果客户端没有实现所确定策略的处理器，则停止处理并引发错误 DEREFERENCING_ERROR_HANDLER_NOT_FOUND.

5.1.5 使用处理器结果

最后一步是在发起解引用的上下文中，使用调用处理器所得的结果来完成 DID URL 解引用过程。这可能涉及

  1. 显示返回的资源，
  2. 将片段标识符应用于返回的资源，使其在显示界面中滚动到可见位置，
  3. 使调用进程能够获取结果，或者
  4. 在无法完成解引用时产生错误 DEREFERENCING_ERROR_FAILED 。

DID URL 可以包含预期在解引用期间应用的查询参数，例如 transformKeys 扩展。预期支持此类扩展的实现在适当时会于本阶段应用这些扩展。

5.2 服务选择算法

当 DID URL 包含 service 参数时，使用以下算法确定应使用哪个服务来解引用该 DID URL。

示例 3 
did:example:1234?service=%23files
  1. 从 DID 文档中选择 service ，其 id 属性应匹配 service DID 查询参数的值。如果 id 属性或 service DID 参数中的任一项或两者包含相对引用，则对应的绝对 URI 必须 被计算并用于确定是否匹配，所用规则见 RFC3986 第 5 节： 引用解析 以及 相对 DID URL 一节，后者位于 去中心化标识符（DID） v1.0。
  2. 如果没有服务匹配，则停止后续处理并引发错误 DEREFERENCING_ERROR_SERVICE_NOT_FOUND；不选择任何服务。
  3. 如果有多个服务匹配，则停止后续处理并引发错误 DEREFERENCING_ERROR_MULTIPLE_MATCHING_SERVICES；不选择任何服务。
  4. 如果只有一个服务匹配，则选中该服务。继续执行 服务步骤.

5.3 默认服务处理器

如果选定服务的类型没有专用处理器，或者服务的唯一 type 值是 PathHandler，则使用此默认处理器策略。调用时，执行以下算法。

考虑以下 DID URL 和 DID 文档片段：

示例 4 
    did:example:abc/image.png?service=#FileServer
  
service : [{
  "id":"#FileServer",
  "path":"/",
  "serviceEndpoint": [
    "https://example.com/didimages/",
    "https://example.com/otherImages/",
    "https://example.com/lastImages/"]
...
}]

  1. 选择服务端点 如果 serviceEndpoint 是单个值，则使用该值。如果 serviceEndpoint 是数组，则随机选择该服务的一个 serviceEndpoint 值作为起点。由于数组中的每个值预期都可解析到同一组资源（触发该服务的任意给定 DID URL 都会从任一端点检索到同一资源），成功解引用其中任意一个就足够了。实现 必须 跟踪每个尝试过的端点，以便依次尝试各端点，直到返回成功结果或已尝试完整组端点。换句话说，仅在所有端点均失败后才引发失败错误 DEREFERENCING_ERROR_NO_SERVICE_ENDPOINTS_SUCCEED 。 
    serviceEndpoint = "https://example.com/didimages/"
  2. 确定资源路径 通过提取 DID URL 的不匹配部分并将其追加到 serviceEndpoint的路径来构造资源路径。首先，将 DID URL 路径的不匹配部分提取为 pathExtension。上述示例中的 pathExtension 为“image.png”，这是去除服务的 path 值“/”所得；去除前 DID URL 的路径部分为 /image.png。 
    pathExtension = "image.png";
    将 pathExtension 追加到 serviceEndpoint 的路径部分，以定义 resourcePath. 
    resourcePath = /didimages/image.png
  3. 规范化路径 规范化所得的 ResourcePath 以创建 NormalizedResourcePath ，方法是按 [RFC3986] 第 5.2.4 节“移除路径片段”的定义移除点片段。然后检查所得的 NormalizedResourcePath ，验证 NormalizedResourcePath 最左侧的字符是否匹配以下对象路径部分最左侧的字符： serviceEndpoint。如果不匹配，则引发错误 DEREFERENCE_ERROR_PATH_NORMALIZATION_ERROR。
  4. 构造资源 URL 将选定 serviceEndpoint 中的路径部分替换为规范化资源路径，保持服务端点 URL 的所有其他元素不变。 
    ResourceUrl = https://example.com/didimages/image.png
  5. 解引用资源 URL 根据方案解引用所得的 ResourceUrl ，按照其协议方案（scheme）进行处理。例如，对于 https URL，对该 URL 执行 GET 操作。
注意

此默认处理器不处理 relativeRef 参数。其他处理器可自由处理 relativeRef 并使用任何其他 DID URL 查询参数；要使用此类处理器，请在 DID 文档的服务对象中指定关联的 type 值。

5.4 PathHandler 路径匹配算法

当 DID 文档包含路径以及一个或多个类型为 PathHandler 的对象时，使用以下算法确定应使用哪个对象和处理器来解引用 DID URL。

  1. 在类型为 PathHandler的对象中，选择其 path 属性从 DID URL 路径部分的开头起具有最长完整匹配的对象。 path 属性的完整值必须出现在 DID URL的路径部分中。
    给定 DID URL did:example:1234/image.png 以及以下三个 PathHandling 对象
    示例 5 
    service : [{
  "id":"#PathServiceRoot",
  "type":["PathHandler", "PathService"],
  "path":"/"
  ...
},{
  "id":"#PathServiceImage",
  "type":["PathHandler", "PathService"],
  "path":"/image"
  ...
}],
linkedResource : [{
  "id":"#SecuredImage",
  "type":["PathHandler", "LinkedResource"],
  "path":"/image.png"
  ...
}]

    在此场景中，将选中 id 为 SecuredImage 的 linkedResource，其处理策略由 LinkedResource 规范定义。

  2. 如果两个或多个对象具有相同长度的匹配，则停止处理并返回错误 DEREFERENCING_ERROR_MULTIPLE_MATCHING_PATH_HANDLERS.

5.5 返回 DID 文档

调用此处理器时，只需返回 Resolve 检索到的 DID 文档，包括可能引发的任何解引用错误。

5.6 解引用错误

解引用可能产生下述多种不同错误。客户端 应该 在适当时使用这些错误。

DEREFERENCING_ERROR_FAILED
发生了通用或未分类的内部错误，导致整个解引用过程失败。（使用处理器结果)
DEREFERENCING_ERROR_HANDLER_NOT_FOUND
没有可用于所指示处理策略的处理器。（调用处理器)
DEREFERENCING_ERROR_MULTIPLE_DOCUMENT_PROPERTIES
解引用过程在尝试解引用 DID URL 时遇到多个相互冲突的文档属性。（文档属性步骤)
DEREFERENCING_ERROR_MULTIPLE_MATCHING_PATH_HANDLERS
解引用过程发现多个不同的路径处理器与请求的路径匹配。（PathHandlers 步骤)
DEREFERENCING_ERROR_MULTIPLE_METADATA_PROPERTIES
解析元数据包含多个相互冲突的属性，导致无法为解引用作出明确选择。（元数据步骤)
DEREFERENCING_ERROR_MULTIPLE_QUERY_PARAMETERS
DID URL 包含多个不兼容的查询参数。（查询参数步骤)
DEREFERENCING_ERROR_MULTIPLE_SERVICE_PARAMETERS
DID URL 包含多个 service 参数。（服务参数步骤)
DEREFERENCING_ERROR_MULTIPLE_MATCHING_SERVICES
解引用过程根据 URL 参数识别出多个匹配的服务端点，因而无法作出明确选择。（服务步骤, 服务选择算法)
DEREFERENCING_ERROR_NO_SERVICE_ENDPOINTS_SUCCEED
识别出了有效服务端点，并尝试了网络交互，但所有请求都未返回成功响应。（默认服务处理器)
DEREFERENCE_ERROR_PATH_NORMALIZATION_ERROR
DID URL 包含的路径被规范化后得到的 URL 超出了所选服务端点的管辖范围。DID URL 路径覆盖了服务端点的路径部分。（默认服务处理算法)
DEREFERENCING_ERROR_PATH_HANDLER_HANDLER_NOT_DEFINED
DID URL 包含路径，DID 文档也包含匹配的 PathHandler 对象，但解引用环境中未定义或注册用于处理它的适当处理器。（PathHandlers 步骤)
DEREFERENCING_ERROR_RESOLUTION_ERROR
解引用过程失败，因为底层标识符解析过程在解引用完成之前遇到了错误。（解析 DID)
DEREFERENCING_ERROR_SERVICE_NOT_FOUND
解引用过程中引用的特定服务（例如，通过 service 查询参数引用的服务）未在解析后的文档中找到。（服务步骤)

6. 元数据结构

输入和输出元数据通常会参与 DID 解析, DID URL 解引用以及其他 DID 相关过程。用于传达此元数据的结构 必须 是一个 属性 映射。每个属性名 必须 是一个 字符串。每个属性值，以及任何 复杂数据结构（例如映射或列表）中的每个值，必须 是 字符串, 数字, 映射, 列表, 集合, 布尔值，或 null。整个元数据结构 必须 能够按照以下规则序列化： JSON 序列化规则 ，该规则位于 [INFRA] 规范中。实现 可以 将元数据结构序列化为其他数据格式。

注

数值表示在不同平台和序列化方式之间会有所不同（例如 IEEE-754 浮点数、固定位宽整数，以及 “bigint”/bignum 类型）。Infra 标准尚未为数字提供 全面的 指南。建议实现者避免使用可能在不同平台上 表示不同的元数据数字——尤其是 以下内容：

  • 非整数值，例如浮点数或分数
  • 超出常见固定位宽范围的整数，例如大于 32 位无符号整数的整数（最大值 232 - 1 或 4,294,967,295）

当互操作性需要此类值时，属性定义的一种良好做法是 使用规范的 字符串序列化（例如，使用明确定义的精度和 舍入策略格式化为浮点数字符串），并记录任何预期的范围或格式。

所有使用元数据结构作为输入或输出的函数实现， 都能够以确定性的方式完整表示此处描述的所有数据类型。 由于使用元数据结构的输入和输出是根据数据类型而非其序列化来 定义的，因此 表示方法属于该函数实现的内部事项， 不在本规范范围内。

7. DID 解析架构

（存在风险的功能）问题 3

本节目前被标记为存在风险。

7.1 方法架构

DID 解析 算法涉及根据某个 DID 的 DID 方法执行其上的 Resolve 操作（见 4. DID 解析）。

每种 DID 方法都会定义此方法操作，即 DID 解析器如何 从 DID 获得 DID 文档。底层数据格式、协议、技术基础设施和过程在 各种 DID 方法之间可能 差异很大。

DID 方法考量示例包括以下内容：

  • DID 方法可能使用不可变区块链、分布式账本、分布式 文件系统、点对点网络或其他去中心化基础设施作为其 可验证数据 注册表（的一部分）。
  • DID 方法可能使用 DNS、HTTP 或 Web 服务器作为其 可验证数据 注册表（的一部分）。
  • DID 方法可能使用上述技术基础设施的任意组合。
  • DID 方法可能以明文形式在 可验证数据注册表中存储实际的 DID 文档， 并可能在 “Resolve” 操作期间简单地检索该 文档。
  • DID 方法可能以更复杂的方式定义其 “Resolve” 操作， 该方式可能涉及中间的、部分的或临时的 DID 文档， 并使用多步骤过程“即时”构造 DID 文档。
  • DID 方法在执行 “Resolve” 操作期间可能需要与远程服务器或网络交互。
  • DID 方法可能以完全本地的方式执行 “Resolve” 操作， 不需要与任何远程服务器或网络交互。例如， 在 [DID-KEY] 方法中，DID 本身封装了一个公钥， 而 “Resolve” 操作只是一个简单的本地转换过程。

基于上述考量，并结合 DID 方法的 “Resolve” 操作的性质， DID 解析器与 可验证数据注册表 之间的交互 可以被视为 可验证解析或 不可验证解析：

可验证解析会在适用 DID 方法可达到的范围内，最大化对 “Resolve” 操作结果完整性和 正确性的信心。这可以通过多种方式完成， 例如以下方式：

  • 如果可以在本地、可信 网络环境中访问 可验证数据注册表， 则可以完成 可验证解析。
    • 例如，在基于区块链的 DID 方法中，如果 区块链全节点部署在本地服务器上，则可能完成 可验证解析。
  • 如果通过远程服务器访问 可验证数据注册表， 那么如果该远程服务器 可信，且可以通过安全信道访问，仍可能完成 可验证解析。
  • 如果通过 远程服务器访问 可验证数据注册表， 但 可验证解析可能通过以下方式 完成：DID 解析器有某种方式 验证由 DID 方法返回的 DID 文档和 DID 文档元数据。
    • 例如，在基于区块链的 DID 方法中，即使无法直接访问 区块链全节点，仍可以通过使用 处理元数据来验证数据的轻客户端，实现 可验证解析。

不可验证解析不具有此类保证， 因此 较不理想，例如：

  • 如果通过远程且不可信的 中介访问 可验证数据注册表， 则会发生 不可验证解析。
    • 例如，在基于区块链的 DID 方法的情况下，可以使用由第三方运营的远程区块链浏览器 API 从 区块链中查找数据。
注： 实现细节

可验证解析是否可能，不仅取决于 DID 方法 本身，还取决于 DID 解析器 实现该 DID 方法的方式。 DID 方法 MAY 允许多种方式来实现其 “Resolve” 操作，并且 SHOULD 就至少一种 实现 可验证解析的方式提供指导。

注：可验证数据注册表的 局限性

与 可验证解析相关的保证 总是受到 DID 方法底层 可验证数据 注册表的架构、协议、密码学元素和其他 方面的限制。被认为最强的 可验证解析 实现形式，是那些不需要与任何远程网络交互的形式 （例如，参见 [DID-KEY]）， 以及那些 最大限度减少对特定网络基础设施依赖、将 “信任根”缩减为已证明的熵和密码学的形式（例如，参见 [KERI]）。

为了启用 可验证解析，许多 DID 方法使用数字 签名、状态证明、Merkle 树中的包含证明、密码学 事件日志或其他类型的证明。如果 DID 方法使用 此类证明，则它 MUST 在其 DID 方法规范中说明如何使用这些证明 来验证 “Resolve” 操作结果的正确性。

DID 方法 MAY 也将此类证明包含在 DID 文档 本身中，或包含在 DID 文档元数据的 proof 属性中。 即使 客户端不信任 DID 解析器， 这也可能使其能够独立验证 DID 解析 过程的结果。

请注意，源自 DID 方法的证明是 DID 方法特定的， 并且必须在适用 DID 方法的技术范围内理解。对 DID 文档 或 DID 文档元数据 的简单签名并不一定证明对 DID 的控制，也不保证该 DID 文档就是 该 DID的 正确文档。 这些证明有助于在 DID 方法 本身所关涉的范围内，验证 DID 解析过程结果的完整性和 真实性。然而，它们并不 保证 客户端与 DID 解析器之间的 绑定是 安全的。另请参见 7.2 解析器 架构。

7.2 解析器架构

DID 解析和 DID URL 解引用算法被定义为抽象函数（见 4. DID 解析和 5. DID URL 解引用）。

这些算法由 DID 解析器和 DID URL 解引用器实现，并由 客户端通过 绑定调用。绑定 定义了如何使用具体的编程或 通信接口访问抽象函数。

绑定示例包括以下内容：

  • DID 解析器 可以在应用程序中通过 调用软件库或 SDK 来调用。
  • DID 解析器 可以作为命令行工具调用。
  • DID 解析器 可以通过 HTTP(S) API 或其他 网络协议调用，例如见 10.1 HTTP(S) 绑定。

基于上述考量，并结合绑定的性质， 客户端与 DID 解析器或 DID URL 解引用器之间的交互 可以被视为 本地绑定或 远程绑定：

在可能的情况下，优先使用 本地绑定，因为它们 最大限度减少对第三方和中介的依赖，降低安全 风险，并最大化对 DID 解析和 DID URL 解引用 函数结果完整性和正确性的信心。

在某些情况下，可能无法使用 本地绑定；例如，在受限的 IoT（物联网） 环境中，或当 DID 方法需要复杂 基础设施时，或当需要支持许多不同 DID 方法时。

如果 客户端 使用 远程绑定，则适用 以下考量：

  • 远程绑定 SHOULD 使用 可信的 DID 解析器 实例，最好由 客户端 自身控制（例如自托管）。
  • 远程绑定 SHOULD 使用 安全信道，例如 VPN 和/或带有双向认证的 TLS。
  • 客户端可以通过 远程绑定查询多个 DID 解析器， 并比较结果。

DID 解析器 MAY 也可以在 DID 解析元数据的 proof 属性中包含证明。

请注意，源自 DID 解析器的证明 与 DID 方法无关，并且可由 DID 解析器 跨所有 DID 方法统一应用。这些证明有助于 在 DID 解析器本身 所关涉的范围内，验证 DID 解析 过程结果的完整性和真实性。然而，它们并不 保证适用 DID 方法的 “Resolve” 操作结果本身是 正确的。另请参见 7.1 方法架构。

7.2.1 多种方法

DID 解析器 可能支持用于多种 DID 方法的 DID 解析 算法：

在这种情况下，7.1 方法架构中关于 可验证解析和 不可验证解析 实现的上述考量，分别适用于每个受支持的 DID 方法。

7.2.2 代理解析

DID 解析器 MAY 调用另一个 DID 解析器， 后者作为代理执行 DID 解析 算法，如 4. DID 解析中所定义。

第一个 DID 解析器随后充当 客户端， 并选择适合的 绑定来调用第二个 DID 解析器。 例如，DID 解析器 可以通过 本地绑定（例如命令行 工具）调用，而该工具又通过 远程绑定（例如 HTTP(S) 绑定）调用另一个 DID 解析器。

使用代理解析时，“下游”解析器 SHOULD 以透明方式保留来自 “上游”解析器的所有 DID 解析元数据和 DID 文档元数据， 包括可能存在的任何证明。在此过程中，“下游”解析器 MAY 添加其自己的 DID 解析元数据， 包括关于代理解析过程本身的任何元数据。

注： 与 DNS 的比较

这类似于 DNS 架构中的“存根解析器”调用“递归解析器”， 尽管这些概念并不完全可比（DNS 解析 使用单一的具体协议，而 DID 解析是一个抽象函数， 由不同 DID 方法和不同 绑定实现）。

7.2.3 客户端侧解引用

DID URL 解引用算法的不同部分 可以由 解析器架构中的不同组件执行。

具体而言，解引用含有 DID 片段的 DID URL时，片段由客户端在使用 DID URL 解引用处理器结果过程中处理。

7.3 示例

给定 DID URL did:xyz:1234#keys-1，可以通过本地绑定调用 DID 解析器以执行 DID 解析算法，而客户端通过解引用片段（即 DID 文档的一部分）完成 DID URL 解引用算法。

给定 DID URL did:xyz:1234?service=agent&relativeRef=%2Fsome%2Fpath%3Fquery#frag，调用 DID 解析器以执行 DID 解析算法，而客户端完成 DID URL 解引用算法的其余部分，处理查询参数、解引用资源，然后解引用该资源内的片段。

给定 DID URL did:xyz:1234#keys-1，可以通过本地绑定调用 DID 解析器，后者通过远程绑定调用另一个 DID 解析器以执行 DID 解析算法，而客户端通过解引用片段（即 DID 文档的一部分）完成 DID URL 解引用算法。

10.1 HTTP(S) 绑定

本节定义一种 DID 解析器 绑定 ，它通过 HTTP(S) 端点公开 DID 解析 函数（包括所有解析选项和元数据）。参见 7.2 解析器 架构.

注

使用 HTTP(S) 解析器会产生对远程方的依赖，请求者的隐私 可能会因包含各种 HTTP 标头而降低，例如 Referer、Origin、Cookies 和 Authorization。此外， 客户端与 DID 解析器 之间某个组件的缓存 可能会进一步降低请求的隐私性。

HTTP(S) 绑定需要一个已知的 HTTP(S) URL，可在该 URL 调用 DID 解析器。此 URL 称为 DID 解析器 HTTP(S) 端点。

此绑定通常被视为 远程绑定，但如果 HTTP(S) 端点运行在 本地环境中，例如 localhost 上，也可以是 本地绑定。

所有 符合规范的 DID 解析器 必须 实现 GET 版本的 HTTPS 绑定 ，并且 可以 实现 POST 版本。所有 HTTPS 绑定 必须 使用 TLS。在证书中使用 DNS 名称 并非必需；解析器 可以 使用为 IP 地址签发的 TLS 证书。

使用此绑定，可以执行 DID 解析 函数（见 4. DID 解析），方法如下：

  1. 使用 DID 解析器 HTTP(S) 端点初始化一个 request HTTP(S) URL。
    示例 13 
    https://resolver.example/1.0/identifiers/
  2. 对于 DID 解析函数：
    1. 将 input DID 追加到 request HTTP(S) URL。

    3. 将 Accept HTTP request header 设为 accept resolution option 的值，以 仅请求结果中的 didDocument 值。
  3. 对于 HTTP(S) GET 绑定：
    1. 如果提供了其他 resolution options ，即除 accept 之外的选项：

    2. 对以下 URL 执行 HTTP GET 请求： request HTTP(S) URL。这会调用 DID 解析 函数，执行位置为远程 DID 解析器。

Accept: application/did-resolution

    2. 对以下 URL 执行 HTTP POST 请求： request HTTP(S) URL。这会调用 DID 解析 函数，执行位置为远程 DID 解析器。

    1. 如果 Content-Type HTTP response header 的值是 application/did-resolution：
      1. 如果函数成功，HTTP 响应状态码必须为 200。
      2. HTTP body MUST 包含一个 DID 解析结果（见 8. DID 解析结果），该结果是 DID 解析 函数的结果。
    2. 否则，如果函数成功并返回 didDocument：
      1. HTTP 响应状态码 MUST 为 200。
      2. HTTP 响应 MUST 包含一个 Content-Type HTTP response header。其值 MUST 是 didResolutionMetadata 中 contentType 元数据属性的值（见 4.2 DID 解析元数据）。
      3. HTTP 响应正文 MUST 包含 DID 解析 函数结果中的 didDocument，并使用 与 Content-Type HTTP response header 对应的 表示。
注

参见此处，了解与 HTTP(S) 绑定对应的 OpenAPI 定义。

11. 安全考量

本节包含各种安全考量，建议在生产环境中使用 DID 解析的人予以考虑。建议读者在阅读本节之前，先 熟悉 去中心化标识符规范的安全考量章节 中提供的一般安全建议。

11.1 身份验证/授权

DID 解析和 DID URL 解引用不 涉及任何身份验证或授权功能。类似于 DNS 解析，任何人都可以执行该过程，而无需任何凭证 或非公开知识。

11.2 缓存

DID 解析器可以 维护一个通用的 DID 文档缓存。它 也可以维护特定于某些 DID 方法的缓存。

noCache 解析选项可用于请求 某种缓存行为。

此 resolution option 是 OPTIONAL。

此属性的可能值为：

  • "false"（默认值）：允许缓存 DID 文档。
  • "true"：请求禁用缓存，并从 可验证数据 注册表检索一个新的 DID 文档。

缓存行为可以通过 DID 解析器的配置、 noCache 解析选项、DID 文档的内容（例如 cacheMaxTtl 字段），或这些 属性的组合来控制。

实现 noCache 的解析器可能更容易受到拒绝 服务攻击，因为恶意客户端可以绕过缓存来强制 代价高昂的网络请求和资源消耗。使用 noCache 请求解析的客户端预期某些 解析器会拒绝绕过缓存的解析请求。 拒绝无缓存解析的解析器 MUST 以 FEATURE_NOT_SUPPORTED 错误响应，并明确说明 不允许绕过缓存，以便客户端可以尝试 不使用 noCache 进行解析。

11.3 JSON-LD 上下文完整性

如果从远程位置获取 JSON-LD Context 文件，攻击者可能会篡改该上下文 文件（例如，通过攻陷服务器 或通过中间人攻击拦截请求）。

因此，强烈建议任何执行远程检索 JSON-LD Context URL 的 DID 解析器使用上下文文件及其对应哈希的注册表 （或功能等效机制），以帮助确保 端到端安全。预期实现会在 资源的密码学哈希值与预期哈希值不匹配时抛出错误。

11.4 版本控制

如果提供了 versionId 或 versionTime DID 参数，则 DID 解析算法会返回 DID 文档的特定版本。

DID 参数 versionId 和 versionTime 互斥。

versionId DID 参数的使用是特定于 DID 方法的。其可能值可 包括顺序编号、随机 UUID、内容哈希等。

DID 文档元数据 MAY 包含一个 versionId 属性， 该属性会随着对 DID 文档执行的每次 Update 操作而变化。

注

虽然大多数 DID 方法支持 Update 操作，但并不要求 DID 方法保留所有以前的 DID 文档 版本，因此并非所有 DID 方法 都支持版本控制。

11.5 VDR 网络分叉

使用分布式系统（例如 分布式账本）作为 VDR（可验证数据注册表）的 DID 方法 需要管理 网络分叉可能发生的潜在情况。因此，使用 分布式系统作为 VDR 的 DID 方法规范 SHOULD 指定一种方式，以便将其使用的 VDR 与此类 分叉区分开来。

11.6 解引用循环

当 DID URL 解引用器 客户端解引用以下文档中的标识符和链接资源时： DID 文档 ，尤其是诸如 verificationMethod、 controller或 alsoKnownAs 等字段，可能会遇到解引用循环。如果一个 DID 文档 引用另一个 DID（或 URL），而后者最终指回先前已解引用的标识符，就会形成循环。 DID URL 解引用器 在解引用以下对象时也可能遇到这种情况： DID URL ，当它引用一个 DID 服务端点时。 

did:example:alice
	└── verificationMethod.controller → did:example:bob
		└── verificationMethod.controller → did:example:alice

执行递归解引用的 DID URL 解引用器及其客户端应当预期、检测并处理 此类循环。

安全和性能风险：如果未检测并缓解 循环，递归解引用可能导致：

  • 软件中的无限循环或 栈溢出。
  • 资源耗尽（例如内存、网络或 CPU）。
  • 客户端或中介中的拒绝服务（DoS）漏洞。

缓解指导：鼓励递归跟随外部 DID 文档引用的组件 跟踪已经解引用过的标识符， 并检测循环何时发生，然后采取适当行动。 此外，开发者可能希望限制递归深度或广度， 以减少潜在攻击面。

11.7 查询字符串 规范化与注入风险

本节为非规范性内容。

DID URL 的查询组件用于传递影响解析和解引用行为的 DID 参数（见 3. DID 参数）。查询字符串处理的若干 方面具有安全含义，建议实现者仔细考虑。

11.7.1 通过 relativeRef 进行路径遍历

将经过百分号解码的 relativeRef DID 参数值与作为基 URI 的 serviceEndpoint URL 相结合，使用以下位置定义的引用解析算法： RFC3986 第 5 节，构造最终资源 URL。如果 relativeRef 的值包含路径遍历序列，攻击者可能使解引用器构造出超出服务端点预期路径范围的资源 URL。

路径遍历可能使用多种编码方式尝试。以下是 攻击者可能使用的序列的非详尽示例：

  • 字面 dot-dot-slash：../
  • 百分号编码变体：%2E%2E%2F、%2E%2E/、.%2E/、 %2E./
  • 双重编码变体：%252E%252E%252F
  • 平台特定变体（例如，Windows 衍生路径库中的 ..\）

鼓励实现者：

  • 在应用 RFC3986 第 5 节 引用解析算法后，对已解析路径进行规范化，并验证生成路径不会 遍历到服务端点 URL 基路径之上。
  • 将经规范化后会产生路径不以 serviceEndpoint URL 基路径为前缀的 资源 URL 的 relativeRef 值视为 无效输入，例如通过返回 INVALID_DID_URL 错误（见 9. 错误）。
  • 在完全百分号解码后应用规范化和验证，以防范 编码后的遍历变体。表层字符串匹配（例如仅检查 字面字符串 ../）并不是可靠的遍历检测机制。
注： relativeRef 解析循环

当服务端点 URL 本身是一个会被递归解引用的 DID URL 时，此问题尤为严重。在这种情况下， relativeRef 中的遍历序列可能会影响与预期不同的 DID 文档的解析。 另请参见 11.6 解引用循环。

11.7.2 作为缓存绕过向量的规范化不一致

如 3.2 查询 规范化中所述，同一逻辑 DID URL 可以由多个语法上 不同的字符串表示。在代理或多组件解析架构中（见 7.2.2 代理 解析），不同组件可能应用不同的 规范化规则（或完全不规范化）。

了解组件之间规范化不一致的攻击者可能会：

  • 构造一个由某个组件从缓存提供、但由另一个 组件从 可验证数据 注册表重新解引用的 DID URL，从而可能绕过与缓存 响应相关的内容完整性检查。
  • 使两个逻辑上相同的 DID URL被缓存为 不同条目，膨胀缓存大小，并可能导致缓存 耗尽。
  • 利用缓存代理与 上游解析器之间不同的重复参数处理方式，向解析 请求中注入意外的参数值。

为缓解这些风险，鼓励实现者：

  1. 在解析流水线的最外层入口点应用查询字符串规范化（按照 3.2 查询规范化），并在任何缓存或 转发发生之前完成。
  2. 使用 DID URL 的规范化形式作为缓存键， 并记录所应用的规范化算法。
  3. 避免假定从上游 组件接收的 DID URL 已经规范化；在 处理前应用独立规范化是一种更安全的做法。

11.7.3 通过拼接进行参数 注入

通过字符串拼接以编程方式构造 DID URL 的实现 （例如，将调用者提供的值追加为 DID 参数）如果在拼接前未验证并编码输入， 可能容易受到参数注入攻击。

例如，调用者提供的 service 值 files&versionId=2 如果在未编码的情况下拼接，可能会向 DID URL 中注入额外的 versionId 参数， 从而以调用者可能并未预期或授权的方式 改变解析行为。这类似于基于 HTTP 的系统中的查询字符串 注入漏洞。

鼓励实现者在将所有调用者提供的参数 值拼接到 DID URL 查询字符串之前，按照 RFC3986 第 2.1 节对其进行百分号编码，并 验证参数值在 解码后符合本规范中 该参数的预期值格式（见 3. DID 参数）、适用 DID 方法规范或 DID Document Resolution Extensions [DID-EXTENSIONS-RESOLUTION] 中的定义。

12. 隐私考量

本节详细说明 DID 解析特有的隐私考量。 建议读者在阅读本节之前，先熟悉 去中心化标识符规范 和 受控标识符规范 的隐私考量章节中提供的一般隐私建议。

12.1 DID 解析和解引用请求者的画像分析

DID 解析器和 DID URL 解引用器将能够 记录其服务收到的解析和解引用请求。随着时间推移， 这些日志可用于跟踪请求这些服务的客户端并为其画像。 为缓解此隐私风险，客户端应向其信任的服务发出此类请求， 例如，因为存在既有业务 关系，或因为该服务运行在其控制的基础设施上。

客户端还可以采取步骤混淆其向服务发出的请求，以降低 关联和画像分析的可能性。混淆技术 包括 Oblivious HTTP、使用可信代理执行解析 请求，以及使用可信缓存。

12.2 特定方法的 考量

不同 DID 方法会根据方法的设计决策和底层 VDR 具有不同的额外隐私影响和考量。 建议实现者审查其打算支持的 特定 DID 方法的隐私考量。鼓励 DID 方法设计者遵循 W3C 威胁建模指南 来生成威胁模型，以帮助实现者理解方法设计的 隐私影响。

A. 与其他技术的关系

在 Internet 上将标识符解析为地址时，最常用的机制之一是 [RFC1034] 中描述的全局域名系统（DNS）。 DNS 以及用于将域名映射到互联网 协议地址的过程和系统，是托管网站的常见要求。

去中心化标识符 （DID）v1.0 规范引入了一种新型标识符，它不依赖 全局域名系统，并引入了一个不要求架构中任何 部分中心化的标识符解析过程概念。这种新架构允许 以去中心化方式创建和管理可全局解析的标识符， 以对抗标识符寻租和审查。它使个人能够完全拥有并 控制自己的标识符，而不是从第三方租用标识符。

获得 DID URL 的个人，会在其软件中使用它们，方式与继续 使用基于 DNS 的 URL 十分相似。软件使用 DID 解析器接口 （在本规范中定义）来确定要检索资源的位置。 DID 解析过程与 DNS 解析过程非常相似，对个人而言是不透明的，并在软件内部发生， 不需要个人直接参与。

与 DNS 中心化以及相应发明 DID 和 DID 解析相关的研究， 由 去中心化标识符（DID）v1.0 规范中 与 DID 历史相关的章节记录。

C. 修订历史

本节不具规范性。

本节列出了自本规范作为 W3C 首次公开工作草案发布以来的变更。

自候选 推荐标准快照以来的更改包括：

  • 其他错误类型的 HTTP 状态码：该 HTTP(S) 绑定不再要求对其状态码表中未列出的错误类型使用 500 状态码； 该状态码现在由实现确定。定义错误类型的 规范可以声明它细化了本规范中定义的哪个错误 类型。
  • 通过 HTTP(S) 进行 DID URL 解引用：HTTP(S) 绑定、其示例及其 OpenAPI 定义不再涵盖 DID URL 解引用，并且移除了基于网络的 DID URL 解引用器这一一致性类别。
  • 属性位置： contentType：DID 解析算法现在在定义 contentType 的 DID 解析元数据中返回 contentType 。
  • 完整结果的状态码：HTTP(S) 绑定现在要求成功的完整 DID 解析结果使用 200 状态码；仅对其他响应应用裸 DID 文档的规则，并允许 410 覆盖其他状态码。
  • 其他错误类型的 URL：定义错误类型的规范现在必须定义其 URL。删除了添加 https://www.w3.org/ns/did# 前缀的规则，因为它已不再适用于任何错误类型。

自首个公开工作草案以来的更改包括：

  • 文档范围和结构补充
    • 标题和作者信息：标题被 简化为“去中心化标识符解析（DID 解析）v1”，并新增了编辑（Stephen Curran、Joe Andrieu）。
    • 上下文相关章节：候选推荐标准新增了 “实现者概述”“受众”和“用例”等不具规范性的 介绍性章节，以便为开发者和架构师提供更完善的 背景信息。
    • 一致性类别：候选推荐标准专门为基于网络的 实现引入了两个新的一致性类别：“符合要求的基于网络的 DID 解析器”和“符合要求的基于网络的 DID URL 解引用器”。
  • 解析接口和算法
    • 抽象接口简化：首次公开工作草案 定义了两个不同的抽象函数： resolve()（返回数据模型）和 resolveRepresentation()（返回字节 流）。候选推荐标准将其合并为单个 resolve() 函数，该函数负责返回能够被格式化为 一致表示形式的 DID 文档。
    • 相对 URL 展开：候选推荐标准引入了一个 名为 expandRelativeUrls 的新 DID 解析选项。 当其设置为 true 时， 解析器会自动将在 DID 文档中找到的所有相对 DID URL 展开为绝对 DID URL。
    • DID 参数和规范化：候选推荐标准 通过正式定义 service、serviceType、 relativeRef、versionId 和 versionTime 的行为，扩展了 DID 参数相关内容。它还引入了“查询 规范化”一节，提供关于百分号编码、 重复参数处理和特定于方法的 规范化指导。
    • 日期时间标准化：候选推荐标准为所有日期时间值（例如 versionTime、created 和 updated）规定了严格格式，要求它们是 调整为 UTC 且不包含亚秒精度的 XML 日期时间 字符串。
  • DID URL 解引用变更
    • 存在风险的特性：候选推荐标准明确将 整个“DID URL 解引用”一节及其 相应的数据结果结构标记为“存在风险”，并指出 其可能会被大幅修改或移除。
    • 临时算法：由于“存在风险”状态，CR 引入了“暂定 - DID URL 解引用”一节，探索基于顺序“处理策略”的模块化替代方案。
    • 验证关系：候选推荐标准新增 verificationRelationship 作为解引用 选项。在进行片段解引用时，该算法会验证 解析出的验证方法是否被正式授权用于 指定关系；如果未获得授权，则抛出错误。
    • 移除服务端点构造：用于“服务端点构造”的 独立算法 （首次公开工作草案中的第 11 节）已从候选推荐标准版本中移除。
  • 错误处理和可扩展性
    • RFC9457 错误格式：候选推荐标准不再像 首次公开工作草案那样对错误使用简单的单关键字 ASCII 字符串， 而是要求使用 RFC9457（HTTP API 的问题详情）。
    • 错误 URI：候选推荐标准中的错误类型现在 映射到特定的 W3C URI（例如 https://www.w3.org/ns/did#INVALID_DID），并引入了 INVALID_DID_DOCUMENT 和 FEATURE_NOT_SUPPORTED 等新错误。
    • 转向扩展：候选推荐标准不再引用 首次公开工作草案中用于元数据和选项注册的 “DID 规范注册表”，而是建议 实现者改用“DID 解析扩展”和“DID 文档属性扩展”。
  • 扩展的安全和隐私考量
    • 新的安全向量：候选推荐标准大幅扩展了 安全考量一节，以处理如下漏洞：
      • 解引用循环：跟随嵌套的 DID 文档引用时出现无限循环或资源耗尽的风险。
      • 查询字符串/参数注入： 因缓存规范化不一致或不安全的程序化字符串拼接而产生的 漏洞。
      • 路径遍历：攻击者使用恶意 relativeRef 参数序列 （例如 ../）逃逸服务端点预期路径的风险。
      • JSON-LD 完整性和网络分叉： 关于验证 JSON-LD 上下文文件和处理 VDR（可验证数据注册表）网络分叉的指导。
    • 新的隐私章节：候选推荐标准引入了 独立的“隐私考量”一节，强调 DID 解析器和解引用器可能记录请求解析的客户端并对其进行画像的 风险，并建议使用可信代理或 Oblivious HTTP 等缓解策略。
