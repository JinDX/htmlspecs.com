HTTP QUERY 方法

摘要

本规范定义了 HTTP 的 QUERY 方法。QUERY 要求请求 目标以安全且幂等的方式处理所附内容，然后以 该处理的结果作出响应。这与 POST 请求类似，但 QUERY 请求可以 自动重复或重新开始，无需担心部分状态变更。

1. 引言

本规范定义了 HTTP QUERY 请求方法，用于发出安全、 幂等的请求 (第 9.2 节，见 [HTTP])，其中包含一个 表示，用于描述目标资源应如何处理该请求。

一种常见的查询模式如下：

GET /feed?q=foo&limit=10&sort=-published HTTP/1.1
Host: example.org

但是，当传递的数据过多，以至于无法编码到请求的 URI 中时，这种 模式就会出现问题：

  • 通常无法预先知道大小限制，因为请求可能经过多个 彼此不协调的系统（但请注意，第 4.1 节，见 [HTTP]，建议发送方 和接收方至少支持 8000 个八位字节），
  • 在目标 URI 中表达某些类型的数据效率较低，因为将这些数据 编码为有效 URI 会产生额外开销，
  • 请求 URI 比请求内容更可能被记录到日志中，而且还可能出现在 书签中，
  • 将查询直接编码到请求 URI 中，实际上会将每一种可能的 查询输入组合都视为不同的资源。

作为使用 GET 的替代方案，许多实现使用 HTTP POST 方法来 执行查询，如下例所示。在这种情况下，查询 操作的输入作为请求内容传递，而不是使用请求 URI 的查询 组件。

使用 HTTP POST 请求查询的典型方式如下：

POST /feed HTTP/1.1
Host: example.org
Content-Type: application/x-www-form-urlencoded

q=foo&limit=10&sort=-published

然而，在这种变体中，如果不了解 请求所发往的资源和服务器的具体情况，就无法轻易看出正在执行的是安全、幂等的查询 操作。

QUERY 方法提供了一种填补 GET 与 POST 用法之间空白的解决方案， 上述示例可表示为：

QUERY /feed HTTP/1.1
Host: example.org
Content-Type: application/x-www-form-urlencoded

q=foo&limit=10&sort=-published

与 POST 一样，查询操作的输入作为请求内容传递，而 不是作为请求 URI 的一部分。不过，与 POST 不同，该方法明确具有安全性和 幂等性，因此可以使用缓存和自动重试等功能。

基于任何重要资源都应由 URI 标识这一设计原则， 本规范描述了服务器如何为查询本身或 特定查询结果分配 URI，以便稍后在 GET 请求中使用。

总结如下：

2. QUERY 方法

QUERY 方法用于发起服务器端查询。GET 方法 请求目标 URI 所标识资源的表示（定义见 第 7.1 节，位于 [HTTP]），而 QUERY 方法 用于要求目标资源在该目标 资源的范围内执行查询操作。

请求内容及其媒体类型定义了查询。源服务器根据 目标资源确定操作的范围。

如果 Content-Type 请求字段 ([HTTP]，第 8.3 节) 缺失或与请求内容不一致，服务器必须使请求失败。

与所有 HTTP 方法一样，目标 URI 的查询部分参与标识 被查询的资源。它是否以及如何直接影响查询结果，取决于 具体资源，不在本规范的范围内。

QUERY 请求对于目标资源是安全的 ([HTTP]，第 9.2.1 节)； 也就是说，客户端既不请求也不预期目标 资源的状态发生任何变化。这并不妨碍服务器创建额外的 HTTP 资源， 通过这些资源可检索更多信息（参见第 2.3 节和第 2.4 节）。

此外，QUERY 请求是幂等的 ([HTTP]，第 9.2.2 节)； 可以在需要时重试或重复，例如在连接失败之后。

根据 第 15.3 节，见 [HTTP]，2xx（成功） 响应码表示请求已被成功接收、理解并接受。

具体而言，200（成功）响应表示查询已被成功处理， 且该处理的结果作为响应内容包含在内。

2.1. 媒体类型与内容协商

QUERY 请求的语义同时取决于请求内容和相关的 元数据，例如媒体类型 ([HTTP]，第 8.3.1 节)。 一般而言，对于内容与元数据不一致的请求所存在的任何问题，都必须使用 4xx（客户端错误）响应予以拒绝 ([HTTP]，第 15.5 节)。

以下列表描述了各种失败情况，并建议了具体的状态码：

  • 如果请求缺少媒体类型信息，则按定义它就是不正确的，需要 使用 4xx 状态码使其失败，例如 400（客户端错误）。
  • 如果指定了媒体类型，但资源不支持该类型，则适合使用 415 （不支持的媒体类型）。这明确包括以下情况： 原则上已知该媒体类型，但它缺少针对 目标资源的 QUERY 的特定语义。在这两种情况下，Accept-Query 响应字段 (第 3 节) 可用于告知客户端所支持的媒体类型。
  • 如果指定了媒体类型，但它与实际请求内容不一致，则 可以返回 400（错误请求）。也就是说，不允许服务器根据请求内容推断媒体 类型，然后覆盖缺失或“错误”的值 （即“内容嗅探”）。
  • 如果指定的媒体类型已被理解，且内容确实与 该类型一致，但由于查询的实际内容而无法处理 查询，则可以使用状态码 422（无法处理的内容）。例如， 语法正确的 SQL 查询标识了一个不存在的表。
  • 如果客户端使用 Accept 字段 ([HTTP]，第 12.5.1 节) 请求了资源不支持的特定响应媒体类型，则适合使用 406（不可 接受）状态码。

2.2. 等价资源

对于任意给定的 QUERY 请求，其等价资源是一个响应 GET 请求、代表该 QUERY 请求及其目标，并同时考虑消息 内容和元数据的资源 (第 6 节，见 [HTTP])。具体而言，这 包括表示元数据 (第 8 节，见 [HTTP])，例如 内容的媒体类型。

换言之，等价资源是通过纳入请求内容， 从实现 QUERY 的资源派生而来的。

术语等价资源用于定义其他 HTTP 方面的行为，例如选定表示。服务器可以但不必为 这些资源分配 URI（参见 第 1.1 节，位于 [URI]）。如果 分配了 URI，这些资源就可以通过 GET 请求访问。

2.3. Content-Location 响应字段

成功响应（2xx，第 15.3 节，见 [HTTP]）可以包含一个 Content-Location 首部字段，其中包含与 操作结果对应的资源标识符；详情参见 第 8.7 节，位于 [HTTP]。这 表示服务器声明：客户端可以向 指定 URI 发送 GET 请求，以检索刚刚执行的查询操作的结果。所 指示的资源可能是临时的。

参见附录 A.4.1 中的示例。

2.4. Location 响应字段

服务器可以为 QUERY 请求的等价资源 (第 2.2 节) 分配 URI。如果服务器这样 做，则可以将该资源的 URI 包含在 2xx 响应的 Location 首部字段中（参见 第 10.2.2 节， 位于 [HTTP]）。这表示 服务器声明：客户端可以向指定 URI 发送 GET 请求，以重复刚刚执行的查询 操作，而无需重新发送查询内容。此资源的 URI 可能 是临时的；如果后续请求失败，客户端可以使用原始 QUERY 请求目标和之前提交的内容重试。

参见附录 A.4.2 中的示例。

2.5. 重定向

在某些情况下，服务器可能选择通过 将用户代理重定向到其他 URI 来间接响应 QUERY 请求（参见 第 15.4 节，位于 [HTTP]）。

状态码为 301（永久移动，[HTTP]，第 15.4.2 节）或 308（永久重定向，[HTTP]，第 15.4.9 节）的响应，表示目标资源已永久移动到 Location 响应字段所引用的其他 URI ([HTTP]，第 10.2.2 节)。同样，状态码为 302（找到，[HTTP]，第 15.4.3 节）或 307（临时重定向，[HTTP]，第 15.4.8 节）的响应，表示目标资源已临时移动。在这四种 情况下，服务器都在建议用户代理可以通过 向 Location 所引用的新目标 URI 发送类似的 QUERY 请求， 来完成其原始 QUERY 请求。

请注意，在收到 301 或 302 响应后将 POST 重定向为 GET 请求的例外情况，不适用于 QUERY 请求。

状态码为 303（参见其他，第 15.4.4 节， 见 [HTTP]）的 QUERY 响应表示， 原始查询可以通过对 Location 响应字段所引用的 URI 发出普通检索请求来完成 ([HTTP]，第 10.2.2 节)。对于 HTTP，这意味着向新目标 URI 发送 GET 请求，如 以下示例所示：附录 A.4.3。

2.6. 条件请求

QUERY 请求的选定表示 (第 3.2 节，见 [HTTP]) 与对该 QUERY 请求的等价资源 (第 2.2 节) 发出 GET 请求时 的选定表示相同。

条件 QUERY 要求仅在条件首部字段所描述的 情况下，才在响应中返回选定表示（即经过任何内容协商后的查询结果）， 这些情况定义于 第 13 节，位于 [HTTP]。

参见附录 A.5 中的 示例。

2.7. 缓存

QUERY 方法的响应是可缓存的；缓存可以使用它来 满足后续的 QUERY 请求，依据 第 4 节，位于 [HTTP-CACHING]。

QUERY 请求的缓存键 (第 2 节，见 [HTTP-CACHING]) 必须纳入请求内容 (第 6 节，见 [HTTP-CACHING]) 及相关 元数据 (第 8 节， 见 [HTTP])。

为提高缓存效率，缓存可以先移除请求内容和相关元数据中 在语义上无关紧要的差异。例如， 通过：

  • 移除内容编码 (第 8.4 节， 见 [HTTP])。
  • 根据请求的 Content-Type 字段中任何媒体 子类型后缀所指示的格式约定知识进行规范化（例如，"+json"；参见 第 4.2.8 节，位于 [RFC6838]）。
  • 根据请求的 Content-Type 字段所指示的 内容本身的语义知识进行规范化。

请注意，任何此类转换都仅用于生成 缓存键；它不会更改请求本身。

客户端可以使用 "no-transform" 缓存指令 (第 5.2.1.6 节，见 [HTTP-CACHING])，表明它们希望 不发生此类转换（但请注意，此指令仅具有建议性质）。

请注意，缓存 QUERY 方法响应本质上比缓存 GET 响应更复杂，因为必须完整读取请求内容才能 确定缓存键。如果 QUERY 响应提供了 Location 响应字段 (第 2.4 节) 来指示等价资源的 URI (第 2.2 节)，客户端可以在 后续请求中改用 GET，从而简化处理。

2.8. 范围 请求

QUERY 的范围请求语义与 GET 的范围请求语义相同，定义见 第 14 节，位于 [HTTP]。不过，字节范围请求 （本文撰写时唯一定义的范围单位）对于 QUERY 请求的结果几乎没有价值。

查询格式通常会定义自身限制结果集或对结果集分页的方式，例如 SQL 中的 "FETCH FIRST ... ROWS ONLY"。预计将使用这些内置功能 来替代 HTTP 范围请求。

3. Accept-Query 首部字段

资源可以使用 "Accept-Query" 响应首部字段，直接表明支持 QUERY 方法，同时标识可以 使用的具体查询格式媒体类型。

Accept-Query 包含一个媒体范围列表 (第 12.5.1 节，见 [HTTP])，使用“结构化字段” 语法 [STRUCTURED-FIELDS]。媒体 范围由元素为 Token 或 String 的 List 结构化首部字段表示， 包含不带参数的媒体范围值。

媒体类型参数（如果有）映射为类型为 String 或 Token 的结构化字段参数。选择 Token 还是 String 在语义上无关紧要。也就是说， 接收方可以将 Token 转换为 String，但不 得根据接收到的类型对它们进行不同处理。

媒体类型并不与 Token 完全对应；例如，媒体类型允许以数字开头。在 这类情况下，需要使用 String 格式。

唯一支持的通配符用法是匹配任意类型的 "*/*"，或 匹配指定类型的任意子类型的 "xxxx/*"。

字段值中所列类型的顺序无关紧要。

Accept-Query 字段的值适用于服务器上具有相同 路径的每一个 URI；换言之，查询组件被忽略。如果对同一资源的请求 返回不同的 Accept-Query 值，则使用最近收到的新鲜值（依据 第 4.2 节，位于 [HTTP-CACHING]）。

例如：

Accept-Query: "application/jsonpath", application/sql;charset="UTF-8"

尽管此字段的语法看起来与其他字段类似，例如 "Accept" (第 12.5.1 节，见 [HTTP])，但它是结构化字段， 因此必须按照以下位置的规定处理：第 4 节，位于 [STRUCTURED-FIELDS]。

4. 安全注意事项

QUERY 方法与所有 HTTP 方法一样，受相同的一般安全注意事项约束， 如 [HTTP] 所述。

它可替代在 URI 中传递请求信息的方式（例如，在 查询组件中）。在某些情况下，这种方式更可取，因为与请求内容相比，URI 更可能被中间设备记录到日志中或 以其他方式处理。在其他情况下，如果 查询包含敏感信息，URI 可能被记录到日志中这一点会促使 选择 QUERY 而非 GET。

如果服务器创建临时资源来表示 QUERY 请求的结果（例如， 用于 Location 或 Content-Location 字段），为该资源分配 URI，且 请求包含不能记录到日志中的敏感信息，则该 URI 应当选择为不包含原始请求内容中任何敏感部分 的形式。

如果缓存错误地规范化 QUERY 内容，或其规范化方式与 资源处理内容的方式存在显著差异，那么当 规范化造成误匹配时，缓存可能返回不正确的响应。

来自实现了跨源资源共享 (CORS) 的用户代理的 QUERY 请求 将需要“预检”请求，因为 QUERY 不属于 CORS 安全列出的 方法集合（参见 [FETCH]）。

附录 A. 示例

以下示例仅用于说明；如果需要发送的查询 确实如此简短，那么使用 GET 可能更合适。

大多数示例使用的媒体类型是 "application/x-www-form-urlencoded"（也用于来自浏览器 用户客户端的 POST 请求，定义见 "application/x-www-form-urlencoded" ，位于 [URL]）。为简洁起见，已 省略 Content-Length 字段。

A.1. 简单查询

以下是一个具有直接响应的简单查询：

QUERY /contacts HTTP/1.1
Host: example.org
Content-Type: application/x-www-form-urlencoded
Accept: application/json

select=surname,givenname,email&limit=10&match=%22email=*@example.*%22

响应：

HTTP/1.1 200 OK
Content-Type: application/json

[
  { "surname": "Smith",
    "givenname": "John",
    "email": "smith@example.org" },
  { "surname": "Jones",
    "givenname": "Sally",
    "email": "sally.jones@example.com" },
  { "surname": "Dubois",
    "givenname": "Camille",
    "email": "camille.dubois@example.net" }
]

A.2. 发现 QUERY 支持

OPTIONS 提供了一种发现 QUERY 支持的简单方式 (第 9.3.7 节， 见 [HTTP]) 方法：

OPTIONS /contacts HTTP/1.1
Host: example.org

响应：

HTTP/1.1 200 OK
Allow: GET, QUERY, OPTIONS, HEAD

Allow 响应字段 (第 10.2.1 节， 见 [HTTP]) 表示 指定资源所支持的方法集合。

除了使用 OPTIONS，还有其他方式。例如，可以在事先不知道服务器是否支持的情况下， 尝试发送 QUERY 请求。服务器随后要么处理该 请求，要么以 4xx 状态响应，例如 405（不允许的方法，第 15.5.6 节， 见 [HTTP]），其中包含 Allow 响应字段。

A.3. 发现 QUERY 格式

可以通过 Accept-Query 响应字段发现 QUERY 支持的媒体类型 (第 3 节)：

HEAD /contacts HTTP/1.1
Host: example.org

响应：

HTTP/1.1 200 OK
Content-Type: application/xhtml
Accept-Query: application/x-www-form-urlencoded, application/sql

哪些请求方法的响应会包含 Accept-Query，取决于 所访问的资源。

除了检查 Accept-Query，还可以发出 QUERY 请求，然后在 收到 4xx 状态时，例如 415 响应（不支持的媒体类型，第 15.5.16 节，见 [HTTP]）， 检查 Accept 响应字段 (第 12.5.1 节， 见 [HTTP])：

HTTP/1.1 415 Unsupported Media Type
Content-Type: application/xhtml
Accept: application/x-www-form-urlencoded, application/sql

A.4. Content-Location、Location 和 间接响应

如第 2.3 节和第 2.4 节所述，成功响应中的 Content-Location 和 Location 响应 字段（2xx，第 15.3 节，见 [HTTP]）提供了一种 标识可响应 GET 请求的替代资源的方式，这些资源可以用于获取已收到的 请求结果，也可以用于后续执行相同操作的请求。回到 附录 A.1 中的示例： 

QUERY /contacts HTTP/1.1
Host: example.org
Content-Type: application/x-www-form-urlencoded
Accept: application/json

select=surname,givenname,email&limit=10&match=%22email=*@example.*%22

响应：

HTTP/1.1 200 OK
Content-Type: application/json
Content-Location: /contacts/stored-results/17
Location: /contacts/stored-queries/42
Last-Modified: Sat, 25 Aug 2012 23:34:45 GMT
Date: Sun, 17 Nov 2024, 16:10:24 GMT

[
  { "surname": "Smith",
    "givenname": "John",
    "email": "smith@example.org" },
  { "surname": "Jones",
    "givenname": "Sally",
    "email": "sally.jones@example.com" },
  { "surname": "Dubois",
    "givenname": "Camille",
    "email": "camille.dubois@example.net" }
]

A.4.1. 使用 Content-Location

上面收到的 Content-Location 响应字段标识了一个资源， 该资源保存了此字段所在 QUERY 响应的结果：

GET /contacts/stored-results/17 HTTP/1.1
Host: example.org
Accept: application/json

响应：

HTTP/1.1 200 OK
Last-Modified: Sat, 25 Aug 2012 23:34:45 GMT
Date: Sun, 17 Nov 2024, 16:10:25 GMT

[
  { "surname": "Smith",
    "givenname": "John",
    "email": "smith@example.org" },
  { "surname": "Jones",
    "givenname": "Sally",
    "email": "sally.jones@example.com" },
  { "surname": "Dubois",
    "givenname": "Camille",
    "email": "camille.dubois@example.net" }
]

请注意，不能保证服务器会无限期地提供此资源， 因此，在收到错误响应后，客户端需要重新执行 原始 QUERY 请求，以获得新的替代位置。

A.4.2. 使用 Location

Location 响应字段标识了一个资源，该资源将响应 GET，返回 与原始 QUERY 请求具有相同处理过程和参数的当前结果。 

GET /contacts/stored-queries/42 HTTP/1.1
Host: example.org
Accept: application/json

在此示例中，一个条目已于 2024-11-17T16:12:01Z 被移除（如 Last-Modified 字段所示），因此响应仅包含两个条目：

HTTP/1.1 200 OK
Content-Type: application/json
Last-Modified: Sun, 17 November 2024, 16:12:01 GMT
ETag: "42-1"
Date: Sun, 17 Nov 2024, 16:13:17 GMT

[
  { "surname": "Smith",
    "givenname": "John",
    "email": "smith@example.org" },
  { "surname": "Dubois",
    "givenname": "Camille",
    "email": "camille.dubois@example.net" }
]

假设服务器仍然公开该资源，且 查询结果未发生变化，则后续包含以下字段的条件 GET 请求：

If-None-Match: "42-1"

将产生 304（未修改）响应 (第 15.4.5 节，见 [HTTP])。

A.4.3. 间接响应

服务器可以发送“间接”响应 (第 2.5 节)，使用状态码 303（参见其他，第 15.4.4 节，见 [HTTP])。

对于以下附录开头给出的请求：附录 A.4， 服务器可能响应为：

HTTP/1.1 303 See Other
Content-Type: text/plain
Date: Sun, 17 Nov 2024, 16:13:17 GMT
Location: /contacts/stored-queries/42

请参见 "/contacts/stored-queries/42" 处存储的查询。

这与在直接响应中包含 Location 类似，只是没有返回 查询结果。这使服务器只需生成或复用一个 替代资源。随后可以按照以下方式使用此资源：附录 A.4.2。

A.6. 更多查询格式

以下示例展示了对 JSON 形式的 [RFC8259] RFC 勘误数据库的请求。

以下请求使用可扩展样式表语言转换 (XSLT) 来提取 按年份和已定义的勘误类型汇总的勘误信息。

QUERY /errata.json HTTP/1.1
Host: example.org
Content-Type: application/xslt+xml
Accept: application/xml, text/csv

<transform xmlns="http://www.w3.org/1999/XSL/Transform"
  xmlns:j="http://www.w3.org/2005/xpath-functions"
  version="3.0">

  <output method="text"/>

  <param name="input"/>

  <variable name="json"
    select="json-to-xml(unparsed-text($input))"/>

  <variable name="sc">errata_status_code</variable>
  <variable name="sd">submit_date</variable>

  <template match="/">
    <text>year, total, rejected, verified, hdu, reported</text>
    <text>&#10;</text>
    <variable name="en" select="$json//j:map"/>
    <for-each-group select="$en"
      group-by="substring-before(j:string[@key=$sd],'-')">
      <sort select="current-grouping-key()"/>
      <variable name="year" select="current-grouping-key()"/>
      <variable name="errata" select=
        "$en[$year=substring-before(j:string[@key=$sd],'-')]"/>
      <value-of select="concat(
        $year,
        ', ',
        count($errata),
        ', ',
        count($errata['Rejected'=j:string[@key=$sc]]),
        ', ',
        count($errata['Verified'=j:string[@key=$sc]]),
        ', ',
        count(
          $errata['Held for Document Update'=j:string[@key=$sc]]),
        ', ',
        count($errata['Reported'=j:string[@key=$sc]]),
        '&#10;')"/>
    </for-each-group>
  </template>

</transform>

附录 B. 方法名 'QUERY' 的选择

“超文本传输协议 (HTTP) 方法注册表” (<http://www.iana.org/assignments/http-methods>) 已包含另外三个具有“安全”和“幂等”属性的方法："PROPFIND" [RFC4918]、 "REPORT" [RFC3253]， 以及 "SEARCH" [RFC5323]。

原本可以复用其中任意一个方法，通过更新使其符合 本规范定义的新方法 "QUERY"。事实上，本 规范在早期阶段曾使用 "SEARCH"。

最终选择方法名 "QUERY" 的原因如下：

  • 其他方法为请求内容使用通用媒体类型 ("application/xml")； 请求的语义完全取决于请求内容。
  • 此外，它们都源自 WebDAV 活动，而许多人对此抱有复杂的 感受。
  • "QUERY" 很好地体现了与 URI 查询组件之间的关系。
