    指明 HTTP 首部字段参数的
                               字符编码和语言

摘要

   默认情况下，超文本传输协议（HTTP）消息中的首部字段值
   无法轻易携带 US-ASCII 编码字符集以外的字符。
   RFC 2231 定义了一种编码机制，
   用于多用途互联网邮件扩展（MIME）首部字段值
   内部的参数。本文档规定了一种适用于
   HTTP 首部字段的编码，它兼容以下规范中定义的编码
   的简化配置：RFC 2231。

   本文档废止 RFC 5987。

1.  引言

   在 HTTP 首部字段中使用 US-ASCII 编码字符集以外的字符
   （[RFC0020]，首部字段见 [RFC7230]）并不简单：

   o  HTTP 规范不鼓励在字段值中使用非 US-ASCII 字符，
      并将这些字符归入扩充巴科斯-瑙尔范式（ABNF）的
      "obs-text" 产生式（[RFC7230]，第 3.2 节）。

   o  此外，它没有规定字段值的默认字符编码方案，
      因此，任何对非 US-ASCII 字符的使用
      都需要由具体字段的定义予以规定，
      或者需要其他某种带外信息。

   o  最后，一些 API 假定了默认的字符编码方案，
      以便将从 HTTP 消息中获得的八位组序列
      映射为字符序列。例如，XMLHttpRequest
      API（[XMLHttpRequest]）使用接口定义语言类型
      "ByteString"，其实际结果相当于使用 ISO-8859-1
      字符编码方案（[ISO-8859-1]）。

RFC 8187            Charset/Language Encoding in HTTP     September 2017


   另一方面，RFC 2231 为 MIME 首部字段中的
   参数定义了编码机制（[RFC2231]）。与 HTTP 消息不同，
   MIME 消息确实需要通过非二进制传输机制发送。
   本文档规定了一种适用于 HTTP 首部字段的编码，
   该编码兼容以下规范所定义的编码的简化配置：
   RFC 2231。这种编码可应用于任何采用
   通用“参数”（"name=value"）语法的 HTTP 首部字段。

   本文档废止 [RFC5987] 并将其状态改为“历史”；
   变更概述见附录 A。

      注意：本文档余下部分引用 RFC 2231，
      仅用于解释为何选择所采用的特性；
      因此，这些引用完全是资料性的。

      注意：此编码不适用于通过 HTTP 传输的消息载荷，
      例如使用媒体类型 "multipart/form-data" 时的载荷
      （[RFC7578]）。

2.  记法约定

   本文档中的关键词 "MUST"、"MUST NOT"、"REQUIRED"、"SHALL"、"SHALL NOT"、
   "SHOULD"、"SHOULD NOT"、"RECOMMENDED"、"NOT RECOMMENDED"、"MAY" 和
   "OPTIONAL" 应按以下规范中的说明解释：
   [RFC2119]。

   本规范使用 [RFC5234] 定义的 ABNF 记法。
   通过引用纳入的核心规则定义于
   [RFC5234] 附录 B.1：ALPHA（字母）、DIGIT（十进制 0-9）、HEXDIG
   （十六进制 0-9/A-F/a-f）以及 LWSP（线性空白）。

   本规范使用 [RFC6365] 中定义的术语，即：
   “字符编码方案”（下文简称“字符编码”）、
   "charset" 和“编码字符集”。

   注意，这与 RFC 2231 不同；该 RFC 使用“字符集”
   一词来表示“字符编码方案”。

3.  与 RFC 2231 的比较与编码定义

   RFC 2231 定义了 MIME 的若干扩展。下文讨论
   这些扩展是否适用于 HTTP 首部字段，以及如何适用。

   概括如下：

   o  不需要参数续接（第 3.1 节），





Reschke                      Standards Track                    [Page 3]

RFC 8187            Charset/Language Encoding in HTTP     September 2017


   o  字符编码和语言信息很有用，
      因此规定了一个简单的子集（第 3.2 节），并且

   o  不需要在编码词中指定语言
      （第 3.3 节）。

3.1.  参数续接

   [RFC2231] 第 3 节 定义了一种机制，
   用于应对 MIME 首部的长度限制。这些限制
   不适用于 HTTP（[RFC7231]，附录 A.6）。

   因此，参数续接不是本规范定义的
   编码的一部分。

3.2.  参数值的字符编码和语言信息

   [RFC2231] 第 4 节 规定了如何在参数值中
   嵌入语言信息，以及如何对非 ASCII 字符进行编码，
   以应对 MIME 和 HTTP 首部字段
   参数中的限制。

   但是，RFC 2231 未规定必须实现的字符编码，
   这使发送方难以决定应使用哪种编码。
   因此，实现本规范的接收方必须（MUST）支持
   "UTF-8" 字符编码 [RFC3629]。

   此外，RFC 2231 允许省略字符编码信息。
   本规范定义的编码
   不允许这样做。

3.2.1.  定义

   通常以星号字符结尾的参数名
   表示存在扩展参数值。但请注意，
   这只是一种约定，扩展参数值
   必须在使用此扩展的首部字段定义中
   明确规定（见第 4 节）。

   扩展参数值的 ABNF 规定如下：











Reschke                      Standards Track                    [Page 4]

RFC 8187            Charset/Language Encoding in HTTP     September 2017


     ext-value     = charset  "'" [ language ] "'" value-chars
                   ; like RFC 2231's <extended-initial-value>
                   ; (see [RFC2231], Section 7)

     charset       = "UTF-8" / mime-charset

     mime-charset  = 1*mime-charsetc
     mime-charsetc = ALPHA / DIGIT
                   / "!" / "#" / "$" / "%" / "&"
                   / "+" / "-" / "^" / "_" / "`"
                   / "{" / "}" / "~"
                   ; as <mime-charset> in Section 2.3 of [RFC2978]
                   ; except that the single quote is not included
                   ; SHOULD be registered in the IANA charset registry

     language      = <Language-Tag, see [RFC5646], Section 2.1>

     value-chars   = *( pct-encoded / attr-char )

     pct-encoded   = "%" HEXDIG HEXDIG
                   ; see [RFC3986], Section 2.1

     attr-char     = ALPHA / DIGIT
                   / "!" / "#" / "$" / "&" / "+" / "-" / "."
                   / "^" / "_" / "`" / "|" / "~"
                   ; token except ( "*" / "'" / "%" )

   扩展参数的值部分（ext-value）是一个词元，
   由以下三部分组成：

   1.  必需的（REQUIRED）字符编码名称（charset），

   2.  可选的（OPTIONAL）语言信息（language），以及

   3.  表示实际值的字符序列（value-chars），
       各部分以单引号字符分隔。

   注意，字符编码名称和语言标签均
   限制为 US-ASCII 编码字符集，且匹配时不区分大小写
   （见 [RFC2978] 第 2.3 节 和 [RFC5646]
   第 2.1.1 节）。

   在值部分中，不属于 attr-char 的字符
   使用指定的字符编码编码为八位组序列。
   随后，该八位组序列按以下规定进行百分号编码：
   [RFC3986] 第 2.1 节。





Reschke                      Standards Track                    [Page 5]

RFC 8187            Charset/Language Encoding in HTTP     September 2017


   生成方必须（MUST）使用 "UTF-8"（[RFC3629]）字符编码。
   扩展字符编码（mime-charset）
   保留供将来使用。

      注意：接收方应准备好稳健地处理编码错误，
      例如格式错误或不完整的百分号转义序列，
      或无法解码的八位组序列。
      本规范不强制要求任何特定行为；
      例如，以下策略均可接受：

      *  忽略该参数，

      *  去除无法解码的八位组序列，以及

      *  将无法解码的八位组序列替换为替代字符，
         例如 Unicode 字符 U+FFFD
         （替代字符）。

3.2.2.  历史说明

   RFC 7230 的 token 产生式（[RFC7230]，第 3.2.6 节）不同于
   RFC 2231 使用的产生式（引自 [RFC2045]
   第 5.1 节），区别在于排除了花括号（即 "{" 和 "}"）。
   因此，attr-char 产生式也
   排除了这两个字符。

   此处定义的 <mime-charset> ABNF 与
   [RFC2978] 第 2.3 节 中的定义不同，它不允许单引号
   字符（另见 RFC 勘误 ID 1912 [Err1912]）。事实上，
   截至本文撰写时，尚未注册任何使用该字符的
   字符编码名称。

   为向后兼容 RFC 2231，本规范定义的编码
   与通用参数语法有所不同：
   它不允许 quoted-string 记法。使用通用
   解析器组件的实现可能无法检测到 quoted-string
   记法的使用，因此即使该格式无效，
   也可能接受它。

   [RFC5987] 还曾要求支持 ISO-8859-1（[ISO-8859-1]）；
   为兼容旧代码，鼓励接收方
   也支持这种编码。

3.2.3.  示例

   使用 "token" 的非扩展记法：

     foo: bar; title=Economy



Reschke                      Standards Track                    [Page 6]

RFC 8187            Charset/Language Encoding in HTTP     September 2017


   使用 "quoted-string" 的非扩展记法：

     foo: bar; title="US-$ rates"

   使用 Unicode 字符 U+00A3（"£"，英镑符号）的
   扩展记法：

     foo: bar; title*=utf-8'en'%C2%A3%20rates

   注意：Unicode 英镑符号字符 U+00A3 先使用
   UTF-8 字符编码编码为八位组序列 C2 A3，
   然后进行百分号编码。另请注意，空格字符被编码为
   %20，因为它不属于 attr-char。

   使用 Unicode 字符 U+00A3（"£"，英镑符号）
   和 U+20AC（"€"，欧元符号）的扩展记法：

     foo: bar; title*=UTF-8''%c2%a3%20and%20%e2%82%ac%20rates

   注意：Unicode 英镑符号字符 U+00A3 先使用
   UTF-8 字符编码编码为八位组序列 C2 A3，
   然后进行百分号编码。同样，Unicode 欧元符号字符 U+20AC
   先编码为八位组序列 E2 82 AC，再进行百分号
   编码。还请注意，HEXDIG 同时允许小写和大写
   字符，因此接收方必须理解这两种形式；语言
   信息是可选的，而字符编码不是。

3.3.  在编码词中指定语言

   [RFC2231] 第 5 节 扩展了 [RFC2047] 定义的编码，
   以支持在编码词中指定语言。现已废止的 HTTP/1.1 规范 RFC 2616
   曾引用 RFC 2047
   （[RFC2616]，第 2.2 节），但并未明确它适用于哪个首部
   字段。因此，HTTP/1.1 规范的当前修订版
   已弃用以下规范定义的编码形式：RFC
   2047（见 [RFC7230] 第 3.2.4 节）。

   因此，本规范不包含此特性。

4.  在 HTTP 首部字段定义中的使用指南

   使用下述扩展的 HTTP 首部字段规范
   应明确声明使用了第 3.2 节定义的扩展。
   一种简单的做法是规范性地引用本规范，
   并将 ext-value 产生式纳入具体首部字段
   参数的 ABNF 中。





Reschke                      Standards Track                    [Page 7]

RFC 8187            Charset/Language Encoding in HTTP     September 2017


   例如：

     foo         = token ";" LWSP title-param
     title-param = "title" LWSP "=" LWSP value
                 / "title*" LWSP "=" LWSP ext-value
     ext-value   = <see RFC 8187, Section 3.2>

      注意：下述规范定义的参数值续接特性，
      即 [RFC2231] 第 3 节，使得具有相同名称的扩展参数
      不能出现多个实例，因为续接的处理
      会变得有歧义。因此，
      建议使用此扩展的规范禁止这种情况，
      以兼容 RFC 2231。

      注意：本规范不会自动为以星号结尾的
      参数名赋予新的解释。
      如上所述，应由非扩展参数的规范
      决定是否采用此处定义的语法。
      尽管如此，已知一些现有实现
      会在参数名以星号结尾时
      自动切换为这种记法；因此，
      将以星号结尾的参数名用于其他用途，很可能导致
      互操作性问题。

4.1.  何时使用此扩展

   [RFC2277] 第 4.2 节 要求含有人类可读文本的
   协议元素能够携带语言信息。因此，
   当参数值属于文本且其语言已知时，
   应始终使用 ext-value 产生式。

   此外，只要参数值需要携带
   US-ASCII 编码字符集之外的字符
   （[RFC0020]），也应使用此扩展；请注意，
   定义一个被限制为仅使用 Unicode 字符集某个子集的
   新参数是不可接受的。

4.2.  错误处理

   首部字段规范需要定义是否允许同名参数
   出现多个实例，以及应如何处理它们。
   本规范建议使用扩展语法的参数
   优先。这样，生成方即可同时使用
   这两种格式，而不会破坏尚不理解扩展语法的
   接收方的正常工作。






Reschke                      Standards Track                    [Page 8]

RFC 8187            Charset/Language Encoding in HTTP     September 2017


   示例：

     foo: bar; title="EURO exchange rates";
               title*=utf-8''%e2%82%ac%20exchange%20rates

   在此情况下，发送方为旧接收方提供 ASCII 版本的标题，
   同时也为理解本规范的接收方提供国际化版本。
   显然，后者应优先使用
   新语法而非旧语法。

5.  安全考虑

   本文档描述的格式能够传输非 ASCII 字符，
   因此可能出现字符“欺骗”情形：
   显示出的值看起来与其实际内容不同。

   此外，还存在与 UTF-8 解码相关的
   已知攻击情形。

   有关这两个主题的更多信息，见 [RFC3629] 第 10 节。

   此外，本文档规定的扩展能够
   为单个参数传输多个语言版本。
   当同一参数的不同语言版本并不等价时，
   这种用法可能允许欺骗攻击。
   这种攻击是否能够奏效，
   取决于所规定的参数。

附录 A.  相对于以下规范的变更： RFC 5987

   本节概述相对于 [RFC5987] 的变更：

   o  文档标题改为“指明 HTTP 首部字段参数的
      字符编码和语言”。

   o  重写了引言，以更清楚地解释
      字段值中非 ASCII 字符的相关问题。

   o  移除了支持 "ISO-8859-1" 编码的要求。

   o  本文档不再尝试重新定义通用“参数”的
      ABNF（事实证明，HTTP 中并不存在真正通用的
      参数定义；例如，在空白处理方面
      存在细微差异）。

   o  删除了关于现有实现中错误处理缺陷的说明，
      因为该说明已不再准确。

附录 B.  实现报告

   本文档定义的编码目前用于四个
   不同的 HTTP 首部字段：

   o  "Authentication-Control"，定义于 [RFC8053]，

   o  "Authorization"（用于 HTTP 摘要认证，定义于
      [RFC7616]），

   o  "Content-Disposition"，定义于 [RFC6266]，以及

   o  "Link"，定义于 [RFC5988]。

   由于该编码是 1997 年
   [RFC2231] 所定义编码的配置／澄清，因此许多用户代理
   在 [RFC5987] 发布时就已支持在 "Content-Disposition" 中使用它。

   自 [RFC5987] 发布以来，又有三个流行的桌面用户
   代理增加了对此编码的支持；详情见
   <http://purl.org/NET/http/content-disposition-tests#encoding-
   2231-char>。截至本文撰写时，所有主流桌面
   用户代理的当前版本均支持它。
