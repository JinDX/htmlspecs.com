RFC 9931

HTTP/1.1 乐观协议转换的安全考虑

摘要

在 HTTP/1.1 中，客户端可以请求在现有连接上改用新协议。本文讨论在该请求得到确认之前，客户端所发送数据涉及的安全考虑，并向 RFC 9112 和 RFC 9298 增加新的要求，以避免相关安全问题。¶

1. 概述

本文讨论在同一连接上从 HTTP/1.1 切换至其他协议时产生的一些安全考虑，包括：¶

  • 回顾相关标准；¶

  • 讨论在转换确认前由客户端发送数据可能带来的安全风险；¶

  • 评估现有升级令牌的安全性；以及¶

  • 为实现和未来的标准文档提供指导。¶

对 [HTTP/1.1] 和 [CONNECT-UDP]的更新，包括新的规范性要求，分别见第 8 节和第 6.3节。¶

2. 要求用语

本文中的关键词 "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", "OPTIONAL" 仅当且仅当如这里所示以全大写形式出现时，才按 BCP 14 [RFC2119] [RFC8174] 的说明 解释。¶

3. 背景

在 HTTP/1.1 [HTTP/1.1] 及其后续版本中，单个连接可用于多个请求。在 HTTP/2 [HTTP/2] 和 HTTP/3 [HTTP/3]中，每个请求都由流 ID 显式区分，因此可以多路复用。然而，HTTP/1.1 中的请求严格顺序执行，每个新请求通过前一请求的结束隐式区分。¶

HTTP/1.1 也是唯一允许客户端改变连接剩余部分所用协议的 HTTP 版本。请求这种协议转换有两种机制。一种是 Upgrade 首部字段（[HTTP]， 第 7.8 节）。在请求中包含该字段，表示客户端希望在此连接上使用 HTTP/1.1 以外的协议。如果服务器接受协议变更，就回复 101（Switching Protocols，切换协议）状态码（[HTTP]， 第 15.2.2 节）。¶

另一种机制是 HTTP CONNECT 方法（第 9.3.6 节 ，见 [HTTP]）。该方法表示客户端希望与指定主机和端口建立 TCP 连接。如果接受请求，服务器回复 2xx（Successful，成功）响应，表示请求已接受且 TCP 连接已建立。此后，该 TCP 连接用作 TCP 隧道，而非 HTTP/1.1 连接。¶

这两种机制也都允许服务器拒绝请求。例如， 第 7.8 节 （[HTTP] ）规定：¶

如果服务器希望在该连接上继续使用当前协议，则可以（ MAY ）忽略收到的 Upgrade 首部字段。¶

而 第 9.3.6 节 （[HTTP] ）规定：¶

服务器必须（ MUST ）拒绝目标端口号为空或无效的 CONNECT 请求，通常以 400（Bad Request，错误请求）状态码响应。¶

升级被拒绝很常见，原因可能多种多样，例如：¶

  • 服务器不支持客户端指示的任何升级令牌（即客户端提出的新协议），因此继续使用 HTTP/1.1。¶

  • 服务器知道，对该资源的这次请求而言，升级到提出的协议并不比 HTTP/1.1 更好，因此选择用 HTTP/1.1 响应。¶

  • 服务器要求客户端在升级协议之前进行认证，因此回复 401（Authentication Required，需要认证）状态码，并在 Authorization 响应首部字段中提供质询（[HTTP]， 第 11.6.2 节）。¶

  • 资源已经迁移，因此服务器回复 3xx（Redirection，重定向）状态码（[HTTP]， 第 3.4 节）。¶

同样，服务器也经常拒绝 HTTP CONNECT 请求，例如：¶

  • 服务器不支持 HTTP CONNECT。¶

  • 服务器策略不允许访问指定目标。¶

  • 目标无法解析、不可达或不接受连接。¶

  • 代理要求客户端先认证，再继续处理。¶

拒绝请求后，服务器将继续按照 HTTP/1.1 解释该连接上收到的字节。¶

第 7.8 节 （[HTTP] ）还规定：¶

客户端在完整发送请求消息之前，不能开始在连接上使用升级后的协议（即不能在消息发送到一半时改变所发送的协议）。¶

换言之，完成请求消息是客户端开始使用新协议的 必要 条件。然而必须明确，这不是 充分 条件，因为服务器可能拒绝请求。¶

某些情况下，客户端可能预测服务器很可能接受所请求的协议转换。例如，使用某升级令牌的请求最近成功过，客户端就可能预期后续使用相同令牌的请求也会成功。如果预期正确，客户端通常可以不等待服务器响应，而立即“乐观地”发送新协议的最初字节，从而减少延迟。本文探讨这种“乐观”行为的安全影响。¶

4. 可能的安全问题

如果 HTTP/1.1 连接仅涉及两个独立参与方（客户端与服务器），协议转换不会引入新的安全问题：双方本就必须准备好应对对方随时在连接上发送任意数据。然而，如果请求或响应包含第三方数据，HTTP 连接往往涉及不止两方。例如，浏览器（第一方）可能向某源（第二方）发送 HTTP 请求，其路径、首部或内容由另一个源的网站（第三方）控制。转换后的协议，例如 WebSocket [WEBSOCKET]，也经常用于传输第三方选择的数据。¶

如果第三方数据源不可信，其提供的数据就可能“受攻击者控制”。攻击者控制的数据与乐观协议转换相结合，会产生两个显著的安全问题。¶

4.1. 请求走私

在请求走私攻击中（[HTTP/1.1]， 第 11.2 节），攻击者控制的数据会被服务器解释为额外的 HTTP 请求。这使攻击者得以代表客户端发出请求，同时绕过客户端关于允许发出哪些请求的规则。当客户端与服务器对双方之间流动的数据有不同解释时，就可能发生请求走私。¶

如果服务器接受协议转换请求，就按新协议解释后续字节；如果拒绝，则按 HTTP/1.1 解释这些字节。但客户端只有收到服务器响应的状态码之后，才能知道服务器采用哪种解释。如果客户端乐观地使用新协议，服务器就可能把新协议中受攻击者控制的数据误解为客户端发出的额外 HTTP 请求。¶

【编者概括，非 RFC 原文翻译】此处省略原文的具体攻击示例。风险在于不可信数据可能跨越连接级认证的信任边界；原文涉及认证（[TLS]， 第 4.4.2 节）和请求语义（[HTTP]， 第 9.3.3 节）。本文保留这些引用供理解规范背景，不提供报文、载荷或操作顺序。¶

4.2. 解析器漏洞利用

另一类相关攻击利用协议理解不一致，触发服务器请求解析逻辑中的漏洞。这类攻击适用于 HTTP 客户端受到服务器信任、但转换后的数据源不受信任的情形。如果服务器软件在开发时假设部分或全部 HTTP 请求数据不受攻击者控制，乐观传输可能打破该假设，从而暴露服务器 HTTP 请求解析器中的漏洞。¶

5. 运行问题

如果服务器拒绝转换请求，该连接仍可继续用于 HTTP/1.1。通常并不要求因转换遭拒而关闭连接；如果很可能还会向此服务器发送其他 HTTP 请求，保持连接有性能优势。因此，通常不应仅因转换被拒绝而关闭连接。¶

6. 对使用现有升级令牌的 HTTP Upgrade 的影响

本节说明本文的考虑事项对一些已注册升级令牌 [IANA-UPGR] 的影响；在撰写时，这些令牌被认为仍在使用。¶

6.1. "TLS"

“TLS” 升级令牌族定义于 [RFC2817]，其中正确强调了服务器可能拒绝升级。如果客户端忽视此可能性而乐观地发送 TLS 数据，结果不可能构成有效的 HTTP/1.1：TLS 连接的第一个八位字节必须是 22（ContentType.handshake），但 HTTP/1.1 方法不允许该字符（见 [TLS] 的 第 5.1 节 和 [HTTP/1.1] 的 第 3 节）。符合规范的 HTTP/1.1 服务器会将其视为解析错误，关闭连接且不再处理后续请求。¶

6.2. "WebSocket"/"websocket"

第 4.1 节 （[WEBSOCKET] ）规定：¶

客户端发送初始握手后，必须（ MUST ）等待服务器响应，才能发送任何进一步的数据。¶

因此，WebSocket 协议已经禁止乐观地使用 HTTP Upgrade。此外，WebSocket 要求对客户端发往服务器的帧应用高熵掩码（第 5.1 节 ，见 [WEBSOCKET]）。¶

6.3. "connect-udp"

第 5 节 （[CONNECT-UDP] ）规定：¶

客户端可以（ MAY ）在收到 UDP 代理请求的响应之前，乐观地开始在 HTTP 数据报中发送 UDP 分组。¶

然而，在 HTTP/1.1 中，该“代理请求”是 HTTP Upgrade 请求。在某些情况下升级很可能被拒绝，例如 UDP 目标地址（由攻击者控制）无效时。此外，“connect-udp”协议流的内容可能包含不可信材料（即可能来自客户端设备上其他应用的 UDP 分组），因而可能发生请求走私。为避免这些问题，本文以如下文字替换上述规定，排除 HTTP/1.1 的任何乐观发送：¶

客户端可以（ MAY ）在收到 UDP 代理请求的响应前，乐观地开始在 HTTP 数据报中发送 UDP 分组，但仅限使用 HTTP/2 或更高版本时。由于存在请求走私风险，客户端不得（ MUST NOT ）在 HTTP/1.x 中乐观地发送 UDP 分组。¶

6.4. "connect-ip"

“connect-ip”升级令牌定义于 [CONNECT-IP]。 第 11 节 （[CONNECT-IP] ）禁止客户端在 HTTP/1.1 中乐观地发送分组，因而避免了该问题。¶

7. 未来升级令牌的设计指导

目前已有一些良好的设计示例，可以减少或消除本文讨论的安全问题，也可能适用于未来规范：¶

  • 禁止乐观地使用 HTTP Upgrade（第 4.1 节 ，见 [WEBSOCKET] ，以及 第 11 节 ，见 [CONNECT-IP]）。¶

  • 嵌入有意终止 HTTP/1.1 处理的固定前导序列（第 3.4 节 ，见 [HTTP/2]）。¶

  • 对客户端发往服务器的数据应用高熵掩码（第 5.1 节 ，见 [WEBSOCKET]）。¶

未来的升级令牌规范应考虑这里讨论的安全问题，并就实现如何避免这些问题提供明确指导。¶

7.1. 请求方法的选择

某些升级令牌（例如“TLS”）被定义为可用于任意普通 HTTP 方法。升级后的协议继续提供 HTTP 语义，并传送对该 HTTP 请求的响应。¶

第 6 节 提到的其他升级令牌不保留 HTTP 语义，因此方法无关紧要。它们都仅为不含内容的 GET 请求而规定。¶

未来的升级令牌规范中，如果 HTTP 方法在其他方面无关紧要，且请求不需要承载任何消息内容，就应将使用范围限制为不含内容的 GET 请求。这可以提高与其他升级令牌的一致性，并简化服务器实现。¶

8. HTTP CONNECT 的要求

本文更新 [HTTP/1.1] ，纳入本节余下的文字。本节要求仅适用于 HTTP/1.1。¶

代表不可信 TCP 客户端发送 CONNECT 请求的代理客户端，必须（ MUST ）采取以下一项或两项措施：¶

  1. 等待收到 2xx（Successful，成功）响应后，再转发任何 TCP 载荷数据。¶

  2. 发送“Connection: close”请求首部。¶

如果代理客户端未实现这两种行为中的至少一种，就容易遭受简单的请求走私攻击（[HTTP/1.1]， 第 11.2 节）。¶

在撰写时，一些代理客户端被认为存在上述漏洞。作为缓解措施，代理服务器在拒绝 CONNECT 请求时，必须（ MUST ）关闭底层连接，不得再处理该连接上的任何其他请求。无论请求是否包含“close”连接选项，这一要求都适用。¶

注意，这项缓解措施往往会使正确实现的客户端建立连接更慢，特别是在返回 407（Proxy Authentication Required，需要代理认证）响应时。使用不受此攻击影响的 HTTP/2 或 HTTP/3 可以避免这种性能损失。¶

作为性能优化，如果已知客户端在转发不可信 TCP 载荷前会等待 2xx（Successful，成功）响应（即符合上面的第 1 项），代理服务器可以（ MAY ）禁用该缓解措施。代理服务器可依据请求的 User-Agent 首部字段和用户代理供应商关于其合规性的文档，识别符合要求的客户端。¶
