1.  引言

   本规范注册与 JSON Web 签名（JWS）[JWS]、JSON Web
   加密（JWE）[JWE] 和 JSON Web 密钥（JWK）[JWK] 规范一起使用的密码算法和标识符。
   它为这些标识符定义了若干 IANA 注册表。所有这些
   规范都使用基于 JSON 的 [RFC7159] 数据结构。本
   规范还描述了这些算法和密钥类型所特有的语义和操作。

   将算法和标识符注册在这里，而不是注册在
   JWS、JWE 和 JWK 规范中，旨在使这些规范在所要求、推荐、
   可选和弃用算法的集合随时间变化时仍能保持不变。这也允许
   对 JWS、JWE 和 JWK 规范进行更改，而无需更改本
   文档。

   本规范定义的名称很短，因为一个核心目标是
   使生成的表示形式保持紧凑。

   本文档中的关键词“必须”、“不得”、“要求”、“应当”、“不得”、

3.2.  使用 SHA-2 函数的 HMAC

   基于散列的消息认证码（HMAC）允许使用
   一个秘密值加上密码散列函数来生成 MAC。这
   可用于证明生成 MAC 的一方持有
   MAC 密钥。实现和
   验证 HMAC 的算法在 RFC 2104 [RFC2104] 中给出。

   此算法必须使用与散列输出大小相同（例如，
   对于 "HS256" 为 256 位）或更大的密钥。（此
   要求基于 NIST SP 800-117 [NIST.800-107] 的 第 5.3.4 节（HMAC
   密钥的安全影响），其中指出
   有效安全强度是密钥安全强度
   与内部散列值大小两倍中的较小者。）

   HMAC SHA-256 MAC 按照 RFC 2104 生成，使用 SHA-256 作为
   散列算法 "H"，使用 JWS 签名输入作为 "text" 值，
   并使用共享密钥。HMAC 输出值即为 JWS
   签名。

   以下 "alg"（算法）头部参数值用于
   表示 JWS 签名是使用
   相应算法计算得到的 HMAC 值：

                +-------------------+--------------------+
                | "alg" 参数值      | MAC 算法           |
                +-------------------+--------------------+
                | HS256             | 使用 SHA-256 的 HMAC |
                | HS384             | 使用 SHA-384 的 HMAC |
                | HS512             | 使用 SHA-512 的 HMAC |
                +-------------------+--------------------+

   JWS 的 HMAC SHA-256 MAC 通过按照 RFC 2104 计算 HMAC
   值来验证，其中使用 SHA-256 作为散列算法 "H"，使用
   接收到的 JWS 签名输入作为 "text" 值，并使用
   共享密钥。随后将计算出的 HMAC 值与对接收到的已编码
   JWS 签名值进行 base64url 解码后的结果进行比较。计算出的 HMAC 值
   与 JWS 签名值的比较必须
   以恒定时间方式完成，以抵御时序攻击。

3.4.  使用 ECDSA 的数字签名

   椭圆曲线数字签名算法（ECDSA）[DSS] 支持
   使用椭圆曲线密码学，它能够提供
   与 RSA 密码学相当的安全性，但使用更短的密钥长度，
   并且许多操作具有更高的处理速度。这意味着
   ECDSA 数字签名的长度将显著短于
   具有同等强度的 RSA 数字签名。

   本规范定义将 ECDSA 与 P-256 曲线和
   SHA-256 密码散列函数配合使用，将 ECDSA 与 P-384 曲线
   和 SHA-384 散列函数配合使用，以及将 ECDSA 与 P-521 曲线和
   SHA-512 散列函数配合使用。P-256、P-384 和 P-521 曲线
   定义于 [DSS]。

   ECDSA P-256 SHA-256 数字签名按如下方式生成：

   1.  使用 ECDSA
       P-256 SHA-256 和所需私钥对 JWS 签名输入生成数字签名。输出将是
       一对 (R, S)，其中 R 和 S 是 256 位无符号整数。

   2.  将 R 和 S 按大端顺序转换为八位字节序列，每个
       数组长度为 32 个八位字节。这些八位字节序列
       表示不得通过省略值中包含的任何前导零
       八位字节而缩短。

   3.  按先 R 后 S 的顺序串联这两个八位字节序列。
       （请注意，许多 ECDSA 实现会直接将此
       串联结果作为其输出。）

   4.  得到的 64 八位字节序列即为 JWS 签名值。

   表示 JWS 签名是使用
   相应算法计算得到的数字签名值：

           +-------------------+-------------------------------+
           | ES256             | 使用 P-256 和 SHA-256 的 ECDSA |
           | ES384             | 使用 P-384 和 SHA-384 的 ECDSA |
           | ES512             | 使用 P-521 和 SHA-512 的 ECDSA |

3.6.  使用算法 "none"

   也可以创建不提供完整性保护的 JWS。
   这样的 JWS 称为不安全 JWS。不安全 JWS 使用
   "alg" 值 "none"，其格式与其他 JWS 完全相同，但
   必须使用空八位字节序列作为其 JWS 签名值。
   接收方必须验证 JWS 签名值是空
   八位字节序列。

   支持不安全 JWS 的实现不得将此类
   对象视为有效，除非应用程序明确指定
   对某个特定对象不提供完整性保护是可以接受的。
   实现默认不得接受不安全 JWS。为了
   缓解降级攻击，应用程序不得在全局级别
   表示接受不安全 JWS，并且应该
   针对每个对象分别表示接受。有关使用此算法的安全
   注意事项，请参阅 第 8.5 节。

5.2.2.1.  AES_CBC_HMAC_SHA2 加密

   认证加密算法接受四个八位字节
   串作为输入：秘密密钥 K、明文 P、附加认证数据
   A 和初始化向量 IV。认证密文
   值 E 和认证标签值 T 作为输出提供。
   明文中的数据被加密并认证，而
   附加认证数据被认证但不加密。

   加密过程如下，或者使用一组等效的
   步骤：

   1.  从输入密钥 K 按如下方式生成
       次级密钥 MAC_KEY 和 ENC_KEY。这两个密钥都是八位字节
       串。

          MAC_KEY 按顺序由 K 的前 MAC_KEY_LEN 个八位字节
          组成。
          ENC_KEY 按顺序由 K 的后 ENC_KEY_LEN 个八位字节
          组成。

RFC 7518                JSON Web 算法（JWA）               2015 年 5 月


       输入密钥 K 中的八位字节数必须等于
       MAC_KEY_LEN 和 ENC_KEY_LEN 之和。这些参数的值由
       第 5.2.3 节到 5.2.5 节中的认证加密算法
       指定。请注意，在输入密钥 K 中，MAC 密钥位于
       加密密钥之前；这与标识符 "AES_CBC_HMAC_SHA2"
       中算法名称的顺序相反。

   2.  使用的 IV 是一个为密码算法随机或
       伪随机生成的 128 位值。

   3.  使用 PKCS #7 填充对明文执行 CBC 加密，
       其中 ENC_KEY 作为密钥，IV 作为初始化向量。我们将此步骤得到的密文输出
       记为 E。

   4.  八位字节串 AL 等于
       附加认证数据 A 的位数，并表示为 64 位无符号
       大端整数。

       [RFC2104] 来计算消息认证标签 T：

          附加认证数据 A，
          初始化向量 IV，
          上一步计算出的密文 E，以及
          上面定义的八位字节串 AL。

       计算得到的 MAC 输出记为 M。M 的前 T_LEN 个八位字节
       用作 T。

   6.  返回密文 E 和认证标签 T，作为
       认证加密的输出。

   IV 和 E 分别表示密钥、明文、附加认证数据、

      MAC_KEY = K 的前 MAC_KEY_LEN 个八位字节，
      ENC_KEY = K 的后 ENC_KEY_LEN 个八位字节，
      E = CBC-PKCS7-ENC(ENC_KEY, P),

5.2.2.2.  AES_CBC_HMAC_SHA2 解密

   认证解密操作有五个输入：如上定义的 K、A、IV、E
   和 T。它只有一个输出：要么是
   明文值 P，要么是表示输入
   未通过认证的特殊符号 FAIL。认证解密算法
   如下，或者使用一组等效的步骤：

   1.  按照 第 5.2.2.1 节步骤 1 的方式，从
       输入密钥 K 生成次级密钥 MAC_KEY 和 ENC_KEY。

   2.  通过按照
       第 5.2.2.1 节步骤 5 中的输入计算 HMAC，
       来检查 A 和 E 的完整性和真实性。将前一步中的值 T
       与 HMAC 输出的前 MAC_KEY 长度位进行比较。如果
       这些值相同，则认为 A 和 E 有效，
       并继续处理。否则，丢弃 MAC 验证中使用的
       所有数据，认证
       解密操作返回失败指示，并
       停止该操作。（但有关抵御时序攻击的安全
       注意事项，请参阅 [JWE] 第 11.5 节。）

   3.  解密值 E，并检查和
       移除 PKCS #7 填充。值 IV 用作初始化向量。值
       ENC_KEY 用作解密密钥。

   4.  返回明文值。

5.2.3.  AES_128_CBC_HMAC_SHA_256

   此算法是上述通用
   AES_CBC_HMAC_SHA2 算法的具体实例。它使用带 SHA-256 散列函数 [SHS] 的 HMAC 消息
   认证码 [RFC2104] 提供消息认证，
   并将 HMAC 输出截断为 128
   位，对应于
   [RFC4868] 中定义的 HMAC-SHA-256-128 算法。对于加密，它使用
   [NIST.800-38A] 第 6.2 节中定义的 CBC 操作模式下的 AES，

8.1.  密码敏捷性

   实现者应该意识到，密码算法会
   随时间推移而变弱。随着新的密码分析技术被开发出来以及
   计算性能提高，破解特定
   密码算法所需的工作量将会降低。因此，实现者和
   部署必须准备好让所支持和使用的算法集合
   随时间发生变化。因此，密码
   算法实现应该采用模块化设计，以便能够轻松加入新算法。

8.2.  密钥生命周期

   许多算法都有与
   密钥生命周期和/或密钥可使用次数相关的安全注意事项。
   当这些算法与 JOSE 数据结构一起使用时，这些安全注意事项
   仍然适用。有关密钥生命周期的具体指导，请参阅 NIST SP 800-57
   [NIST.800-57]。

8.3.  RSAES-PKCS1-v1_5 安全注意事项

   尽管 RFC 3447 第 8 节 [RFC3447] 明确要求人们
   不要在新应用中采用 RSASSA-PKCS1-v1_5，而应
   迁移到 RSASSA-PSS，但出于互操作性原因，本规范确实包含
   RSASSA-PKCS1-v1_5，因为它已被
   广泛实现。

   与 RSAES-PKCS1-v1_5 一起使用的密钥必须遵循
   RFC 3447 第 7.2 节中的约束。此外，不得使用
   “对 RSA 密码系统的二十年攻击”[Boneh99] 第 3 节中所述的
   低公钥指数值密钥。

8.4.  AES GCM 安全注意事项

   与 AES GCM 一起使用的密钥必须遵循
   [NIST.800-38D] 第 8.3 节中的约束，其中指出：“认证加密函数的
   总调用次数不得超过 2^32，包括
   所有 IV 长度以及使用给定密钥的认证加密
   函数的所有实例”。按照此规则，使用
   同一密钥值时，AES GCM 的使用次数不得超过 2^32 次。

   同一个 IV 值绝不能与同一个 AES
   GCM 密钥多次使用。一种防止这种情况的方法是将计数器与密钥一起存储，
   并在每次使用时递增该计数器。该计数器也可用于
   防止超过上述 2^32 限制。

   此安全注意事项不适用于组合的 AES-CBC
   HMAC SHA-2 或 AES Key Wrap 算法。

8.5.  不安全 JWS 的安全注意事项

   不安全 JWS（使用 "alg" 值 "none" 的 JWS）不提供
   完整性保护。因此，它们只能用于
   载荷通过数字签名
   或 MAC 值以外的方式受到保护，或者无需保护的上下文中。

   一种防止默认接受不安全 JWS 的示例方法是，
   假想的 JWS 软件库的 "verify" 方法具有
   一个布尔值 "acceptUnsecured" 参数，用来指示 "none" 是
   可接受的 "alg" 值。另一个例子是，"verify" 方法
   可以接受应用程序可接受的算法列表
   作为参数，并且如果
   "none" 不在该列表中，则拒绝不安全 JWS 值。

   以下示例说明了不应在全局级别接受
   不安全 JWS 的原因。假设某应用程序通过两个通道接受
   JWS：（1）HTTP，以及（2）带客户端
   认证的 HTTPS。它要求通过
   HTTP 接收的对象具有 JWS 签名，但通过 HTTPS 接受不安全 JWS。如果应用程序
   在全局范围表示接受 "none"，那么攻击者
   可以通过 HTTP 向其提供不安全 JWS，而该
   对象仍能成功通过验证。相反，应用程序需要
   针对通过 HTTPS 接收的每个对象表示接受 "none"
   （例如，将上述第一个
   假想 JWS 软件库中的 "acceptUnsecured" 设置为 "true"），但不能对
   通过 HTTP 接收的每个对象这样做。

8.6.  拒绝服务攻击

   验证签名的接收代理和
   加密消息的发送代理在使用大于本规范规定大小的密钥
   验证签名和加密消息时，需要注意密码处理
   资源的使用。攻击者可能会
   提供使用会导致过量
   密码处理的密钥的内容，例如，使用大于
   本规范规定大小的密钥。实现应该设置并
   强制执行其接受的密钥大小上限。NIST SP 800-57 [NIST.800-57] 的 第 5.6.1 节
   （可比算法强度）
   包含有关最大批准密钥大小的说明，这些说明可能
   适用。

   等）来加密多个 JWK 或 JWK 集对象，或者多次加密
   同一个 JWK 或 JWK 集对象。一项防止

8.8.  密码注意事项

   密码容易受到多种攻击。为了帮助缓解
   其中一些限制，本文档应用 RFC
   2898 [RFC2898] 中的原则，从用户提供的
   密码派生密码密钥。

   然而，密码的强度仍然具有显著影响。
   高熵密码对字典攻击具有更强的抵抗力。
   [NIST.800-63-2] 包含估算密码熵的指导原则，
   可以帮助应用程序和用户生成更强的密码。

   理想密码的长度应与
   派生密钥长度相同（或更长）。但是，大于某个
   算法特定大小的密码会首先经过散列，这会将攻击者的
   有效搜索空间缩小到散列算法的长度。推荐
   用于 "PBES2-HS256+A128KW" 的密码不少于
   16 个八位字节且不超过 128 个八位字节，而用于
   "PBES2-HS512+A256KW" 的密码不少于 32 个八位字节且不超过
   128 个八位字节。

   尽管如此，仍需谨慎考虑在哪里以及如何使用基于密码的
   加密。如果迭代次数太小，这些算法仍可能受到
   基于字典的攻击；如果这些算法用于保护
   攻击者可以无限次尝试绕过
   保护的数据，例如存储在文件系统上的受保护数据，则尤其需要
   关注这一点。
