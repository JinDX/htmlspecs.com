2. 引言

本规范定义关联 Web 存储（LWS）协议，该协议使客户端应用能够 根据代理的身份和权限访问和管理 Web 资源。

通过将资源服务器管理关联资源层次结构并提供其访问的方式标准化，该 协议使用户能够使用不同的客户端应用与同一份已存储数据交互。这些 关联资源通过容器和包含关系来定义，二者描述事物所处的 位置，同时还通过描述资源之间相互关系的元数据来定义。

该协议定义了对这些资源进行创建、读取、更新和删除的标准操作。每个 资源均由一个 URI 标识。客户端从根容器开始浏览资源层次结构， 通过服务器响应中提供的链接发现所包含的资源及其关系。

代理的身份通过身份提供方确认，该提供方可以位于关联 Web 存储 服务器之外。这种松散耦合意味着服务器不一定直接管理凭据；相反，它 可以接收并验证已签名的身份验证凭据，该凭据作为令牌由受信任的身份 提供方签发。因此，用户可以向符合规范的服务器出示现有身份，而不总是需要一个 专门用于该服务器的新账户或现有账户。LWS 使用以下规范中定义的用户身份验证， 例如 OpenID Connect、SAML 2.0 和自签名受控标识符（CID）的规范。

授权确定发出请求的代理是否有权访问资源或对其执行 操作。符合规范的 LWS 服务器为每个资源指定一个资源管理者，由其确定 资源是私有的（即仅供其所有者使用）、受限的（即供一个已定义的 用户集合使用），还是公开的（即供任何用户使用）。服务器在处理每个客户端请求时，执行 资源管理者的访问决策。

本规范的预期使用者包括：

  • 构建访问以下资源的客户端应用的开发者：存储资源
  • 构建符合规范的服务器以协调对以下资源的访问的开发者：存储资源

不同的 LWS 服务器实例各自维护自己的关联资源层次结构。代理可以使用 相同的身份标识跨服务器浏览，对每个服务器资源的访问取决于 该服务器的资源管理者授予的权限。不能保证每个 LWS 服务器实例 都支持所有可能的代理标识符；任何给定的 LWS 服务器实例都可能要求代理 通过特定身份提供方标识自身，以获得对该服务器实例所管理资源的 访问权限。

2.1 资源访问

LWS 协议定义标准交互，使某一方能够将某些资源提供给 某些 代理。

  • 所提供的资源 - （可用资源？已发布的 资源？）（未 在 UCS 中定义）服务暴露的网络可访问实体，可供交互、 检索或操作，所用协议由本文档定义。
  • 请求代理 - （实体，见 UCS）一种实体 （例如客户端、用户或进程），它发起请求以与可提供的资源交互。

2.2 安全与隐私

一个 资源管理者 可以使一个 所提供的资源 保持私有，可以将其向任何人公开，或者可以将其可见性限制在一组受约束的 请求代理 之内。

  • 身份验证 - 验证一个 代理 身份的过程，该代理 正在执行请求。
  • 授权 - 确定一个 代理 是否有权访问特定资源或执行一组 操作 之一的过程。
  • 资源 管理者 - （控制者，见 UCS）一个 代理，其有权控制对以下资源的访问：所提供的资源。

3. 术语

术语“授权服务器”和“客户端”由 OAuth 2.0 授权框架定义 [RFC6749]。

术语“最终用户”和“签发方”由 OpenID Connect 核心 1.0 定义 [OPENID-CONNECT-CORE]。

本规范定义以下术语：

  • 访问授权 — 一个由 存储控制者 创建的数据对象，表达 某个 代理 执行特定动作的能力，其作用对象为 存储资源 且处于某些 已定义的约束之内。
  • 访问配置文件 — 访问配置文件描述 表达有效访问策略的要求。每个访问配置文件均使用 一个 URI 标识，服务器表示支持一个或多个访问配置文件的方式是 在其服务对象的 conformsTo 属性中引用这些配置文件，该服务对象位于其 存储描述 资源中。
  • 访问请求 — 一个由 代理 提交的数据对象，表达一个 对以下资源执行特定动作的请求：存储资源，包括 期望的范围 和约束。
  • 代理 — 由 URI 标识的个人、社会实体或软件。
  • 身份验证凭据 — 一种安全 令牌，断言关于某个 代理 或最终用户的声明。该令牌通过密码学证明来保障安全。 身份验证凭据的示例包括身份断言，例如 OpenID Connect ID 令牌 和基于 SAML 的断言，以及 能力断言，例如 ZCAP。
  • 身份验证套件 — 一种已定义的验证 机制，适用于以下凭据的具体序列化形式：身份验证凭据。
  • 辅助资源 — 一种 存储资源 它相对于某个 存储资源 扮演特定角色，后者称为其 主要 资源， 且其生命周期与该主要资源绑定。 本规范定义 链接集资源 和 元数据资源 作为辅助资源的类型， 但 LWS 服务器 可以自由管理其他种类的辅助资源（例如访问控制 资源、通知收件箱）。 辅助资源通过 Web 链接发现 [RFC8288]，这些链接具有特定类型（参见第 9.1 资源元数据 节）。 在某些实现中，一些辅助资源可能与其主要资源相同。
  • 存储 资源 — 一种 HTTP 资源，其定义见 HTTP 语义，它支持以下规范所定义的读取操作：关联 Web 存储 协议。 遵循 HTTP 语义，本规范“不限制资源的性质；它仅 定义一个可用于与资源交互的接口。” [RFC9110] 此类由 IRI https://www.w3.org/ns/lws#StorageResource 标识。
  • 容器 — 一种 存储资源，它能够 枚举一组 存储资源，并符合以下章节中描述的约定， 见 第 8 节 容器。创建新资源于 容器中或删除现有容器的能力遵循以下章节概述的要求：第 9 节 操作。
  • 数据资源 — 一种承载数据的 存储资源 例如文档、图像或结构化信息，其对更新和删除操作的支持 遵循以下章节概述的要求：第 9 节 操作。
  • 包含关系 — 以下二者之间的关系：一个 容器 与以下 存储资源 它们的生命周期由该 容器 管理。
  • 链接集 资源 — 一种 辅助资源，其 表示符合 链接集：媒体类型和一种链接关系类型 供链接集使用。链接集资源的更新操作遵循 以下章节概述的要求：第 9 节 操作。
  • 元数据 资源 — 一种 辅助资源，由一个 存储 管理，描述一个 存储资源，并符合以下内容中描述的约定， 见 待定。元数据资源的生命周期绑定到以下 存储资源，即它所描述的资源。
  • 资源 — 资源是，如 以下规范所述 [WebArch] 和 [RFC3986]，“任何可能 由 URI 标识的事物”。其本质特征可以通过消息传达的资源（例如 网页、图像、结构化数据对象……）称为 信息 资源 [WebArch]。
  • 存储 — 一组 按层次结构组织的 HTTP 资源，其生命周期遵循以下规范描述的约定进行管理： 关联 Web 存储协议。一个存储由一个 存储 描述资源 描述，该资源引用一组提供可供操作的服务，其作用对象为 这些资源。
  • 存储控制者 — 一个 代理，控制以下存储中的所有资源：存储。
  • 存储描述 — 一个 存储资源，符合以下文档的要求： W3C 受控标识符文档 [CID-1.0]，它描述一个 存储 及其 服务和能力。
  • 存储根 — 一个 容器，位于以下 包含关系 层次结构的根部，该层次结构属于 一个 存储。存储根是唯一的 存储资源，它没有父级于 LWS 包含关系 层次结构中，也没有 主要资源。
  • 通知 — 一条消息，描述发生于某个 资源上的事件。
  • 订阅 — 一项注册，表达接收 给定资源或一组资源的通知的意愿。
  • 订阅者 — 一个 代理，它创建一个 订阅 并 接收由此产生的通知。
  • 通知套件 — 一种已定义的投递机制， 适用于具体渠道，通知通过该渠道发送给一个 订阅者。

4. 身份验证

本节定义一种机制，用于识别 代理 和最终用户，它们与 关联 Web 存储服务器交互。本规范不强制要求特定的 格式用于一个 身份验证凭据，但它确实描述了如何将 现有身份系统 与关联 Web 存储授权框架结合使用。

4.1 身份验证 凭据数据模型

本节描述的数据模型概述了适用于任何 具体序列化形式的要求，针对一个 身份验证凭据。

一个 身份验证凭据 必须 包含关于主体的可检测篡改的声明，包括：

  • 主体 必需 — 最终用户的标识符。此标识符 必须 是 URI。
  • 签发方 必需 — 签发以下 身份验证凭据 的实体的标识符。此标识符 必须 是 URI。
  • 客户端 必需 — 客户端应用的标识符。此标识符 应当 是 URI。
  • 受众 限制 建议 — 一个值列表，该列表 应当 包含授权服务器标识符。

4.2 身份验证 凭据验证

验证一个 身份验证凭据 需要一种信任 关系，其双方为 凭据的验证方和签发方。这种信任关系 可以 建立 于带外机制之上。任何其他用于建立信任的机制， 在验证方与签发方之间，均概述于特定的 身份验证套件 中。

一个 身份验证凭据 必须 经过签名。建议 该签名 使用非对称密码学。

4.3 身份验证 凭据类型标识符

每个 身份验证套件 必须 关联一个令牌类型 URI。一个 身份验证套件 应当 使用 IANA “OAuth URI”注册表中定义的 URI。

5. 授权

关联 Web 存储描述了一种在 Web 上持久保存和管理受保护数据的机制。 授权是一种机制， 借助该机制，代理 请求并出示访问令牌，以访问这些 受保护的数据。

本节定义一个基于 OAuth 2.0 的授权框架 [RFC6749]，作为用于 获取和出示 访问令牌的基线机制。服务器 可以 支持超出此范围的其他授权机制， 即此基线之外的机制。

5.1 角色

LWS 授权中的角色与 OAuth 2.0 第 1.1 节定义的角色相同 [RFC6749]： 资源所有者、 资源服务器、 客户端（在本规范中称为 授权客户端，以 避免歧义），以及 授权服务器。 存储服务器是一种同时符合 LWS 存储规范的资源服务器。

5.2 协议流程

本规范描述客户端与授权服务器之间的交互，以及 客户端与符合规范的存储服务器之间的交互。

授权服务器与存储服务器之间的交互不在本 规范的范围内。 授权服务器可以与存储服务器是同一台服务器，也可以是独立的实体。

5.2.1 授权服务器 发现

存储服务器管理的所有受保护资源都需要一个有效的访问令牌，该令牌由一个 受信任的 授权服务器生成。客户端可以通过发起请求来发现受信任的授权服务器的位置，所发起的是 一个 对受保护资源的未经授权的 HTTP 请求。

生成 401（未授权）响应的存储服务器 必须 发送一个 WWW-Authenticate 首部字段， 其中至少包含一个符合规范的质询。符合规范的质询 必须 包含 resource_metadata 参数，该参数定义于以下规范的第 5.1 节 [RFC9728]，其值是以下文档的 URL， 即 受保护资源元数据 文档，对应于 所请求的资源。

响应还 必须 包含一个 Link 首部，标识以下 存储，其中包含 所请求的资源，具体如 6.1.2 发现与绑定 中所述。客户端将此 URI 作为 resource 参数提供，以请求访问令牌，具体如 5.2.5.1 请求 中所述。

可以 包含其他首部和参数。

以下给出一个 401 响应示例。

示例 1 
HTTP/2 401 Unauthorized
Link: <https://storage.example/storage_1>; rel="https://www.w3.org/ns/lws#storage"
WWW-Authenticate: Bearer resource_metadata="https://storage.example/.well-known/oauth-protected-resource/storage_1/photos/img.jpg",
                error="invalid_token"

5.2.2 受保护资源 元数据

（有移除风险的特性）问题

工作组正在积极征求实现者对受保护资源元数据 支持的反馈。 如果未能收集到足够的实现经验，此特性可能被移除或更改。

一个 受保护资源元数据 文档描述客户端如何获取 用于某个 资源的访问令牌。它 必须 符合 OAuth 2.0 受保护资源元数据 [RFC9728]。

本规范扩展 [RFC9728]，具体如下： authorization_servers 参数是 必需 的，位于 受保护资源元数据文档中，其值 必须 包含 至少一个签发方标识符，来自 授权服务器。

注

受保护资源元数据文档中的 resource 值标识 所请求的资源，而非 以下 存储，后者包含该资源。相比之下， 令牌请求的 resource 参数 标识该存储，它将成为访问令牌的受众。

以下给出一个受保护资源元数据文档示例。

示例 2 
{
    "resource": "https://storage.example/storage_1/photos/img.jpg",
    "authorization_servers": ["https://authorization.example"]
}

5.2.3 发现结果验证 由客户端执行

客户端用于获取访问令牌的值由存储服务器提供，包含于一个 401 （未授权） 响应中。在请求访问令牌之前，客户端 必须 执行 以下检查，每项检查都会比较一个 发现的值与产生该 401 响应的请求 URI。如果任何检查失败， 客户端 不得 使用发现的值来请求访问令牌。

  • resource_metadata URL 必须 具有相同的方案和 权威部分，与请求的 URI 一致。
  • resource 值，位于以下 受保护资源元数据 文档中，必须 完全等于 请求的 URI，这是以下规范第 3.3 节的要求 [RFC9728]。
  • 客户端 必须 获取以下 存储描述，其所属的 存储 由 Link 首部标识，且其 StorageRoot 服务的 serviceEndpoint 必须 具有相同的方案 和权威部分，与请求的 URI 一致。
注

这些检查确保受保护资源元数据与存储均描述以下 服务器，即 客户端向其发送请求的服务器，从而使以下规范第 7.3 节描述的 TLS 服务器身份验证 [RFC9728] 适用于 该元数据。没有这些检查，恶意服务器可能导致客户端获取一个访问令牌， 用于另一个 存储，然后重放该令牌。客户端可以缓存存储描述，以避免检索 它，在每次 令牌请求之前。参见 16.3 资源发现。

5.2.4 授权服务器 元数据

授权服务器 必须 提供一个元数据资源，使客户端能够 发现端点的位置和能力，具体描述 见 [RFC8414]。此元数据资源 必须 可通过具有以下路径的 URL 访问： /.well-known/lws-configuration。

除了以下规范定义的元数据之外 [RFC8414]，一个 LWS 授权服务器元数据文档 还定义以下参数：

  • subject_token_types_supported 可选。JSON 数组，包含一个有效的 subject_token_type 值列表， 这些值可提供给授权服务器的令牌端点。授权服务器 应当 声明其支持的主体令牌，方法是将此 条目包含在服务器元数据文档中。
  • subject_identifier_types_supported 可选。JSON 数组，包含一个主体标识符类型列表，这些类型由 授权服务器支持。 每个值都是以其方案开头的 URI，例如 "https:"；或者，对于 去中心化标识符， 则为 "did:" 后接 DID 方法名（例如 "did:web"、 "did:key"）。 授权服务器 应当 声明其支持的主体标识符类型， 方法是将此条目包含在服务器元数据文档中。 如果省略，默认值为 ["https"]。

以下给出一个授权服务器元数据资源示例。

示例 3 
{
    "issuer": "https://authorization.example",
    "grant_types_supported": [
        "urn:ietf:params:oauth:grant-type:token-exchange"],
    "token_endpoint": "https://authorization.example/token",
    "jwks_uri": "https://authorization.example/jwks",
    "claims_supported": [
        "sub",
        "iss",
        "client_id",
        "aud"],
    "response_types_supported": [
        "token"],
    "subject_token_types_supported": [
        "urn:ietf:params:oauth:token-type:jwt",
        "urn:ietf:params:oauth:token-type:id_token"],
    "subject_identifier_types_supported": [
        "did:web",
        "did:key",
        "https"]
}

5.2.5 令牌交换

LWS 授权服务器是符合规范的 OAuth 2.0 授权服务器，能够签发 访问令牌给客户端， 以供其与存储服务器交互时使用。为了签发访问令牌，客户端必须先出示一个 有效的主体令牌， 例如一个 身份验证凭据，将其提供给 授权服务器，所用机制为 OAuth 2.0 令牌交换 [RFC8693]。

5.2.5.1 请求

授权服务器的令牌端点 必须 支持 urn:ietf:params:oauth:grant-type:token-exchange 授权类型，具体如 OAuth 2.0 令牌交换中所述 [RFC8693]。

使用令牌交换授权类型时，适用以下附加要求：

  • resource 参数是 必需 的。此 参数的值 必须 是 URI，并将用于 填充所生成访问令牌中的 aud（受众）声明。 所提供的值 必须 是以下 URI，属于 存储，其中包含所请求的资源，该 URI 提供 于 Link 首部中，该首部来自 一个未经授权的响应。授权服务器 必须 拒绝任何 请求，如果其中的 resource 参数 标识一个未知或不受信任的 存储。
  • subject_token 参数是 必需 的。 此参数的值 必须 包含有效的主体令牌， 例如一个 身份验证 凭据。
  • 在向客户端返回访问令牌之前，授权服务器 必须 成功验证所有出示的令牌。

令牌请求的非规范性示例（subject_token 参数已被 截断）。

示例 4 
POST /token HTTP/1.1
Host: authorization.example
Content-Type: application/x-www-form-urlencoded

grant_type=urn%3Aietf%3Aparams%3Aoauth%3Agrant-type%3Atoken-exchange
&resource=https%3A%2F%2Fstorage.example%2Fstorage_1
&subject_token=eyJ0eXAiOiJhcytqd3QiLCJhbGciO...fiK51VwhsxJ-siBMR-YFiA
&subject_token_type=urn%3Aietf%3Aparams%3Aoauth%3Atoken-type%3Aid_token
5.2.5.2 响应

如果令牌请求有效且客户端有权发起该请求，则 授权服务器的响应 必须 符合 OAuth 2.0 授权框架的第 5.1 节 [RFC6749]。所生成的访问 令牌 必须 符合 用于 OAuth 2.0 访问令牌的 JSON Web 令牌配置文件 [RFC9068]。

此外，访问令牌必须满足以下要求：

  • sub（主体）— 必需。此声明 必须 是一个 URI，标识以下 代理，其正在执行 该操作
  • iss（签发方）— 必需。此声明 必须 是授权服务器的 URI
  • client_id（客户端标识符）— 必需。 此声明 必须 是标识客户端的 URI。
  • aud（受众）— 必需。此声明 必须 包含以下 URI，由 客户端在 resource 参数中提供，它是一个 存储 的 URI。此 值将用于限制 访问令牌对哪些实体有效。
  • exp（过期时间）— 必需。 授权服务器 应当 签发生命周期较短的令牌 （建议：300 秒或更短），以限制令牌 失窃造成的暴露风险。
  • iat（签发时间）— 必需。
  • jti（JWT 标识符）— 必需。

以下给出一个成功令牌响应的非规范性示例。

示例 5 
HTTP/1.1 200 OK
Content-Type: application/json

{
    "access_token":"eyJ0eXAiOiJhcytqd3QiLCJhbGciOiJFUzI1NiIs...DeWt4QuZXso",
    "token_type":"Bearer",
    "expires_in":300
}

所有无效或未经授权的请求 必须 产生错误响应， 具体描述见第 5.2 节，位于 OAuth 2.0 授权框架 [RFC6749]。

示例 6 
HTTP/1.1 400 Bad Request
Content-Type: application/json

{
    "error":"invalid_request"
}

5.2.6 令牌验证 由存储服务器执行

一旦客户端持有访问令牌，它就会将该令牌出示给存储服务器。 存储服务器负责在执行任何操作之前验证该令牌。

5.2.6.1 提交

客户端 必须 向存储服务器出示访问令牌，所用的是 Authorization 首部， 其中的身份验证方案定义于 [RFC6750]。

示例 8 
Authorization: Bearer eyJ0eXAiOiJhcytqd3QiLCJhbGciOiJFUzI1NiIs...DeWt4QuZXso
5.2.6.2 验证

存储服务器 必须 验证访问令牌，方法是执行 以下检查，任何检查失败时均拒绝请求：

  • JWT 签名验证：使用授权服务器的公钥验证 JWT 签名， 该密钥检索自 授权服务器元数据中指定的 jwks_uri。存储服务器 应当 缓存这些密钥，并且 必须 支持密钥轮换。
  • 签发方验证：验证 iss 声明是否匹配预期的授权 服务器标识符。
  • 受众验证：验证 aud 声明是否包含以下 存储 的 URI，该存储包含 目标资源。
  • 时间验证，允许系统之间存在一定的时钟偏差。
    • 验证当前时间是否早于 exp（过期时间）声明。
    • 验证当前时间是否不早于 nbf（生效时间）声明，如果该声明 存在。
    • 验证 iat（签发时间）声明是否不在未来。

如果验证失败，存储服务器 必须 返回 401 Unauthorized， 并带有一个 WWW-Authenticate 首部， 其中包含 resource_metadata 参数和适当的 error 参数 （例如， invalid_token、invalid_request 或 insufficient_scope）。

如果令牌在其他方面有效，但授权策略不允许所请求的 操作， 则存储服务器 必须 拒绝该请求。

6. 发现

6.1 存储描述资源

一个 存储描述资源 提供 客户端可以使用的信息， 当其与一个 存储 交互时，包括能力和 服务端点的描述。

6.1.1 数据模型

一个 存储描述资源 是一种 特化的 W3C 受控标识符 文档 [CID-1.0]。 它符合以下规范定义的数据模型 [CID-1.0]，并扩展了 LWS 特有的属性。

  • id - id 属性是 必需 的。其值 必须 是规范 URI， 属于以下 存储。 根据 [CID-1.0]，此 URI 也是规范 URL，对应于该受控标识符文档。
  • type - type 属性是 必需 的。其值 必须 是一个字符串， 等于 Storage，或是一组字符串，其中包含一个等于 Storage 的项 （区分大小写）。
  • capability - capability 属性是 可选 的。其值 必须 是一组 能力，其中每项能力由包含以下属性的映射描述。 可以 存在其他属性。
    • id - id 属性是 可选 的。如果存在，其值 必须 是 URI。
    • type - type 属性是 必需 的。其值 必须 是一个字符串 或一组字符串。
  • service - service 属性是 必需 的。其值 必须 是一组服务， 其中每个服务由包含以下属性的映射描述。其他 属性 可以 存在。 该集合 必须 包含一个服务，其 type 等于 StorageRoot。
    • id - id 属性是 可选 的。如果存在，其值 必须 是 URI。
    • type - type 属性是 必需 的。其值 必须 是一个字符串 或一组字符串。
    • serviceEndpoint - serviceEndpoint 属性是 必需 的。其值 必须 是 URI。
示例 9: 最小存储描述资源 
{
  "@context": [
    "https://www.w3.org/ns/cid/v1",
    "https://www.w3.org/ns/lws/v1"
  ],
  "id": "https://storage.example/",
  "type": "Storage",
  "service": [{
    "type": "StorageRoot",
    "serviceEndpoint": "https://storage.example/root/"
  }]
}

6.1.2 发现与绑定

所有针对 GET 和 HEAD 请求的响应，如果请求的目标是 存储 资源，必须 包含一个 Link 首部，其目标是以下 存储 的规范 URI，并包含一个 关系 （rel）参数，其值等于 https://www.w3.org/ns/lws#storage。

对以下 存储 URI 的请求 必须 返回一个文档，该文档 符合 存储描述资源 数据模型，并具有 媒体类型 application/lws+cid， 除非内容协商要求其他格式。

6.1.3 存储能力

一个 存储描述 可以包含描述， 涉及以下 存储 支持的附加能力。

一个 存储，如果允许客户端更改 up 链接， 该链接属于一个 存储资源， 并由此将资源移动于以下 容器 之间，具体如 9.6 移动资源于 容器之间 中所述，则 必须 描述一项能力，其 type 等于 MoveResource。客户端 不得 假定 up 链接可以修改，如果 不存在此能力。以下属性定义用于一个 MoveResource 能力：

  • appliesTo - appliesTo 属性是 可选 的。如果存在，其值 必须 是一 组字符串，指明以下 存储资源 的类型，即该 能力所适用的类型，例如 DataResource 或 Container。如果该属性不存在，则该能力 适用 于 数据资源，且仅限于此。
  • preservesIdentifier - preservesIdentifier 属性是 可选 的。 如果存在，其值 必须 是一个布尔值，表示以下 存储 是否保留标识符， 该标识符属于被移动的资源。如果该属性不存在，客户端 不得 假定 标识符会被 保留，并且 必须 依赖更新响应来确定 以下对象的标识符，即 该资源。
示例 10: 存储描述资源，声明客户端可以移动 资源于容器之间 
{
  "@context": [
    "https://www.w3.org/ns/cid/v1",
    "https://www.w3.org/ns/lws/v1"
  ],
  "id": "https://storage.example/",
  "type": "Storage",
  "capability": [{
    "type": "MoveResource",
    "appliesTo": ["DataResource", "Container"],
    "preservesIdentifier": true
  }],
  "service": [{
    "type": "StorageRoot",
    "serviceEndpoint": "https://storage.example/root/"
  }]
}

6.1.4 存储服务

一个 存储描述资源 必须 包含一个 StorageRoot 服务，其 serviceEndpoint 是以下 存储根 容器的 URI。 与一个 存储 连接的其他服务也 可以 存在。 这些附加服务的 API 定义不在本规范的范围内。

6.1.5 存储 描述表示

一个 存储描述 必须 能够以媒体类型 application/lws+cid 序列化。 @context 属性 必须 是一个数组，以以下 URI 开头： https://www.w3.org/ns/cid/v1 和 https://www.w3.org/ns/lws/v1。 其他表示 可以 通过内容协商提供。

    "https://www.w3.org/ns/lws/v1"

  "type": "Storage",
  "capability": [{
    "type": "https://feature.example/PatchSupport",

      "text/turtle": ["application/sparql-update"],

      "application/linkset+json": ["application/json-patch+json", "application/merge-patch+json"]
    }
  }, {
    "type": "https://feature.example/ResumableUploads"
  }, {
    "type": "https://feature.example/ContentNegotiation",
    "source": "application/ld+json",
    "target": ["text/turtle", "application/n-triples"]
  }, {
    "type": "https://feature.example/ContentNegotiation",
    "source": "image/jpeg",

7. 逻辑资源组织

7.1 容器模型

关联 Web 存储将资源组织到 容器 中。一个 容器 是一种 特化的资源，持有对其他资源的引用，这些资源称为其成员。容器充当 组织单元，类似于目录或集合，使客户端能够对资源进行分组、发现 和浏览。容器维护对其成员资源的引用， 这些成员既可以包含非容器资源，也可以包含其他容器资源，从而实现 层次结构。通常，容器仅持有极少的自身内容， 除了元数据或其成员的枚举；其主要作用是聚合和组织 下级资源。存储 系统的根被指定为一个 容器，充当 没有上级父容器的最高组织单元。以下 容器表示 的结构定义于 8.1 容器 表示；其媒体类型和分页要求定义于 12. LWS 媒体类型。 存储 可以 充当根容器，从而允许直接写入。

每个 LWS 存储 都有一个 存储 根，充当顶层组织单元。该 存储根 没有父级，并充当以下 存储 层次结构的入口点。

LWS 中的资源分为以下两类：

  • 容器 — 包含其他 资源的资源。
  • 数据资源 — 承载数据的资源 （例如文档、图像或结构化数据文件）。

7.2 包含关系

以下 包含关系，即资源与其父级 容器 之间的关系，通过 rel="up" 链接 关系表达。服务器 必须 包含一个 Link 首部，带有 rel="up" 并指向父容器，包含于对任何 非根资源的 GET 和 HEAD 请求的响应中。 

Link: </alice/notes/>; rel="up"

一个 容器 的成员列在其表示中，使用 items 属性。服务器管理此列表；客户端无法直接修改它。成员关系 的更改是资源创建和删除的副作用，而在允许以下 up 链接被修改的服务器上，该链接属于资源，将资源移动于以下 容器 之间也会产生此副作用，具体如 9.6 在容器之间移动资源 中所述。

7.3 包含关系完整性

服务器 必须 维护 包含关系 的完整性，在任何时候均如此：

  • 创建：当新资源创建于一个 容器 中时， 服务器 必须 以原子方式将该资源添加到该 容器 的 items 列表中。
  • 删除：当资源被删除时，服务器 必须 以原子方式将其从父级 容器 的 items 列表中移除。 删除一个 容器 要求该 容器 为 空，除非显式请求递归删除。
  • 移动：当资源的 up 链接更改时，服务器 必须 以原子方式将该资源从以下 items 列表中移除，即其 原父级 容器 的列表，并将其添加到 items 列表中，该列表属于 目标 容器。对更改 up 链接的支持是 可选 的，由此产生的要求定义于 9.6 移动资源于 容器之间。
  • 无孤立资源：每个非根资源 必须 能够从 以下 存储根 到达，通过 包含关系 层次结构。
  • 无环：一个 容器 不得 直接或 间接包含自身。

7.4 资源标识

资源由 URI 标识。资源的 URI 独立于其在以下 包含关系 层次结构中的位置。服务器在资源 创建期间分配 URI，并且 可以 采纳客户端提示，但客户端 不应当 假定 URI 结构反映包含关系。

包含关系 通过元数据表达 （rel="up" 链接和 items 属性，后者位于 容器 表示中），而非通过 URI 路径结构。这种分离使服务器能够灵活地进行 URI 分配，同时维护定义明确的组织模型。

7.5 容器成员关系 与授权

如果客户端对一个 容器 具有读取访问权限，则 容器 表示 必须 包含所有资源的标识符，这些资源包含 于该 容器 中且客户端有权访问。它 可以 同时包含以下资源的标识符，这些资源包含于该 容器 中但客户端无权访问。

客户端能够读取一个 容器 列表，并不意味着其有权访问所包含的 资源本身，反之亦然。

8. 容器

8.1 容器表示

一个 LWS 容器表示 描述一个 容器 及其内容。本节定义其必需和 可选属性，适用于以 application/lws+json 提供的情况。其他 RDF 媒体 类型的表示可通过 内容协商 请求。

8.1.1 容器属性

容器表示 必须 包含以下属性：

  • id: 以下 容器 的 URI。
  • type: 值 "Container"。
  • totalItems: 一个整数，表示资源总数， 这些资源包含于以下 容器 中，且可以向客户端披露。此 计数 应当 准确，但也 可以 是 近似值。
  • items: 所含资源描述的数组（见下文）。如果 该 容器 为空，则此值 必须 是 空数组。当 容器 列表被 分页时，items 仅包含当前页的资源；参见 分页 以了解详情。

8.1.2 所含资源 描述

items 数组中的每个条目描述一个包含于以下 容器 中的资源。所含资源描述 必须 包含：

  • id: 所含资源的 URI。
  • type: 资源的类型。必须 是 "DataResource" 或 "Container"，或者一个数组，至少包含 这两个字符串之一。服务器 可以 包含其他用户定义的类型，以 URI 表示（例如 ["DataResource", "http://example.org/customType"]）。

所含资源描述 应当 包含：

  • format: 资源的媒体类型（例如， "text/plain"、"image/jpeg"）。必须 存在， 对于 DataResources 而言。
  • size: 资源的大小，以字节为单位，用整数表示。
  • modified: 资源最后修改的日期和时间， 表示为 ISO 8601 日期时间字符串。

9. 操作

本节定义关联 Web 存储（LWS）服务器 必须 支持的四项核心操作。这些操作以 独立于传输的方式操纵资源和容器，侧重于语义而非实现细节。每项操作 都规定输入、预期行为和可能的响应。响应包括成功指示、资源 表示（适用时）和错误情况。实现 必须 以原子且一致的方式处理这些操作，这意味着每项操作要么完全成功，要么 失败且不会产生部分副作用。出现错误时，响应 应当 提供 足够的详细信息，使 代理 能够理解问题，同时不泄露敏感信息。

对于每项核心操作（创建、读取、更新、删除），我们描述要使用的 HTTP 方法、必需的 首部或其他特殊注意事项（包括内容协商、容器列表的分页， 以及条件请求），以及服务器应执行的操作和返回的内容。标准 HTTP 状态码用于 指示结果，并针对配额超限等场景提供附加映射， 如（507 Insufficient Storage）或前置条件失败（412 Precondition Failed）。此 绑定力求遵循 HTTP/1.1 和相关 RFC（例如 [RFC7231] 用于 HTTP 语义，[RFC7233] 用于范围 请求，[RFC5789] 用于 PATCH，[RFC8288] 用于 Web 链接， 以及 [RFC9264] 用于链接 集），以便自然地与 Web 标准集成。可发现性通过以下机制得到强调， 例如 Link 首部以及 401 响应中的 WWW-Authenticate 首部， 从而避免硬编码 URI 位置。各项操作均要求集成元数据，确保原子性，并 使用链接集处理服务器管理和用户管理的属性。

注：与本规范中的所有示例一样，本节给出的示例（HTTP 请求 和响应片段）均为 非规范性内容，旨在说明典型用法。实际 要求在描述性文字和表格中陈述。此外，虽然此绑定涵盖 HTTP（作为 初始目标协议），但原则上 LWS 操作将来可以绑定到其他协议。 以下 容器 表示的媒体类型要求定义于 12. LWS 媒体类型。

9.1 资源元数据

9.1.1 元数据

本节定义将元数据关联到以下 存储 资源 的模型。LWS 元数据系统基于 Web 链接的原则 [RFC8288]，它允许服务器描述关系， 即使用带类型的链接描述资源之间的关系。元数据增强可发现性，支持自描述 API，并与资源操作及 容器 层次结构相协调。

元数据模型 LWS 中的所有元数据均表示为一组源自某个资源的带类型链接（该资源为链接 上下文）。每个链接包括：

  • 链接目标：标识相关资源的 URI。
  • 关系类型：定义关系性质的字符串。
  • 可选的目标属性：附加键值对，进一步描述链接或 目标资源。

元数据区分资源及其表示，允许在适用时使用多种媒体类型。 对于 数据资源，元数据包括表示，每个表示 都有 format 和可选的 sizeInBytes。对于 容器 和 数据资源，我们将指向其父级 容器 资源的链接视为以下对象元数据的一部分，即 该资源。

该 链接集资源 对于 存储 中的每个资源，服务器 必须 提供元数据 链接，将其作为独立资源，遵循 [RFC9264]。

  • 发现：资源的链接集可通过带有以下关系的 Link 首部发现： rel="linkset"。
  • 媒体类型：一个 链接集资源 必须 以 application/linkset+json 提供。
  • 完整性：'linkset' 链接 必须 指向服务器管理的资源。 对链接集的更新 必须 与关联资源 操作保持原子性，以维护一致性。

发现元数据 客户端主要通过 GET 或 HEAD 请求的响应中的 Link 首部发现元数据。

  • 存储：服务器 必须 包含一个 Link 首部，带有 rel="https://www.w3.org/ns/lws#storage"，包含于相关响应中。
  • 包含关系：服务器 必须 包含一个带有 rel="up" 的 Link 首部，指向父级 容器，适用于任何非根资源。
  • 偏好：客户端 可以 使用 Prefer 首部 [RFC7240]，并带有 URI https://www.w3.org/ns/lws#PreferLinkRelations，以包含或省略特定的 关系。

元数据类型

类别 描述
系统管理 由服务器维护；只读。包括 linkset、type、 format、size、modified。
核心元数据 由客户端管理（受服务器限制）。包括 up、 items、title、creator。
用户定义 用户创建的自定义词汇和索引。

可修改性注意事项 核心元数据 可以 由客户端修改。为确保互操作性， 服务器 必须 使用标准 HTTP 首部声明其能力：

  1. 方法发现：服务器 必须 声明对 GET 和 PATCH 的支持， 这些操作针对 链接集资源，通过 Allow 首部声明。

  2. 补丁格式发现：服务器 必须 声明对 JSON Patch 的支持 [RFC6902]，通过 Accept-Patch 首部：Accept-Patch: application/json-patch+json。

  3. 可选方法：服务器 可以 支持 PUT 或其他补丁 格式；如果支持，这些 必须 分别包含于 Allow 和 Accept-Patch 首部中。

[!IMPORTANT] 客户端 不应当 假定支持 PUT 或特定补丁 格式，除非它们已在资源首部中声明，并且 必须 妥善处理 405 Method Not Allowed 或 415 Unsupported Media Type 响应。

管理元数据 元数据通过与资源关联的以下 链接集 资源 URI 交互来管理。服务器 必须 包含一个 ETag 首部，其 定义见 [RFC9110]，包含于 GET 和 HEAD 请求的响应中。

  • 部分更新（PATCH）：这是元数据管理的主要机制。服务器 必须 支持使用 application/json-patch+json 的 PATCH。

  • 替换（PUT）：如果已在 Allow 首部中声明，则客户端 可以 替换整个链接集。如果服务器不支持 PUT，它 必须 以 405 Method Not Allowed 拒绝请求。

  • 限制：服务器 可以 限制对特定链接的修改， （例如 up 或 items）以维护系统完整性。服务器 必须 保留客户端无权修改的链接，当 应用补丁时。允许客户端修改 up 链接的服务器，由此也 允许资源移动于以下 容器 之间；此类服务器 必须 在其以下 存储描述 中描述一项 MoveResource 能力，具体描述 见 6.1.3 存储能力，由此产生的要求定义于 9.6 移动资源 于容器之间。

  • 生命周期：元数据的生命周期与所描述的资源绑定；删除资源 必须 导致自动移除其关联的 链接集资源 元数据。

9.2 创建资源

创建资源 操作将一个新的 所提供的资源 添加到现有的 容器。此 操作既处理以下 数据资源 的创建，也处理子容器的创建。

输入：

  • 目标容器：以下 容器 的标识符，其中 将创建新资源。
  • 标识提示：对新资源标识符的可选建议。服务器 可以使用此提示，但并非必须使用。
  • 内容：新资源的初始内容和类型。

行为：

  • 标识生成：服务器确定新 资源的最终标识符（URI）。如果提供了标识提示，服务器会尝试采纳它，同时确保 唯一性和有效性，范围限定于以下 容器 内。如果未提供提示，则 服务器生成唯一标识符。
  • 容器成员关系更新：服务器以原子方式将新资源添加到 目标 容器 的成员列表中。
  • 元数据初始化：服务器为新 资源初始化系统元数据。如果资源具有关联的 元数据资源，它也会 被初始化。

可能的响应：

  • 已创建：操作成功。服务器返回最终 标识符，标识新创建的资源。
  • 未找到目标：指定的目标 容器 不 存在。
  • 不允许：客户端的身份已知，但其无权 在此 容器 中创建资源。
  • 未知请求方：服务器无法识别客户端的身份，并要求 身份验证。
  • 冲突：具有所生成标识符的资源已经存在，或者存在 其他状态冲突。
  • 未知错误：发生了意外的内部错误。

新资源通过向目标 容器 URI 发送 POST 来创建，服务器分配 最终标识符。客户端 可以 为新 资源提供初始的用户管理元数据，方法是在 POST 请求中包含一个或多个 Link 首部，遵循以下规范的 Web 链接语法 [RFC8288]。服务器管理的元数据 必须 在创建时由服务器自动生成，并且 不得 被 客户端提供的链接覆盖。

成功时，服务器 必须 返回 201 状态码，并将新 URI 放在 Location 首部中。服务器 必须 包含 Link 首部， 用于关键的服务器管理元数据，包括指向父级 容器 的链接 （rel="up"），以及指向已创建资源的专用 链接集资源 的链接 （rel="linkset"; type="application/linkset+json"）。其他链接 应当 包含 rel="type"（指示 https://www.w3.org/ns/lws#Container 或 https://www.w3.org/ns/lws#DataResource）。消息体 可以 为空，或 包含资源的最小表示。所有元数据的创建和链接 必须 与资源创建保持原子性，以维护一致性。

POST（发送到容器 URI） – 使用服务器分配的名称创建： 使用 POST 在现有 容器 内添加新资源。服务器分配标识符， 用于该资源。客户端按以下方式指示要创建的资源类型：

  • 要创建一个 容器，客户端 必须 包含一个带有 rel="type" 的 Link 首部， 指向 Container 类型： Link: <https://www.w3.org/ns/lws#Container>; rel="type"。
  • 要创建一个 数据资源，客户端将 资源内容包含于请求消息体中，并带有适当的 Content-Type 首部。

示例（使用 POST 创建新的数据资源）：

POST /alice/notes/ HTTP/1.1
Host: example.com
Authorization: Bearer <token>
Content-Type: text/plain
Content-Length: 47

milk
eggs
bread
butter
apples
orange juice

在此示例中，客户端正在向以下 容器 发送 POST：/alice/notes/。它 提供 text/plain 内容（购物清单）。如果 /alice/notes/ 存在，并且 客户端已获授权，服务器将创建一个新的 数据资源，并将其添加到 容器 的成员中。

示例（POST 的响应 — 数据资源）：

HTTP/1.1 201 Created
Location: /alice/notes/shoppinglist.txt
Content-Type: text/plain; charset=UTF-8
Link: </alice/notes/shoppinglist.txt.meta>; rel="linkset"; type="application/linkset+json"
Link: </alice/notes/>; rel="up"
Link: <https://www.w3.org/ns/lws#DataResource>; rel="type"
Content-Length: 0

示例（向不存在的容器发送 POST）：

POST /alice/notes/ HTTP/1.1
Host: example.com
Authorization: Bearer <token>
Content-Type: text/plain
Content-Length: 4

test

如果 /alice/notes/ 不存在，服务器报告 未找到目标 结果：

HTTP/1.1 404 Not Found

注： 创建资源操作向单个现有的 容器添加资源。由于 包含关系 通过元数据而非 URI 路径结构表示（参见 7. 逻辑资源组织），本规范未定义在一次操作中创建多层 容器 ；客户端通过各自的创建资源操作创建每个 容器 。

创建 容器：要创建一个新的 容器，客户端向现有的父级 容器 发送 POST，并带有一个 Link 首部，指示 Container 类型。例如：

POST /alice/ HTTP/1.1
Host: example.com
Authorization: Bearer <token>
Content-Length: 0
Link: <https://www.w3.org/ns/lws#Container>; rel="type"

示例（POST 的响应 — 容器）：

HTTP/1.1 201 Created
Location: /alice/notes/
Link: </alice/notes/.meta>; rel="linkset"; type="application/linkset+json"
Link: </alice/>; rel="up"
Link: <https://www.w3.org/ns/lws#Container>; rel="type"
Content-Length: 0

这会创建一个新的 容器，位于 /alice/notes/，并由服务器生成 元数据，其中包括值为 https://www.w3.org/ns/lws#Container 的 rel="type"。

关于创建的附加说明（HTTP 绑定）：

  • POST 不是幂等的。重复执行可能创建重复项；客户端 应当 避免无意的重试，或使用唯一标识符/检查来防止这种情况。
  • 元数据更新具有原子性；服务器 必须 确保以下 链接集资源 已创建，并填充了强制要求的 服务器管理字段，然后才返回成功。
  • 为提高可发现性，服务器 应当 包含一个 Link 首部，带有 rel="https://www.w3.org/ns/lws#storage"，包含于 401 响应中，以引导客户端而无需 硬编码 URI。

管理和检索元数据（与创建相关）： 虽然元数据主要通过读取操作检索，但它在创建期间生成。客户端可以 在创建后立即对新资源 URI 使用 GET 或 HEAD 来检索它。客户端可以使用 Prefer 首部，请求包含特定的元数据链接（通过关系类型）和 属性。

9.3 读取资源

检索现有资源的表示或以下 容器 的列表。

  • 输入：目标标识符和可选参数。
  • 行为：
    • 对于非容器资源，服务器返回资源内容。
    • 对于 容器，服务器返回成员 资源的列表，该列表 可以 根据以下内容进行过滤：授权。列表必须包含 每个成员的核心元数据。
  • 结果：所请求的表示或失败通知。

读取资源操作通过 HTTP GET 请求来请求资源表示（HEAD 用于 仅请求首部的情况）。行为有所不同，取决于目标 URL 是一个 容器，还是非容器资源（数据资源）。服务器 必须 通过元数据区分资源类型。所有响应 必须 集成 第 8.1 节定义的元数据，包括用于关键关系的 Link 首部，例如 rel="linkset"、rel="up" 和 rel="type"。服务器 必须 确保读取期间资源状态及其元数据之间的原子性。

GET（非容器资源） – 检索资源的内容： 向资源 URI 发送 GET 以获取完整内容（如果已获授权）。以 200 OK 响应，消息体包含 数据，Content-Type 与存储的媒体类型匹配。服务器 必须 支持 范围请求，遵循 [RFC7233]，以进行部分 检索。响应 必须 包含一个 ETag 首部，其定义见 [RFC9110]。

示例（使用 GET 获取文件）：

GET /alice/notes/shoppinglist.txt HTTP/1.1
Authorization: Bearer <token>
Accept: text/plain

这会请求 /alice/notes/shoppinglist.txt 的内容，表示客户端希望 以文本形式获取它。假设资源存在、是文本，并且客户端有权访问：

HTTP/1.1 200 OK
Content-Type: text/plain; charset=UTF-8
Content-Length: 34
ETag: "abc123456"
Link: </alice/notes/shoppinglist.txt.meta>; rel="linkset"; type="application/linkset+json"
Link: </alice/notes/>; rel="up"
Link: <https://www.w3.org/ns/lws#DataResource>; rel="type"

milk
cheese
bread
guacamole
soda
chocolate bars
hash
eggs

服务器返回了文本内容（共 34 字节，如 Content-Length 所示）。 内容与文件中存储的数据完全一致。ETag: "abc123456" 是一个验证器， 用于缓存和条件请求。响应包含 Link 首部，用于 元数据的可发现性，其中带有 up 和 type 等必需字段。

GET（容器 资源） – 列出一个 容器 的内容： 当目标 URI 对应一个 容器（通过元数据类型确定）时，GET 请求返回一个 列表，其中列出该 容器 的成员。带有 Content-Type: application/lws+json 的响应是一个 容器 表示，其定义见 容器 表示 一节；对于此表示，列表包括每个成员的元数据： 资源标识符（必须）、类型（必须）、媒体类型 （对于 DataResources 为 必须）、大小（应当），以及 修改时间戳（应当）。

示例（使用 GET 获取容器）：假设以下 容器 存在且客户端有权访问。 选项卡展示使用不同媒体类型的同一请求；参见 12.1.2 内容协商。

请求：

GET /alice/notes/ HTTP/1.1
Authorization: Bearer <token>
Accept: application/lws+json

响应首部：

HTTP/1.1 200 OK
Content-Type: application/lws+json
ETag: "container-etag-789"
Link: </alice/notes/.meta>; rel="linkset"; type="application/linkset+json"
Link: </alice/>; rel="up"
Link: <https://www.w3.org/ns/lws#Container>; rel="type"

响应消息体：

{
  "@context": "https://www.w3.org/ns/lws/v1",
  "id": "/alice/notes/",
  "type": "Container",
  "totalItems": 2,
  "items": [
    {
      "type": "DataResource",
      "id": "/alice/notes/shoppinglist.txt",
      "format": "text/plain",
      "size": 47,
      "modified": "2025-11-24T12:00:00Z"
    },
    {
      "type": ["DataResource", "http://example.org/customType"],
      "id": "/alice/notes/todo.json",
      "format": "application/json",
      "size": 2048,
      "modified": "2025-11-24T13:00:00Z"
    }
  ]
}

请求：

GET /alice/notes/ HTTP/1.1
Authorization: Bearer <token>
Accept: text/turtle; profile="https://www.w3.org/ns/lws/v1"

响应首部：

HTTP/1.1 200 OK
Content-Type: text/turtle; profile="https://www.w3.org/ns/lws/v1"
ETag: "container-etag-789"
Link: </alice/notes/.meta>; rel="linkset"; type="application/linkset+json"
Link: </alice/>; rel="up"
Link: <https://www.w3.org/ns/lws#Container>; rel="type"

响应消息体：

@prefix lws: <https://www.w3.org/ns/lws#> .
@prefix dcterms: <http://purl.org/dc/terms/> .
@prefix schema: <http://schema.org/> .
@prefix xsd: <http://www.w3.org/2001/XMLSchema#> .

<> a lws:Container ;
  lws:totalItems 2 ;
  lws:items <shoppinglist.txt>, <todo.json> .

<shoppinglist.txt> a lws:DataResource ;
  dcterms:format "text/plain" ;
  schema:size "47"^^xsd:long ;
  dcterms:modified "2025-11-24T12:00:00Z"^^xsd:dateTime .

<todo.json> a lws:DataResource, <http://example.org/customType> ;
  dcterms:format "application/json" ;
  schema:size "2048"^^xsd:long ;
  dcterms:modified "2025-11-24T13:00:00Z"^^xsd:dateTime .

在此示例中，/alice/notes/ 是一个 容器。响应使用 JSON-LD，并带有 LWS 上下文，列出成员及其必需的元数据。每个项都包含其 type、 id、format、size 和 modified 时间戳，作为扁平的 属性。

在所有情况下，服务器 必须 将以下元数据包含于响应 首部中：一个 ETag 首部，其定义见 [RFC9110]，以及 Link 首部， 带有 rel="linkset"、rel="up" 和 rel="type"，表明它是一个 容器。

HEAD（任何资源或 容器） – 仅首部/元数据： LWS 服务器 必须 支持 HEAD [RFC9110]，适用于 容器 和非容器，返回与 GET 相同的首部， （包括 Content-Type、用于元数据的 Link），但不带消息体。这使得 无需传输内容即可检索元数据。

缓存和条件请求：LWS 利用 HTTP 缓存语义。服务器 应当 支持条件请求，其定义见 [RFC9110]， 包括实体标签（ETags）和基于日期的验证器等机制（例如 If-Modified-Since 首部）。如果资源或 容器 列表 未更改，则以 304 Not Modified 响应，以避免冗余传输。

可发现性和授权：为增强可发现性， 401 Unauthorized 响应包含一个 WWW-Authenticate 首部，带有 resource_metadata 参数，具体如 授权服务器发现 中所述，以便客户端能够 定位授权服务器而无需硬编码 URI。

9.4 更新资源

通过完全替换或部分补丁修改现有[所提供的资源]的状态。

  • 输入：目标标识符、新内容和可选的并发约束。
  • 行为：服务器以原子方式应用更改。如果并发约束已被 提供，则当资源自上次被以下对象读取后已被修改时拒绝更新，即 请求方。
  • 结果：更新确认或冲突通知。

更新资源 修改 现有 所提供的 资源 的内容，所用方式为 PUT 请求（替换整个资源）或 PATCH 请求（应用 部分修改）。客户端必须对资源 URL 具有写入访问权限，才能执行这些 操作。 注：本节描述更新资源的主要内容。要更新其元数据，请参见第 9.3.2 节。 LWS 服务器 必须 将针对资源 URI 的 PUT 和 PATCH 请求处理为 仅修改资源内容，默认不影响关联的 链接集资源。要选择在单次原子操作中同时更新内容和 元数据，客户端 可以 包含 Link 首部，包含于针对资源 URI 的 PUT/PATCH 请求中，并指定偏好 'Prefer: set-linkset'（其定义见 [RFC7240]）。在这种情况下， 服务器 必须 将提供的 Link 首部解释为对链接集的替换 （对于 PUT）或部分更新（对于 PATCH），同时应用内容更改。 此行为对于服务器是 可选 的，但如果支持，则 必须 通过 Prefer 首部显式调用，以防止 无意的元数据覆盖。不支持组合更新的服务器 必须 忽略该偏好或以 501 Not Implemented 响应。

PUT（替换完整资源） – 向资源 URI 发送 PUT，将新的完整内容放在 消息体中，并带有匹配的 Content-Type（通常与现有类型一致）。PUT 是幂等的， 对于现有资源而言。客户端 应当 使用条件请求，其定义见 [RFC9110]，以避免覆盖并发更改。

示例（使用 PUT 更新资源）：

PUT /alice/personalinfo.json HTTP/1.1
Authorization: Bearer <token>
Content-Type: application/json
If-Match: "abc123456"
{
"name": "Alice",
"age": 30,
"city": "New London",
"state": "Connecticut"
}

在此示例中，客户端正在更新一个现有 JSON 资源，位于 /alice/personalinfo.json。它包含一个 If-Match 首部，带有一个实体标签， （ETag），该标签来自先前的 GET 或 HEAD 请求。服务器将其 与当前实体标签（ETag）进行比较；如果匹配，则继续替换内容，使用 所提供的 JSON。如果不匹配，服务器拒绝更新（因为资源已被更改， 在此期间由其他人更改）。 成功响应：如果更新成功，服务器可以以 200 OK 响应，并 可能包含更新后的表示或某种确认（例如新内容或其中一部分）。 或者，服务器可以以 204 No Content 响应，表示成功且没有消息体， （在无需传达其他信息时尤其常见）。例如： 

HTTP/1.1 204 No Content
  • 错误响应：如果 If-Match 前置条件不匹配， （发生并发修改），服务器以 412 Precondition Failed 响应。如果 资源不存在，旨在更新的 PUT 将产生 404 Not Found。如果 客户端未获授权，则为 403 Forbidden（或 401 Unauthorized，如果没有有效的 凭据被提供）。如果请求载荷无效，则为 400 Bad Request。

PATCH（部分更新） – HTTP PATCH 方法 [RFC5789] 允许客户端指定对资源的部分修改，而无需发送全部的新 内容。这对于大型资源很有用，因为发送全部内容效率低下，如果 只有一小部分发生更改；也适用于希望应用特定更改的并发编辑场景。LWS 服务器 必须 至少支持 JSON Patch， （application/json-patch+json），其定义见 [RFC6902]。

更新资源元数据（对链接集使用 HTTP PUT / PATCH） 资源的元数据通过修改其对应的 链接集资源 来更新， 该资源通过带有 rel="linkset" 的 Link 首部发现。 完全替换（PUT）：向以下 链接集资源 URI 发送 PUT 请求，并将完整的 链接集文档放在消息体中，会替换该资源的所有元数据。 部分更新（PATCH）：向以下 链接集资源 URI 发送 PATCH 请求，会添加、移除或 修改特定链接。

元数据的条件请求 由于资源的元数据可能被多个参与者修改，因此防止并发覆盖是 重要的。服务器和客户端 应当 使用条件请求，其定义见 [RFC9110]，用于对以下 链接集资源 执行 PUT 和 PATCH 操作。当服务器收到一个条件 请求且其前置条件失败时，它 必须 拒绝请求，返回一个 412 Precondition Failed 状态码。 示例（使用 PUT 替换链接集）： 客户端先获取链接集。 

GET /alice/personalinfo.json.meta HTTP/1.1
Authorization: Bearer <token>
Accept: application/linkset+json
HTTP/1.1 200 OK
Content-Type: application/linkset+json
{
  "linkset": [
    {
      "anchor": "/alice/personalinfo.json",
      "describedby": [ { "href": "/schemas/personal-info.json" } ]
    }
  ]
}

客户端现在希望添加一个许可协议。它构造一个新的完整链接集文档，并发送一个 PUT 请求。

PUT /alice/personalinfo.json.meta HTTP/1.1
Authorization: Bearer <token>
Content-Type: application/linkset+json
{
  "linkset": [
    {
      "anchor": "/alice/personalinfo.json",
      "describedby": [ { "href": "/schemas/personal-info.json" } ],
      "license": [ { "href": "https://creativecommons.org/licenses/by/4.0/" } ]
    }
  ]
}

如果成功，服务器以成功响应。

HTTP/1.1 204 No Content

更新规则汇总 如果只想更改资源的内容 → 对资源本身执行 PUT/PATCH。 如果只想更改资源的链接（元数据）→ 对资源关联的以下 链接集资源 执行 PUT/PATCH。 如果希望同时更改内容和链接 → 对资源本身执行 PUT/PATCH，并包含适当的 Link 首部以及 'Prefer: set-linkset'。同时设置二者的行为默认关闭。

9.5 删除资源

永久移除资源及其关联的元数据。

  • 输入：目标标识符、可选的递归标志（用于 容器），以及可选的并发约束。
  • 行为：
    • 对于非容器资源，服务器移除内容、元数据，并更新 父级 容器 的成员关系。
    • 对于 容器，服务器通常要求该 容器 为空，除非递归删除已被 显式请求且受到支持。
  • 结果：移除确认或失败通知。

删除资源操作使用 HTTP DELETE 方法实现，如上述抽象 操作所定义。本节规定输入、行为和响应的 HTTP 绑定。

DELETE 请求以资源或以下 容器 的 URI 为目标，以将其移除。客户端 可以 包含一个带有 ETag 的 If-Match 首部，以进行并发 检查。

删除与 包含关系： 删除资源时，服务器 必须 以原子方式将其从以下对象中移除： 父级 容器 的 items 列表。父容器的 totalItems 计数 应当 相应更新。

对于非容器资源，服务器移除资源内容、关联的元数据（链接集资源），以及 包含关系 引用， 该引用位于父级 容器 中。

对于 容器 资源，服务器默认采用非递归 删除。如果 容器 非空且未请求递归，服务器 必须 以 409 Conflict 拒绝请求。服务器 可以 支持递归删除以下 容器 内所有包含的资源，该容器正被 删除。客户端 必须 使用 Depth: infinity 首部来请求 递归删除，其定义见 [RFC4918]。

成功时，服务器 必须 以 204 No Content 响应。服务器 应当 支持条件请求，其定义见 [RFC9110]。

如果客户端缺乏授权，服务器 必须 返回 403 Forbidden（如果 客户端的身份已知但权限不足）或 401 Unauthorized（如果没有有效的 身份验证被提供）。在披露资源存在会带来安全风险的情况下， 服务器 可以 改为返回 404 Not Found。

示例（使用 DELETE 删除非容器资源）：

DELETE /alice/notes/shoppinglist.txt HTTP/1.1
Authorization: Bearer <token>
If-Match: "abc123456"

假设 ETag 匹配且客户端已获授权，服务器删除资源及其元数据， 并以原子方式将其从父容器 /alice/notes/ 中移除：

HTTP/1.1 204 No Content

示例（使用 DELETE 非递归地删除非空容器）：

DELETE /alice/notes/ HTTP/1.1
Authorization: Bearer <token>

假设 /alice/notes/ 包含资源，服务器拒绝删除：

HTTP/1.1 409 Conflict
Content-Type: text/plain

无法删除 容器 /alice/notes/ - 容器 非空。

示例（使用 DELETE 递归删除容器，如果支持）：

DELETE /alice/notes/ HTTP/1.1
Authorization: Bearer <token>
Depth: infinity

假设服务器支持递归且客户端对所有内容都具有权限，服务器 以原子方式删除容器及其后代：

HTTP/1.1 204 No Content

9.6 移动资源于 容器之间

本规范未定义专门的 HTTP 方法，用于将一个 所提供的资源 从 一个 容器 移动到另一个，这与 MOVE 方法不同， 该方法由 WebDAV 定义 [RFC4918]。 移动改为表示为对资源的以下 包含关系 元数据的更新： 客户端更改资源的以下 链接集资源 中的 up 链接， 使其指向目标 容器，所用的是 更新 资源 操作。服务器从该更改推导出实际的移动。

注
移动不能简化为先执行一个 创建资源 操作，然后执行一个 删除资源 操作。服务器分配资源标识符，因此一个 客户端如果在另一个 容器 中重新创建内容，不一定能够保留 原始资源的标识符，且指向该标识符的每个链接都可能失效， 由此产生后果。这两个请求也不具有原子性：观察者可能在两个 容器 中都看到资源，或者两个都看不到。将移动表示为对以下 包含关系 元数据的更改可避免这两个问题，因为 资源的标识及其内容不会被该更改触及。

服务器支持： up 链接由服务器管理，且不要求服务器允许客户端 修改它，具体如 9.1 资源 元数据 中所述。允许客户端修改资源的 up 链接，并 由此允许资源移动于以下 容器 之间的服务器，必须 描述一项 MoveResource 能力，包含于其以下 存储 描述 中，具体如 6.1.3 存储能力 中所述，并且 必须 实现 本节的要求。不允许此行为的服务器 必须 拒绝 请求，使用适当的 4xx 状态码，例如 409 Conflict，并且 必须 不 描述 MoveResource 能力。

请求移动： 客户端通过对资源的以下 链接集资源 应用部分更新来移动资源， 将 up 链接的目标替换为目标 容器 的标识符。如 9.1 资源元数据 所要求，服务器 必须 支持 application/json-patch+json [RFC6902]，用于此更新。与任何 对以下 链接集资源 的修改一样，客户端 应当 通过包含一个 If-Match 首部字段将请求设为条件请求，该字段携带当前的 ETag，属于以下 链接集资源，具体如 9.4 更新资源 中所述；服务器 可以 要求条件请求，并以 428 Precondition Required 拒绝无条件请求。

目标 必须 是一个现有的 容器。服务器 必须 拒绝以下补丁，它会将 up 链接的目标设置为 现有 容器 之外的任何对象，并使用适当的 4xx 状态码，例如 409 Conflict。服务器同样 必须 拒绝会导致资源 没有 up 链接的补丁，因为每个非根资源都能从以下 存储根 到达。

本规范未将目标限制为以下 存储，即持有被移动资源的存储。 但是，不要求服务器支持将资源移动到一个 容器，该容器位于另一个 存储 中， 并且 可以 以适当的 4xx 状态码拒绝此类补丁，例如 409 Conflict。接受此类补丁的服务器仍须遵守本节中的其他要求， 包括以原子方式应用更改的要求。

注
JSON Patch 使用 JSON 指针标识要更改的值 [RFC6901]，其中成员 在数组中通过其位置寻址。因此，替换 up 链接目标的补丁依赖于资源的链接上下文在 linkset 数组中的位置，以及目标对象在 up 数组中的位置。客户端获知这些 位置，方法是读取 链接集资源，条件请求则确保 应用补丁时这些位置仍然有效。客户端还可以使用以下方式保护更改： test 操作，例如针对链接上下文的 anchor，或针对 up 链接的当前目标。与完全替换以下 链接集资源 不同，此类补丁使所有其他链接 保持不变，因此客户端不必重新陈述其未更改的链接。

对 包含关系 的影响： 更新成功时，服务器 必须 以原子方式将资源从以下 items 列表中移除，该列表属于其原父级 容器，并将其添加到以下 items 列表中，该列表属于目标 容器。totalItems 计数， 属于这两个 容器 的，应当 相应 更新，且这两个 容器 的 ETag 必须 更新，以反映 该更改。

被移动资源的内容及其用户定义的元数据不受移动影响。服务器 必须 保留以下 链接集资源 中的链接， 即客户端无权修改的链接，包括服务器管理的链接，例如 linkset 和 type。辅助资源，其生命周期绑定到被移动 资源的，在移动后仍与其绑定。

服务器 必须 拒绝会违反以下 包含关系 完整性 要求的更新，要求见 7. 逻辑资源组织，并使用适当的 4xx 状态码，例如 409 Conflict。 特别是，一个 容器 不得 被移动到其自身 或其自身的某个后代中，因为这会在以下 包含关系 层次结构中引入环。

被移动资源的标识： 资源的 URI 独立于其在以下 包含关系 层次结构中的位置， 具体如 7. 逻辑资源组织 中所述。因此，服务器 应当 保留 被移动资源的标识符，使指向它的现有链接保持有效，并且 应当 声明其是否这样做，使用 preservesIdentifier 属性，该属性属于 MoveResource 能力。如果该属性不存在，客户端 不得 假定标识符会被保留。

不保留被移动资源标识符的服务器 必须 响应， 使用 200 OK 并提供更新后的 链接集资源 的表示，其 anchor 是资源的新标识符，并且 必须 包含一个 Content-Location 首部字段，携带以下 链接集资源 本身的新标识符。此类服务器 应当 响应针对旧标识符的后续请求，这些标识符属于 资源及其 辅助资源，响应为 301 Moved Permanently，并包含 一个指向新标识符的 Location 首部字段。

移动 容器： 服务器 可以 支持更改以下 容器 的 up 链接，并且 必须 表明其 这样做，方法是在 appliesTo 属性中包含 Container，该属性属于 MoveResource 能力。当一个 容器 被移动时，其后代也随之移动， 且其标识符须遵守与被移动的以下 容器 的标识符相同的要求。支持移动 数据资源，但不支持移动 容器 的服务器 必须 以适当的 4xx 状态码拒绝此类请求，例如 409 Conflict，并且 不得 包含 Container，于 appliesTo 属性中。

授权： 服务器 不得 应用对 up 链接的更改，除非 发出请求的 代理 同时获准执行以下 删除资源 操作，针对被移动的资源，以及执行 创建资源 操作，在目标 容器 中。

当一个 容器 被移动时，该 容器 是唯一一个 父级发生更改的资源：其后代保留彼此之间的相对位置，并且，在 服务器保留标识符的情况下，也保留其标识符。因此，以下 代理 不 必须获得在目标中重新创建每个后代的授权。然而，适用于 这些后代的策略仍可能更改，因为访问经常根据以下位置来管理， 即 包含关系 层次结构中的位置。因此，授权， 即移动以下 容器 所需的授权，是删除该容器所需的授权， 以递归方式删除，具体如 9.5 删除资源 中所述，同时还须具备在目标 容器 中创建的授权。服务器 必须 评估此 授权，针对整个子树，在应用更改之前进行，并且 不得 仅部分应用更改。

注
对资源的访问经常由策略管理，这些策略根据以下内容表达： 资源在 包含关系 层次结构中的位置。因此，移动资源可能 更改谁能够访问它，向任一方向更改，而无需编辑任何策略。一个 实现如何使此后果对以下 存储 控制者 和 代理 可见，不在本规范的范围内。参见 16.6 移动资源 于容器之间 和 17.3 在容器之间移动资源。

示例（将数据资源移动到另一个容器）： 在此示例中，以下 存储 分配不透明的标识符，它们不反映 包含关系。 被移动的资源由 https://storage.example/f8c3de3d 标识，其 链接集资源 由 https://storage.example/9b1e07a4 标识，源和目标 容器 由 https://storage.example/1d4f8a02 和 https://storage.example/c2a71f60 分别标识。客户端已经 读取了 链接集资源，其中 up 链接是 第一个链接上下文的第一个目标对象。 

PATCH /9b1e07a4 HTTP/1.1
Host: storage.example
Authorization: Bearer <token>
Content-Type: application/json-patch+json
If-Match: "meta-v3"

[
  { "op": "replace", "path": "/linkset/0/up/0/href", "value": "https://storage.example/c2a71f60" }
]

假设客户端已获授权且目标 容器 存在，服务器移除该 资源，从 https://storage.example/1d4f8a02 的 items 列表中移除，并将其添加到 https://storage.example/c2a71f60 的 items 列表中，同时更新以下 链接集资源，以原子方式进行： 

HTTP/1.1 204 No Content
ETag: "meta-v4"
Link: <https://storage.example/c2a71f60>; rel="up"

资源仍可通过 https://storage.example/f8c3de3d 访问，且现在是以下对象的成员： https://storage.example/c2a71f60。由于资源的标识符从未编码其 位置，于 层次结构中的位置，因此只能在以下 包含关系 元数据中观察到移动。

示例（服务器分配新标识符的移动）：

PATCH /alice/notes/shoppinglist.txt.meta HTTP/1.1
Host: example.com
Authorization: Bearer <token>
Content-Type: application/json-patch+json
If-Match: "meta-v3"

[
  { "op": "replace", "path": "/linkset/0/up/0/href", "value": "/alice/archive/" }
]

一个服务器，从以下 包含关系 层次结构推导标识符，并因此 声明 "preservesIdentifier": false，则无法保留标识符。它报告 所产生的标识符，包含于更新后的 链接集资源 中：

HTTP/1.1 200 OK
Content-Type: application/linkset+json
Content-Location: /alice/archive/shoppinglist.txt.meta
ETag: "meta-v4"

{
  "linkset": [{
    "anchor": "/alice/archive/shoppinglist.txt",
    "up": [{ "href": "/alice/archive/" }],
    "linkset": [{ "href": "/alice/archive/shoppinglist.txt.meta",
                  "type": "application/linkset+json" }]
  }]
}

示例（将容器移动到其自身的某个后代中）：

PATCH /alice/notes/.meta HTTP/1.1
Host: example.com
Authorization: Bearer <token>
Content-Type: application/json-patch+json
If-Match: "meta-v7"

[
  { "op": "replace", "path": "/linkset/0/up/0/href", "value": "/alice/notes/2026/" }
]

服务器拒绝更新，因为这会在以下 包含关系 层次结构中引入环： 

HTTP/1.1 409 Conflict
Content-Type: application/problem+json

{
  "title": "无法将容器移动到其自身的某个后代中",
  "status": 409,
  "detail": "/alice/notes/2026/ 是 /alice/notes/ 的后代"
}

通知： 声明支持移动资源且会发出通知的服务器 应当 使用单个 Move 活动描述成功的移动，具体 描述见 10.2.3 活动 类型，而非使用单独的 Delete 和 Create 活动。

9.7 HTTP 状态 映射汇总

此表将通用的 LWS 响应（来自 第 8 节）映射到 HTTP 状态码和载荷，以保持一致性，并纳入以下特定场景，例如 分页、条件请求、配额约束和元数据集成：

LWS 响应 HTTP 状态码 HTTP 载荷
成功（读取或更新，并返回 数据） 200 OK 资源 表示，包含于响应消息体中（对于 GET，或 PUT/PATCH 返回内容时），并带有 相关首部（Content-Type、用于元数据的 Link，例如 rel="linkset" 或 rel="up"）。对于容器列表，包含 JSON-LD，带有规范性上下文和成员元数据（标识符、类型、大小、时间戳等）。
已创建（新资源） 201 Created 通常没有响应消息体（或为新资源的最小表示）。 Location 首部设置为新资源的 URI。Link 首部用于 服务器管理的元数据。
已删除（没有要返回的内容） 204 No Content 没有响应消息体。表示资源已被删除，或请求已成功且没有 其他需要说明的内容。服务器 可以 使用 410 Gone，用于 永久删除。
错误请求（输入或约束无效） 400 Bad Request 错误详情，说明发生了什么问题。服务器 应当 使用 以下规范定义的标准格式 [RFC9457]，用于 结构化错误响应，例如一个 JSON 对象，具有以下字段："type"、 "title"、"status"、"detail" 和 "instance"。
未知请求者 401 Unauthorized 可选的错误详情，例如采用 [RFC9457] 中定义的格式。 WWW-Authenticate 标头指示客户端如何进行身份验证。
不被允许 403 Forbidden 可选的错误详情，例如采用 [RFC9457] 中定义的格式。
未找到目标 404 Not Found 可选的错误详情，例如采用 [RFC9457] 中定义的格式。

不希望向无权访问某资源的客户端透露该资源是否存在的服务器，可以使用 404 Not Found 响应，而不是 403 Forbidden，如 [RFC9110] 所述。

10. 通知

本节定义一种机制，使客户端能够及时接收有关更改的更新， 这些更改涉及关联 Web 存储服务器管理的资源。本规范定义通用的 通知数据模型和订阅机制；具体的投递渠道 在单独的通知套件规范中描述。

10.1 通知发现

存储 可以 支持通知。支持通知的存储 必须 声明一个服务对象，位于其 service 数组中，该数组属于其 存储描述 资源，且服务对象的 type 等于 NotificationService。

服务对象 必须 包含一个 serviceEndpoint 属性，其 值 是订阅端点的 URI。服务对象 必须 包含一个 subscriptionType 属性，其值是字符串数组，每个字符串 标识一个受支持的 订阅 类型。

服务对象上 可以 存在其他属性。

示例 12: 包含通知 服务的存储描述 
{
  "@context": ["https://www.w3.org/ns/lws/v1"],
  "id": "https://storage.example/",
  "type": "Storage",
  "service": [{
    "type": "NotificationService",
    "serviceEndpoint": "https://notification.example/subscriptions",
    "subscriptionType": [
      "WebhookSubscription"
    ]
  }]
}
注

不要求服务器支持所有订阅类型。 subscriptionType 数组精确声明可用的类型。

10.2 通知数据模型

一个 通知 表示为一个 JSON-LD 文档，具有 Notification 类型。信封携带有关投递 上下文的元数据，并封装一个活动流 2.0 [ACTIVITYSTREAMS-CORE] [ACTIVITYSTREAMS-VOCABULARY] 活动，用于描述事件。

10.2.1 信封属性

通知信封具有以下属性：

  • type — 必需。其值 必须 是字符串 Notification。
  • storage — 必需。标识 LWS 存储的 URI， 该通知与此存储关联。
  • activity — 必需。一个 JSON 对象或一个 JSON 对象数组， 其中每个对象都符合活动流 2.0 数据模型，描述一个或 多个已发生的事件。参见 10.2.2 活动属性。
示例 13: 通知信封 
{
  "@context": [
    "https://www.w3.org/ns/lws/v1",
    "https://www.w3.org/ns/activitystreams"
  ],
  "type": "Notification",
  "storage": "https://storage.example/",
  "activity": {
    "id": "ec4dcc48-6581-4232-81c9-584525a98693",
    "type": ["Delete"],
    "object": {
      "id": "https://storage.example/alice/notes/shopping.txt",
      "type": ["DataResource"]
    },
    "origin": "https://storage.example/alice/notes/",
    "published": "2026-03-26T10:30:00Z"
  }
}

10.2.2 活动属性

activity 属性中的每个活动对象 必须 符合 该 活动流 2.0 数据模型，并且 必须 包含以下属性：

  • id — 必需。唯一标识该活动的字符串。
  • type — 必需。字符串数组，至少包含 一个 活动流 2.0 活动类型。
  • object — 必需。标识资源的 JSON 对象， 该资源是通知所涉及的对象。object 必须 包含 下述 属性：
    • id — 必需。资源的 URI。
    • type — 必需。字符串数组，包含至 少 一种资源类型。本规范定义的值包括 Container 和 DataResource。其他类型值 可以 被包含。
  • published — 必需。符合以下规范的日期时间值： [RFC3339]，指示何时 发生了该活动。

以下属性是 可选 的：

  • actor — 标识执行该动作的代理的 URI。
  • target — 标识容器的 URI，该 资源被添加到此容器中。用于 Create 和 Move 活动。
  • origin — 标识容器的 URI，该 资源从此容器中被移除。用于 Delete 和 Move 活动。

10.2.3 活动类型

服务器 必须 支持以下活动流 2.0 活动类型，以 指示 存储资源 的更改：

  • Create — 在容器中创建了一个新资源。 target 字段指示资源被添加到的容器。
  • Update — 现有资源的内容或元数据已被修改。
  • Delete — 资源已被移除。origin 字段 指示资源被移除前所在的容器。

允许客户端在容器之间移动资源的服务器，具体行为描述见 9.6 移动资源于 容器之间，必须 支持以下活动类型：

  • Move — 资源已从一个容器移动到另一个容器。 origin 字段指示资源被移除前所在的容器， 而 target 字段指示资源被添加到的容器。 object 字段描述移动后的资源。

也 可以 支持其他活动类型。

10.2.4 批处理通知

服务器 可以 将多个活动合并到单个通知 信封中，方法是 提供活动对象数组，作为 activity 属性的值。

示例 14: 批处理通知 
{
  "@context": [
    "https://www.w3.org/ns/lws/v1",
    "https://www.w3.org/ns/activitystreams"
  ],
  "type": "Notification",
  "storage": "https://storage.example/",
  "activity": [
    {
      "id": "a1b2c3d4-5678-9abc-def0-1234567890ab",
      "type": ["Create"],
      "object": {
        "id": "https://storage.example/alice/notes/meeting.txt",
        "type": ["DataResource"]
      },
      "target": "https://storage.example/alice/notes/",
      "published": "2026-03-26T10:30:00Z"
    },
    {
      "id": "b2c3d4e5-6789-abcd-ef01-234567890abc",
      "type": ["Update"],
      "object": {
        "id": "https://storage.example/alice/profile",
        "type": ["DataResource"]
      },
      "published": "2026-03-26T10:30:01Z"
    }
  ]
}

10.3 订阅

要接收通知，一个 订阅者 创建一个 订阅，方法是 发送 一个经过身份验证的 POST 请求，目标为该服务的 serviceEndpoint，即 NotificationService。请求消息体 必须 符合 application/lws+json 媒体类型。

10.3.1 订阅请求

订阅请求 必须 包含以下字段：

  • type — 必需。标识订阅 类型的字符串。 其值 必须 是以下数组中列出的类型之一： subscriptionType 数组，属于 NotificationService。
  • topic — 必需。URI 数组，标识 资源， 即订阅包含的资源。

订阅请求 可以 包含其他字段，按照其 具体的 订阅类型的要求提供。

示例 15: 订阅请求 
POST /subscriptions HTTP/2
Host: notification.example
Authorization: Bearer <access-token>
Content-Type: application/lws+json

{
  "@context": ["https://www.w3.org/ns/lws/v1"],
  "type": "WebhookSubscription",
  "topic": [
    "https://storage.example/alice/notes/",
    "https://storage.example/alice/profile"
  ],
  "inbox": "https://receiver.example/hooks/lws"
}

10.3.2 订阅范围

一个 订阅，如果针对容器，则是递归的：订阅者 接收 容器本身以及通过传递包含关系归属于 该容器的所有资源的通知。一个 订阅，如果针对数据资源，则仅适用于该 单个资源。

10.3.3 订阅 授权

服务器 必须 在创建以下 订阅 时实施资源授权。 如果一个 订阅者 无法以等同于读取的权限访问所有 资源， 这些资源列在 topic 数组中，则服务器 必须 拒绝该 订阅 请求。

授权也 必须 在通知投递时实施。服务器 不得 投递一个 通知，如果它所涉及的资源是该 订阅者 在事件发生时无权读取的资源。这适用于所有资源， 位于一个 订阅 的范围内，包括子容器中的资源。

如果以下 订阅者 对资源或容器的访问权限，这些资源或容器处于 某个订阅的范围内，即 订阅，在以下 订阅 创建后被撤销，则服务器 必须 停止投递受影响资源的通知。服务器 不应当 终止整个 订阅， 除非以下 订阅者 已失去 对 topic 数组中所有资源的访问权限。

注

订阅时的授权验证以下 订阅者 具有正当的 接收通知的依据。投递时的授权确保 通知始终与以下 订阅者 的当前权限一致， 并考虑可能发生于以下 订阅 创建之后的授权更改。

10.3.4 订阅响应

成功的订阅创建请求的响应 必须 符合 该 application/lws+json 媒体类型，并且 必须 包含以下 字段：

  • type — 必需。一个字符串，等于订阅类型， 来自 该请求。
  • subscription — 必需。表示该 订阅的 URL。

10.3.5 订阅类型 标识符

每个 通知 套件 必须 关联一个订阅类型字符串。 订阅类型字符串用于以下对象的 subscriptionType 数组中： NotificationService，以及订阅请求的 type 字段中。

11. 访问请求与授权

访问请求与授权为一个 代理 提供请求访问 资源的机制，并使一个 存储控制者 能够在已定义的约束下授予访问权限。 用于请求和授予访问权限的端点充当一种专用收件箱。

一个 代理 不会出示一个 访问授权 给服务器作为授权令牌。 相反，该 访问授权 作为记录，说明授权了什么、授权给谁， 以及附带哪些约束。当一个 访问授权 被创建或撤销（删除）时， 服务器负责调整任何底层访问策略，以反映此 更改。一个 访问授权 端点与特定策略 实施层之间的交互不在本规范的范围内。

以下 访问配置文件，其定义见本节，基于以下来源的概念： 该 开放数字权利语言（ODRL），包括 动作、约束和受让方。其他配置文件可以使用不同的概念框架。

11.1 发现

存储 可以 声明支持 访问请求 和 访问授权， 在其以下 存储描述资源 中声明。当此类支持 被声明时，一个服务 对象，描述以下 访问请求 的端点，必须 具有一个 type，等于字符串 AccessRequestService，而一个 服务对象，描述以下 访问授权 的端点，必须 具有一个 type，等于字符串 AccessGrantService。服务 对象 应当 包含一个 conformsTo 属性，其值是一个 集合， 包含一个或多个 URI，标识以下 访问配置文件，它们受该 端点支持。可以 包含其他属性：

示例 16: 包含访问请求和授权 服务的存储描述 
{
  "@context": [
    "https://www.w3.org/ns/cid/v1",
    "https://www.w3.org/ns/lws/v1"
  ],
  "id": "https://storage.example/",
  "type": "Storage",
  "service": [
    {
      "type": "StorageRoot",
      "serviceEndpoint": "https://storage.example/root/"
    },
    {
      "type": "AccessRequestService",
      "serviceEndpoint": "https://access.example/request/",
      "conformsTo": ["https://www.w3.org/ns/lws#AccessProfile"]
    },
    {
      "type": "AccessGrantService",
      "serviceEndpoint": "https://access.example/grant/",
      "conformsTo": ["https://www.w3.org/ns/lws#AccessProfile"]
    }
  ]
}

11.2 数据模型

一个 访问请求 或 访问授权 是一个数据 对象，表达属性， 用于标识和路由，以及一个 access 对象，用于描述 所请求或获准的操作。一个配置文件，描述以下 访问请求，并使用 ODRL 概念，其描述见 11.3 访问配置文件。

以下示例说明一个 访问请求。此示例展示时 使用以下章节定义的 JSON-LD 序列化：11.4.1 JSON-LD 序列化。

示例 17: 访问请求 
{
  "@context": [
    "https://www.w3.org/ns/lws/v1"
  ],
  "type": ["AccessRequest"],
  "inbox": "https://id.example/agent/inbox/",
  "storage": "https://storage.example/",
  "access": [{
    "type": ["AccessPolicy"],
    "action": ["read", "create"],
    "assignee": "https://id.example/agent",
    "target": {
      "type": "StorageResource",
      "value": ["https://storage.example/root/projects/"]
    },
    "constraint": [
      {
        "leftOperand": "purpose",
        "operator": "eq",
        "rightOperand": "https://purpose.example/collaboration"
      },
      {
        "leftOperand": "dateTime",
        "operator": "lteq",
        "rightOperand": "2026-06-09T10:00:00Z"
      }
    ]
  }]
}

以下示例说明一个 访问授权。此示例展示时 使用以下章节定义的 JSON-LD 序列化：11.4.1 JSON-LD 序列化。

示例 18: 访问授权 
{
  "@context": [
    "https://www.w3.org/ns/lws/v1"
  ],
  "type": ["AccessGrant"],
  "storage": "https://storage.example/",
  "access": [{
    "type": ["AccessPolicy"],
    "action": ["read"],
    "assignee": "https://id.example/agent",
    "target": {
      "type": "StorageResource",
      "value": ["https://storage.example/root/projects/"]
    },
    "constraint": [
      {
        "leftOperand": "purpose",
        "operator": "eq",
        "rightOperand": "https://purpose.example/collaboration"
      },
      {
        "leftOperand": "dateTime",
        "operator": "lteq",
        "rightOperand": "2026-06-09T10:00:00Z"
      }
    ]
  }]
}

其他属性 可以 存在于 访问请求 和 访问授权 上。

11.2.1 类型

type 属性表达文档的类型。

type 属性的值 必须 是一个或多个 术语 和 绝对 URL 字符串。对于一个 访问请求，其值 必须 包含术语 AccessRequest。 对于一个 访问授权，其值 必须 包含术语 AccessGrant。可以 包含其他类型值。

此属性是 必需 的。

本文档定义以下类型值，用于 访问请求 和 访问授权：

  • AccessRequest — 一个 代理 请求访问资源的请求。
  • AccessGrant — 一个授权，由 存储 控制者 授予 对资源的访问权限。
示例 19: type 属性 
{
  "type": ["AccessGrant"]
}

11.2.2 存储

storage 属性标识 LWS 存储，以下 访问请求 或 访问授权 的范围被 限定于该存储。

storage 属性的值 必须 是 URI。

此属性是 必需 的。

示例 20: storage 属性 
{
  "storage": "https://storage.example/"
}

11.2.3 收件箱

inbox 属性指定一个 URI，用于接收与以下对象相关的通知： 该 访问请求 或 访问授权 （参见 11.6 通知）。

inbox 属性的值 必须 是 URI。

此属性是 可选 的。

示例 21: inbox 属性 
{
  "inbox": "https://id.example/agent/inbox/"
}

11.2.4 访问

access 属性描述一个或多个 访问配置文件 的特征，基于以下对象支持的配置文件： 服务器。一个 配置文件，基于该 ODRL 信息模型，其描述 见 11.3 访问配置文件。

access 属性的值 必须 是一个集合，包含一个 或多个 对象。

此属性是 必需 的。

11.3 访问配置文件

本规范定义一个访问配置文件，基于 ODRL 信息模型 和 ODRL 词汇，通过 以下 URL 标识： https://www.w3.org/ns/lws#AccessProfile。

11.3.1 类型

type 属性表达访问策略的类型。

type 属性的值 必须 是一个或多个 术语 和 绝对 URL 字符串，并且 必须 包含 术语 AccessPolicy。可以 包含其他类型值。

此属性是 必需 的。

示例 22: 访问策略类型 
{
  "access": [{
    "type": ["AccessPolicy"]
  }]
}

11.3.2 动作

action 属性描述以下 操作，即以下 代理 希望 执行的操作（请求的情况），或获准执行的操作（授权的情况）。

action 属性的值 必须 是一个集合，包含一个 或多个 字符串。每个值 必须 对应以下对象识别的操作： 服务器。 以下值 必须 受到支持：read、modify、 create 和 delete。read、 modify 和 delete 值定义于 ODRL 词汇。 create 值由本 规范定义。

这些动作值对应以下 LWS 操作：

  • read — 检索资源或其元数据（HTTP GET、HEAD）
  • modify — 修改现有资源（HTTP PUT、PATCH）
  • create — 在容器内创建新资源（HTTP POST）
  • delete — 移除现有资源（HTTP DELETE）

此属性是 必需 的。

示例 23: action 属性 
{
  "access": [{
    "action": ["read", "create"]
  }]
}

11.3.3 受让方

assignee 属性标识请求访问的一方（在 请求的情况下），或被授予访问权限的一方（在授权的情况下）。

assignee 属性的值 必须 是 URI。公开 访问 可以 被 分配，使用以下来源的 Agent 类：FOAF 词汇，该类由 URI http://xmlns.com/foaf/0.1/Agent 标识。

此属性是 必需 的。

示例 24: assignee 属性 
{
  "access": [{
    "assignee": "https://id.example/agent"
  }]
}

11.3.4 目标

target 属性标识资源，以下 访问请求 或 访问授权 适用于这些资源。

target 属性 必须 是一个对象，包含 以下属性：

  • type — 一个 术语 或 绝对 URL 字符串，标识 该 目标匹配器的类型。
  • value — 包含一个或多个字符串的集合，用于标识 目标资源。

本规范定义以下 type 值，供 目标对象使用：

  • https://www.w3.org/ns/lws#DataResource — 匹配 类型为 lws:DataResource 的资源。
  • https://www.w3.org/ns/lws#Container — 匹配 类型为 lws:Container 的资源。
  • https://www.w3.org/ns/lws#StorageResource — 匹配 任何 存储资源。

服务器 可以 支持其他类型值。

此属性是 可选 的。

示例 25: 具有 StorageResource 类型的 target 属性 
{
  "access": [{
    "target": {
      "type": "StorageResource",
      "value": [
        "https://storage.example/root/2025",
        "https://storage.example/root/2026"
      ]
    }
  }]
}

11.3.5 约束

constraint 属性定义用于限制或限定 所请求或授予的访问的条件。此属性使用 ODRL 约束模型。

constraint 属性的值（如果存在）必须 是一个 集合， 其中包含约束对象。每个约束对象必须 包含以下 属性：

  • leftOperand — 标识受约束的操作数的字符串。
  • operator — 标识比较运算符的字符串。
  • rightOperand — 用于比较的值。其类型取决于 leftOperand。

当存在多个约束对象时，所有约束都必须 得到 满足。

声明支持此配置文件的服务器必须 支持以下 leftOperand 值：

  • client — 表示 HTTP 请求的客户端标识符
  • format — 表示目标 HTTP 资源的媒体类型
  • type — 表示资源的链接首部中表达的类型 URL
  • purpose — 表示所请求或授予的访问的预期 用途
  • dateTime — 表示当前日期时间

此属性是可选的。

以下示例展示了这些约束的用法：

11.3.5.1 用途约束

以下示例使用值为 purpose 的 leftOperand 来描述所请求或授予的访问的预期 用途。当使用 eq 运算符 时，rightOperand 的值是标识用途的 URI。 当使用 isAnyOf 运算符时，rightOperand 的值是用途 URI 的数组；如果 声明的用途与所列任一值匹配，则满足该约束：

示例 26：用途约束 
{
  "access": [{
    "constraint": [
      {
        "leftOperand": "purpose",
        "operator": "isAnyOf",
        "rightOperand": [
          "https://purpose.example/collaboration",
          "https://purpose.example/research"
        ]
      }
    ]
  }]
}
11.3.5.2 客户端约束

以下示例使用值为 client 的 leftOperand 将访问限制 为特定客户端应用程序。当使用 eq 运算符时， rightOperand 的值是标识客户端的 URI：

示例 27：客户端约束 
{
  "access": [{
    "constraint": [
      {
        "leftOperand": "client",
        "operator": "eq",
        "rightOperand": "https://app.example/client-id"
      }
    ]
  }]
}
11.3.5.3 格式约束

以下示例使用值为 format 的 leftOperand 将 访问限制为具有特定媒体类型的资源。当使用 eq 运算符 时，rightOperand 的值是标识 IANA 媒体类型的字符串。当 使用 isAnyOf 运算符时，rightOperand 的值 是媒体类型字符串的数组；如果资源的 媒体类型与所列任一值匹配，则允许访问：

示例 28：格式约束 
{
  "access": [{
    "constraint": [
      {
        "leftOperand": "format",
        "operator": "isAnyOf",
        "rightOperand": ["image/jpeg", "image/png"]
      }
    ]
  }]
}
11.3.5.4 资源类型 约束

所有存储资源都将包含链接首部， 用于指示类型值：

示例 29：包含类型值的链接首部 
Link: <https://www.w3.org/ns/lws#DataResource>; rel="type"
Link: <https://type.example/Playlist>; rel="type"

以下示例使用值为 type 的 leftOperand，根据 HTTP Link 首部中声明的资源类型限制访问。 当使用 eq 运算符时，rightOperand 的值 是标识资源类型的 URI。当使用 isAnyOf 运算符 时，rightOperand 的值是类型 URI 的数组；如果资源的类型 与所列任一值匹配，则允许访问：

示例 30：资源类型约束 
{
  "access": [{
    "constraint": [
      {
        "leftOperand": "type",
        "operator": "isAnyOf",
        "rightOperand": [
          "https://type.example/Playlist",
          "https://type.example/Song"
        ]
      }
    ]
  }]
}
11.3.5.5 时间约束

以下示例使用值为 dateTime 的 leftOperand 将访问限制 在特定时间窗口内。gteq 运算符定义窗口的起点， 而 lteq 运算符定义其终点。时间约束的 rightOperand 值是一个 XML Schema dateTime 字符串：

示例 31：时间约束 
{
  "access": [{
    "constraint": [
      {
        "leftOperand": "dateTime",
        "operator": "gteq",
        "rightOperand": "2026-03-09T12:00:00Z"
      },
      {
        "leftOperand": "dateTime",
        "operator": "lteq",
        "rightOperand": "2026-06-09T10:00:00Z"
      }
    ]
  }]
}
11.3.5.6 组合约束

当存在多个约束对象时，所有约束都必须 得到 满足，才能 允许访问。以下示例将访问限制为特定客户端 应用程序，并要求在特定日期之前：

示例 32：组合后的约束 
{
  "access": [{
    "action": ["read"],
    "assignee": "https://id.example/agent",
    "target": {
      "type": "StorageResource",
      "value": ["https://storage.example/root/projects/"]
    },
    "constraint": [
      {
        "leftOperand": "dateTime",
        "operator": "lteq",
        "rightOperand": "2026-06-09T10:00:00Z"
      },
      {
        "leftOperand": "client",
        "operator": "eq",
        "rightOperand": "https://app.example/client-id"
      }
    ]
  }]
}

11.4 序列化

本节定义的数据模型独立于任何特定的 序列化方式。

11.4.1 JSON-LD 序列化

本规范为访问请求 和 访问授权定义了 JSON-LD 序列化方式。使用此序列化方式的文档必须 包含一个 @context 属性，其值是一个有序集合，其中包含 https://www.w3.org/ns/lws/v1。额外的上下文条目可以 予以 包含，以定义扩展术语。

与此序列化方式关联的媒体类型是 application/lws+json。

示例 33：JSON-LD @context 
{
  "@context": [
    "https://www.w3.org/ns/lws/v1"
  ]
}

11.5 协议

访问请求和访问授权端点 是 LWS 容器，并且必须 遵守本规范定义的规则。

这些端点至少需要支持 GET 和 POST 操作。DELETE 操作 是建议支持的。其他操作可以 支持。

这些端点必须 对请求和响应载荷均支持 11.4.1 JSON-LD 序列化中定义的 JSON-LD 序列化方式。服务器 可以 支持其他序列化方式。

代理 通过向访问请求端点提交 POST 请求来创建访问请求，即向 该 访问请求端点提交。存储 控制者创建访问授权的方式是 向访问授权端点提交 POST 请求。

成功的 POST 操作必须 在响应中包含 Location 首部， 其值设置为 新资源的 URL。

11.5.1 访问请求端点

  • POST / — 创建访问请求。
  • GET / — 检索访问请求列表。
  • GET /:id — 检索特定访问请求。
  • DELETE /:id — 取消访问请求。

11.5.2 访问授权端点

  • POST / — 创建访问授权。
  • GET / — 检索访问授权列表。
  • GET /:id — 检索特定访问授权。
  • DELETE /:id — 撤销访问授权。

11.6 通知

问题 103：LWS 通知特性 work-item

本节需要与 LWS 中尚待定义的通知章节保持一致。

通知提供了一种机制，用于向代理和存储 控制者告知 访问请求和访问授权的变化。当 inbox 属性 出现在访问请求或访问授权中时， 服务器应当 将 通知投递到该端点，向 受让方告知该事件。

通知的序列化必须 符合 LWS 通知数据模型的要求。

投递到 inbox 端点的通知必须 符合 LWS 协议中定义的通知投递要求。

注

本节描述的通知机制类似于 关联数据通知模式，在该模式中， 通知通过 inbox 属性被发现，并通过向该收件箱发送 POST 请求来投递。

11.6.1 通知事件

服务器应当 响应以下事件发送通知：

  • 创建访问请求：当新的访问 请求被 提交时，存储控制者应当 收到通知。
  • 创建访问授权：当新的访问授权 被创建时， 发起请求的代理应当 在 所指定的 inbox 收到通知，该收件箱位于 关联的访问请求中。

服务器可以 响应其他事件发送通知。

12. LWS 媒体类型

12.1 LWS 媒体类型

LWS 存储描述必须 能够以媒体类型 application/lws+cid 进行序列化。 application/lws+cid 媒体类型标识一种文档，该文档是 W3C 受控标识符文档 [CID-1.0] 的特化，并使用 LWS 词汇进行扩展。

LWS 容器表示必须 支持媒体类型 application/lws+json。

虽然 LWS 容器表示使用 JSON-LD 约定，但 LWS 的约束和要求 使使用专用媒体类型具有合理性。

12.1.1 LWS 配置文件

URI https://www.w3.org/ns/lws/v1 标识 LWS 配置文件 [RFC6906]。容器的表示符合LWS 配置文件，条件是它 与相同容器状态和页面的 application/lws+json 表示在 RDF 意义上同构；也就是说，它编码的 RDF 按照RDF 数据集 比较 [RDF12-CONCEPTS] 中的定义，同构于 application/lws+json 表示在作为 JSON-LD 解释时所编码的 RDF [JSON-LD11]。application/lws+json 表示始终符合LWS 配置文件。

12.1.2 内容协商

服务器必须 满足对容器的 application/lws+json 请求，并且必须 将 Content-Type 响应首部设置为所选表示的媒体类型。

客户端通过在 RDF 媒体类型的 profile 参数中包含LWS 配置文件的 URI，来请求符合该配置文件的表示，该 URI 即LWS 配置文件 URI，置于相应 RDF 媒体类型的参数中。定义了此参数的 RDF 媒体类型包括 application/ld+json [JSON-LD11]、text/turtle [RDF12-TURTLE]、application/trig [RDF12-TRIG]、application/n-triples [RDF12-N-TRIPLES]，以及 application/n-quads [RDF12-N-QUADS]。如果服务器选择了此类媒体类型， 响应必须 符合LWS 配置文件，也就 是说，它必须 与 application/lws+json 表示在 RDF 意义上同构，并且其 Content-Type 必须 包含相同的 profile 参数。服务器不得 选择此类媒体类型， 如果它无法以该媒体类型生成符合LWS 配置文件的表示。

当所选表示取决于请求的 Accept 首部时，响应应当 包含 Vary: Accept 首部 [RFC9110]。

12.1.3 分页

某些复合资源（例如容器）可能包含大量资源。 为使客户端能够逐步检索列表，服务器应当 对 成员数量超过服务器所确定阈值的容器支持分页，该阈值 由服务器确定。

12.1.3.1 分页模型

分页基于链接：服务器通过 HTTP Link 首部提供分页 URI [RFC8288]， 使客户端无需依赖数字偏移量即可遍历完整列表。

当列表被分页时，响应体仅包含当前页的条目。 复合资源的 id、type 和 totalItems 属性 反映完整的成员集合，而 items 仅包含当前页的资源。

12.1.3.2 分页链接 关系

分页 URI 在 Link 首部中使用以下标准链接 关系传递：

  • rel="first"：结果第一页的 URI。必须 出现在分页响应中。
  • rel="last"：结果最后一页的 URI。可以 出现在分页响应中。
  • rel="next"：结果下一页的 URI。必须 在存在后续 页面时出现。必须 在最后一页省略。
  • rel="prev"：结果上一页的 URI。可以 在存在先前 页面时出现。必须 在第一页省略。

所有分页 URI 对客户端都是不透明的。客户端不应当 构造或修改分页 URI；它们应当 使用服务器提供的 URI。

12.1.3.3 请求页面

客户端请求复合资源的 URI 以获取第一页。响应包含 分页 Link 首部，客户端沿这些链接检索后续页面。服务器可以 同时支持 通过先前扫描期间获得的分页 URI 直接访问特定页面。

返回分页响应时，服务器必须 以 200 OK 响应。totalItems 属性位于响应体中，应当 反映所有页面中的条目 总数，而不只是当前页的条目数。

16. 安全注意事项

本节为非规范性内容。

正式的安全注意事项章节，涵盖威胁模型、安全要求以及 安全部署 LWS 的实现指南。

《OAuth 2.0 安全的当前最佳实践》[RFC9700] 中描述的建议适用于本 规范。

16.1 传输安全

本节为非规范性内容。

传输层安全（TLS）是防止篡改、欺骗和 信息泄露的重要机制。可以按照 [RFC6125] 验证受 TLS 保护的通信。 实现方面的安全注意事项见《安全使用传输 层安全（TLS）和数据报传输层安全（DTLS）的建议》[RFC9325]。

16.2 令牌安全

本节为非规范性内容。

持有者令牌和数字凭据容易遭到窃取和重放。缓解措施包括使用 合理的较短有效期、将令牌绑定到特定受众，以及安全地存储令牌。

  • 短有效期：授权服务器为访问令牌分配 300 秒（5 分钟）或更短的 有效期，可以限制已外泄凭据的潜在暴露风险。
  • 受众绑定：通过诸如 aud 声明等方式，将访问令牌绑定到特定目标服务器，可以防止令牌被重放到其他服务器。访问令牌的 受众如果包含 多个服务器，则其中任意服务器都可以将其重放到其他服务器；授权 服务器可通过 签发以单个存储 URI 为受众的令牌来避免此问题。处理凭据的应用程序，如果凭据的受众 未 受限制，则在将这些凭据发送给其他实体时需要谨慎， 尤其是发送给不可信的 授权服务器时。如果凭据签发方无法限制令牌的受众，客户端 可以使用 OAuth 2.0 令牌交换 [RFC8693] 等机制，在 与不同安全域中的授权服务器交互之前， 创建受众受约束的凭据。
  • 发送方约束令牌：任何获得持有者令牌的一方都可以使用它，而受众 限制 并不能阻止已外泄的令牌被重放到预期的存储服务器。由于 受众是 一个存储，因此被盗令牌可用于该存储中代理 获准访问的每个资源。 将访问令牌绑定到客户端密钥，例如使用 OAuth 2.0 持有证明展示 （DPoP） [RFC9449]，可将 被盗令牌的使用限制为该密钥的持有者。受保护资源元数据文档可以 声明存储服务器支持的 DPoP 证明算法，以及它是否要求 与 DPoP 绑定的访问 令牌，所用参数为 dpop_signing_alg_values_supported 和 dpop_bound_access_tokens_required，它们定义于 [RFC9728]。
  • 安全存储：持久保存凭据的应用程序需要确保这些对象得到 安全存储。每当未加密的令牌存储在浏览器的 localStorage、URL 或日志中时，该令牌就更容易遭受外泄攻击。

16.3 资源发现

本节为非规范性内容。

客户端从存储服务器发送的响应中获知授权服务器的位置，而 该客户端 可能并不信任该存储服务器。以下注意事项适用于此发现过程。

  • 不可信元数据：恶意存储服务器可以将客户端引导到一个授权服务器，而 该客户端并 不信任它；向该授权服务器出示身份验证凭据的客户端，会向该 授权服务器泄露 凭据。客户端可以应用自身关于信任哪些授权 服务器的 策略来降低此风险。5.2.3 客户端对发现的验证中的检查要求 受保护资源 元数据描述同一服务器上的请求资源，从而防止服务器出示 属于 其他资源服务器的元数据。当客户端使用的 是 身份验证凭据，且其受众 仅限于接收该凭据的授权服务器时，泄露的影响也会降低。
  • 存储绑定：客户端从存储服务器响应的 Link 首部中获取存储 URI，该 存储 服务器如果是恶意服务器，就可以提供其他存储的 URI，导致客户端获取 一个访问令牌， 该令牌用于那个存储，却被出示给恶意服务器，后者便可以重放它。因此， 客户端 必须使用存储描述来确认， 所请求的 URI 由与 存储根同源的位置提供，然后才能请求访问令牌，相关说明见 本规范的 5.2.3 客户端对发现的验证。
  • 服务器端请求伪造：质询中的 resource_metadata URL、存储 URI（位于 Link 首部中），以及受保护资源元数据文档中的签发方标识符，都是 由 存储服务器选择的，而客户端会检索它们标识的文档。代表 其他方执行此 检索的客户端（例如服务器端应用程序）面临服务器端请求伪造风险，相关说明 见 [RFC9728] 第 7.7 节。预防措施包括 将检索限制为 https 方案，以及 阻止对内部 IP 地址范围的请求。

16.4 访问请求与授权

本节为非规范性内容。

  • 强烈鼓励服务器将授权规则同时应用于 访问请求和访问授权 端点。尤其是对 访问授权端点的写入权限，应限制 为已获授权的 存储控制者和特定客户端。
  • 当代理创建访问请求时，鼓励服务器验证 请求中的 assignee 值是否与 请求代理经过身份验证的身份相关联。
  • 由于访问请求端点接受来自外部 代理的内容， 鼓励服务器实施防止滥用的措施，例如速率限制、 载荷大小限制，或在接受提交之前要求进行身份验证。 如果没有此类保护，该端点可能易受垃圾内容、资源耗尽 或其他形式的不需要的内容影响。

16.5 通知

本节为非规范性内容。

  • 信息泄露：通知可能泄露资源的存在或 修改模式。订阅以及单个 通知投递的访问控制必须 与底层 相应 资源的访问控制保持一致。
  • 订阅滥用：建议采用速率限制和端点验证， 以防止订阅机制遭到滥用。

16.6 在容器之间 移动资源

本节为非规范性内容。

  • 适用策略的变化：对资源的访问通常由策略控制， 这些策略根据资源在包含关系 层次中的位置来表达。因此，更改资源的 up 链接可能扩大或缩小 可以访问该资源的代理集合，而无需编辑任何策略，也无需 对 资源内容作出更改。向 存储控制者以及请求移动的代理展示这一 后果，是一种有效的 缓解措施，不过实现如何做到这一点不在本 规范的范围内。
  • 权限组合：移动资源结合了在源 容器中删除和在目标容器中创建的效果。服务器 必须 按照9.6 在容器之间移动 资源的要求评估这两项授权； 如果仅评估更新资源元数据的授权，就会允许 代理 将资源放入其无权写入的容器，或者从 其无权删除资源的容器中移除资源。
  • 移动容器：移动容器会移动其后代，其中 可能包含请求移动的代理不知道的资源。虽然 这些后代的父级不变，但适用于它们的策略可能改变，因此支持 移动容器的服务器必须 评估 对被移动子树执行递归 删除所需的授权，正如9.6 在容器之间移动资源所要求的那样，并且不得 部分应用一个在子树某部分授权失败的移动操作。
  • 放宽服务器管理的元数据限制：描述 MoveResource 能力，会使原本由服务器自行维护的 up 链接 变为可由客户端写入。服务器应当 仅在其 部署需要时 描述此能力，应当 将其 appliesTo 属性限制为 需要支持的 资源类型，并且必须 继续保留客户端无权 修改的 链接。

17. 隐私注意事项

本节为非规范性内容。

LWS 协议的隐私影响，包括数据最小化、用户同意以及 保护隐私的实现模式。

凭据承载有关用户和代理的信息。虽然数字签名可以防止篡改， 但客户端或第三方仍可能读取未加密凭据中的值。

因此，鼓励凭据签发方创建仅包含必要信息的令牌，这些信息用于 进行 身份验证或授权，并避免包含敏感属性，除非有此需要。

一般而言，将未加密的凭据数据写入日志是一种反模式。如果这样做 确有必要， 实现可以截断凭据或对其进行哈希处理，以保护凭据主体的隐私。

在 JWT 中使用假名标识符时，存储服务器仍可能将 同一个代理的请求 随时间推移关联起来。 为在这种情况下保护用户隐私，客户端应用程序可以请求批量签发 JWT，其中每个 JWT 仅使用一次。 这并不能阻止存储服务器使用其他信息，例如 JWT 内容的相似性或 来源 IP 地址， 来关联请求。使用假名标识符时，授权服务器需要注意， 不要多次签发相同的标识符。

17.1 访问请求与授权

本节为非规范性内容。

  • 访问请求或访问授权可能 泄露敏感信息， 涉及相关的资源、代理和用途。鼓励服务器将 这些资源的可见性限制为已获授权的各方，例如存储控制者 和文档中标识的受让方。例如，存储控制者可能 能够读取和删除所有资源，而其他代理只能 访问其作为受让方的资源。
  • 当访问授权包含客户端约束时，建议 相应 服务器在响应其他客户端发出的请求时过滤掉该授权。例如， 如果代理仅在使用特定 客户端时获准访问某个资源，那么当代理使用其他客户端时，该授权将不可见。

17.2 通知

本节为非规范性内容。

  • 活动跟踪：通知天然会泄露资源何时 发生变化。订阅者应当 仅接收 其有权 访问的资源的通知。
  • 行为者披露：在通知中包含 actor 属性， 会揭示是谁作出了更改。这在某些情况下可能不合适。 默认情况下应当 省略 actor 属性。服务器可以 将 是否包含该属性设为可配置。
  • 时序分析：即使不披露内容，通知的时序也可能揭示使用 模式。

17.3 在容器之间 移动资源

本节为非规范性内容。

  • 意外暴露：移动资源的代理可能没有意识到， 目标容器所受策略比源容器的策略更加 宽松。在更改资源的 up 链接之前，展示 适用策略之间的差异，是一种有效的缓解措施，不过客户端如何做到这一点不在本 规范的范围内。
  • 保留标识符：此注意事项仅适用于服务器 根据包含关系层次推导标识符的情况。此类服务器如果保留 被移动资源的标识符，就会留下一个持续泄露 该资源最初创建时所在容器的标识符。 将 标识符视为不透明值的服务器（正如本规范所建议的那样）不会造成这种泄露， 因为它们的标识符从未编码层次中的位置。

    最好在工作组决定 存储如何描述其分配 标识符的方法之后，再给出此注意事项的具体示例。

  • 重定向：在先前标识符处留下的 301 Moved Permanently 响应， 会向可能无权访问资源的代理披露该资源的 新标识符。如果标识符根据包含关系 层次推导，它还会披露资源在该层次中的新位置， 从而泄露资源被移入的容器；如果标识符是不透明的， 则仅 披露新标识符。服务器应当 对此类响应应用与 被移动资源 本身相同的访问控制，并且可以 改为以 404 Not Found 响应。

  • 元数据描述：JSON 数组，包含此授权服务器所支持的 OAuth 2.0 "subject_token_type" 值的 列表
  • 变更控制方：W3C
  • 规范文档：LWS-Auth 第 5 节
  • 元数据名称：subject_identifier_types_supported
  • 元数据描述：JSON 数组，包含此 授权服务器所支持的主体标识符类型列表
  • 变更控制方：W3C
  • 规范文档：LWS-Auth 第 5 节

18.3 媒体类型 application/lws+json

本规范注册 application/lws+json 媒体类型，专门用于 标识 符合关联 Web 存储容器格式的文档。

  • 类型名称：application
  • 子类型名称：lws+json
  • 必需参数：无
  • 编码注意事项：使用 application/lws+json 媒体类型的资源 需要符合 application/json 媒体类型的全部要求，因此受 相同编码 注意事项的约束，这些事项规定于 [RFC8259] 第 11 节。
  • 安全注意事项：按本规范中的定义。
  • 联系方：W3C 关联 Web 存储工作组 <public-lws-wg@w3.org>

请注意，虽然关联 Web 存储格式使用 JSON-LD 约定，但 LWS 实现还存在一些约束和额外 要求，使使用专用媒体类型具有合理性。

18.4 媒体类型 application/lws+cid

本规范注册 application/lws+cid 媒体类型，用于标识 符合关联 Web 存储协议的存储描述文档，该格式是 W3C 受控标识符 1.0 文档格式的特化。

  • 类型名称：application
  • 子类型名称：lws+cid
  • 必需参数：无
  • 编码注意事项：使用 application/lws+cid 媒体类型的资源 需要符合 application/json 媒体类型的全部要求，因此受相同编码注意事项的约束，这些事项规定于 [RFC8259] 第 11 节。
  • 安全注意事项：按本规范中的定义
  • 联系方：W3C 关联 Web 存储工作组 <public-lws-wg@w3.org>
