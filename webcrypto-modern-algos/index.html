1. 简介

本节不具规范性。

本提案旨在使 Web 加密 API 中可用的密码算法集现代化，以便 Web 应用程序能够使用具备后量子安全性且 性能良好的密码算法。 为此，添加以下密码算法：

  • ML-KEM [FIPS-203]
  • ML-DSA [FIPS-204]
  • SLH-DSA [FIPS-205]
  • AES-OCB [RFC7253]
  • ChaCha20-Poly1305 [RFC8439]
  • SHA3-256、SHA3-384 和 SHA3-512 [FIPS-202]
  • cSHAKE128、cSHAKE256、KMAC128 和 KMAC256 [NIST-SP800-185]
  • TurboSHAKE128、TurboSHAKE256、KT128 和 KT256 [RFC9861]
  • Argon2d、Argon2i 和 Argon2id [RFC9106]

为了支持 ML-KEM 以及将来可能出现的其他 KEM， 本提案引入了用于密钥封装和解封装的函数： SubtleCrypto.encapsulateKey、 SubtleCrypto.encapsulateBits、 SubtleCrypto.decapsulateKey 和 SubtleCrypto.decapsulateBits。

此外，本提案还引入了 SubtleCrypto.getPublicKey 函数， 它提供了一种从非对称私钥派生公钥的便捷方式， 当只需要私钥时，无需分别存储公钥和私钥。

最后，本提案旨在简化特性检测， 方法是添加 SubtleCrypto.supports 函数， 该函数可用于检测指定操作是否支持给定的算法标识符 （包括任何参数）。

2. 规范约定

本规范遵循 [webcrypto] 第 18.3 节中规定的约定。此处定义的算法均 不要求实现，但如果符合规范的用户代理实现了某个 算法，则它必须实现本文档规定的所有受支持操作， 并且必须针对每个受支持的操作，执行 [webcrypto] 第 18.4.3 节中规定的定义算法 步骤。

除了 [webcrypto] 中定义的受支持的操作之外，本规范还使用 以下操作：

  • 封装
  • 解封装
  • 获取共享密钥长度

3.1 数据类型

3.1.1 密钥格式

本规范将 [webcrypto] 中 KeyFormat 的定义替换为以下内容： 

WebIDLenum KeyFormat { "raw-public", "raw-private", "raw-seed", "raw-secret", "raw", "spki", "pkcs8", "jwk" };

本规范规定了多个新的已识别密钥格式 值：

raw-public
未格式化的公钥字节序列。
raw-private
未格式化的私钥字节序列。
raw-seed
未格式化的私钥种子字节序列。
raw-secret
未格式化的秘密密钥字节序列。

对于 [webcrypto] 中所有现有的对称算法， “raw-secret”作为“raw”的别名。

对于 [webcrypto] 中所有现有的非对称算法， “raw-public”作为“raw”的别名。

在 deriveKey() 方法的导入密钥步骤中， 必须使用“raw-secret”作为格式， 而不是“raw”。

3.1.2 密钥用途

本规范将 [webcrypto] 中 KeyUsage 的定义替换为以下内容： 

WebIDLenum KeyUsage { "encrypt", "decrypt", "sign", "verify", "deriveKey", "deriveBits", "wrapKey", "unwrapKey", "encapsulateKey", "encapsulateBits", "decapsulateKey", "decapsulateBits" };

本规范规定了多个新的已识别密钥用途 值：

encapsulateKey
允许将密钥用于 SubtleCrypto.encapsulateKey。
encapsulateBits
允许将密钥用于 SubtleCrypto.encapsulateBits。
decapsulateKey
允许将密钥用于 SubtleCrypto.decapsulateKey。
decapsulateBits
允许将密钥用于 SubtleCrypto.decapsulateBits。

3.2 方法和参数

3.2.1 encapsulateKey 方法

encapsulateKey(encapsulationAlgorithm, encapsulationKey, sharedKeyAlgorithm, extractable, usages) 方法封装一个密钥，并返回一个 EncapsulatedKey 对象。 其行为如下：

  1. 令 encapsulationAlgorithm、encapsulationKey、 sharedKeyAlgorithm、 extractable 和 usages 分别为传递给 encapsulateKey() 方法的 encapsulationAlgorithm、 encapsulationKey、 sharedKeyAlgorithm、extractable 和 keyUsages 参数。

  2. 令 normalizedEncapsulationAlgorithm 为规范化 算法的结果，其中 alg 设置为 encapsulationAlgorithm，op 设置为 “encapsulate”。

  3. 如果发生错误，则返回一个以 normalizedEncapsulationAlgorithm 拒绝的 Promise。

  4. 令 normalizedSharedKeyAlgorithm 为规范化 算法的结果，其中 alg 设置为 sharedKeyAlgorithm，op 设置为 “importKey”。

  5. 如果发生错误，则返回一个以 normalizedSharedKeyAlgorithm 拒绝的 Promise。

  6. 令 realm 为 this 的相关 领域。

  7. 令 promise 为一个新的 Promise。

  8. 返回 promise，并并行执行剩余步骤。

  9. 如果以下步骤或引用的过程要求 抛出错误， 则在加密任务源上， 给定 realm 的全局对象，排入一个全局任务， 以使用返回的错误拒绝 promise； 然后终止 算法。

  10. 如果 normalizedEncapsulationAlgorithm 的 name 成员不等于 encapsulationKey 的 [[algorithm]] 内部槽的 name 属性，则抛出一个 InvalidAccessError。

  11. 如果 encapsulationKey 的 [[usages]] 内部槽不包含值为“encapsulateKey”的条目， 则抛出一个 InvalidAccessError。

  12. 令 encapsulatedBits 为使用 encapsulationKey 执行由 encapsulationKey 的 [[algorithm]] 内部槽指定的封装操作所得的结果。

  13. 令 sharedKey 为执行由 normalizedSharedKeyAlgorithm 指定的导入密钥操作所得的结果，其中使用“raw-secret”作为 format，使用 encapsulatedBits 的 sharedKey 字段作为 keyData，使用 sharedKeyAlgorithm 作为 algorithm，并使用 extractable 和 usages。

  14. 将 sharedKey 的 [[extractable]] 内部槽设置为 extractable。

  15. 将 sharedKey 的 [[usages]] 内部槽设置为 usages 的规范化值。

  16. 令 encapsulatedKey 为一个新的 EncapsulatedKey 字典， 其中将 sharedKey 设置为 sharedKey， 并将 ciphertext 设置为 encapsulatedBits 的 ciphertext 字段。

  17. 在加密任务源上， 给定 realm 的全局对象，排入 一个全局任务，以执行剩余步骤。

  18. 令 result 为按照 [WebIDL] 的定义， 在 realm 中将 encapsulatedKey 转换为 ECMAScript 对象所得的结果。

  19. 使用 result 兑现 promise。

  18. 使用 result 兑现 promise。

3.2.6 supports 方法

supports(operation, algorithm, length) 方法返回一个布尔值，指示实现是否 支持使用指定的 AlgorithmIdentifier 执行给定操作，并可通过可选的 length 参数指示当 operation 为 "deriveBits" 时要派生的位数。 其行为如下：

  1. 如果 operation 不是以下值之一： "encrypt"、"decrypt"、"sign"、"verify"、 "digest"、"generateKey"、"deriveKey"、 "deriveBits"、 "importKey"、"exportKey"、"wrapKey"、 "unwrapKey"、 "encapsulateKey"、"encapsulateBits"、 "decapsulateKey"、"decapsulateBits" 或 "getPublicKey"， 返回 false。

  2. 返回检查算法支持情况的结果， 其中将 op 设置为 operation，将 alg 设置为 algorithm， 并将 length 设置为 length。

supports(operation, algorithm, additionalAlgorithm) 方法返回一个布尔值，指示实现是否 支持使用指定的 AlgorithmIdentifier 执行给定操作。 当 operation 为 "deriveKey" 时，附加算法指示要派生的密钥类型； 当 operation 为 "wrapKey" 时，指示包装前要导出的密钥类型； 当 operation 为 "unwrapKey" 时，指示解包后要导入的密钥类型。 其行为如下：

  1. 如果 operation 不是以下值之一： "encrypt"、"decrypt"、"sign"、"verify"、 "digest"、"generateKey"、"deriveKey"、 "deriveBits"、 "importKey"、"exportKey"、"wrapKey"、 "unwrapKey"、 "encapsulateKey"、"encapsulateBits"、 "decapsulateKey"、"decapsulateBits" 或 "getPublicKey"， 返回 false。

  2. 如果 operation 为 "deriveKey" 或 "unwrapKey"：

    如果检查 算法支持情况的结果 （其中将 op 设置为 "importKey" 并将 alg 设置为 additionalAlgorithm） 为 false， 则返回 false。

    如果 operation 为 "wrapKey"：

    如果检查 算法支持情况的结果 （其中将 op 设置为 "exportKey" 并将 alg 设置为 additionalAlgorithm） 为 false， 则返回 false。

  3. 如果 operation 为 "encapsulateKey" 或 "decapsulateKey"：

    1. 令 normalizedAlgorithm 为 规范化 算法的结果，其中 将 alg 设置为 algorithm，并将 op 设置为 "get shared key length"。

    2. 如果发生错误，则返回 false。

    3. 令 sharedKeyLength 为执行由 normalizedAlgorithm 指定的获取共享 密钥长度 算法并使用 algorithm 所得到的结果。

    4. 令 normalizedAdditionalAlgorithm 为 规范化 算法的结果，其中 将 alg 设置为 additionalAlgorithm，并将 op 设置为 "importKey"。

    5. 如果发生错误，则返回 false。

    6. 如果根据操作步骤确定 支持情况的结果 （其中将 op 设置为 "importKey"，将 normalizedAlgorithm 设置为 normalizedAdditionalAlgorithm，并将 length 设置为 null）为 false， 则返回 false。

    7. 如果由 normalizedAdditionalAlgorithm 指定的导入密钥操作，对于每个满足以下条件的 keyData 值都会 抛出错误： 该值是 一个字节序列， 其以位为单位的长度为 sharedKeyLength，且 format 为 "raw-secret"， 则返回 false。

  4. 令 length 为 null。

  5. 如果 operation 为 "deriveKey"：

    1. 如果检查算法 支持情况的结果 （其中将 op 设置为 "get key length" 并将 alg 设置为 additionalAlgorithm） 为 false， 则返回 false。

    2. 令 normalizedAdditionalAlgorithm 为 规范化 算法的结果，其中 将 alg 设置为 additionalAlgorithm，并将 op 设置为 "get key length"。

    3. 令 length 为执行由 additionalAlgorithm 指定的获取密钥长度 算法并使用 normalizedAdditionalAlgorithm 所得到的结果。

    4. 将 operation 设置为 "deriveBits"。

  6. 返回检查算法支持情况的结果， 其中将 op 设置为 operation，将 alg 设置为 algorithm， 并将 length 设置为 length。

3.3 检查对 算法的支持

检查算法支持情况算法 定义了检查给定算法是否支持给定操作的过程。 其输入为操作名称 op、一个 AlgorithmIdentifier alg 和一个 length 参数。其输出为布尔值。 其行为如下：

  1. 如果 op 为 "encapsulateKey" 或 "encapsulateBits"，将 op 设置为 "encapsulate"。

  2. 如果 op 为 "decapsulateKey" 或 "decapsulateBits"，将 op 设置为 "decapsulate"。

  3. 如果 op 为 "getPublicKey"：

    1. 令 normalizedAlgorithm 为 规范化 算法的结果，其中 将 alg 设置为 alg，并将 op 设置为 "exportKey"。

    2. 如果发生错误，则返回 false。

    3. 如果由 normalizedAlgorithm 标识的密码算法 不支持从私钥派生公钥， 则返回 false。

    4. 否则，返回 true。

  4. 令 normalizedAlgorithm 为 规范化 算法的结果，其中 将 alg 设置为 alg，并将 op 设置为 op。

  5. 如果发生错误：

    1. 如果 op 为 "wrapKey"， 返回检查算法 支持情况的结果， 其中将 op 设置为 "encrypt" 并将 alg 设置为 alg。

    2. 如果 op 为 "unwrapKey"， 返回检查算法 支持情况的结果， 其中将 op 设置为 "decrypt" 并将 alg 设置为 alg。

    3. 否则，返回 false。

  6. 返回根据操作 步骤确定支持情况的结果， 其中将 op 设置为 op，将 normalizedAlgorithm 设置为 normalizedAlgorithm， 并将 length 设置为 length。

根据操作步骤确定支持情况算法 确定规范化算法的操作步骤是否表明支持该操作。 其输入为操作名称 op、一个 Algorithm normalizedAlgorithm 和一个 length 参数。其输出为布尔值。 其行为如下：

  1. 如果指定的操作或规范化算法（或其某个参数值） 预期会由于实现特定的原因而失败（对于任意密钥和/或数据） （例如已知不符合规范），则返回 false。

  2. 如果 op 为 "generateKey" 或 "importKey"，令 usages 为空列表。

  3. 对于由 normalizedAlgorithm 指定的算法中 由 op 指定的操作的每个步骤：

    如果该步骤要求抛出错误：
    返回 false。
    如果该步骤要求生成密钥：
    返回 true。
    如果该步骤依赖不可用的参数，例如 key、 plaintext 或 ciphertext：
    返回 true。
    如果该步骤要求返回一个值：
    返回 true。
    否则：
    执行该步骤。
    注

    所引用算法中的步骤可以访问此上下文中的 normalizedAlgorithm、 length 和 usages 变量。

  4. 断言：永远不会 到达此步骤， 因为该操作的某个步骤必然会要求 返回一个值或抛出错误，从而分别使我们返回 true 或 false。

6. ML-KEM

6.1 描述

本节不具规范性。

本节描述了如何按照 [FIPS-203] 的规定， 使用 ML-KEM 进行密钥封装和解封装。

6.2 注册

此算法的已识别算法 名称为 “ML-KEM-512”、“ML-KEM-768”和“ML-KEM-1024”。

操作 参数 结果
封装 无 EncapsulatedBits
解封装 无 字节 序列
获取共享密钥长度 无 整数
generateKey 无 CryptoKeyPair
importKey 无 CryptoKey
exportKey 无 object

6.3 操作

6.3.1 封装

  1. 如果 key 的 [[type]] 内部槽不是 "public"， 则抛出一个 InvalidAccessError。

  2. 使用 [FIPS-203] 第 7.2 节中描述的封装密钥检查，其中参数集由 algorithm 的 name 成员指示， 并使用由 key 的 [[handle]] 内部槽表示的密钥作为 ek 输入参数。

    注

    如果有利于性能，可以为 CryptoKey 对象缓存或预计算此检查的结果。

  3. 如果封装密钥检查失败，则返回一个 OperationError。

  4. 令 sharedKey 和 ciphertext 为执行 [FIPS-203] 第 7.2 节中描述的 ML-KEM.Encaps 函数所产生的输出， 其中参数集由 algorithm 的 name 成员指示， 并使用由 key 的 [[handle]] 内部槽表示的密钥作为 ek 输入参数。

  5. 如果 ML-KEM.Encaps 函数返回错误，则返回一个 OperationError。

  6. 令 result 为一个新的 EncapsulatedBits 字典。

  7. 将 result 的 sharedKey 属性 设置为创建 一个包含 sharedKey 的 ArrayBuffer 所得到的结果。

  8. 将 result 的 ciphertext 属性 设置为创建 一个包含 ciphertext 的 ArrayBuffer 所得到的结果。

  9. 返回 result。

6.3.2 解封装

  1. 如果 key 的 [[type]] 内部槽不是 "private"， 则抛出一个 InvalidAccessError。

  2. 使用 [FIPS-203] 第 7.3 节中描述的解封装输入检查，其中参数集由 algorithm 的 name 成员指示， 使用由 key 的 [[handle]] 内部槽表示的密钥作为 dk 输入参数，并使用 ciphertext 作为 c 输入参数。

    注

    如果有利于性能，可以为 CryptoKey 对象 缓存或预计算解封装密钥类型检查和哈希检查的结果。

  3. 如果解封装密钥检查失败，则返回一个 OperationError。

  4. 令 sharedKey 为执行 [FIPS-203] 第 7.3 节中描述的 ML-KEM.Decaps 函数所产生的输出， 其中参数集由 algorithm 的 name 成员指示， 使用由 key 的 [[handle]] 内部槽表示的密钥作为 dk 输入参数，并使用 ciphertext 作为 c 输入参数。

  5. 返回 sharedKey。

6.3.3 获取共享密钥长度

  1. 返回 256。

6.3.4 生成密钥

  1. 如果 usages 包含的某个条目不是 "encapsulateKey"、"encapsulateBits"、 "decapsulateKey" 或 "decapsulateBits" 之一， 则抛出一个 SyntaxError。

  2. 按照 [FIPS-203] 第 7.1 节中的描述生成一个 ML-KEM 密钥对， 其中参数集由 normalizedAlgorithm 的 name 成员指示。

    注

    为了能够导出种子 (d, z)， 需要将 d 和 z 作为所生成 密钥材料的一部分存储。

  3. 如果密钥生成步骤失败， 则抛出一个 OperationError。

  4. 令 algorithm 为一个新的 KeyAlgorithm 对象。

  5. 将 algorithm 的 name 属性设置为 normalizedAlgorithm 的 name 属性。

  6. 令 publicKey 为一个新的 CryptoKey， 表示所生成密钥对的封装密钥。

  7. 将 publicKey 的 [[type]] 内部槽设置为 "public"。

  8. 将 publicKey 的 [[algorithm]] 内部 槽设置为 algorithm。

  9. 将 publicKey 的 [[extractable]] 内部 槽设置为 true。

  10. 将 publicKey 的 [[usages]] 内部槽设置为 usages 与 [ "encapsulateKey", "encapsulateBits" ] 的 用法 交集。

  11. 令 privateKey 为一个新的 CryptoKey， 表示所生成密钥对的解封装密钥。

  12. 将 privateKey 的 [[type]] 内部槽设置为 "private"。

  13. 将 privateKey 的 [[algorithm]] 内部 槽设置为 algorithm。

  14. 将 privateKey 的 [[extractable]] 内部 槽设置为 extractable。

  15. 将 privateKey 的 [[usages]] 内部槽设置为 usages 与 [ "decapsulateKey", "decapsulateBits" ] 的 用法 交集。

  16. 令 result 为一个新的 CryptoKeyPair 字典。

  17. 将 result 的 publicKey 属性 设置为 publicKey。

  18. 将 result 的 privateKey 属性 设置为 privateKey。

  19. 返回 result。

6.3.5 导入密钥

  1. 令 keyData 为要导入的密钥数据。

  2. 如果 format 为 "spki"：

    1. 如果 usages 包含的某个条目不是 "encapsulateKey" 或 "encapsulateBits"， 则抛出一个 SyntaxError。

    2. 令 spki 为在 keyData 上运行 解析 subjectPublicKeyInfo 算法的结果。

    3. 如果解析期间发生错误， 则抛出一个 DataError。

    4. 如果 normalizedAlgorithm 的 name 成员为 "ML-KEM-512"：

      令 expectedOid 为 id-alg-ml-kem-512 (2.16.840.1.101.3.4.4.1)。

      如果 normalizedAlgorithm 的 name 成员为 "ML-KEM-768"：

      令 expectedOid 为 id-alg-ml-kem-768 (2.16.840.1.101.3.4.4.2)。

      如果 normalizedAlgorithm 的 name 成员为 "ML-KEM-1024"：

      令 expectedOid 为 id-alg-ml-kem-1024 (2.16.840.1.101.3.4.4.3)。

      否则：

      抛出一个 NotSupportedError。

    5. 如果 spki 的 algorithm AlgorithmIdentifier 字段中的 algorithm 对象标识符字段 不等于 expectedOid， 则抛出一个 DataError。

    6. 如果 spki 的 algorithm AlgorithmIdentifier 字段中的 parameters 字段存在， 则抛出一个 DataError。

    7. 令 publicKey 为由 spki 的 subjectPublicKey 字段标识的 ML-KEM 公钥。

    8. 令 key 为一个新的 CryptoKey， 表示 publicKey。

    9. 将 key 的 [[type]] 内部槽 设置为 "public"

    10. 令 algorithm 为一个新的 KeyAlgorithm。

    11. 将 algorithm 的 name 属性设置为 normalizedAlgorithm 的 name 属性。

    12. 将 key 的 [[algorithm]] 内部槽设置为 algorithm。

    如果 format 为 "pkcs8"：

    1. 如果 usages 包含的某个条目不是 "decapsulateKey" 或 "decapsulateBits"， 则抛出一个 SyntaxError。

    2. 令 privateKeyInfo 为在 keyData 上运行 解析 privateKeyInfo 算法的结果。

    3. 如果解析期间发生错误， 则抛出一个 DataError。

    4. 如果 normalizedAlgorithm 的 name 成员为 "ML-KEM-512"：

      令 expectedOid 为 id-alg-ml-kem-512 (2.16.840.1.101.3.4.4.1)。

      令 asn1Structure 为 ASN.1 ML-KEM-512-PrivateKey 结构。

      如果 normalizedAlgorithm 的 name 成员为 "ML-KEM-768"：

      令 expectedOid 为 id-alg-ml-kem-768 (2.16.840.1.101.3.4.4.2)。

      令 asn1Structure 为 ASN.1 ML-KEM-768-PrivateKey 结构。

      如果 normalizedAlgorithm 的 name 成员为 "ML-KEM-1024"：

      令 expectedOid 为 id-alg-ml-kem-1024 (2.16.840.1.101.3.4.4.3)。

      令 asn1Structure 为 ASN.1 ML-KEM-1024-PrivateKey 结构。

      否则：

      抛出一个 NotSupportedError。

    5. 如果 privateKeyInfo 的 privateKeyAlgorithm PrivateKeyAlgorithm 字段中的 algorithm 对象标识符字段 不等于 expectedOid， 则抛出一个 DataError。

    6. 如果 privateKeyInfo 的 privateKeyAlgorithm PrivateKeyAlgorithmIdentifier 字段中的 parameters 字段存在， 则抛出一个 DataError。

    7. 令 mlKemPrivateKey 为执行 解析 ASN.1 结构 算法的结果，其中将 data 设为 privateKeyInfo 的 privateKey 字段，将 structure 设为 asn1Structure，并将 exactData 设置为 true。

    8. 如果解析期间发生错误， 则抛出一个 DataError。

    9. 如果 mlKemPrivateKey 表示采用 expandedKey 格式的 ML-KEM 密钥， 或者如果 mlKemPrivateKey 表示采用 both 格式的 ML-KEM 密钥 且不支持 both 格式，则抛出一个 NotSupportedError。

    10. 如果 mlKemPrivateKey 表示采用 both 格式的 ML-KEM 密钥， 且 seed 字段与 expandedKey 字段不对应， 则抛出一个 DataError。

    11. 令 key 为一个新的 CryptoKey， 表示由 mlKemPrivateKey 标识的 ML-KEM 私钥。

    12. 将 key 的 [[type]] 内部槽 设置为 "private"

    13. 令 algorithm 为一个新的 KeyAlgorithm。

    14. 将 algorithm 的 name 属性设置为 normalizedAlgorithm 的 name 属性。

    15. 将 key 的 [[algorithm]] 内部槽设置为 algorithm。

    如果 format 为 "raw-public"：

    1. 如果 usages 包含的某个条目不是 "encapsulateKey" 或 "encapsulateBits"， 则抛出一个 SyntaxError。

    2. 令 data 为 keyData。

    3. 令 key 为一个新的 CryptoKey， 表示 data 中的 ML-KEM 公钥数据。

    4. 将 key 的 [[type]] 内部槽 设置为 "public"

    5. 令 algorithm 为一个新的 KeyAlgorithm。

    6. 将 algorithm 的 name 属性设置为 normalizedAlgorithm 的 name 属性。

    7. 将 key 的 [[algorithm]] 内部槽设置为 algorithm。

    如果 format 为 "raw-seed"：

    1. 如果 usages 包含的某个条目不是 "decapsulateKey" 或 "decapsulateBits"， 则抛出一个 SyntaxError。

    2. 令 data 为 keyData。

    3. 如果 data 的位长度不是 512， 则抛出一个 DataError。

    4. 令 privateKey 为执行 [FIPS-203] 第 6.1 节中描述的 ML-KEM.KeyGen_internal 函数的结果， 其中参数集由 normalizedAlgorithm 的 name 成员指示， 使用 data 的前 256 位作为 d，并使用 data 的后 256 位作为 z。

    5. 令 key 为一个新的 CryptoKey， 表示由 privateKey 标识的 ML-KEM 私钥。

    6. 将 key 的 [[type]] 内部槽 设置为 "private"

    7. 令 algorithm 为一个新的 KeyAlgorithm。

    8. 将 algorithm 的 name 属性设置为 normalizedAlgorithm 的 name 属性。

    9. 将 key 的 [[algorithm]] 内部槽设置为 algorithm。

    如果 format 为 "jwk"：
    问题 1

    ML-KEM 的 JWK 格式尚未标准化，因此可能会发生变化。

    1. 如果 keyData 是一个 JsonWebKey 字典：

      令 jwk 等于 keyData。

      否则：

      抛出一个 DataError。

    2. 如果 jwk 的 priv 字段存在， 并且 usages 包含的某个条目不是 "decapsulateKey" 或 "decapsulateBits"， 则抛出一个 SyntaxError。

    4. 如果 jwk 的 kty 字段不是 "AKP"， 则抛出一个 DataError。

    5. 如果 jwk 的 alg 字段不是 [draft-ietf-jose-pqc-kem-05] 第 8 节（图 1 或 2）中指示的、与 normalizedAlgorithm 的 name 成员对应的 alg 值之一，则抛出一个 DataError。

      例如，ML-KEM-512 和 ML-KEM-512+A128KW 是 ML-KEM-512 的有效 "alg" 值。

    6. 如果 usages 非空且 jwk 的 use 字段存在 且不等于 "enc"，则抛出一个 DataError。

    7. 如果 jwk 的 key_ops 字段存在，并且 根据 JSON Web Key [JWK] 的要求无效，或者它未包含 所有指定的 usages 值， 则抛出一个 DataError。

    8. 如果 jwk 的 ext 字段存在且 值为 false，并且 extractable 为 true， 则抛出一个 DataError。

    9. 如果 jwk 的 priv 字段存在：

      1. 如果 jwk 的 priv 属性不包含有效的 base64url 编码种子， 该种子表示一个 ML-KEM 私钥， 则抛出 一个 DataError。

      2. 令 key 为一个新的 CryptoKey 对象，该对象表示 通过将 jwk 的 priv 属性解释为 base64url 编码种子 所标识的 ML-KEM 私钥。

      3. 将 key 的 [[type]] 内部槽设置为 "private"。

      4. 如果 jwk 的 pub 属性不包含表示与 key 对应的 ML-KEM 公钥的 base64url 编码公钥， 则抛出 一个 DataError。

      否则：

      1. 如果 jwk 的 pub 属性不包含有效的 base64url 编码公钥， 该公钥表示一个 ML-KEM 公钥， 则抛出 一个 DataError。

      2. 令 key 为一个新的 CryptoKey 对象，该对象表示 通过将 jwk 的 pub 属性解释为 base64url 编码公钥 所标识的 ML-KEM 公钥。

      3. 将 key 的 [[type]] 内部槽设置为 "public"。

    10. 令 algorithm 为一个新的 KeyAlgorithm 对象实例。

    11. 将 algorithm 的 name 属性设置为 normalizedAlgorithm 的 name 成员。

    12. 将 key 的 [[algorithm]] 内部槽设置为 algorithm。

    否则：
    抛出一个 NotSupportedError。

  3. 返回 key。

6.3.6 导出密钥

  1. 令 key 为要导出的 CryptoKey。

  2. 如果无法访问由 key 的 [[handle]] 内部槽表示的底层密码密钥材料， 则抛出一个 OperationError。

  3. 如果 format 为 "spki"：

    1. 如果 key 的 [[type]] 内部槽不是 "public"， 则抛出一个 InvalidAccessError。

    2. 令 keyAlgorithm 为 key 的 [[algorithm]] 内部槽。

    3. 令 data 为 [RFC5280] 中定义的 SubjectPublicKeyInfo ASN.1 结构的一个实例，具有以下属性：

      • 将 algorithm 字段设置为一个 AlgorithmIdentifier ASN.1 类型，具有以下 属性：

        • 如果 keyAlgorithm 的 name 成员为 "ML-KEM-512"：

          将 algorithm 对象标识符设置为 id-alg-ml-kem-512 (2.16.840.1.101.3.4.4.1) OID。

          如果 keyAlgorithm 的 name 成员为 "ML-KEM-768"：

          将 algorithm 对象标识符设置为 id-alg-ml-kem-768 (2.16.840.1.101.3.4.4.2) OID。

          如果 keyAlgorithm 的 name 成员为 "ML-KEM-1024"：

          将 algorithm 对象标识符设置为 id-alg-ml-kem-1024 (2.16.840.1.101.3.4.4.3) OID。

          否则：

          抛出 一个 NotSupportedError。

      • 将 subjectPublicKey 字段设置为 keyData。

    4. 令 result 为对 data 进行 DER 编码的结果。

7. ML-DSA

7.1 描述

本节不具规范性。

本节描述了如何按照 [FIPS-204] 的规定， 使用 ML-DSA 进行签名和验证。

7.2 注册

此算法的已识别算法 名称为 “ML-DSA-44”、“ML-DSA-65”和“ML-DSA-87”。

操作 参数 结果
sign ContextParams 字节 序列
verify ContextParams 布尔值
generateKey 无 CryptoKeyPair
importKey 无 CryptoKey
exportKey 无 对象

7.3 ContextParams 字典 

WebIDLdictionary ContextParams : Algorithm {
  BufferSource context;
};

context 成员表示要与消息 关联的可选上下文数据。

注

ContextParams 字典与 [webcrypto-secure-curves] 的 Ed448Params 字典相同，在合并本提案时，后者可以由前者替代。

7.4 操作

7.4.1 签名

  1. 如果 context 成员 normalizedAlgorithm 存在且其长度大于 255 字节，则抛出一个 OperationError。

  2. 如果 key 的 [[type]] 内部槽不是 "private"， 则抛出一个 InvalidAccessError。

  3. 令 context 为 normalizedAlgorithm 的 context 成员； 如果 normalizedAlgorithm 的 context 成员不存在， 则为空八位字节字符串。

  4. 令 result 为执行 [FIPS-204] 第 5.2 节中规定的 ML-DSA.Sign 签名算法所得的结果， 其中参数集由 normalizedAlgorithm 的 name 成员指示， 使用与 key 关联的 ML-DSA 私钥作为 sk， 使用 message 作为 M，并使用 context 作为 ctx。

  5. 如果 ML-DSA.Sign 算法返回错误，则返回一个 OperationError。

  6. 返回 result。

7.4.2 验证

  1. 如果 normalizedAlgorithm 的 context 成员 存在且其长度大于 255 字节，则抛出一个 OperationError。

  2. 如果 key 的 [[type]] 内部槽不是 "public"， 则抛出一个 InvalidAccessError。

  3. 令 context 为 normalizedAlgorithm 的 context 成员； 如果 normalizedAlgorithm 的 context 成员不存在， 则为空八位字节字符串。

  4. 令 result 为执行 [FIPS-204] 第 5.3 节中规定的 ML-DSA.Verify 验证算法所得的结果， 其中参数集由 normalizedAlgorithm 的 name 成员指示， 使用与 key 关联的 ML-DSA 公钥作为 pk， 使用 message 作为 M，使用 signature 作为 σ，并 使用 context 作为 ctx。

  5. 如果 ML-DSA.Verify 算法返回错误，则返回一个 OperationError。

  6. 返回 result。

7.4.3 生成密钥

  1. 如果 usages 包含不是 “sign”或“verify” 之一的条目，则抛出一个 SyntaxError。

  2. 按照 [FIPS-204] 第 5.1 节中的描述生成一个 ML-DSA 密钥对，其中使用 由 normalizedAlgorithm 的 name 成员指示的参数集。

    注

    为了能够导出种子 ξ， 需要将其作为生成的 密钥材料的一部分存储。

  3. 如果密钥生成步骤失败， 则抛出一个 OperationError。

  4. 令 algorithm 为一个新的 KeyAlgorithm 对象。

  5. 将 algorithm 的 name 属性设置为 normalizedAlgorithm 的 name 属性。

  6. 令 publicKey 为一个新的 CryptoKey， 它表示所生成密钥对的公钥。

  7. 将 publicKey 的 [[type]] 内部槽设置为“public”。

  8. 将 publicKey 的 [[algorithm]] 内部槽设置为 algorithm。

  9. 将 publicKey 的 [[extractable]] 内部槽设置为 true。

  10. 将 publicKey 的 [[usages]] 内部槽设置为 usages 与 [ "verify" ] 的用途 交集。

  11. 令 privateKey 为一个新的 CryptoKey， 它表示所生成密钥对的私钥。

  12. 将 privateKey 的 [[type]] 内部槽设置为“private”。

  13. 将 privateKey 的 [[algorithm]] 内部槽设置为 algorithm。

  14. 将 privateKey 的 [[extractable]] 内部槽设置为 extractable。

  15. 将 privateKey 的 [[usages]] 内部槽设置为 usages 与 [ "sign" ] 的用途 交集。

  16. 令 result 为一个新的 CryptoKeyPair 字典。

  17. 将 result 的 publicKey 属性设置为 publicKey。

  18. 将 result 的 privateKey 属性设置为 privateKey。

  19. 返回 result。

8.1 描述

本节不具规范性。

本节描述了如何按照 [FIPS-205] 的规定， 使用 SLH-DSA 进行签名和验证。

8.2 注册

此算法的已识别算法 名称为“SLH-DSA-SHA2-128s”、“SLH-DSA-SHAKE-128s”、 “SLH-DSA-SHA2-128f”、“SLH-DSA-SHAKE-128f”、 “SLH-DSA-SHA2-192s”、“SLH-DSA-SHAKE-192s”、 “SLH-DSA-SHA2-192f”、“SLH-DSA-SHAKE-192f”、 “SLH-DSA-SHA2-256s”、“SLH-DSA-SHAKE-256s”、 “SLH-DSA-SHA2-256f”和“SLH-DSA-SHAKE-256f”。

8.3 JSON Web Key 表示形式

SLH-DSA 密钥使用 [RFC9964] 中定义的“AKP”（算法密钥对）密钥类型进行 JWK 表示。“alg”（算法）参数标识具体的 SLH-DSA 参数集。 公钥包含在“pub”参数中。如果包含私钥，则使用“priv”参数表示。以 JWK 表示时，所有密钥参数均采用 base64url 编码。

8.4 操作

8.4.1 签名

  1. 如果 normalizedAlgorithm 的 context 成员 存在且其长度大于 255 字节，则抛出一个 OperationError。

  2. 如果 key 的 [[type]] 内部槽不是 "private"， 则抛出一个 InvalidAccessError。

  3. 令 context 为 normalizedAlgorithm 的 context 成员； 如果 normalizedAlgorithm 的 context 成员不存在， 则为空八位字节字符串。

  4. 令 result 为执行 slh_sign 签名算法所得的结果，该算法在 [FIPS-205] 第 10.2.1 节中规定， 其中参数集由 normalizedAlgorithm 的 name 成员指示， 使用与 key 关联的 SLH-DSA 私钥作为 SK， 使用 message 作为 M，并使用 context 作为 ctx。

  5. 如果 slh_sign 算法返回错误，则返回一个 OperationError。

  6. 返回 result。

8.4.2 验证

  1. 如果 key 的 [[type]] 内部槽不是 "public"， 则抛出一个 InvalidAccessError。

  2. 令 context 为 normalizedAlgorithm 的 context 成员； 如果 normalizedAlgorithm 的 context 成员不存在， 则为空八位字节字符串。

  3. 令 result 为执行 slh_verify 验证算法所得的结果，该算法在 [FIPS-205] 第 10.3 节中规定， 其中参数集由 normalizedAlgorithm 的 name 成员指示， 使用与 key 关联的 SLH-DSA 公钥作为 PK， 使用 message 作为 M，使用 signature 作为 SIG，并 使用 context 作为 ctx。

  4. 如果 slh_verify 算法返回错误，则返回一个 OperationError。

  5. 返回 result。

8.4.3 生成密钥

  1. 如果 usages 包含不是 “sign”或“verify” 之一的条目，则抛出一个 SyntaxError。

  2. 按照 [FIPS-205] 第 10.1 节中的描述生成一个 SLH-DSA 密钥对，其中使用 由 normalizedAlgorithm 的 name 成员指示的参数集。

  3. 如果密钥生成步骤失败， 则抛出一个 OperationError。

  4. 令 algorithm 为一个新的 KeyAlgorithm 对象。

  5. 将 algorithm 的 name 属性设置为 normalizedAlgorithm 的 name 属性。

  6. 令 publicKey 为一个新的 CryptoKey， 它表示所生成密钥对的公钥。

  7. 将 publicKey 的 [[type]] 内部槽设置为“public”。

  8. 将 publicKey 的 [[algorithm]] 内部槽设置为 algorithm。

  9. 将 publicKey 的 [[extractable]] 内部槽设置为 true。

  10. 将 publicKey 的 [[usages]] 内部槽设置为 usages 与 [ "verify" ] 的用途 交集。

  11. 令 privateKey 为一个新的 CryptoKey， 它表示所生成密钥对的私钥。

  12. 将 privateKey 的 [[type]] 内部槽设置为“private”。

  13. 将 privateKey 的 [[algorithm]] 内部槽设置为 algorithm。

  14. 将 privateKey 的 [[extractable]] 内部槽设置为 extractable。

  15. 将 privateKey 的 [[usages]] 内部槽设置为 usages 与 [ "sign" ] 的用途 交集。

  16. 令 result 为一个新的 CryptoKeyPair 字典。

  17. 将 result 的 publicKey 属性设置为 publicKey。

  18. 将 result 的 privateKey 属性设置为 privateKey。

  19. 返回 result。

    2. 令 data 为一个字节序列， 其中包含由 key 的 [[handle]] 内部槽所表示的 SLH-DSA 公钥。

    3. 令 result 为 data。

    如果 format 是“raw-private”：

    1. 如果 key 的 [[type]] 内部槽不是“private”， 则抛出一个 InvalidAccessError。

    2. 令 data 为一个字节序列， 其中包含由 key 的 [[handle]] 内部槽所表示的 SLH-DSA 私钥。

    3. 令 result 为 data。

    如果 format 是“jwk”：

    1. 令 jwk 为一个新的 JsonWebKey 字典。

    2. 令 keyAlgorithm 为 key 的 [[algorithm]] 内部槽。

    3. 将 jwk 的 kty 属性设置为 “AKP”。

    4. 将 jwk 的 alg 属性设置为 keyAlgorithm 的 name 成员。

    5. 将 jwk 的 pub 属性 设置为与 key 的 [[handle]] 内部槽对应的 base64url 编码公钥。

    6. 如果 key 的 [[type]] 内部槽是“private”：
      将 jwk 的 priv 属性 设置为由 key 的 [[handle]] 内部槽所表示的 base64url 编码私钥。

    7. 将 jwk 的 key_ops 属性设置为 key 的 usages 属性。

    8. 将 jwk 的 ext 属性设置为 key 的 [[extractable]] 内部槽。

    9. 令 result 为 jwk。

    否则：

    抛出一个 NotSupportedError。

  4. 返回 result。

9.1 描述

本节不具规范性。

“AES-OCB”算法标识符用于按照 [RFC7253] 中的描述， 使用 OCB 模式下的 AES 执行认证加密和解密。

9.2 注册

此算法的已识别算法名称 是“AES-OCB”。

操作 参数 结果

decrypt AeadParams 字节 序列
generateKey AesKeyGenParams CryptoKey
importKey 无 CryptoKey
exportKey 无 对象
get key length AesDerivedKeyParams 整数

9.3 AeadParams 字典 

WebIDLdictionary AeadParams : Algorithm {
  required BufferSource iv;
  BufferSource additionalData;
  [EnforceRange] octet tagLength;
};

iv 成员表示要使用的初始化向量。

additionalData 成员表示要包含的 附加认证数据。

9.4 操作

9.4.1 加密

  1. 如果 normalizedAlgorithm 的 iv 成员的长度大于 15 字节， 则抛出一个 OperationError。

  2. 如果 normalizedAlgorithm 中不存在 tagLength 成员：
    令 tagLength 为 128。
    如果 normalizedAlgorithm 的 tagLength 成员是 64、96 或 128 之一：
    令 tagLength 等于 normalizedAlgorithm 的 tagLength 成员
    否则：
    抛出一个 OperationError。

  3. 如果 normalizedAlgorithm 中存在 additionalData 成员， 则令 additionalData 为该成员；否则令其为空八位字节 字符串。

  4. 令 C 为使用 AES 作为 分组密码，执行 [RFC7253] 第 4.2 节中描述的 OCB-ENCRYPT 函数所得的输出，其中使用 key 的 [[handle]] 内部槽所表示的密钥作为 K 输入参数， 使用 normalizedAlgorithm 的 iv 成员作为 N 输入参数， 使用 additionalData 作为 A 输入参数， 使用 plaintext 作为 P 输入参数，并 使用 tagLength 作为 TAGLEN 全局参数。

  5. 返回 C。

9.4.2 解密

  1. 如果 normalizedAlgorithm 的 iv 成员的长度大于 15 字节， 则抛出一个 OperationError。

  2. 如果 normalizedAlgorithm 中不存在 tagLength 成员：
    令 tagLength 为 128。
    如果 normalizedAlgorithm 的 tagLength 成员是 64、96 或 128 之一：
    令 tagLength 等于 normalizedAlgorithm 的 tagLength 成员
    否则：
    抛出一个 OperationError。

  3. 如果 ciphertext 的长度小于 tagLength 比特， 则抛出一个 OperationError。

  4. 如果 normalizedAlgorithm 中存在 additionalData 成员， 则令 additionalData 为该成员；否则令其为空八位字节 字符串。

  5. 使用 AES 作为分组密码，执行 [RFC7253] 第 4.3 节中描述的 OCB-DECRYPT 函数，其中使用 key 的 [[handle]] 内部槽所表示的密钥作为 K 输入参数， 使用 normalizedAlgorithm 的 iv 成员作为 N 输入参数， 使用 additionalData 作为 A 输入参数， 使用 ciphertext 作为 C 输入参数，并 使用 tagLength 作为 TAGLEN 全局参数。

    如果算法结果是表示认证失败的 “INVALID”：
    抛出一个 OperationError
    否则：
    令 plaintext 为 OCB-DECRYPT 的输出 P。

  6. 返回 plaintext。

9.4.3 生成密钥

  1. 如果 usages 包含不是 “encrypt”、“decrypt”、 “wrapKey”或“unwrapKey” 之一的条目，则抛出一个 SyntaxError。

  2. 如果 normalizedAlgorithm 的 length 成员不等于 128、192 或 256 之一， 则抛出一个 OperationError。

  3. 生成一个长度等于 normalizedAlgorithm 的 length 成员的 AES 密钥。

  4. 如果密钥生成步骤失败， 则抛出一个 OperationError。

  5. 令 key 为一个新的 CryptoKey 对象，表示所生成的 AES 密钥。

  6. 将 key 的 [[type]] 内部槽设置为“secret”。

  7. 令 algorithm 为一个新的 AesKeyAlgorithm。

  8. 将 algorithm 的 name 属性设置为“AES-OCB”。

  9. 将 algorithm 的 length 属性设置为等于 normalizedAlgorithm 的 length 成员。

  10. 将 key 的 [[algorithm]] 内部槽设置为 algorithm。

  11. 将 key 的 [[extractable]] 内部槽设置为 extractable。

  12. 将 [[usages]] 内部槽 key 设置为 规范化值 usages 的值。

  13. 返回 key。

9.4.4 导入密钥

  1. 令 keyData 为要导入的密钥数据。

  2. 如果 usages 包含不是 “encrypt”、“decrypt”、 “wrapKey”或“unwrapKey” 之一的条目，则抛出一个 SyntaxError。

  3. 如果 format 是“raw-secret”：

    1. 令 data 为 keyData。

    2. 如果 data 的比特长度不是 128、192 或 256， 则抛出一个 DataError。

    如果 format 是“jwk”：
    1. 如果 keyData 是一个 JsonWebKey 字典：

      令 jwk 等于 keyData。

      否则：

      抛出一个 DataError。

    2. 如果 jwk 的 kty 字段不是 “oct”， 则抛出一个 DataError。

    3. 如果 jwk 不符合 JSON Web Algorithms [JWA] 第 6.4 节的要求， 则抛出一个 DataError。

    4. 令 data 为通过解码 jwk 的 k 字段获得的字节序列。

    5. 如果 data 的长度为 128 比特：
      如果 jwk 中存在 alg 字段，并且该字段不是“A128OCB”， 则抛出一个 DataError。
      如果 data 的长度为 192 比特：
      如果 jwk 中存在 alg 字段，并且该字段不是“A192OCB”， 则抛出一个 DataError。
      如果 data 的长度为 256 比特：
      如果 jwk 中存在 alg 字段，并且该字段不是“A256OCB”， 则抛出一个 DataError。
      否则：
      抛出一个 DataError。

    6. 如果 usages 非空，且 jwk 中存在 use 字段，并且该字段不是“enc”， 则抛出一个 DataError。

    7. 如果 jwk 中存在 key_ops 字段，并且 根据 JSON Web Key [JWK] 的要求 该字段无效，或者不包含所有指定的 usages 值， 则抛出一个 DataError。

    抛出一个 NotSupportedError。

  4. 令 key 为一个新的 CryptoKey 对象，表示值为 data 的 AES 密钥。

  5. 将 key 的 [[type]] 内部槽设置为“secret”。

  6. 令 algorithm 为一个新的 AesKeyAlgorithm。

  7. 将 algorithm 的 name 属性设置为“AES-OCB”。

  8. 将 algorithm 的 length 属性设置为 data 的比特长度。

  9. 将 key 的 [[algorithm]] 内部槽设置为 algorithm。

  10. 返回 key。

9.4.5 导出密钥

  1. 如果无法访问 key 的 [[handle]] 内部槽所表示的底层密码密钥材料， 则抛出一个 OperationError。

  2. 如果 format 是“raw-secret”：

    1. 令 data 为一个字节序列， 其中包含由 key 的 [[handle]] 内部槽所表示的密钥的原始八位字节。

    2. 令 result 为 data。

    如果 format 是“jwk”：

    1. 令 jwk 为一个新的 JsonWebKey 字典。

    2. 将 jwk 的 kty 属性设置为 字符串“oct”。

    3. 将 jwk 的 k 属性设置为一个字符串，其中包含由 key 的 [[handle]] 内部槽所表示的密钥的原始八位字节，并按照 JSON Web Algorithms [JWA] 第 6.4 节进行编码。

    4. 如果 key 的 length 属性为 128：
      将 jwk 的 alg 属性设置为 字符串“A128OCB”。
      如果 key 的 length 属性为 192：
      将 jwk 的 alg 属性设置为 字符串“A192OCB”。
      如果 key 的 length 属性为 256：
      将 jwk 的 alg 属性设置为 字符串“A256OCB”。

    5. 将 jwk 的 key_ops 属性设置为等于 key 的 usages 属性。

    6. 将 jwk 的 ext 属性设置为等于 key 的 [[extractable]] 内部槽。

    7. 令 result 为 jwk。

    否则：

    抛出一个 NotSupportedError。

  3. 返回 result。

9.4.6 获取密钥长度

  1. 如果 normalizedDerivedKeyAlgorithm 的 length 成员不是 128、192 或 256，则抛出一个 OperationError。

  2. 返回 normalizedDerivedKeyAlgorithm 的 length 成员。

13. TurboSHAKE

13.1 描述

本节不具规范性。

本节描述了 [RFC9861] 中规定的 TurboSHAKE128 和 TurboSHAKE256。

TurboSHAKE 是一个可扩展输出函数（XOF）族，它基于 SHA-3 中所用 Keccak 置换的减少轮数版本，因此 在保持相同安全强度的同时，其速度大约是 SHAKE 函数的两倍。

注

为实现 128 位碰撞安全性，TurboSHAKE128 的输出应至少为 256 位。 为实现 256 位碰撞安全性，TurboSHAKE256 的输出应至少为 512 位。 这些输出长度也超过了相应的原像和第二原像安全性 要求（这些要求只要求输出长度等于目标安全级别）。 当输出长度达到这些阈值时，TurboSHAKE128 可达到 NIST 后量子 安全级别 2，而 TurboSHAKE256 可达到级别 5。 请参阅 [RFC9861] 第 7 节。

注

尽管从技术上可以实现，但在 digest() 之外将 TurboSHAKE 用作其他算法的一部分 （例如用于 HMAC 的 hash 参数） 不太可能有用，也不预期会得到支持。 supports() 的结果应 反映是否支持此类用法。

13.2 注册

已识别算法 名称是 “TurboSHAKE128”和 “TurboSHAKE256”。

操作 参数 结果
digest TurboShakeParams 字节 序列

13.3 TurboShakeParams 字典

14. KangarooTwelve

14.1 描述

本节不具规范性。

本节描述了 [RFC9861] 中规定的 KT128 和 KT256。

KangarooTwelve 是一个可扩展输出函数（XOF）族，它在 TurboSHAKE 之上应用树哈希，从而能够并行处理输入数据。 KT128 在内部使用 TurboSHAKE128，而 KT256 使用 TurboSHAKE256。

注

为实现 128 位碰撞安全性，KT128 的输出应至少为 256 位。 为实现 256 位碰撞安全性，KT256 的输出应至少为 512 位。 这些输出长度也超过了相应的原像和第二原像安全性 要求（这些要求只要求输出长度等于目标安全级别）。 当输出长度达到这些阈值时，KT128 可达到 NIST 后量子 安全级别 2，而 KT256 可达到级别 5。 请参阅 [RFC9861] 第 7 节。

注

尽管从技术上可以实现，但在 digest() 之外将 KangarooTwelve 用作其他算法的一部分 （例如用于 HMAC 的 hash 参数） 不太可能有用，也不预期会得到支持。 supports() 的结果应 反映是否支持此类用法。

14.2 注册

已识别算法 名称是 “KT128”和 “KT256”。

15.7.2 验证

  1. 如果 normalizedAlgorithm 中存在 customization 成员， 则令 customization 为该成员；否则令其为空八位字节 字符串。

  2. 如果 normalizedAlgorithm 的 name 成员与 “KMAC128”区分大小写地匹配：

  4. 如果 computedMac 等于 signature，则返回 true；否则 返回 false。 此比较必须以常量时间执行。

15.7.3 生成密钥

  1. 如果 usages 包含不是“sign”或 “verify”的条目，则抛出一个 SyntaxError。

  2. 如果 normalizedAlgorithm 中存在 length 成员：
    令 length 等于 normalizedAlgorithm 的 length 成员。
    否则，如果 normalizedAlgorithm 的 name 成员与 “KMAC128”区分大小写地匹配：
    令 length 为 128。
    否则，如果 normalizedAlgorithm 的 name 成员与 “KMAC256”区分大小写地匹配：
    令 length 为 256。

  3. 生成一个长度为 length 比特的密钥。

  4. 如果密钥生成步骤失败， 则抛出一个 OperationError。

  5. 令 key 为一个新的 CryptoKey 对象，表示所生成的 密钥。

  6. 将 key 的 [[type]] 内部槽设置为“secret”。

  7. 令 algorithm 为一个新的 KmacKeyAlgorithm。

  8. 将 algorithm 的 name 属性设置为 normalizedAlgorithm 的 name 成员。

  9. 将 algorithm 的 length 属性设置为 length。

  10. 将 key 的 [[algorithm]] 内部槽设置为 algorithm。

  11. 将 key 的 [[extractable]] 内部槽设置为 extractable。

  12. 将 [[usages]] 内部槽设置为 key 的 规范化值 usages。

  13. 返回 key。

15.7.4 导入密钥

  1. 令 keyData 为要导入的密钥数据。

  2. 如果 usages 包含不是 “sign”或“verify”的条目， 则抛出一个 SyntaxError。

  3. 如果 format 是“raw-secret”：

    1. 令 data 为 keyData。

    如果 format 是“jwk”：
    1. 如果 keyData 是一个 JsonWebKey 字典：

      令 jwk 等于 keyData。

      否则：

      抛出一个 DataError。

    2. 如果 jwk 的 kty 字段不是 “oct”， 则抛出一个 DataError。

    3. 如果 jwk 不符合 JSON Web Algorithms [JWA] 第 6.4 节的要求， 则抛出一个 DataError。

    4. 令 data 为通过解码 jwk 的 k 字段获得的字节序列。

    5. 如果 normalizedAlgorithm 的 name 成员与 “KMAC128”区分大小写地匹配：
      如果 jwk 中存在 alg 字段，并且该字段不是“K128”， 则抛出一个 DataError。
      如果 normalizedAlgorithm 的 name 成员与 “KMAC256”区分大小写地匹配：
      如果 jwk 中存在 alg 字段，并且该字段不是“K256”， 则抛出一个 DataError。

    6. 如果 usages 非空，且 jwk 中存在 use 字段，并且该字段不是“sig”， 则抛出一个 DataError。

    7. 如果 jwk 中存在 key_ops 字段，并且 根据 JSON Web Key [JWK] 的要求 该字段无效，或者不包含所有指定的 usages 值， 则抛出一个 DataError。

    8. 如果 jwk 中存在 ext 字段，并且 其值为 false，而 extractable 为 true， 则抛出一个 DataError。

    否则：
    抛出一个 NotSupportedError。

  4. 令 length 为 data 的比特长度。

  5. 如果 normalizedAlgorithm 中存在 length 成员：
    如果 normalizedAlgorithm 的 length 成员 大于 length：
    抛出一个 DataError。
    如果 normalizedAlgorithm 的 length 成员 小于或等于 length 减 8：
    抛出一个 DataError。
    否则：
    将 length 设置为等于 normalizedAlgorithm 的 length 成员。

  6. 令 key 为一个新的 CryptoKey 对象，表示由 data 的前 length 比特组成的 KMAC 密钥。

  7. 将 key 的 [[type]] 内部槽设置为“secret”。

  8. 令 algorithm 为一个新的 KmacKeyAlgorithm。

  9. 将 algorithm 的 name 属性设置为 normalizedAlgorithm 的 name 成员。

  10. 将 algorithm 的 length 属性设置为 length。

  11. 将 key 的 [[algorithm]] 内部槽设置为 algorithm。

  12. 返回 key。

15.7.5 导出密钥

  1. 如果无法访问 key 的 [[handle]] 内部槽所表示的底层密码密钥材料， 则抛出一个 OperationError。

  2. 令 bits 为由 key 的 [[handle]] 内部槽所表示的密钥的原始比特。

  3. 令 data 为一个包含 bits 的字节序列。

  4. 如果 format 是“raw-secret”：

    1. 令 result 为 data。

    如果 format 是“jwk”：

    1. 令 jwk 为一个新的 JsonWebKey 字典。

    2. 将 jwk 的 kty 属性设置为 字符串“oct”。

    3. 将 jwk 的 k 属性设置为一个包含 data 的字符串，并按照 JSON Web Algorithms [JWA] 第 6.4 节进行编码。

    4. 令 keyAlgorithm 为 key 的 [[algorithm]] 内部槽。

    5. 如果 keyAlgorithm 的 name 成员是“KMAC128”：
      将 jwk 的 alg 属性设置为 字符串“K128”。
      如果 keyAlgorithm 的 name 成员是“KMAC256”：
      将 jwk 的 alg 属性设置为 字符串“K256”。

    6. 将 jwk 的 key_ops 属性设置为等于 key 的 usages 属性。

    7. 将 jwk 的 ext 属性设置为等于 key 的 [[extractable]] 内部槽。

    8. 令 result 为 jwk。

    否则：

    抛出一个 NotSupportedError。

  5. 返回 result。

15.7.6 获取密钥长度

  1. 如果 normalizedAlgorithm 中存在 length 成员：
    令 length 等于 normalizedAlgorithm 的 length 成员。
    否则，如果 normalizedAlgorithm 的 name 成员与 “KMAC128”区分大小写地匹配：
    令 length 为 128。
    否则，如果 normalizedAlgorithm 的 name 成员与 “KMAC256”区分大小写地匹配：
    令 length 为 256。

  2. 返回 length。

  11. 返回 result。

16.4.2 导入密钥

  1. 令 keyData 为要导入的密钥数据。

  2. 如果 format 不是“raw-secret”，则抛出一个 NotSupportedError

  6. 将 key 的 [[type]] 内部槽设置为“secret”。

  7. 令 algorithm 为一个新的 KeyAlgorithm 对象。

  8. 将 algorithm 的 name 属性设置为 normalizedAlgorithm 的 name 成员。

  9. 将 key 的 [[algorithm]] 内部槽设置为 algorithm。

  10. 返回 key。

16.4.3 获取密钥长度

  1. 返回 null。

18. 采用指南

本节不具规范性。

本规范定义了许多算法和操作。为了向 实现者提供指导，并加速 Web 平台的后量子迁移， 本节建议应优先实现哪些算法和 操作。

SubtleCrypto.supports 方法通过支持特性检测、优雅 回退和渐进增强，简化了本规范中其他所有算法和 操作的快速采用。

SubtleCrypto.getPublicKey 方法对于实际使用本规范和 [webcrypto] 中定义的非对称算法非常重要。它允许应用程序只存储私钥而不存储 对应的公钥，也无需验证私钥和 公钥确实对应，从而简化了密钥管理。此外，它允许库 作者接受不可提取的私钥作为协议的输入， 这些协议会将公钥值承诺到其输出中。

就算法而言，以下算法被认为是后量子迁移以及 在 Web 上启用现代密码协议的最高 优先级，按优先级顺序排列：

  1. ML-KEM 是 NIST 标准化的主要后量子密钥 封装机制 [FIPS-203]。 与传统密钥协商结合使用时，它能够实现混合 后量子/传统（PQ/T）密钥建立，如 [draft-ietf-hpke-hpke] 等协议及其 PQ 和 PQ/T 算法 [draft-ietf-hpke-pq] 中所采用的方式。
  2. ML-DSA 是 NIST 标准化的主要后量子数字 签名算法 [FIPS-204]。
  3. ChaCha20-Poly1305 是一种广泛 部署的 AEAD 密码 [RFC8439]，用于许多协议 （TLS、SSH、WireGuard、HPKE）。
  4. SHA-3 和 cSHAKE （具体为 SHA3-256 和 cSHAKE256）用于许多后量子 构造，包括 ML-KEM 密钥派生和混合 KEM 组合器。值得注意的是，在不提供任何自定义 参数的情况下调用 cSHAKE256，会产生与 SHAKE256 相同的输出，因此一个 实现即可同时满足自定义（cSHAKE256）和 非自定义（SHAKE256）用例。 但是，如果没有 cSHAKE 实现， SHAKE 实现仍可能有用，但必须确保在 customization 参数存在且 非空时抛出 NotSupportedError（并使 SubtleCrypto.supports 返回 false）。
  5. Argon2 是一种内存困难的基于密码的 密钥派生函数 [RFC9106]， 能够增强对高度并行化环境 （如 GPU 和 FPGA）中暴力破解攻击的抵抗能力。

SLH-DSA 是 NIST 标准化的一种无状态、基于哈希的数字 签名算法 [FIPS-204]。 目前它的采用程度 低于 ML-DSA，但如果需要 ML-DSA 的替代方案， 实现它可能会变得有用。

除此之外，AES-OCB、 TurboSHAKE、 KangarooTwelve 和 KMAC 都是有价值的补充，但对于 后量子迁移而言并不那么紧迫。

19. 使用示例

此示例在 Argon2 可用时使用 Argon2 从密码派生密钥，否则使用 PBKDF2； 然后在 AES-OCB 可用时使用 AES-OCB 通过该密钥加密和解密一些文本，否则使用 AES-GCM。

示例 1：使用从密码派生的密钥加密一些数据 
const password = 'correct horse battery staple';
const derivationAlg =
  SubtleCrypto.supports?.('importKey', 'Argon2id') ?
    'Argon2id' :
    'PBKDF2';
const encryptionAlg =
  SubtleCrypto.supports?.('importKey', 'AES-OCB') ?
    'AES-OCB' :
    'AES-GCM';
const passwordKey = await crypto.subtle.importKey(
  derivationAlg === 'Argon2id' ? 'raw-secret' : 'raw',
  new TextEncoder().encode(password),
  derivationAlg,
  /* 可提取： */ false,
  ['deriveKey']
);
const nonce = crypto.getRandomValues(new Uint8Array(16));
const derivationParams =
  derivationAlg === 'Argon2id' ?
    {
      nonce,
      parallelism: 4,
      memory: 2 ** 21,
      passes: 1
    } :
    {
      salt: nonce,
      iterations: 100_000,
      hash: 'SHA-256'
    };
const key = await crypto.subtle.deriveKey(
  {
    name: derivationAlg,
    ...derivationParams
  },
  passwordKey,
  {
    name: encryptionAlg,
    length: 256
  },
  /* 可提取： */ false,
  ['encrypt', 'decrypt']
);
const plaintext = 'Hello, world!';
const iv = crypto.getRandomValues(new Uint8Array(16));
const encrypted = await crypto.subtle.encrypt(
  { name: encryptionAlg, iv },
  key,
  new TextEncoder().encode(plaintext)
);
// 存储派生和加密算法及其参数
// 以及密文（例如存储在 IndexedDB 或数据库中），
// 并在以后检索它们。然后，使用原始参数和密码
// 派生密钥。此处我们立即使用同一个密钥对象
// 再次解密。
const decrypted = new TextDecoder().decode(await crypto.subtle.decrypt(
  { name: encryptionAlg, iv },
  key,
  encrypted
));
