摘要

本规范描述了一种数据模型，可用于描述一个或多个已识别 实体，例如一个或多个人和/或组织，这些实体被认为会执行 特定操作，例如签发或验证可验证凭证。该 数据模型支持发布或直接共享此类 信息，提供一种可通过密码学验证并保护隐私的 机制，持有者可通过该机制证明其所使用 凭证对应的 实体在特定生态系统中受到认可。该 规范旨在与现有的“信任基础设施” 互操作，例如 X.509 证书颁发机构列表和 ETSI 信任服务列表，同时 支持使用可验证凭证构建新的去中心化生态系统。

1. 简介

可验证凭证 生态系统依赖于验证者 确定特定颁发者是否被认可执行 特定操作的能力，例如颁发某种类型的可验证凭证。 以往，这种确定通常通过 带外流程、双边协议或专有注册表完成，而这些方式 难以通过自动化方式发现、查询或推理。随着可验证凭证 越来越多地部署于教育、医疗保健、 金融服务和政府等领域，对一种标准化、可互操作的 机制来表达和传达对执行已知操作的实体的认可 已变得至关重要。如果没有这种机制，生态系统参与者 将被迫构建定制的“信任基础设施”，从而导致碎片化、 集成成本增加，并阻碍跨境和跨领域 互操作性。

本规范通过定义一种任何 实体都可以用来将认可信息作为可验证凭证 发布或共享的数据模型，以去中心化方式解决表达被认可实体 （例如个人和组织）及其执行的操作（例如颁发 和验证）这一难题。 该模型并不强制使用单一的中央注册表，而是允许 任何实体——政府机构、行业联盟、标准 组织，甚至个人——颁发 RecognizedEntityCredential，声明其知晓一个或多个 被认可执行特定操作的实体。此设计使由相互重叠、彼此竞争且互为补充的 “信任注册表”构成的网络能够共存， 允许生态系统参与者选择其信任的实体，并跨 多个注册表进行推理。本规范还支持 与现有“信任基础设施”互操作，例如 X.509 证书颁发机构列表 和 ETSI 信任服务列表，从而允许引用现有的被认可实体信息， 并将其组合到新的去中心化生态系统中。

本文基于可验证凭证数据 模型，定义 一种特定应用，而不是修改可验证凭证数据模型 v2.0 本身。 它利用 JSON-LD 的关联数据基础，在现有术语之外添加少量新的 类型和属性。因此，RecognizedEntityCredential 是一种普通的可验证凭证 — 使用与任何其他凭证相同的机制进行签发、出示和 验证。

有意了解本规范所支持的各种用例的读者， 建议阅读第 2. 用例节。 本文档其余部分按以下章节组织：

  • 第 2. 用例节描述了促成本规范 设计的一组用例。
  • 第 3. 数据模型节定义了核心数据模型，包括 RecognizedEntity、RecognizedAction 和 RecognizedEntityCredential 类型及其属性和完整示例。
  • 附录 A. 威胁模型讨论了与本规范实现者 相关的安全、隐私和市场竞争方面的考虑。

2. 用例

本节描述了促成本规范设计的 一组用例。

2.1 教育

某国家教育主管机构希望公布一组由其认可为 其管辖范围内合法机构的大学和学院。 该机构颁发单个被认可实体凭证，其中列出每个 被认可机构及其通用名称、法定名称、徽标和网站等 描述性信息。这使软件能够向相关方显示 关于被认可机构的可信信息——例如大学名称、徽标和网站——， 因为软件已通过自动化且可进行密码学验证的方式确认 该机构受到国家主管机构认可，而无需直接联系该主管机构。

2.2 生命事件记录

一个全国性的生命记录机构协会不仅希望公布其认可的 实体——例如城市、地区或省级机构——还希望公布 每个实体被认可可签发哪些特定的 可验证凭证。 例如，某个特定的地区办事处被认可可以为其 管辖区域签发出生证明、结婚证明和死亡证明。 该协会签发一个 认可实体凭证，其中 每个 认可实体 都与一个 认可操作 相关联，该操作描述 其可能签发的生命记录类型以及该记录所遵循的模式。 接收到出生证明的 验证者 随后既可以确认其 签发者 是一个 获认可的管辖机构，也可以确认该管辖机构被认可 可以签发该特定类型的生命记录。

2.3 跨境贸易

全球约 5000 万个贸易实体每年交换 大约 50 亿张商业发票。出口商将 商业发票作为可验证凭证 颁发，并将其发送给进口商。 随后，进口商将该发票提交给进口海关机构 以办理边境清关，并提交给贸易融资贷款机构以办理跟单信用证 结算。海关机构和贷款机构均不与 出口商存在直接关系——它们通过进口商间接收到发票， 但必须确定出口商是否为合法 注册实体。

验证依赖于两个相互独立但彼此关联的凭证，它们在 不同时间颁发，并具有不同的生命周期：

  • 商业发票可验证 凭证，由出口商的 DID 颁发——每年颁发数十亿份，生命周期为数周至数月。
  • 出口经济体的国家商业登记机构向出口商颁发的 RecognizedEntityCredential——在任何时间均有数百万份有效，生命周期 从数年到数十年不等。

收到发票后，验证者解析出口商的 DID， 发现由国家商业登记机构颁发的关联 RecognizedEntityCredential， 并确认发票中的 DID 与该凭证的主体 相匹配。这使海关机构或贷款机构同时获得文档 完整性——发票未被篡改——和身份完整性—— 颁发者是 出口经济体中的注册实体——从而无需 事先了解出口商即可实现自动化边境清关和自动化贸易融资尽职调查。

2.4 产品合格评定

合格评定机构（CAB）将合格证书（CoC）作为 一项可验证凭证 颁发，用于证明 特定产品的安全或质量性能。CoC 随产品通过供应链进入 进口市场。然而，进口 国的市场监管机构通常与 CAB 不存在直接关系，也无法 独立确定该证书是否由真正 获得认可的检测实验室颁发。

当出口国的国家认可机构向 CAB 颁发 RecognizedEntityCredential——证明 CAB 的认可 范围——时，便可以建立一条关联的验证链，类似于上述 跨境贸易用例：

  • 合格证书可验证 凭证，由 CAB 的 DID 颁发，声明产品符合特定安全或质量标准。
  • 国家认可机构向 CAB 颁发的 RecognizedEntityCredential，证明 CAB 获得认可，可在 规定范围内执行合格评定。

收到 CoC 后，市场监管机构解析 CAB 的 DID，发现由国家 认可机构颁发的关联 RecognizedEntityCredential，并确认该证书中的 DID 与该凭证的主体相匹配。这使该机构同时获得文档 完整性——CoC 未被篡改——和身份完整性—— 颁发者是 真正获得认可的 CAB——从而无需人工验证 CAB 的认可状态， 即可在边境对货物进行预先清关。

2.5 联合标识符

常见用途中存在多个联合标识符示例。 国际标准书号（ISBN）、法人实体标识符（LEI）、 运输集装箱的 BIC 编号，以及互联网域名系统。在 每种情况下，中央机构都会向注册机构分配一个前缀，注册机构随后会向 第三方分配一段扩展该原始前缀的标识符范围。该 第三方随后可以进一步扩展字符串，以创建完整的 标识符。

当凭证中提供此类标识符时，依赖方可能希望 验证该标识符是否由联合标识符 方案所有者所知的参与方，完全按照其操作程序构建。

此类方案的一个示例是 GS1，该组织为世界上许多 条形码提供支持。其用例的详细说明见 [可验证 凭证用例](https://www.w3.org/TR/vc-use-cases/#chain-of-gs1-credentials-to-identify-a-trade-item) 文档 [vc-use-cases]。

3. 数据模型

以下各节概述了本规范用于 可验证颁发者和验证者列表的数据模型。

本节所述的数据模型是利用为本文评估的 各种现有技术的输入构建的，包括 EBSI 可信颁发者注册表、ETSI TS 119 612、eSSIF-Lab TRAIN、Trust over IP Foundation 信任注册表协议以及 Rebooting the Web of Trust 输入 文档。本节所述的数据模型能够表达 这些其他规范中描述的许多概念，但并非全部概念。

本项工作的统一数据模型可以表示为服务提供商列表， 这些服务提供商表示提供凭证颁发或验证等服务的 实体或组织。该数据模型还包括 列表运营者说明的详细信息。

3.1 通用属性

本节中的属性可以添加到第 3.4 RecognizedEntityCredential节所定义的 RecognizedEntityCredential 中的对象。本节列出的每个通用属性 均为OPTIONAL；颁发者无需提供任何这些值。

属性 描述
id 以全局无歧义方式标识实体的 URL。此属性的值 在 第 4.4 节：标识符 中定义，该节属于可验证凭证数据模型 v2.0规范。
type 实体的类型。此属性的值在 第 4.5 节：类型 中定义，该节属于可验证凭证数据模型 v2.0规范。如果该实体是可验证 凭证的颁发者，则 type 属性MUST为 RecognizedIssuer。
name 实体的人类可读名称。此属性的值在 第 4.6 节：名称 和描述 中定义，该节属于可验证凭证数据模型 v2.0规范。
legalName 组织或实体向法律 主管机构注册的正式法定名称，该名称可能与常用名称不同。该值MUST为 字符串。
image 指向实体视觉表示的链接，例如徽标、照片或 图标。该值MUST为URL，其中包括使用 [RFC2397] 中所述 data: URL 方案的值。
url 指向与该实体关联的主要网站或 Web 资源的 URL。该值MUST为URL。
sameAs 一个或多个在其他上下文或系统中引用同一实体的 URL， 从而能够跨不同平台进行交叉引用和验证。 每个值MUST为URL。
description 提供实体详细信息的人类可读描述。此属性的值 在 第 4.6 节：名称 和描述 中定义，该节属于可验证凭证数据模型 v2.0规范。
digestMultibase 用于验证与实体关联的资源完整性的一个或多个密码学摘要。 此属性的值在 第 5.3 节：相关资源的完整性 中定义，该节属于可验证凭证数据模型 v2.0规范。

3.2 RecognizedEntity

被认可实体是由 RecognizedEntityCredential 的颁发者认可 执行特定操作的任何实体。

属性 描述
id 以全局无歧义方式标识实体的 URL。此属性的值 在 第 4.4 节：标识符 中定义，该节属于可验证凭证数据模型 v2.0规范。
type type 属性MUST为 RecognizedEntity。此属性的值 在 第 4.5 节：类型 中定义，该节属于可验证凭证数据模型 v2.0规范。
recognizedTo 第 3.3 RecognizedAction节中定义的、 被认可实体预期执行的 特定操作。如果该被认可实体预期执行多个 操作，则此属性可以出现多次。
recognizedIn 一个对象，其中包含对认可实体文档的引用，该文档包含此特定的 认可实体，以及 已知其可以执行的操作。该对象的 id 值必须是一个 URL。该 对象的 type 值必须符合 可验证凭证数据模型 v2.0 规范中定义的 类型值空间，并且应该为 ExternalEntityList 或 RecognizedEntityCredential。

除上述属性外，还可以包含第 3.1 通用属性节中的属性。

recognizedIn 条目中 type 属性的值为 ExternalEntityList 时，应该符合 有效的实体列表规范。在这种情况下，由 id 属性引用的列表 URL 的源确立该列表的信任根。 这方面的示例包括 X.509 证书颁发机构列表，如 互联网 X.509 公钥基础设施证书和证书吊销列表（CRL）配置文件 中所规定的，以及欧盟 ETSI 信任服务列表，如 电子 签名和基础设施（ESI）；可信列表 中所规定的。 对于 ExternalEntityList 类型，验证者和 凭证 消费者需要获取由 id 属性引用的 实体列表资源，以确定该资源所符合的实体列表 规范， 确定其是否支持该规范，并据此进行处理/终止。 type 属性值为 RecognizedEntityCredential 的列表必须符合 认可实体 v1.0。

3.3 RecognizedAction

被认可操作是 被认可实体预期执行的操作。

属性 描述
type type 属性必须为 RecognizedAction。
action 一个字符串，用于 指定要执行的操作名称，例如 issue 或 verify。
recognizedBy 一个URL，或包含第 3.1 通用属性中属性的对象，用于表示 执行认可任务的实体。
outputValidation outputValidation 属性的值必须为一个或多个数据 模式，为验证者提供足够的 信息，以确定 所提供的数据是否符合所提供的模式。每个验证器必须 指定其 type（例如 JsonSchema）以及一个 id 属性，该属性必须为一个用于 标识模式文件的URL。 具体的类型定义决定每个数据模式的确切 内容。如果存在多个模式，则有效性 根据每个相关 type 属性所规定的处理规则来确定。
validFrom 认可操作有效的最早时间点，也 就是认可实体被认可 执行该操作的起始日期和时间。该值必须为一个 XML Schema dateTime 值，以 UTC 表示且不包含亚秒精度，例如 2025-01-01T00:00:00Z。此属性为可选；如果 不存在，则应用外层认可实体凭证的有效 期限。

3.4 RecognizedEntityCredential

发布被认可实体凭证 时，该凭证MUST是 可验证凭证数据模型 v2.0中定义的符合要求的可验证凭证， 并表达下一节中规定的数据模型。 它描述了封装被认可实体的可验证凭证 的格式。

被认可实体在可验证凭证中表达， 使持有者能够将其直接提供给 验证者。这种 有时称为“证书装订”的机制，通过确保 验证者无需联系 颁发者 来检索被认可实体凭证，从而增强 持有者的隐私。 尽管如此，验证者仍可能 选择忽略由持有者提供的被认可实体凭证，即使 可以验证其真实性，例如验证者希望获取更新版本的 被认可实体 凭证时。

属性 描述
id 包含一组被认可实体的可验证 凭证MAY 表达一个 id 属性，以便其他系统更容易检索该凭证。

validUntil 凭证保持有效的最晚时间点。此属性 在可验证凭证数据模型规范的 第 4.6 节：有效期中定义。

4. 算法

本节描述验证者在处理 本规范定义的可验证 凭证和被认可实体凭证时可以使用的 算法。

4.1 基于凭证的发现

基于凭证的发现是指这样一个过程： 一个 从未知签发者 接收到可验证凭证的 验证者找到一个 认可该 认可实体凭证，该凭证认可该 签发者，并且在 必要时，沿着认可实体凭证的层次结构向上遍历，直到到达 一个其自身签发者已被验证者 认可的凭证。

该机制依赖于 recognizedIn 属性。当该属性出现在 可验证凭证的 issuer 对象上时， 包括出现在认可实体凭证的 issuer 对象 上时，recognizedIn 属性引用一个 认可实体的可验证凭证， 其中将该签发者列为一个 认可实体。验证者可以获取所引用的 可验证凭证 并检查该可验证凭证的 签发者。 如果验证者 认可该签发者， 则发现成功。如果不认可，验证者可以沿着已获取的可验证 凭证的 issuer 对象上的 recognizedIn 属性向层次结构上一级移动，并重复该过程，直到 到达其认可的签发者或达到配置的 限制。

持有者可以预先获取该层次结构中的认可实体凭证，并将它们与可验证凭证一起提供给 验证者， 使用第 3.4 RecognizedEntityCredential节中描述的“证书装订”机制。当持有者提供 这些 可验证 凭证时，验证者无需自行获取 它们， 前提是验证者对所提供 可验证 凭证的新鲜度感到满意。需要更新 信息的验证者 可以拒绝由持有者提供的可验证凭证 或忽略它们， 并直接获取认可实体 凭证。

为针对一组已配置的认可签发者 （recognizedIssuers）以及一组可选的由持有者提供的 可验证凭证 （providedDocuments），对一个可验证凭证 （credential）执行基于凭证的发现， 验证者运行 以下算法。成功时，该算法返回一个表示 认可链的列表；如果无法到达任何已认可的签发者，则返回 错误。

  1. 令 current 为 credential，并令 chain 为一个 空列表。
  2. 令 maxDepth 为验证者 被配置为遍历的最大认可链深度。如果 chain 的长度超过 maxDepth，则返回错误。
  3. 令 issuer 为 current 的 issuer 属性值，并令 issuerId 为其标识符。
  4. 如果 issuerId 是 recognizedIssuers 的成员，则将 current 追加到 chain 并返回 chain；发现 成功。
  5. 如果 issuer 不包含 recognizedIn 属性，则返回错误； 无法进一步遍历认可层次结构。
  6. 令 listReference 为 recognizedIn 属性的值，并令 listId 为其 id。
  7. 令 list 为由 listId 标识的认可实体凭证，如果 providedDocuments 中存在该凭证且足够新鲜，则从中获取，否则从 listId 获取。
  8. 验证 list 上的证明，确认它当前有效，并 确认 issuerId 作为一个认可实体的 id 出现在 list 的 credentialSubject 中。如果任何检查失败，则返回 错误。
  9. 将 current 追加到 chain，将 current 设置为 list，然后返回步骤 2，以评估该列表的签发者。

4.2 基于标识符的发现

基于标识符的发现是指这样一个过程： 一个 从未知签发者接收到可验证凭证的 验证者从该 签发者的标识符开始，将该标识符解析为 一个受控标识符 文档，并使用该 文档中声明的服务来检索一个可能包含 认可实体凭证的可验证 出示，该凭证认可该签发者。与 依赖于 issuer 对象上存在 recognizedIn 引用的基于凭证的发现不同，基于标识符的发现并不作此 假设；它转而通过解引用 签发者自身的 标识符来获取认可信息。

该机制依赖于签发者在可通过其标识符发现的 服务端点上发布认可 信息。签发者的 标识符通常表示为 issuer 对象的 id（例如 issuer.id），它是一个可以解析或解引用为 受控标识符 文档的URL，例如一个DID 文档。该文档 可以声明一个其 type 数组同时包含 WhoisService 和 PathService 的服务；该服务的 serviceEndpoint 标识 签发者 发布描述自身的可验证 出示的位置。所 发布的可验证 出示由该签发者签名，并包含 将该签发者的标识符作为 credentialSubject 的可验证凭证。 其中可以包含一个认可实体凭证，在 该凭证中，签发者 作为一个认可实体出现。

以这种方式获取认可实体 凭证的验证者 会完全按照基于凭证的发现中的方式对其进行处理。如果 验证者 认可该认可实体凭证的签发者，则发现 成功。如果不认可，并且该认可实体凭证在其自身的 issuer 对象上带有 recognizedIn 属性，则验证者可以 继续进行基于凭证的发现，以 遍历认可 层次结构，直到到达其认可的签发者。

下图从 验证者的 视角展示了基于标识符的发现 过程。在层次结构的每一级都会重复相同的步骤，直到到达一个已认可的 信任锚点。

要针对一组已配置的认可签发者 （recognizedIssuers），对一个基于标识符的发现执行 于一个可验证凭证 （credential）上的特定操作（action，例如 issue），一个验证者运行以下 算法。该 算法返回一个具有两个布尔结果的结果：recognized， 表示 credential 的签发者最终是否 被 recognizedIssuers 的某个成员认可，以及 actionRecognized，表示该签发者是否被认可 执行 action，以及当某个认可操作声明了 outputValidation 时，credential 是否符合它。成功时， 结果还包括用于建立该结果的认可链。

  1. 令 result 为一个结构，其中 recognized 设置为 false，actionRecognized 设置为 false，且 chain 设置 为 一个空列表。
  2. 令 issuer 为 credential 的 issuer 属性值，并令 issuerId 为其标识符。
  3. 解析或解引用 issuerId 以获取一个受控标识符 文档 idDocument。如果无法解析 issuerId， 则返回 result。
  4. 令 service 为 idDocument 的 service 数组中一个其 type 同时包含 WhoisService 和 PathService 的服务。如果不存在这样的服务，则返回 result； 此签发者不支持基于标识符的发现。
  5. 令 endpoint 为 service 的 serviceEndpoint，并 检索在 endpoint 发布的可验证 出示 presentation。如果检索失败，则返回 result。
  6. 验证 presentation 上的证明，并确认其绑定到 issuerId。如果验证失败，则返回 result。
  7. 令 candidates 为 presentation 中包含的认可实体凭证，其中 issuerId 作为 credentialSubject 中某个认可实体的 id 出现。如果 candidates 为空，则返回 result。
  8. 对 candidates 中的每个 list，验证 list 上的证明并确认它当前有效，丢弃任何 未通过任一检查的 list。
  9. 对每个有效的 list，令 anchor 为 确定 list 的签发者是否 被认可的结果：如果 list 的签发者 是 recognizedIssuers 的成员，则 anchor 是一个包含 list 的列表；否则，如果 list 的 issuer 对象包含 recognizedIn 属性，则 anchor 是针对 recognizedIssuers 对 list 执行 基于凭证的发现所返回的认可链， 如果该过程未成功，则为空。
  10. 如果没有任何有效的 list 产生 anchor，则返回 result；该签发者未被认可。
  11. 否则，选择一个产生了 anchor 的有效 list， 将 result.recognized 设置为 true，并将 result.chain 设置为 credential，后跟 list，再后跟 其 anchor 的元素。
  12. 令 entity 为所选 list 的 credentialSubject 中 id 为 issuerId 的认可实体，并令 actions 为其 recognizedTo 属性声明的认可操作。
  13. 如果 actions 中任何认可操作具有 等于 action 的 action 值， 并且该认可操作要么未声明 outputValidation，要么 credential 符合其 outputValidation 引用的每个模式，则将 result.actionRecognized 设置为 true。
  14. 返回 result。

A. 威胁模型

本节为非规范性内容。

本节详细说明本规范的总体威胁模型， 包括安全方面的考虑、隐私方面的考虑以及市场 竞争方面的考虑。

建议读者在阅读本节之前，先熟悉 可验证凭证数据模型 v2.0 规范的 安全方面的考虑和 隐私方面的考虑 各节中提供的一般安全和 隐私建议。 实现者应将该 规范中提供的一般警告应用于本规范提供的每项具体功能。

A.1 目标威胁

  1. 未经授权的签发者冒充 安全 — 一个未获认可的实体伪造、重放或重复使用被盗的认可实体凭证，使其可验证 凭证看起来来自一个 合法认可的签发者。
  2. 认可实体凭证篡改 安全 — 恶意中间方替换或修改已出示捆绑包中的认可实体凭证， 从而使未获认可的签发者的可验证 凭证看起来受合法的认可链涵盖。

A.2 实现威胁

  1. 列表检索拒绝服务 安全 — 大量获取请求、缓慢滴流式服务器或过大的列表 会在验证者检索并 处理认可实体 凭证时耗尽其连接、内存 或 CPU。
  2. 通过列表获取造成的隐私泄露 隐私 — 当验证者从列表发布者处获取认可实体凭证时，发布者 会得知正在验证哪个签发者，从而能够 监视商业关系和活动模式。
  3. 未经审查的认可实体凭证传播 安全 — 持有者 通过点对点 渠道共享认可实体 凭证，而验证者在未 针对信任锚独立验证其 完整性的情况下接受该凭证，从而传播欺诈性的认可声明。
  4. 列表发布者冒充 安全 — 攻击者使用易混淆的标识符或 显示名称伪造列表发布者身份，使验证者将 攻击者控制的注册表视为 权威信任锚。
  5. 接受过时的认可 安全 — 已撤销或已被攻破的签发者仍能通过 验证，因为 认可实体凭证具有过长的 有效期，或者因为 验证者依赖被过度 缓存的、已过时的列表数据。
  6. 外部资源替换 安全 — 当引用未受完整性保护时，攻击者可通过服务器入侵、域名接管或 DNS 劫持， 用恶意内容替换外部引用的资源， 例如模式文件。
  7. 无界认可链信任 安全 — 当验证者未 强制实施深度限制或独立验证链中的每个链接时，通过 recognizedIn 链接的较低级注册表中的已被攻破条目 会被传递地信任。
  8. 滥用认可操作 安全 — 验证者 对自由格式的 action 值作出的解释比 列表发布者预期的更加宽松，从而授予认可实体 比获授权范围更广的能力。
  9. 过于宽松的模式约束 安全 — 宽泛、不完整或宽松的 outputValidation 模式规则使 已认可的签发者能够生成比 列表发布者预期授权范围更广的一类可验证 凭证。
  10. JSON Schema 攻击 安全 — 恶意构造或编写不当的 outputValidation 模式 包含病态正则表达式或深度嵌套结构，从而导致 验证者发生灾难性回溯或内存耗尽。

A.3 外部威胁

  1. 对认可实体标识符的监视 隐私 — 由于认可实体 凭证会公开列出带有其 标识符和属性的签发者，跨列表聚合凭证会导致 对认可实体进行系统性画像和监视。
  2. 关联造成的危害 隐私 — 认可实体凭证会暴露某个生态系统的 成员身份，而一次后续披露就可能使参与者面临针对、歧视或 声誉损害，即使该生态系统原本旨在保持私密。
  3. 认可实体标识符遭入侵 安全 — 攻击者如果攻破了某个已认可 签发者标识符的 私钥材料，就可以冒充该真正已登记的签发者， 生成能够通过验证的欺诈性可验证 凭证。
  4. 验证者信任锚配置错误 安全 — 验证者 操作者意外将错误的认可实体凭证配置为信任 锚，导致验证者接受 由非预期治理机构审查的签发者。

A.4 依赖项威胁

  1. 反竞争性列表把关 市场竞争 — 先发列表发布者选择性拒绝竞争对手注册，或 受到胁迫而撤销合法实体，从而对依赖单一 列表的验证者造成反竞争性锁定。
  2. 密码学相关量子计算机破解密码学 安全 — 密码学相关量子计算机破解常用的签名方案， 使攻击者能够伪造被认可实体凭证 和可验证 凭证上的证明，并导致信任链崩溃。

安全方面的考虑

W3C 正在迁移到一种整体式威胁建模方法， 并正在逐步弃用新规范中的“安全方面的考虑”章节。 有关安全方面考虑的文档，请参阅附录 A. 威胁模型。

隐私方面的考虑

W3C 正在迁移到一种整体式威胁建模方法， 并正在逐步弃用新规范中的“隐私方面的考虑”章节。有关 隐私方面考虑的文档，请参阅附录 A. 威胁模型。

B.2 联合国 GRID 跨境贸易 示例

议题 2

整个示例目前正在由 UNTP 审查，并可能会根据该组织及其他方面的意见 进行更改。

联合国全球注册机构信息目录（GRID）是一个可公开访问的数字目录，由联合国在 联合国贸易便利化与电子业务中心（UN/CEFACT）的主持下运行，其中列出了来自 参与的联合国会员国的权威注册机构，包括国家商业登记机构、土地登记机构和 商标登记机构。GRID 解决了全球贸易和公共管理中的一项关键验证缺口：当供应链 参与者、海关机构或贸易融资贷款机构收到外国实体提供的与贸易相关的 可验证凭证 时，它们通常与该实体没有 直接关系，因而无法独立验证其合法登记情况。由于全球每年交换数十亿份贸易 文件，人工验证并不可行。GRID 通过提供可信且可扩展的全球权威注册机构映射 解决了这一问题，从而实现自动验证并降低冒充和欺诈的风险。

由此形成的验证链包含三个凭证层级，每个凭证均在不同时间签发，具有不同的 生命周期，并由不同的 签发者签发：

  • 一份贸易文件可验证 凭证，例如商业发票， 由出口商的 DID 签发，生命周期为数周至数月，每年的签发量达数十亿份。
  • 由国家注册机构的 DID 向单个出口商签发的 RecognizedEntityCredential， 用于证明出口商的 DID 由已登记的法律实体控制，生命周期可达数年至数十年， 每个已登记实体对应一个凭证。
  • 由 GRID 的 DID 向国家注册机构签发的 RecognizedEntityCredential， 用于证明该注册机构是获得认可的主权机构，其生命周期以数十年计。全球大约有 一千个此类权威国家登记机构。

发现过程从贸易文件开始，朝信任锚方向逐步进行，并在每一步使用 基于标识符的发现，这是因为发布一个 列出国家登记机构中所有已登记实体的单一凭证可能达到国家登记机构难以实际承受的 规模：其中可能包含两百万个实体，每天更新数百次，并由数千万个验证者每天多次 获取该列表。作为替代，每个已登记实体都持有自己的 RecognizedEntityCredential，并将其发布在其 DID 文档中的 WhoisService 端点。国家注册机构同样会在其自己的 WhoisService 端点发布 GRID 向其签发的 RecognizedEntityCredential。这种方式将列表的发布去中心化，使生态系统中的 每个认可实体共同承担信息分发的负担。下图说明了这些 关系：

C. 与其他技术的关系

本节为非规范性内容。

本规范在设计时考虑了现有的“信任 基础设施”技术，下面介绍其中三种。本规范 定义的数据模型能够表达这些技术中的许多概念， 并被设计为通过 recognizedIn 属性与其互操作。

C.1 ETSI 信任服务列表

本节为非规范性内容。

欧洲电信标准协会（ETSI）在 [ETSI-TRUST-LISTS] 中定义了 信任服务列表（TSL）的格式，该格式在 欧盟各地用于发布可信服务提供商列表——这些实体 根据 eIDAS 法规获准颁发电子签名、电子印章、时间戳和其他 信任服务。每个欧盟成员国都会发布一份 国家 TSL，而欧盟委员会则发布一份列表清单（LoTL）， 其中引用每个国家 TSL，从而形成一个定义明确的分层信任 联合体系。

ETSI 信任服务列表与本 规范具有若干共同的概念目标：二者都描述被认可执行特定 操作的实体，将这些实体与标识元数据相关联，并且旨在 供依赖方在验证过程中使用。不过，本 规范与 ETSI 信任服务列表在若干关键方面有所不同：

  • 格式：ETSI 信任服务列表以经过签名的 XML 文档表示。本规范使用 JSON-LD 和可验证凭证数据 模型，从而能够与更广泛的去中心化身份生态系统集成。
  • 治理：ETSI 信任服务列表由一个 以欧盟成员国主管机构为根的集中式分层结构治理。 本规范同时支持集中式和去中心化治理 模型，允许任何实体在其自身 生态系统中充当认可机构。
  • 范围：ETSI 信任服务列表的范围限于 eIDAS 监管的电子信任服务。本规范不受特定领域限制， 可以表达任何领域中的认可，包括教育、 医疗保健和金融服务。
  • 以持有者为中心的共享：ETSI 信任服务列表发布在 众所周知的 URL 上，并由依赖方获取。本 规范还支持“证书装订”，即持有者 将被认可实体凭证直接出示给验证者，从而减少 验证者在每次交互期间联系中央注册表的需要。

C.2 X.509 证书颁发机构 列表

本节为非规范性内容。

X.509 [RFC5280] 是一项公钥基础设施（PKI）标准， 定义了证书和证书链的格式。证书 颁发机构（CA）是受信任可颁发 X.509 证书的实体，这些证书将 公钥与身份绑定。对 CA 的信任通常通过 将其纳入浏览器或操作系统信任存储——一份经过筛选的 根 CA 列表——或通过可追溯至此类根的证书链来建立。

X.509 CA 基础设施和本规范都旨在解决以下问题： 确定在给定上下文中能否依赖某个实体执行特定 操作。不过，本规范与 X.509 CA 列表在若干关键方面有所不同：

  • 数据模型：X.509 证书使用具有固定模式的二进制 ASN.1 格式 对标识符和公钥 关联进行编码。本规范 使用灵活且可扩展的 JSON-LD 数据模型，可以表达有关 被认可标识符以及这些标识符所标识实体获准执行的操作的任意 元数据。
  • 信任层级：X.509 PKI 依赖严格分层的 信任链，其根是少量受到全球信任的根 CA。本 规范支持一种信任网络模型，其中多个相互重叠且彼此 竞争的认可注册表可以共存，生态系统参与者可以 选择其信任的认可机构。
  • 操作语义：X.509 证书使用密钥用法和 扩展密钥用法标志来限制证书可用于何种用途，但 这些用途限于一组固定的密码学操作。本 规范可以表达对任意领域特定操作的认可， 例如颁发特定类型的凭证，从而支持更丰富且 更具上下文针对性的认可声明。
  • 去中心化颁发：向现有信任 存储添加新的 CA 需要获得浏览器供应商和/或操作系统维护者的接受，这是一个 集中式且通常缓慢的过程。相比之下，本规范允许任何 实体颁发 RecognizedEntityCredential，并在其 生态系统内共享，而无需获得中央把关方的批准。

C.3 ISO/IEC 18013-5 mDL VICAL

本节为非规范性内容。

ISO/IEC 18013-5 定义了移动驾驶执照（mDL），这是一项 将驾驶执照表示为移动文档（mDoc）的标准。作为该 生态系统的一部分，该标准定义了已验证颁发者证书颁发机构列表 （VICAL），它是一种经过签名的数据结构，其中包含一组 被认可为有权颁发 mDL 的证书颁发机构实体。依赖方 使用 VICAL 确定所出示 mDL 的颁发者在其 管辖范围内是否受到信任。

VICAL 概念与本规范具有共同目标，即使依赖 方能够确定凭证颁发者在特定 生态系统中是否受到认可。不过，本规范与 mDL VICAL 在若干关键方面有所不同：

  • 格式：VICAL 是一种使用 CBOR 编码并由 COSE 签名的 数据结构，与 mDL 生态系统紧密耦合。本规范 使用 JSON-LD 和可验证凭证数据模型，因此适用于 更广泛的凭证类型和部署环境。
  • 范围：VICAL 专用于 mDL 用例和 ISO/IEC 18013-5 信任模型。本规范可以使用任何类型的凭证 来表达对任何类型的可验证凭证及任何种类 操作的认可；它不限于颁发驾驶执照凭证。
  • 操作表达能力：VICAL 记录受到信任、 可以颁发 mDL 证书的 CA，但没有一种通用机制来 表达 CA 被认可执行的操作范围或其他类型的操作。本 规范的 RecognizedAction 结构明确记录 被认可实体获准执行的操作以及适用的凭证模式， 从而实现更细粒度的授权。
  • 去中心化：VICAL 由每个 mDL 生态系统中指定的 VICAL 提供商管理，并通过集中式 渠道分发。本规范允许任何实体发布认可 凭证，而无需依赖指定的中央提供商，从而支持 更开放且可组合的信任生态系统。
