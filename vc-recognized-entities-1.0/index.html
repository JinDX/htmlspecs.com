摘要

本规范描述了一种数据模型，可用于描述一个或多个已识别 实体，例如一个或多个人和/或组织，这些实体被认为会执行 特定操作，例如签发或验证可验证凭证。该 数据模型支持发布或直接共享此类 信息，提供一种可通过密码学验证并保护隐私的 机制，持有者可通过该机制证明其所使用 凭证对应的 实体在特定生态系统中受到认可。该 规范旨在与现有的“信任基础设施” 互操作，例如 X.509 证书颁发机构列表和 ETSI 信任服务列表，同时 支持使用可验证凭证构建新的去中心化生态系统。

    1. 简介

    可验证凭证 生态系统依赖于验证者 确定特定颁发者是否被认可执行 特定操作的能力，例如颁发某种类型的可验证凭证。 以往，这种确定通常通过 带外流程、双边协议或专有注册表完成，而这些方式 难以通过自动化方式发现、查询或推理。随着可验证凭证 越来越多地部署于教育、医疗保健、 金融服务和政府等领域，对一种标准化、可互操作的 机制来表达和传达对执行已知操作的实体的认可 已变得至关重要。如果没有这种机制，生态系统参与者 将被迫构建定制的“信任基础设施”，从而导致碎片化、 集成成本增加，并阻碍跨境和跨领域 互操作性。

    本规范通过定义一种任何 实体都可以用来将认可信息作为可验证凭证 发布或共享的数据模型，以去中心化方式解决表达被认可实体 （例如个人和组织）及其执行的操作（例如颁发 和验证）这一难题。 该模型并不强制使用单一的中央注册表，而是允许 任何实体——政府机构、行业联盟、标准 组织，甚至个人——颁发 RecognizedEntityCredential，声明其知晓一个或多个 被认可执行特定操作的实体。此设计使由相互重叠、彼此竞争且互为补充的 “信任注册表”构成的网络能够共存， 允许生态系统参与者选择其信任的实体，并跨 多个注册表进行推理。本规范还支持 与现有“信任基础设施”互操作，例如 X.509 证书颁发机构列表 和 ETSI 信任服务列表，从而允许引用现有的被认可实体信息， 并将其组合到新的去中心化生态系统中。

    本文基于可验证凭证数据 模型，定义 一种特定应用，而不是修改可验证凭证数据模型 v2.0 本身。 它利用 JSON-LD 的关联数据基础，在现有术语之外添加少量新的 类型和属性。因此，RecognizedEntityCredential 是一种普通的可验证凭证 — 使用与任何其他凭证相同的机制进行签发、出示和 验证。

    有意了解本规范所支持的各种用例的读者， 建议阅读第 2. 用例节。 本文档其余部分按以下章节组织：

    • 第 2. 用例节描述了促成本规范 设计的一组用例。
    • 第 3. 数据模型节定义了核心数据模型，包括 RecognizedEntity、RecognizedAction 和 RecognizedEntityCredential 类型及其属性和完整示例。
    • 附录 A. 安全注意事项、B. 隐私注意事项 和 C. 市场竞争注意事项 讨论与本规范实现者有关的安全、隐私和市场竞争注意事项。

    2. 用例

    本节描述了促成本规范设计的 一组用例。

    2.1 教育

    某国家教育主管机构希望公布一组由其认可为 其管辖范围内合法机构的大学和学院。 该机构颁发单个被认可实体凭证，其中列出每个 被认可机构及其通用名称、法定名称、徽标和网站等 描述性信息。这使软件能够向相关方显示 关于被认可机构的可信信息——例如大学名称、徽标和网站——， 因为软件已通过自动化且可进行密码学验证的方式确认 该机构受到国家主管机构认可，而无需直接联系该主管机构。

    2.2 生命事件记录

    一个全国性的生命记录机构协会不仅希望公布其认可的 实体——例如城市、地区或省级机构——还希望公布 每个实体被认可可签发哪些特定的 可验证凭证。 例如，某个特定的地区办事处被认可可以为其 管辖区域签发出生证明、结婚证明和死亡证明。 该协会签发一个 认可实体凭证，其中 每个 认可实体 都与一个 认可操作 相关联，该操作描述 其可能签发的生命记录类型以及该记录所遵循的模式。 接收到出生证明的 验证者 随后既可以确认其 签发者 是一个 获认可的管辖机构，也可以确认该管辖机构被认可 可以签发该特定类型的生命记录。

    2.3 跨境贸易

    全球约 5000 万个贸易实体每年交换 大约 50 亿张商业发票。出口商将 商业发票作为可验证凭证 颁发，并将其发送给进口商。 随后，进口商将该发票提交给进口海关机构 以办理边境清关，并提交给贸易融资贷款机构以办理跟单信用证 结算。海关机构和贷款机构均不与 出口商存在直接关系——它们通过进口商间接收到发票， 但必须确定出口商是否为合法 注册实体。

    验证依赖于两个相互独立但彼此关联的凭证，它们在 不同时间颁发，并具有不同的生命周期：

    • 商业发票可验证 凭证，由出口商的 DID 颁发——每年颁发数十亿份，生命周期为数周至数月。
    • 出口经济体的国家商业登记机构向出口商颁发的 RecognizedEntityCredential——在任何时间均有数百万份有效，生命周期 从数年到数十年不等。

    收到发票后，验证者解析出口商的 DID， 发现由国家商业登记机构颁发的关联 RecognizedEntityCredential， 并确认发票中的 DID 与该凭证的主体 相匹配。这使海关机构或贷款机构同时获得文档 完整性——发票未被篡改——和身份完整性—— 颁发者是 出口经济体中的注册实体——从而无需 事先了解出口商即可实现自动化边境清关和自动化贸易融资尽职调查。

    2.4 产品合格评定

    合格评定机构（CAB）将合格证书（CoC）作为 一项可验证凭证 颁发，用于证明 特定产品的安全或质量性能。CoC 随产品通过供应链进入 进口市场。然而，进口 国的市场监管机构通常与 CAB 不存在直接关系，也无法 独立确定该证书是否由真正 获得认可的检测实验室颁发。

    当出口国的国家认可机构向 CAB 颁发 RecognizedEntityCredential——证明 CAB 的认可 范围——时，便可以建立一条关联的验证链，类似于上述 跨境贸易用例：

    • 合格证书可验证 凭证，由 CAB 的 DID 颁发，声明产品符合特定安全或质量标准。
    • 国家认可机构向 CAB 颁发的 RecognizedEntityCredential，证明 CAB 获得认可，可在 规定范围内执行合格评定。

    收到 CoC 后，市场监管机构解析 CAB 的 DID，发现由国家 认可机构颁发的关联 RecognizedEntityCredential，并确认该证书中的 DID 与该凭证的主体相匹配。这使该机构同时获得文档 完整性——CoC 未被篡改——和身份完整性—— 颁发者是 真正获得认可的 CAB——从而无需人工验证 CAB 的认可状态， 即可在边境对货物进行预先清关。

    2.5 联合标识符

    常见用途中存在多个联合标识符示例。 国际标准书号（ISBN）、法人实体标识符（LEI）、 运输集装箱的 BIC 编号，以及互联网域名系统。在 每种情况下，中央机构都会向注册机构分配一个前缀，注册机构随后会向 第三方分配一段扩展该原始前缀的标识符范围。该 第三方随后可以进一步扩展字符串，以创建完整的 标识符。

    当凭证中提供此类标识符时，依赖方可能希望 验证该标识符是否由联合标识符 方案所有者所知的参与方，完全按照其操作程序构建。

    此类方案的一个示例是 GS1，该组织为世界上许多 条形码提供支持。其用例的详细说明见 可验证 凭证用例 文档 [vc-use-cases]。

    3. 数据模型

    以下各节定义本规范用于表达被认可实体以及其获认可执行的被认可操作的数据模型。

    本节所述的数据模型基于多种现有技术的输入构建，包括 EBSI 可信颁发者注册表、ETSI TS 119 612、eSSIF-Lab TRAIN、Trust over IP Foundation 信任注册表协议，以及 Rebooting the Web of Trust 输入文档。本节所述的数据模型能够表达这些其他规范中的许多概念，但并非全部概念。

    一份被认可实体凭证由 RecognizedIssuer 颁发，并包含一个或多个被认可实体，例如颁发或验证可验证凭证的组织。每个被认可实体都可以关联到其获认可执行的被认可操作。

    3.1 通用属性

    本节中的属性可以添加到第 3.4 RecognizedEntityCredential节所定义的 RecognizedEntityCredential 中的对象。本节列出的每个通用属性 均为OPTIONAL；颁发者无需提供任何这些值。

    属性 描述
    id 以全局无歧义方式标识实体的 URL。此属性的值 在 第 4.4 节：标识符 中定义，该节属于可验证凭证数据模型 v2.0规范。
    type 实体的类型。此属性的值在 第 4.5 节：类型 中定义，该节属于可验证凭证数据模型 v2.0规范。如果该实体是可验证 凭证的颁发者，则 type 属性MUST为 RecognizedIssuer。
    name 实体的人类可读名称。此属性的值在 第 4.6 节：名称 和描述 中定义，该节属于可验证凭证数据模型 v2.0规范。
    legalName 组织或实体向法律主管机关登记的正式法定名称，可以与其常用名称不同。如 可验证凭证数据模型 v2.0 规范的 第 11.1 节：语言与基本方向 所述，该值MUST为一个或多个字符串或语言值对象。拥有多种语言正式法定名称的实体可以通过提供一个语言值对象数组来表达每个名称。
    image 指向实体视觉表示的链接，例如徽标、照片或 图标。该值MUST为URL，其中包括使用 [RFC2397] 中所述 data: URL 方案的值。
    url 指向与该实体关联的主要网站或 Web 资源的 URL。该值MUST为URL。
    sameAs 一个或多个在其他上下文或系统中引用同一实体的 URL， 从而能够跨不同平台进行交叉引用和验证。 每个值MUST为URL。
    description 提供实体详细信息的人类可读描述。此属性的值 在 第 4.6 节：名称 和描述 中定义，该节属于可验证凭证数据模型 v2.0规范。

    RecognizedEntityCredential 中任何具有 id 属性的对象还可以 关联该 id 所标识资源的密码学哈希，使验证者能够检测该资源 自被认可实体凭证签发以来是否发生变化。 用于表示此类哈希的属性在可验证凭证数据模型 v2.0 规范的 第 5.3 节：相关资源的完整性中定义。

    3.2 RecognizedEntity

    被认可实体是由 RecognizedEntityCredential 的颁发者认可 执行特定操作的任何实体。

    属性 描述
    id 以全局无歧义方式标识实体的 URL。此属性的值 在 第 4.4 节：标识符 中定义，该节属于可验证凭证数据模型 v2.0规范。
    type type 属性MUST为 RecognizedEntity。此属性的值 在 第 4.5 节：类型 中定义，该节属于可验证凭证数据模型 v2.0规范。
    recognizedTo 第 3.3 RecognizedAction节中定义的、 被认可实体预期执行的 特定操作。如果该被认可实体预期执行多个 操作，则此属性可以出现多次。
    recognizedIn 一个对象，其中包含对认可实体文档的引用，该文档包含此特定的 认可实体，以及 已知其可以执行的操作。该对象的 id 值必须是一个 URL。该 对象的 type 值必须符合 可验证凭证数据模型 v2.0 规范中定义的 类型值空间，并且应该为 ExternalEntityList 或 RecognizedEntityCredential。
    registration 一个或多个对象，每个对象描述认可实体如何被记录在颁发者维护的登记册中，例如国家企业登记册、认可登记册或联合标识符体系的分配记录。每个对象预期携带从登记册所处生态系统定义的词汇表中选取的属性，例如登记册分配给认可实体的标识符以及registration的范围。第 D.2 联合国 GRID 跨境贸易 示例 节展示了使用 UNTP 数字身份锚 [UNTP-DIA] 定义的属性表达的registration。如果认可实体在颁发者处拥有多个registration，此属性可能出现多次。

    除上述属性外，还可以包含第 3.1 通用属性节中的属性。

    recognizedIn 条目中 type 属性的值为 ExternalEntityList 时，应该符合 有效的实体列表规范。在这种情况下，由 id 属性引用的列表 URL 的源确立该列表的信任根。 这方面的示例包括 X.509 证书颁发机构列表，如 互联网 X.509 公钥基础设施证书和证书吊销列表（CRL）配置文件 中所规定的，以及欧盟 ETSI 信任服务列表，如 电子 签名和基础设施（ESI）；可信列表 中所规定的。 对于 ExternalEntityList 类型，验证者和 凭证 消费者需要获取由 id 属性引用的 实体列表资源，以确定该资源所符合的实体列表 规范， 确定其是否支持该规范，并据此进行处理/终止。 type 属性值为 RecognizedEntityCredential 的列表必须符合 认可实体 v1.0。

    registration 和 recognizedTo 属性相互独立；对于给定的认可实体，可以表达其中任一属性、两个属性或均不表达。registration描述认可实体在颁发者维护的登记册中的登记情况，例如其企业注册号和法律形式、认可范围或分配给它的标识符范围。recognizedTo 属性描述其输出得到颁发者认可的操作，例如符合特定模式的可验证凭证。

    3.3 RecognizedAction

    被认可操作是 被认可实体预期执行的操作。

    属性 描述
    type type 属性必须为 RecognizedAction。
    action 一个字符串，用于 指定要执行的操作名称，例如 issue 或 verify。
    recognizedBy 一个URL，或包含第 3.1 通用属性中属性的对象，用于表示 执行认可任务的实体。
    credentialValidator credentialValidator 属性的值 MUST 为第 3.5 节凭证验证器所定义的一个或多个凭证验证器，为验证者提供足够的信息，以判断认可实体生成的可验证凭证是否满足认可机构的约束。如果存在多个凭证验证器，则可验证凭证 MUST 满足其中的每一个。
    validFrom 认可操作有效的最早时刻，即从该日期和时间起，认可实体被认可执行该操作。该值MUST为以 UTC 表示、无亚秒精度的 XML Schema dateTime 值，例如 2025-01-01T00:00:00Z。此属性是OPTIONAL；如果不存在，则适用外层认可实体凭证的有效期。该时间点包含在有效期内。如第 4.3 认可验证 节所述，验证者将其与评估时间进行比较。
    validUntil 认可操作有效的最晚时刻，即在该日期和时间之后，认可实体不再被认可执行该操作。该值MUST为以 UTC 表示、无亚秒精度的 XML Schema dateTime 值，例如 2030-01-01T00:00:00Z。此属性是OPTIONAL；如果不存在，则适用外层认可实体凭证的有效期。该时间点包含在有效期内。如第 4.3 认可验证 节所述，验证者将其与评估时间进行比较。

    3.4 RecognizedEntityCredential

    发布被认可实体凭证 时，该凭证MUST是 可验证凭证数据模型 v2.0中定义的符合要求的可验证凭证， 并表达下一节中规定的数据模型。 它描述了封装被认可实体的可验证凭证 的格式。

    被认可实体在可验证凭证中表达， 使持有者能够将其直接提供给 验证者。这种 有时称为“证书装订”的机制，通过确保 验证者无需联系 颁发者 来检索被认可实体凭证，从而增强 持有者的隐私。 尽管如此，验证者仍可能 选择忽略由持有者提供的被认可实体凭证，即使 可以验证其真实性，例如验证者希望获取更新版本的 被认可实体 凭证时。

    属性 描述
    id 包含一组被认可实体的可验证 凭证MAY 表达一个 id 属性，以便其他系统更容易检索该凭证。
    type 包含一组被认可实体的可验证 凭证MUST 表达一个包含 RecognizedEntityCredential 值的 type 属性。
    issuer 可验证凭证数据模型规范的 第 4.7 节：颁发者 中定义的可验证凭证的颁发者。此对象的类型为 RecognizedIssuer，还MAY包含第 3.1 通用属性 节列出的其他属性。此对象MAY包含第 3.2 RecognizedEntity 节定义的 recognizedIn 属性，引用一个包含颁发者自身的认可实体文档；这支持第 4.1 基于凭证的发现 节描述的基于凭证的发现过程，使验证者能够遍历认可层级，直到到达其认可的颁发者。
    validFrom 凭证开始有效的最早时间点。此属性 在可验证凭证数据模型规范的 第 4.6 节：有效期中定义。
    validUntil 凭证保持有效的最晚时间点。此属性 在可验证凭证数据模型规范的 第 4.6 节：有效期中定义。
    credentialSubject 第 3.2 RecognizedEntity节中定义的 一个或多个 RecognizedEntity 对象的集合。

    3.5 凭证验证器

    凭证验证器是认可操作的 credentialValidator 属性的值。它链接到一个文件，验证者使用该文件来判断认可实体生成的可验证凭证是否满足认可机构的约束。该文件的媒体类型决定凭证验证器的种类，进而决定验证者如何对其求值，详见第 4.4 节凭证验证。

    属性 描述
    id id 属性是 REQUIRED。其值 MUST 为链接到用于验证可验证凭证的文件的 URL。该值 MAY 为 [RFC2397] 所述的嵌入该文件的 data: URL。
    type type 属性 MUST 为 CredentialValidator。
    mediaType mediaType 属性是 REQUIRED。其值为 id 标识的文件的媒体类型，定义见《可验证凭证数据模型 v2.0》规范的第 5.3 节：相关资源的完整性，并标识凭证验证器的种类。本规范在以下各节定义凭证验证器的 application/schema+json 和 text/javascript 媒体类型。

    凭证验证器 SHOULD 使用《可验证凭证数据模型 v2.0》规范的第 5.3 节：相关资源的完整性所述机制之一，提供 id 标识的文件的密码学哈希。哈希将凭证验证器绑定到该文件的一个确切版本。对文件的任何更改，包括空白或注释的更改，都会产生不同的哈希。

    3.5.1 JSON Schema

    JSON Schema 凭证验证器是 mediaType 为 application/schema+json 的凭证验证器。其 id 链接到 JSON Schema [JSON-SCHEMA]。验证者通过依据该模式验证可验证凭证来对其求值。JSON Schema 凭证验证器仅检查正在验证的可验证凭证。

    Example 5 : 声明 JSON Schema 凭证验证器的认可操作 
    "recognizedTo": {
  "type": "RecognizedAction",
  "action": "issue",
  "recognizedBy": "did:web:learning-commission.example",
  "credentialValidator": {
    "id": "https://learning-commission.example/credentials/bachelors.json",
    "type": "CredentialValidator",
    "mediaType": "application/schema+json",
    "digestMultibase": "uEiBZl963sknNAHgPyslVv6VztZpfWQoRvW1htfx-UwirFo"
  }
}

    3.5.2 JavaScript

    （存在风险的功能）问题 1: JavaScript 凭证验证器属于存在风险的功能

    JavaScript 凭证验证器属于存在风险的功能；如果没有至少两个独立实现，则可能在本规范成为 W3C 推荐标准之前从中移除。

    JavaScript 凭证验证器是 mediaType 为 text/javascript 的凭证验证器。其 id 链接到 JavaScript 代码，验证者运行该代码来判断可验证凭证是否满足认可机构的约束。代码接收正在验证的可验证凭证，并通过其 options 接收认可链，因此可以比较该链中不同可验证凭证的值。例如，它可以确认一个可验证凭证中的标识符是否以链中更高层的认可实体凭证向其颁发者许可的前缀开头。验证者按照第 4.4.1 节 JavaScript 验证器处理的描述运行该代码。

    以下示例展示了 GS1 成员组织的一项认可操作，其中声明了两个凭证验证器。JSON Schema 凭证验证器检查 Healthy Tots 颁发的键凭证的结构。JavaScript 凭证验证器检查该键凭证中的 GTIN 是否以许可给 Healthy Tots 的 GS1 公司前缀开头，以及该 GS1 公司前缀是否以许可给该成员组织的 GS1 前缀开头。代码从认可链中读取这两个前缀。此方法至少有两个好处：1）GS1 发布一个可适用于所有被许可方的脚本；2）获取该脚本能够保护隐私，因为 GS1 不会得知正在验证哪个被许可方。

    4. 算法

    本节描述验证者在处理本规范定义的可验证凭证和认可实体凭证时可使用的算法。这些算法将发现与验证分离。

    发现定位可能用于确立对颁发者认可的认可实体凭证。第 4.1 基于凭证的发现 节和第 4.2 基于标识符的发现 节描述了实现这一目的的两种机制。验证者MAY使用任何其他机制，包括如第 D.3 基于持有者的交付 节所述，直接从持有者接收认可实体凭证。

    注: 发现并不确立认可

    定位到认可实体凭证并不能确立颁发者受到认可。跳过第 4.3 认可验证 节检查的验证者可能接受与相关颁发者无关的可验证凭证，或接受其认可链始终无法到达验证者所接受锚点的凭证。

    第 4.3 认可验证 节描述的认可验证确定所发现的可验证凭证是否确立认可。无论这些凭证通过何种方式发现，该过程的适用方式都相同。

    注: 标识符比较不使用规范形式

    比较主体（例如颁发者）的标识符以判断集合成员资格或等价性时，使用简单字符串比较。虽然可以在比较之前计算某种标识符体系中标识符的规范形式，但不同标识符体系的规范化规则可能不同，导致实现高度复杂。为减轻实现负担，选择使用简单字符串比较。简单字符串比较有时会将规范意义上相同的标识符判为不等价，例如两个 HTTPS URL 仅某个查询参数不同却返回同一文档。这一缺点是为了降低标识符比较的实现负担而作出的权衡。

    这两个过程都假定每个可验证凭证已单独通过验证。也就是说：其证明验证通过；在第 4.3 认可验证 节所述评估时间处于有效期内；并且已按照 可验证凭证数据模型 v2.0 规范的 Section 7.1: Verification 和 Appendix A: Validation 检查其状态（如果有）。这些过程适用于任何可验证凭证，此处不再重复。

    这些算法在多个位置从 Web 获取资源。所获取的 URLs 来自尚未检查的可验证凭证和标识符文档。获取策略为验证者可以获取的内容设定限制。验证者的 HTTP 客户端和标识符解析器应用这些限制。

    获取策略规定允许哪些 URL 方案，以及允许哪些地址。它会阻止私有地址，例如环回地址、链路本地地址和局域网内的地址。由于发送请求之前会查找名称，因此策略会检查该名称指向的地址。它以相同方式检查每次重定向，并限制跟随重定向的次数。

    注: 证明检查无法撤回请求

    这些算法在获取资源之后检查资源。此时请求已到达目标，其在目标处产生的任何作用也已经发生。证明检查告诉验证者是否应信任响应，却无法撤回请求。只有获取策略在请求发出之前发挥作用。

    4.1 基于凭证的发现

    基于凭证的发现是指这样一个过程： 一个 从未知签发者 接收到可验证凭证的 验证者找到一个 认可该 认可实体凭证，该凭证认可该 签发者，并且在 必要时，沿着认可实体凭证的层次结构向上遍历，直到到达 一个其自身签发者已被验证者 认可的凭证。

    该机制依赖于 recognizedIn 属性。当该属性出现在 可验证凭证的 issuer 对象上时， 包括出现在认可实体凭证的 issuer 对象 上时，recognizedIn 属性引用一个 认可实体的可验证凭证， 其中将该签发者列为一个 认可实体。验证者可以获取所引用的 可验证凭证 并检查该可验证凭证的 签发者。 如果验证者 认可该签发者， 则发现成功。如果不认可，验证者可以沿着已获取的可验证 凭证的 issuer 对象上的 recognizedIn 属性向层次结构上一级移动，并重复该过程，直到 到达其认可的签发者或达到配置的 限制。

    持有者可以预先获取该层次结构中的认可实体凭证，并将它们与可验证凭证一起提供给 验证者， 使用第 3.4 RecognizedEntityCredential节中描述的“证书装订”机制。当持有者提供 这些 可验证 凭证时，验证者无需自行获取 它们， 前提是验证者对所提供 可验证 凭证的新鲜度感到满意。需要更新 信息的验证者 可以拒绝由持有者提供的可验证凭证 或忽略它们， 并直接获取认可实体 凭证。

    为了针对配置的已认可颁发者集合（recognizedIssuers）和可选的持有者提供的可验证凭证集合（providedDocuments），对可验证凭证（credential）执行基于凭证的发现，验证者运行以下算法。算法返回一条chain，即以 credential 开头、随后为沿 recognizedIn 引用找到的每个认可实体凭证组成的可验证凭证列表。然后，验证者对返回的chain运行第 4.3 认可验证 节中的算法。

    注: 到达锚点并不意味着验证结束

    该算法一旦到达 recognizedIssuers 中的颁发者就会停止，因为在找到候选锚点后没有必要再获取更多可验证凭证。这项检查限制了获取过程，但并未确立认可。始终未到达 recognizedIssuers 中任何成员的chain仍会被返回，并由第 4.3 认可验证 节拒绝。

    注: 发现不检查中间约束

    此算法沿 recognizedIn 引用进行查找。它不读取 recognizedTo。认可方可以为其认可的每个实体附加凭证验证器。第 4.3 节认可验证会对返回的 chain 中的每个凭证运行这些验证器，从紧邻锚点的位置开始沿链向下进行。

    注: 此算法可在调用方的时间预算内运行

    maxDepth独立地限制此算法。当基于标识符的发现调用它时，其获取操作也计入调用方的 maxDuration；耗尽预算会从调用方的操作引发错误。

    1. 令 current 为 credential，令 chain 为包含 credential 的列表。
    2. 令 maxDepth 为验证者配置为允许遍历的最大认可链深度。如果 chain 的长度超过 maxDepth，则引发 LIMIT_EXCEEDED_ERROR。
    3. 令 issuer 为 current 的 issuer 属性值，并令 issuerId 为其标识符。
    4. 如果 issuerId 是 recognizedIssuers 的成员，则已经到达候选锚点，因此返回 chain。
    5. 如果 issuer 不包含 recognizedIn 属性，则无法进一步遍历认可层级，因此返回 chain。
    6. 令 listReference 为 recognizedIn 属性的值，并令 listId 为其 id。
    7. 令 list 为由 listId 标识的认可实体凭证：如果 providedDocuments 中存在该凭证且足够新，则从中取得；否则从 listId 获取。对该获取操作应用获取策略。如果无法取得 list，或获取策略阻止该获取操作，则引发标识 listId 的 RETRIEVAL_ERROR。
    8. 将 list 追加到 chain，将 current 设为 list，并返回步骤 2，以评估该列表的颁发者。

    4.2 基于标识符的发现

    基于标识符的发现是指这样一个过程： 一个 从未知签发者接收到可验证凭证的 验证者从该 签发者的标识符开始，将该标识符解析为 一个受控标识符 文档，并使用该 文档中声明的服务来检索一个可能包含 认可实体凭证的可验证 出示，该凭证认可该签发者。与 依赖于 issuer 对象上存在 recognizedIn 引用的基于凭证的发现不同，基于标识符的发现并不作此 假设；它转而通过解引用 签发者自身的 标识符来获取认可信息。

    该机制依赖于签发者在可通过其标识符发现的 服务端点上发布认可 信息。签发者的 标识符通常表示为 issuer 对象的 id（例如 issuer.id），它是一个可以解析或解引用为 受控标识符 文档的URL，例如一个DID 文档。该文档 可以声明一个其 type 数组同时包含 WhoisService 和 PathService 的服务；该服务的 serviceEndpoint 标识 签发者 发布描述自身的可验证 出示的位置。所 发布的可验证 出示由该签发者签名，并包含 将该签发者的标识符作为 credentialSubject 的可验证凭证。 其中可以包含一个认可实体凭证，在 该凭证中，签发者 作为一个认可实体出现。

    以这种方式获取认可实体 凭证的验证者 会完全按照基于凭证的发现中的方式对其进行处理。如果 验证者 认可该认可实体凭证的签发者，则发现 成功。如果不认可，并且该认可实体凭证在其自身的 issuer 对象上带有 recognizedIn 属性，则验证者可以 继续进行基于凭证的发现，以 遍历认可 层次结构，直到到达其认可的签发者。

    下图从 验证者的 视角展示了基于标识符的发现 过程。在层次结构的每一级都会重复相同的步骤，直到到达验证者认可的认可锚点。

    为了在时间预算（maxDuration）内，针对配置的已认可颁发者集合（recognizedIssuers），对可验证凭证（credential）执行基于标识符的发现，验证者运行以下算法。算法返回候选链列表，每条链都是以 credential 开头的可验证凭证列表。然后，验证者对返回的链运行第 4.3 认可验证 节中的算法，该节描述如何在各链的结果之间进行选择。

    maxDuration限制一次发现操作从算法开始时起的总耗时。它涵盖所有工作，包括嵌套的基于凭证的发现所执行的工作。maxDepth限制单条链；maxDuration限制整个操作。超过该限制会引发 LIMIT_EXCEEDED_ERROR。

    注: 预算耗尽取决于条件和顺序

    是否耗尽预算取决于网络条件和遍历顺序，因此同一个可验证 出示可能在某个验证者处成功，而在另一个处失败。预算耗尽的验证者尚未确立有关颁发者的任何结论。该错误表示超出预算，而不是认可失败，因此验证者可以使用更大的 maxDuration 重试。

    注: 发现不检查中间约束

    此算法构建候选链。它不读取 recognizedTo。认可方可以为其认可的每个实体附加凭证验证器。第 4.3 节认可验证会对每条返回链中的每个凭证运行这些验证器，从紧邻锚点的位置开始沿链向下进行。验证器验证失败的链仍表明颁发者受到认可，但不表明颁发者被认可执行所请求的操作。第 4.3 节认可验证解释了验证者如何从多条链的结果中进行选择。

    1. 令 chains 为空列表。
    2. 令 issuer 为 credential 的 issuer 属性值，并令 issuerId 为其标识符。
    3. 解析或解引用 issuerId，以取得受控标识符文档 idDocument。对解析过程中执行的任何获取操作应用获取策略。如果无法解析 issuerId，或获取策略阻止获取，则引发标识 issuerId 的 RETRIEVAL_ERROR。
    4. 令 service 为 idDocument 的 service 数组中，其 type 同时包含 WhoisService 和 PathService 的服务。如果不存在这样的服务，则返回 chains；此颁发者不支持基于标识符的发现。
    5. 令 endpoint 为 service 的 serviceEndpoint，并获取发布在 endpoint 处的可验证 出示 presentation。颁发者控制 endpoint，且此时尚未验证任何内容，因此对此获取操作应用获取策略。如果获取失败，或获取策略阻止获取，则返回 chains。
    6. 验证 presentation 上的证明，并确认其绑定到 issuerId。如果验证失败，则引发 CRYPTOGRAPHIC_SECURITY_ERROR。
    7. 令 candidates 为 presentation 中包含的、其 credentialSubject 中某个认可实体的 id 为 issuerId 的认可实体凭证。如果 candidates 为空，则返回 chains。
    8. 对 candidates 中的每个 list 执行以下操作。如果 list 的颁发者是 recognizedIssuers 的成员，则将由 credential 后接 list 组成的链追加到 chains。否则，如果 list 的 issuer 对象包含 recognizedIn 属性，则针对 recognizedIssuers 对 list 执行基于凭证的发现，并将由 credential 后接返回链中的元素组成的链追加到 chains。如果从此算法开始起的耗时超过 maxDuration，则引发一个标识 maxDuration 及正在获取的 URL（如果有）的 LIMIT_EXCEEDED_ERROR。
    9. 返回 chains。

    4.3 认可验证

    认可验证是验证者用来判断一条可验证凭证链是否确立某个可验证凭证的颁发者受到认可，以及是否被认可执行某项特定操作的过程。该过程不依赖于链的取得方式。由基于凭证的发现返回的链、由基于标识符的发现返回的链，以及如第 D.3 基于持有者的交付 节所述由持有者交付的链，都以相同方式进行验证。

    此算法检查链中可验证凭证之间的关系。它不检查任何单个可验证凭证的内部有效性，第 4. 算法 节假定这已得到确立。

    为了针对配置的已认可颁发者集合（recognizedIssuers），在评估时间（evaluationDateTime）以及时间预算（maxDuration）内，对任何发现机制生成的链（chain）执行针对特定操作（action，例如 issue）的认可验证，验证者运行以下算法。算法返回含有两个布尔结果的结果：recognized 表示 chain 中第一个可验证凭证的颁发者是否最终得到 recognizedIssuers 某个成员的认可；actionRecognized 表示该颁发者是否被认可执行 action，以及在认可操作声明 credentialValidator 时，可验证凭证是否符合其要求。actionRecognized 还要求链中的每个认可实体凭证都满足其自身认可方声明的约束。结果还包含凭证验证报告的 errors 和 warnings。

    maxDuration 限制一次认可验证的总耗时，从算法开始时起计量。无论链包含多少个链接、操作和验证器，它都涵盖算法执行的每次凭证验证。无论链来自发现还是持有者，该限制都适用。先运行发现的验证者传入发现预算的剩余时间。预算耗尽时，验证者停止任何仍在运行的验证器。

    此算法每次执行凭证验证时，都将其结果中的 errors 和 warnings 追加到 result.errors 和 result.warnings。如果这些错误包括 LIMIT_EXCEEDED_ERROR，或耗时超过 maxDuration，则算法引发标识该限制的 LIMIT_EXCEEDED_ERROR，而不是返回 result。因此，调用方可以区分预算耗尽和约束未满足，并可使用更大的 maxDuration 重试。

    evaluationDateTime是评估认可的时间点。验证者通常将其设为当前日期和时间。如果验证者要判断在过去某个日期是否存在认可，则将其设为该日期。此算法中的所有日期比较都使用 evaluationDateTime。有效期的端点包含在有效期内。等于 validFrom 或 validUntil 值的时刻处于该值限定的有效期内。

    1. 令 result 为一个结构，其 recognized 设为 false，actionRecognized 设为 false，errors 和 warnings 各设为空列表。
    2. 如果 chain 包含少于两个可验证凭证，则返回 result。认可链至少由一个可验证凭证和一个认可其颁发者的认可实体凭证组成。
    3. 令 maxDepth 为验证者配置为接受的最大认可链深度。如果 chain 的长度超过 maxDepth，则返回 result。
    4. 令 seen 为空集合。对于 chain 中的每个可验证凭证，令 id 为其颁发者的标识符。如果 id 已是 seen 的成员，则该链包含环，因此返回 result。否则，将 id 加入 seen。
    5. 令 window 为 chain 中每个可验证凭证同时有效的时间段。为确定该时间段，令 window 始于 chain 中最晚的 validFrom 属性值，终于 chain 中最早的 validUntil 属性值。未表达 validFrom 属性的可验证凭证不限制起始时间，未表达 validUntil 属性的凭证不限制结束时间。如果 window 的结束时间早于起始时间，则不存在这样的时间段，因此返回 result。如果 evaluationDateTime 位于 window 之外，则 chain 中至少一个可验证凭证在评估时间无效，因此返回 result。
    6. 对于 chain 中每一对相邻的可验证凭证，其中 subject 是前一个可验证凭证、list 是后一个，确认 list 是认可实体凭证，并且 list 的 credentialSubject 包含一个认可实体，其 id 通过简单字符串比较等于 subject 的颁发者的标识符。如果不满足，则两个可验证凭证无关，因此返回 result。
    7. 确认 chain 中最后一个可验证凭证的颁发者是 recognizedIssuers 的成员。如果不是，则该链未终止于验证者认可的锚点，因此返回 result。否则，将 result.recognized 设为 true。
    8. 检查 chain 中的每个中间认可实体凭证，从紧邻锚点的位置开始，朝第一个可验证凭证移动。也就是说，按顺序从 chain 中倒数第二个可验证凭证回到第二个，对每个可验证凭证，令 intermediate 为该可验证凭证，令 list 为 chain 中位于其后的可验证凭证，令 entity 为 list 的 credentialSubject 中 id 等于 intermediate 的颁发者标识符的认可实体。如果 entity 没有 recognizedTo 属性，则其认可方未对其施加约束，因此继续处理下一个可验证凭证。否则，执行以下步骤。
      1. 令 actions 为 entity 的 recognizedTo 属性声明的、有效期包含 evaluationDateTime 的认可操作。如果认可操作既未表达 validFrom 属性也未表达 validUntil 属性，则适用外层认可实体凭证的有效期。如果只表达其中一个属性，则外层凭证的对应属性适用于未表达的值。如果 actions 为空，则返回 result。
      2. 对于 actions 中声明 credentialValidator 的每个认可操作，使用其 credentialValidator 属性声明的凭证验证器，以及 chain 值为 chain 中 intermediate 之后所有项、action 值为 action、evaluationDateTime 值为 evaluationDateTime 的 options，按照第 4.4 节凭证验证的描述对 intermediate 执行凭证验证。如果结果的 valid 值不是 true，则返回 result。
    9. 令 credential 为 chain 中的第一个可验证凭证，令 list 为第二个，并令 entity 为 list 的 credentialSubject 中其 id 为 credential 的颁发者标识符的认可实体。如果 entity 的 recognizedTo 属性声明的任一认可操作满足以下全部条件，则将 result.actionRecognized 设为 true。
      1. 其 action 值等于 action。
      2. 其有效期包含 evaluationDateTime，按上一步的方式确定。
      3. 它未声明 credentialValidator；或者，使用其 credentialValidator 属性声明的凭证验证器，以及 chain 值为 chain 中第一项之后所有项、action 值为 action、evaluationDateTime 值为 evaluationDateTime 的 options，按照第 4.4 节凭证验证的描述对 credential 执行凭证验证，返回的结果的 valid 值为 true。
    10. 返回 result。
    注: 验证从锚点开始沿链向下进行

    在运行任何凭证验证器之前，所有证明都已验证，且已确认链终止于锚点。随后，验证器从紧邻锚点的位置开始依次运行，最后处理第一个可验证凭证。只有在某个实体通过其自身认可方设定的检查之后，该实体声明的验证器才会运行。认可机构可以借此限制其认可的实体能够继续认可哪些实体。第 D.1 节 GS1 联合标识符示例中的 GS1 前缀就是一个例子。对中间凭证的检查不比较 action 值。每个生态系统使用凭证验证器来说明中间实体能够认可什么。在中间凭证处，评估时间有效的每项认可操作都必须通过验证，因此添加另一项操作不能绕过限制。针对某类凭证的验证器因此需要接受其不加限制的凭证种类。没有 credentialValidator 的认可操作本身不设置限制。不检查验证者所认可锚点之上的限制，因为链终止于该锚点。

    注: 认可与操作认可是不同结果

    recognized 为 true 而 actionRecognized 为 false 的结果表示：颁发者得到验证者所认可锚点的认可，但未被认可执行相关操作，或生成的可验证凭证不符合认可操作要求的模式。当该操作关系到交易时，验证者预期应将此结果视为失败。

    对于给定的认可实体，缺少 recognizedTo 属性的认可实体凭证断言该实体受到认可，但不约束其执行的操作。要求明确认可某项操作的验证者会将此类认可实体凭证视为产生值为 false 的 actionRecognized。

    发现机制可能产生多条候选链，例如当颁发者发布来自多个认可机构的认可实体凭证时，基于标识符的发现就会如此。验证者按以下方式在其中选择。链的顺序不会改变结果。

    1. 对每条候选链运行此算法。所有运行共享一个时间预算，每次运行获得剩余时间。一旦某个结果的 recognized 和 actionRecognized 都设为 true，验证者就可以停止。
    2. 如果任何结果的 recognized 和 actionRecognized 都设为 true，则颁发者被认可执行该操作。使用该结果。
    3. 否则，如果任何一次运行引发了错误，例如 LIMIT_EXCEEDED_ERROR，则引发该错误。该链本来可能成功，因此验证者不能断定颁发者未受认可。
    4. 否则，如果任何结果的 recognized 设为 true，则颁发者受到认可，但未被认可执行该操作。使用该结果。
    5. 否则，颁发者未受认可。使用任一结果。

    如果在某一步有多个结果符合条件，可以使用其中任何一个。它们确立的结论相同，但其 errors 和 warnings 可能不同。共享预算是否耗尽可能取决于网络条件以及运行各条链的顺序，详见第 4.2 节基于标识符的发现。

    4.4 凭证验证

    凭证验证是验证者判断可验证凭证是否满足认可操作的 credentialValidator 属性声明的约束的过程。第 4.3 节认可验证从紧邻锚点的位置开始，对每个中间认可实体凭证执行此过程，然后对链中的第一个可验证凭证执行。只有在遍历链、确认链中每对相邻的可验证凭证都相关，并确认链终止于验证者认可的锚点后，才会执行此过程。如第 4. 节算法所述，链中每个可验证凭证上的证明已经得到验证。

    凭证验证不会改变发现、遍历或验证链的方式，所使用的凭证验证器种类也不会改变这些方式。每个凭证验证器都使用为其 mediaType 定义的处理方式，针对已经验证的链进行求值。当验证者不支持某个凭证验证器的 mediaType 时，凭证验证始终失败。

    每个凭证验证器的输入都是正在验证的可验证凭证和一个选项映射。选项携带求值所使用的所有其他信息。它们包含以下属性。

    属性 描述
    chain 如果可验证凭证作为认可链的一部分进行验证，则存在此属性。它是一个包含链中其余部分的数组，即链中除正在验证的凭证以外的每个可验证凭证，每个都表示为验证者收到的 JSON 对象，并按第 4.3 节认可验证定义的顺序排列。正在验证的可验证凭证单独传入，因此该数组从链的第二项开始。其第一项 chain[0] 是声明该凭证验证器的认可实体凭证，最后一项是验证者认可的锚点颁发的认可实体凭证。验证者已验证每一项上的证明。
    action 验证者针对链中第一个可验证凭证检查的操作，例如 issue，详见第 4.3 节认可验证。链中的每个凭证验证器都收到相同的值，包括验证中间认可实体凭证的验证器。
    evaluationDateTime 评估认可的时间点，详见第 4.3 节认可验证，以 UTC 的 XML Schema dateTime 值表示，例如 2026-11-04T00:00:00Z。

    其他规范 MAY 定义附加选项。如果凭证验证器不认识某个选项，则 MUST 抛出 UNRECOGNIZED_OPTION_ERROR。

    为了使用凭证验证器列表（validators）和选项映射（options）对可验证凭证（credential）执行凭证验证，验证者运行以下算法。算法返回的结果包含布尔值 valid、errors 列表和 warnings 列表。

    1. 令 result 为一个结构，其 valid 设为 true，errors 和 warnings 各设为空列表。
    2. 如果 validators 为单个对象，则将其视为包含该对象的列表。
    3. 对于 validators 中的每个 validator，使用为其 mediaType 属性值定义的处理方式对其求值：
      1. 如果 validator 的 type 不是 CredentialValidator，则向 result.errors 追加一个标识该 type 的 CREDENTIAL_VALIDATION_ERROR，将 result.valid 设为 false，然后继续处理下一个 validator。
      2. 如果 mediaType 为 application/schema+json，则在 credential 不符合 validator 的 id 属性标识的 JSON Schema [JSON-SCHEMA] 时，将 result.valid 设为 false。
      3. 否则，如果 mediaType 为 text/javascript，则令 validatorResult 为对 validator、credential 和 options 运行第 4.4.1 节 JavaScript 验证器处理中的算法所得的结果。将 validatorResult.errors 中的各项追加到 result.errors，将 validatorResult.warnings 中的各项追加到 result.warnings。如果 validatorResult.valid 不是 true，则将 result.valid 设为 false。
      4. 否则，验证者不支持该 mediaType。向 result.errors 追加一个标识该 mediaType 的 CREDENTIAL_VALIDATION_ERROR，并将 result.valid 设为 false。
    4. 返回 result。
    注: 仅对具有锚点的链求值凭证验证器

    第 4.3 节认可验证只有在确认链终止于验证者认可的锚点，并且链中每对相邻凭证都相关之后，才执行凭证验证。因此，只有当凭证验证器由认可关系可追溯到验证者已知认可根的颁发者声明时，验证者才检索并求值该验证器，包括运行其标识的任何代码。验证器从锚点开始沿链向下运行，因此只有在声明验证器的实体通过其自身认可方设置的验证器之后，该验证器才运行。

    4.4.1 JavaScript 验证器处理

    本节定义凭证验证如何针对已经验证的链，对 JavaScript 凭证验证器求值。代码由第三方编写，并通过认可实体凭证下载。由于验证者并不总是认识该第三方，因此将下载的代码视为不可信，并在沙箱中运行；沙箱无法访问网络、读取验证者自身的状态或获知沙箱之外的任何其他信息。只要安全性和隐私结果以及求值结果相同，验证者 MAY 使用不同于以下算法的算法。

    以下术语用于描述沙箱：

    验证宿主
    检索验证器代码、创建沙箱、向沙箱发送输入并接收结果的验证者软件。
    验证器代码
    由 JavaScript 凭证验证器的 id 属性标识的 JavaScript 代码。
    包装代码
    验证宿主与验证器代码一同放入沙箱的代码。它加载验证器代码，从验证宿主接收输入，调用验证器代码，并将其结果返回给验证宿主。

    验证器代码 MUST 为 [ECMASCRIPT] 定义的 ECMAScript 模块，其默认导出为一个函数。

    运行验证器代码的沙箱 SHOULD 满足以下安全要求。

    • 它阻止验证器代码发出任何种类的网络请求，包括从非 data: URL 的 URL 导入其他模块。
    • 它阻止验证器代码读取或修改验证宿主的任何状态，包括其内存、存储、Cookie、文档和密钥材料。验证器代码接收输入的副本，而不是验证宿主对象的引用。
    • 它不提供在沙箱销毁后仍然存在的存储，并且永不复用。每次调用验证器代码都从一个新沙箱开始，从而避免一次求值影响另一次，并使验证器代码无法跟踪验证者对哪些认可链求值。
    • 它允许验证宿主在不需要验证器代码配合的情况下随时终止验证器代码，使验证宿主能够强制执行运行时间和内存限制。
    注: 在同一进程中运行代码并不构成沙箱

    与验证宿主共享堆或事件循环的 JavaScript 环境，例如 Node.js 的 vm 模块，不满足上述要求。能够满足要求的环境包括独立的操作系统进程、isolated-vm 等库提供的隔离实例，以及编译为 WebAssembly 的 JavaScript 引擎。

    为了按照第 4.4 节凭证验证的描述，使用选项映射（options）对可验证凭证（credential）运行 JavaScript 凭证验证器（validator），验证者运行以下算法。算法返回的结果包含布尔值 valid、errors 列表和 warnings 列表。每个错误和警告都是 ProblemDetails 对象。

    1. 令 result 为一个结构，其 valid 设为 false，errors 和 warnings 各设为空列表。
    2. 如果验证者无法提供满足本节要求的沙箱，则向 result.errors 追加 CREDENTIAL_VALIDATION_ERROR，并返回 result。
    3. 令 codeUrl 为 validator 的 id 属性值。如果 codeUrl 是 data: URL，则令 code 为其编码的字节。否则，令 code 为验证者缓存的验证器代码的副本；如果没有缓存，则为从 codeUrl 检索的字节。对该检索应用检索策略。如果无法获得 code，或检索策略阻止该检索，则向 result.errors 追加标识 codeUrl 的 RETRIEVAL_ERROR，并返回 result。
    4. 如果 validator 提供了验证器代码的密码学哈希，则按照《可验证凭证数据模型 v2.0》规范第 5.3 节：相关资源的完整性的描述，确保 code 的密码学哈希与颁发者提供的哈希匹配。如果不匹配，则向 result.errors 追加标识 codeUrl 的 CRYPTOGRAPHIC_SECURITY_ERROR，并返回 result。在此检查成功之前，不得解析或运行 code 的任何部分。
    5. 令 maxDuration 和 maxMemory 为验证者配置为允许验证器代码使用的运行时间和内存限制。创建一个新沙箱，将包装代码和 code 放入其中，并开始计量耗时和内存使用量。如果在销毁沙箱之前的任何时刻超出任一限制，则销毁沙箱，向 result.errors 追加一个标识所超出限制的 LIMIT_EXCEEDED_ERROR，并返回 result。
    6. 将 credential 和 options 序列化为 JSON [RFC8259] 并发送到沙箱中。包装代码解析它们，将 code 作为 ECMAScript 模块加载，并以解析后的 credential 为第一个参数、解析后的 options 为第二个参数，调用该模块的默认导出，即验证函数。如果函数返回 promise，则包装代码等待其敲定。
    7. 如果 code 无法解析为 ECMAScript 模块，或其默认导出不是函数，则销毁沙箱，向 result.errors 追加 CREDENTIAL_VALIDATION_ERROR，并返回 result。
    8. 如果函数抛出异常或返回被拒绝的 promise，则销毁沙箱。如果异常具有值为 URL 的 type 属性，例如 UNRECOGNIZED_OPTION_ERROR，则向 result.errors 追加一个 ProblemDetails 对象，其 type 为该值，detail 为异常消息。否则，向 result.errors 追加 CREDENTIAL_VALIDATION_ERROR。返回 result。
    9. 包装代码将函数返回的值序列化为 JSON 并发送给验证宿主。销毁沙箱。令 output 为解析该 JSON 得到的结果。
    10. 如果 output 不具有第 4.4.1.1 节 JavaScript 凭证验证函数描述的验证结果形式，则向 result.errors 追加 CREDENTIAL_VALIDATION_ERROR，并返回 result。
    11. 将 result.valid 设为 output 的 valid 值。将 output 的 errors 值中的各项（如果有）追加到 result.errors，将其 warnings 值中的各项（如果有）追加到 result.warnings。
    12. 如果 result.errors 不为空，则将 result.valid 设为 false。
    13. 返回 result。
    4.4.1.1 JavaScript 凭证验证函数

    验证函数是验证器代码的默认导出。包装代码按以下方式调用它： 

    validate(credential, options) → result

    Example 10 : 检查认可链中各级 GS1 前缀的验证器代码 
    /**
 * Checks that the GTIN in a key credential begins with the GS1 Company
 * Prefix licensed to its issuer, and that each prefix licensed in the
 * recognition chain begins with the prefix licensed one level above it.
 *
 * @param {object} credential - The key credential being validated.
 * @param {object} options - The validation options.
 * @param {Array<object>} options.chain - The rest of the recognition
 *   chain; `chain[0]` recognizes the issuer of `credential`.
 * @param {string} options.action - The action being evaluated.
 * @param {string} options.evaluationDateTime - The evaluation time.
 *
 * @returns {{valid: boolean, errors: Array<object>,
 *   warnings: Array<object>}} The validation result.
 */
export default function validate(credential, options) {
  const errors = [];
  const warnings = [];
  const getId = value => typeof value === 'string' ? value : value?.id;

  // throw on any option this validator does not recognize
  const knownOptions = new Set(['chain', 'action', 'evaluationDateTime']);
  for(const name of Object.keys(options)) {
    if(!knownOptions.has(name)) {
      const error = new Error(`Unrecognized option "${name}".`);
      error.type =
        'https://www.w3.org/TR/vc-data-model#UNRECOGNIZED_OPTION_ERROR';
      throw error;
    }
  }

  // the prefixes are read from the recognition chain, so it is required
  const {chain} = options;
  if(!Array.isArray(chain)) {
    errors.push({
      type: 'https://id.gs1.org/validators#MISSING_CHAIN',
      title: 'Missing recognition chain',
      detail: 'This validator requires the recognition chain.'
    });
    return {valid: false, errors, warnings};
  }

  // `prefixes[i]` is the prefix that `chain[i]` licenses to the issuer of the
  // credential one level below it, which is `credential` when `i` is 0
  const prefixes = [];
  for(let i = 0; i < chain.length; ++i) {
    const issuerId = getId((i === 0 ? credential : chain[i - 1]).issuer);
    const entity = [].concat(chain[i].credentialSubject)
      .find(subject => subject.id === issuerId);
    if(typeof entity?.licenceValue !== 'string') {
      errors.push({
        type: 'https://id.gs1.org/validators#MISSING_LICENCE',
        title: 'Missing licence value',
        detail: `No licensed prefix found for ${issuerId}.`
      });
      return {valid: false, errors, warnings};
    }
    prefixes.push(entity.licenceValue);
  }

  // a GTIN-14 in a GS1 Digital Link URI: https://id.gs1.org/01/{gtin}
  const gtin = new URL(credential.credentialSubject.id).pathname.split('/')[2];
  if(!gtin?.slice(1).startsWith(prefixes[0])) {
    errors.push({
      type: 'https://id.gs1.org/validators#PREFIX_MISMATCH',
      title: 'Prefix mismatch',
      detail: `GTIN ${gtin} does not begin with prefix ${prefixes[0]}.`
    });
  }
  for(let i = 1; i < prefixes.length; ++i) {
    if(!prefixes[i - 1].startsWith(prefixes[i])) {
      errors.push({
        type: 'https://id.gs1.org/validators#PREFIX_MISMATCH',
        title: 'Prefix mismatch',
        detail: `Prefix ${prefixes[i - 1]} does not begin with prefix ${prefixes[i]}.`
      });
    }
  }

  const anchorId = getId(chain.at(-1).issuer);
  if(anchorId !== 'did:web:id.gs1.org') {
    warnings.push({
      type: 'https://id.gs1.org/validators#NOT_GS1_ANCHORED',
      title: 'Chain not anchored at GS1 Global Office',
      detail: `Chain ends at ${anchorId}, not at the GS1 Global Office.`
    });
  }

  return {valid: errors.length === 0, errors, warnings};
}

    A. 安全注意事项

    本节为非规范性内容。

    本节详述将认可实体数据模型部署到生产环境时的一般安全注意事项。下文每项注意事项概述了为本规范识别的一项安全威胁。每项威胁的完整分析及其应对措施见Recognized Entities Threat Model v1.0。

    建议读者在阅读本节之前，先熟悉 可验证凭证数据模型 v2.0 规范的 安全方面的考虑和 隐私方面的考虑 各节中提供的一般安全和 隐私建议。 实现者应将该 规范中提供的一般警告应用于本规范提供的每项具体功能。

    A.1 冒充未获授权的颁发者

    未受认可的实体伪造、重放或重用被窃取的认可实体凭证，使其可验证凭证看似来自合法受认可的颁发者。该威胁的完整分析及应对措施见Recognized Entities Threat Model v1.0中的冒充未获授权的颁发者。

    A.2 篡改认可实体凭证

    恶意中间方替换或修改所出示凭证包中的认可实体凭证，使未受认可颁发者的可验证凭证看似由合法认可链覆盖。该威胁的完整分析及应对措施见Recognized Entities Threat Model v1.0中的篡改认可实体凭证。

    A.3 列表获取拒绝服务

    当验证者获取并处理认可实体凭证时，大量获取请求、缓慢滴流式服务器或过大的列表耗尽其连接、内存或 CPU。该威胁的完整分析及应对措施见Recognized Entities Threat Model v1.0中的列表获取拒绝服务。

    A.4 传播未经审查的认可实体凭证

    持有者通过对等渠道共享认可实体凭证，而验证者未根据认可锚点独立验证其完整性就予以接受，从而传播虚假的认可声明。该威胁的完整分析及应对措施见Recognized Entities Threat Model v1.0中的传播未经审查的认可实体凭证。

    A.5 冒充列表发布者

    攻击者使用易混淆的标识符或显示名称伪造列表发布者身份，使验证者将攻击者控制的登记系统视为权威认可锚点。该威胁的完整分析及应对措施见Recognized Entities Threat Model v1.0中的冒充列表发布者。

    A.6 接受过时的认可

    由于认可实体凭证有效期过长，或验证者依赖大量缓存的过时列表数据，已被撤销或遭入侵的颁发者仍能通过验证。该威胁的完整分析及应对措施见Recognized Entities Threat Model v1.0中的接受过时的认可。

    A.7 替换外部资源

    当引用未受到完整性保护时，攻击者通过入侵服务器、接管域名或劫持 DNS，将外部引用资源（如模式文件）替换为恶意内容。该威胁的完整分析及应对措施见Recognized Entities Threat Model v1.0中的替换外部资源。

    A.8 不受限制的认可链信任

    当验证者不实施深度限制或不独立验证链中的每个环节时，通过 recognizedIn 链接的下级登记系统中的受损条目会被传递性地信任。该威胁的完整分析及应对措施见Recognized Entities Threat Model v1.0中的不受限制的认可链信任。

    A.9 滥用认可的操作

    验证者对自由形式的 action 值作出比列表发布者原意更宽松的解释，从而赋予认可实体超出授权范围的能力。该威胁的完整分析及应对措施见Recognized Entities Threat Model v1.0中的滥用认可的操作。

    A.10 过于宽松的模式约束

    范围过宽、不完整或宽松的 credentialValidator 模式规则允许受认可的颁发者生成比列表发布者原本授权范围更广的可验证凭证。该威胁的完整分析及应对措施见Recognized Entities Threat Model v1.0中的过于宽松的模式约束。

    A.11 JSON Schema 攻击

    由 credentialValidator 属性引用的、恶意构造或编写不佳的 JSON Schema 包含病态正则表达式或深层嵌套结构，导致验证者发生灾难性回溯或内存耗尽。该威胁的完整分析及应对措施见Recognized Entities Threat Model v1.0中的JSON Schema 攻击。

    A.12 通过检索实施服务器端请求伪造

    验证者获取来自未经验证的凭证或标识符文档的 URL，因此签发者可以将验证者的请求指向其自身无法访问的主机。有关此威胁及其应对措施的完整分析，请参阅被认可实体威胁模型 v1.0中的通过检索实施服务器端请求伪造。

    A.13 认可实体标识符遭入侵

    攻破受认可颁发者标识符私钥材料的攻击者能够冒充该真实登记的颁发者，生成可通过验证的欺诈性可验证凭证。该威胁的完整分析及应对措施见Recognized Entities Threat Model v1.0中的认可实体标识符遭入侵。

    A.14 验证者认可锚点配置错误

    验证者的运营者意外将错误的认可实体凭证配置为认可锚点，导致验证者接受由非预期治理机构审查认可的颁发者。该威胁的完整分析及应对措施见Recognized Entities Threat Model v1.0中的验证者认可锚点配置错误。

    A.15 基于虚假证据的准入

    列表发布者若根据虚假的身份或资格证据接纳实体，就会为该实体签发有效的被认可实体凭证；验证者执行的任何签名检查都无法发现这一虚假依据。有关此威胁及其应对措施的完整分析，请参阅被认可实体威胁模型 v1.0中的基于虚假证据的准入。

    A.16 具有密码学相关能力的量子计算机破解密码学

    具有密码学相关能力的量子计算机（CRQC）攻破常用签名方案，使攻击者能够伪造认可实体凭证和可验证凭证上的证明，从而瓦解信任链。该威胁的完整分析及应对措施见Recognized Entities Threat Model v1.0中的具有密码学相关能力的量子计算机破解密码学。

    整个示例目前正在由 UNTP 审查，并可能会根据该组织及其他方面的意见 进行更改。

    联合国全球注册机构信息目录（GRID）是一个可公开访问的数字目录，由联合国在 联合国贸易便利化与电子业务中心（UN/CEFACT）的主持下运行，其中列出了来自 参与的联合国会员国的权威注册机构，包括国家商业登记机构、土地登记机构和 商标登记机构。GRID 解决了全球贸易和公共管理中的一项关键验证缺口：当供应链 参与者、海关机构或贸易融资贷款机构收到外国实体提供的与贸易相关的 可验证凭证 时，它们通常与该实体没有 直接关系，因而无法独立验证其合法登记情况。由于全球每年交换数十亿份贸易 文件，人工验证并不可行。GRID 通过提供可信且可扩展的全球权威注册机构映射 解决了这一问题，从而实现自动验证并降低冒充和欺诈的风险。

    由此形成的验证链包含三个凭证层级，每个凭证均在不同时间签发，具有不同的 生命周期，并由不同的 签发者签发：

    • 一份贸易文件可验证 凭证，例如商业发票， 由出口商的 DID 签发，生命周期为数周至数月，每年的签发量达数十亿份。
    • 由国家注册机构的 DID 向单个出口商签发的 RecognizedEntityCredential， 用于证明出口商的 DID 由已登记的法律实体控制，生命周期可达数年至数十年， 每个已登记实体对应一个凭证。
    • 由 GRID 的 DID 向国家注册机构签发的 RecognizedEntityCredential， 用于证明该注册机构是获得认可的主权机构，其生命周期以数十年计。全球大约有 一千个此类权威国家登记机构。

    发现过程从贸易文件开始，朝认可锚点方向逐步进行，并在每一步使用 基于标识符的发现，这是因为发布一个 列出国家登记机构中所有已登记实体的单一凭证可能达到国家登记机构难以实际承受的 规模：其中可能包含两百万个实体，每天更新数百次，并由数千万个验证者每天多次 获取该列表。作为替代，每个已登记实体都持有自己的 RecognizedEntityCredential，并将其发布在其 DID 文档中的 WhoisService 端点。国家注册机构同样会在其自己的 WhoisService 端点发布 GRID 向其签发的 RecognizedEntityCredential。这种方式将列表的发布去中心化，使生态系统中的 每个认可实体共同承担信息分发的负担。下图说明了这些 关系：

    如果验证者 不直接认可乌托邦商业登记处， 则会转而对乌托邦商业登记处的 DID 执行 基于标识符的发现。 验证者解析 did:web:register.business.utopia.example，找到其 WhoisService 端点，并获取发布在该端点的可验证出示。该出示由乌托邦商业登记处的 DID 签名， 其中包含 GRID 签发的 RecognizedEntityCredential；在该凭证中，乌托邦商业 登记处作为认可实体。由于 GRID 是由 联合国运营的知名认可锚点，发现过程在此终止，从而完成从商业发票到全球贸易身份 基础设施根节点的认可链。

    注: 凭证主体可以包含生态系统特定信息

    以上示例使用的 RegisteredIdentity 类型以及 registeredId、idScheme、registerType、registrationScopeList 和 registrationCountry 属性是 UNTP 词汇表 [UNTP-DIA] 定义的生态系统特定扩展。它们分别携带登记机构分配的企业注册号、分配该号码的登记册、登记册种类、登记实体的法律形式以及登记国家。这些属性并非本规范定义；它们出现在示例中，只为说明登记机构颁发的RecognizedEntityCredential在实践中可能携带的信息种类。本规范仅定义包含它们的 registration 属性。

    D.3 基于持有者的交付

    本节为非规范性内容。

    第 4. 算法 节描述的基于凭证的发现和基于标识符的发现过程都要求验证者从网络获取信息。基于凭证的发现获取 recognizedIn 属性指定的认可实体凭证；基于标识符的发现解析颁发者的标识符，并从服务端点获取可验证 出示。离线或不愿在交易期间联系第三方的验证者无法执行这两种过程。

    在基于持有者的交付中，持有者使用第 3.4 RecognizedEntityCredential 节描述的“证书装订”机制，将认可实体凭证连同其支持的可验证凭证一起提供给验证者。持有者提供建立认可链所需的每个可验证凭证，因此验证者在本地评估该链。持有者的隐私也得到改善，因为没有列表发布者会获知正在验证哪个颁发者。

    基于持有者的交付依赖于每个认可实体持有自己的认可实体凭证，而不是由单个可验证凭证枚举生态系统中的每个实体。如上文第 D.2 联合国 GRID 跨境贸易 示例 节所示，为每个登记实体颁发单独凭证的登记机构，使实体无需联系机构即可出示自己的认可信息。

    向验证者交付认可实体凭证的三种方式会泄露不同数量的验证相关信息。基于持有者的交付泄露最少，因为验证者不联系第三方，其他方也不会获知发生了验证。从列表发布者获取会泄露更多，因为发布者会获知某次验证正在发生或即将发生，不过获取整个认可实体凭证而不是单个实体资源的验证者不会泄露其正在检查哪个颁发者。如第 4.2 基于标识符的发现 节所述，验证者从WhoisService端点获取会泄露最多信息，因为端点属于正在接受验证的颁发者，该颁发者因而会获知对自身可验证凭证的每一次验证。威胁 Privacy Leakage via List Fetch 描述了这一暴露及减少其影响的措施。

    过时的凭证

    本节为非规范性内容。

    验证者没有义务接受持有者提供的认可实体凭证。如第 3.4 RecognizedEntityCredential 节所述，需要更新信息的验证者可能忽略提供的可验证凭证，并在恢复连接后自行获取认可实体凭证。离线验证者无法在交换期间这样做，因此接受有限的陈旧性风险。认可可能在持有者缓存其认可实体凭证之后，或在验证者上次刷新其自身缓存数据之后被撤销。

    部署可以通过为装订的认可实体凭证配置可接受的最大存续时间、颁发有效期适合预期离线时长的认可实体凭证，以及在有连接时刷新缓存的认可锚点和状态信息，来降低这一风险。威胁 Stale Recognition Acceptance 提供了相关指引。

    注: 离线交付不会削弱验证

    在此示例中，验证者执行的每项检查都是密码学检查，且在本地进行。基于持有者的交付改变的是认可实体凭证到达验证者的方式，而不是验证者对其执行的检查。持有者无法在不使证明失效的情况下修改认可实体凭证，不过持有者确实可以选择出示哪些可验证凭证；见威胁 传播未经审查的认可实体凭证。

    CE 标记生态系统增加了算法未表达的规则：

    • 通报链和认可链都必须验证通过。仅就该算法而言，任意一条候选链通过即可。
    • 在每一跳（不仅是第一跳），匹配实体的 recognizedTo（该实体为认可实体）都允许下一份凭证所执行的操作：相同的 action，以及该凭证所满足的 credentialValidator。
    • 每个匹配实体的 recognizedBy（该实体为认可实体）等于包含该实体的凭证的 颁发者。
    • 对于 ScopedRecognizedAction，其范围涵盖证书的法规、合格评定模块和产品类别。
    注：被认可操作的范围

    action 和 credentialValidator 限制合格评定机构能够颁发哪种凭证，但不限制其获通报所针对的法规、合格评定模块或产品类别；这些限制决定给定证书是否有效。本示例将这些限制作为 recognizedTo 的直接属性，其类型为 ScopedRecognizedAction，这是 CE 标记生态系统定义的 RecognizedAction 的特化，并复用 UNTP 术语作为值。仅获通报评估玩具的机构也会呈现结构相同的认可链。

    注：registration 与 recognizedTo 中的范围

    认可凭证为不同目的两次声明范围。其 registrationScopeList 位于 registration 中，指向认可机构登记册中的范围文档，表示该机构在登记册中的地位。ScopedRecognizedAction 将相同限制表述为对获认可颁发的证书的机器可检查约束。验证者检查后者；前者让验证者或人员能够查阅权威记录。4.3 认可验证中的算法不评估这两者；两项检查都属于 CE 标记生态系统。

    注：从捆绑的出示组装链

    本示例中的凭证不携带 recognizedIn。持有者按D.3 基于持有者的交付所述交付这些凭证，而认可验证适用于产生的链，无论这些链以何种方式获得。本规范未定义的是验证者如何从无序的捆绑凭证集合构建有序候选链；上述按 DID 匹配的方法是一种实现方式。在线且发现出示不完整的验证者可以回退到基于标识符的发现。

    D.4.1 离线验证颁发者密钥

    捆绑交付免除了获取认可凭证的需要，但检查证明仍需要颁发者的公钥。在D.3 基于持有者的交付中，验证者预先缓存其认可锚的密钥材料。这里，大多数证明来自中间颁发者和持有者，而验证者无法预先知道它们的密钥。did:web DID 文档通过 HTTPS 获取，捆绑的副本并不能证明任何事情，因为 did:web 文档不具备自认证能力。以下比较弥补这一缺口的两种方法。

    由父级凭证绑定密钥。每份被认可实体凭证还声明其主体签名所用的密钥。父级的证明因而为子级密钥作保，如同 X.509 证书链，验证者只需要预先安装根密钥。标识符仍使用 did:web。主体上的 verificationMethod 属性并非本规范定义，而是来自 [CID]。

    E. 与其他技术的关系

    本节为非规范性内容。

    本规范在设计时考虑了现有的“信任 基础设施”技术，下面介绍其中三种。本规范 定义的数据模型能够表达这些技术中的许多概念， 并被设计为通过 recognizedIn 属性与其互操作。

    E.1 ETSI 信任服务列表

    本节为非规范性内容。

    欧洲电信标准协会（ETSI）在 [ETSI-TRUST-LISTS] 中定义了 信任服务列表（TSL）的格式，该格式在 欧盟各地用于发布可信服务提供商列表——这些实体 根据 eIDAS 法规获准颁发电子签名、电子印章、时间戳和其他 信任服务。每个欧盟成员国都会发布一份 国家 TSL，而欧盟委员会则发布一份列表清单（LoTL）， 其中引用每个国家 TSL，从而形成一个定义明确的分层信任 联合体系。

    ETSI 信任服务列表与本 规范具有若干共同的概念目标：二者都描述被认可执行特定 操作的实体，将这些实体与标识元数据相关联，并且旨在 供依赖方在验证过程中使用。不过，本 规范与 ETSI 信任服务列表在若干关键方面有所不同：

    • 格式：ETSI 信任服务列表以经过签名的 XML 文档表示。本规范使用 JSON-LD 和可验证凭证数据 模型，从而能够与更广泛的去中心化身份生态系统集成。
    • 治理：ETSI 信任服务列表由一个 以欧盟成员国主管机构为根的集中式分层结构治理。 本规范同时支持集中式和去中心化治理 模型，允许任何实体在其自身 生态系统中充当认可机构。
    • 范围：ETSI 信任服务列表的范围限于 eIDAS 监管的电子信任服务。本规范不受特定领域限制， 可以表达任何领域中的认可，包括教育、 医疗保健和金融服务。
    • 以持有者为中心的共享：ETSI 信任服务列表发布在 众所周知的 URL 上，并由依赖方获取。本 规范还支持“证书装订”，即持有者 将被认可实体凭证直接出示给验证者，从而减少 验证者在每次交互期间联系中央注册表的需要。

    E.2 X.509 证书颁发机构 列表

    本节为非规范性内容。

    X.509 [RFC5280] 是一项公钥基础设施（PKI）标准， 定义了证书和证书链的格式。证书 颁发机构（CA）是受信任可颁发 X.509 证书的实体，这些证书将 公钥与身份绑定。对 CA 的信任通常通过 将其纳入浏览器或操作系统信任存储——一份经过筛选的 根 CA 列表——或通过可追溯至此类根的证书链来建立。

    X.509 CA 基础设施和本规范都旨在解决以下问题： 确定在给定上下文中能否依赖某个实体执行特定 操作。不过，本规范与 X.509 CA 列表在若干关键方面有所不同：

    • 数据模型：X.509 证书使用具有固定模式的二进制 ASN.1 格式 对标识符和公钥 关联进行编码。本规范 使用灵活且可扩展的 JSON-LD 数据模型，可以表达有关 被认可标识符以及这些标识符所标识实体获准执行的操作的任意 元数据。
    • 信任层级：X.509 PKI 依赖严格分层的 信任链，其根是少量受到全球信任的根 CA。本 规范支持一种信任网络模型，其中多个相互重叠且彼此 竞争的认可注册表可以共存，生态系统参与者可以 选择其信任的认可机构。
    • 操作语义：X.509 证书使用密钥用法和 扩展密钥用法标志来限制证书可用于何种用途，但 这些用途限于一组固定的密码学操作。本 规范可以表达对任意领域特定操作的认可， 例如颁发特定类型的凭证，从而支持更丰富且 更具上下文针对性的认可声明。
    • 去中心化颁发：向现有信任 存储添加新的 CA 需要获得浏览器供应商和/或操作系统维护者的接受，这是一个 集中式且通常缓慢的过程。相比之下，本规范允许任何 实体颁发 RecognizedEntityCredential，并在其 生态系统内共享，而无需获得中央把关方的批准。

    E.3 ISO/IEC 18013-5 mDL VICAL

    本节为非规范性内容。

    ISO/IEC 18013-5 定义了移动驾驶执照（mDL），这是一项 将驾驶执照表示为移动文档（mDoc）的标准。作为该 生态系统的一部分，该标准定义了已验证颁发者证书颁发机构列表 （VICAL），它是一种经过签名的数据结构，其中包含一组 被认可为有权颁发 mDL 的证书颁发机构实体。依赖方 使用 VICAL 确定所出示 mDL 的颁发者在其 管辖范围内是否受到信任。

    VICAL 概念与本规范具有共同目标，即使依赖 方能够确定凭证颁发者在特定 生态系统中是否受到认可。不过，本规范与 mDL VICAL 在若干关键方面有所不同：

    • 格式：VICAL 是一种使用 CBOR 编码并由 COSE 签名的 数据结构，与 mDL 生态系统紧密耦合。本规范 使用 JSON-LD 和可验证凭证数据模型，因此适用于 更广泛的凭证类型和部署环境。
    • 范围：VICAL 专用于 mDL 用例和 ISO/IEC 18013-5 信任模型。本规范可以使用任何类型的凭证 来表达对任何类型的可验证凭证及任何种类 操作的认可；它不限于颁发驾驶执照凭证。
    • 操作表达能力：VICAL 记录受到信任、 可以颁发 mDL 证书的 CA，但没有一种通用机制来 表达 CA 被认可执行的操作范围或其他类型的操作。本 规范的 RecognizedAction 结构明确记录 被认可实体获准执行的操作以及适用的凭证模式， 从而实现更细粒度的授权。
    • 去中心化：VICAL 由每个 mDL 生态系统中指定的 VICAL 提供商管理，并通过集中式 渠道分发。本规范允许任何实体发布认可 凭证，而无需依赖指定的中央提供商，从而支持 更开放且可组合的信任生态系统。
