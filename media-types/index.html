1.  引言

   近来的互联网协议经过精心设计，使其在某些方面易于
   扩展。特别是，许多协议，包括但不限于 HTTP
   [RFC2616] 和 MIME [RFC2045]，都能够
   承载任意带标签的内容。

   用于标记这类内容的机制是媒体类型，它由
   顶级类型和子类型组成，子类型还进一步组织为
   树。媒体类型还可以选择定义称为
   参数的伴随数据。

   这些标签需要一个注册过程，以便使此类值的集合
   以合理有序、定义明确且公开的方式
   得到定义。

   本文档规定媒体类型注册的准则，并
   定义在互联网号码分配机构 (IANA) 中央注册表中注册媒体类型（第 5 节）
   以及媒体类型结构化后缀（第 6 节）时应使用的程序。

   按这些程序管理的媒体类型注册表位置
   是：

      http://www.iana.org/assignments/media-types/

1.1.  历史说明

   媒体类型注册过程最初是为
   在异步互联网邮件环境中使用的媒体类型进行注册而定义的。在这种邮件环境中，需要
   限制可能的媒体类型数量，以提高
   在远程邮件系统能力未知时的互操作性
   可能性。随着媒体类型被用于新的
   环境，而在这些环境中媒体类型数量增加并不会成为
   互操作性的障碍，原来的程序显得
   过于严格，因此必须进行泛化。这一工作
   最初在 [RFC2048] 中完成，但其中定义的程序
   仍然是 MIME 文档集的一部分。媒体类型规范
   和注册程序现在成为一份独立文档，以明确
   它独立于 MIME。

1.2.  本文档中使用的约定

   本文档中的关键词 “MUST”、“MUST NOT”、“REQUIRED”、“SHALL”、“SHALL NOT”、
   “SHOULD”、“SHOULD NOT”、“RECOMMENDED”、“MAY” 和 “OPTIONAL”，当它们
   以全大写形式出现时，应按照 [RFC2119] 中的说明进行解释。它们
   也可能以小写或大小写混合形式作为
   普通英语单词出现，此时不具有任何规范性含义。

   本规范使用增强巴科斯-诺尔范式 (ABNF)
   [RFC5234] 表示法，包括该文档附录 B中定义的
   核心规则。

2.  媒体类型注册前提

   注册一种或多种新媒体类型首先要
   构造一个注册提案。注册可以发生在
   若干不同的注册树中，这些注册树具有不同的
   要求，如下文所述。通常，新的注册
   提案会以适合所涉及注册树的方式进行传阅和审查。
   如果提案可接受，则注册该媒体类型。
   以下各节说明用于不同注册树的
   要求和程序。

3.  注册树和子类型名称

   为提高
   注册过程的效率和灵活性，可以注册不同结构的子类型名称，
   以适应不同的自然需求，
   例如，一个将被推荐由互联网社区广泛支持和
   实现的子类型，或者一个用于
   传输与专有软件关联文件的子类型。以下
   小节定义了通过使用分面名称来区分的注册“树”，
   例如，以“树.”
   前缀开头的子类型名称。请注意，在本文档之前定义的一些媒体类型
   并不符合下述命名约定。有关这些类型的讨论见附录
   A。

3.2.  供应商树

   供应商树用于与公开
   可用产品关联的媒体类型。在此上下文中，“供应商”和“生产者”的含义非常
   宽泛，并被视为等同。请注意，
   行业联盟以及不符合公认标准相关组织资格的非商业实体，
   完全可以在供应商树中注册媒体类型。

   任何需要
   交换与某个产品或一组产品关联文件的人，都可以将注册放入供应商树。
   但是，该注册恰当地归属于
   生产使用被注册类型的软件的供应商或
   组织，并且该供应商或组织可以随时选择
   声明由第三方完成的注册的所有权，以便
   更正或更新它。更多信息见第 5.5 节。

   当第三方代表其他人注册类型时，两个
   实体都应该在注册的 Change Controller 字段中注明。
   一种可能的格式是“Foo，代表
   Bar”。

   供应商树注册通过前导分面
   “vnd.” 来区分。之后可以由注册者自行决定，
   接一个知名生产者的媒体子类型名称（例如
   “vnd.mudpie”），或者接一个经 IANA 批准的生产者
   名称标识，再跟随媒体类型或产品标识（例如
   vnd.bigcompany.funnypictures）。

   虽然供应商树中待注册媒体类型无需进行公开展示
   和审查，但鼓励使用 media-types@iana.org
   邮件列表进行审查，以提高
   这些规范的质量。供应商树中的注册可以
   直接提交给 IANA，在批准前将接受专家审查
   [RFC5226]。

3.3.  个人或自定义树

   以实验方式创建或作为
   非商业分发产品一部分创建的媒体类型，可以在
   个人或自定义树中注册。这些注册通过
   前导分面“prs.”来区分。

   “个人”注册及相关规范的所有者
   是进行注册的人或实体，或者是按照
   下文所述转移了责任的人或实体。

3.4.  未注册的 x. 树

   以“x.”作为第一个分面的子类型名称可用于
   专门在私有、本地环境中使用的类型。
   此树中的类型无法注册，并且仅供
   交换双方主动同意时使用。

   但是，由于上文所述供应商树和个人树
   的简化注册程序，几乎不应该再有
   使用未注册类型的必要。因此，强烈不建议
   使用“x.”树中的类型。

   请注意，名称以“x-”开头的类型不再
   被视为此树的成员（见 [RFC6648]）。还请注意，
   如果某种普遍有用且已广泛部署的类型错误地以
   “x-”作为名称前缀，则可以按照
   附录 A中定义的程序，使用其当前
   名称在另一树中注册。

3.5.  其他注册树

   根据社区需要，可以不时通过 IETF 标准行动
   创建新的顶级
   注册树。明确假定这些树可以创建出来，
   由知名的永久性组织进行外部
   注册和管理；
   例如，科学学会可以注册与其所涵盖科学领域相关的媒体类型。
   通常，对
   这些其他注册树之一的规范审查质量，预期应等同于
   公认标准相关组织在标准树中的注册。
   当 IETF 执行
   此类审查时，需要考虑提出请求的组织
   在相关媒体类型主题方面更高的专业知识。

4.1.  功能要求

   媒体类型必须作为真正的媒体格式发挥作用。不允许注册
   更适合被视为传输编码、
   字符集或者另一种类型的独立实体集合的内容。
   例如，虽然存在用于解码
   base64 传输编码 [RFC2045] 的应用程序，但 base64 不能注册为
   媒体类型。

   无论涉及哪一种注册树，
   此要求都适用。

4.2.  命名要求

   所有已注册媒体类型都必须分配顶级类型和
   子类型名称。这些名称的组合用于唯一
   标识媒体类型，而子类型名称分面（或不存在
   分面）则标识注册树。顶级类型和
   子类型名称均不区分大小写。

   类型和子类型名称必须符合以下 ABNF：

      type-name = restricted-name
      subtype-name = restricted-name

      restricted-name = restricted-name-first *126restricted-name-chars
      restricted-name-first  = ALPHA / DIGIT
      restricted-name-chars  = ALPHA / DIGIT / "!" / "#" /
                               "$" / "&" / "-" / "^" / "_"
      restricted-name-chars =/ "." ; 第一个点之前的字符始终
                                   ; 指定分面名称
      restricted-name-chars =/ "+" ; 最后一个加号之后的字符始终
                                   ; 指定结构化语法后缀

   请注意，此语法比
   [RFC2045] 第 5.1 节或[RFC4288]
   第 4.2 节中的 ABNF 所允许的语法限制稍多。还请注意，虽然此语法允许名称最长达到
   127 个字符，但实现限制可能使这样的长名称
   出现问题。因此，<type-name> 和 <subtype-name> 应该
   限制在 64 个字符以内。

   尽管名称语法将“.”视为与其他任何
   字符等同，但任何初始“.”之前的字符始终指定
   注册分面。请注意，这意味着没有分面的标准
   树注册不能在子类型名称中使用句点。

4.2.1.  文本媒体类型

   “text”顶级类型用于发送主要
   以文本形式存在的材料。

   文本的许多子类型，尤其包括

   字符集名称。

   （例如“text/xml”）时，不应该

   参数，从而消除指定默认值的选项。如果
   尽管有此建议仍有充分理由让该参数可选，
   每个子类型可以指定自己的默认值，或者
   也可以指定不存在默认值。

   默认值。有关“charset”参数与文本子类型结合使用的更多信息，

   都必须明确规定如何确定字符集；不再允许依赖

4.2.5.  应用媒体类型

   “application”顶级类型用于不适合
   其他任何类型名称的离散数据，尤其用于
   需要由某种应用程序处理的数据。这类
   信息必须先由应用程序处理，才能被用户
   查看或使用。“application”

   演示文稿、日程数据，以及用于“主动”
   （计算型）材料的语言。（尤其是最后一种可能带来
   实现者必须了解的安全问题。
   [RFC2046] 中的“application/postscript”媒体类型注册
   提供了一个如何处理这些问题的良好示例。）

   例如，会议日程程序可以为
   关于拟议会议日期的信息定义标准
   表示形式。智能用户代理会使用这些信息与用户
   进行对话，然后可能根据该
   对话发送其他材料。更一般地说，已经开发出若干
   “主动”语言，其中以适当专用语言编写的程序
   被传输到远程位置，并在
   接收者的环境中自动运行。此类应用可以定义为
   “application”顶级类型的子类型。

   “application”的子类型通常是
   数据所针对应用程序名称的全部或一部分。
   但这并不意味着任何应用程序名称都可以
   随意直接用作“application”的子类型；该子类型
   需要注册。

4.2.7.  其他顶级类型

   在某些情况下，新媒体类型可能无法“归入”任何当前

   定义新的类型名称来容纳它。新顶级类型名称的定义

4.2.8.  结构化语法名称后缀

   MIME 中的 XML [RFC3023] 定义了对媒体类型定义的
   第一个此类扩充，用于进一步指定该
   媒体类型的底层结构。引用如下：

      本文档还标准化了一种约定（使用后缀
      “+xml”）来命名媒体类型……当这些媒体类型
      表示 XML MIME（多用途互联网邮件扩展）
      实体时。

   也就是说，它规定了一个后缀（在该例中为“+xml”），附加
   到基础子类型名称之后。

   自该文档发布以来，使用这种后缀约定表示其他知名
   结构化语法已经成为事实上的实践。特别是，
   已有媒体类型注册了诸如
   “+der”、“+fastinfoset”和“+json”的后缀。本规范将
   这种实践正式化，并建立结构化类型名称
   后缀注册表。

   判断某个结构化类型名称后缀是否可注册的主要准则
   是：该后缀应由易于获得的
   说明进行描述，最好是在成熟的
   标准相关组织发布的文档中，并且存在一个
   可用于 RFC 规范性参考文献部分的引用。

   使用命名结构化语法的媒体类型在注册时
   应该使用该结构化语法对应的
   已注册“+suffix”。同样，媒体类型不得被赋予
   包含其实际上并未使用的结构化语法后缀的
   名称。鉴于可能与未来的后缀定义发生
   冲突，不应该使用尚未注册的结构化语法
   “+suffix”构造。

4.3.  参数要求

   媒体类型可以选择使用一个或多个媒体类型参数，或者
   某些参数可能因为该媒体类型是定义了一组
   适用于其任何子类型的参数之内容类型的子类型，而自动对其可用。
   无论哪种情况，当媒体类型在标准树中注册时，
   任何参数的名称、值和含义都必须完整规定；
   当媒体类型在供应商树或个人树中注册时，
   则应该尽可能完整地规定。

   参数名称的语法与媒体类型名称和值一样：

       parameter-name = restricted-name

   请注意，此语法比 [RFC2045] 中并由 [RFC2231] 修订的 ABNF
   所允许的语法限制稍多。

   参数名称不区分大小写，其出现顺序
   不具有任何含义。同一个特定参数被指定
   多次属于错误。

   参数值没有已定义的语法。因此，
   注册必须规定参数值语法。此外，
   某些传输机制会对参数值语法施加限制，因此
   需要注意限制使用可能有问题的
   语法；例如，尽管某些协议允许纯二进制值参数，
   但最好避免使用。

   请注意，协议可以根据其选择如何表示参数，
   对参数值语法施加进一步限制。
   MIME [RFC2045] [RFC2231] 和 HTTP [RFC2045] [RFC5987] 都允许
   二进制参数以及使用特定字符集表示的参数值，
   但其他协议可能不那么灵活。

   不应该通过定义新参数的方式，为标准树中已注册的类型
   引入新功能，不过可以添加新
   参数来传递不会

4.4.  规范化和格式要求

   无论注册树为何，所有已注册媒体类型都必须采用
   单一、规范的数据格式。

   对于标准树中注册的所有类型，都必须存在
   一份永久且易于公开获取的媒体类型格式规范。
   该规范必须提供足够的细节，以便
   使用该媒体类型的独立实现之间可以实现互操作。
   该规范至少必须在媒体类型
   注册提案本身中被引用（如果没有实际包含在其中）。

   对于在供应商树
   和个人树中注册的媒体类型，其格式和处理细节规范可能公开，也可能不公开。

   信息限制为哪些软件及
   版本生成或处理这类媒体类型。因此，鼓励
   在注册中引用或包含格式规范，

   公开可用性，通常会决定该注册究竟只是
   保留一个名称以避免与其他用途冲突，

   有用的互操作。

   明确允许注册涉及专利技术的媒体类型。

4.5.  互换建议

   理想情况下，媒体类型的定义应使其能够在尽可能多的
   系统和应用之间互操作。但是，某些媒体类型
   不可避免地会在不同平台之间存在
   互操作问题。不同版本、字节顺序以及
   网关处理细节方面的问题都可能且确实会出现。

   并不要求媒体类型具有普遍互操作性，但只要可能，
   就应该指出已知的互操作问题。
   发布媒体类型不要求对互操作性进行穷尽审查，
   互操作性考虑部分也需要
   持续评估。

   无论涉及哪一种注册树，
   本小节中的建议都适用。

4.6.  安全要求

   对所有在标准树中注册的类型，都必须进行安全问题
   分析。对于在供应商树或个人树中注册的媒体类型，
   鼓励但不要求进行类似分析。
   不过，无论是否进行了安全分析，
   无论注册树为何，对所有安全问题的描述都必须尽可能
   准确。特别是，
   安全考虑不得声称“此类型不存在相关安全
   问题”。供应商树或个人树中的类型
   可以在安全考虑中说明“尚未评估
   与此类型相关的安全问题”。

   完全没有要求任何树中注册的媒体类型
   必须安全或完全没有风险。尽管如此，无论注册树为何，
   媒体类型注册中都必须指出所有
   已知安全风险。

   所有注册中的安全考虑部分都需要
   持续评估和修改，尤其可以通过

   扩展。

   媒体类型注册树本身的一部分“发布”。

   如前所述，由其他标准相关
   组织制定的文档中所定义媒体类型的标准树注册，必须由
   该组织制定的正式标准规范进行说明。
   此外，注册模板上的任何版权都必须允许
   IANA 将其复制到 IANA 注册表中。

   除 IETF 在标准树中的注册外，媒体类型的注册
   并不意味着 IANA 或 IETF 对其背书、批准或
   推荐，甚至也不证明该
   规范是充分的。要成为 IETF 标准，协议或
   数据对象必须经过 IETF 标准流程。虽然该流程
   在适当情况下能够提供额外保证，但对于方便地注册
   媒体类型而言，这一过程过于困难且耗时过长。

   标准树适用于那些确实需要在公认标准
   相关组织中经过实质性审查和批准过程的
   媒体类型。供应商树和个人树则适用于那些
   不需要此类过程的媒体类型。预计 IETF 会
   不时发布针对特定应用的适用性声明，
   推荐实现和支持那些已证明在相关场景中特别有用的
   媒体类型。

   如上所述，注册顶级类型需要
   IETF 中的标准行动，因此需要发布一份
   标准路线 RFC。

5.  媒体类型注册程序

   媒体类型注册程序并不是正式的标准
   流程，而是一种管理程序，旨在允许
   社区发表评论并进行合理性检查，而不会造成过度的时间延迟。

   标准树中的所有 IETF 注册都需要遵循正常的 IETF
   流程。发布互联网草案是必需的
   第一步，然后按照下文讨论发布到 media-types@iana.org
   列表。

5.1.  初步社区审查

   标准树中潜在媒体类型注册的通知
   应该发送到 media-types@iana.org 邮件列表进行审查。
   该邮件列表是为审查
   提议的媒体类型和访问类型而设立的。其他树中的注册也可以
   发送到该列表进行审查；这样做完全是可选的，
   但强烈鼓励。

5.2.1.  临时注册

   标准化流程通常需要相当长的时间才能完成。
   为了促进原型设计和测试，通常有必要
   在流程早期分配标识符，包括但不限于媒体类型。
   这样，标准开发期间使用的标识符在流程完成后
   可以保持不变，实现和文档
   也不必更新。

   因此，提供了一个临时注册流程，
   以支持标准树中媒体类型名称的早期分配。
   对于标准树类型，可以向 IANA 提交临时注册。
   此类注册唯一必需的字段是
   媒体类型名称和联系信息（包括标准
   相关组织名称）。

   收到临时注册后，IANA 将检查名称
   和联系信息，然后在一个独立的、
   公开可见的临时注册列表中发布该注册。

   临时注册可以随时更新或放弃。
   当注册被放弃时，该媒体类型在任何意义上都不再
   注册；之后可以像任何其他尚未分配的媒体类型名称一样
   重新注册。

5.3.  审查和批准

   除临时标准树注册外，
   提交给 IANA 的注册将转交给媒体
   类型审查者。媒体类型审查者由
   IETF 应用领域主管指定，将审查注册，
   以确保其符合本文档规定的要求。
   不符合这些要求的注册将退回
   提交者进行修订。

   媒体类型审查者作出的决定可以按照
   [RFC2026] 第 6.5.4 节中规定的程序向 IESG 提出申诉。

   一旦媒体类型注册通过审查，IANA 将
   注册该媒体类型，并向社区提供
   媒体类型注册信息。

   对于来自其他标准
   相关组织的标准树注册，IANA 还将检查提交者是否
   确实属于公认标准相关组织。如果提交者
   当前尚未被认可为此类组织，则会请求 IESG
   确认其身份。标准树注册在继续进行之前
   必须获得 IESG 的认可。

5.4.  对媒体类型注册的评论

   社区成员可以将对已注册媒体类型的评论
   提交给 IANA，地址为 iana@iana.org。这些评论将由
   媒体类型审查者审查，然后在可能的情况下转交给
   媒体类型的“所有者”。评论提交者可以
   请求将其评论附加到媒体类型注册
   本身；如果 IANA 在与媒体类型审查者协商后
   批准，则该评论将与该类型注册一起
   提供访问。

5.5.  变更程序

   一旦媒体类型由 IANA 发布，其所有者可以
   请求更改其定义。上文对不同注册树的
   描述指定了每类注册的“所有者”。
   处理变更请求时使用与原始注册请求
   相适用的相同程序。

   媒体类型注册不得删除；如果某个媒体类型
   被认为不再适合使用，可以通过更改其“intended use”
   字段将其声明为 OBSOLETE；这类媒体类型将在
   IANA 发布的列表中明确标记。

8.  IANA 考虑

   本文档的目的是定义媒体
   类型和结构化语法后缀的 IANA 注册表，以及
   管理这些注册表的程序。此外，本文档要求 IANA
   维护一份标准相关组织列表，其中列出
   IESG 已批准其在标准树中进行媒体类型注册的组织。

   现有媒体类型注册表已经扩展，以包含一个
   临时注册部分。标准树中仅允许标准树
   注册，并且只能由 IANA 标准相关
   组织列表中的组织提出请求。有关
   临时注册的更多信息，见第 5.2.1 节。

   IANA 还在临时注册表顶部添加了以下
   注释：

      与其他一些临时 IANA 注册表不同，此注册表
      仅供临时使用。此注册表中的条目要么
      最终确定并移入主媒体类型注册表，要么
      被放弃并删除。此注册表中的条目仅适合
      用于开发和测试目的。

   结构化语法名称后缀注册表已按如下方式
   创建：

   o  名称为“Structured Syntax Suffix”注册表。

   o  注册过程在第 6 节中规定。

   o  注册表条目所需的信息以及条目
      格式在第 6.2 节中规定。

   o  注册表的初始内容在 [RFC6839] 中规定。

   媒体类型和结构化后缀注册表中的条目
   都将由 IANA 标注原始注册日期以及
   条目最近一次更新的日期。在本规范实施之前
   进行的注册，如有必要，可以如此标记，而不是
   标注具体日期。

   由于注册条目可以多次更新，IANA 还将
   维护每个注册的变更历史，使得
   可以确定注册在任意给定时间的
   状态。

附录 A.  祖父条款媒体类型

   一些具有无分面子类型名称、在 1996 年之前注册的
   媒体类型，如果按照本文档中的指南
   注册，将会被赋予分面名称，并放入供应商树
   或个人树。鼓励但不要求重新注册这些类型，
   以反映适当的树。本文档中概述的所有权和
   变更控制原则适用于这些类型，
   就如同它们已在上述树中注册一样。

   也可能不时出现这种情况：某个具有
   无分面子类型名称的媒体类型已经被广泛部署，但尚未
   注册。（请注意，这包括以
   “x-”前缀开头的子类型名称。）如果可能，这类媒体类型应该
   使用适当的分面子类型名称重新注册，并可能使用
   已弃用别名来标识原始名称（见第 4.2.9 节）。
   但是，如果无法做到，则经媒体类型审查者和 IESG
   双方批准后，该类型可以使用其无分面名称
   注册到适当的树中。

附录 B.  自 RFC 4288 以来的变更

   o  用于表示使用特定结构化语法的后缀现在已经
      得到完整规定，并定义了后缀注册
      流程。

   o  现在允许在供应商树或个人树中注册已广泛部署的
      未注册无分面类型名称，但须经
      媒体类型审查者和 IESG 批准。

   o  标准树注册流程已经修订，以
      包含专家审查，并进行了泛化，以涵盖
      非 IETF 流文档中的媒体类型等情况。

   o  注册模板中新增了片段标识符字段，
      并增加了关于如何规定片段标识符的简要
      指示。

   o  个人树注册的规范要求
      已更改为与供应商树相同。
      文本已更改为鼓励（但不要求）
      提供规范。

   o  定义其他树的流程已经澄清，
      明确要求 IETF 标准行动。

   o  已广泛部署且名称以“x-”开头的类型现在可以作为
      例外在供应商树中注册。

      小幅变更更容易进行。

      所有请求都由 IANA 而非 IESG 处理。

      在标准树中提前分配类型。

   o  整个文档进行了许多编辑性修改，

      更易于理解。

      已弃用别名列表的能力。

      未注册“x.”树的成员。与任何无分面
      类型一样，新增了特殊程序，允许在适当的树中注册
      此类类型。

      指定变更控制者进行更改，即使该控制者不是创建该类型的供应商或

   o  现在要求有限用途媒体类型注明所提供的
      使用该媒体类型的应用程序列表是否
      详尽无遗。

      要求名称必须以字母数字字符开头。

      [RFC6657] 中规定的变更。
