摘要

本规范描述了可验证凭证数据模型的一种扩展机制，该机制可用于通过 视觉、听觉或触觉媒介来表示可验证凭证。它涵盖了 将可验证凭证渲染到实体文档、数字图像、 屏幕阅读器或盲文输出。

    1. 引言

    当颁发者希望通过 视觉、听觉或触觉机制，以特定方式向观察者呈现可验证凭证时， 可以使用渲染方法。例如，一份 员工徽章凭证的颁发者可能希望包含其企业 徽标的丰富图像，并将员工信息以特定方式放置在徽章的特定区域中。 他们可能还希望为有与 视力相关的无障碍需求的个人提供徽章重要内容的音频朗读。

    本文档通篇使用的一些术语定义于 可验证凭证数据模型 v2.1规范的术语一节中。

    2. 数据模型

    以下各节概述了本规范用于 渲染方法的数据模型

    2.1 renderMethod 属性

    renderMethod 属性是 可验证凭证数据模型 v2.1规范中预留的扩展点。颁发者可以在 可验证凭证 中使用此属性来表示一种或多种首选的呈现方法。

    renderMethod
    renderMethod 属性的值必须指定一个或 多个渲染方法，软件可使用这些方法通过视觉、听觉或触觉机制来表达 可验证 凭证。每个 renderMethod 值都必须指定其 type，例如 TemplateRenderMethod。每个渲染 提示的确切内容由特定的 renderMethod type 定义决定。

    2.2 TemplateRenderMethod

    当颁发者 希望为可验证凭证 指定基于模板的渲染指令时， 他们可以添加一个使用 下述数据模型的 renderMethod 属性。

    属性 描述
    id 一个可选的字符串，遵循URL 标准，且在获取后 解引用到一个渲染模板。
    type 一个必需的字符串，其值必须为 TemplateRenderMethod。
    renderSuite 一个必需的字符串，用于标识 生成具体渲染时使用的算法。
    name 一个可选的、人类可读的字符串，可显示该字符串以提供 将要执行的渲染类型的提示。此属性可用于 使个人能够在多种呈现模式之间进行选择的 图形界面。
    description 一个可选的、人类可读的字符串，用于提供比 name 更详细的描述，说明特定渲染在何时可能有用。
    renderProperty 一个可选的列表，其中包含多个字符串值，每个值都符合 JavaScript 对象表示法（JSON） 指针语法，用于指定在使用此特定渲染方法时公开可验证 凭证中的哪些属性。如果未提供 renderProperty，则假定使用该渲染方法时会共享整个可验证 凭证。
    template 一个可选的URL 或映射，用于 提供或引用将用于执行渲染的 模板。如果该值是URL， 它可以是包含模板 代码的 data: URL [RFC2397]。如果该值 是一个映射，它必须符合以下规则：
    属性 描述
    id 一个必需的字符串，遵循 URL 标准，且 在获取后， 解引用到诸如 SVG 或 PDF 文件之类的模板。
    mediaType 一个推荐的字符串，用于标识 id 值的媒体类型， 如媒体类型 规范和注册程序中所规定。
    digestMultibase 模板文件的一个可选的 multibase 编码 Multihash。 multibase 值必须为 u（base64url-nopad），且 multihash 值必须为输出 256 位的 SHA-2（0x12）。
    digestMultibase 如果指定了 id，则为所引用渲染方法的一个可选的 multibase 编码 Multihash。 multibase 值必须为 u （base64url-nopad），且 multihash 值必须为输出 256 位的 SHA-2（0x12）。

    2.2.1 card 渲染 套件

    card 渲染套件使用 JSON 模板将 可验证 凭证转换为标准化的数据展示格式。此格式 使钱包能够以响应式卡片布局显示凭证，其中突出显示关键 数据，并提供可配置的附加字段。实现此方法的钱包 可以在其自己的卡片 UI 设计中渲染标准化 JSON 输出，从而即使钱包本身不 原生支持某种特定凭证类型，也能够显示凭证。

    模板是一个与 card 输出结构匹配的 JSON 对象。 模板中的字符串值可以是 JSON 指针字符串（如 JavaScript 对象表示法（JSON） 指针中所规定），它们引用可验证 凭证中的字段。在 处理模板时，会针对凭证数据对 JSON 指针字符串进行求值， 并用解析出的值替换它们。模板必须 符合下面定义的 JSON 模板架构，并且生成的输出 必须符合 card 输出架构。不支持跨多个 字段的复合数据；每个字段引用单个 JSON 指针。

    2.2.1.1 JSON 模板架构

    card 渲染套件的模板必须是一个 符合以下结构的 JSON 对象。模板结构与 输出结构匹配，但字符串值可以是字面量字符串或引用 可验证 凭证中字段的 JSON 指针字符串（以 / 开头）。模板在处理之前应该使用此 架构进行验证。

    属性 类型 描述
    name 字符串 一个必需的字符串，它可以是字面量显示名称，也可以是 引用凭证数据的 JSON 指针 字符串（例如 "/credentialSubject/degree/name"）。
    description 字符串 一个必需的字符串，它可以是字面量描述，也可以是 引用凭证数据的 JSON 指针 字符串。
    icon 字符串 一个可选的字符串，它可以是字面量 URL/data URI，也可以是 引用凭证数据的 JSON 指针 字符串。
    theme 映射 一个具有以下属性的可选颜色主题对象：
    • primaryColor（字符串）：作为字面量字符串或 JSON 指针的主色
    • accentColor（字符串）：作为字面量字符串或 JSON 指针的强调色
    fields 列表 一个自定义数据字段的必需有序列表。每个字段 都是一个具有以下内容的对象：
    • label（字符串）：字段 标签（必须是字面量字符串，而不是 JSON 指针）
    • value（字符串）：作为 JSON 指针字符串的字段 值（例如 "/issuer"）
    • language（字符串）：一个可选的语言标签（如用于标识 语言的标签中所规定），用于指示字段标签 和/或值的语言
    • direction（字符串）：一个可选的方向标签（如Web 上的字符串： 语言和方向元数据中所规定），用于指示字段标签 和/或值的文本方向
    validFrom 字符串 一个可选的字符串，它可以是字面量 ISO 8601 日期， 也可以是引用凭证数据（有效期开始日期）的 JSON 指针 字符串。
    validUntil 字符串 一个可选的字符串，它可以是字面量 ISO 8601 日期， 也可以是引用凭证数据（有效期结束日期）的 JSON 指针 字符串。

    2.2.1.2 卡片输出架构

    card 模板的输出必须是一个符合 以下结构的 JSON 对象：

    属性 类型 描述
    name 字符串 凭证卡片的一个必需显示名称。
    description 字符串 凭证卡片的一段必需描述文本。
    icon 字符串 用于在卡片上显示图标或图像的一个可选 URL 或 data URI。
    theme 映射 一个具有以下属性的可选颜色主题对象：
    • primaryColor（字符串）：用于背景和突出显示的主色
    • accentColor（字符串）：用于突出显示和强调的强调色
    fields 列表 一个自定义数据字段的必需有序列表。每个字段 都是一个具有以下内容的对象：
    • label（字符串）：字段 标签
    • value（字符串）：字段 值
    • language（字符串）：一个可选的语言标签（如用于标识 语言的标签中所规定），用于指示字段的语言
    • direction（字符串）：一个可选的方向标签（如Web 上的字符串： 语言和方向元数据中所规定），用于指示字段标签 和/或值的文本方向
    validFrom 字符串 一个可选的 ISO 8601 日期字符串，用于指示 凭证何时开始有效。
    validUntil 字符串 一个可选的 ISO 8601 日期字符串，用于指示 凭证何时失效。

    2.2.2 html 渲染 套件

    html 渲染套件允许模板作者提供一个 HTML 模板 来渲染可验证 凭证。HTML 可以远程引用，也可以 通过 data: URL 作为 template 或 template.id 的值（当 template 的值是对象时）。HTML 片段中的 JavaScript 负责渲染通过 HTML 数据块 （即 <script type="application/vc"></script>）提供的经过筛选的可验证 凭证数据，该数据块与 HTML 模板一起托管在 沙盒化 iframe 中。

    示例 7：使用 HTML 渲染套件的 VC 示例 
    {
  "@context": [
    "https://www.w3.org/ns/credentials/v2",
    "https://www.w3.org/ns/credentials/examples/v2"
  ],
  "type": [
    "VerifiableCredential",
    "NameCredential"
  ],
  "issuer": {
    "id": "did:example:1234",
    "name": "颁发者"
  },
  "credentialSubject": {
    "name": "示例名称",
    "notRendered": "不应出现"
  },
  "renderMethod": {
    "type": "TemplateRenderMethod",
    "renderSuite": "html",
    "renderProperty": [
      "/issuer/name",
      "/credentialSubject/name"
    ],
    "template": {
      "id": "https://test.example/credential-templates/NameCredential.html",
      "mediaType": "text/html",
      "digestMultibase": "zQmerWC85Wg6wFl9znFCwYxApG270iEu5h6JqWAPdhyxz2dR"
    },
    "outputPreference": {
      "accessMode": [
        "visual"
      ],
      "mediaType": "application/html",
      "style": {
        "width": "800px",
        "height": "800px"
      }
    }
  }
}

    实现必须提供一个允许 JavaScript 使用经过筛选的可验证 凭证数据安全 渲染 HTML 模板的环境。 此外，宿主页应该通过使用 Oblivious HTTP [RFC9458] 或其他借助保护性中继将发起请求的客户端与所请求源解除关联的方法， 保护所发出任何请求 （例如解引用 template.id）的隐私。

    使用以下术语来描述此环境：

    宿主页
    提供用于渲染 HTML 模板的安全环境。
    模板 代码
    在渲染方法中提供或由其远程引用的 HTML 片段。
    包装器 代码
    包装 HTML 模板以提供额外安全 限制以及与宿主页通信的代码。

    该环境至少必须阻止导航、加载外部 内容以及访问宿主页，以防止跟踪及其他 隐私危害。

    例如，基于浏览器的实现可以通过以下方式组合提供这样的环境： 对宿主页施加内容安全策略 [CSP3] 限制，对托管 HTML 模板的 iframe 进行沙箱化，以及使用包装 代码包装 HTML 模板以添加额外的 CSP 限制，并 与宿主页提供就绪和错误事件通信。

    2.2.2.1 宿主页

    宿主页（通常是钱包或可验证 凭证渲染器）必须 阻止 HTML 模板导航顶层浏览上下文、 访问外部内容、访问宿主页以及 加载任何远程 内容。

    如果使用宿主页，则适用以下规则：

    • 内容安全策略（CSP）限制必须包含 frame-src 'none'。 这会强制 iframe 使用 srcdoc 而不是 src，从而 阻止 浏览器加载 HTML 模板。反过来，这会强制 宿主页代码预加载远程引用的模板 代码，并在将模板注入包装器代码之前，根据相关 digestMultibase 值检查 响应。
    • 托管 HTML 模板的 iframe 上必须设置 sandbox="allow-scripts"， 以阻止导航和顶层访问。
    示例 8：最小宿主页 
    <html>
  <head>
    <meta http-equiv="content-security-policy" content="frame-src 'none'">
  </head>
  <body>
    <iframe id="renderer" sandbox="allow-scripts allow-modals" srcdoc=""></iframe>
  </body>
</html>

    2.2.2.1.3 就绪和 错误事件

    在包装器代码中创建的 iframe必须提供一个通信通道， 允许模板在渲染完成或 渲染过程中发生错误时通知宿主页。这可以使用 postMessage API 和由包装器代码设置的 MessageChannel 来实现。

    下面所示的 JavaScript 将添加到上述宿主页中， 为 iframe 添加 一个用于设置 MessageChannel 的 onload 事件。 宿主页 还会创建一个 Promise，当从 包装器代码收到 ready 消息时兑现， 或在收到 error 消息时拒绝。包装器代码 还提供一个供模板使用的 window.renderMethodReady 方法，用于 通知宿主页渲染已完成，或发送回 错误消息。

    示例 12：为设置 MessageChannel 而添加到宿主页的内容 
    // 一个在渲染就绪时兑现（或在渲染失败时拒绝）的 promise
// 可用于改为显示渲染结果或错误
let resolveRender;
let rejectRender;
const readyPromise = new Promise((resolve, reject) => {
  resolveRender = resolve;
  rejectRender = reject;
});

// 设置供 iframe 中的模板代码使用的通信通道
renderer.onload = () => {
  // 创建 MessageChannel；将一个端口传输到 iframe
  const channel = new MessageChannel();
  // 启动消息队列，以免 iframe 加载时丢失消息
  channel.port1.start();
  // 处理 `ready` 消息
  channel.port1.onmessage = function ready(event) {
    if(event.data === 'ready') {
      // iframe 已就绪，因此取消隐藏它
      resolveRender();
    } else {
      rejectRender(new Error(event.data?.error?.message));
    }
    channel.port1.onmessage = undefined;
  };
  // 发送 "start" 消息；将 `port2` 发送到 iframe 以用于返回通信
  renderer.contentWindow.postMessage('start', '*', [channel.port2]);
};

// 设置对就绪或错误事件的响应
// NOTE: 本节特定于钱包/渲染器的 UX 需求
readyPromise.then(() => {
  console.log('渲染已就绪');
  const renderer = document.getElementById('renderer');
  renderer.hidden = false;
}).catch(err => {
  const errorMessage = document.getElementById('error-message');
  errorMessage.style.display = 'block';
  errorMessage.innerText = '渲染失败：' + err.message;
  console.error('渲染失败', err);
});
    示例 13：用于连接 MessageChannel 并创建 `renderMethodReady` 的包装器代码附加内容 
    // 添加一个 promise，它将兑现为来自
// 父窗口的通信端口
const portPromise = new Promise(resolve => {
  window.addEventListener('message', function start(event) {
    if(event.data === 'start' && event.ports?.[0]) {
      window.removeEventListener('message', start);
      resolve(event.ports[0]);
    }
  });
});

// 将一个函数附加到 window，供模板在
// “就绪”（或发生错误）时调用，该函数将发送消息
// 给父级，以便父级决定是否显示 iframe
window.renderMethodReady = function(err) {
  portPromise.then(port => port.postMessage(
    !err ? 'ready' : {error: {message: err.message}}));
};

    使用此设置，模板 JavaScript 可以调用 window.renderMethodReady() 来通知宿主页渲染已完成，或者调用 window.renderMethodReady(new Error("error message")) 来通知宿主页 发生了错误。

    3. 算法

    以下各节概述了本规范用于 渲染方法的算法。

    3.1 卡片模板处理

    处理 card 模板时，必须执行 以下步骤：

    1. 根据上面定义的 JSON 模板架构验证模板 JSON 对象。 如果验证失败，处理必须停止，并且必须返回 错误。
    2. 对于模板对象中的每个字符串值：
      1. 如果字符串值以 / 开头（表示它是 JSON 指针）， 则使用 JSON 指针算法 JavaScript 对象表示法（JSON） 指针对其求值，并以 可验证 凭证作为目标文档。
      2. 如果 JSON 指针求值成功，则用 解析出的值替换 JSON 指针字符串。如果解析出的值不是字符串，则将其转换为 字符串表示形式。
      3. 如果 JSON 指针求值失败或返回 null，则行为由 实现定义。实现可以使用空字符串、 将该 值保留为 null，或发出错误信号。
      4. 如果字符串值不以 / 开头，则将其视为字面量字符串 并保持不变。
    3. 根据 card 输出架构验证生成的 JSON 对象。如果 验证失败，处理必须停止，并且必须返回错误。

    请注意，不支持跨多个字段的复合数据。模板中的每个字段 都引用单个 JSON 指针，该指针解析为凭证中的单个 值。

    3.2 HTML 模板处理

    以下各节概述了 html 渲染 套件用于安全渲染 HTML 模板的算法。只要安全和隐私结果以及输出相同，可以使用替代算法。

    3.2.1 宿主页

    宿主页必须创建一个 iframe 元素来托管 HTML 模板。 宿主页必须将 iframe 上的 sandbox 属性设置为 allow-scripts，以阻止导航和顶层访问。

    1. 令 vc 为要渲染的可验证 凭证。
    2. 令 renderMethod 为 vc 中选定的 renderMethod 属性，其中 renderMethod.type 为 TemplateRenderMethod，并且 renderMethod.renderSuite 为 html。
    3. 如果 renderMethod.template 是字符串，则令 template 为 renderMethod.template 的值。
    4. 如果 renderMethod.template 是映射，则令 template 为 获取 renderMethod.template.id 中 URL 的结果。

    如果存在 renderMethod.renderProperty，则宿主页必须筛选可验证 凭证 vc，使其仅包含 renderMethod.renderProperty 中指定的属性。如果 renderMethod.renderProperty 不存在，则使用整个可验证 凭证。

    此筛选必须通过将 Data Integrity ECDSA Cryptosuites v1.0 规范 [VC-DI-ECDSA] 的 第 3.4.13 节 selectJsonLd 中定义的 selectJsonLd 算法应用于 renderMethod.renderProperty 中存在的 JSON 指针 [RFC6901] 值来完成。

    宿主页必须通过将经过筛选的 可验证 凭证和 HTML 模板嵌入到上面定义的包装器代码 模板中来创建包装器代码。

    1. 令 wrapperCode 为一个 HTML 文档，其 <head> 中包含 <meta http-equiv="Content-Security-Policy" content="default-src data: 'unsafe-inline'">。
    2. 令 datablock 为一个 type 为 application/vc 的 HTML 数据块。
    3. 将 datablock 的内容设置为经过筛选的可验证 凭证 的字符串化 JSON 格式。
    4. 将 datablock 插入 wrapperCode 的 <head> 中。
    5. 将 template 的值插入 wrapperCode 的 <body> 中。

    宿主页必须将 iframe 的 srcdoc 属性设置为生成的包装器代码。

    1. 将 iframe 的 srcdoc 属性设置为 wrapperCode 的字符串化 HTML。

    宿主页必须按照上文所述，与包装器代码建立通信 通道，以接收 ready 和 error 消息。

    1. 令 renderPromise 为一个新的 Promise，它：
      1. 在 resolve 时，可用于向用户显示 iframe。
      2. 在 reject 时，向用户显示错误消息。
    2. 在 iframe 的 onload 事件中：
      1. 令 channel 为一个新的 MessageChannel。
      2. 在 channel 上创建并启动一个新的 port1 监听器，用于监听 现在通过 wrapperCode 注入 iframe 的 template 中代码发送的 ready 消息。
      3. 在 port1 监听器中，如果收到 ready 消息，则兑现 renderPromise。 如果收到 error 消息，则使用错误 消息拒绝 renderPromise。
      4. 使用 postMessage 将 channel 的 port2 发送到 iframe 内容窗口。

    宿主页应该使用 renderPromise 来确定渲染何时 完成，或渲染期间是否发生错误。

    3.2.2 包装器代码

    包装器代码必须设置为通过 MessageChannel 接收来自宿主页的 通信，并提供 window.renderMethodReady 方法供 模板代码使用。

    1. 在 window.onload 事件中...
      1. 令 port 为通过 message 事件从宿主页接收到的 MessagePort。
      2. 创建 window.renderMethodReady 函数，该函数...
        1. 如果调用时没有参数，则通过 port 向宿主页发送 ready 消息。
        2. 如果调用时传入 Error 参数，则通过 port 向宿主页 发送包含错误消息的 error 消息。

    A. 威胁模型

    本节为非规范性内容。

    本节总结了本规范的威胁模型，涵盖与渲染方法的 发布、检索和处理相关的安全和隐私考虑。完整分析，包括响应和 数据流图，见 可验证凭证渲染方法威胁 模型。

    建议读者在阅读本节之前，熟悉 可验证凭证数据模型 v2.1 规范的 威胁模型一节中提供的通用威胁模型。实现者 应将该规范中提供的通用分析应用于 本规范提供的每项具体功能。

    A.1 目标威胁

    1. 不受控制的凭证呈现 安全 - 如果没有由颁发者声明的渲染方法，则如何显示 可验证 凭证完全由持有者或验证者 软件决定， 该软件可能省略声明、重新排序或重新标记字段、丢弃有效性信息，或者 应用具有误导性的品牌信息，因此即使凭证是真实的，观察者也会对 颁发者所证明的内容形成错误理解。

    A.2 实现威胁

    1. 不受信任数据的不安全渲染 安全 - html 渲染套件会执行模板提供的代码，并使用作为不受信任输入的凭证 值，因此，即使敌意内容包含在格式正确且经过验证的凭证中，也可能尝试在 渲染期间访问周围的 宿主页、导航离开或联系外部位置。

    A.3 部署威胁

    1. 通过模板和资源获取进行跟踪 隐私 - 通过位置检索模板或其引用的资源，会向 颁发者或 主机暴露正在渲染凭证这一事实，而每个凭证独有的 位置或编码到传出请求中的凭证数据，会将每次渲染 转变为跟踪或数据外泄信号。

    A.4 外部威胁

    1. 有害的渲染输出 安全 - 由于渲染模板控制视觉、听觉和触觉输出， 敌意模板可以被设计为伤害查看它的人，例如使用 能够诱发癫痫发作的闪烁图案或突然出现的扰乱性声音， 即使底层凭证是真实的也是如此。

    A.5 依赖项威胁

    1. 继承的渲染环境攻击面 安全 - html 渲染套件依赖所选 渲染环境提供的限制，因此，任何使沙盒能够被逃逸、策略能够被 绕过，或者模板与宿主之间的隔离被破坏的缺陷，即使渲染方法完全按照规定使用，也会成为 渲染过程中的缺陷。

    安全考虑

    W3C 正在迁移到一种整体性的威胁建模方法， 并且正在逐步弃用新规范中的安全考虑章节。 有关安全考虑的文档，请参阅附录 A. 威胁模型。

    隐私考虑

    W3C 正在迁移到一种整体性的威胁建模方法， 并且正在逐步弃用新规范中的隐私考虑章节。有关隐私 考虑的文档，请参阅附录 A. 威胁模型。

    B. 与其他技术的关系

    本节为非规范性内容。

    为传达一种由颁发者首选且人类可感知的可验证凭证呈现形式， 我们考察了若干现有方法和技术。本节总结了这些替代方案，并说明为何选择 本规范中所述的呈现方法方案。

    由客户端决定的呈现

    不定义任何机制，并将呈现交由持有者或验证者 软件处理，无需额外数据，但这使颁发者无法传达 预期的呈现形式，因而凭证呈现不一致，声明或 品牌形象可能被不实呈现，如 不受控制的 凭证呈现中所述。凭证 格式，例如 ISO/IEC 18013-5 移动驾驶 执照（mDL）和 JSON Web Token （RFC 7519）采用这种 方式，只定义凭证携带的声明，而将其 呈现交由使用方软件处理。Microsoft 的 信息卡 （CardSpace）现已停用，它采用了这种方式的一种受限变体，允许 颁发者仅提供 卡片名称和徽标，由身份选择器使用统一的卡片框架 进行呈现。本规范添加了一种由颁发者声明的替代方案， 而不是禁止由客户端决定的呈现。

    特定于凭证类型的显示注册表

    通过注册表按凭证类型标准化呈现，可使已知类型获得一致的 呈现效果，但需要预先了解每种类型，无法 扩展至自定义凭证，也无法表达颁发者特有的品牌形象。 平台钱包，例如 Apple 钱包 （PassKit）、 Google 钱包和 Samsung 钱包采用这种 方式，在由平台控制的固定布局中呈现一组固定的预定义通行证或对象类型， 其中颁发者可以填入字段值 和资源，但无法表达平台目录之外的布局或品牌形象。 本规范定义的呈现方法策略则随凭证一同传输，或 由凭证引用，因此即使是不熟悉的类型，也能按照 其颁发者的意图呈现。

    这种集中式、受控且以注册表为中心的解决方案也与 原本被规定为 以下生态系统组成部分的分布式、去中心化且无需许可的模式相悖： 去中心化标识符（DID）和 可验证凭证（VC）。

    PDF、SVG 和 HTML 文档等呈现格式

    分发完全呈现的 PDF、静态 SVG 或 HTML 文档具有 自包含性并受到广泛支持，但此类快照无法适应 选择性披露，无法根据已验证数据重新呈现，并且 未绑定到受保护的内容。本规范将这些格式作为 在呈现时与声明值结合使用的模板，而不是成品 文档。

    数据完整性和证明机制

    本规范不定义新的完整性机制，而是依赖于 现有的保护机制，例如可验证凭证数据完整性 1.0和 digestMultibase属性，以 将被引用的模板 绑定到凭证。读者可以通过阅读 篡改未受保护的外部资源威胁来了解这些通用的 保护机制，该威胁载于 可验证凭证威胁模型中。

    SD-JWT VC 类型元数据呈现

    SD-JWT VC 定义了一个rendering属性，用于在支持 一组固定样式属性的simple方法与禁止 执行任何代码并将声明值替换到 SVG 文本占位符中的svg_templates方法之间进行选择。该小组研究了这种方法，发现它对于实际 用例而言限制过多：由于占位符只能出现在文本节点中，且无法运行任何代码， 因此无法表达条件字段、长度可变的 列表、值格式化和响应式布局等数据驱动的呈现工具。这些 功能是医疗保健、零售以及 银行/金融等领域的要求。相比之下，本规范并不绑定到单一的 凭证序列化格式，而是定义了跨越 无代码声明式card套件、在 受限的“沙盒化”环境中执行的数据驱动html套件，以及静态nfc套件的呈现套件。
