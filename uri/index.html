Abstract

   A Uniform Resource Identifier (URI) is a compact sequence of
   characters that identifies an abstract or physical resource.  This
   specification defines the generic URI syntax and a process for
   resolving URI references that might be in relative form, along with
   guidelines and security considerations for the use of URIs on the
   Internet.  The URI syntax defines a grammar that is a superset of all
   valid URIs, allowing an implementation to parse the common components
   of a URI reference without knowing the scheme-specific requirements
   of every possible identifier.  This specification does not define a
   generative grammar for URIs; that task is performed by the individual
   specifications of each URI scheme.

1.  引言

   统一资源标识符 (URI) 提供了一种简单且可扩展的
   资源标识方式。本 URI 语法
   和语义规范源自万维网
   全球信息倡议所引入的概念，该倡议使用这些标识符
   可追溯至 1990 年，并在《WWW 中的通用资源标识符》
   [RFC1630] 中有所描述。该语法旨在满足
   《互联网资源定位符的功能建议》
   [RFC1736] 和《统一
   资源名称的功能要求》[RFC1737] 中提出的建议。

   本文档废止 [RFC2396]，后者合并了《统一资源
   定位符》[RFC1738] 和《相对统一资源定位符》
   [RFC1808]，以便为所有 URI 定义单一的通用语法。
   本文档还废止 [RFC2732]，后者引入了 IPv6 地址语法。
   本文档排除 RFC 1738 中定义各个 URI 方案具体语法的
   部分；这些部分将作为独立
   文档更新。新 URI 方案的注册流程
   由 [BCP35] 单独定义。新 URI
   方案设计者的建议可见 [RFC2718]。相对于 RFC
   2396 的所有重要变更均在附录 D中注明。

   本规范按照 [BCP19] 中给出的定义使用术语“字符”和“编码字符
   集”，并使用“字符编码”一词代替 [BCP19] 所称的
   “charset”。

1.1.  URI 概述

   URI 具有以下特征：

   统一性

      统一性提供了多项益处。它允许不同类型
      的资源标识符在同一上下文中使用，即使
      用于访问这些资源的机制可能不同。它
      允许在不同类型的资源标识符之间统一解释共同语法
      约定的语义。它
      允许引入新类型的资源标识符，而不会
      干扰现有标识符的使用方式。它
      允许标识符在许多不同上下文中重用，
      从而使新的应用程序或协议能够利用一个预先
      存在的、大型且广泛使用的资源标识符集合。

   资源

      本规范不限制什么可以成为
      资源的范围；相反，“资源”一词以一般意义使用，
      指任何可能由 URI 标识的事物。常见示例
      包括电子文档、图像、具有一致用途的信息
      来源（例如“洛杉矶今天的天气报告”）、服务
      （例如 HTTP 到 SMS 网关）以及
      其他资源的集合。资源不一定
      可通过互联网访问；例如，人、公司以及
      图书馆中的装订书籍也可以是资源。同样，
      抽象概念也可以是资源，例如数学方程的运算符和
      操作数、关系的类型
      （例如“父级”或“雇员”），或者数值（例如零、
      一和无穷大）。

   标识符

      标识符包含在其标识
      范围内将所标识对象与所有其他事物区分开来所需的信息。
      本文对“标识”和“进行标识”的使用
      指的就是将一个资源与所有
      其他资源区分开来的目的，而不论该目的如何实现
      （例如通过名称、地址或上下文）。不应
      将这些术语误解为假设标识符定义或包含了
      所引用对象的身份，尽管某些标识符
      可能确实如此。也不应假定使用 URI 的系统
      会访问所标识的资源：在许多情况下，
      URI 仅用于指称资源，并无访问这些资源的意图。
      同样，被标识的“一个”资源本质上可能并非
      单一对象（例如，资源可以是命名集合，或
      随时间变化的映射）。

   URI 是由字符序列组成的标识符，
   该序列与第 3 节中名为 <URI> 的语法规则匹配。它通过单独定义的
   可扩展命名方案集合（第 3.1 节）
   实现对资源的统一标识。如何
   实现、分配或启用该标识，则委托给
   各方案规范。

   本规范不对
   资源的性质、应用程序为何可能需要引用
   资源的原因，或哪些系统可能为了
   标识资源而使用 URI 作任何限制。本规范不要求
   URI 随时间持续标识同一资源，尽管这是
   所有 URI 方案的共同目标。不过，本

   规范中的任何内容都不会阻止应用程序将自身限制为
   特定类型的资源，或限制为保持
   该应用程序所需特征的 URI 子集。

   URI 具有全局作用域，并且无论上下文如何都以一致方式解释，

   最终用户的上下文有关。例如，“http://localhost/”
   对该引用的每个用户都具有相同解释，即使
   与“localhost”对应的网络接口对于
   每个最终用户可能不同：解释与访问相互独立。

   最终用户本地上下文进行标识的 URI 只应在
   上下文本身就是资源定义特征时使用，
   例如在线帮助手册引用最终
   用户文件系统中的文件时（例如“file:///etc/hosts”）。

1.1.1.  通用语法

   每个 URI 都以方案名称开头，如第 3.1 节所定义，该名称
   引用一个用于在该
   方案内分配标识符的规范。因此，URI 语法是一种联合且可扩展的命名
   系统，其中每个方案的规范可以进一步限制
   使用该方案之标识符的语法和语义。

   本规范定义 URI 语法中
   所有 URI 方案都必须具备或许多 URI 方案共有的元素。因此，
   它定义实现与方案
   无关的 URI 引用解析机制所需的语法和语义，通过这种机制，
   可以将 URI 的方案相关处理推迟到
   需要方案相关语义时再进行。同样，使用 URI 引用的协议和数据
   格式可以引用本
   规范，将其作为所有 URI 所允许语法范围的定义，
   包括尚未定义的方案。这
   将标识方案的发展与使用
   URI 的协议、数据格式和实现的发展解耦。

   通用 URI 语法解析器可以将任何 URI 引用解析为
   其主要组件。确定方案后，可以
   对这些组件进行进一步的方案特定解析。换句话说，
   URI 通用语法是所有 URI
   方案语法的超集。

1.1.3.  URI、URL 和 URN

   URI 可以进一步分类为定位符、名称或二者兼有。
   “统一资源定位符”(URL) 一词指 URI 的一个子集，
   它们除了标识资源外，还通过描述其主要访问机制
   （例如其网络“位置”）提供
   定位该资源的方法。“统一资源名称”
   (URN) 一词在历史上既用于指“urn”方案
   [RFC2141] 下的 URI，这些 URI 即使资源不再存在或
   不可用，也要求保持全局唯一且持久；
   也用于指具有名称属性的任何其他 URI。

   单个方案不必仅被分类为
   “名称”或“定位符”之一。来自任何给定方案的 URI 实例
   可以具有名称、定位符或二者的特征，这通常
   取决于命名机构分配
   标识符时的持久性和谨慎程度，而不是
   方案本身的任何特性。未来的规范及相关文档应该
   使用一般性术语“URI”，而不是更具限制性的术语
   “URL”和“URN”[RFC3305]。

1.2.  设计考虑

1.2.1.  转录

   URI 语法在设计时将全球范围内的转录作为
   主要考虑因素之一。URI 是来自一个
   非常有限集合的字符序列：基本拉丁字母、数字
   和少量特殊字符。URI 可以用多种
   方式表示；例如纸上的墨迹、屏幕上的像素，或
   字符编码八位字节序列。URI 的解释仅取决于
   所使用的字符，而不取决于这些字符在
   网络协议中如何表示。

   转录目标可以通过一个简单场景来说明。
   想象两位同事 Sam 和 Kim 在一次
   国际会议期间坐在酒吧里交流研究想法。Sam 向 Kim
   询问一个可以获取更多信息的位置，于是 Kim 将研究
   站点的 URI 写在餐巾纸上。回家后，Sam 拿出
   餐巾纸，将 URI 输入计算机，计算机随后检索
   Kim 所指的信息。

   该场景揭示了若干设计考虑：

   o  URI 是字符序列，并不总是表示为
      八位字节序列。

   o  URI 可能从非网络来源转录，因此
      应由最有可能能够
      输入计算机的字符组成，同时受到
      不同语言和
      区域设置中的键盘（及相关输入设备）限制。

   o  URI 经常需要由人记忆，而当 URI 由有意义或
      熟悉的组件组成时，人们更容易记住它。

   这些设计考虑并不总是一致。例如，
   URI 组件最有意义的名称往往需要
   某些无法在部分系统中输入的字符。
   将资源标识符从一种媒介转录到另一种媒介的能力，
   被认为比让 URI 由最有意义的组件组成
   更为重要。

   在本地或区域上下文中，随着技术改进，用户
   可能会受益于能够使用更广泛的字符；
   此类使用不由本规范定义。如果方案或引用 URI 的协议元素
   允许这种表示，则可以在 URI 内使用百分号编码的
   八位字节（第 2.1 节）来表示 US-ASCII 编码字符集范围之外的字符

1.2.2.  将标识与交互分离

   对 URI 的一个常见误解是，它们只用于引用
   可访问的资源。URI 本身只提供
   标识；URI 的存在既不保证也不暗示
   可以访问资源。相反，与
   URI 引用关联的任何操作都由其所在的协议元素、数据格式
   属性或自然语言文本定义。

   给定一个 URI，系统可以尝试对资源执行各种
   操作，这些操作可以用“访问”、
   “更新”、“替换”或“查找属性”等词来描述。这些操作
   由使用 URI 的协议定义，而不是由本

2.4.  何时编码或解码

   在正常情况下，URI 内八位字节进行
   百分号编码的唯一时机是在从
   各组成部分生成 URI 的过程中。此时，实现确定哪些
   保留字符将用作子组件分隔符，
   哪些字符可以安全地用作数据。一旦生成，URI 始终
   处于百分号编码形式。

   当 URI 被解引用时，与方案特定解引用过程
   有关的组件和子组件（如果有）
   必须在安全解码这些组件内的百分号编码八位字节之前
   被解析并分离，否则数据可能会被
   误认为组件分隔符。唯一的例外是
   对应于非保留集合字符的百分号编码八位字节，
   它们可以随时解码。例如，与波浪号（“~”）
   字符对应的八位字节经常被旧版 URI 处理实现编码为“%7E”；
   可以将“%7E”替换为
   “~”，而不会改变其解释。

   由于百分号（“%”）字符用作
   百分号编码八位字节的指示符，因此如果该八位字节要在 URI 中作为数据使用，
   必须将它百分号编码为“%25”。实现不得
   对同一字符串进行多次百分号编码或解码，因为对
   已经解码的字符串再次解码可能导致将百分号
   数据八位字节误解释为百分号编码的开始，或者在
   对已经百分号编码的字符串再次编码时发生相反情况。

3.1.  方案

   每个 URI 都以方案名称开头，该名称引用
   在该方案中分配标识符的规范。因此，URI 语法是
   一种联合且可扩展的命名系统，其中每个方案的
   规范可以进一步限制
   使用该方案的标识符语法和语义。

   方案名称由字符序列组成，以
   字母开头，后跟字母、数字、加号
   （“+”）、句点（“.”）或连字符（“-”）的任意组合。虽然方案名称不区分
   大小写，但规范形式为小写，并且规定方案的文档
   必须使用小写字母。为提高健壮性，实现
   应该接受方案名称中的大写字母，将其视为与小写字母等价
   （例如既允许“HTTP”也允许“http”），但为了
   保持一致性，只应该生成小写方案名称。

      scheme      = ALPHA *( ALPHA / DIGIT / "+" / "-" / "." )

   本文档不规定各个具体方案。新 URI 方案的
   注册过程由 [BCP35] 单独定义。
   方案注册表维护方案名称与
   其规范之间的映射。新 URI 方案设计者的建议可见
   [RFC2718]。URI 方案规范必须定义自己的
   语法，使所有匹配其方案特定语法的字符串
   也都匹配 <absolute-URI> 语法，如第 4.3 节所述。

   当遇到违反一个或多个方案特定
   限制的 URI 时，方案特定解析过程应该将该
   引用标记为错误，而不是忽略未使用部分；这样做
   可以减少等价 URI 的数量，并有助于发现
   对通用语法的滥用，这可能表明 URI 是为了
   误导用户而构造的（第 7.6 节）。

   许多 URI 方案包含用于命名
   权威机构的分层元素，使 URI 其余部分所定义的

   进一步委托）。通用语法提供了一种通用
   方法，用于区分基于注册名称或
   服务器地址的权威部分，以及可选的端口和用户信息。

   authority 组件前面是双斜杠（“//”），其终止位置为
   下一个斜杠（“/”）、问号（“?”）或数字

   拒绝这些数据，并且应该拒绝以未加密形式存储此类数据。

   图形化超文本浏览器，应在可行时以

   当 userinfo 被误导性构造成看起来像可信域名时，
   这种呈现方式将有助于用户
   识别它（第 7.6 节）。

3.2.3.  端口

   authority 的 port 子组件由 host 后面可选的
   十进制端口号指定，并通过一个
   冒号（“:”）字符与 host 分隔。

      port        = *DIGIT

   方案可以定义默认端口。例如，“http”方案
   定义默认端口“80”，对应其保留的 TCP
   端口号。端口号所指定的端口类型（例如
   TCP、UDP、SCTP）由 URI 方案定义。如果
   port 为空，或者其值与
   方案默认端口相同，URI 生成器和规范化器应该省略 port 组件及其“:”分隔符。

3.3.  路径

   path 组件包含通常以分层
   形式组织的数据，它与非分层 query 组件中的数据
   （第 3.4 节）一起，用于在 URI
   方案和命名权威机构（如果有）的作用域内标识资源。path 在
   第一个问号（“?”）或数字符号（“#”）字符处终止，或者
   在 URI 末尾终止。

   如果 URI 包含 authority 组件，则 path 组件
   必须为空或以斜杠（“/”）字符开头。如果 URI
   不包含 authority 组件，则 path 不能以
   两个斜杠字符（“//”）开头。此外，URI 引用
   （第 4.1 节）可以是相对路径引用，此时
   第一个路径段不能包含冒号（“:”）字符。ABNF
   需要五条独立规则来消除这些情况的歧义，
   对于给定 URI 引用中的 path 子字符串，只有其中一条
   会匹配。我们使用通用术语“path component”来描述
   解析器与这些规则之一匹配的 URI 子字符串。

      path          = path-abempty    ; 以“/”开头或为空
                    / path-absolute   ; 以“/”开头但不是“//”
                    / path-noscheme   ; 以不含冒号的段开头
                    / path-rootless   ; 以段开头
                    / path-empty      ; 零个字符

      path-abempty  = *( "/" segment )
      path-absolute = "/" [ segment-nz *( "/" segment ) ]
      path-noscheme = segment-nz-nc *( "/" segment )
      path-rootless = segment-nz *( "/" segment )
      path-empty    = 0<pchar>

   path 由一系列以斜杠

   将用作相对引用的上下文时，才要求使用斜杠字符
   表示层次。例如，URI
   <mailto:fred@example.com> 的 path 是“fred@example.com”，而
   URI <foo://info.example.com?fred> 的 path 为空。

   路径段“.”和“..”也称为点段，
   被定义用于 path 名称层次中的相对引用。它们
   用于相对路径引用
   （第 4.2 节）的开头，以指示命名层次
   树中的相对位置。这与某些操作系统
   文件目录结构中分别表示当前目录
   和父目录的作用类似。不过，与文件
   系统不同，这些点段仅在 URI path
   层次中解释，并在解析过程中被移除（第
   5.2 节）。

   除分层 path 中的点段外，通用语法将路径段
   视为不透明。URI 生成应用程序
   经常使用段中允许的保留字符来分隔
   方案特定或解引用处理器特定的子组件。例如，
   分号（“;”）和等号（“=”）保留字符经常
   用于分隔适用于该段的参数和参数值。
   逗号（“,”）保留字符也常用于
   类似目的。例如，一个 URI 生成器可能使用诸如
   “name;v=1.1”的段表示对
   “name”1.1 版本的引用，而另一个可能使用诸如“name,1.1”的段
   表示相同内容。参数类型可以由方案特定
   语义定义，但在大多数情况下，参数语法特定于
   URI 解引用算法的实现。

3.5.  片段

   URI 的 fragment identifier 组件允许通过引用主
   资源及附加标识信息，间接
   标识次级资源。所标识的
   次级资源可以是主资源的某部分或子集、主资源表示的某种视图，或者
   由这些表示定义或描述的其他资源。
   fragment identifier 组件通过
   数字符号（“#”）字符的存在来指示，并由 URI 的末尾终止。

      fragment    = *( pchar / "/" / "?" )

   fragment identifier 的语义由
   对主资源执行检索操作可能产生的表示集合定义。
   因此，fragment 的格式和解析取决于潜在检索到的
   表示的媒体类型 [RFC2046]，尽管只有在
   URI 被解引用时才会实际执行这种检索。如果不存在此类表示，
   则 fragment 的语义被视为未知，实际上
   不受约束。fragment identifier 的语义独立于
   URI 方案，因此不能由方案规范重新定义。

   各个媒体类型可以对 fragment identifier 语法定义自己的
   限制或内部结构，以指定
   该媒体类型可将其标识为次级资源的
   不同类型子集、视图或外部引用。如果
   主资源具有多个表示（对
   根据检索请求属性选择表示的资源而言，这很常见，
   也称为内容协商），那么 fragment 所标识的内容应该在所有这些
   表示之间保持一致。每个表示都应该定义
   fragment，使其无论如何表示都对应
   同一个次级资源，或者应该让 fragment
   保持未定义（即未找到）。

4.  使用

   当应用程序引用 URI 时，并不总是使用
   “URI”语法规则定义的完整引用形式。为了节省
   空间并利用分层局部性，许多互联网
   协议元素和媒体类型格式允许使用 URI 的缩写形式，
   而另一些则将语法限制为特定形式的 URI。
   本规范定义最常见的引用语法形式，
   因为它们会影响并依赖于
   通用语法的设计，需要统一解析算法才能
   一致地解释。

4.1.  URI 引用

   URI-reference 用于表示资源
   标识符最常见的使用形式。

      URI-reference = URI / relative-ref

   URI-reference 要么是 URI，要么是相对引用。如果
   URI-reference 的前缀不匹配方案后跟
   其冒号分隔符的语法，则该 URI-reference 是相对
   引用。

   URI-reference 通常首先被解析为五个 URI
   组件，以确定存在哪些组件以及
   该引用是否为相对引用。然后解析每个组件
   的子部分并对其进行验证。URI-reference 的 ABNF
   加上“首次匹配优先”的消歧规则，足以
   定义通用语法的验证型解析器。熟悉
   正则表达式的读者可参阅附录 B，其中给出了一个
   非验证型 URI-reference 解析器示例，它会获取任意
   给定字符串并提取 URI 组件。

4.2.  相对引用

   相对引用利用分层语法
   （第 1.2.3 节），以相对于另一个分层 URI 的命名空间
   表示 URI 引用。

      relative-ref  = relative-part [ "?" query ] [ "#" fragment ]

      relative-part = "//" authority path-abempty
                    / path-absolute
                    / path-noscheme
                    / path-empty

   相对引用所引用的 URI，也称为目标
   URI，通过应用第 5 节的引用解析算法获得。

   以两个斜杠字符开头的相对引用称为
   网络路径引用；这类引用很少使用。以
   单个斜杠字符开头的相对引用称为
   绝对路径引用。不以斜杠字符开头的相对引用称为
   相对路径引用。

   包含冒号字符的路径段（例如“this:that”）
   不能用作相对路径引用的第一个段，因为
   它会被误认为方案名称。此类段必须
   在前面加一个点段（例如“https://www.rfc-editor.org/rfc/this:that”），以构成相对
   路径引用。

4.3.  绝对 URI

   某些协议元素只允许没有
   fragment identifier 的 URI 绝对形式。例如，为随后
   由相对引用使用定义基础 URI，需要一个
   不允许 fragment 的 absolute-URI 语法规则。

      absolute-URI  = scheme ":" hier-part [ "?" query ]

   URI 方案规范必须定义自己的语法，使所有
   匹配其方案特定语法的字符串也都匹配
   <absolute-URI> 语法。无论 fragment identifier 对
   可通过该方案标识的资源是否适用，方案规范都不会定义
   fragment identifier 的语法或用法，因为 fragment 标识
   与方案定义正交。不过，鼓励方案规范
   包含大量示例，包括
   在适当情况下展示该方案 URI 与 fragment identifier
   一起使用的示例。

4.4.  同文档引用

   当 URI 引用所引用的 URI 除其 fragment
   组件（如果有）外，与基础 URI（第 5.1 节）
   相同时，该引用称为“同文档”引用。最常见的
   同文档引用示例是为空的相对引用，或者仅包含
   数字符号（“#”）分隔符及其后的
   fragment identifier 的相对引用。

   当为了检索
   操作而解引用同文档引用时，该引用的目标被定义为与该引用位于同一个
   实体（表示、文档或消息）中；
   因此，解引用不应该导致新的检索操作。

   在比较基础 URI 和目标 URI 之前对其进行规范化，
   如第 6.2.2 节和第 6.2.3 节所述，是允许的，但实践中很少
   执行。规范化可能扩大同
   文档引用的集合，这可能对某些缓存
   应用程序有益。因此，引用作者不应该假定某个
   略有不同但等价的引用 URI，一定会（或一定不会）
   被任何给定应用程序解释为同文档引用。

4.5.  后缀引用

   URI 语法被设计用于无歧义地引用资源，并通过
   URI 方案实现可扩展性。不过，随着 URI 标识和
   使用变得普遍，传统媒体（电视、广播、
   报纸、广告牌等）越来越多地使用 URI 的后缀作为

RFC 3986                   URI 通用语法                   2005 年 1 月


   引用，仅由 URI 的 authority 和 path
   部分组成，例如

      www.w3.org/Addressing/

   或者仅使用一个 DNS 注册名称。这类引用
   主要供人解释，而不是供机器使用，
   假设基于上下文的启发式规则足以
   补全 URI（例如，大多数以“www”开头的注册名称
   很可能具有“http://”URI 前缀）。虽然没有
   一套用于消除 URI 后缀歧义的标准启发式规则，但许多
   客户端实现允许用户输入它们并
   通过启发式方式解析。

   尽管使用后缀引用的做法很常见，
   但应尽可能避免，并且在
   预期长期引用的情况下绝不应该使用。上述启发式规则
   会随着时间变化，特别是当新的 URI 方案
   变得流行时，并且脱离上下文使用时经常出错。
   此外，它们还可能导致类似
   [RFC1535] 所述的安全问题。

   由于 URI 后缀与相对路径引用具有相同语法，
   因此不能在预期相对
   引用的上下文中使用后缀引用。因此，后缀引用仅限于
   没有定义基础 URI 的位置，例如对话框和
   离线广告。

5.  引用解析

   本节定义在允许相对引用的上下文中解析 URI 引用的
   过程，使结果成为
   与第 3 节的 <URI> 语法规则匹配的字符串。

5.1.  确立基础 URI

   “relative”一词意味着存在一个“base URI”，相对引用
   是相对于它应用的。除仅 fragment 的
   引用（第 4.4 节）外，只有在基础 URI
   已知时才能使用相对引用。解析器必须在
   解析可能为相对引用的 URI 引用之前确立基础 URI。
   基础 URI 必须符合 <absolute-URI> 语法规则（第 4.3 节）。如果
   基础 URI 从某个 URI 引用获得，则该引用必须
   在用作基础 URI 之前转换为绝对形式，并移除任何 fragment 组件。

5.1.1.  嵌入内容中的基础 URI

   在某些媒体类型中，相对引用的基础 URI 可以
   嵌入内容本身，以便解析器可以轻松
   获取它。这对于描述性文档可能很有用，例如
   目录，因为这类文档可能通过不同于其通常检索上下文的
   协议传输给其他人（例如电子邮件或
   USENET 新闻）。

   为每种媒体类型规定如何嵌入基础 URI
   超出本规范的范围。适当的语法（如果
   可用）由与每种媒体类型关联的
   数据格式规范描述。

5.1.2.  来自封装实体的基础 URI

   如果没有嵌入基础 URI，则基础 URI 由
   表示的检索上下文定义。对于封装
   在另一个实体（例如消息或归档）中的文档，检索
   上下文就是该实体。因此，一个
   表示的默认基础 URI 是封装该
   表示的实体的基础 URI。

   MHTML
   [RFC2557] 定义了在 MIME 容器类型
   （例如 message 和 multipart 类型）中嵌入基础 URI 的机制。不使用 MIME 消息首部语法，

   可以定义自己的语法，将基础 URI 定义为
   消息的一部分。

5.1.3.  来自检索 URI 的基础 URI

   如果没有嵌入基础 URI，并且表示未被封装
   在其他某个实体中，那么，如果曾使用 URI 来检索该
   表示，该 URI 应被视为基础 URI。请注意，
   如果检索是重定向请求的结果，则最后使用的 URI
   （即实际检索到
   表示的 URI）就是基础 URI。

5.1.4.  默认基础 URI

   如果上述条件均不适用，则基础 URI
   由应用程序上下文定义。由于这种定义
   必然取决于应用程序，未能使用其他方法之一
   定义基础 URI，可能导致同一内容被
   不同类型的应用程序以不同方式解释。

   包含相对引用的表示的发送者
   负责确保能够为这些引用确立基础 URI。
   除仅 fragment 的引用外，只有在基础 URI
   定义明确的情况下，才能可靠地使用相对
   引用。

5.2.1.  预解析基础 URI

   基础 URI (Base) 按照
   第 5.1 节的过程确立，并解析为
   第 3 节所述的五个主要组件。请注意，基础 URI 中只有 scheme 组件
   必须存在；其他组件可以为空或
   未定义。如果某个组件关联的分隔符
   没有出现在 URI 引用中，则该组件未定义；path 组件永远不会
   未定义，但它可以为空。

   按第 6.2.2 节和
   6.2.3 节所述对基础 URI 进行规范化是可选的。URI 引用必须先转换为其
   目标 URI，然后才能进行规范化。

      endif;

   伪代码还引用“remove_dot_segments”例程，用于
   解释并移除所引用 path 中特殊的完整路径段
   “.”和“..”。无论 path 是否为相对路径，
   都是在从引用中提取 path 后执行此操作，
   以便在形成目标 URI 之前移除
   任何无效或多余的点段。虽然可以用多种方式完成
   这一移除过程，但这里描述一种使用两个字符串
   缓冲区的简单方法。

   1.  输入缓冲区使用现在已连接的 path
       组件初始化，输出缓冲区初始化为空
       字符串。

   2.  当输入缓冲区非空时，按如下方式循环：

       A.  如果输入缓冲区以“../”或“https://www.rfc-editor.org/rfc/”前缀开头，

       B.  如果输入缓冲区以“/./”或“/.”前缀开头，

           前缀替换为“/”；否则，

       C.  如果输入缓冲区以“/../”或“/..”前缀开头，
           且“..”是完整路径段，则在输入缓冲区中将该
           前缀替换为“/”，并从输出
           缓冲区中移除最后一个段及其前面的“/”（如果有）；否则，

       D.  如果输入缓冲区仅由“.”或“..”组成，则从
           输入缓冲区中移除它；否则，

       E.  将输入缓冲区中的第一个路径段移动到输出
           缓冲区末尾，包括起始的“/”字符（如果
           有）以及后续直到但不包括
           下一个“/”字符或输入缓冲区末尾的所有字符。

   3.  最后，将输出缓冲区作为

5.3.  组件重组

   已解析的 URI 组件可以重新组合以获得相应的
   URI 引用字符串。使用伪代码表示如下：

      result = ""

      if defined(scheme) then
         append scheme to result;
         append ":" to result;
      endif;

      if defined(authority) then
         append "//" to result;
         append authority to result;
      endif;

      append path to result;

      if defined(query) then
         append "?" to result;
         append query to result;
      endif;

      if defined(fragment) then
         append "#" to result;
         append fragment to result;
      endif;

      return result;

   请注意，我们谨慎保留了以下区别：
   一个组件未定义，意味着其分隔符没有
   出现在引用中；而组件为空，则意味着
   分隔符存在，并且其后立即是下一个
   组件分隔符或引用末尾。

   某个段的一部分，则不得移除。

      "/./g"          =  "http://a/g"
      "/../g"         =  "http://a/g"
      "g."            =  "http://a/b/c/g."
      ".g"            =  "http://a/b/c/.g"
      "g.."           =  "http://a/b/c/g.."
      "..g"           =  "http://a/b/c/..g"

   更不常见的是相对引用使用了不必要
   或无意义形式的完整路径段“.”和“..”。

      "https://www.rfc-editor.org/rfc/../g"        =  "http://a/b/g"
      "https://www.rfc-editor.org/rfc/g/."         =  "http://a/b/c/g/"
      "g/./h"         =  "http://a/b/c/g/h"
      "g/../h"        =  "http://a/b/c/h"
      "g;x=1/./y"     =  "http://a/b/c/g;x=1/y"
      "g;x=1/../y"    =  "http://a/b/c/y"

   某些应用程序在将引用与基础 path 合并并移除点段之前，
   未能将引用的 query 和/或
   fragment 组件与 path 组件分离。这种错误很少
   被察觉，因为 fragment 的典型使用不会包含层次
   （“/”）字符，而 query 组件通常也不会在
   相对引用中使用。

      "g?y/./x"       =  "http://a/b/c/g?y/./x"
      "g?y/../x"      =  "http://a/b/c/g?y/../x"
      "g#s/./x"       =  "http://a/b/c/g#s/./x"
      "g#s/../x"      =  "http://a/b/c/g#s/../x"

   某些解析器允许相对
   引用中出现 scheme 名称，前提是它与基础 URI scheme 相同。这被
   认为是先前 partial URI 规范中的一个漏洞
   [RFC1630]。应避免使用这种方式，但为了向后
   兼容仍允许这样做。

      "http:g"        =  "http:g"         ; 对严格解析器
                      /  "http://a/b/c/g" ; 为向后兼容

6.  规范化和比较

   URI 上最常见的操作之一是简单比较：
   在不使用 URI 访问各自资源的情况下，确定两个 URI 是否等价。
   每次访问响应缓存、浏览器检查其历史记录以
   为链接着色，或者 XML 解析器处理命名空间中的标签时，
   都会执行比较。
   网络爬虫和索引引擎经常在比较 URI 之前进行广泛规范化，
   以缩小搜索空间或减少
   请求操作和响应存储的重复。

   URI 比较是为了某个特定目的执行的。为了不同目的
   比较 URI 的协议或实现，在应投入多少
   工作来减少别名标识符方面，
   往往面临不同的设计权衡。本
   节描述可用于比较 URI 的各种方法、
   它们之间的权衡，以及可能
   使用这些方法的应用类型。

6.1.  等价性

   由于 URI 用来标识资源，因此当它们标识同一资源时，
   大概应该认为它们等价。不过，
   这种等价定义在实践中用处不大，因为实现
   除非完全了解或控制两个资源，否则无法比较它们。
   因此，
   URI 等价或差异的判定基于字符串
   比较，并可能辅以 URI 方案定义提供的附加规则。
   我们使用“不同”和
   “等价”术语来描述此类比较可能的结果，
   但等价性存在许多取决于应用程序的不同版本。

   即使可以确定两个 URI 等价，
   URI 比较也不足以确定两个 URI
   是否标识不同资源。例如，两个不同
   域名的所有者可以决定从两个域名提供同一资源，
   从而产生两个不同 URI。因此，比较方法被
   设计为尽量减少假阴性，同时严格避免假
   阳性。

   在测试等价性时，应用程序不应该直接比较
   相对引用；应该先将引用转换为各自的目标 URI
   再比较。当比较 URI 是为了
   选择（或避免）网络操作，例如检索
   表示时，应该从比较中排除 fragment 组件（如果有）。

6.2.  比较阶梯

   实践中使用多种方法测试 URI 等价性。
   这些方法形成一个范围，根据
   所需处理量和假阴性概率降低程度进行区分。
   如上所述，假阴性无法
   完全消除。实践中可以降低其概率，但这种
   降低需要更多处理，并不适用于所有
   应用程序，因为成本可能不合算。

   如果将这一系列比较实践看作阶梯，
   以下讨论将沿阶梯向上，从
   成本低但产生假阴性概率相对较高的实践开始，
   再逐步讨论计算
   成本更高而假阴性风险更低的实践。

6.2.1.  简单字符串比较

   如果两个 URI 作为字符字符串完全相同，
   就可以安全地得出它们等价的结论。这种
   等价测试的计算成本极低，并且广泛用于
   各类应用程序，特别是解析领域。

   测试字符串等价性需要一些基本注意事项。
   此过程经常称为“逐位”或
   “逐字节”比较，这种说法可能会产生误导。测试
   字符串是否相等通常基于对组成字符串的
   字符逐对比较，从第一个字符开始，
   一直进行到两个字符串都耗尽且所有字符都
   相等、遇到一对不相等字符，或者
   一个字符串先于另一个耗尽。

   这种字符比较要求每对字符都处于
   可比较形式。例如，如果一个 URI 以 EBCDIC 编码存储在
   字节数组中，而另一个存储在 Java String 对象
   （UTF-16）中，则直接进行逐位比较会产生
   错误。更准确的说法应该是逐字符
   相等，而不是逐字节或逐位相等。
   实际上，逐字符比较应该在转换为共同字符
   编码后按码位逐一执行。

   URI 别名的生成和使用会导致假阴性。
   无论采用何种比较方法，都可以通过始终以已经
   规范化的形式提供 URI 引用来减少不必要的别名
   （即与应用下述规范化后
   所产生形式相同的形式）。

6.2.2.  基于语法的规范化

   实现可以使用基于本规范所提供定义的
   逻辑来降低假阴性概率。
   这种处理的成本比逐字符
   字符串比较适度更高。例如，采用这种
   方法的应用程序可以合理地认为以下两个 URI 等价：

      example://a/b/c/%7Bfoo%7D
      eXAMPLE://a/./b/../b/%63/%7bfoo%7d

   Web 用户代理（例如浏览器）通常在确定
   缓存响应是否可用时应用这种 URI
   规范化。基于语法的规范化包括
   大小写规范化、百分号编码规范化以及移除
   点段等技术。

6.2.2.1.  大小写规范化

   对所有 URI 而言，百分号编码
   三字符组中的十六进制数字（例如“%3a”和“%3A”）不区分大小写，因此
   应该规范化为使用大写字母 A-F。

   当 URI 使用通用语法组件时，组件
   语法等价规则始终适用；即 scheme 和
   host 不区分大小写，因此应该规范化为
   小写。例如，URI <HTTP://www.EXAMPLE.com/> 与
   <http://www.example.com/> 等价。除非方案特别
   另有定义，否则假定其他通用语法
   组件区分大小写（见第 6.2.3 节）。

6.2.2.2.  百分号编码规范化

   百分号编码机制（第 2.1 节）是其他方面相同的 URI
   之间产生差异的常见来源。除了上述
   大小写规范化问题外，一些 URI 生成器会对
   不需要百分号编码的八位字节进行百分号编码，从而产生
   与其非编码形式等价的 URI。这些 URI 应该
   通过解码任何对应于非保留字符的百分号编码八位字节
   进行规范化，如第 2.3 节所述。

6.2.2.3.  路径段规范化

7.  安全考虑

   URI 本身并不构成安全威胁。不过，由于 URI
   经常被用于提供一组紧凑的网络资源访问
   指令，因此必须谨慎正确解释 URI 内的数据，
   防止这些数据导致非预期访问，
   并避免包含不应以明文
   泄露的数据。

7.1.  可靠性和一致性

   无法保证某个 URI 一旦用于检索
   信息，未来仍能通过该 URI 检索到
   相同信息。也无法保证未来通过该 URI
   检索到的信息在可观察上与过去
   检索到的信息相似。URI 语法并不限制给定
   方案或权威机构如何划分其命名空间，或如何随时间
   维护它。此类保证只能从
   控制该命名空间和相关资源的人获得。特定
   URI 方案可以定义其他语义，例如名称持久性，
   如果该方案要求所有命名机构都遵守这些语义。

7.2.  恶意构造

   有时可以构造 URI，使尝试执行
   看似无害的幂等操作，例如
   检索表示，实际上会导致可能造成损害的
   远程操作。不安全的 URI 通常通过
   指定不同于相关网络协议所保留端口号的
   端口号来构造。客户端无意间连接到运行
   不同协议服务的站点，而 URI 中的数据包含
   指令，这些指令按照另一协议进行解释时，
   会导致意外操作。此类滥用的常见示例是
   使用端口组件为
   “25”的基于协议方案，从而欺骗用户代理软件通过 SMTP 服务器发送非预期
   或冒充消息。

   应用程序应该阻止解引用指定
   “知名端口”范围（0 - 1023）内 TCP
   端口号的 URI，除非用于解引用该 URI 的协议
   与该知名端口预期使用的协议兼容。尽管 IANA 维护
   知名端口注册表，但应用程序应该使这种
   限制可由用户配置，以避免阻止新服务的
   部署。

7.3.  后端转码

   当 URI 被解引用时，其中的数据通常同时由
   用户代理和一个或多个服务器解析。例如，在 HTTP 中，
   典型用户代理会将 URI 解析为五个主要组件，
   访问 authority 的服务器，并向其发送
   authority、path 和 query 组件中的数据。典型服务器会获取
   这些信息，将 path 解析为段并将 query 解析为
   键/值对，然后调用实现特定处理器
   响应请求。因此，对于
   将 URI 作为整体或拆分为独立组件处理的服务器实现，
   一个常见安全问题是正确解释
   该 URI 中字符和百分号编码所表示的八位字节数据。

   百分号编码的八位字节必须在
   解引用过程的某个阶段进行解码。应用程序必须先将 URI 拆分为
   组件和子组件，然后再解码八位字节，
   否则解码后的八位字节可能被误认为分隔符。
   对 URI 内数据进行安全检查应该在
   解码八位字节之后执行。不过请注意，“%00”百分号编码
   (NUL) 可能需要特殊处理，如果
   应用程序不期望在组件中接收原始数据，则应该拒绝它。

   当 URI path 解释过程
   涉及使用后端文件系统或相关系统
   函数时，应该格外小心。文件系统通常会赋予
   特殊字符（例如“/”、“\”、“:”、“[”和“]”）
   以及特殊设备名称（例如“.”、“..”、“...”、“aux”、
   “lpt”等）操作含义。在某些情况下，仅仅测试
   这类名称是否存在就会导致操作系统暂停或调用无关的
   系统调用，从而带来有关
   拒绝服务和非预期数据传输的严重安全问题。
   本规范不可能列出所有这类重要
   字符和设备名称。实现者应该研究
   可能连接到其应用程序的存储设备类型的
   保留名称和字符，并相应限制
   从 URI 组件获得的数据的使用。

7.4.  罕见 IP 地址格式

   虽然 IPv4address 的 URI 语法只允许常见的
   IPv4 地址字面量点分十进制形式，但许多
   处理 URI 的实现使用依赖平台的系统例程，
   例如 gethostbyname() 和 inet_aton()，将字符串
   字面量转换为实际 IP 地址。不幸的是，这类系统例程
   经常允许并处理比
   第 3.2.2 节所述更广泛的格式集合。

   例如，许多实现允许由三个
   数字组成的点分形式，其中最后一部分被解释为 16 位数值
   并放入网络地址最右侧两个字节（例如
   B 类网络）。类似地，由两个数字组成的点分形式意味着
   最后一部分被解释为 24 位数值并放入
   网络地址最右侧三个字节（A 类）；而
   单个数字（不含点）被解释为 32 位数值并
   直接存入网络地址。使情况更加
   混乱的是，一些实现允许每个点分部分按照 C
   语言规定解释为十进制、八进制或十六进制
   （即前导 0x 或 0X 表示十六进制；前导 0
   表示八进制；否则数字解释为十进制）。

   由于平台实现之间存在差异，这些额外 IP 地址格式
   不允许出现在 URI 语法中。不过，如果应用程序尝试
   根据字符串字面量形式的 IP 地址过滤
   对资源的访问，它们可能成为安全问题。
   如果执行这种过滤，应将字面量转换为
   数值形式，并根据数值进行过滤，而不是根据
   字符串形式的前缀或后缀进行过滤。

7.5.  敏感信息

   URI 生成器不应该提供包含预期保密的用户名或
   密码的 URI。URI 经常
   由浏览器显示、以明文书签存储，并由
   用户代理历史记录和中间应用程序（代理）记录。
   已弃用 userinfo 组件中出现的密码，
   除极少数“password”参数旨在公开的情况外，
   应将其视为错误（或直接忽略）。

7.6.  语义攻击

   由于 userinfo 子组件很少使用，并且在
   authority 组件中出现在 host 之前，因此可以用它构造
   一个旨在误导人类用户的 URI，使其看起来标识的是某个
   （可信的）命名权威机构，而实际上标识的是隐藏在干扰信息后面的另一个
   权威机构。例如



Berners-Lee 等人             标准路线                       [第 45 页]

RFC 3986                   URI 通用语法                   2005 年 1 月


      ftp://cnn.example.com&story=breaking_news@10.0.0.1/top_story.htm

   可能会使人类用户认为 host 是“cnn.example.com”，
   而实际上是“10.0.0.1”。请注意，具有误导性的 userinfo
   子组件可能比上面的示例长得多。

   像上面这样的误导性 URI，是针对用户对
   URI 含义的先入观念发起的攻击，而不是针对
   软件本身的攻击。用户代理可以通过在呈现 URI 时
   区分不同组件来降低此类攻击的影响，例如
   如果存在 userinfo，则使用不同颜色或色调来
   呈现它，尽管没有万全之策。有关
   基于 URI 的语义攻击的更多信息可见 [Siedzik]。

                 / path-rootless

   由于“首次匹配优先”算法与 POSIX 正则表达式使用的
   “贪婪”
   消歧方法相同，因此使用正则表达式解析
   URI 引用可能包含的五个组件是自然且常见的做法。

   以下一行是用于将
   格式正确的 URI 引用拆分为其组件的正则表达式。



Berners-Lee 等人             标准路线                       [第 50 页]

RFC 3986                   URI 通用语法                   2005 年 1 月


      ^(([^:/?#]+):)?(//([^/?#]*))?([^?#]*)(\?([^#]*))?(#(.*))?
       12            3  4          5       6  7        8 9

   上面第二行中的数字仅用于帮助阅读；
   它们表示每个子表达式（即每对
   括号）的引用点。我们将子表达式
   <n> 匹配的值称为 $<n>。例如，将上述表达式与

      http://www.ics.uci.edu/pub/ietf/uri/#Related

   匹配，会得到以下子表达式匹配结果：

      $1 = http:
      $2 = http
      $3 = //www.ics.uci.edu
      $4 = www.ics.uci.edu
      $5 = /pub/ietf/uri/
      $6 = <undefined>
      $7 = <undefined>
      $8 = #Related
      $9 = Related

   其中 <undefined> 表示该组件不存在，如
   上述示例中的 query 组件。因此，我们
   可以确定五个组件的值如下：

      scheme    = $2
      authority = $4
      path      = $5
      query     = $7
      fragment  = $9

   反过来，我们可以使用第 5.3 节的算法从
   URI 引用的组件重新创建 URI 引用。

附录 C.  在上下文中界定 URI

   URI 经常通过不能为其解释提供
   清晰上下文的格式传输。例如，URI 经常
   包含在纯文本中；示例包括通过电子邮件、
   USENET 新闻以及印刷纸张发送的文本。在这种情况下，
   必须能够将 URI 与文本其余部分区分开来，
   尤其是与可能被误认为
   URI 一部分的标点符号区分开。

   实践中，URI 以多种方式界定，但通常
   位于双引号“http://example.com/”、尖括号
   <http://example.com/> 中，或者仅使用空白字符：



Berners-Lee 等人             标准路线                       [第 51 页]

RFC 3986                   URI 通用语法                   2005 年 1 月


      http://example.com/

   这些包围符不构成 URI 的一部分。

   在某些情况下，可能必须添加额外空白字符（空格、换行符、制表符等），
   以便将很长的 URI 跨行
   分割。提取 URI 时应该忽略这些空白字符。

   连字符（“-”）字符之后不应该引入空白字符。
   由于某些排版程序和打印机在换行时可能会（错误地）在
   行末引入连字符，因此，对于包含
   紧跟在连字符之后的换行符的 URI，其解释器应该忽略换行符周围的所有
   空白字符，并且应该意识到该连字符
   可能实际上属于 URI，也可能并不属于 URI。

   特别建议在每个 URI 周围使用 <> 尖括号，
   作为包含嵌入空白字符的引用的界定方式。

   前缀“URL:”（后面可以带空格，也可以不带）过去曾被
   推荐用来帮助区分 URI 与其他用括号包围的
   标识符，但实践中并不常用，现在也
   不再推荐。

   为提高健壮性，接受用户输入 URI 的软件应该尝试
   识别并移除分隔符和嵌入的空白字符。

   例如，文本

      是的，Jim，我在“http://www.w3.org/Addressing/”下找到了它，
      不过你大概也可以从 <ftp://foo.example.
      com/rfc/> 获取它。请注意 <http://www.ics.uci.edu/pub/
      ietf/uri/historical.html#WARNING> 中的警告。

   包含以下 URI 引用：

      http://www.w3.org/Addressing/
      ftp://foo.example.com/rfc/
      http://www.ics.uci.edu/pub/ietf/uri/historical.html#WARNING

附录 D.  相对于 RFC 2396 的变更

D.1.  新增内容

   新增了 URI 的 ABNF 规则，以对应
   该术语的一种常见用法：带可选 fragment 的绝对 URI。

   IPv6（及更高版本）字面量已加入 authority 组件 host 部分
   可能使用的标识符列表，如
   [RFC2732] 所述，同时将“[”和“]”加入
   保留集合，并加入版本标志以预留未来版本的 IP
   字面量。现在规定方括号在
   authority 组件内属于保留字符，并且除用作
   host 中 IP 字面量的分隔符外不得使用。为了在不
   改变 path、query 和 fragment 组件技术定义的情况下
   完成此变更，这些规则被重新定义为直接
   指定允许的字符。

   由于 [RFC2732] 将 IPv6 字面
   地址的定义交由 [RFC3513]，而后者遗憾地缺少
   IPv6address 的 ABNF 描述，因此我们为 IPv6address 创建了一条新的 ABNF 规则，
   与[RFC3513] 第 2.2 节定义的文本表示相匹配。
   同样，IPv4address 的定义也经过改进，以便
   将每个十进制八位字节限制在 0-255 范围内。

   关于 URI 规范化和比较的第 6 节已经
   完全重写并扩展，其中采用了 Tim Bray 的意见以及
   W3C 技术架构组中的讨论成果。

   [RFC2234] 的 ABNF。此变更要求原来

   ABNF 已修正，以允许 path 组件为空。
   这也允许 absolute-URI 在
   “scheme:”之后不包含任何内容，实践中“dav:”命名空间
   [RFC2518] 和许多 WWW
   浏览器实现内部使用的“about:”方案都存在这种情况。
   authority 和 path 之间边界的歧义
   已通过使用五条独立 path 匹配规则消除。

   使用通用语法的基于注册表的命名权威机构现在
   定义在 host 规则中。此变更使当前
   实现能够符合规范，因为其中提供的任何名称都只是被传给
   本地名称解析机制。
   它还消除了在此重新规定 DNS 名称
   格式的必要。此外，它允许 host 组件包含
   百分号编码八位字节，这是使
   国际化域名能够在 URI 中提供、在 URI
   处理之上的应用层以其原生字符编码进行处理，
   并以 UTF-8 字符编码的注册名称形式传递给 IDNA 库所必需的。
   server、hostport、hostname、
   domainlabel、toplabel 和 alphanum 规则已被删除。

   [RFC2396] 的相对引用解析算法已
   在本次修订中使用伪代码重写，以提高清晰度并
   修复以下问题：

   o  判断 URI 引用是否为同文档
      引用的过程已与 URI 解析器解耦，以一种与已部署 URI 处理实现的
      内部架构一致的方式简化了
      应用程序中的 URI 处理接口。现在的判断基于

      基础 URI 进行比较，而不是根据引用本身的格式。

      “同文档”引用，相比
      RFC 2396 给出的规则尤其如此，特别是在使用规范化减少
      别名时。不过，它不会改变现有
      同文档引用的状态。

   o  将 path 合并例程拆分为两个例程：merge，用于
      描述基础 URI path 与相对路径
      引用的组合；remove_dot_segments，用于描述如何从组合后的 path 中移除
      特殊的“.”和“..”段。
      remove_dot_segments 算法现在应用于所有 URI 引用
      path，以匹配常见实现并改进
      实践中的 URI 规范化。此变更只会影响
      异常引用以及基础 URI 具有非分层 path 的同方案引用的
      解析。
